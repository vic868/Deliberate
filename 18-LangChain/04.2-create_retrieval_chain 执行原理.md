# create_retrieval_chain 执行原理（源码级）

> [!abstract] 一句话
> 它**不是 Chain 类，也不是执行函数**，而是一个**工厂函数**：返回一条纯 LCEL `Runnable`。真正的执行发生在你调用 `.invoke()` 时。函数体只做一件事——用**两次 `RunnablePassthrough.assign()`** 往输入字典里依次追加 `context` 和 `answer` 两个键。

---

## 1. 源码本体（约 10 行）

`langchain_classic/chains/retrieval.py`（V1.0）与 v0.3 的 `langchain/chains/retrieval.py` 实现一致，只是包路径变了：

```python
from typing import Any, Dict, Union
from langchain_core.retrievers import BaseRetriever, RetrieverOutput
from langchain_core.runnables import Runnable, RunnablePassthrough

def create_retrieval_chain(
    retriever: Union[BaseRetriever, Runnable[dict, RetrieverOutput]],
    combine_docs_chain: Runnable[Dict[str, Any], str],
) -> Runnable:
    """Create retrieval chain that retrieves documents and then passes them on."""
    if not isinstance(retriever, BaseRetriever):
        retrieval_docs: Runnable[dict, RetrieverOutput] = retriever
    else:
        retrieval_docs = (lambda x: x["input"]) | retriever

    retrieval_chain = (
        RunnablePassthrough.assign(
            context=retrieval_docs.with_config(run_name="retrieve_documents"),
        ).assign(answer=combine_docs_chain)
    ).with_config(run_name="retrieval_chain")
    return retrieval_chain
```

**注意它没有任何 `if 检索失败`、没有任何 LLM 调用、没有任何循环**——全部是 Runnable 的声明式组装。`.with_config(run_name=...)` 只是给 LangSmith 追踪起名，不影响逻辑。

## 2. 三个关键机制

### 2.1 `RunnablePassthrough.assign()`：透传 + 追加

`RunnablePassthrough()` 单独用是「原样返回整个输入」；而 `.assign(**kwargs)` 返回的是 `RunnableAssign`（可理解为 `RunnableParallel` + 合并）：

1. 复制输入 dict（**原有键全部保留**）；
2. 并行执行 `kwargs` 里每个 Runnable，入参都是**同一个原始 dict**；
3. 把各结果按 key 合并进副本并返回。

所以两次 `.assign()` 是**累积**，不是重建：

| 阶段 | dict 内容 |
|---|---|
| 输入 | `{"input": "张成刚是谁？"}` |
| 第一次 assign 后 | `{"input": "...", "context": [Document, ...]}` |
| 第二次 assign 后 | `{"input": "...", "context": [Document, ...], "answer": "..."}` |

### 2.2 `retriever` 的两种形态（那个 `isinstance` 分支）

| 传入的 retriever | 处理方式 | 原因 |
|---|---|---|
| `BaseRetriever` 子类（如 `VectorStoreRetriever`） | `(lambda x: x["input"]) \| retriever` | 检索器只吃 **str**，得先把 dict 投影成 `x["input"]` 这个字符串 |
| 其他 `Runnable[dict, RetrieverOutput]` | **原样使用**，整个 dict 直接传进去 | 它自己会读 dict，可以拿到 `input`、`chat_history` 等全部字段 |

> [!tip] 第二条分支就是会话式 RAG 的入口
> `create_history_aware_retriever(...)` 返回的是一个 `Runnable`（内部是 `RunnableBranch`），不是 `BaseRetriever`。把它传给 `create_retrieval_chain` 时走第二条分支，于是它能拿到 `chat_history` 做问题改写。这也是「`RunnableBranch`」出现的地方——它属于 history-aware retriever，**不在 `create_retrieval_chain` 内部**（这点容易记混）。

### 2.3 `.assign(answer=combine_docs_chain)` 吃的是整个 dict

第二次 assign 传给 `combine_docs_chain` 的不是「检索结果」，而是**已含 `input` + `context` 的完整字典**。所以 `create_stuff_documents_chain` 的 prompt 才能同时拿到 `{input}` 和 `{context}`。返回值（默认经 `StrOutputParser` 变成 `str`）被写入 `answer` 键。

## 3. 逐帧推演（对应讲义 §7 的调用）

```python
resp = chain2.invoke({"input": "张成刚是谁？"})
```

| 帧 | 发生了什么 | 数据形态 |
|---|---|---|
| 0 | `.invoke()` 触发，`RunnableAssign` 收到输入 dict | `{"input": "张成刚是谁？"}` |
| 1 | `retrieval_docs` = `(λx: x["input"]) \| retriever`：`"张成刚是谁？"` 被 embedding → 向量库相似度检索 | `str → List[Document]` |
| 2 | 第一次 `assign` 把上一步结果写进 `context` | `{"input", "context": [Document...]}` |
| 3 | 第二次 `assign` 把**整个 dict** 交给 `chain1`（stuff 文档链） | dict 入 |
| 4 | `chain1` 返回 `str`，写入 `answer` | `{"input", "context", "answer"}` |
| 5 | 外层返回，`resp["answer"]` 是答案，`resp["context"]` 是**原始 Document 列表** | 可溯源 |

> [!important] 为什么 `resp["context"]` 还是 `List[Document]`，不是拼好的长字符串？
> 因为 `combine_docs_chain` 是**子 Runnable**，它收到的 dict 是外层传进去的一份数据；它在自己内部把 `context` 覆盖成字符串，但**不会回写外层的字典**。外层的 `context` 停留在帧 2 的 `List[Document]`。这正是 `create_retrieval_chain` 保留 `context` 用于溯源的设计意图。

## 4. 子链 `create_stuff_documents_chain` 内部做了什么

```python
# langchain_classic/chains/combine_documents/stuff.py（简化）
def create_stuff_documents_chain(llm, prompt, *, output_parser=None,
                                 document_prompt=None, document_separator="\n\n",
                                 document_variable_name="context"):
    _validate_prompt(prompt)                                  # 校验 prompt 必须含 {context}
    _document_prompt = document_prompt or DEFAULT_DOCUMENT_PROMPT   # "{page_content}"
    _output_parser = output_parser or StrOutputParser()

    def format_docs(inputs: dict) -> str:
        return document_separator.join(
            format_document(doc, _document_prompt) for doc in inputs[document_variable_name]
        )

    return (
        RunnablePassthrough.assign(**{document_variable_name: format_docs})  # List[Document] → str
        | prompt | llm | _output_parser
    ).with_config(run_name="stuff_documents_chain")
```

三段动作：

1. **拍平**：把 `context` 里的每个 `Document` 用 `format_document` 格式化（默认只取 `page_content`），用 `\n\n` 拼成一个字符串，**就地覆盖 `context` 键**；
2. **渲染**：`prompt` 用这份 dict 填 `{context}` / `{input}` 等变量 → `PromptValue`；
3. **生成 + 解析**：`llm` → `AIMessage` → `StrOutputParser` → `str`。

> [!note] 讲义 §7 那个特殊写法
> 讲义把 `("{assistant}", "{context}")` 放在 assistant 角色里。功能上没问题——`{context}` 是 prompt 变量，放在哪个角色只影响模型怎么理解这段话；更常见的是放进 system 或 human 消息。另外 `document_prompt` 可以引用 metadata 里的键，例如 `PromptTemplate.from_template("[{source}] {page_content}")`，能顺带把出处喂给模型。

## 5. 与手写 LCEL 的本质区别（讲义 §6 vs §7）

```python
# A. 讲义 §6 手写（RunnableParallel）
chain = (
    {"question": RunnablePassthrough(), "context": docs_find}
    | prompt | client
)
chain.invoke("请介绍一下猫")      # 输入是 str，输出是 AIMessage

# B. create_retrieval_chain（两次 assign）
chain2 = create_retrieval_chain(retriever, chain1)
chain2.invoke({"input": "张成刚是谁？"})   # 输入是 dict，输出是 dict
```

| 维度 | A 手写 `RunnableParallel` | B `create_retrieval_chain` |
|---|---|---|
| dict 构造方式 | **重建**：只保留字典字面量里写的键 | **累积**：`assign` 保留全部原始输入键 |
| 输入 | 字符串（或一个 dict，取决于写法） | 约定 `{"input": ...}` |
| 输出 | `AIMessage`（可再接 parser） | dict：`input` / `context` / `answer` |
| 检索结果是否留在输出 | 否，被 prompt 消费掉 | **是**，`context` 保留 `List[Document]`，便于溯源/评估 |
| 检索器包装 | `docs_find` 需手工 `RunnableLambda` | 自动：`(λx: x["input"]) \| retriever` |
| 文档 → 字符串 | 自己写 `format_docs` | 由 `chain1` 负责 |
| 适用场景 | 教学、快速原型、完全自定义 | 标准 2-Step RAG、需要看检索来源 |

**等价手写版（≈6 行，推荐新项目直接用）**：

```python
chain = (
    RunnablePassthrough.assign(context=(lambda x: x["input"]) | retriever)
    .assign(answer=chain1)
)
# 或者不需要保留 context 时，更简洁：
chain = {"context": (lambda x: x["question"]) | retriever,
         "question": RunnablePassthrough()} | prompt | client | StrOutputParser()
```

## 6. 常见误解 / 坑

| 误解 | 实际情况 |
|---|---|
| 「调用 `create_retrieval_chain` 就会去查库」 | 它只**组装并返回 Runnable**，检索发生在 `.invoke()` 时；构造阶段不产生任何 IO |
| 「它是老式 `Chain` 子类」 | 不是，返回的是纯 LCEL `Runnable`（`RunnableAssign` / `RunnableBinding`），所以 `.invoke/.batch/.stream/.astream_events` 全套可用 |
| 「输入键叫什么都行」 | 第一个分支硬编码 `x["input"]`。用 `{"question": ...}` 会 `KeyError`；要换键就走第二条分支，传一个自己写的 `Runnable[dict, ...]` |
| 「`resp["context"]` 是拼好的字符串」 | 是 `List[Document]`；字符串只存在于 `chain1` 内部那份副本里 |
| 「prompt 里可以没有 `{context}`」 | `create_stuff_documents_chain` 的 `_validate_prompt` 会校验，缺 `context` 直接报错（可用 `document_variable_name` 改名） |
| 「自动带 `chat_history`」 | 早期版本实现里 assign 过 `chat_history=lambda x: x.get("chat_history", [])`，当前实现已移除，但 docstring 仍保留这段说明。**若 prompt 用了 `MessagesPlaceholder("chat_history")`，调用时自己传**，或改用 `create_history_aware_retriever` |
| 「V1.0 里没有这个函数了」 | 在，只是从 `langchain.chains` 挪到 **`langchain_classic.chains`**；RAG 这一章 V0.3 → V1.0 逐字未改，见 [[08-Day03 课堂复盘 RAG 实战与工具中间件]] |

---

## 7. 一句话收束

> **`create_retrieval_chain` = 把「检索 → 生成」表达成两次字段追加。`assign` 保证原始输入不丢、中间产物（`context`）留在输出里，而子链内部对 `context` 的拍平只是它自己的副本——这就是它既能出答案、又能溯源的原因。**
