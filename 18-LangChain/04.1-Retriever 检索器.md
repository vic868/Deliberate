# Retriever 检索器（RAG 专题）

> [!abstract] 一句话
> **检索器 = 向量库的包装器**。它把「怎么查」从「查什么」里剥出来：底层换成 Milvus 或 FAISS，查询代码一个字不改。这和 `ChatOpenAI` 屏蔽各家 Chat API 差异是同一个思路。

> [!info] 为什么单独拆出来
> 原文档里检索相关的知识散落在 §5.1（为什么需要）、§5 前半（向量库直查）、§6（LCEL 里的坑）、§7（两种链路）、§8（排查清单）。本篇把它们收拢成一条完整线索。

---

## 1. 讲义原问题：向量库本来就能查，为什么还要检索器？

> 讲义原话：「看起来检索器可有可无，因为向量库本身就提供了检索功能，为何 LangChain 中还要提供一个检索器呢？」

直接调向量库，你得懂 **Chroma / FAISS / Pinecone / Milvus** 各自的：

- 查询语法与参数名（`similarity_search` / `max_marginal_relevance_search` / …）
- 连接管理、鉴权、异常处理
- 返回结构与分数口径

LangChain 用 **`VectorStoreRetriever`** 把这些差异吃掉，只暴露一个统一接口：

```python
retriever = vector_store.as_retriever()   # 返回 VectorStoreRetriever 实例
docs = retriever.invoke("狸花猫")          # → list[Document]
```

### 1.1 三层关系

```mermaid
flowchart TB
    Q["用户问题 str"] --> R
    subgraph RET["Retriever 层 · 统一接口"]
        R["VectorStoreRetriever<br/>invoke / batch / stream"]
    end
    R -->|委托查询| V
    subgraph VS["VectorStore 层 · 各家实现"]
        V["Chroma / FAISS / Milvus / Pinecone<br/>similarity_search / MMR / 阈值检索"]
    end
    V -->|list[Document]| C["context → Prompt → LLM"]
    R -.作为 Runnable 直接进 LCEL.-> C
```

**四个理由**，按重要性排：

| # | 理由 | 具体收益 |
|---|---|---|
| 1 | 统一接口 | 换向量库只改 `from_documents(...)` 一行，查询与链路代码不动 |
| 2 | 是 Runnable | 可直接作为 `RunnableParallel` 的一个值参与 LCEL 编排（`invoke` / `batch` / `stream` 都有） |
| 3 | 可组合 | 多个检索器可以用 `EnsembleRetriever` 融合，形成语义 + 关键词混合检索 |
| 4 | 关注点分离 | 检索策略（`search_type` / `k` / 过滤）与业务链路解耦，调参不碰业务代码 |

## 2. 向量库直查 vs 检索器（别混用）

原文档 §5 前半其实演示的是**向量库自带查询**，§5.1 之后才切到检索器：

```python
from langchain_chroma import Chroma
from langchain_core.runnables import RunnableLambda

vector_store = Chroma.from_documents(documents=documents, embedding=llm_embeddings)

# ── A. 向量库直查（调试用，绑死在 Chroma 上） ──
vector_store.similarity_search("狸花猫")
vector_store.similarity_search_with_score("狸花猫")     # Chroma 默认 L2，分数越小越相似

docs_find = RunnableLambda(vector_store.similarity_search).bind(k=1)  # 手工包成 Runnable
docs_find.batch(["狸花猫", "海豚"])                     # 批量查

# ── B. 检索器（生产用，屏蔽底层） ──
retriever = vector_store.as_retriever()
retriever.invoke("狸花猫")
```

| 维度 | `vector_store.similarity_search` | `retriever.invoke` |
|---|---|---|
| 层次 | 存储层 API | 抽象层 Runnable |
| 换库 | 查询代码跟着改 | 不改 |
| 能否直接进 LCEL | 不能，得用 `RunnableLambda` 手工包装 | **能**，本身就是 Runnable |
| 批量 | 自己写或 `.batch` 包装 | `.batch([...])` 原生支持 |
| 能否被融合 | 不方便 | 可作为 `EnsembleRetriever` 的一个成员 |

> [!important] 这是理解 §6 那个坑的钥匙
> `docs_find` 是手工把「库方法」包成的 Runnable；`retriever` 天然就是 Runnable。所以讲义里「必须把值写成 Runnable」这条规则，**对检索器来说是自动满足的**。

## 3. 常用检索参数（延伸 · 官方文档，讲义未展开）

`as_retriever()` 的两个主要参数：`search_type` 决定调底层哪个方法，`search_kwargs` 把参数透传给这个方法。

```python
retriever = vector_store.as_retriever(
    search_type="similarity",                 # 默认
    search_kwargs={"k": 4},                   # 默认 k=4
)
```

| `search_type` | 含义 | 配套 `search_kwargs` |
|---|---|---|
| `similarity`（默认） | 相似度 top-k | `k` |
| `mmr` | 最大边际相关性，返回「相关且彼此不重复」的结果，缓解信息冗余 | `k`、`fetch_k`（候选池，默认 20）、`lambda_mult`（0 最大多样性 / 1 最大相关性，默认 0.5） |
| `similarity_score_threshold` | 只返回相关性达标的结果 | `score_threshold`、`k` |

`search_kwargs` 里还能用 `filter` 按 **Document 的 metadata** 过滤，例如 `{"filter": {"source": "鱼类宠物文档"}}`——这正好把 §一 里「metadata 可回溯出处」用起来，实现按来源/章节限定检索范围。

> [!warning] 分数口径别串台
> `similarity_search_with_score()` 在 Chroma 下返回的是 **L2 距离（越小越相似）**；而 `similarity_score_threshold` 的 `score_threshold` 用的是向量库内部的**相关性分（越大越相关）**。不要把前者的数值直接拿来当后者的阈值调。
>
> 本节属课外补充，讲义 P35–P45 只演示了 `as_retriever()` 无参形式与 `bind(k=1)`；参数细节以所装版本的官方文档为准：https://python.langchain.com/docs/how_to/vectorstore_retriever/

## 4. 检索器在链里的两种接法

### 4.1 LCEL（V1.0 推荐）——检索器直接当 `context` 的值

```python
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser

prompt = ChatPromptTemplate.from_template(
    "仅使用提供的上下文回答问题，不知道就说不知道。\n问题：{question}\n上下文：{context}"
)

chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | client
    | StrOutputParser()
)
chain.invoke("请介绍一下猫")
```

- 字典字面量 → `RunnableParallel`：`question` 原样透传，`context` 由检索器并行查出。
- `retriever` 无需任何包装，因为它是 Runnable；这正是 §2 表格里 B 方案的价值。
- `RunnablePassthrough()` 不可省：定义链时还不知道用户要问什么。详见 [[03.3-RunnablePassthrough]] / [[03.2-RunnableParallel]]。

> [!note] 讲义 §6 那句 warning 怎么读
> 讲义写：「直接把 `docs_find`（一个 Runnable）塞进 `context` 是行不通的」，但紧接着的示例代码正是 `{"question": RunnablePassthrough(), "context": docs_find} | prompt | client`。
> 两句合起来要表达的真实规则是：**`context` 的值必须是 Runnable 或可调用对象**（因为字典会变成 `RunnableParallel`），不能是「已经查好的 Document 列表」、`vector_store.similarity_search(...)` 的返回值，或一个没被包装的裸方法。`docs_find` 因 `RunnableLambda` 包装过所以可用；`retriever` 天生可用。按「值必须是 Runnable」理解就不会自相矛盾。

### 4.2 classic 链路（讲义 §7 原写法）

```python
from langchain_classic.chains.combine_documents import create_stuff_documents_chain
from langchain_classic.chains.retrieval import create_retrieval_chain

system_prompt = "您是问答任务的助理。使用以下检索到的上下文来回答问题。如果你不知道答案，就说你不知道。"
prompt_template = ChatPromptTemplate.from_messages([
    ("system", system_prompt),
    ("assistant", "{context}"),   # 讲义写法：把检索结果放在 assistant 消息里
    ("human", "{input}"),
])

chain1 = create_stuff_documents_chain(client, prompt_template)  # 文档 → stuff 进 prompt
chain2 = create_retrieval_chain(retriever, chain1)              # 检索 → 文档链

resp = chain2.invoke({"input": "张成刚是谁？"})
print(resp["answer"])     # 返回 dict：input / context / answer
```

| 项目 | 说明 |
|---|---|
| `create_stuff_documents_chain` | 把检索到的 `Document[]` 塞进 `{context}`，交给 LLM |
| `create_retrieval_chain` | 用 `retriever` 先查，再把结果喂给文档链 |
| 输入键 | 约定为 `input`（LCEL 里可自定义） |
| 输出 | dict，`answer` 是答案，`context` 保留检索到的原文便于溯源 |
| V1.0 路径 | 从 `langchain.chains` 移到 **`langchain_classic`**；新项目优先用 4.1 的 LCEL 写法 |

> [!tip] 一个稳定的版本结论
> 据 [[08-Day03 课堂复盘 RAG 实战与工具中间件]] 的 V0.3/V1.0 逐页对比，**检索这一页（V1.0 P11 / V0.3 P21）两版完全一致**。所以本节的检索知识跨版本通用，唯一要留意的就是 import 路径。

## 5. 不止一种检索器（vault 内延伸）

[[08-Day03 课堂复盘 RAG 实战与工具中间件]] §4.2 补齐了课件里的四种创建方式，正好对应 04 末尾「往哪走」提到但没展开的**混合检索**：

```python
retriever_faiss  = FAISS.from_texts(texts, embeddings).as_retriever()   # 语义，纯文本建库
retriever_chroma = Chroma.from_documents(docs, embeddings).as_retriever() # 语义，Document 建库
retriever_bm25   = BM25Retriever.from_texts(texts)                       # 关键词，不依赖 embedding
ensemble = EnsembleRetriever(retrievers=[retriever_faiss, retriever_bm25], weights=[0.7, 0.3])
```

| 类型 | 擅长 | 短板 |
|---|---|---|
| 向量检索（FAISS / Chroma / Milvus） | 语义相近、改写过的问法 | 专有名词、型号、编号可能不准，依赖 embedding 质量 |
| BM25 关键词检索 | 精确术语、型号、编号、人名 | 同义词、语义扩展无能为力 |
| `EnsembleRetriever` 混合 | 两者互补 | `weights` 需结合各检索器得分量级调，默认等权不等于最优 |

> 依赖：`rank_bm25` / `faiss-cpu`；V1.0 下 `EnsembleRetriever` 的 import 路径以当前版本文档为准。

## 6. 检索质量排查清单

按「先数据、再切分、再模型、最后检索策略」的顺序排，越靠前影响越大：

| 现象 | 排查顺序 |
|---|---|
| 结果牛头不对马嘴 | ① `bs4.SoupStrainer` 是否圈对了正文 → ② `chunk_size` / `chunk_overlap` 是否合适 → ③ embedding 模型是否适配中文/领域 → ④ `k` 是否过大或过小 |
| 结果高度重复 | 换 `search_type="mmr"`，调 `fetch_k` / `lambda_mult` |
| 需要限定范围 | `search_kwargs={"filter": {...}}` 用 metadata 过滤 |
| 精确词（编号 / 人名）查不准 | 叠加 BM25，走 `EnsembleRetriever` 混合检索 |
| 分数判断反了 | Chroma 默认 L2，**越小越相似**；threshold 口径不同（见 §3 warning） |
| 换库要改一堆代码 | 统一走 `as_retriever()`，别在业务代码里直调各家 API |
| `context` 没被真正执行 | 值必须是 Runnable：`retriever` 或 `RunnableLambda(...)`，配合 `RunnablePassthrough` 组成 `RunnableParallel` |

## 7. 一句话收束

> **VectorStore 负责「存得下、算得动」，Retriever 负责「统一查、可编排」。** 因为它是 Runnable，才能被 `RunnableParallel` 并行调度、被 `EnsembleRetriever` 组合、被 Agent 当工具调用——这是向量库直查给不了的。
