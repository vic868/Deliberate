## 一、SQL 调优实战

### 1.1 索引（深挖级）

| 问题 | 得分骨架 |
|---|---|
| B+ 树为什么适合做索引 | 矮胖（3-4 层存千万级）、非叶子只存键（扇出大）、**叶子成链表支持范围查询**；B 树数据分散各层，范围查询要回旋 |
| 聚簇 vs 二级索引 | 聚簇叶子存整行；二级索引叶子存主键 → **回表** |
| 覆盖索引 | 查询列全在索引里 → 免回表（Extra: `Using index`） |
| 最左前缀 | 联合索引 `(a,b,c)` 从左连续匹配；**范围查询后的列失效** |
| 索引下推 ICP | 5.6+，引擎层先过滤（减少回表），Extra: `Using index condition` |
| 索引失效 8 场景 | 函数/运算、隐式类型转换、`like '%x'`、`or` 一侧无索引、`!=`/`not in`、最左前缀断裂、字符集不一致、优化器判全表更快 |
| 索引设计原则 | 区分度高、覆盖 where/order by/join；**别建太多**（写放大）；联合索引顺序按"等值在前、范围在后" |
| 前缀索引 | 长字符串取前 N 字符，省空间但**不能用于覆盖索引** |

### 1.2 慢查询定位与优化

**标准流程（面试按这个说）**
1. 开慢查询日志（`slow_query_log`、`long_query_time`）
2. `mysqldumpslow` / `pt-query-digest` 聚合出 TOP SQL
3. `explain` 看执行计划：`type`、`key`、`rows`、`filtered`、`Extra`
4. 优化：加/改索引 → 改写 SQL → 减少数据量
5. 回归验证 + 加监控

**`explain` 关键列**

| 列 | 关注点 |
|---|---|
| `type` | system > const > eq_ref > ref > range > index > **ALL（要警惕）** |
| `key` | 实际用的索引，为 NULL 说明没走索引 |
| `rows` | 预估扫描行数 |
| `Extra` | `Using index`（好）、`Using filesort`（要优化）、`Using temporary`（要优化） |

**常见优化手法**
- **深分页**：游标法（`where id > last_id limit 10`）或延迟关联
- **大事务拆分**：减少锁持有时间、避免主从延迟
- **join 优化**：小表驱动大表、被驱动表关联列必须有索引
- **子查询**：改写成 join（MySQL 5.6+ 有优化，但 join 更可控）
- **排序**：让 `order by` 走索引（避免 filesort）
- **count**：`count(*)` 有优化，`count(列)` 不统计 NULL
- **批量插入**：合并 values、控制事务大小
- `force index` 慎用（数据分布会变）

### 1.3 事务与锁（深挖）

- **MVCC**：隐藏列 `trx_id` + `roll_pointer` + undo 版本链 + ReadView；**RC 每次查询新建 ReadView，RR 只在第一次建**
- **当前读 vs 快照读**
- **锁**：Record Lock / **Gap Lock** / **Next-Key Lock** / 插入意向锁
- **间隙锁只在 RR 生效**，RC 没有
- 死锁：`show engine innodb status` 看 LATEST DETECTED DEADLOCK；避免固定顺序访问 + 缩小事务 + 走索引减少锁范围
- 锁等待：`innodb_lock_wait_timeout`

## 二、PL/SQL 与存储过程（**简历点名，必须准备反问题**）

### 2.1 技术题

| 问题 | 得分骨架 |
|---|---|
| 存储过程优点 | 减少网络交互（一次调用多语句）、**预编译执行计划**、逻辑集中、权限可控（不暴露表） |
| 存储过程缺点 | **难调试、难版本管理、难测试**、数据库迁移困难、**业务逻辑与 DB 强耦合**、扩缩容受限、DBA 与开发职责混淆 |
| 什么时候该用 | 批量数据处理、复杂报表统计、数据迁移/清洗、**对性能极敏感的批量作业** |
| 什么时候不该用 | 互联网业务的**在线事务逻辑**（应放应用层，便于水平扩展与灰度） |
| 游标 | 逐行处理，**性能差**；能用集合操作（`UPDATE ... FROM` / `MERGE`）就别用游标 |
| 异常处理 | `EXCEPTION WHEN OTHERS THEN` + `ROLLBACK`；注意**不要吞异常** |
| 性能陷阱 | 循环里逐行 DML、隐式类型转换、`SELECT *`、缺索引、大事务 |
| PL/SQL vs MySQL 存储过程 | Oracle PL/SQL 功能强（包、游标、自治事务）；MySQL 存储过程能力弱、调试差 |

> [!important] 面试标准答法（把缺点说在前面）
> "存储过程我在**批量数据处理和报表统计**里用得比较多——一次调用完成复杂逻辑，
> 减少网络往返，性能确实好。但**在线业务逻辑我不建议放存储过程**：
> 难测试、难版本管理、数据库成了瓶颈就不好水平扩展。
> 所以我的原则是：**在线链路逻辑放应用层，重批处理才下沉到存储过程。**"

### 2.2 可能的追问
- "存储过程和函数区别？" → 函数有返回值可嵌入 SQL，过程没有
- "触发器用过吗？为什么很多公司禁用？" → 隐式执行难排查、影响性能、级联触发风险
- "Oracle 和 MySQL 你更熟哪个？" → 按实际答，别硬撑

## 三、MySQL 高可用架构

### 3.1 复制基础

| 问题 | 得分骨架 |
|---|---|
| 复制流程 | master 写 binlog → dump 线程发送 → slave IO 线程写 relay log → SQL 线程重放 |
| binlog 格式 | STATEMENT（日志小、不确定函数有问题）/ ROW（**推荐**、安全但日志大）/ MIXED |
| 主从延迟原因 | 从库单线程重放、大事务、从库压力大、网络 |
| 延迟解决 | 并行复制（`slave_parallel_workers`）、半同步复制、**写后读主**、缓存 |
| 半同步 | 至少一个从库 ack 才返回（`AFTER_SYNC` 无损） |
| GTID | 全局事务 ID，简化故障切换与定位 |

### 3.2 MGR（MySQL Group Replication）

> [!tip] 已独立成专题 → [[07-MGR与Keepalived高可用]]（MGR 提交流程图 / 认证机制 / 脑裂五板斧 / VRRP 状态机 / 配置示例 / 10 道 Q&A / 话术），下面只留速记。

| 问题 | 得分骨架 |
|---|---|
| 是什么 | MySQL 5.7.17+ 官方高可用方案，基于**组通信（Paxos 变体 XCom）**的**多副本一致性**复制 |
| 核心机制 | ① 组成员管理（故障自动剔除/加入）② **认证（certification）冲突检测** ③ 事务在组内**全序广播**后统一提交 |
| 两种模式 | **单主（Single-Primary）**：只有一个可写，推荐；**多主（Multi-Primary）**：都可写，冲突概率高 |
| 复制方式 | **不依赖传统主从**，是组内广播 + 认证；数据强一致（多数派确认） |
| 前置要求 | 表必须 **InnoDB**、必须有**主键**、必须开 **GTID**、`binlog_format=ROW` |
| 故障转移 | 多数派存活即可自动选主；**少于多数派（脑裂防护）则拒绝写入** |
| 流控 | `group_replication_flow_control_mode`，防止快节点拖垮慢节点 |
| 局限 | 对**网络延迟敏感**（同城/同机房）、成员数建议 ≤9、大事务影响大、多主模式对 gap lock / `SELECT FOR UPDATE` 有限制 |
| 适用场景 | 对**数据一致性要求高**、能接受略高写入延迟的核心库 |

### 3.3 Keepalived

| 问题 | 得分骨架 |
|---|---|
| 是什么 | 基于 **VRRP 协议**做 VIP 漂移的高可用工具 |
| VRRP 原理 | 一组路由器构成虚拟路由器，**Master 持有 VIP 并周期性发 VRRP 通告**；Backup 超时未收到 → 抢占成为新 Master 并接管 VIP |
| 关键参数 | `state`、`priority`（越大越优先）、`virtual_router_id`（同组必须一致）、`advert_int`、`nopreempt` |
| 健康检查 | `vrrp_script` 定期执行脚本（如检查 MySQL 进程/端口/`select 1`），失败则降优先级触发切换 |
| **脑裂风险** | 心跳断了但服务还活着 → **双主同时持有 VIP**，数据冲突 |
| 防脑裂 | ① `unicast_peer` 单播替代组播 ② 脚本双检（同时检查对端）③ **fencing/仲裁**（STONITH）④ 应用层写幂等 + 冲突检测 |
| 常见组合 | Keepalived + 双主复制（VIP 漂移）／Keepalived + HAProxy（读负载均衡）／Keepalived + MHA / Orchestrator（真正的故障转移） |

> [!warning] 关键认知（说出来很加分）
> "Keepalived 只解决 **VIP 漂移**，它**不理解 MySQL 的复制状态**。
> 所以严格的方案应该是 Keepalived 负责接入层漂移，**故障转移交给 MHA / Orchestrator / MGR**，
> 否则容易出现'VIP 切过去了但数据没同步完'的问题。"

### 3.4 高可用方案对比

| 方案 | 一致性 | 自动切换 | 复杂度 | 说明 |
|---|---|---|---|---|
| 主从 + Keepalived | 异步（弱） | 靠脚本 | 低 | 简单但**有脑裂与丢数据风险** |
| MHA | 异步（可能丢数据） | 是 | 中 | 老牌，社区活跃度下降 |
| **MGR** | **强一致（多数派）** | 是 | 中高 | 官方方案，推荐 |
| PXC | 强一致 | 是 | 高 | Percona，写放大明显 |
| Orchestrator | 异步 | 是 | 中 | 拓扑管理 + 自动切换，配合 ProxySQL |
| 云 RDS 高可用版 | 半同步 | 是 | 低 | 交给云，省心 |

## 四、分库分表（延伸）

- 垂直拆（按业务/字段）vs 水平拆（按行）
- 分片键要让查询**尽量落单分片**（user_id / tenant_id）
- 问题：跨片查询、分布式事务、全局 ID、扩容迁移
- 中间件：ShardingSphere、MyCat
- **顺序**：读写分离 → 索引优化 → 归档 → 分区表 → 最后才分库分表

## 六、话术模板

> "数据库这块我做过比较系统的调优。有一次线上一个订单查询接口 P99 到了 2 秒，
> 用慢查询日志定位到一条深分页 SQL，`explain` 显示全表扫描 + filesort，
> 我改成**延迟关联 + 覆盖索引**，并加了联合索引，P99 降到 80ms。
> 高可用方面我参与过 MGR 单主模式的部署——选它是因为它对数据一致性要求高，
> 组内多数派确认才算提交；Keepalived 我们只用来做 VIP 漂移，
> 故障转移的判断还是靠 MGR 自己的组成员管理，避免脑裂。"
