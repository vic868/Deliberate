## 一、Hadoop

### HDFS

| 问题 | 得分骨架 |
|---|---|
| 架构 | NameNode（元数据）+ DataNode（数据块）+ SecondaryNameNode（合并 fsimage/edits，**不是热备**） |
| 块大小 | 默认 128MB（老版本 64MB）；**块大是为了降低寻址开销** |
| 副本机制 | 默认 3 副本；机架感知（同机架 2 + 异地 1） |
| 写流程 | 客户端请求 → NN 返回可写 DN 列表 → **Pipeline 串行写** → 逐级 ack |
| 读流程 | 请求 NN 拿块位置 → **就近读**（机架感知）→ 校验和验证 |
| NN 高可用 | Active/Standby + **JournalNode 共享 edits** + ZKFC 自动切换 |
| 小文件问题 | 每个文件一个元数据条目 → **NN 内存压力**；解法：合并、HAR、HBase |

### YARN

| 问题 | 得分骨架 |
|---|---|
| 架构 | ResourceManager（全局资源）+ NodeManager（单机）+ ApplicationMaster（单应用）+ Container |
| 提交流程 | 提交 → RM 分配 Container 启 AM → AM 申请资源 → NM 启 Container 执行任务 |
| 调度器 | FIFO / Capacity（多队列、容量保证）/ **Fair（公平，生产常用）** |

### MapReduce

- 流程：Input → **Map → 环形缓冲区（溢写 + 排序 + 合并）→ Shuffle → Reduce → Output**
- **Combiner**：map 端预聚合，减少网络传输（**必须满足结合律**）
- **Partition**：决定 key 去哪个 reduce，默认 hash
- Shuffle 是性能瓶颈（磁盘 IO + 网络）

## 二、Hive

| 问题 | 得分骨架 |
|---|---|
| 架构 | 客户端 → **MetaStore**（元数据，常在 MySQL）→ 驱动 → **执行引擎（MR/Tez/Spark）** → HDFS |
| 内表 vs 外表 | 内表删表删数据；**外表只删元数据**（生产多用外表，避免误删） |
| 分区 vs 分桶 | 分区 = 目录（按日期/地区裁剪数据）；分桶 = 文件内 hash 分片（**利于 join 和抽样**） |
| **数据倾斜** | 表现：某 reduce 卡住；原因：key 分布不均、join 大表对小表、count distinct；解法：**map join**、加盐打散、两阶段聚合、调小文件 |
| **小文件** | 危害：NN 压力 + 每个文件一个 map 任务；解法：`concatenate`、合并、`merge` 参数、写入时控制 |
| 优化手段 | **谓词下推**、列裁剪、分区裁剪、map join（小表广播）、动态分区、`distribute by` 控制分发、`orc/parquet` + 压缩、向量化执行、CBO |
| 文件格式 | TextFile（慢）→ **ORC / Parquet**（列式 + 压缩 + 谓词下推）；ORC 对 Hive 更友好 |
| Hive on MR vs Tez vs Spark | MR 慢（多次落盘）；Tez 用 DAG 减少落盘；Spark 内存计算最快 |
| 排序关键字 | `order by`（全局，单 reduce，慢）、`sort by`（局部有序）、`distribute by`（控制分区）、`cluster by`（= distribute + sort） |
| 动态分区 | 按查询结果自动建分区；要设 `hive.exec.max.dynamic.partitions` 防爆 |

## 三、HBase

| 问题 | 得分骨架 |
|---|---|
| 架构 | HMaster（元数据/负载均衡/Region 分配）+ HRegionServer（读写）+ ZooKeeper（选举/元数据）+ HDFS（存储） |
| 数据模型 | Table → **RowKey** → ColumnFamily → Column(Qualifier) → **Timestamp 多版本**；稀疏、按 RowKey 字典序排序 |
| **RowKey 设计** | ① **散列**（加盐/哈希前缀）避免热点 ② **长度适中**（越短越好，几十字节） ③ 把常用查询维度拼进去（如 `反转时间戳` 支持倒序取最新） |
| 热点问题 | 单调递增 RowKey → 全写一个 Region；解法：**加盐（前缀散列）、哈希、反转** |
| **LSM 树** | 写 MemStore（内存）→ 达阈值 flush 成 **HFile** → 后台 **Compaction** 合并；**写快读慢** |
| 写流程 | 写 WAL（HLog）→ MemStore → 返回成功；flush 后落 HDFS |
| 读流程 | 先查 MemStore → 再查 BlockCache → 再查 HFile（布隆过滤器 + 索引加速） |
| Compaction | Minor（小合并）/ Major（全合并，**性能影响大**，慎用）；作用是清理多版本与删除标记 |
| 列族设计 | **列族越少越好**（一般 1-2 个），因为列族是存储与刷盘单位 |
| 适用场景 | 海量稀疏数据、**按 RowKey 随机读写**、写多读少（如日志、时序、消息） |
| 不适用 | 复杂查询、多条件组合查询、join、聚合分析 → 该用 Hive/ClickHouse |
| 二级索引 | HBase 原生没有；用 Phoenix 或自己建索引表 |

## 四、Flink（**重点，写了"深入掌握"**）

### 4.1 核心概念

| 问题 | 得分骨架 |
|---|---|
| 架构 | JobManager（调度/Checkpoint 协调）+ TaskManager（执行，按 **Slot** 划分资源）；**Slot 共享**提升资源利用率 |
| 时间语义 | **Event Time（事件时间，最常用）** / Ingestion Time / Processing Time |
| **Watermark** | 用于处理**乱序**，表示"事件时间小于该值的都到齐了"；`forBoundedOutOfOrderness(Duration)`；**Watermark 是单调递增的** |
| 窗口 | 滚动 Tumbling / 滑动 Sliding / 会话 Session / 累计 Cumulative（Flink 1.13+ 新增） |
| **迟到数据** | ① `allowedLateness` 允许窗口关闭后再触发 ② **Side Output 侧输出流**收集超迟数据 ③ 兜底批处理修正 |
| 状态 | Keyed State（ValueState/ListState/MapState/AggregatingState）、Operator State；**状态后端** HashMapStateBackend（内存）/ **EmbeddedRocksDBStateBackend（大状态，推荐）** |
| 状态 TTL | `StateTtlConfig` 防状态无限膨胀 |
| 反压 | 下游处理不过来 → 上游降速；**Flink 1.13+ 用 `busyRatio`/`backPressuredTimeMsPerSecond` 指标**；解法：加并行度、优化算子、异步 IO |

### 4.2 Checkpoint 与 Exactly-Once（**必深挖**）

| 问题 | 得分骨架 |
|---|---|
| **Checkpoint 原理** | 基于 **Chandy-Lamport 算法**：JobManager 周期性注入 **Barrier** → Barrier 随数据流对齐 → 算子收到所有输入的 Barrier 后**快照本地状态**到状态后端 → 完成后通知 JM |
| **Barrier 对齐** | 对齐期间**先到的数据要缓存**（会阻塞，造成反压）；`EXACTLY_ONCE` 需要对齐；**`AT_LEAST_ONCE` 不对齐更快** |
| **Unaligned Checkpoint** | 1.11+ 支持，Barrier 越过缓冲区（数据也一起快照），解决反压下的 Checkpoint 超时 |
| **端到端 Exactly-Once** | 需要**两阶段提交（2PC）**：`TwoPhaseCommitSinkFunction`；Checkpoint 完成时才真正提交（Kafka Sink 用事务）；**要求 Source 可重放 + Sink 支持事务** |
| Savepoint | 手动触发的、带元数据的状态快照，用于**升级/迁移/扩缩容**；与 Checkpoint 的区别：Savepoint 是用户触发的、格式更稳定 |
| 重启策略 | 固定延迟 / 失败率 / 指数延迟；配合 `restart-strategy` |

### 4.3 Flink SQL（简历点名）

| 问题 | 得分骨架 |
|---|---|
| 建表 | `CREATE TABLE ... WITH ('connector'='kafka', ...)`；时间属性用 `WATERMARK FOR ts AS ts - INTERVAL '5' SECOND` |
| 窗口 TVF | `TUMBLE` / `HOP` / `CUMULATE`；配合 `TABLE(TUMBLE(TABLE t, DESCRIPTOR(ts), INTERVAL '1' MINUTE))` |
| 去重 | `ROW_NUMBER() OVER (PARTITION BY id ORDER BY ts DESC) = 1`（**Top-N 去重**） |
| Top-N | `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...) <= N` |
| 双流 Join | Regular Join（状态无限增长，要配 TTL）/ **Interval Join**（有时间边界，推荐）/ **Temporal Join**（维表随时间变化，关联当时版本） |
| 维表关联 | **Lookup Join**（每行查外部库，配缓存）/ Temporal Join（带版本） |
| CDC | Flink CDC（Debezium）接 MySQL binlog → 实时同步；支持全量 + 增量；用于实时数仓 ODS 层 |
| 状态 TTL | `table.exec.state.ttl` 防止 join 状态无限膨胀（**很关键**） |

### 4.4 实时数仓

- 分层：**ODS（原始）→ DWD（明细）→ DWS（轻度汇总）→ ADS（应用）**
- Lambda（离线 + 实时双链路，口径易不一致）vs **Kappa（纯流式，一套链路）**
- 关键难点：**实时与离线口径统一**、维表变更、乱序与迟到、幂等写入、大状态
- 幂等写入：主键 upsert（Doris/ClickHouse 的 `ReplacingMergeTree` / 主键模型）

## 六、话术模板

> "实时链路我用 Flink 做过：Kafka 接业务 binlog 和埋点，Flink SQL 做清洗、去重、
> 维表关联和分钟级聚合，写入 Doris 供报表查询，端到端延迟控制在秒级。
> 踩过的坑主要是两个：一是**乱序**，用 Watermark + allowedLateness 加侧输出兜住；
> 二是**双流 join 状态膨胀**，加了状态 TTL 才稳住。
