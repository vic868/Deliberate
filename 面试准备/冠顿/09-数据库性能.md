# 🗃️ 微服务治理 · 数据库性能

> [[00-JD与匹配分析]] · 对应任职要求第 3 条 · 八股基础见 [[面试准备/技术面试题库/06-MySQL与数据库|通用题库·MySQL]]

> [!abstract] 负责人视角
> 初级答"加索引"，负责人答**四层**：SQL 层 → 架构层 → 治理层（慢查询 SOP）→ 容量层。
> 加分句：**"数据库性能问题的 80% 是 SQL 和架构问题，20% 才是参数问题。"**

---

## 一、四层优化框架（答题总纲）

```
第1层 SQL/索引：explain、慢 SQL 改写、索引设计        （治点）
第2层 架构：读写分离、缓存前置、归档、分库分表        （治线）
第3层 治理：慢查询巡检、topSQL、变更审核              （治面）
第4层 容量：压测水位、增长预估、提前扩容              （治未来）
```

---

## 二、SQL/索引层（快问快答）

| 问题 | 得分骨架 |
|---|---|
| 一条 SQL 突然变慢的可能原因 | ① 统计信息过期导致执行计划翻转 ② 数据量到了索引失效临界点 ③ 锁等待（别的事务持锁）④ 脏页刷盘（内存不足）⑤ 主从切换后配置差异 |
| 索引失效场景 | 函数/运算、隐式类型转换、前置通配 like、or 两侧有非索引列、最左前缀断裂、联合索引范围后的列 |
| 深分页 | 游标法（`where id > last_id limit n`）或延迟关联（先查 id 再 join 回表） |
| count 慢 | 二级索引计数 / 去掉 join 只 count 主表 / 汇总表 |
| join 优化 | **小表驱动大表**、被驱动表关联列必须有索引、避免 join 后再过滤 |

## 三、架构层（每个手段的适用边界）

| 手段 | 解决什么 | 代价/边界 |
|---|---|---|
| **读写分离** | 读压力 | **主从延迟** → 写后立即读的场景要读主（会话内标记/强制路由） |
| **缓存前置** | 热点读 | 一致性代价（→ [[07-缓存]]） |
| **冷热分离/归档** | 单表体积 | 归档表的查询路由、历史数据查询入口 |
| **分库分表** | 单表容量与写入瓶颈 | 复杂度激增，**最后才上** |
| **读写分离 + 池化参数** | 连接耗尽 | HikariCP 池大小不是越大越好（DB 连接是稀缺资源） |

### 分库分表要点（JD 点名 ShardingSphere）

- **先回答"什么时候分"**：不是行数到 X 万就分——是**写入瓶颈**（单库写入 IOPS/锁竞争）或**单表运维极限**（DDL 超时、备份过长）到了才分；多数系统先靠**索引优化 + 归档 + 读写分离**活很久
- 分片键：高频查询必须落单分片（user_id/tenant_id）；**带不上分片键的查询会广播全分片**
- 三个连带问题：**跨片查询/聚合**（走汇总表或 ES）、**分布式 ID**（雪花/号段）、**扩容迁移**（双写 → 历史迁移 → 校验 → 切流）
- 形态：**ShardingSphere-JDBC**（应用内，性能好）/ **Proxy**（独立代理，语言无关）

## 四、热点与一致性写（深挖）

**热点行更新**（秒杀库存、热门账户余额）：
1. **Redis 预扣**，DB 异步批量落库（→ [[05-并发]]）
2. **行拆分**：一行拆 N 行随机取一，聚合值另算
3. **异步合并**：先记流水，定时按流水重算绝对值（天然幂等友好）
4. **排队**：单线程串行处理该行（低吞吐高一致场景）

**大事务治理**：
- 危害：锁持有久 → 堵塞与死锁、undo 膨胀、**主从延迟**、回滚巨慢
- 治理：事务内**禁止 RPC/MQ 同步调用**、批量拆批（每批 500-1000）、监控 `information_schema.innodb_trx` 长事务告警

## 五、治理层：慢查询 SOP（负责人必答）

```
日常：慢查询日志 → pt-query-digest 聚合 TOP SQL → 周会过 Top5
上线前：SQL 审核（不走上索引的 SQL 不让合）
巡检：全表扫描 SQL、无索引 SQL、长事务、锁等待
目标：慢 SQL 数量趋势下降，而不是"救火"
```

> [!tip] 负责人金句
> "我不接受'DBA 每天救火'的状态。慢 SQL 要变成**周报里的趋势指标**：
> 新增几个、解决几个、遗留几个——数据库性能是治理出来的，不是调优出来的。"

## 六、容量层

- **压测拿水位**：当前单库 QPS 上限、连接数上限、什么时候触发分库分表——**要有数字**，不能"感觉还撑得住"
- **增长预估**：按业务增速推算表体积/体积翻倍时间，提前一个季度规划
- DDL 变更规范：大表 DDL 用 gh-ost/pt-osc（在线变更），低峰执行，**有回滚方案**

---

## 七、高频 Q&A

**Q1：单表多大要分表？**
> **没有固定数字**。判断依据是三个信号：查询性能下降且索引无法解决、DDL/备份耗时不可接受、写入出现锁竞争。
> 几千万行的窄表照样健康，几百万行的宽表大字段也可能撑不住。
> **回答"看读写模式和瓶颈信号"比背数字专业。**

**Q2：读写分离后读到旧数据怎么办？**
> 三种：① **写后读主**（会话内标记，N 秒内强制走主）② 关键查询强制主库 ③ 业务上接受最终一致 + 提示"处理中"。
> 根因是主从延迟，所以要**监控延迟**（秒级告警），延迟过大先降级非实时功能。

**Q3：分库分表后最大的坑？**
> ① 分片键外的查询广播全分片 ② 跨片 join 与聚合 ③ 扩容迁移（双写+校验+切流，必须可回滚）④ 事务边界被打破。
> 所以**能不分就不分**，先归档、读写分离、缓存。

**Q4：怎么保证 DDL 不锁表/不影响业务？**
> 大表用 gh-ost/pt-osc 在线改表（影子表 + 增量同步 + 原子 rename）；低峰执行；提前评估表大小与 binlog 量；主从分别执行时注意延迟。

**Q5：你会怎么向业务方解释"为什么这个需求要排期优化数据库"？**
> 用数据：当前水位（QPS/容量/慢 SQL 趋势）+ 风险预测（什么时间会到瓶颈、到时候影响什么业务）→ 争取每迭代 15-20% 的治理时间。

---

## 八、一分钟话术

> "数据库性能我按四层治理。
> **SQL 层**：慢查询日志聚合 TOP SQL，explain 卡 type 和 rows，索引按最左前缀和覆盖设计；
> **架构层**：读写分离注意主从延迟的写后读问题，分库分表是最后手段——
> 用 ShardingSphere 时先想清楚分片键，带不上分片键的查询会广播全分片；
> **治理层**：慢 SQL 进周报看趋势，上线前 SQL 审核，大事务有监控；
> **容量层**：压测拿水位、按增速提前规划，大表 DDL 走 gh-ost。
> 一句话：**数据库性能是治理出来的，不是救火救出来的。**"
