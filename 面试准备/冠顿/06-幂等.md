# 🔁 微服务治理 · 幂等

> [[00-JD与匹配分析]] · 对应任职要求第 3 条 · 关联 [[面试准备/技术面试题库/08-消息队列|通用题库·MQ]]

> [!abstract] 一句话定位
> **所有异步链路和所有写接口的标配**。JD 单独把"幂等"从一致性里拎出来，说明他们被坑过。
> 负责人金句：**"写接口必须有幂等键"是我的架构评审一票项。**

---

## 一、为什么会有"非幂等"（先讲清来源，显专业）

重复请求的**五个来源**：

| 来源 | 场景 |
|---|---|
| **用户重复操作** | 双击提交、刷新回退再提交 |
| **网络重试** | HTTP 超时客户端重试、Feign/RestTemplate 重试 |
| **MQ at-least-once** | 消费超时未 ack → broker 重投 |
| **任务重复执行** | 定时任务多实例、任务平台重跑、失败重试 |
| **上游重发** | 第三方回调（支付回调必然多次） |

**幂等定义**：同一操作执行一次和 N 次，**对系统状态的影响相同**。

---

## 二、六种方案对比（一张表 + 选用原则）

| 方案 | 可靠性 | 性能 | 适用 | 坑 |
|---|---|---|---|---|
| **数据库唯一索引** | ⭐⭐⭐⭐⭐（最强兜底） | 中（有唯一冲突开销） | **所有写接口的最终防线** | 冲突要捕获并转为"查询返回已有结果"，不能抛 500 |
| **状态机** | ⭐⭐⭐⭐⭐ | 好 | 有状态流转的实体（订单） | 只防"非法流转"，不防"同状态重复副作用" |
| **去重表/流水表** | ⭐⭐⭐⭐ | 中 | 消费幂等、回调幂等 | 表会膨胀，要归档 |
| **Token 机制** | ⭐⭐⭐⭐ | 好 | 表单提交防重 | **取 token 与提交 token 的删除必须原子**（Lua），否则并发下失效 |
| **乐观锁版本号** | ⭐⭐⭐⭐ | 好 | 更新类操作 | 只适合"更新同一行"，不能防"新建两条" |
| **Redis setnx 去重** | ⭐⭐⭐ | **最好** | 高频、可容忍极小概率重复 | **Redis 宕机/主从切换会丢标记** → 只能做第一道，不能做唯一防线 |

> [!important] 核心原则（说出这条就赢了大多数人）
> **Redis 去重只能做第一道快速过滤，唯一索引/状态机必须是最后兜底。**
> "只用 Redis 做幂等"在生产上一定会丢数据——主从切换的瞬间标记就没了。

## 三、组合拳（生产标准姿势）

```
前端防抖（体验层）
  → 网关/入口去重（Redis，快速过滤，可选）
    → 业务层幂等键校验（去重表/状态机）
      → 数据库唯一索引（最终兜底）
        → 对账（发现漏网之鱼）
```

- **幂等键怎么生成**：客户端生成（uuid/设备号+序列）最可靠；服务端用业务唯一约束（订单号+类型、三方流水号）
- **幂等返回什么**：重复请求**返回第一次的结果**（200 + 原结果），**不是报错**——否则客户端会一直重试

---

## 四、按场景的标准答法

**Q1：用户双击提交订单怎么防？**
> 三层：前端按钮置灰 + 请求带客户端生成的 requestId → 服务端以 requestId 做去重（Redis 快查 + 唯一索引兜底）→ 重复请求返回首次结果。
> 同时订单号用服务端生成，避免客户端造号。

**Q2：MQ 消息重复消费怎么处理？**
> 消费逻辑以**业务唯一键**（orderId + 事件类型）查流水表：不存在 → 执行 + 插流水（**同事务**）；已存在 → 直接 ack 返回。
> 关键：**"查重 + 执行 + 记流水"必须在同一个本地事务**，否则并发下两个消费者同时查都"不存在"。

**Q3：支付回调一定多次，怎么处理？**
> 以**第三方交易流水号**做唯一索引；回调先查单据状态——已终态直接返回 success（**别返回失败，否则对方一直重发**）；
> 状态机校验流转合法性；金额与订单核对不一致要落异常表人工介入。

**Q4：定时任务多实例同时跑怎么办？**
> 任务粒度幂等：以"数据版本/处理标记"做条件更新；或分布式锁互斥 + 分片（每实例处理不同分片）；
> **设计目标：任务跑两遍，结果和一遍一样**——这才是真正的幂等，靠锁防并发是辅助。

**Q5：update 语句天然幂等吗？**
> 不一定。**绝对值更新幂等**（`set status=2 where status=1`），**增量更新不幂等**（`set n=n-1`）。
> 所以增量操作要么前置幂等判断，要么把"增量"改成"由流水重算绝对值"。

---

## 五、治理视角（负责人加分项）

1. **评审一票项**：新增写接口必须回答"幂等键是什么"——答不出不通过
2. **框架化**：把幂等做成**注解/组件**（`@Idempotent(key = "#orderId")`，Redis + 唯一索引封装），而不是每个接口手写——**靠规范不靠自觉**
3. **监控**：幂等命中数要有监控——**突然升高说明上游在疯狂重试**，是系统故障的早期信号
4. **测试**：并发重放测试（同请求并发打 10 次）纳入核心接口的验收

---

## 六、一分钟话术

> "幂等我分三层做。
> **入口层**快速过滤：客户端幂等键 + Redis 去重，挡掉大部分重复；
> **业务层**是主力：去重表或状态机，'查重、执行、记流水'放同一个事务；
> **数据库唯一索引**是最终兜底——因为 Redis 在主从切换时会丢标记，唯一索引不会骗人。
> 重复请求统一返回首次结果而不是报错，避免客户端无限重试。
> 治理上我把'幂等键'做成架构评审一票项，并封装成注解组件，**靠规范不靠自觉**；
> 幂等命中率还接了监控——**命中率突然升高，往往是上游故障的第一个信号**。"

## ⭐ 幂等接口设计七步法（"如何设计一个幂等接口"标准答案）

> [!abstract] 这题考什么
> 面试官给一个接口让你设计幂等，**不是让你背方案列表**，是看你的设计是否**有步骤、有取舍、能落地**。
> 七步答完 = 完整闭环。

### 第 1 步：列出重复来源（决定幂等键由谁生成）
| 来源 | 说明 |
|---|---|
| 用户重复操作 | 双击提交、刷新回退再提交 |
| 网络重试 | HTTP/Feign 超时重试 |
| MQ at-least-once | 消费超时未 ack → 重投 |
| 任务重跑 | 定时任务多实例/失败重试 |
| 三方回调重发 | 支付回调必然多次 |

### 第 2 步：定幂等键（核心）
- 原则：**同一业务意图必同键，不同意图必不同键**
- 优先客户端生成：requestId（uuid / 设备号+序列）——覆盖"用户重复点击"
- 服务端业务唯一键：订单号+操作类型、**三方交易流水号**（回调场景）
- 幂等键**标识的是"意图"**，不是"接口"

### 第 3 步：判断操作是否天然幂等（能省则省）
- ✅ 查询接口：天然幂等
- ✅ 绝对值更新：`set status=2 where status=1` 天然幂等
- ❌ 新增、增量更新（`n=n-1`）、扣减：**必须做防重设计**

### 第 4 步：选防重层（三层组合，逐层兜底）
```
① 快速层   Redis setnx(key, "processing", TTL)   —— 性能过滤，不可靠
② 业务层   状态机校验 / 去重表 —— 「查重 + 执行 + 记流水」同一事务
③ 兜底层   数据库唯一索引 —— insert 冲突 = 已执行 → 转查结果返回
```
- **Redis 只能当第一道**（主从切换丢标记），唯一索引才是真兜底
- 并发窗口：同键并发 → 唯一索引约束兜底；或 Lua 把"检查+占用"做成原子

### 第 5 步：定重复请求的返回语义
- **返回第一次的结果**（200 + 原结果），**绝不报 500**——报错会让客户端无限重试
- 已受理未完成 → 返回"处理中"+ 查询入口，让客户端轮询而不是重试

### 第 6 步：失败路径设计
- 业务失败 → **删除幂等标记**（或流水记 failed），允许客户端带同键重试
- 重试要有上限和退避；流水表定期归档

### 第 7 步：验证与运营
- **并发重放测试**：同幂等键并发打 10 次 → 只产生一条副作用、返回一致
- 对账兜底（→ [[04-事务一致性]]）
- **幂等命中率监控**：命中率突升 = 上游在疯狂重试 = 上游故障的最早信号

### 参考伪代码
```java
handle(req) {
    key = req.idempotencyKey;                       // 第2步
    if (!redis.setnx(key, "processing", 10min)) {   // 第4步①
        r = loadResult(key);
        return r != null ? r : "处理中";             // 第5步
    }
    try {
        tx(() -> {
            insert(flowTable, key, ...);            // 第4步③ 唯一索引
            result = business();                    // 真正业务
            saveResult(key, result);
        });
        return result;
    } catch (DuplicateKeyException e) {             // 并发窗口兜底（第6步）
        return loadResult(key);
    } catch (BizException e) {
        redis.delete(key);                          // 第6步 失败放行重试
        throw e;
    }
}
```

### 一分钟话术
> "设计幂等接口我走七步：**先列重复来源**（用户重试/网络重试/MQ 重投/任务重跑/三方回调），
> **再定幂等键**——同一业务意图必同键，优先客户端 requestId 或三方流水号；
> 第三判断操作是否天然幂等，绝对值更新就不用做；
> 第四选三层防重：Redis 快速过滤、去重表/状态机同事务校验、**唯一索引兜底**；
> 第五定返回语义——重复请求返回首次结果，处理中返回状态，绝不报 500；
> 第六设计失败路径，业务失败删标记允许重试；
> 最后并发重放测试 + 对账 + 命中率监控。
> 落地上我把这套封装成 @Idempotent 注解组件，**幂等键是架构评审的一票项**。"
