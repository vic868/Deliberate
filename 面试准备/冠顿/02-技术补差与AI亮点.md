## 一、RocketMQ（你写 Kafka，JD 要 RocketMQ）

### 与 Kafka 概念对照（一张表搞定迁移）

| | Kafka | RocketMQ |
|---|---|---|
| 存储单位 | Topic → **Partition** | Topic → **Queue**（MessageQueue） |
| 消费模型 | Consumer Group + offset | Consumer Group + **消费位点**，支持**集群/广播**两种模式 |
| 顺序 | 分区内有序 | 队列内有序，支持**顺序消息**（生产端按 key 选队列） |
| 延迟消息 | ❌ 需自建 | ✅ **固定 18 个级别**（5.x 支持任意时长） |
| 事务消息 | 有，但偏流处理 | ✅ **半消息 + 本地事务 + 回查**，业务事务消息的标准做法 |
| 死信队列 | 需自建 | ✅ 内置（重试 16 次后进 DLQ） |
| 重试 | 需自建 | ✅ 内置重试队列（%RETRY%group） |
| 吞吐 | 极高（百万级） | 高（十万级，够业务用） |
| 适用 | 日志、流计算、大数据管道 | **业务系统**（事务、顺序、延迟、重试都是内置的） |

### 必考三题

**① 事务消息流程（背下来）**
```
1. 发送半消息（half message）→ Broker 落盘但对消费者不可见
2. 执行本地事务
3. 成功 → commit；失败 → rollback
4. 若 Broker 没收到确认 → 定时回查生产者（checkLocalTransaction）
5. 回查依据：本地事务日志/状态表
```

**② 延迟消息**：固定 18 级别（1s 5s 10s 30s 1m 2m...2h）；5.x 支持任意时间。典型场景：**订单 30 分钟未支付自动关闭**（比扫表优雅）。

**③ 顺序消息**：生产端按业务 key（如 orderId）`select` 同一个队列 → 单线程消费该队列；**代价是吞吐下降**，且失败会阻塞该队列。

> [!tip] 迁移话术
> "Kafka 我用得深，RocketMQ 的模型我清楚。选型上业务系统我会优先 RocketMQ——
> **事务消息、延迟消息、重试和死信都是内置的**，Kafka 这些要自己搭。
> 我们项目用 Kafka 主要因为大数据链路要消费同一份数据。"

## 二、Elasticsearch（简历没写，速补最小集）

> [!warning] 策略：不装精通
> "生产上我主要用 ES 做查询侧和与 MySQL 的数据同步，索引设计是团队一起定的。"
> 下面这些点答出来，就已经超过"没写过"的候选人。

| 问题 | 得分骨架 |
|---|---|
| **为什么快 / 倒排索引** | 正排：文档→词；**倒排：词→文档列表**。分词后建 term dictionary + posting list，查询时先查词典再取 posting list；用 **FST** 压缩词典、BKD 树支持数值/地理 |
| **写入流程** | 写入 memory buffer + translog → **refresh（默认 1s）** 生成 segment 变为可搜索 → translog **flush** 落盘 → segment 后台 **merge** |
| **近实时** | refresh 间隔导致写入到可搜索有 ~1s 延迟（**NRT**） |
| **深分页** | `from+size` 在分布式下要 each 分片取 from+size 条，深翻页开销爆炸；用 **`search_after`**（推荐）或 scroll（导出场景） |
| **与 MySQL 同步** | **Canal / Flink CDC** 订阅 binlog → 写 ES；保证最终一致 + 全量重建兜底 |
| **分词** | 中文用 IK（ik_max_word 索引 / ik_smart 查询）；自建词库加业务词 |
| **聚合** | terms 聚合做分组统计，近似值（shard 级聚合再合并，`doc_count_error`） |
| ** brain 集群** | master-eligible / data / coordinating 角色分离；脑裂用 `discovery.zen.minimum_master_nodes`（7.x 后自动） |

## 三、Apollo 配置中心

| 问题 | 得分骨架 |
|---|---|
| 是什么 | 携程开源的**分布式配置中心**，集中管理多环境多集群配置 |
| 核心能力 | **多环境（dev/test/prod）多集群**、配置**灰度发布**、**权限与审计**、变更通知（长轮询 60s）、版本回滚 |
| **与 Nacos 怎么选** | Apollo：**权限、审计、灰度、发布审批**强 → 大公司多团队用；Nacos：**注册中心+配置一体**、部署轻 → 中小团队；你简历写了 Nacos 就直说"两个都了解，Nacos 用得多，Apollo 的灰度和审计机制我清楚" |
| 配置热更新 | 客户端长轮询拉取变更 → `@RefreshScope` / 监听器回调 |

## 四、ShardingSphere

| 问题 | 得分骨架 |
|---|---|
| 两种形态 | **ShardingSphere-JDBC**（增强版驱动，应用内分片，性能好、无中间层）vs **ShardingSphere-Proxy**（独立代理进程，语言无关、运维方便） |
| 分片策略 | 精确（=）、范围、**复合分片**、hint 强制路由 |
| 分片键选择 | 让**高频查询落单分片**（user_id/tenant_id）；不一致的查询会广播全分片 |
| 带来的问题 | 跨分片查询/join、分布式事务、**全局 ID**（雪花）、**扩容迁移**（双写 + 历史数据迁移 + 校验切流） |
| 你的优势 | [[面试准备/技术面试题库/06-MySQL与数据库]] 的分库分表知识直接可用，只需记住这个框架的名字和两种形态 |

## 五、K8S / DevOps / Service Mesh（速补概念级）

| 问题 | 得分骨架 |
|---|---|
| **K8S 核心对象** | Pod（最小调度单位）、Deployment（无状态 + 副本管理）、Service（稳定访问入口）、Ingress（七层路由）、ConfigMap/Secret（配置）、HPA（自动扩缩容）、StatefulSet（有状态） |
| Pod 为什么抽象出来 | 支持多容器共享网络/存储（sidecar 模式）；容器重启不影响 IP 稳定性由 Service 保证 |
| **发布策略** | 滚动（默认，渐进替换）、蓝绿（双环境切流）、**灰度/金丝雀**（按比例/按用户路由）——生产推荐灰度 |
| CI/CD | GitLab CI / Jenkins：提交 → 构建 → 单测 → 镜像 → 部署测试环境 → 审批发布；**发布必须可回滚** |
| **Service Mesh（是什么、为什么）** | 把**服务间通信**（熔断、重试、路由、mTLS、可观测）下沉到 **sidecar 代理**（Istio+Envoy），业务代码零侵入；代价是多一跳延迟 + 运维复杂度。**答法："了解原理，没在生产用过"**——它是"优先"项，不是必须 |
| DevOps 理念 | 开发对交付全生命周期负责；一切进版本库、一切自动化、一切可回滚 |

## 六、SLO / 监控 / Trace（职责 5，技术侧）

- **三层指标**：业务（下单量/成功率）→ 应用（QPS/P99/错误率，**RED**：Rate/Errors/Duration）→ 资源（CPU/内存/连接，**USE**）
- **SLI/SLO/SLA**：SLI 是可测量指标；SLO 是目标（P99<300ms、可用性 99.9%）；SLA 是对外承诺+赔偿
- **Trace**：traceId 网关生成 → 全链路透传（HTTP header / MQ 消息头）→ 日志带 traceId → SkyWalking 出调用链
- 告警：**可行动**才发；P0 电话、P1 群、P2 日报；定期清理

> 你有大数据背景（Flink/实时链路），可以把"日志与指标的处理链路"讲得很具体——这是加分的连接点。

## 七、⭐ AI 落地亮点（JD 第 6 条，你的差异化机会）

> [!important] 这条几乎是为准备的候选人设的区分题
> "有推进 AI 在研发的落地，熟练使用主流的 coding agent 和 work agent"
> 大多数候选人只会说"我用 Copilot 写代码"。**你能讲出负责人视角的落地打法。**

### 7.1 概念先分清（答对即显专业）
- **Coding Agent**：辅助**写代码**的智能体（Claude Code、Cursor、GitHub Copilot、通义灵码）——理解代码库、多文件编辑、跑测试、自我修正
- **Work Agent / 工作流 Agent**：把**研发流程环节**交给 Agent 执行——需求分析、代码评审、测试生成、缺陷定位、文档生成、发布摘要

### 7.2 落地打法（负责人视角，四步）

**① 从"痛点高频 + 风险低"的场景切入**

| 场景 | 收益 | 风险 |
|---|---|---|
| 单元测试生成 | 最快见效，省 30-50% 时间 | 低（有人 review） |
| Code Review 预审 | 机器先查低级问题，人审业务逻辑 | 低 |
| 代码解读/交接文档 | 老系统维护、新人上手 | 极低 |
| SQL/配置生成 | 提速 | 中（必须 review） |
| 排障助手 | 结合监控/日志给排查建议 | 中 |

**② 定规矩再推广**（没有规矩的 AI 落地必然出事故）
- AI 生成的代码**必须过 code review**，责任在人不在工具
- 敏感信息（密钥、客户数据）**禁止**喂给外部模型
- 生成代码同样要过静态扫描和测试卡口
- 明确哪些目录/模块不允许 AI 直接改

**③ 度量效果**（负责人必须能报数字）
- 需求交付周期变化、单测覆盖率变化、CR 平均耗时、缺陷逃逸率
- **先小范围试点 2-3 人，拿到数据再全团队推**

**④ 逐步升级到 work agent**
- 第一步：编码辅助（个人提效）
- 第二步：CI 里挂 AI 预审/测试生成（流程化）
- 第三步：需求→任务拆解、发布摘要等流程 Agent

### 7.3 你的真实素材（全部可讲）

- ✅ **日常深度使用 AI 编码工具**做开发、排查、重构（这是真的）
- ✅ **做过 RAG demo**（Spring AI Alibaba）——懂 AI 应用的工程化路径
- ✅ 理解企业落地三要素：**场景选择、规矩先行、效果度量**
- ✅ 知道边界：AI 写的代码责任在人、敏感数据不出域、生成质量要评测

**话术模板**：
> "AI 在研发落地这件事，我分两层看。**工具层**——coding agent 我现在每天都在用，
> 编码、排查、写测试，提效非常明显；我的规矩是：AI 生成的代码一样要过 review 和测试卡口，
> 责任在人不在工具，敏感数据不出域。
> **流程层**——我会从'高频 + 低风险'切入：先推单测生成和 CR 预审，小范围试点拿数据，
> 有效果再全团队推。再往后是把 review 预审、发布摘要这些挂进 CI，变成 work agent。
> 另外我自己做过一个 RAG demo（Spring AI Alibaba），所以**AI 应用怎么工程化落地、坑在哪**，
> 我有体感，不是只站在使用者的角度。"

> [!tip] 这段话的杀伤力
> 岗位要的是"**推进** AI 落地"——你要展现的不是"我会用"，而是
> "**我知道怎么让一个团队安全地、可度量地用起来**"。这是负责人视角，绝大多数候选人给不出来。
