# 🔗 微服务治理 · 事务一致性

> [[00-JD与匹配分析]] · 对应任职要求第 3 条 · 基础八股见 [[面试准备/技术面试题库/09-分布式与微服务|通用题库·分布式]]

> [!abstract] 这题在负责人层面考什么
> 初级答"用什么框架"，**负责人答"什么场景用什么方案、代价是什么、最后防线是什么"**。
> 核心句：**能用本地事务的绝不引入分布式事务；能最终一致的绝不上强一致；对账永远是最后防线。**

---

## 一、先做决策：真的需要分布式事务吗？（多数人跳过这步）

**第一原则：能不拆事务边界就不拆。**

```
问自己三个问题：
① 这些操作必须在同一个服务里吗？（很多"分布式事务"是拆分不当造成的）
② 业务能接受中间态吗？（能 → 最终一致，成本低一个数量级）
③ 失败了能补偿吗？（能 → Saga；不能回滚 → 前置校验 + 预扣）
```

| 场景 | 正确做法 |
|---|---|
| 订单创建 + 扣库存（同库） | **本地事务**，别折腾 |
| 订单服务 + 库存服务（已拆） | 最终一致：本地消息表 / 事务消息 |
| 资金类（必须强一致） | TCC 或 同库合并事务，**别用异步最终一致** |
| 调用第三方（无法回滚） | 预扣/冻结 + 异步确认 + 对账 |

## 二、五种方案对比（一张表记牢）

| 方案 | 一致性 | 侵入性 | 性能 | 适用 |
|---|---|---|---|---|
| **2PC/XA** | 强一致 | 低（DB 支持） | **差**（同步阻塞、锁持有久） | 数据库间短事务，互联网业务**基本不用** |
| **TCC** | 强（业务层面） | **高**（三个接口） | 较好 | 资金、核心交易 |
| **Saga** | 最终一致 | 中（补偿逻辑） | 好 | 长流程、跨多服务 |
| **本地消息表** | 最终一致 | 中 | 好 | **通用首选**，简单可靠 |
| **事务消息**（RocketMQ） | 最终一致 | 低 | 好 | 有 MQ 基础设施的团队 |

### 各方案的关键细节（追问必到）

**TCC 三大坑（必背）**：
- **空回滚**：Try 没执行（超时未收到），Cancel 先到 → Cancel 要判断"Try 是否发生过"（事务控制表记录）
- **悬挂**：Cancel 执行完，阻塞的 Try 才到 → Try 要检查"是否已回滚"，拒绝执行
- **幂等**：Try/Confirm/Cancel 都可能重试 → 全部要幂等

**Seata AT 模式**：
- 一阶段：解析 SQL，记录**前后镜像**（undo log），本地事务提交并**注册分支**
- 二阶段：提交 = 删 undo log；回滚 = 用前镜像**反向补偿**
- 关键：**全局锁**——防止其他全局事务修改未提交的行 → 这是它的**性能瓶颈和死锁来源**
- 适用：并发不高的内部系统；高并发热点数据别用 AT

## 三、本地消息表 vs 事务消息（**高频对比题**）

| | 本地消息表 | RocketMQ 事务消息 |
|---|---|---|
| 原理 | 业务与消息**同库同事务**写入 → 后台扫描/定时投递 | 半消息 → 本地事务 → commit/rollback → **回查** |
| 优点 | **实现简单、可靠**、不依赖 MQ 特性 | 无业务表侵入、投递及时 |
| 缺点 | 消息表膨胀需清理；有扫描延迟 | 依赖 MQ 的回查实现，**回查逻辑要查业务状态** |
| 共同点 | **两者都保证"本地事务成功 ⇒ 消息必达"**，下游仍需幂等 | 同左 |

> 话术："我倾向本地消息表——不依赖 MQ 的事务特性，出问题好排查；对时效敏感的场景用事务消息。
> 但无论哪种，**下游必须幂等**，且要有**定时对账**兜底。"

---

## 四、最后防线：对账（负责人必须主动讲）

- 实时链路保证的是"大概率一致"，**对账保证的是"最终一定一致"**
- 三层对账：**实时比对**（关键数据双写校验）→ **T+1 全量对账** → **抽样人工核验**
- 差异处理分级：可自动冲正的自动冲正；不能的生成工单；**差异必须有去向**（零差异也要有"核对过 0 条"的记录）
- 对账维度：数量对账 + 金额对账 + 状态对账

> [!important] 负责人金句
> "我判断一个团队的事务治理是否成熟，**不看它用了多炫的框架，看它有没有对账**。
> 没有对账的最终一致等于没保证。"

## 五、高频 Q&A

**Q1：下单要扣库存、加积分，跨三个服务，怎么保证一致性？**
> 先反问业务容忍度。绝大多数场景：**主流程只保证"订单+库存"**（本地消息表/事务消息同步扣减），
> 积分走**异步最终一致**（发消息 → 积分服务消费 → 幂等 → 失败重试 → 死信人工）。
> 全链路配 **T+1 对账**。若资金 involved → TCC。
> **不要一上来就说"用 Seata 全局事务"——那是初级答案。**

**Q2：为什么互联网公司少用 2PC/XA？**
> ① 同步阻塞：prepare 后资源被锁住，吞吐骤降 ② 协调者单点 ③ 数据不安全的窗口（二阶段部分提交）④ 网络分区下体验极差。**互联网用最终一致 + 补偿换吞吐。**

**Q3：TCC 的空回滚、悬挂、幂等怎么解决？**
> 用一张**事务控制表**（xid + 状态）：
> 空回滚 = Cancel 前查 Try 记录，没有则插入"已回滚"标记直接返回成功；
> 悬挂 = Try 执行前查到"已回滚"标记则拒绝；
> 幂等 = 状态机 + 唯一键，重复请求直接返回首次结果。

**Q4：跨服务查询的一致性呢（订单里要显示积分）？**
> 不要实时 join：① 冗余关键字段（下单时快照）② 查询时聚合（接受短暂不一致）③ CQRS（事件驱动构建查询视图）。**显示类数据接受秒级不一致。**

**Q5：怎么验证一致性方案是对的？**
> 测试：故障注入（杀 MQ、超时、部分失败）+ 对账脚本；上线后看**差异率监控**——一致性方案没有验证 = 没有。

---

## 六、一分钟话术

> "事务一致性我分三层看。
> **第一层尽量收敛事务边界**——很多分布式事务是服务拆分不当造成的，能同库就同库。
> **第二层按业务选型**：资金强一致用 TCC（注意空回滚/悬挂/幂等三件事），
> 一般业务用本地消息表或事务消息做最终一致，代价是下游要幂等。
> **第三层必须配对账兜底**——实时链路只能保证大概率一致，对账才保证最终一致，
> 差异要有监控、有工单、有去向。
> 另外我会在架构评审时把关：**谁要引入分布式事务，先回答'为什么不能最终一致'**。"
