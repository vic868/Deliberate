# 🚨 微服务治理 · 故障恢复

> [[00-JD与匹配分析]] · 对应任职要求第 3 条（"故障恢复"） · 关联 [[面试准备/冠顿/03-监控告警Trace与SLO|监控与SLO]]

> [!abstract] 这题考什么
> 不是考你背"降级熔断限流"六个字，是考：
> **真出事时你第一动作是什么、预案是否演练过、怎么让 MTTR 越来越短**。
> 负责人金句：**"故障不可能为零，我的 KPI 是 MTTR 和复发率。"**

---

## 一、故障分类（先分类，再谈预案）

| 类别 | 例子 | 主要手段 |
|---|---|---|
| **依赖故障** | DB 主库挂、Redis 集群异常、MQ 不可用、第三方支付超时 | 切换、降级、熔断 |
| **自身故障** | 发布引入 bug、OOM/FullGC、线程池打满 | **回滚**、扩容、参数回退 |
| **容量故障** | 流量洪峰击穿水位 | 限流、扩容、排队 |
| **网络故障** | 机房网络抖动、DNS | 多机房、超时重试 |
| **数据故障** | 误删表、脏数据、缓存污染 | 备份恢复、binlog 闪回、数据修正 |

---

## 二、应急响应：P0 的第一动作（必考）

**四步：止血 → 定位 → 恢复 → 复盘**

1. **止血（分钟级）**：优先级排序——
   **回滚 > 降级/切流 > 限流保护 > 现场修复**
   - 刚发完版就出问题 → **第一动作是回滚**（不要现场 debug）
   - 依赖挂了 → 切备用/降级开关
   - 流量打爆 → 限流 + 非核心降级
2. **定位**：traceId 链路 + 指标变化点 + 最近变更（发布/配置/数据）
3. **恢复**：确认指标回归 → 观察期
4. **复盘（24-48h 内）**：时间线 → 根因（5 Why，挖到**流程**而不是个人）→ action items（owner + deadline）→ 下次复盘先查上次 items 闭环

> [!important] 两个负责人级原则
> ① **先恢复服务，再查根因**——别在生产环境上 debug
> ② **无指责复盘（blameless）**——追责会让下次没人敢第一时间上报

## 三、分场景恢复手册（每个都要能讲）

### DB 主库挂了
```
① 确认故障（监控 + 探活）→ ② 提升从库为主（GTID 定位 + 补齐差异）
③ 应用切换数据源（DNS/配置中心/代理）→ ④ 观察复制与数据一致性
⑤ 老主库恢复后降级为从库
数据会不会丢？取决于复制模式：
  异步 → 可能丢最后几秒；半同步（AFTER_SYNC）→ 不丢已确认事务
```

### Redis 集群挂了
> 第一动作**保 DB**：读降级走 DB 副本 + 接口限流；分布式锁类功能降级（幂等兜底）；
> 恢复后注意**缓存预热**（防止冷启动击穿）与数据重建。

### MQ 不可用
> 有降级开关的业务改为**同步调用或本地落库重试**（消息落表，恢复后重放）；
> 没有降级设计的 → 限流保核心，事后补数据。**教训：MQ 必须有绕行方案。**

### 发布后出问题
> **一键回滚**是硬要求；回滚前先想**数据兼容性**——新代码写的字段/消息，老代码能不能读？
> 所以发布要遵守：**先加后删**（字段分两个版本下线）、消息结构向后兼容。

### 误删数据
> 预防大于恢复：危险操作走工单 + 二次确认、备份策略（每日全量 + binlog）、
> **延迟从库**（delay 1h 的从库是真救星）、恢复工具（binlog2sql/MyFlash 做闪回）。

## 四、高可用设计（让故障"可恢复"）

| 层 | 设计 |
|---|---|
| **冗余** | 无状态多实例、DB 主从/MGR、Redis 哨兵/Cluster、MQ 集群——**任何单点都是事故** |
| **故障转移** | 自动切换（哨兵/MGR/K8S 重调度）+ **切换演练** |
| **隔离** | 核心与非核心服务独立部署、线程池隔离、独立 DB 资源——非核心挂了不拖核心 |
| **超时重试熔断** | 所有远程调用必有超时；重试要有上限与退避；熔断防雪崩 |
| **多机房** | 同城双活（延迟低、RPO≈0）→ 异地多活（成本高，核心业务才做）；单元化按用户分片 |
| **预案** | 每个依赖故障都有对应开关，**开关平时演练，没演练过的预案等于没有** |

## 五、混沌工程与演练（负责人亮点）

- **故障演练**：定期注入故障（杀实例、断网、延迟注入）验证：告警有没有响、切换有没有生效、值班会不会处理
- **预案清单化**：每个 P0/P1 风险对应一个预案（谁执行、几步、验证方式）
- **红蓝对抗 / 抢占式排障**：新人在测试环境复现历史故障
- 度量：**演练通过率**、MTTR 趋势

> 话术："我判断预案是否有效的标准很朴素——**随机挑一个值班同学，半夜把他叫醒，他能不能照着预案十分钟内止血**。
> 不能，就说明预案是文档不是能力。"

## 六、度量指标（负责人要会报数字）

| 指标 | 含义 | 目标方向 |
|---|---|---|
| **MTTR** | 平均恢复时间 | ↓（预案、自动化、演练） |
| **MTBF** | 平均无故障时间 | ↑（治理、压测） |
| **故障复发率** | 同根因二次故障 | ↓（复盘闭环） |
| **SLO 达成率 / 错误预算** | 服务质量（→ [[03-监控告警Trace与SLO]]） | 达标且有预算消耗记录 |
| **演练覆盖率** | 关键预案演练过的比例 | ↑ |

## 七、高频 Q&A

**Q1：半夜 P0，核心接口全挂，你的前 10 分钟做什么？**
> ① 确认影响面（哪些业务/多少用户）并**同步信息**（拉群、公告，让业务方不是最后一个知道）
> ② 判断最近变更：刚发布 → 立即回滚；没发布 → 看指标定位依赖
> ③ 止血动作执行（回滚/切流/扩容），**同时**安排人查根因
> ④ 恢复后观察 30 分钟 → 当天发初步报告，48h 内正式复盘

**Q2：怎么缩短 MTTR？**
> ① 回滚自动化（一键、分钟级）② 常见故障预案化 + 演练 ③ 监控定位快（traceId + 变更关联）④ 值班机制与升级路径清晰。**MTTR 的大头往往不是定位，是决策犹豫——预案就是消除犹豫。**

**Q3：怎么预防同一个故障发生两次？**
> 复盘 action items 必须闭环（负责人跟踪）→ 根因落到**机制**：监控补盲区、流程加卡点、代码加防御（幂等/超时/限流）→ 把案例沉淀成评审检查项和新员工教材。

**Q4：异地多活怎么做？**
> 先问业务值不值（成本数倍）：核心思路是**单元化**——按用户分片到不同机房，单元内闭环，跨单元只同步变更数据；难点在**数据冲突**与**流量切换**，先同城双活再演进异地。

**Q5：你们怎么验证备份是可用的？**
> 定期**恢复演练**（恢复到临时实例并抽验数据），不是"有备份文件"就算——**没恢复过的备份等于没备份**。

---

## 八、一分钟话术

> "故障恢复我抓三件事。
> **应急**：止血优先于定位——刚发布就回滚，依赖挂了就切流降级，流量打爆就限流，
> 处理顺序固化成预案，值班照着走，不靠临场发挥。
> **设计**：冗余 + 故障转移 + 隔离 + 全链路超时，非核心与核心隔离，
> 任何单点在我这里都是事故隐患。
> **闭环**：无指责复盘，action items 我亲自跟，同根因二次故障是我的红线；
> 预案定期演练——**没演练过的预案等于没有**。
> 我的度量就是 MTTR 和故障复发率，故障不可能为零，但必须越来越快恢复、不再复发。"
