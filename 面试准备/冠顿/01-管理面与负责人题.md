# 👥 冠顿 · 管理面与负责人题

> 返回 [[00-JD与匹配分析]]

> [!important] 这个岗位的胜负手
> JD 职责 7 条里有 **5 条是管理**（目标制定、绩效、研发流程、架构演进、工程文化）。
> 技术你已经超配，**这场面试的胜负手是"你像不像一个负责人"**。
> 答题姿势要从"我做过什么"切换到"**我怎么让一群人做成事**"。

---

## 一、管理经验怎么定位（开场必答）

> [!warning] 你的软肋
> JD 要"2 年以上技术团队管理或技术负责人经验"，你之前自评管理经验不足。
> **策略：不撒谎，但把"实际承担的负责人职责"讲满。**

**话术模板**：
> "我的管理经验分两块。
> **项目维度**：在送物机器人和回收平台两个项目里，我是后端牵头人——负责需求拆解、方案评审、任务分配和交付质量，团队 X 人，跨后端/前端/嵌入式协作。
> **人的维度**：带教过 X 个新人/校招生，从环境搭建到独立交付有完整的培养路径。
> 正式的管理头衔时间不算长，但**方案评审、任务拆解、面试、绩效建议这些负责人职责我一直在实际承担**。
> 我理解从'带项目'到'带团队'还差的是：绩效的魄力、人才培养的体系化、以及跨项目的资源调配——这也是我看这个岗位的原因之一。"

> [!tip] 为什么这个答法安全
> 它把"没有正式头衔"转化成"**实际职责我都在做，我清楚差什么**"——
> 面试官要的不是头衔，是**你是否理解负责人这个角色在干什么**。

## 二、团队管理（职责 1）

| 问题              | 答题骨架                                                                                                     |
| --------------- | -------------------------------------------------------------------------------------------------------- |
| **怎么制定团队目标？**   | 从业务目标倒推：业务要什么 → 技术侧拆成「需求交付 + 技术治理」两条线 → 季度定 3-4 个可衡量的目标 → 迭代落地；**目标必须可验证**（上线时间、故障率、性能指标），不写"提升代码质量"这种虚的 |
| **怎么拆解和分工？**    | 按人扬长避短：核心/高风险模块给强的人，但要**交叉备份**避免单点；新人从边界模块切入，配 mentor；分工写在任务单上，验收标准前置                                    |
| **怎么定优先级？**     | 一个矩阵：**业务价值 × 技术风险**；业务要的排前，但**每迭代强制预留 15-20% 给技术治理**（否则技术债会吃掉未来的交付速度）                                   |
| **怎么做绩效？**      | ① **事前**定标准（写清楚"什么算好"）② **过程留痕**（任务单、review 记录、事故复盘）③ 结果**一对一面谈**，先让本人自评 ④ 改进项具体到行为；避免"凭印象打分"            |
| **遇到低绩效怎么办？**   | 先诊断原因（能力/意愿/分工不当）→ 明确改进项 + 时间盒（1-2 个迭代）→ 中间检查 → 确实不行**尽早处理**，拖着对团队伤害更大                                   |
| **怎么培养人？**      | 分层：新人（mentor 制 + 边界模块）、骨干（独立负责一个域 + 参加 review）、高级（牵架构 + 带人）；**培养靠"给有挑战的事 + 及时反馈"，不是靠讲课**                 |
| **核心成员要离职怎么办？** | 先真诚谈（了解真实原因）→ 能解决的解决；同时**立刻做交接与去单点化**（文档、交叉备份）——"任何人不该成为系统的单点"                                           |

## 三、研发流程与质量（职责 2、4）

| 问题 | 答题骨架 |
|---|---|
| **方案评审怎么搞？** | 门槛前置：影响多服务/数据结构变更/引入新组件的**必须评审**；评审材料模板（背景、方案对比、风险、回滚）；**评审的是取舍，不是表演**——没方案的会不开 |
| **Code Review 怎么推行？** | ① 工具前置（lint、checkstyle、Sonar）把低级问题挡在人工之前 ② review 标准模板（正确性 > 可读性 > 风格）③ **merge 前必须 1 个 approve** ④ review 意见对事不对人 ⑤ **负责人以身作则，自己也被人 review** |
| **有人不遵守规范怎么办？** | 先看规范是否合理（不合理就改）→ 再看是否有工具拦截 → 私下沟通 → 仍不改的，用数据说话（问题率）纳入绩效；**别用人情管流程** |
| **自动化测试怎么落地？** | 不追求覆盖率数字，抓**核心链路的集成测试 + 关键工具类的单测**；测试纳入 CI 卡口；老代码**改到哪补到哪**，不搞运动式补测 |
| **CI/发布/回滚** | 分支策略（主干 + 短生命周期分支）、CI 卡口（编译/单测/静态扫描）、发布走**灰度/滚动**，**发布必须能回滚**（一键回滚预案 + 数据兼容性检查） |
| **交付延期怎么办？** | 提前暴露（周会/日报看燃尽）→ 砍范围优先于降质量 → 加人只对可并行的任务有效（Brooks 定律）→ 事后复盘是**流程问题还是估算问题** |

## 四、架构演进与技术治理（职责 3）

| 问题 | 答题骨架 |
|---|---|
| **怎么制定架构演进路线？** | ① 先画现状（服务边界、依赖图、痛点清单）② 按业务Roadmap排演进优先级 ③ **每个阶段可执行、可验收**（不是"微服务化"三个字，而是"X 月把订单和积分拆开，指标是发布互不影响"）④ 小步快跑，不搞大重构运动 |
| **业务交付和技术治理冲突怎么办？** | 不硬顶业务：把治理项**拆小**塞进迭代（每迭代 15-20%）；对高风险技术债，用**故障数据**说服业务（"上季度 X 次故障，根因都是这个"）；**让业务方理解治理是交付速度的一部分** |
| **什么时候该拆微服务？** | 团队规模和业务边界到了再拆；**先模块化清楚，再物理拆分**；拆的判据是"独立部署的收益 > 分布式带来的复杂度" |
| **技术债怎么管理？** | 建清单（影响面/紧急度）→ 高危的按故障概率排期 → 在 code review 里防新增 → **定期公示给业务方** |

## 五、监控、SLO 与故障（职责 5）

| 问题 | 答题骨架 |
|---|---|
| **指标体系怎么建？** | 分层：**业务指标**（下单量、成功率）→ **应用指标**（QPS、P99、错误率，RED 方法）→ **资源指标**（CPU/内存/连接数，USE 方法）；核心链路必须有**大盘** |
| **SLO 怎么定？** | SLI（可测量的指标，如 P99<300ms、可用性 99.9%）→ SLO（目标值）→ 错误预算；**SLO 不是越高越好**，要和业务成本平衡 |
| **告警怎么治理？** | 告警必须**可行动**（收到知道干什么）；分级（P0 电话/P1 群通知/P2 日报）；定期清理不行动的告警——**告警疲劳比没告警更危险** |
| **线上事故怎么处理？** | **止血 → 定位 → 恢复 → 复盘**四步；先恢复服务（回滚/降级/扩容）再查根因；复盘**对事不对人**（blameless），输出 action items 并跟踪闭环 |
| **Trace 怎么落地？** | 全链路 traceId 贯穿（网关生成、MQ 透传、日志带 traceId）；SkyWalking/Zipkin；**能一眼看到慢在哪个环节**才算合格 |

## 六、工程文化（职责 7）

JD 原话："事实导向、主动负责、及时暴露风险并持续改进"

| 追问 | 答法要点 |
|---|---|
| 怎么让团队"及时暴露风险"？ | **关键是暴露风险不挨罚**——延期早报是好事，瞒报才是问题；负责人自己先示范（主动说自己的判断错了） |
| 怎么"事实导向"？ | 用数据争论，不用职位争论；复盘看日志和监控，不靠回忆和站队 |
| 团队氛围差/有抱怨怎么办？ | 先听（1v1）→ 分辨是情绪还是真问题 → 真问题进治理清单 → 处理结果公开反馈 |

## 七、情境题速答

- **"你带的人和你意见冲突，而且他是对的？"** → 采纳他的方案并公开承认（这建立信任）；事后一起复盘我当时的判断错在哪
- **"业务方压死线，技术上必须走捷径？"** → 可以走捷径，但**必须记录技术债 + 约定偿还时间 + 评估风险敞口**；绝不允许"无记录的捷径"
- **"接手一个烂摊子团队，先做什么？"** → 第 1 周只做三件事：**摸现状**（架构/人/在途需求）、**稳交付**（不改流程先保上线）、**建信任**（1v1 听每个人的看法）；第二个月再动流程
- **"你自己还要写代码，怎么平衡管理和编码？"** → JD 第 6 条就是"牵头人 + 核心代码编写"。答：管理占 60%，代码我**抓核心模块和关键 review**，不抢别人的活——负责人写代码是为了保持技术判断力，不是为了证明自己能写

## 八、反问清单（负责人视角）

1. 团队现在多少人？后端几人？**是接手现有团队还是从 0 组建？**（答法完全不同）
2. 团队目前最大的痛点是什么——交付慢、故障多，还是人不够？
3. 公司对这个岗位**未来 6 个月的期望**是什么？
4. 现在的技术栈和部署方式？（K8S 用了吗？微服务拆到什么程度？）
5. 绩效和调薪机制？
