# ⚡ 微服务治理 · 并发

> [[00-JD与匹配分析]] · 对应任职要求第 3 条 · 锁/AQS/线程池基础见 [[面试准备/技术面试题库/02-并发与多线程|通用题库·并发]]

> [!abstract] 负责人视角的并发
> JD 要的不是"你懂 AQS"，是"**系统的并发问题你能定位、能治理、能预防**"。
> 答题结构：**现象 → 定位 → 方案对比 → 治理机制**。

---

## 一、并发的四类典型问题（先分类再答题）

| 类型 | 典型现象 | 典型方案 |
|---|---|---|
| **超卖/资损类** | 库存扣成负数、余额扣穿 | 原子扣减（Lua/乐观锁）+ 预扣 |
| **重复类** | 重复下单、重复扣款 | 幂等（→ [[06-幂等]]） |
| **击穿类** | 热点失效打爆 DB | 互斥重建/逻辑过期 |
| **雪崩类** | 一个慢服务拖垮全链路 | 隔离 + 熔断 + 限流 |

---

## 二、锁的三个层次（选型是必考）

| 层次 | 手段 | 适用 | 风险 |
|---|---|---|---|
| **JVM 内** | synchronized / ReentrantLock / CAS | 单机内共享状态 | 多实例失效 |
| **数据库** | 乐观锁（版本号/条件更新）、悲观锁（for update） | 低频强一致写 | 悲观锁伤吞吐、锁等待 |
| **分布式** | Redis（Redisson）/ ZK | 跨实例互斥 | 锁过期、续期、脑裂 |

**选型决策**：
- **能不用分布式锁就不用**——先用**条件更新**（`update stock set n = n - 1 where id = ? and n >= 1`），天然原子且幂等友好
- 分布式锁用于**保护"不能重复执行的批处理/任务"**，而不是热点扣减
- **热点扣减用 Redis + Lua 预扣**，DB 异步落库

> [!tip] 金句
> "高并发下最好的锁是**不锁**——把互斥问题转化为**原子操作 + 幂等 + 排队**。"

---

## 三、高并发读

1. **多级缓存**：本地（Caffeine）→ Redis → DB；本地缓存要控容量与时效
2. **热点探测**：实时统计 top key → 自动加副本/推本地（京东热 key 方案思路）
3. **读扩散控制**：详情页聚合接口一次返回，避免前端 N+1 打后端
4. **静态化**：能 CDN/页面缓存的不要进应用层
5. **DB 读写分离**：注意主从延迟对业务的影响（→ [[09-数据库性能]]）

---

## 四、高并发写

1. **削峰填谷**：MQ 缓冲，消费端按 DB 承载力匀速（→ [[08-消息]]）
2. **合并写**：计数类先 Redis 累加，定时批量落库
3. **热点行拆分**：单行热点更新拆成 N 行随机取一（库存分段）
4. **异步化**：非核心链路（通知、积分、日志）异步，主链路只做必要校验
5. **批量**：insert 批量、update 合并，减少交互次数

---

## 五、限流与隔离（雪崩防护）

| 层 | 手段 |
|---|---|
| 入口 | 网关限流（IP/用户/接口维度）、验证码/排队 |
| 应用 | **Sentinel**（QPS/线程数/关联限流）、Guava RateLimiter（单机令牌桶） |
| 资源 | **线程池隔离**（核心/非核心分开）、信号量隔离 |
| 数据 | Redis 预扣、DB 连接池上限 |

**限流算法**：固定窗口（临界问题）→ 滑动窗口 → 漏桶（恒定速率）→ **令牌桶（允许突发，最常用）**。

**熔断降级**：失败率/慢调用比例触发 → 快速失败 → 半开试探恢复；**降级要有兜底数据**（默认值/缓存旧值/文案），不是简单抛异常。

---

## 六、线程模型与异步（深挖点）

- IO 密集用异步：`CompletableFuture` 编排（**必须传自定义线程池**，别用默认 ForkJoinPool）
- **线程池隔离（舱壁模式）**：每个下游依赖独立线程池/信号量，一个下游挂不拖垮全部
- **异步链路的三件事**：超时、上下文传递（traceId/TTL）、异常兜底
- 排查：线程池打满 → `jstack` 看线程都 WAITING 在哪 → 多半是下游慢 → 上隔离和超时

## 七、高频 Q&A

**Q1：库存扣减怎么做才不超卖？**
> 三方案并说：
> ① **DB 条件更新**：`update ... set n=n-1 where id=? and n>=1`，简单可靠，热点行有上限
> ② **Redis + Lua 预扣**：原子校验并扣减，异步落库，抗热点（要处理 Redis 与 DB 的一致性：先落库成功再确认，或对账）
> ③ 分段库存：单行热点拆 N 行，聚合值另算
> **选型：常规流量用 ①；秒杀/热点用 ②+③；资金类绝不用异步预扣。**

**Q2：接口 QPS 突然涨 10 倍，怎么扛？**
> 先保命再优化：① 限流保核心（非核心降级）② 缓存兜读 ③ MQ 削峰兜写
> 然后定位增长来源（营销活动？爬虫？攻击？）→ 对症：扩容、黑名单、活动预热。
> **负责人视角：建立容量预案——平时就知道系统水位上限是多少。**

**Q3：线程池参数怎么定？打满了怎么排查？**
> 参数是起点不是终点：CPU 密集 N+1、IO 密集 2N 起步，**最终靠压测**。
> 打满排查：看队列长度和拒绝数（先确认在拒绝）→ jstack 看线程栈卡在哪个下游 → 是慢 SQL/第三方超时 → 加超时、扩池、隔离。
> **根因常是"没设超时"**——所有远程调用必须有超时。

**Q4：缓存击穿时并发重建怎么防？**
> 互斥锁（只放一个请求去重建，其他等待/返回旧值）或**逻辑过期**（不设 TTL，值里带过期时间，过期后异步重建先返回旧值）。
> 热点 key 提前预热 + 逻辑过期是生产首选（避免重建期间的不可用窗口）。

**Q5：怎么预防并发问题？（治理视角）**
> ① 评审清单：写接口必须有幂等键、远程调用必须有超时、热点更新必须评估
> ② 压测常态化：大促前全链路压测，提前暴露水位
> ③ 监控前置：线程池队列、拒绝数、锁等待要有监控和告警
> ④ 复盘沉淀：每次并发事故变成一条评审检查项

---

## 八、一分钟话术

> "并发治理我按'读、写、隔离、预案'四块做。
> 读靠多级缓存和热点探测；写靠削峰、合并和热点行拆分——
> 库存这类我用 Redis + Lua 原子预扣，DB 异步落库，资金类绝不过度异步。
> 隔离上核心/非核心线程池分开，每个远程调用必须有超时，熔断降级有兜底数据。
> 治理上我会把**幂等键、超时、容量评估**放进架构评审清单，
> 大促前全链路压测拿到水位，让并发问题在上线前暴露，而不是在凌晨两点。"
