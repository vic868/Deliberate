# 🗄️ 微服务治理 · 缓存

> [[00-JD与匹配分析]] · 对应任职要求第 3 条 · 八股基础见 [[面试准备/技术面试题库/07-Redis与缓存|通用题库·Redis]]

> [!abstract] 差异化定位
> 通用题库解决了"穿透/击穿/雪崩是什么"。这篇解决负责人视角的三件事：
> **一致性方案的演进决策、线上治理（大key/热key/命中率）、出事时的应急**。

---

## 一、一致性方案的演进（讲"演进"比讲"方案"高一个段位）

```
阶段1：先删缓存再更新 DB
  → 并发下：删完缓存，读请求把旧值从 DB 回填 → 长期脏数据 ❌

阶段2：Cache Aside（先更新 DB，再删缓存）
  → 标准答案，但有两个残留问题：
     ① 读"删后更前"的间隙回填旧值（概率低）
     ② 主从延迟期间读到旧 DB 再回填 ❌

阶段3：延迟双删
  → 更新 DB → 删缓存 → 延迟 N ms → 再删一次
  → 延迟怎么定？覆盖"主从延迟 + 一次回填"的时间，经验值 500ms~1s，**只能缩小窗口不能根除**

阶段4：订阅 binlog 异步删缓存（Canal / Flink CDC）
  → 与业务解耦、可靠（MQ 重投）、天然覆盖主从延迟后的最终数据 ✅
  → 代价：引入链路组件，删缓存本身也可能失败 → 要重试 + 兜底
```

**最终答案模板**：
> "主链路用 Cache Aside（更新 DB 后删缓存）；
> 强要求下加 **Canal 订阅 binlog 异步删**，彻底解决主从延迟的回填脏数据；
> 所有缓存必须设 **TTL 兜底**（哪怕几分钟），再加**对账/命中率监控**。
> 我的立场是**最终一致**——为了缓存强一致付出分布式事务的代价不值得。"

---

## 二、三大问题速答 + 生产增强

| 问题 | 基础解法 | 生产增强 |
|---|---|---|
| **穿透**（查不存在的数据） | 空值缓存（短 TTL）、布隆过滤器 | 入口参数校验 + 风控（恶意扫描直接限流） |
| **击穿**（热点 key 过期瞬间） | 互斥锁重建 | **逻辑过期**（值里带过期时间，过期后异步重建、先返旧值）——生产首选，因为互斥锁会造成等待 |
| **雪崩**（大量 key 同时失效 / Redis 挂） | TTL 加随机、多级缓存 | **应急 SOP**：Redis 挂 → 熔断降级读 DB 的接口 + DB 限流，保住 DB 不被打死 |

> [!tip] 雪崩应急才是负责人答题点
> "雪崩发生时的第一动作不是修 Redis，是**保住 DB**：
> 对走 DB 的接口限流/降级非核心功能，宁可部分不可用，不能让 DB 被打穿。"

## 三、线上治理（负责人必答）

### 大 key
- **危害**：阻塞（单线程）、网络带宽、迁移/删除卡顿、内存不均
- **发现**：`redis-cli --bigkeys`、RDB 离线分析（redis-rdb-cli）、客户端埋点统计
- **治理**：拆分（hash 分桶）、压缩、**`unlink` 异步删除**（不是 `del`）、大 value 拆到对象存储

### 热 key
- **危害**：单分片 CPU 打满、带宽打满
- **发现**：`--hotkeys`（LFU 模式）、客户端统计、代理层监控
- **治理**：**本地缓存兜一层**（Caffeine，秒级过期）、key 加随机后缀打散到多个副本、读写分离

### 命中率监控
- 命中率**突然下降** = 故障信号之一：可能是失效策略变了、缓存被清、key 设计变更
- 要有**分业务前缀的命中率**，而不是只看全局

### 多级缓存的一致性
- 本地缓存（Caffeine）+ Redis 两级时，**本地缓存的时效必须短**（秒级）或用**版本号/广播失效**（Redis pub/sub 通知各实例删本地）
- 接受秒级不一致，别追求两级强一致

## 四、高频 Q&A

**Q1：为什么是"更新 DB 后删缓存"，不是"更新缓存"？**
> ① 更新缓存在并发写时会互相覆盖产生脏数据，删除天然幂等 ② 很多缓存值是计算聚合结果，写时算不如读时算（lazy） ③ 删除 + 惰性加载省掉无效写。

**Q2：延迟双删的延迟时间怎么定？**
> 覆盖"主从同步延迟 + 一次并发回填窗口"，经验 500ms~1s，放异步线程池执行。
> 但要诚实：**它只是缩小窗口，根除要靠 binlog 订阅或 TTL 兜底**。

**Q3：Redis 挂了业务怎么办？**
> 分级：核心读链路降级**读 DB 副本 + 限流**；写链路（依赖 Redis 的锁/计数）降级为 DB 条件更新；
> **所有降级开关平时就演练过**，不能现场想。

**Q4：缓存和 DB 双写不一致，你怎么发现？**
> 对账：抽样比对缓存与 DB（或只监控"删缓存失败率"和"binlog 订阅延迟"）；
> 再配合**过期时间**——所有不一致最终会被 TTL 清零，所以 TTL 是最后防线，必须设。

**Q5：什么数据适合放缓存？**
> 读多写少、可容忍短暂不一致、量可控。**资金余额这类强一致数据不要只放缓存**——要么不放，要么缓存只是展示层加速、以 DB 为准。

---

## 五、一分钟话术

> "缓存我三句话讲完。
> **一致性**：主链路 Cache Aside，强要求下加 Canal 订阅 binlog 异步删，
> TTL 是最后防线，立场是最终一致。
> **治理**：大 key 用 RDB 离线分析发现、unlink 异步删；热 key 本地缓存兜一层加副本打散；
> 分业务前缀监控命中率——命中率突变是故障信号。
> **应急**：Redis 挂的第一动作是保 DB——限流降级，预案平时演练过。
> 我团队的规则是：**所有缓存必设 TTL，所有热点必配本地兜底，所有降级必先演练**。"
