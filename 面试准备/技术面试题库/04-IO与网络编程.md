## 一、IO 模型

| 模型 | 说明 |
|---|---|
| BIO | 一连接一线程，阻塞；连接数大就崩 |
| NIO | **同步非阻塞 + 多路复用**；Selector 轮询就绪事件 |
| AIO | 异步回调，由 OS 完成后通知（Linux 支持不完善，少用） |

**五种 IO 模型**：阻塞 IO、非阻塞 IO、IO 多路复用、信号驱动、异步 IO

| 问题 | 得分骨架 |
|---|---|
| select / poll / epoll | select 有 1024 限制且 O(n) 轮询；poll 无限制但仍 O(n)；**epoll 基于红黑树 + 就绪链表，O(1)** |
| epoll LT vs ET | LT 水平触发（不处理会一直通知，默认，安全）；ET 边缘触发（只通知一次，**必须循环读到 EAGAIN**，效率高） |
| Java NIO 三大组件 | Channel、Buffer、Selector |
| Buffer 核心属性 | capacity / position / limit；`flip()` 写转读、`clear()` 重置、`compact()` 保留未读 |
| 零拷贝 | `mmap`（内存映射）、`sendfile`（内核态直接发，Kafka/Nginx 用）、`splice`；减少 CPU 拷贝与上下文切换 |
| 堆外内存 | `DirectByteBuffer`，减少一次拷贝；由 Cleaner 回收，注意 OOM |

## 二、Netty

| 问题 | 得分骨架 |
|---|---|
| 线程模型 | **主从 Reactor 多线程**：bossGroup 处理 accept，workerGroup 处理读写 |
| 核心组件 | EventLoopGroup、Channel、ChannelPipeline、ChannelHandler、ByteBuf |
| ByteBuf 优势 | 读写指针分离（无需 flip）、池化（PooledByteBufAllocator）、堆外内存、引用计数 |
| 粘包/拆包 | TCP 是字节流无边界；解法：定长、分隔符、**长度字段**（`LengthFieldBasedFrameDecoder`）、协议自带长度（如 MQTT） |
| 心跳 | `IdleStateHandler` + 自定义 handler 发心跳；配合重连（指数退避） |
| 为什么 Netty 快 | epoll + 多路复用、无锁串行化设计、池化、零拷贝、FastThreadLocal |
| 常见应用 | Dubbo、RocketMQ、gRPC、Spring WebFlux、ES |

## 三、TCP / HTTP

| 问题 | 得分骨架 |
|---|---|
| 三次握手 | SYN → SYN+ACK → ACK；**目的是确认双方收发能力 + 同步序列号**；两次不够（防历史连接） |
| 四次挥手 | FIN → ACK → FIN → ACK；TIME_WAIT 等 **2MSL** |
| 为什么 TIME_WAIT | 保证最后 ACK 到达、让旧报文消散 |
| **CLOSE_WAIT 过多** | 说明**被动关闭方没调 close()** → 代码 bug（连接泄漏） |
| TIME_WAIT 过多 | 短连接过多；解法：连接池、`tcp_tw_reuse`、调内核参数 |
| TCP 可靠传输 | 序列号 + 确认 + 超时重传 + 滑动窗口 + 拥塞控制（慢启动/拥塞避免/快重传/快恢复） |
| TCP vs UDP | 可靠有序 vs 快但不可靠；UDP 用于直播、DNS、游戏 |
| HTTP 1.0 / 1.1 / 2 / 3 | 短连接 / **长连接+管道化** / **多路复用+头部压缩+服务端推送** / **基于 QUIC（UDP）** |
| HTTPS 流程 | 证书验证 → 非对称协商出对称密钥 → 对称加密传输 |
| 对称 vs 非对称加密 | AES 快用于数据；RSA/ECC 慢用于密钥交换与签名 |
| WebSocket | 全双工长连接，握手用 HTTP Upgrade；适合推送/IM |
| MQTT | 轻量发布订阅，**QoS 0/1/2**、遗嘱、保留消息、Clean Session；**IoT 首选** |
| 长连接保活 | 心跳 + 超时重连 + 会话恢复；**重连风暴**要用退避 + 抖动 + 服务端限流放行 |
