## 一、基础概念

| 问题 | 得分骨架 |
|---|---|
| 线程 6 种状态 | NEW / RUNNABLE / BLOCKED / WAITING / TIMED_WAITING / TERMINATED |
| 创建线程的方式 | 继承 Thread / 实现 Runnable / Callable+FutureTask / **线程池（推荐）** |
| `start()` vs `run()` | `start` 才会创建新线程并走到 `run`；直接调 `run` 就是普通方法调用 |
| `sleep` vs `wait` | sleep 不释放锁（Thread 静态方法）；wait 释放锁（Object 方法，需在 synchronized 内） |
| `wait/notify` 为什么要配 while | **防虚假唤醒**（spurious wakeup）；`if` 只判断一次会出错 |
| `notify` vs `notifyAll` | 前者随机唤醒一个（可能唤醒错对象导致信号丢失），一般用 `notifyAll` |
| `join` / `yield` / `interrupt` | 等待线程结束 / 让出 CPU / 设置中断标志（不强制停止，靠协作） |
| 守护线程 | `setDaemon(true)`；JVM 在所有非守护线程结束后退出 |
| 线程优先级 | `setPriority` 只是提示，**不可靠**，别依赖 |

## 二、锁与内存模型 `#高频`

| 问题 | 得分骨架 |
|---|---|
| **JMM** | 主内存 + 工作内存；8 大原子操作；`happens-before` 规则（程序顺序、监视器锁、volatile、线程启动/终止、传递性） |
| **volatile** | 保证**可见性 + 禁止重排序**，**不保证原子性**；底层：内存屏障（LoadLoad/StoreStore 等）；DCL 单例必须加它 |
| **synchronized 原理** | 字节码 `monitorenter/monitorexit`；对象头 Mark Word |
| **锁升级** | 无锁 → 偏向锁 → 轻量级锁（CAS 自旋）→ 重量级锁（OS 互斥量）；**JDK15 后偏向锁默认禁用** |
| 偏向锁为什么要撤销 | 出现竞争时要升级，撤销需 STW（safepoint）；高竞争场景下反而拖慢 |
| 锁优化手段 | 锁消除、锁粗化、自适应自旋、读写分离 |
| `synchronized` vs `ReentrantLock` | 前者 JVM 层、自动释放、非公平、不可中断；后者 API 层、可中断、可超时、可公平、**支持多个 Condition** |
| **AQS 原理** `#高频` | `volatile int state` + CLH 双向队列 + CAS；`tryAcquire/tryRelease` 由子类实现；独占（ReentrantLock）与共享（Semaphore/CountDownLatch） |
| ReentrantLock 可重入实现 | state 累加 + 记录持有线程 |
| 公平锁 vs 非公平锁 | 公平锁按队列顺序（吞吐低）；非公平锁允许插队（默认，吞吐高） |
| **CAS 与 ABA** | 比较并交换；ABA 用**版本号**（AtomicStampedReference）解决；自旋开销大、只能保证一个变量 |
| LongAdder 为什么比 AtomicLong 快 | 分段累加（Cell 数组）分散 CAS 竞争；`sum()` 非强一致 |
| `ReadWriteLock` / `StampedLock` | 读读不互斥；StampedLock 支持乐观读（**不可重入**） |
| 死锁四条件 | 互斥、持有并等待、不可剥夺、循环等待；排查用 `jstack` 看 `deadlock`；避免：顺序加锁、tryLock 超时 |

## 三、线程池 `#高频`

**7 大参数**：corePoolSize / maximumPoolSize / keepAliveTime / TimeUnit / workQueue / threadFactory / handler

**执行流程**：
```
提交任务 → 核心线程未满? → 建核心线程
        → 队列未满?     → 入队
        → 未达最大线程? → 建非核心线程
        → 触发拒绝策略
```

| 问题 | 得分骨架 |
|---|---|
| 为什么先入队再加线程 | 避免频繁创建销毁线程；队列起到缓冲作用 |
| 4 种拒绝策略 | AbortPolicy（抛异常，默认）/ CallerRunsPolicy（调用者执行，**天然背压**）/ DiscardPolicy / DiscardOldestPolicy |
| 常见队列 | ArrayBlockingQueue（有界，推荐）/ LinkedBlockingQueue（默认**无界**，易 OOM）/ SynchronousQueue（不缓存）/ PriorityBlockingQueue |
| 线程数怎么定 | CPU 密集 N+1；IO 密集 2N 起步；**最终靠压测**，配合 QPS × 耗时估算 |
| 线程池为什么不用 Executors | `newFixedThreadPool`/`newSingleThreadExecutor` 用无界队列易 OOM；`newCachedThreadPool` 最大线程数是 Integer.MAX_VALUE 易创建过多线程 → **手动 new ThreadPoolExecutor** |
| 线程池状态 | RUNNING / SHUTDOWN / STOP / TIDYING / TERMINATED |
| `execute` vs `submit` | submit 返回 Future 且**会吞异常**（需 get 才抛出） |
| 线程池怎么优雅关闭 | `shutdown()` 不接受新任务、等已提交完成；`shutdownNow()` 中断 |
| 动态调整线程池 | 改 core/max + 队列容量；`setCorePoolSize` 后要唤醒 |

## 四、ThreadLocal `#高频`

- 结构：每个 Thread 持有 `ThreadLocalMap`，key 是 **ThreadLocal 弱引用**，value 强引用
- **内存泄漏**：key 被 GC 后变成 null，value 仍被 Thread 强引用 → 线程池里线程长期存活就泄漏
- 解决：**用完必须 `remove()`**（放在 finally）
- 用途：上下文传递（用户信息、TraceId）、SimpleDateFormat 复用
- **父子线程传递**：`InheritableThreadLocal`（线程池场景失效，要用阿里的 TransmittableThreadLocal）

在 Java 的 `synchronized` 内置锁机制中，**轻量级锁**与重量级锁（重锁）是 JVM（HotSpot）为了在不同线程竞争强度下平衡性能开销而设计的两种锁状态：

  

### 一、轻量级锁（Lightweight Lock）

- **设计初衷与适用场景**：
    
      
    - 适用于**多个线程在不同时间段交替执行同步块、但彼此没有实质性冲突**的轻度竞争场景。
        
          
        
    - 目的是利用用户态的 CAS 操作替代传统操作系统的互斥量，避免线程陷入内核态挂起与唤醒带来的性能损耗。
        
          
        
- **底层实现机制**：
    
      
    - **Mark Word 标志**：对象头中的锁标志位为 **`00`**，存储内容为指向当前线程栈帧中锁记录（Lock Record）的指针。
        
          
        
    - **加锁过程**：线程在进入同步块前，会在当前线程的栈帧中建立一个锁记录（Lock Record）空间。随后线程尝试通过 **CAS 操作**将加锁对象头的 Mark Word 替换为指向该 Lock Record 的指针。
        
          
        
    - **获取结果**：如果 CAS 替换成功，说明当前没有其他线程竞争，该线程成功获取轻量级锁；若 CAS 失败，说明存在其他线程争用，需要进一步处理。
        
          
        

### 二、重量级锁（Heavyweight Lock / 重锁）

- **设计初衷与适用场景**：
    
      
    - 适用于**高并发、锁争用激烈**的场景。
        
          
        
    - 当线程尝试通过自适应自旋等 CAS 方式多次尝试后仍无法获得锁时，锁会膨胀为重量级锁。
        
          
        
- **底层实现机制**：
    
      
    - **Mark Word 标志**：对象头中的锁标志位更新为 **`10`**，存储内容为指向 C++ 实现的监视器对象（`ObjectMonitor`）的指针。
        
          
        
    - **操作系统接入**：重量级锁依赖操作系统底层的互斥原语（如 Linux 下的 `pthread_mutex`）进行互斥排他控制。
        
          
        
    - **线程调度与开销**：未抢到锁的线程会被放入 `ObjectMonitor` 的阻塞队列（`_EntryList`）中挂起并进入 `BLOCKED` 状态。因为涉及用户态与内核态的上下文频繁切换，其调度开销较大，故被称为“重量级锁”。
        
          
        
    - **管程核心结构**：`ObjectMonitor` 内部维护了 `_owner`（当前持有锁的线程）、`_recursions`（锁重入次数）、`_EntryList`（阻塞等待队列）以及调用 `wait()` 挂起时存放线程的 `_WaitSet`（等待队列）。
        
          
        

### 三、核心维度对比

|**对比维度**|**轻量级锁 (Thin Lock)**|**重量级锁 (Fat Lock / 重锁)**|
|---|---|---|
|**锁标志位**|`00`|`10`|
|**Mark Word 存储内容**|指向线程栈帧中 Lock Record 的指针|指向堆外 `ObjectMonitor` 互斥量的指针|
|**底层依赖机制**|用户态 CAS 原子操作|操作系统互斥量（如 `pthread_mutex`）|
|**未抢到锁的线程行为**|通过自旋或重试继续争抢，不立刻阻塞挂起|被操作系统直接挂起，进入 `_EntryList` 等待唤醒|
|**性能与资源开销**|极低（仅消耗少许 CPU 自旋与内存指针替换）|较高（涉及用户态与内核态的频繁切换）|
|**触发转换关系**|产生实质性竞争、自旋多次仍失败时触发锁膨胀|由轻量级锁升级而来，锁升级通常是单向不可逆的|
