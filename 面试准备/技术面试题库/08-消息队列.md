## 一、为什么用 MQ

**三大作用**：解耦、异步、削峰填谷
**代价**：系统复杂度上升、一致性变弱、需要幂等与顺序处理

---

## 二、选型对比

| | Kafka | RocketMQ | RabbitMQ |
|---|---|---|---|
| 吞吐 | **最高**（百万级） | 高（十万级） | 中（万级） |
| 延迟 | ms 级 | ms 级 | **微秒级** |
| 顺序消息 | 分区内有序 | 支持**严格顺序**（队列级） | 队列内有序 |
| 事务消息 | 支持（较复杂） | **原生支持** | 不支持 |
| 延迟消息 | 不支持（需自建） | **支持（18 个级别）** | 插件 |
| 适用 | 日志、大数据、流处理 | **电商/业务**（事务、顺序、延迟） | 企业集成、路由灵活 |

## 三、Kafka 核心

| 问题 | 得分骨架 |
|---|---|
| 架构 | Producer → **Broker**（Topic → Partition → Replica）→ Consumer Group |
| 分区的作用 | 水平扩展 + 并行消费；**分区内有序，全局无序** |
| 副本与 ISR | leader 读写，follower 同步；**ISR = 与 leader 保持同步的副本集合** |
| `acks` 参数 | 0（不等）/ 1（leader 确认）/ -1 或 all（ISR 全确认） |
| HW 与 LEO | HW 消费者可见位置；LEO 日志末端；**只有 HW 之前的消息才能被消费** |
| 为什么快 | 顺序写磁盘 + 页缓存 + 零拷贝（sendfile）+ 批量压缩 + 分区并行 |
| 消费位移 | 老版本存 ZK，新版本存 `__consumer_offsets` |
| Rebalance | 消费者增减触发分区重分配 → **期间停止消费**；避免：合理设置 session.timeout、静态成员 |
| 幂等与事务 | 幂等 producer（PID+序列号）、事务（跨分区原子写） |

## 四、必答四问 `#高频`

### 1. 怎么保证消息不丢？
| 环节 | 措施 |
|---|---|
| 生产 | `acks=all` + 重试 + 同步发送 |
| Broker | 副本数 ≥3、`min.insync.replicas≥2`、刷盘策略 |
| 消费 | **手动提交 offset**（业务处理成功后再提交） |

### 2. 怎么保证不重复（幂等）？
> MQ 一般保证 **at least once**，重复不可避免 → 消费端做幂等
- **唯一键 + 去重表**（数据库唯一索引）
- Redis `setnx` 去重（注意并发与过期）
- 业务状态机（只允许特定状态流转）
- 数据库乐观锁 / 版本号

### 3. 怎么保证顺序？
- 全局有序：单分区/单队列（牺牲性能）
- **局部有序**：按业务键（如 orderId）hash 到同一分区，且单线程消费该分区
- 注意：重试队列会打乱顺序 → 需要顺序的场景别用重试乱序

### 4. 消息堆积怎么办？
- 先定位：消费者慢？还是生产突增？
- 应急：**增加消费者/分区数**（注意消费者数 ≤ 分区数）、提高消费并行度、批量消费
- 根因：优化消费逻辑（慢 SQL、外部调用）、异步化、加缓存
- 兜底：临时转存、降级、丢弃非核心消息（有策略地丢）

## 五、其他高频

| 问题 | 得分骨架 |
|---|---|
| 事务消息 | 半消息 → 执行本地事务 → 提交/回滚；回查机制兜底（RocketMQ） |
| 延迟消息 | RocketMQ 18 个延迟级别 / 时间轮；RabbitMQ 死信 + TTL |
| 死信队列 | 重试多次仍失败的消息转入，人工处理 |
| 消息积压后如何快速恢复 | 临时扩容 + 转存到新 topic 并行消费 |
| 推 vs 拉 | 推实时性好（Kafka 本质是长轮询拉） |
| 如何做广播 | 不同 consumer group / Kafka 不同 groupId |
