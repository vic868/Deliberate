## 一、先看清风险：AI 经历为什么最容易穿

面试官验证 AI 经历有**固定套路**，七连问基本能筛掉所有编造：

| # | 追问 | 编造者通常卡在 |
|---|---|---|
| 1 | 用的哪个模型？为什么选它？ | 说不出选型理由 |
| 2 | 上下文多大？超了怎么办？ | 只会说"够用" |
| 3 | chunk 怎么切？多少 token？重叠多少？ | 答不出具体参数 |
| 4 | 检索命中率多少？怎么评估的？ | **没有数字** |
| 5 | 为什么用向量库？不用 ES 的 BM25？ | 不懂两者差异 |
| 6 | 文档级权限怎么隔离？ | **这是最致命的，没做过想不到** |
| 7 | 幻觉怎么处理？成本多少？ | 只会说"加 Prompt" |

> [!danger] 一旦被识破，代价是"全盘失信"
> 你简历写了「精通高并发」「深入掌握框架源码」——面试官本来就在验证你。
> 如果 AI 部分是假的，他的结论不是"AI 这块不行"，而是"**这人整体在吹**"。
> 前面辛苦建立的信任会一起崩。

## 二、三条路，选哪条

### 策略 A：诚实定位 + 设计能力（今天就能用，零风险）

**简历那行改成**：
> AI 应用工程化：系统学习 LLM 原理与工程化落地（Prompt 工程、RAG、Agent），熟悉 Spring AI / LangChain 开发范式，**具备将其与现有 Java 微服务架构结合的设计能力**

**面试答法**：坦白没落地 → 亮出学习与实践 → **主动给出业务落地方案设计**（这是加分项，不是减分项）

### 策略 B：把已有的 demo 讲透（**你已经做到了**）

你已经有 Spring AI Alibaba 的 RAG demo——**这就是真东西，不用再造**。现在要做的是三件事：
1. 简历**如实**写"基于 Spring AI Alibaba 完成企业知识库 RAG Demo（个人实践项目）"
2. **回填细节**：语料是什么、chunk 多大、embedding 模型、向量库、Top-K、效果怎么验证
3. 准备「**如果要上生产还缺什么**」这道必杀题

> 完整答辩材料 → [[03-SpringAIAlibaba-RAG-Demo-答辩准备]]

> [!tip] 心态
> **demo 不掉价，讲不出细节才掉价。**
> 面试官对"个人 demo"预期本来就低，你把细节讲透就是超额交付。
> 反过来，写"企业级实战"却答不出生产问题，落差才是致命的。

### 策略 C：编造业务落地场景（**强烈不建议**）

即使侥幸过了面试，入职后同事一句"你们那个 RAG 怎么做的"就露。**收益远小于风险。**

> [!tip] 最优解：A + B
> 用 B 造出真实证据，用 A 的话术框架讲出来。这样你既有"真做过"的底气，又有"能设计"的高度。

## 三、核心话术：「你们的大模型用在哪里？」

> [!important] 这段背下来，四段式，**主动坦白反而加分**

**第一段 · 坦白，但要有主动权**

> "说实话，我现在负责的两个系统——酒店送物机器人后端和回收积分平台——都是纯业务系统，**没有落地大模型**。我不想编一个场景给您，因为一追问细节就露馅了，那对我们双方都是浪费时间。"

**第二段 · 把 AI 能力落到证据上**

> "我的大模型能力来自两块：一是系统学习，Transformer、RAG、Agent 这些原理我啃过；二是我自己做了实践项目——我搭了一个企业知识库 RAG，用 Spring AI + pgvector，完整处理了文档切分、混合检索、重排和文档级权限隔离，检索命中率做到了 X%。"

**第三段 · 把话题引到设计能力（真正的加分项）**

> "不过我很认真想过**这类业务**该怎么用。比如酒店送物机器人：客人说'送两瓶水到 1208'，ASR 转文本后交给 LLM 做意图识别和槽位抽取——房间号、物品、数量——用 Function Calling 直接生成结构化任务单，这样就不用做一层层的语音按键菜单了。机器人被挡住或超时的异常场景，可以让 LLM 生成安抚话术推到客房屏。回收平台那边更典型：**各地垃圾分类标准不一样，这正是 RAG 的标准场景**——把各地标准做成知识库，居民问'奶茶杯算什么垃圾'，检索后由模型回答并给出依据，再加多模态模型对拍照识别做兜底。"

**第四段 · 收尾，把定位说清楚**

> "所以我的定位是：**Java 工程化能力和高并发架构我是扎实的，大模型的原理和实践我也做了，现在缺的是一个真实的业务场景。** 这也是我为什么对这个岗位感兴趣。"

**为什么这样答反而更强**：面试官见过太多"我做过 RAG"然后被问穿的候选人。一个**敢说没做过、但能当场给出落地方案**的人，可信度和架构能力评价都更高。

## 四、如果还想把 demo 做扎实（可选增强，半天工作量）

> 目标：**做出一个你能讲 20 分钟、且全部是真的的东西**。

### 第 1 步：准备语料（1 小时）
把你**现有项目的文档**导出来：接口文档、业务规则、FAQ、运维手册。
- 20-50 个片段就够，不用多
- 格式：markdown 或 txt，一个主题一个文件
- 好处：面试时可以说"我把回收平台的业务规则做成了知识库"，**贴近你的真实经历**

### 第 2 步：技术选型（越简单越好）
| 组件 | 选择 | 理由 |
|---|---|---|
| 框架 | Spring Boot + **Spring AI** | 和你 Java 背景一致，简历已写 |
| 模型 | **你手上那个大模型** | 直接用，不用再找 |
| 向量库 | 先用内存版（`SimpleVectorStore`），进阶换 **pgvector** | 内存版当天能跑通；pgvector 可讲"为什么选它" |
| 切分 | 固定长度 + 重叠 | 300-500 token，重叠 10-20% |

### 第 3 步：跑通主链路（2-3 小时）
```
文档 → 切分 → Embedding → 存向量库 → 检索 Top-K → 拼 Prompt → 流式输出
```

### 第 4 步：加 3 个"工程化"点（这是区别于玩具的关键）
1. **来源引用**：回答里带上出自哪个文档，解决溯源
2. **文档级权限过滤**：给文档打标签，检索时**强制过滤**（面试官最爱问这个）
3. **简单评测**：准备 20 个问题，人工看命中率 → **这样你就有了"命中率 X%"这个数字**

### 第 5 步：准备"踩坑故事"（面试的加分项）
真实做过就一定有坑，挑 2 个讲：
- 切太大导致检索不准 / 切太小丢上下文
- 纯向量检索对专有名词不敏感 → 加 BM25 混合检索
- 中文 Embedding 模型选型踩坑
- 成本/延迟：加了缓存后降了多少

> [!success] 做完之后你的简历可以这样写（全部真实）
> 「独立完成企业知识库 RAG 系统（个人实践项目）：Spring Boot + Spring AI + pgvector，
> 实现文档切分、向量检索 + BM25 混合检索、来源引用与文档级权限过滤，
> 自建 20 题评测集，检索命中率 X%。」
