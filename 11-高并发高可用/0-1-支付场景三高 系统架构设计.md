# 支付系统架构设计（三高）

> 支付场景核心诉求：**资金安全 > 数据一致 > 高可用 > 高并发**
> 与电商秒杀不同，支付**不能靠"降级"牺牲一致性**，宁可拒绝服务也不能错账。

## 三、支付核心链路时序图

### 3.1 支付下单主流程（同步 + 异步）

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant GW as 支付网关
    participant R as 风控
    participant O as 订单服务
    participant RT as 渠道路由
    participant CH as 渠道适配
    participant WX as 微信/支付宝
    participant MQ as Kafka
    participant N as 通知服务
    participant M as 商户

    U->>GW: 发起支付请求(带幂等Key)
    GW->>GW: 验签 + 幂等校验(Redis)
    GW->>R: 风控检查
    R-->>GW: 通过 / 拒绝
    GW->>O: 创建支付单
    O->>O: 落库(状态=PAYING)
    O->>RT: 渠道路由
    RT-->>O: 选择渠道
    O->>CH: 调用渠道下单
    CH->>WX: 统一下单
    WX-->>CH: 返回 prepay_id
    CH-->>O: 返回支付参数
    O-->>GW: 返回给前端
    GW-->>U: 唤起收银台

    Note over WX,M: 用户完成支付后
    WX->>GW: 异步回调(notify)
    GW->>GW: 验签 + 幂等
    GW->>O: 更新订单状态=SUCCESS
    O->>MQ: 发送支付成功事件
    MQ->>N: 消费事件
    N->>M: 异步通知商户(重试+签名)
    M-->>N: ACK
```

## 四、关键设计点详解

### 4.1 幂等性（支付的生命线）

```mermaid
flowchart LR
    A[请求] --> B{Redis<br/>幂等Key存在?}
    B -- 是 --> C[返回上次结果]
    B -- 否 --> D[SETNX 占位]
    D -- 成功 --> E[执行业务]
    D -- 失败 --> C
    E --> F[更新结果到Redis]
    F --> G[返回]
```

**三层幂等**：

| 层级 | 手段 |
|------|------|
| 网关 | 商户订单号 + 签名去重 |
| 服务 | Redis SETNX + 唯一索引 |
| DB | `uk_merchant_order` 唯一约束兜底 |

---

### 4.2 分布式事务（账户扣款 + 订单更新）

```mermaid
flowchart TB
    subgraph TCC["TCC 模式（强一致场景）"]
        T1[Try: 冻结额度] --> T2[Confirm: 扣减]
        T1 --> T3[Cancel: 解冻]
    end

    subgraph MQ_TX["本地消息表 + MQ（最终一致）"]
        M1[业务操作 + 消息落库<br/>同一本地事务] --> M2[投递MQ]
        M2 --> M3[下游消费]
        M3 --> M4[失败重试 + 对账补偿]
    end

    subgraph SAGA["Saga 模式（长流程）"]
        S1[步骤1] --> S2[步骤2] --> S3[步骤3]
        S3 -.失败.-> C2[补偿2]
        C2 --> C1[补偿1]
    end
```

**支付系统推荐**：
- 核心扣款 → **TCC**
- 通知/清结算 → **本地消息表 + MQ**
- 跨系统长流程 → **Saga**

---

### 4.3 渠道路由（高可用关键）

```mermaid
flowchart TB
    REQ[支付请求] --> RULE{路由规则}
    RULE -->|费率优先| C1[渠道A 0.38%]
    RULE -->|成功率优先| C2[渠道B 99.9%]
    RULE -->|灰度/降级| C3[渠道C 备用]
    C1 --> HC{健康检查}
    C2 --> HC
    C3 --> HC
    HC -->|健康| SEND[发起支付]
    HC -->|故障| FAILOVER[自动切换]
    FAILOVER --> C2
```

**路由策略**：
- 权重轮询 + 成功率动态调整
- 渠道故障自动熔断（Sentinel）
- 多渠道路由兜底（微信挂了切支付宝）

### 4.4 热点账户问题

```mermaid
flowchart LR
    subgraph Problem["问题：大商户账户被高并发扣款"]
        P1[1000 TPS 打同一账户]
    end

    subgraph Solution["解决：账户分片 + 异步汇总"]
        S1[账户拆分为 N 个子账户] --> S2[请求按 hash 分散]
        S2 --> S3[异步汇总到主账户]
        S3 --> S4[定时对账校验]
    end

    Problem -.-> Solution
```

**手段**：
1. **账户分片**：一个逻辑账户拆 N 个物理子账户
2. **异步记账**：请求先入 MQ，串行消费
3. **缓冲记账**：Redis 累加，定期落库
4. **行锁优化**：`UPDATE ... WHERE balance >= amount` 替代 `SELECT FOR UPDATE`

## 五、高可用部署拓扑

```mermaid
flowchart TB

        N1[Nginx]

        DB1[(MySQL 主)]
        R1[(Redis 主)]
    end

    subgraph AZ2["同城可用区 B"]
        N2[Nginx]
        K2[K8s Node Pool]
        DB2[(MySQL 从)]
        R2[(Redis 从)]
    end

    subgraph AZ3["异地灾备"]
        K3[K8s 冷备]
        DB3[(MySQL 异地从)]
    end

    VIP[VIP / GSLB] --> N1 & N2
    N1 --> K1
    N2 --> K2
    DB1 <-->|半同步复制| DB2
    DB2 -.异步.-> DB3
    R1 <-->|主从| R2
    K1 -.跨区调用.-> K2
```

**多活策略**：

| 级别 | 说明 |
|------|------|
| 同城双活 | 两个 AZ 同时承载流量，RTT < 2ms |
| 异地多活 | 单元化，用户按 ID 路由到固定单元 |
| 异地灾备 | 冷备/温备，RTO < 30min，RPO ≈ 0 |

## 七、性能与容量设计

| 维度 | 目标 | 手段 |
|------|------|------|
| 峰值 QPS | 10w+ | 无状态 + HPA + 异步化 |
| P99 延迟 | < 200ms | 缓存 + 连接池 + 异步 |
| 成功率 | > 99.99% | 多渠道路由 + 熔断 |
| 数据零丢失 | RPO = 0 | 半同步复制 + 本地消息表 |
| 故障恢复 | RTO < 30s | K8s 自愈 + 自动切换 |

## 八、设计原则（支付版）

> [!important] 支付系统铁律
> 1. **宁可拒绝，不可错账** —— 一致性优先于可用性
> 2. **一切皆幂等** —— 网络不可靠，重试是常态
> 3. **状态机严格流转** —— 禁止状态跳跃
> 4. **对账是最后防线** —— 再完美的系统也要兜底
> 5. **资金操作必须留痕** —— 审计日志不可篡改
> 6. **渠道必须多活** —— 单渠道 = 单点
> 7. **热点必须隔离** —— 大商户不能拖垮全局
> 8. **灰度 + 回滚** —— 支付变更零容忍
