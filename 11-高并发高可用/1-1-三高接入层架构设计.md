# 接入层详细设计（支付场景 · 三高）

> [!abstract] 接入层定位
> 接入层是**流量的第一道闸门**，承担：**抗攻击、负载均衡、限流、SSL 卸载、灰度路由、可观测埋点**。
> 支付场景下，接入层还必须是**资金安全的第一道防线**：验签、防重放、防篡改。

---

## 一、接入层在整体架构中的位置

```mermaid
flowchart TB
    subgraph Internet["公网"]
        U[用户/商户]
        ATK[攻击流量]
    end

    subgraph Access["接入层（本文重点）"]
        DNS[GSLB / 智能DNS]
        CDN[CDN 边缘]
        WAF[WAF + DDoS 高防]

    end

    subgraph Inner["内网"]
        ING[K8s Ingress]
        SVC[后端服务]
    end

    U --> DNS --> CDN --> WAF --> LVS --> NG --> ING --> SVC

```

**分层职责**：

| 层级 | 组件 | 核心职责 |
|------|------|----------|
| L0 | GSLB / 智能 DNS | 就近接入、机房级容灾 |
| L1 | CDN | 静态加速、边缘缓存、抗量 |
| L2 | WAF / 高防 | 攻击清洗、CC 防护 |
| L3 | LVS + Keepalived | 四层负载、VIP 漂移 |
| L4 | Nginx 集群 | 七层负载、限流、SSL、路由 |
| L5 | K8s Ingress | 服务发现、灰度、金丝雀 |

## 二、逐层详解

### 2.1 GSLB / 智能 DNS

```mermaid
flowchart LR
    U[用户请求<br/>pay.xxx.com] --> DNS{智能DNS}
    DNS -->|华东用户| AZ1[华东机房 VIP]
    DNS -->|华北用户| AZ2[华北机房 VIP]
    DNS -->|华南用户| AZ3[华南机房 VIP]
    AZ1 -.健康检查失败.-> DNS
    DNS -.自动摘除.-> AZ2
```

**能力**：
- **就近接入**：按运营商 + 地域解析
- **健康探测**：机房级故障自动摘除
- **权重调度**：灰度 / 容量分配
- **秒级切换**：TTL 设小（30s）+ 备 IP

> [!warning] 坑点
> DNS 缓存不可控，切换有延迟。核心支付域名建议 **TTL ≤ 60s**，并配合 **HTTPDNS** 兜底。

### 2.2 CDN 边缘层

```mermaid
flowchart TB
    U[用户] --> EDGE[CDN 边缘节点]
    EDGE -->|命中| CACHE[返回缓存]
    EDGE -->|未命中| ORIGIN[回源 Nginx]
    ORIGIN --> SVC[后端服务]

    subgraph Static["适合 CDN"]
        S1[静态资源 JS/CSS/图片]
        S2[收银台页面]
        S3[对账文件下载]
    end

    subgraph Dynamic["不适合 CDN"]
        D1[支付下单接口]
        D2[回调通知]
        D3[账户查询]
    end
```

**支付场景策略**：
- **动态接口**：`Cache-Control: no-store`，禁止缓存
- **静态资源**：长缓存 + 文件名 hash
- **敏感接口**：CDN 层直接 bypass，不回源前不落任何数据

### 2.3 WAF + DDoS 高防

```mermaid
flowchart LR
    IN[入站流量] --> CLEAN{流量清洗中心}
    CLEAN -->|正常| PASS[放行]
    CLEAN -->|攻击| DROP[丢弃/挑战]
    PASS --> WAF{WAF 规则引擎}
    WAF -->|SQL注入/XSS| BLOCK[拦截]
    WAF -->|CC攻击| CHALLENGE[人机校验]
    WAF -->|正常| BACK[回源]
```

**防护矩阵**：

| 攻击类型 | 手段 |
|----------|------|
| DDoS 流量 | 高防 IP + 流量清洗 |
| CC 攻击 | 频率限制 + 人机验证 |
| SQL 注入 | WAF 规则 + 参数化 |
| XSS | 输入过滤 + CSP |
| 爬虫 | UA/行为分析 + 指纹 |
| 重放攻击 | 时间戳 + Nonce + 签名 |

> [!important] 支付特有防护
> - **防重放**：请求带 `timestamp + nonce`，服务端校验 5 分钟窗口
> - **防篡改**：全参数签名（RSA2 / HMAC-SHA256）
> - **防伪造**：商户证书双向校验

### 2.4 LVS + Keepalived（四层）

```mermaid
flowchart TB
    subgraph VIP["VIP 192.168.1.100"]
        MASTER[LVS Master<br/>Keepalived BACKUP]
        BACKUP[LVS Backup<br/>Keepalived MASTER]
    end

    MASTER -.VRRP 心跳.-> BACKUP
    MASTER --> RS1[RealServer Nginx-1]
    MASTER --> RS2[RealServer Nginx-2]
    MASTER --> RS3[RealServer Nginx-3]

    subgraph Mode["转发模式"]
        DR[DR 模式<br/>性能最高]
        NAT[NAT 模式<br/>配置简单]
        TUN[TUN 模式<br/>跨机房]
    end
```

**选型建议**：
- 同机房 → **DR 模式**（响应直接回客户端，性能最优）
- 跨机房 → **TUN 模式**
- 小规模 → **NAT 模式**

**Keepalived 要点**：
- VRRP 心跳间隔 1s，抢占延迟 3s
- 健康检查脚本探测 Nginx 端口
- 脑裂防护：`nopreempt` + 单播

#### 2.5.3 关键配置示例

```nginx
# ============ 上游集群 ============
upstream pay_backend {
    least_conn;
    server 10.0.1.10:8080 weight=5 max_fails=3 fail_timeout=10s;
    server 10.0.1.11:8080 weight=5 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 weight=3 backup;
    keepalive 200;
}

# ============ 限流 ============
limit_req_zone $binary_remote_addr zone=pay_req:100m rate=100r/s;
limit_conn_zone $binary_remote_addr zone=pay_conn:100m;

# ============ 缓存 ============
proxy_cache_path /data/cache levels=1:2 keys_zone=pay_cache:100m
                 max_size=10g inactive=60m use_temp_path=off;

server {
    listen 443 ssl http2;
    server_name pay.xxx.com;

    # SSL 卸载
    ssl_certificate     /etc/nginx/certs/pay.crt;
    ssl_certificate_key /etc/nginx/certs/pay.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    # 安全头
    add_header Strict-Transport-Security "max-age=31536000" always;
    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options DENY;

    # 支付下单接口：严格限流 + 不缓存
    location /api/pay/create {
        limit_req zone=pay_req burst=200 nodelay;
        limit_conn pay_conn 50;
        proxy_cache off;
        proxy_pass http://pay_backend;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Request-Id $request_id;

        # 超时控制
        proxy_connect_timeout 2s;
        proxy_send_timeout    5s;
        proxy_read_timeout    5s;
    }

    # 灰度：按 header 分流
    location /api/ {
        if ($http_x_gray = "v2") {
            proxy_pass http://pay_backend_v2;
        }
        proxy_pass http://pay_backend;
    }

    # 健康检查
    location /nginx_status {
        stub_status;
        allow 10.0.0.0/8;
        deny all;
    }
}
```

#### 2.5.4 负载均衡算法对比

```mermaid
flowchart LR
    subgraph Algo["算法选型"]
        RR[round-robin<br/>通用]
        LC[least_conn<br/>长连接场景]
        IPH[ip_hash<br/>会话保持]
        CH[consistent_hash<br/>缓存亲和]
    end

    RR -->|支付下单| PAY[推荐 least_conn]
    LC -->|支付下单| PAY
    IPH -->|不推荐| NO[破坏负载均衡]
    CH -->|热点账户| HOT[推荐]
```

> [!tip] 支付场景选型
> - 下单接口 → `least_conn`（避免慢节点堆积）
> - 热点账户 → `consistent_hash`（同一账户固定节点，减少锁竞争）
> - **避免 `ip_hash`**：NAT 出口会导致流量倾斜

## 三、限流体系（接入层核心能力）

### 3.1 多级限流架构

```mermaid
flowchart TB
    REQ[请求] --> L1{L1 CDN<br/>IP 频次}
    L1 -->|超限| D1[拒绝]
    L1 --> L2{L2 WAF<br/>CC 防护}
    L2 -->|超限| D2[人机验证]
    L2 --> L3{L3 Nginx<br/>limit_req}
    L3 -->|超限| D3[429]
    L3 --> L4{L4 Ingress<br/>注解限流}
    L4 -->|超限| D4[429]
    L4 --> L5{L5 服务<br/>Sentinel}
    L5 -->|超限| D5[降级]
    L5 --> SVC[业务处理]
```

### 3.2 限流算法对比

```mermaid
flowchart LR
    subgraph Algo["限流算法"]
        A1[固定窗口<br/>简单/有临界问题]
        A2[滑动窗口<br/>平滑/内存高]
        A3[漏桶<br/>恒定速率/无突发]
        A4[令牌桶<br/>允许突发/推荐]
    end

    A4 -->|支付下单| R[推荐]
    A3 -->|回调通知| R
    A1 -->|粗粒度| OK[可用]
    A2 -->|精细| OK
```

### 3.3 限流维度

| 维度 | 示例 | 场景 |
|------|------|------|
| IP | 100 r/s | 防刷 |
| 商户 | 1000 r/s | 大商户隔离 |
| 接口 | 5000 r/s | 核心接口保护 |
| 用户 | 10 r/s | 防误操作 |
| 全局 | 10w r/s | 系统容量红线 |

> [!important] 限流优先级
> **商户维度 > IP 维度 > 全局维度**
> 支付场景必须做**商户级限流**，避免单商户拖垮全局。

```nginx
    check_http_send "GET /health HTTP/1.0\r\n\r\n";
    check_http_expect_alive http_2xx http_3xx;
}
```

## 六、支付场景特有的接入层设计

### 6.1 验签与防重放

```mermaid
sequenceDiagram
    participant M as 商户
    participant NG as Nginx
    participant GW as 支付网关

    M->>NG: 请求 + sign + timestamp + nonce
    NG->>NG: 1. IP 白名单校验
    NG->>NG: 2. timestamp 窗口校验(±5min)
    NG->>GW: 透传
    GW->>GW: 3. nonce 去重(Redis)
    GW->>GW: 4. RSA2 验签
    GW->>GW: 5. 业务处理
    GW-->>M: 响应
```

> [!warning] 关键点
> - **验签在网关层做**，Nginx 只做粗粒度校验（IP、时间戳）
> - **nonce 存储**：Redis `SETNX` + TTL 10min
> - **签名算法**：RSA2（非对称）优于 MD5（对称）

### 6.2 商户隔离

```mermaid
flowchart TB
    REQ[商户请求] --> ID{识别 merchant_id}
    ID -->|大商户 A| UA[upstream_A<br/>独立资源池]
    ID -->|大商户 B| UB[upstream_B<br/>独立资源池]
    ID -->|中小商户| UC[upstream_common<br/>共享池]

    UA --> QA[独立限流 5000/s]
    UB --> QB[独立限流 3000/s]
    UC --> QC[共享限流 10000/s]
```

### 6.3 回调通知入口

```mermaid
flowchart LR
    WX[微信回调] --> CB[专用回调域名<br/>notify.xxx.com]
    CB --> WAF_CB[独立 WAF 规则]
    WAF_CB --> NG_CB[独立 Nginx 集群]
    NG_CB --> GW_CB[回调网关]
    GW_CB --> VERIFY[验签 + 幂等]
    VERIFY --> MQ[(Kafka)]
```

> [!tip] 为什么回调要独立入口？
> - 回调流量特征与用户流量不同（突发、来源固定）
> - 独立入口可单独限流、单独扩容
> - 避免被用户流量挤占，导致回调延迟 → 商户投诉

## 七、容量与性能

### 7.1 Nginx 性能调优

```nginx
worker_processes auto;              # = CPU 核数
worker_rlimit_nofile 100000;        # 文件描述符

events {
    worker_connections 10000;       # 单 worker 连接数
    use epoll;                      # Linux 高效模型
    multi_accept on;
}

http {
    keepalive_timeout 65;
    keepalive_requests 1000;
    client_max_body_size 10m;
    client_body_buffer_size 128k;

    # 开启高效传输
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;

    # 连接池
    upstream pay_backend {
        keepalive 200;
        keepalive_requests 1000;
        keepalive_timeout 60s;
    }
}
```

### 7.2 容量估算

```mermaid
flowchart LR
```
