# 02 · 结构化思维：5W1H 与任务拆解（WBS）

> 接到任务的两板斧：**先用 5W1H 把事问清楚，再用 WBS 把事拆明白。**
> 拆不明白的事不要承诺，问不清楚的活不要开工。

## 一、5W1H：把问题问全的万能清单

| 要素 | 含义 | 要问的问题 | 管理场景 |
|---|---|---|---|
| **What** | 是什么 | 目标/交付物到底是什么？验收标准是什么？ | 接需求、立项 |
| **Why** | 为什么 | 为什么要做？不做会怎样？优先级依据？ | 拒绝伪需求、对齐目标 |
| **Who** | 谁 | 谁来做？谁负责（R）？谁批准（A）？谁配合？谁受影响？ | 分工、干系人识别 |
| **When** | 何时 | 关键节点、deadline、依赖的时间点？ | 排期、里程碑 |
| **Where** | 何地 | 在哪个系统/环境/模块/市场发生？ | 范围界定 |
| **How** | 如何做 | 方案、流程、步骤、风险与应对？ | 出方案、定流程 |
| **How much** | 多少 | 要投入多少人/钱/时间？产出如何量化？（5W2H） | 估算、ROI |

### 两个升级用法

**① 用来"翻译需求"** —— 业务方说"把性能搞快点"，你回：
> "What：具体哪个接口、什么场景？Why：影响的是下单转化还是客诉？How much：目标 P99 是多少？When：最晚什么时候要？"
> —— 5 个问题问完，需求就从一句话变成了一张可排期的任务卡。

**② 用来"描述问题"**（向上汇报 / 写 bug 单 / 事故报告）：
> "What：支付回调大面积超时；Where：prod 华南集群；When：大促 20:00–20:15；Who：影响约 3k 订单；How：已回滚 + 限流；How much：预计资损 X 元。"
> —— 要素齐全的描述 = 专业。

### 5Why：往下挖根因（5W1H 的纵向版）
现象 → 为什么？→ 为什么？→ …（直到流程/机制层面，而不是"某人不小心"）
> 示例：发布会延期 → 为什么？联调晚 → 为什么？接口文档 3 天才出 → 为什么？需求评审拖了一周 → 为什么？**没有评审 deadline 和 owner** ← 到这里才是可修复的根因。

## 二、WBS：把大象切成能下嘴的块

**定义**：Work Breakdown Structure，以**可交付成果**为导向的层层拆解，拆到"能估算、能分配、能验收"为止。

### 拆解四原则

1. **100% 原则**：子任务之和 = 父任务全部范围，不漏不重（MECE）。
2. **动词/名词清晰**：工作包是"做什么"，命名统一，不混进度表、不混预算表。
3. **拆到"一人一周内可完成"**（80 小时法则）：太大控不住，太碎管不过来。
4. **每项带三件套**：**Owner + Due Date + 验收标准**，否则不算拆完。

### 拆解层级

```
项目（结果）
 └─ 阶段 / 里程碑（Phase）
     └─ 交付物（Deliverable）
         └─ 工作包（Work Package，能估能分能验收）
             └─ 活动（Activity，排期用）
```

### 实战示例：「双十一大促保障」

```
双十一大促保障（目标：大促 0 重大故障）
├── 1. 容量规划
│   ├── 1.1 压测方案与场景设计        [Owner:A][Due:10/15][验收:场景覆盖 Top5 链路]
│   ├── 1.2 全链路压测执行            [Owner:B][Due:10/20][验收:3 倍预估峰值通过]
│   └── 1.3 瓶颈定位与扩容            [Owner:C][Due:10/25][验收:压测报告归档]
├── 2. 稳定性治理
│   ├── 2.1 核心链路限流熔断配置      [Owner:D][Due:10/18][验收:配置上线+演练通过]
│   ├── 2.2 依赖中间件降级预案        [Owner:E][Due:10/18][验收:预案文档+开关就绪]
│   └── 2.3 单点与慢 SQL 治理         [Owner:F][Due:10/22][验收:遗留问题清零]
├── 3. 应急指挥
│   ├── 3.1 值班表与升级路径          [Owner:G][Due:10/25][验收:值班群发布]
│   ├── 3.2 故障演练（Chaos）         [Owner:H][Due:10/28][验收:演练复盘报告]
│   └── 3.3 复盘机制与模板            [Owner:G][Due:10/28][验收:模板评审通过]
└── 4. 汇报与协同
    ├── 4.1 大促作战室与节奏          [Owner:PM][Due:10/28][验收:日站会运行]
    └── 4.2 阶段进展向干系人汇报      [Owner:PM][Due:每 3 天][验收:周报发出]
```

> 拆完自测：**每片叶子能不能在 1 分钟内讲清"谁、什么时候、做到什么样算完"？** 不能就继续拆。

### 拆完之后：责任分配表（RACI）

| 任务 | R执行 | A最终负责 | C被咨询 | I被告知 |
|---|---|---|---|---|
| 全链路压测 | B | 项目经理 | 架构师 | 运维 |
| 限流熔断配置 | D | 项目经理 | SRE | 客服团队 |

> ⚠️ 每行**有且只有一个 A**。A 不唯一 = 出事没人兜；A 为空 = 出事没人管。

## 三、组合拳：从接活到交活的完整链路

```
① 5W1H 问清楚（What/Why/How much…）
        ↓
② WBS 拆到工作包（能估、能分、能验收）
        ↓
③ 估工期 + 定优先级（关键路径 / 四象限）
        ↓
④ RACI 分责任 + 定里程碑
        ↓
⑤ 日站会/周例会盯偏差（燃尽图）
        ↓
⑥ 里程碑验收 + GRAI 复盘（沉淀进模板/流程）
```

## 四、常见坑（自检清单）

- [ ] 拆成了"人"而不是"事"（"小王的部分" ≠ 工作包）
- [ ] 任务没有验收标准 → 永远"做完了但不对"
- [ ] 只拆执行、漏了"评审/测试/发布/沟通"这些隐形工作
- [ ] 漏外部依赖（联调、审批、采购），关键路径上全是乐观估计
- [ ] 加排期 buffer 时"人人有份"，而不是给高风险项加（风险储备 vs 管理储备）
- [ ] 拆完就锁死，需求一变不走变更流程 → 范围蔓延
