## 一、Kafka 到底是什么

### 1.1 三个身份

Kafka 官方定位是**分布式流式平台（Distributed Streaming Platform）**，它同时是：

| 身份 | 含义 | 典型用法 |
|---|---|---|
| **消息系统** | 发布/订阅消息队列，解耦生产与消费 | 业务解耦、异步、削峰填谷 |
| **存储系统** | 消息按配置保留（小时～永久），可反复读取、可回溯 | 事件溯源、CDC 落库、审计日志 |
| **流处理平台** | 提供 Streams API 做有状态的流式计算 | 实时聚合、ETL、窗口统计 |

> [!tip] 一句话抓住本质
> **Kafka 的本质是一个分布式、分区、多副本的「提交日志（Commit Log）」**。
> 消息一旦写入就不可变，只能追加；消费者只是拿着自己的位移（offset）在这条日志上"往前追"。
> 理解了"它是一个日志，不是传统意义上的队列"，很多设计就顺理成章了：为什么消息能重复读、为什么消费不影响存储、为什么顺序性只在分区内成立。

### 1.2 与传统队列的关键差异

| 维度 | 传统 MQ（如 RabbitMQ） | Kafka |
|---|---|---|
| 消费后消息 | 通常被删除 | **保留**（按时间/大小策略），可重复消费 |
| 消费语义 | Broker 推送（push） | 消费者**拉取**（pull），自己管理位移 |
| 顺序性 | 队列内有序 | **分区内有序**，全局无序 |
| 扩展方式 | 增加消费者（队列共享） | **增加分区 + 消费者**（分区是并行单位） |
| 存储定位 | 以"传递"为核心，存储很轻 | **以"日志"为核心，存储是一等公民** |
| 吞吐量级 | 万级 | 十万～百万级 |

> [!note] 拉模式（Pull）为什么更适合 Kafka
> ① 消费者按自身处理能力拉取，天然实现**背压**，不会被压垮；② 可以批量拉取，提高吞吐；③ 可以自由 `seek` 回溯。代价是当没有数据时会有空轮询，Kafka 用 `fetch.max.wait.ms` + `fetch.min.bytes` 的**长轮询**来缓解。

## 二、核心角色全景

### 2.1 架构总图

```

                    │                                                     │
  ┌──────────┐      │   ┌──────────────┐        ┌──────────────┐         │      ┌─────────────────┐
  │ Producer │──────┼──▶│  Broker 1    │        │  Broker 2    │         │      │ Consumer Group A│
  │  (生产者) │      │   │              │        │              │         │      │ ┌─────────────┐ │
  └──────────┘      │   │ T1-P0(Leader)│        │ T1-P0(Follower)│       │      │ │ Consumer 1  │ │
        │           │   │ T1-P1(Follower)       │ T1-P1(Leader)│         │◀─────┼─│ P0,P1       │ │
        │           │   │ T1-P2(Follower)       │ T1-P2(Leader)│        │      │ └─────────────┘ │
        │           │   └──────────────┘        └──────────────┘         │      │ ┌─────────────┐ │
        │           │          ▲                      ▲                 │      │ │ Consumer 2  │ │
        │           │          │   副本同步(fetch)     │                 │◀─────┼─│ P2          │ │
        │           │          └──────────────────────┘                 │      │ └─────────────┘ │
        │           │                                                     │      └─────────────────┘
        │           │   ┌──────────────────────────────┐                 │
        └───────────┼──▶│  Controller / KRaft Quorum   │  元数据管理      │
                    │   │  (__cluster_metadata 日志)    │                 │
                    │   └──────────────────────────────┘                 │
                    └─────────────────────────────────────────────────────┘
```

### 2.2 角色职责表

| 角色 | 职责 | 关键点 |
|---|---|---|
| **Producer** | 生产消息，决定发往哪个分区的哪个副本（其实只发给 leader） | 客户端组件，不占集群资源；批量发送 |
| **Broker** | 一个 Kafka 服务节点；存储分区副本、响应读写请求 | 无状态意味很弱——**它是有状态的（存数据）**，但不维护消费者的消费进度 |
| **Controller** | 集群中唯一，负责分区/副本状态变更、leader 选举、Topic 创建 | KRaft 模式下由 controller 角色的节点承担 |
| **Group Coordinator** | 管理消费组成员、位移提交、触发 Rebalance | 由某个 broker 承担，由 `__consumer_offsets` 分区决定 |
| **Transaction Coordinator** | 管理生产者事务状态 | 由某个 broker 承担，见 [[6-事务与Exactly-Once]] |
| **Consumer** | 拉取消息、维护位移、处理业务 | 属某个消费组；位移由自己（客户端）提交 |
| **Consumer Group** | 逻辑上的一个"订阅者"，组内分摊分区 | 分区与消费者一一对应 |

> [!warning] Controller 与 Coordinator 别搞混
> - **Controller**：管**分区和副本**（谁是 leader、副本放哪），集群级、通常只有一个。
> - **Coordinator**：管**消费组和位移**（谁属于哪个组、位移是什么），是**按消费组分散**到不同 broker 的。
> 面试常被问"消费组的位移存在哪"——答案是内部 Topic `__consumer_offsets`，而**管理它的是该组对应的 Group Coordinator**。

### 2.3 Broker 的"无状态"到底指什么

常见说法："Kafka broker 是无状态的，所以扩容容易。"这句话**只对一半**：

- ❌ Broker **有状态**：它实实在在存着分区副本数据，节点挂了上面的 leader 需要重新选举。
- ✅ Broker **不保存消费进度**：消费位移由客户端提交到 `__consumer_offsets`，因此**消费者与 broker 没有绑定关系**，可以任意上下线、任意连哪个 broker。
- ✅ Broker **不需要记录"谁读过了什么"**：这是拉模式 + 客户端自管位移带来的简化，也是 Kafka 能支撑海量消费者的原因。

## 三、Topic、Partition、Replica

### 3.1 三层结构

| 层次 | 性质 | 类比 |
|---|---|---|
| **Topic** | **逻辑**概念，一类消息的集合 | 数据库的表 / 文件夹 |
| **Partition** | **物理**概念，一个有序追加日志 | 一个日志文件目录 |
| **Replica** | Partition 的副本，跨 broker 冗余 | 文件的多份备份 |

**层级关系**：`Topic (1..n) Partition (1..m) Replica`

### 3.2 Partition 的双重使命

Partition 是 Kafka 最重要的设计决策，它同时解决两个问题：

1. **水平扩展（Scalability）**——不同分区可以分布在不同 broker，存储与吞吐随分区数（≈broker 数）线性扩展。
2. **并行消费（Parallelism）**——一个分区同一时刻只被**组内一个消费者**消费，分区数直接决定消费并行度上限。

代价是：

> [!warning] 分区带来的三个约束
> - **全局有序性丢失**：只能保证分区内有序。
> - **并行度有上限**：消费者数超过分区数时，多出的消费者**空转**（不报错，但也不消费）。
> - **分区不是越多越好**：每个分区都是文件句柄、内存、副本同步任务和 rebalance 成本的来源，详见 [[7-运维与集群调优]]。

### 3.3 分区数怎么定（工程口径）

| 判断依据 | 说明 |
|---|---|
| 目标吞吐 ÷ 单分区吞吐 | 单分区实测吞吐（含副本同步）是关键输入，经验值常取 MB/s 量级 |
| 目标消费并行度 | 分区数 ≥ 期望的消费者实例数（含预留弹性） |
| 未来 1～2 年增长 | 分区**只能增不能减**，宁多勿少（但别夸张） |
| 单分区不宜过小 | 分区过多会显著拖慢 leader 选举与 rebalance |

> [!tip] 实操建议
> 把分区数直接**绑定到磁盘/消费者规模**，而不是拍脑袋。新增分区会让同一个 key 落到不同分区（**破坏 key 的顺序性**），所以**依赖 key 有序的 Topic 一开始就要把分区数定足**。这一点在 [[3-生产者原理]] 的分区器部分展开。

### 3.4 副本与 leader/follower

- 每个分区有 1 个 **leader** 和 0～n 个 **follower**（副本总数 = `replication.factor`）。
- **读写都只走 leader**，follower 的唯一任务是**同步数据**，作为热备。
- follower 主动向 leader 发起 **fetch** 请求（和消费者拉取是同一套机制），不是 leader 推送。
- leader 挂掉后，从 **ISR** 中选一个 follower 转为 leader。

> [!question] 为什么 follower 不提供读（不像 MySQL 读写分离）？
> Kafka 刻意不做 follower 读，原因是：① 避免读到未同步完的数据（一致性简单）；② 避免"读扩散"带来的额外副本间同步复杂度；③ 消费者读取已通过**多个消费者并行**获得横向扩展能力，不需要靠 follower 分担。若确有跨机房读需求，用 **MirrorMaker 2 / 副本 Topic** 而不是 follower 读。

副本同步、ISR、HW/LEO 的完整机制见 [[5-日志存储与副本机制]]。

## 四、元数据管理：ZooKeeper 与 KRaft

### 4.1 演进脉络

| 阶段 | 元数据存储 | 说明 |
|---|---|---|
| 旧架构（≤ 3.x 可选） | **ZooKeeper** | 存 broker 注册、Topic 配置、分区/副本分配、ISR、Controller 选举 |
| 过渡（2.8 实验 → 3.3 生产就绪） | **KRaft** | 元数据作为一条日志存在 `__cluster_metadata` Topic |
| **Kafka 4.0** | **仅 KRaft** | ZooKeeper 模式被**移除** |

### 4.2 KRaft 的核心思想

KRaft（Kafka Raft）把元数据也变成**一条 Kafka 日志**：

- 一组 controller 节点组成 **Controller Quorum**（通常 3 或 5 个，奇数），基于 **Raft 协议**选主并复制元数据。
- 元数据写入 `__cluster_metadata` 这条内部日志，broker 作为 **follower** 消费它来获知集群状态。
- 好处：**单一系统**（不再需要运维 ZK）、元数据变更可用同一套日志机制复制、**controller 故障切换秒级**（老架构 controller 切换可能长达数十秒，因为要重新从 ZK 加载全量元数据）、支持**百万级分区**。

### 4.3 两种进程角色

| 部署模式 | `process.roles` | 适用 |
|---|---|---|
| **分离模式**（推荐生产） | 部分节点 `controller`，部分节点 `broker` | controller 与数据节点隔离，稳定性好 |
| **合并模式** | `broker,controller` | 开发/测试/小集群，省资源 |

```properties
# 分离模式：controller 节点
process.roles=controller
node.id=1
controller.quorum.voters=1@ctrl1:9093,2@ctrl2:9093,3@ctrl3:9093
listeners=CONTROLLER://ctrl1:9093
controller.listener.names=CONTROLLER

# 分离模式：broker 节点
process.roles=broker
node.id=101
controller.quorum.voters=1@ctrl1:9093,2@ctrl2:9093,3@ctrl3:9093
listeners=PLAINTEXT://broker1:9092
inter.broker.listener.name=PLAINTEXT
```

> [!warning] 升级 4.0 的前置条件
> ZooKeeper 模式在 4.0 已不可用，升级前必须先完成 **ZK → KRaft 迁移**（先在 3.x 上迁移并验证，再升 4.0）。迁移与滚动升级步骤见 [[7-运维与集群调优]]。
> 另注意：自 3.x 起，绝大多数运维脚本已用 `--bootstrap-server` 取代 `--zookeeper`。

## 五、核心 API 与生态组件

### 5.1 四个官方 API

| API | 作用 | 一句话用途 |
|---|---|---|
| **Producer API** | 向 Topic 发送消息 | 埋点、日志、事件发布 |
| **Consumer API** | 订阅 Topic 并消费 | 业务消费、数据同步 |
| **Streams API** | 流式处理：消费输入流 → 转换 → 产出输出流 | 实时聚合、ETL、窗口计算 |
| **Connect API** | 用连接器对接外部系统（源/汇） | 数据库 CDC、写入 ES/HDFS |

> [!note] 选择建议
> - 只是"搬数据"（DB ↔ Kafka ↔ 存储）→ **Connect**，不写代码。
> - 需要"算"（聚合、join、窗口）→ **Streams**（或 Flink）。
> - 业务系统内嵌收发 → **Producer/Consumer API**（工程落地见 [[9-SpringBoot实战]]）。

### 5.2 关键周边

| 组件 | 定位 |
|---|---|
| **Kafka Connect** | 声明式数据集成框架；Source（入）/Sink（出）连接器 |
| **Kafka Streams** | 轻量流处理库（普通 Java 应用 + 状态存储，无需额外集群） |
| **MirrorMaker 2** | 跨集群/跨机房复制，用于容灾与数据汇聚 |
| **Schema Registry** | 消息 Schema（Avro/Protobuf/JSON）版本管理与兼容性校验 |
| **ksqlDB** | 基于 Streams 的 SQL 流处理引擎 |

## 六、消息的基本结构

一条 Kafka 消息（Record）不只是"一条数据"，它包含更多元信息：

| 字段 | 说明 | 用途 |
|---|---|---|
| **Key** | 消息键，可为 null | **决定分区**（同 key 必落同一分区 → 保序）；也用于 Compaction |
| **Value** | 消息体 | 业务数据；Compaction 中 **value=null 表示墓碑（删除）** |
| **Timestamp** | 时间戳，有 `CreateTime`（生产者写入时间，默认）与 `LogAppendTime`（broker 追加时间）两种 | 按时间回溯、流处理事件时间 |
| **Headers** | KV 元数据列表 | 传递追踪 ID、Schema 版本、重试次数等 |
| **Offset** | 分区内唯一递增编号 | 位移提交与回溯的基准 |
| **Partition / Topic** | 所属位置 | —— |

> [!tip] Header 常被忽视但很有用
> 在做链路追踪时，把 `traceId` 放进 Header 而不是塞进 Value，可以避免污染业务消息体，且不参与 Compaction 的 value 判定。

## 七、一次完整的读写链路（串起所有角色）

以"生产者发一条消息、消费者组消费它"为例：

| 步骤 | 动作 | 涉及角色 |
|---|---|---|
| 1 | 生产者序列化 → 分区器确定目标分区 | Producer |
| 2 | 消息进 RecordAccumulator，按分区攒批 | Producer |
| 3 | Sender 线程把批次发往该分区 **leader 所在 broker** | Producer → Broker(leader) |
| 4 | leader 追加写入日志（page cache） | Broker(leader) |
| 5 | follower 主动 fetch 同步，直到追上 leader 的 LEO | Broker(follower) |
| 6 | HW 推进（ISR 全部同步后） | Broker 集群 |
| 7 | 消费者 fetch，只能读到 **HW 之前**的数据 | Consumer → Broker(leader) |
| 8 | 消费者处理业务，提交位移到 `__consumer_offsets` | Consumer → Group Coordinator |
| 9 | 消费者崩溃/新增 → Coordinator 触发 **Rebalance** | Group Coordinator |

> 第 3～6 步的存储与副本细节 → [[5-日志存储与副本机制]]
> 第 3 步之前的攒批与参数 → [[3-生产者原理]]
> 第 7～9 步的位移与 Rebalance → [[4-消费者与Rebalance]]

## 八、动手验证

```bash
# 1) 看集群节点与 controller（KRaft 下 --bootstrap-server 即可）
kafka-broker-api-versions.sh --bootstrap-server localhost:9092

# 2) 创建 3 分区 2 副本的 topic
kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic demo-arch --partitions 3 --replication-factor 2

# 3) 查看分区、leader、ISR、以及"优先副本"
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic demo-arch

# 4) 看这个 topic 的元数据（分区分布在哪些 broker）
kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic demo-arch --under-replicated-partitions

# 5) 生产几条消息（key:value），验证同 key 落同一分区
kafka-console-producer.sh --bootstrap-server localhost:9092 \
  --topic demo-arch --property parse.key=true --property key.separator=:
# 输入:  user1:hello    user1:world    user2:hi

# 6) 带 key 与分区打印地消费，观察同 key 的分区号是否一致
kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic demo-arch --from-beginning \
  --property print.key=true --property print.partition=true
```

**观察点**：
- 步骤 3 输出中 `Leader` 不同分区分属不同 broker —— 验证"分区提供水平扩展"。
- 步骤 6 中 `user1` 的两条消息分区号相同、顺序一致 —— 验证"同 key 有序"。
- 把某个 broker 停掉，再看步骤 3：对应分区的 `Leader` 会切换，`Isr` 会少一个 —— 验证"副本容错"，细节见 [[5-日志存储与副本机制]]。

## 九、本篇必答

> [!question] 面试官可能这样问
> **Q：画一下 Kafka 的架构，说说每个组件的职责。**
> A：Producer（按分区批量发送）→ Broker 集群（每个 Topic 拆成多个 Partition，每个 Partition 有 1 leader + N-1 follower，读写只走 leader，follower 同步做热备）→ Consumer Group（组内分区与消费者一一对应，拉模式，自己向 `__consumer_offsets` 提交位移）。集群层面还有 **Controller**（管分区/副本状态与 leader 选举）和 **Group Coordinator**（管消费组与位移），元数据在 KRaft 模式下由 **Controller Quorum** 通过 Raft 维护在 `__cluster_metadata` 日志中；ZooKeeper 模式已在 4.0 移除。
>
> **Q：为什么 Kafka 的并行度由分区数决定？**
> A：分区是最小的并行与有序单位：生产者按分区并行写、消费者组按分区并行读，且一个分区同一时刻只能被组内一个消费者消费。所以分区数同时是**吞吐上限**和**消费并行度上限**，也带来"全局无序、只能增不能减"的约束。
>
> **Q：为什么 broker 挂掉不会丢数据？**
> A：每个分区有多个副本分布在多个 broker，且 follower 持续同步；leader 挂掉后从 ISR 中选出新 leader。但"不丢"有前提——需配合 `acks=all`、`min.insync.replicas>=2`，并禁止非 ISR 副本当选（`unclean.leader.election.enable=false`）。见 [[5-日志存储与副本机制]]。
