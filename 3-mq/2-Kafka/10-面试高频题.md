## 一、六大必答题

### Q1. 如何保证消息不丢失？（最高频）

> [!important] 得分骨架：**分三个环节答，每个环节给具体措施**

| 环节 | 措施 | 为什么 |
|---|---|---|
| **生产端** | `acks=all`（等 ISR 全部确认）+ `retries>0` + **处理发送回调** | 不等确认就返回，leader 挂了消息就没了；异步发送不看回调会静默丢失 |
| **Broker 端** | `replication.factor>=3` + `min.insync.replicas>=2` + `unclean.leader.election.enable=false` | 单副本必丢；若 ISR 收缩到小于 min ISR，broker 会**拒绝写入**（牺牲可用性保可靠）；禁止落后副本当选 leader |
| **消费端** | 关闭自动提交，**业务处理成功后再提交位移** | 先提交后处理 = at-most-once，处理失败就丢了 |

**加分收尾**：还要考虑**副本刷盘**——Kafka 默认依赖 OS page cache 异步刷盘，即使 `acks=all` 也可能在**整个机房断电**时丢失"已确认但未落盘"的数据。对极端可靠性要求可调 `log.flush.interval.messages`，但性能代价极大，实践中更常用 `replication.factor=3` 跨机架来兜底。

**追问：`acks=all` 就不会丢了吗？**
不一定。① ISR 收缩到 `min.insync.replicas` 以下时写入直接失败（是"不可用"而非"丢"）；② 若 `unclean.leader.election.enable=true`，非 ISR 副本可当选 leader，会**截断已有数据**；③ 未刷盘时整机断电。所以 `acks=all` 是**必要条件而非充分条件**。

### Q2. 如何保证消息不重复（幂等）？

> [!important] 得分骨架：**先声明"重复不可避免"，再谈两层幂等**

**第一层：Kafka 自身**
- **幂等生产者**（`enable.idempotence=true`，3.0 起默认开）：PID + 分区级序列号，broker 端按 `(PID, 分区, 序列号)` 去重，解决**生产端重试导致的重复**。
- **事务**：跨分区原子写 + `sendOffsetsToTransaction`，实现"消费-处理-生产"的 Exactly-Once。
- 边界：幂等只保证**单生产者会话、单分区**不重复；事务只覆盖 **Kafka 内部**。

**第二层：消费端业务幂等**（at-least-once 下的必答题）

| 方案 | 做法 | 适用 |
|---|---|---|
| 唯一索引 | 业务唯一键建唯一索引，重复插入报错即忽略 | 写库场景，最常用 |
| 去重表 | 独立去重表记录已处理 ID（可配 TTL） | 通用 |
| 状态机 / 版本号 | 只允许状态单向流转，或版本号递增才更新 | 订单、支付等有状态业务 |
| Redis SETNX | 处理前抢占，配过期时间 | 高频、可容忍极小概率失效 |

**追问：为什么 Kafka 不做到"绝不重复"？**
因为"绝不重复"需要端到端的两阶段提交或全局去重，代价极高且无法覆盖外部系统。工程上选择 **at-least-once + 业务幂等**，把复杂度放在能控制的地方。详见 [[6-事务与Exactly-Once]]。

### Q3. Kafka 如何实现 Exactly-Once？

> [!important] 得分骨架：**幂等生产者（基础）→ 事务（跨分区原子）→ 消费位移纳入事务（闭环）**

1. **幂等生产者**：`enable.idempotence=true`，靠 PID + 序列号让"重试不产生重复"。
2. **事务**：`transactional.id` 绑定生产者身份（epoch 递增可 **fencing 掉僵尸生产者**），Transaction Coordinator 用两阶段提交协调多个分区，写入 **control batch（事务标记）**。
3. **闭环**：消费者配置 `isolation.level=read_committed`，位移通过 `sendOffsetsToTransaction()` 一并提交——**"消息产出"与"位移提交"原子化**，实现 consume-transform-produce 的 EOS。

**关键限制（说出来就是加分项）**：
- 只保证 **Kafka Topic 之间**的原子性，一旦有数据库/HTTP 等外部系统，仍需业务幂等。
- 长事务会让 `read_committed` 消费者卡在 **LSO** 上（head-of-line blocking），延迟上升。
- `transaction.timeout.ms` 到期会被 abort。

### Q4. Kafka 为什么这么快（高吞吐）？

> [!important] 得分骨架：**六个原因，按"磁盘 → 内存 → 网络 → 结构 → 并行"讲**

| 原因 | 原理 |
|---|---|
| **顺序追加写** | 日志只在末尾追加，磁盘顺序写（省去寻道）比随机写快**数量级** |
| **Page Cache** | 读写都尽量命中 OS 页缓存，broker 不自己维护缓存 → JVM heap 可以很小、GC 压力小 |
| **零拷贝（sendfile）** | 消费路径用 `transferTo`，数据从 page cache **直接进网卡**，避免用户态来回拷贝与上下文切换 |
| **批量 + 压缩** | 攒批（`batch.size`/`linger.ms`）摊薄网络与 IO 开销；批次级压缩，压缩后仍可零拷贝直传 |
| **稀疏索引** | offset 索引稀疏 + 二分查找 + 顺序扫描，索引小到可常驻内存 |
| **分区并行** | 分区是最小并行单位，生产/消费/存储都能横向扩展 |

**追问：零拷贝为什么能减少拷贝？**
传统 `read + write`：磁盘→内核缓冲区→用户缓冲区→socket 缓冲区→网卡，**4 次拷贝 4 次上下文切换**；`sendfile`/`transferTo` 让数据在内核内部直接从 page cache 送到 socket，**2 次拷贝**、切换更少。注意：**SSL/TLS 与旧版客户端走不了这条路径**。详见 [[8-性能优化与高吞吐原理]]。

### Q5. 消费 Lag 很高怎么办？

> [!important] 得分骨架：**先定位是"消费能力不足"还是"生产突增"或"消费卡住"**

**排查顺序**：
1. **看 Lag 曲线形状**
   - 缓慢持续增长 → 消费能力 < 生产速率（**能力问题**）
   - 突然飙升后平稳 → 生产突增或消费短暂中断（**事件问题**）
   - 锯齿状但降不下去 → 每轮都在重放/重试（**异常问题**）
2. **看消费端**
   - 是否有大量异常重试/进死信？→ 修业务
   - 单条处理耗时是否过高？→ 优化逻辑、批量化
   - 是否频繁 rebalance？→ 见 Q7
   - `concurrency` 是否已达分区数上限？→ 加分区
3. **扩容手段**：加消费者实例（≤ 分区数）→ 提高 `max.poll.records` 批量处理 → 加分区 → 拆分 Topic

> [!tip] 一个常被忽略的点
> **消费者数超过分区数时，多出来的消费者只会空转**。此时加实例对 Lag 毫无帮助，必须**先扩分区**（注意：扩分区会破坏同 key 的顺序性）。

### Q6. Kafka 如何保证消息顺序？

> [!important] 得分骨架：**分区内有序，全局无序；要全局有序必须单分区**

**保序的三个条件**：
1. **同 key 落同分区**（默认分区器对 key 做 hash）→ key 级有序
2. **生产端 `max.in.flight.requests.per.connection=1`**，或**开启幂等**（`<=5` 配合幂等）
   - 原因：并发在途请求 + 重试会导致批次乱序落盘
3. **消费端单线程按分区顺序处理**，别把消息丢线程池打乱

**代价与取舍**：

| 方案 | 有序范围 | 代价 |
|---|---|---|
| 单分区 | **全局有序** | 完全放弃并行，吞吐极低 |
| 按 key 分区 | **key 内有序** | 最常用；需预先定足分区数（分区只能增不能减，扩容会打乱 key 归属） |
| 无序 | —— | 吞吐最高 |

### Q7. Rebalance 是什么？怎么优化？

> [!important] 得分骨架：**定义 → 危害 → 触发条件 → 治理清单**

**定义**：消费组成员或订阅关系变化时，Coordinator 重新分配"分区 → 消费者"的对应关系（JoinGroup → SyncGroup → 分配）。

**危害**：经典协议下是 **Stop-The-World**，期间**整个消费组停止消费**；且未提交的位移会重复消费。

**触发条件**：消费者加入/主动离开/崩溃（心跳超时）/**处理太慢（`max.poll.interval.ms` 超时）**/订阅的 Topic 变化/分区数变化。

**治理清单**：

| 手段 | 说明 |
|---|---|
| 调大 `max.poll.interval.ms` | 治"处理太慢被踢"，最常见 |
| 调小 `max-poll-records` | 缩短单轮处理时间 |
| 静态成员 `group.instance.id` | 重启不再触发 rebalance |
| **CooperativeStickyAssignor** | 增量式再均衡，不必全量 STW（2.4+） |
| 处理逻辑异步化 | 保证 `poll` 及时（但注意位移语义） |
| KIP-848 新消费组协议 | Broker 端分配器，rebalance 更快（3.7+ 起可用） |

**关键区分（常被追问）**：`session.timeout.ms`（心跳）与 `max.poll.interval.ms`（poll 间隔）是**双重存活判定**——消费者必须**同时**满足两者。处理逻辑慢导致的是后者，调 `session.timeout.ms` 无效。

## 二、快问快答

| 问题 | 要点 |
|---|---|
| Kafka 是推送还是拉取？ | **拉取（pull）**；用 `fetch.min.bytes` + `fetch.max.wait.ms` 长轮询缓解空轮询 |
| 消费位移存在哪？ | 内部压缩 Topic **`__consumer_offsets`**（老版本在 ZooKeeper） |
| `auto.offset.reset` 何时生效？ | **仅当没有已提交位移时**；组提交过就不是它说了算 |
| HW 和 LEO 区别？ | LEO = 副本日志末端；HW = **ISR 中所有副本都已同步到**的位置，消费者只能读到 HW |
| LSO 是什么？ | `read_committed` 下消费者可见上限；受未完成事务阻塞 |
| 为什么 follower 不提供读？ | 简化一致性、避免读扩散；并行读靠多消费者而非多副本 |
| ISR 如何判定？ | **基于时间**：follower 落后 leader 超过 `replica.lag.time.max.ms` 就被踢出 |
| Controller 做什么？ | 管分区/副本状态与 leader 选举；KRaft 下由 controller 角色节点承担 |
| 分区数能减少吗？ | **不能**，只能增加；且增加会打乱同 key 的分区归属 |
| 一个分区能被几个消费者消费？ | 同一消费组内**只能一个**；不同消费组互不影响 |
| 消费者数超过分区数？ | 多出的**空转**，不消费也不报错 |
| `acks` 三个值？ | 0 不等 / 1 等 leader / all 等 ISR（配合 `min.insync.replicas`） |
| `__consumer_offsets` 为什么用压缩？ | 每个 key 只需保留最新位移，用 **log compaction** 避免无界增长 |
| Kafka 4.0 最大变化？ | **ZooKeeper 模式移除**，KRaft 为唯一元数据方案 |
| 如何实现延迟消息？ | Kafka **不原生支持**；用外部调度、多级 Topic 转发或时间轮+定时扫库 |
| 消息太大怎么办？ | 调 `max.request.size` / `message.max.bytes` / `max.partition.fetch.bytes`（三处要一致），或改用对象存储+引用 |
| 如何做消息回溯？ | 按 offset 或时间 `seek` / `--reset-offsets --to-datetime` |

## 三、易错陷阱 TOP 10

> [!danger] 这些答案答错，比不答更扣分
> 1. **"`acks=all` 保证不丢"** —— 还要看 `min.insync.replicas` 与 `unclean.leader.election`。
> 2. **"auto.offset.reset=latest 就是不消费历史"** —— 只在无已提交位移时生效。
> 3. **"消费者越多吞吐越高"** —— 超过分区数只会空转。
> 4. **"HW 就是 leader 的 LEO"** —— 不是，HW 是 ISR 的最小已同步位置。
> 5. **"全部副本都叫 ISR"** —— ISR 是**保持同步**的副本，落后的会被踢出。
> 6. **"自动提交更安全/无所谓"** —— 自动提交是**先提交后处理**倾向，崩溃即丢。
> 7. **"Kafka 事务能保证数据库一致性"** —— 事务只覆盖 Kafka 内部写入。
> 8. **"分区可以缩容"** —— 只能增加。
> 9. **"调整 `session.timeout.ms` 能解决处理慢导致的 rebalance"** —— 该调 `max.poll.interval.ms`。
> 10. **"`read_committed` 没有代价"** —— 会被 LSO 阻塞，长事务下延迟明显上升。

## 四、场景设计题

### 4.1 订单系统：要求"不丢、不重、同订单有序"，怎么设计？

**答题框架**：
1. **Topic 规划**：`order-events`，分区数按业务峰值与消费者规模**一次定足**（因为要保 key 序，不能中途扩）。
2. **生产端**：`key = orderId`（同订单必落同分区）；`acks=all` + `enable.idempotence=true` + 重试；处理发送回调。
3. **Broker**：`replication.factor=3`、`min.insync.replicas=2`、`unclean.leader.election.enable=false`。
4. **消费端**：`enable-auto-commit=false` + 处理成功再提交；单分区顺序处理；`concurrency ≤ 分区数`。
5. **幂等兜底**：订单状态机 + 唯一索引（如 `order_id + event_type` 唯一），即使重复投递也不会重复生效。
6. **容错**：重试 + 死信 Topic + 告警；死信人工/自动补偿。
7. **监控**：Lag、生产失败率、重试率、死信量。

### 4.2 大促削峰：10 万 QPS 涌入，下游只能处理 2 万 QPS

**要点**：
- Kafka 作为**缓冲池**，靠**保留期**承接峰值（注意算磁盘容量，见 [[7-运维与集群调优]]）。
- 下游按能力消费，Lag 会堆积但有界（峰值过后能追平）。
- 分区数按**消费端能力**定（2 万 QPS ÷ 单分区吞吐）。
- 别为了"实时"盲目加消费者：**超过分区数无用**。
- 保护下游：消费端做**限流/并发控制**，必要时 `pause`/`resume` 实现背压。

### 4.3 跨机房容灾怎么做？

**要点**：
- **MirrorMaker 2** 做集群间复制（可用 Connect 生态转换 Topic 名、同步位移）。
- 注意 MM2 是**异步复制**，RPO > 0；同城双活与异地灾备的目标不同。
- 也可用 **Rack Awareness（`broker.rack`）** 让副本跨机架分布，防单机架故障。
- 客户端侧可用 `client.rack` + 就近拉取降低跨机房流量。

## 五、面试前 10 分钟速记卡

> [!abstract] 记住这 8 句
> 1. Kafka = 分布式提交日志；分区内有序，全局无序。
> 2. 读写只走 leader；follower 只同步；消费者只能读到 HW。
> 3. 不丢 = 生产 `acks=all` + 副本 `min.insync.replicas>=2` + 消费"处理后再提交"。
> 4. 不重 = 幂等生产者 + 业务幂等（唯一索引/状态机）；Exactly-Once 靠事务闭环。
> 5. 快 = 顺序写 + PageCache + 零拷贝 + 批量压缩 + 稀疏索引 + 分区并行。
> 6. Rebalance = 分区重分配 + STW；治"处理慢"要调 `max.poll.interval.ms`。
> 7. 并行度 = 分区数；消费者超过分区数会空转；分区只能增不能减。
> 8. 元数据在 KRaft 的 `__cluster_metadata`；4.0 起 ZooKeeper 已移除。
