## 一、集群规划

### 1.1 broker 数量怎么定

规划不是"拍一个数"，而是从四个约束里取最大值再向上取整：

| 约束 | 估算方式 |
|---|---|
| 吞吐 | `ceil(峰值写入带宽 × 副本数 RF ÷ 单 broker 可持续写入带宽)` |
| 容量 | `ceil(总数据容量 × RF ÷ 单 broker 可用磁盘容量)` |
| 可用性 | 至少 3 台（RF=3、`min.insync.replicas=2` 时能容忍 1 台故障） |
| 故障冗余（N-1 原则） | 任意一台下线后，剩余节点仍能承载**全部**流量与容量 |

关键点：

- **单 broker 的写入带宽上限**取下面几项的最小值：磁盘顺序写带宽、网卡带宽（副本流量与客户端流量共用）、CPU（压缩/解压、TLS）、页缓存命中率。
- **N-1 原则最容易被忽略**：按"3 台各跑 33%"规划，一台挂掉后剩下两台要各跑 50%，立刻打满 → 消费者 lag 飙升、副本追不上。正确做法是按"剩余 N-1 台能承载 100%"反推单台配置。
- **RF=3 意味着写入流量放大 3 倍**（leader 写本地 + 2 个 follower 拉取）。规划网卡与磁盘带宽时必须乘 RF。
- 云上还要考虑跨 AZ 的副本流量计费与延迟；`broker.rack` 用于跨机架打散副本（见 2.5）。

### 1.2 分区数估算

分区数由三个需求共同决定，取最大值：

```text
分区数 >= max(
    期望消费并行度            // 分区是消费并行度的硬上限，见 [[4-消费者与Rebalance]]
    峰值写入吞吐 / 单分区可持续吞吐
    峰值写入 TPS / 单分区可持续 TPS
)
```

| 驱动因素 | 说明 |
|---|---|
| 消费并行度 | 一个分区同一时刻只能被组内一个消费者消费 → 分区数就是并行度上限。**按未来 1~2 年的峰值预留**，因为分区只能增不能减（见 4.1） |
| 生产吞吐 | 经验上单个分区可以稳定承载**数 MB/s 到 10 MB/s 量级**的写入，超过就该加分区。具体上限取决于单条大小、批量大小、压缩比、磁盘与网络 |
| 批处理效率 | 分区**过多**的反向代价：每个分区的批更小、请求数更多、producer 端为每个分区维护 batch 缓冲（受 `buffer.memory` 约束）、元数据变大、broker 端文件数与页缓存碎片增加 |
| 顺序性 | 分区数决定 key 的顺序边界（同一 key 落同一分区才有顺序）；扩分区会改变 `hash(key) % 分区数`，破坏变更点前后的顺序 |

> [!tip] 实操结论
> 先问"消费者最多要开多少个线程/实例"，再问"写入吞吐需要多少并行"，取大者并向上取整到便于整除的数值（如 12/24/48）。**不要为了"扩展性"无脑开 100+ 分区**——分区多带来的元数据、句柄、页缓存与 rebalance 成本是真实存在的。

### 1.3 磁盘容量估算（方法，不是魔法数字）

```text
① 单日原始写入量 = 平均消息大小 × 单日消息条数
② 单日落盘量     = 单日原始写入量 ÷ 压缩比
                   （压缩由生产端 compression.type 决定；若上游已压缩，落盘不会再压，压缩比按 1 计）
③ 单副本容量     = 单日落盘量 × 保留天数
④ 数据总容量     = 单副本容量 × 副本数 RF
⑤ 规划容量       = 数据总容量 × 余量系数（建议 1.2 ~ 1.5）
```

余量系数要覆盖的是**具体项目**，而不是"保险起见"：

| 余量来源 | 说明 |
|---|---|
| 索引与时间索引 | 每个 segment 除 `.log` 外还有 `.index`、`.timeindex`，通常占比很小但存在 |
| segment 尾部的删除粒度 | 日志按 segment 删除，实际占用可能比 `retention.bytes` 多出最多一个 `log.segment.bytes` |
| 内部 topic | `__consumer_offsets`（默认 50 分区 × RF3）、`__transaction_state`（默认 50 分区 × RF3，若用事务） |
| 副本重分配 | 迁移期间同一分区同时存在于源与目标 broker → **该分区磁盘占用翻倍** |
| 副本追赶 / 停机堆积 | broker 停机或 follower 落后期间的写入全部堆在存活节点上；恢复前容量压力集中 |
| 磁盘水位 | 磁盘**不要用到 100%**：建议 70%~80% 告警，留出副本追赶与迁移空间。磁盘写满会触发 log dir failure，该目录上的分区直接不可用（见第十节） |

**一个可复用的算例**（展示方法，数字按自己业务替换）：

| 步骤 | 计算 | 结果 |
|---|---|---|
| ① 原始量 | 平均 1 KB × 2 亿条/天 | 200 GB/天 |
| ② 落盘量 | 按压缩比 0.5（文本/JSON 类日志压得动） | 100 GB/天/副本 |
| ③ 单副本 | 保留 7 天 | 700 GB |
| ④ 三副本 | RF=3 | 2.1 TB |
| ⑤ 加余量 | ×1.3（含迁移双份、segment 碎片、内部 topic） | ≈ 2.7 TB |
| ⑥ 决策 | 再加"预留一台故障时的追赶空间"与 OS/日志空间 | 裸容量 ≥ 3.5 TB，且单盘容量选型后**至少 3 块盘**做 JBOD |

补充：

- `retention.ms`（默认 `log.retention.hours=168`，即 7 天）与 `retention.bytes`（默认 -1，不按大小限制）**同时满足才会删**某个 segment；两者都设时，谁先满足就按谁删。
- 分区**不能减**，容量只能通过缩短保留时间或加盘/加机器来释放。

### 1.4 分区数上限受什么约束

| 约束 | 机理 | 超限后的表现 |
|---|---|---|
| **文件句柄** | 每个 log segment 对应 3 个文件（`.log` / `.index` / `.timeindex`）。分区越多、单分区越小，总 segment 数越多，文件句柄需求随 `分区数 × 副本数 × 每分区段数 × 3` 增长 | 报 `Too many open files`，写入失败、broker 日志刷错误 |
| **内存（页缓存）** | 每个分区在 broker 上有副本状态、fetch 状态、索引等元数据，且都参与页缓存竞争。分区越多，单分区可分到的页缓存越少，命中率下降 | 读放大、消费者 fetch 延迟上升、磁盘 IO 飙升 |
| **controller 压力** | 分区元数据要写入元数据存储（ZK 时代写 ZK，KRaft 写 `__cluster_metadata` 日志）。controller 选举后的全量元数据加载、topic 级操作的时间都正比于分区数 | controller 故障恢复变慢（分钟级）、`ControllerEventManager` 队列积压 |
| **创建/删除/rebalance 时间** | topic 创建、删除、副本重分配、首选 leader 选举、broker 重启后的元数据加载都随分区数线性增长 | 运维操作"卡住"，一次重分配要跑几小时 |
| **客户端** | 生产者按分区维护 batch 缓冲（受 `buffer.memory` 限制）、消费者按分区维护 fetch 状态与元数据 | 客户端内存上升、元数据请求变频繁 |

经验区间（作为规划起点，不是硬性限制）：

| 项 | 经验值 |
|---|---|
| 单 broker 分区数（含副本） | **2000 ~ 4000** 是比较舒服的区间 |
| 单集群总分区数（ZK 时代） | 十万量级的经验上限，越多越难运维 |
| KRaft 下 | 元数据日志可支撑的分区规模显著更高（百万量级），但真正的瓶颈转为 **controller 快照大小/加载时间** 与 **rebalance 时长** |

> [!warning] 分区数不是"免费的扩展性"
> 分区数膨胀最直接的后果是：**故障恢复时间变长**（controller 要重建更多元数据）、**rebalance 更慢**（协调器要把更多分区分配出去）、**页缓存命中率下降**。宁可先用较少的分区跑，通过压测确认单分区吞吐，再按需扩容。

### 1.5 规划速查

| 项目 | 建议 |
|---|---|
| broker 数 | ≥ 3，按 N-1 原则规划容量与带宽 |
| RF / `min.insync.replicas` | 3 / 2（可容忍 1 台故障仍可写） |
| 单 broker 分区数 | 2000 ~ 4000 |
| 磁盘水位 | 70% 告警，80% 严重 |
| `log.dirs` | 每块盘一个目录，**不要**用 RAID 条带做冗余（见 2.1） |
| 保留策略 | 按时间为主（`retention.ms`），大小做兜底；明确"最坏情况下磁盘占用" |
| 内部 topic | `offsets.topic.replication.factor=3`、`transaction.state.log.replication.factor=3` |

## 二、硬件与 OS 调优

### 2.1 磁盘选型：SSD / HDD / JBOD vs RAID

| 介质 | 优势 | 劣势 | 适用 |
|---|---|---|---|
| NVMe SSD | 低延迟、高 IOPS，副本追赶与消费者追赶极快，故障恢复快 | 单价高 | 生产首选 |
| SATA / 云盘 SSD | 性价比好，延迟可接受 | 带宽与 IOPS 低于 NVMe | 通用生产 |
| HDD | 容量便宜 | 顺序写尚可，**随机读很差**；消费者追赶、副本追赶、broker 重启恢复都会退化成随机读；单盘故障后的副本重建极慢 | 归档、低吞吐、成本敏感 |

Kafka 的写入是**顺序追加**，所以 HDD 也能跑；但读路径（消费者读历史、follower 拉取落后数据）会命中随机 IO，这才是 HDD 的真正瓶颈。**不要用"顺序写所以 HDD 够用"来论证生产环境选 HDD。**

**JBOD vs RAID**：

| 维度 | JBOD（多盘独立，写进 `log.dirs`） | RAID 10 |
|---|---|---|
| Kafka 官方倾向 | **推荐** | 可接受 |
| 容量利用率 | 高（无冗余开销，冗余由 Kafka 副本提供） | 50% |
| 单盘故障影响 | 该盘上的分区副本**直接离线**，需要重建副本 | 对 Kafka 透明，零影响 |
| 重建成本 | 用 `kafka-reassign-partitions.sh` 把丢失副本重新分配，可限流、可分批 | 硬件 RAID 重建，大容量盘重建期间性能雪崩 |
| 写惩罚 | 无 | RAID 5/6 有明显写惩罚（**不要用于 Kafka**）；RAID 10 无 |

结论：**用 Kafka 自己的副本冗余（RF=3）替代硬件 RAID 的冗余**，选 JBOD，成本最低且故障域最小（单盘故障只影响该盘的分区，不会拖垮整台 broker）。运维能力有限、或单盘容量很小导致故障概率高时，RAID 10 是可接受的折中。

> [!warning] `log.dirs` 的两个坑
> 1. Kafka 把**新分区分配到"当前分区数最少"的那个目录**（按分区**数量**均衡，不按容量或 IO 均衡）。所以**盘容量不一致时会出现容量不均衡**，规划时尽量用同规格盘。
> 2. `log.dirs` 里配置的目录应挂在不同物理盘上；如果只是同一块盘的不同目录，故障域没有隔离，性能也没有提升。

### 2.2 内存：给 page cache，而不是给 JVM heap

Kafka 的读性能几乎完全由 **page cache 命中率**决定：写入顺序追加 → 消费者读的通常就是刚写入的数据 → 大量读直接命中 page cache，根本不碰磁盘。这也是 Kafka 高吞吐的核心原因之一（详见 [[8-性能优化与高吞吐原理]]）。

| 分配对象 | 建议 | 原因 |
|---|---|---|
| page cache（OS） | 物理内存的 **50% 以上**，越多越好 | 决定读性能与副本追赶速度 |
| JVM heap | **4 ~ 8 GB**（Kafka 官方文档提到 6 GB 是较好的起点） | 堆太大 → GC 停顿变长（影响心跳、请求处理、rebalance 判定）+ 挤占 page cache，双重伤害 |
| 堆外 | 网络收发缓冲、索引等 | 注意 `MaxDirectMemorySize` 默认与堆同量级，总量别超物理内存，否则触发 swap |

> [!question] 为什么 broker 不需要"大堆"？
> 因为 broker 的绝大部分"数据"是日志文件，由 OS page cache 管理，不经过堆。堆里只有请求对象、副本状态、元数据、会话等。一个堆 32 GB 的 broker 既没有更快，还因为 Full GC 停顿被踢出 ISR、被判定会话超时而引发 rebalance。**堆越大越稳是典型误解。**

### 2.3 JVM 参数

```bash
# Kafka 3.x 的启动脚本会读取这些环境变量
export KAFKA_HEAP_OPTS="-Xms6g -Xmx6g"
export KAFKA_JVM_PERFORMANCE_OPTS="-XX:+UseG1GC \
  -XX:MaxGCPauseMillis=20 \
  -XX:InitiatingHeapOccupancyPercent=35 \
  -XX:+ExplicitGCInvokesConcurrent \
  -XX:MetaspaceSize=96m \
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/kafka/dump"
# 开启 JMX（kafka-server-start.sh 会识别该环境变量）
export JMX_PORT=9999
```

| 参数 | 作用 | 取舍 |
|---|---|---|
| `-Xms` = `-Xmx` | 固定堆大小 | 避免堆动态伸缩带来的额外停顿；两者不等是"偶发长 GC"的常见原因 |
| `-XX:+UseG1GC` | G1 回收器 | JDK 8u40+ 可用，JDK 11+ 已是默认；老版本默认 CMS/Parallel 在大堆下停顿更差 |
| `-XX:MaxGCPauseMillis` | 停顿目标 | 是**目标**不是保证。设得过小会让 young GC 更频繁，反而降低吞吐 |
| `-XX:InitiatingHeapOccupancyPercent` | 触发并发标记周期的堆占用比例 | 调低 → 更早开始并发标记，降低 Full GC 风险，代价是 CPU 占用上升 |
| `-XX:+ExplicitGCInvokesConcurrent` | 让 `System.gc()` 走并发路径 | 避免应用/依赖里显式 `System.gc()` 引发长时间 STW |
| `-XX:+HeapDumpOnOutOfMemoryError` | OOM 时落堆转储 | 必须配 `-XX:HeapDumpPath` 且确认磁盘余量；否则 OOM 后无据可查 |

JDK 版本：3.x 建议 JDK 11 或 17（`kafka-clients` 与 broker 均支持）；不要用 JDK 8 之外的老版本组合，也不要在同一集群里混用差异过大的 JDK 与 GC 配置。

### 2.4 OS 内核参数

```bash
# /etc/security/limits.conf
kafka  soft  nofile  100000
kafka  hard  nofile  100000

# /etc/sysctl.conf
vm.swappiness = 1
vm.dirty_background_ratio = 5
vm.dirty_ratio = 60
```

| 参数 | 建议 | 原因 |
|---|---|---|
| `ulimit -n`（`nofile`） | ≥ 100000（大集群可更高） | 每个 log segment 对应 3 个文件；网络连接、mmap 也要占用。句柄耗尽的表现是 `Too many open files`，写入直接失败 |
| `vm.swappiness` | **1** | 尽量减少换出（尤其不要把 page cache 换出去）。设为 1 而不是 0 是社区惯例——部分内核上 0 会让内存回收更倾向触发 OOM killer |
| `vm.dirty_background_ratio` | **5** 左右 | 后台刷脏页的阈值。调大 → 脏页积累更多，一次性大刷盘造成写延迟毛刺 |
| `vm.dirty_ratio` | **60 ~ 80** | 进程被迫同步刷脏的阈值。太大 → 单次刷盘停顿可达秒级，broker 表现为请求超时；太小 → 频繁小刷盘，吞吐下降。**Kafka 依赖 OS 刷盘，这两个参数直接影响端到端写延迟** |
| 文件系统 | ext4 或 xfs，挂载加 `noatime` | xfs 在大目录与高并发下表现稳定；`noatime` 减少元数据写 |
| `vm.max_map_count` | 按同机其他组件要求（Kafka 自身不用 mmap 索引） | 同机部署 ES 等组件时需要 |

### 2.5 网络参数与机架感知

| 参数 | 默认 | 调优方向 |
|---|---|---|
| `socket.send.buffer.bytes` | 102400（100 KB） | 跨机房/高 RTT 链路要调大（如 1 MB 量级）。TCP 吞吐上限受带宽时延积（BDP）约束，100 KB 的窗口填不满长肥管道 |
| `socket.receive.buffer.bytes` | 102400（100 KB） | 同上；影响请求接收与副本拉取 |
| `socket.request.max.bytes` | 104857600（100 MB） | 单请求绝对上限，一般不需要动；若有大消息场景见 3.5 |
| 网卡带宽 | — | 规划时算上**副本流量**：RF=3 时写入放大 3 倍，再叠加消费者拉取流量 |
| `broker.rack` | 无 | 机架/可用区标识，让副本跨机架分布，避免整机架断电导致分区不可用 |

> [!warning] `broker.rack` 只影响"新产生的副本分配"
> 设置或修改 `broker.rack` 后，**已有分区不会自动重排**。要真正让副本跨机架，需要显式做一次副本重分配（4.2），并且此时的首选副本/leader 分布也应一并规划。KRaft 模式下 controller quorum 节点同样应跨机架部署。

## 三、Broker 端关键参数调优

### 3.1 线程模型与请求队列

```text
   客户端请求
      │
      ▼
 ┌──────────────────┐    ┌──────────────┐    ┌──────────────────┐
 │ num.network.threads│──>│ 请求队列     │──>│ num.io.threads   │──> 日志/副本
 │ 默认 3            │    │ queued.max.  │    │ 默认 8           │
 │ 收发 + 入队       │    │ requests=500 │    │ 真正处理请求      │
 └──────────────────┘    └──────────────┘    └──────────────────┘
```

| 参数 | 默认 | 调优方向与代价 |
|---|---|---|
| `num.network.threads` | 3 | 负责收发数据与入队，**不做重活**。保持较小（3~8），过大反而增加上下文切换。它多通常不是瓶颈 |
| `num.io.threads` | 8 | 真正处理请求（写日志、读日志、处理副本）。常见做法是设成 **CPU 核数**或与磁盘数匹配。加线程**不能解决磁盘瓶颈**，只会让请求在更深的地方排队 |
| `queued.max.requests` | 500 | 请求队列上限。队列满时网络线程停止读取，形成**背压**。调大能吸收突发，但会增加端到端延迟；调小会让客户端更快拿到超时 |
| `background.threads` | 10 | 后台任务线程（日志清理等） |
| `num.recovery.threads.per.data.dir` | 1 | 启动时每个 log dir 用于恢复日志的线程数。**broker 重启慢**时可调大（如 4~8），代价是启动瞬间 IO 密集 |

判断是否需要加 IO 线程：看 JMX `RequestHandlerAvgIdlePercent`（平均空闲率）**持续低于 0.3**；网络线程看 `NetworkProcessorAvgIdlePercent` 同样持续偏低。但先确认磁盘利用率——**如果磁盘已经 100% 忙碌，加线程是错的**。

### 3.2 副本同步参数

| 参数 | 默认 | 作用与调优取舍 |
|---|---|---|
| `num.replica.fetchers` | 1 | 每个 broker 上用于副本拉取的线程数。分区多或副本经常落后时可加到 2~4；代价是更多磁盘 IO 与网络，可能影响客户端请求。**ISR 频繁收缩时优先看磁盘，而不是盲目加这个值** |
| `replica.fetch.max.bytes` | 1048576（1 MB） | 单分区单次副本 fetch 的**软**上限——若某分区第一批记录就超过它，仍会返回该批以保证进度 |
| `replica.fetch.response.max.bytes` | 10485760（10 MB） | 单次副本 fetch 响应跨所有分区的上限。注意它是**软限**：若第一批记录就超限，仍会返回该批以保证进度（KIP-74 起的行为）。仍需与消息大小保持一致，否则每次 fetch 都会突破内存预期（见 3.5） |
| `replica.fetch.wait.max.ms` | 500 | follower 等待数据的最大时长。调大 → 攒批更好但副本延迟上升 |
| `replica.lag.time.max.ms` | 30000 | follower 超过该时长没追上（且未发起有效 fetch）就被移出 ISR。调大 → ISR 更稳定但故障检测慢、URP 持续时间长；调小 → ISR 抖动（频繁收缩/扩张） |
| `replica.socket.timeout.ms` | 30000 | 副本连接的 socket 超时 |
| `replica.socket.receive.buffer.bytes` | 65536 | 副本拉取的接收缓冲 |
| `min.insync.replicas` | 1 | 与 `acks=all` 配合才有意义：RF=3 + `min.insync.replicas=2` 表示至少 2 个副本写入成功才确认，从而容忍 1 台故障仍可写。**设为 1 时 `acks=all` 形同虚设** |

> [!warning] ISR 频繁收缩/扩张怎么判断
> 看 `kafka.server:type=ReplicaManager,name=IsrShrinksPerSec` 与 `IsrExpandsPerSec`。两者长期非零说明 follower 追不上，常见原因按概率排序：**磁盘 IO 饱和**（最常见）、网络带宽打满、follower 的 `num.replica.fetchers` 不足、长 GC 停顿、`replica.lag.time.max.ms` 设得过小。

### 3.3 刷盘策略：为什么默认不 fsync

| 参数 | 默认 | 说明 |
|---|---|---|
| `log.flush.interval.messages` | `Long.MAX_VALUE` | 累积多少条消息才强制刷盘。默认等于"从不按条数刷" |
| `log.flush.interval.ms` | 无（不主动 fsync） | 按时间强制刷盘 |
| `log.flush.scheduler.interval.ms` | `Long.MAX_VALUE` | 检查是否需要刷盘的间隔 |
| `log.retention.check.interval.ms` | 300000（5 分钟） | 多久检查一次是否有 segment 可删除 |
| `log.segment.bytes` | 1073741824（1 GB） | 段大小，同时是删除与刷盘的粒度 |

**Kafka 的持久性策略是"靠副本，不靠 fsync"**：

- `acks=all` + `min.insync.replicas≥2` 保证消息**已写入多个 broker 的日志**（页缓存级别），从而在单台机器宕机时通过副本恢复；
- 它**不等于已落盘**。极端情况下（多台机器同时断电且都未 fsync）理论上会丢已确认消息，Kafka 的设计取舍是接受这个概率，换取数量级的吞吐优势；
- 强制 `fsync`（把 `log.flush.interval.messages` 或 `log.flush.interval.ms` 设为小值）会让每次刷盘阻塞在毫秒级，吞吐可能下降一个数量级。**只有单副本且完全不能容忍 OS 崩溃的场景才考虑**；
- 依赖 OS 刷盘就意味着 `vm.dirty_*`（2.4）成为写延迟的重要旋钮。

### 3.4 可用性与"安全默认值"

| 参数 | 默认 | 建议 | 原因 |
|---|---|---|---|
| `unclean.leader.election.enable` | **false** | 保持 false | 允许非 ISR 副本被选为 leader 会提升可用性但**可能丢消息**（落后的副本成为 leader，已确认消息丢失）。改成 true 等于自愿放弃一致性 |
| `auto.create.topics.enable` | **true** | **改为 false** | 默认 true 时，任何拼错 topic 名的生产/消费请求都会隐式创建一个 topic，用的是 `num.partitions=1`、`default.replication.factor=1`——**无副本、无保留策略、无人知道它存在**。生产环境这是典型的"幽灵 topic"来源 |
| `num.partitions` | 1 | 显式设为 12/24 之类 | 决定自动创建（或 `kafka-topics.sh` 未指定时）topic 的分区数 |
| `default.replication.factor` | 1 | **显式设为 3** | 默认 1 意味着自动创建的 topic 没有冗余，单 broker 故障即丢数据 |
| `controlled.shutdown.enable` | true | 保持 true | broker 关闭前先把 leader 让给其他副本，缩短不可用窗口（见第八节） |
| `delete.topic.enable` | true | 保持 true | 关闭后 `--delete` 只打标记不真删 |
| `log.retention.hours` | 168（7 天） | 按业务定 | 与容量估算联动 |
| `offsets.topic.replication.factor` | 3 | 保持 3 | `__consumer_offsets` 是关键路径 |
| `offsets.retention.minutes` | 10080（7 天） | 视需要 | 组变空后位移保留时长，过期后 `auto.offset.reset` 重新生效（见 [[4-消费者与Rebalance]]） |
| `transaction.state.log.replication.factor` | 3 | 保持 3 | 用事务时必需 |
| `transaction.state.log.min.isr` | 1 | 用事务时建议 2 | 否则事务日志可能写不进去 |
| `connections.max.idle.ms` | 600000 | 视前置 LB 而定 | 若有 NAT/LB 的空闲超时更短，应把该值调到更小，避免使用已被对端关闭的连接 |

### 3.5 消息大小必须链路一致

放大消息大小时最容易踩的坑是只改了 broker 的 `message.max.bytes`：生产端可能先被 `max.request.size` 拒绝，消费端又可能因为缓冲估算而 OOM。**这条链路上的每个环节都要一起放大**：

| 环节 | 参数 | 默认 |
|---|---|---|
| 生产者 | `max.request.size` | 1048576（1 MB） |
| 生产者 | `buffer.memory` | 33554432（32 MB） |
| Broker（全局） | `message.max.bytes` | 1048588（约 1 MB + 记录开销） |
| Broker（请求上限） | `socket.request.max.bytes` | 104857600（100 MB） |
| Topic 级 | `max.message.bytes` | 继承 broker 的 `message.max.bytes` |
| 副本拉取（软限） | `replica.fetch.max.bytes` | 1048576（1 MB） |
| 副本拉取（软限） | `replica.fetch.response.max.bytes` | 10485760（10 MB） |
| 消费者 | `fetch.max.bytes` | 52428800（50 MB） |
| 消费者 | `max.partition.fetch.bytes` | 1048576（1 MB） |

规则：

1. **硬门槛在"准入"侧**：单条记录批必须 ≤ 生产者的 `max.request.size`、topic 的 `max.message.bytes`（未显式设置时继承 broker 的 `message.max.bytes`），以及 `socket.request.max.bytes`。超过前两者会被拒（`RecordTooLargeException` / `MESSAGE_TOO_LARGE`）；超过 `socket.request.max.bytes` 则整个请求在入口就被判超限，所以 `max.message.bytes` 必须远小于它。
2. **副本侧的 fetch 上限都是"软限"**：`replica.fetch.max.bytes` 与 `replica.fetch.response.max.bytes` 的官方说明都明确写着——若某分区**第一批**记录就超过该值，仍会返回该批以保证进度（KIP-74 引入的行为）。因此"单条消息大于 `replica.fetch.response.max.bytes` 会让 follower 永远拉不到数据、URP 永不恢复"是**旧版本（KIP-74 之前）的结论，现代版本不成立**。
3. **但软限不等于可以忽略**：超大单条会让每次 fetch 都携带一个超大记录批，突破 broker/客户端的缓冲与内存预期，放大 GC 压力与副本同步延迟；消费侧的 `max.partition.fetch.bytes` 与 `fetch.max.bytes` 同理（都是软限，但仍应放大以免内存估算失真、避免单次 fetch 占用过多堆内存）。
4. 大消息本身是反模式：它降低批量效率、放大 GC 与重试成本。若必须用，优先考虑"拆分成多条 + 业务侧组装"，或把大 payload 放对象存储、Kafka 只传引用。

> [!tip] 排查"消息太大"的三条命令
> ```bash
> # 1. 看 topic 实际生效的 max.message.bytes（topic 级配置会覆盖 broker 全局）
> kafka-configs.sh --bootstrap-server broker1:9092 --describe --entity-type topics --entity-name order-topic
> # 2. 看 broker 全局默认
> kafka-configs.sh --bootstrap-server broker1:9092 --describe --entity-type brokers --entity-name 1
> # 3. 确认客户端报错到底是哪个限制触发的（生产者日志 max.request.size / broker message.max.bytes / 副本 fetch）
> ```

## 四、Topic 运维

### 4.1 创建与扩容分区

```bash
# 创建 topic：常用配置直接写在一行里
kafka-topics.sh --bootstrap-server broker1:9092 --create --topic order-topic \
  --partitions 12 --replication-factor 3 \
  --config retention.ms=604800000 \
  --config min.insync.replicas=2 \
  --config max.message.bytes=2097152

# 查看（关注 ISR、Leader、配置覆盖）
kafka-topics.sh --bootstrap-server broker1:9092 --describe --topic order-topic

# 只增加分区（唯一允许的"分区数变更"）
kafka-topics.sh --bootstrap-server broker1:9092 --alter --topic order-topic --partitions 24

# 删除
kafka-topics.sh --bootstrap-server broker1:9092 --delete --topic order-topic
```

> [!warning] "分区只能增不能减"
> Kafka **没有**减少分区的官方命令。原因是已有数据在分区上的归属无法重新映射（消息不会因为分区数变化而搬家）。要减分区只能：新建一个分区更少的 topic → 用消费-生产程序把数据搬过去 → 切流量 → 删除旧 topic。
>
> 增加分区的三个副作用必须提前告知业务方：
> 1. **触发一次 rebalance**（所有消费者重新分配）；
> 2. **key 到分区的映射改变**（`hash(key) % 分区数` 变了），**同一 key 的顺序性在变更点前后不再保证**；
> 3. 依赖"分区数固定"的假设（如按分区做本地聚合、按分区并行计算）全部失效。

### 4.2 副本重分配三阶段（generate → execute → verify）

用于：broker 扩缩容、跨机架打散、修复丢失的副本、把热点分区迁走。

**第一步：generate（生成计划）**

```bash
cat > topics-to-move.json <<'EOF'
{"topics":[{"topic":"order-topic"}],"version":1}
EOF

kafka-reassign-partitions.sh --bootstrap-server broker1:9092 \
  --topics-to-move-json-file topics-to-move.json \
  --broker-list "1,2,3" \
  --generate
```

输出包含两段 JSON：`Current partition replica assignment`（**先保存，用于回滚**）和 `Proposed partition reassignment configuration`（保存为 `reassignment.json`，可按需手工调整 `replicas` 顺序——**第一个副本就是首选副本/leader**）。

**第二步：execute（执行，带限流）**

```bash
kafka-reassign-partitions.sh --bootstrap-server broker1:9092 \
  --reassignment-json-file reassignment.json \
  --throttle 104857600 \
  --execute
```

- `--throttle` 单位是**字节/秒**（上面是 100 MB/s），用于限制迁移流量，避免打满网络影响正常读写；
- `--execute` 会返回当前限流值；如果进度太慢，可以再次执行 `--execute` 并传入更大的 `--throttle` 来提速（同一条重分配任务）；
- 若要在已有副本基础上**只增删个别副本**（而非整体重排），新版提供 `--additional` 模式，避免全量数据搬迁。

**第三步：verify（校验）**

```bash
kafka-reassign-partitions.sh --bootstrap-server broker1:9092 \
  --reassignment-json-file reassignment.json \
  --verify
```

输出 `Status of partition reassignment`，每个分区显示 `completed` 或 `still in progress`。全部完成后必须做两件事：

1. 确认 ISR 已满员（`kafka-topics.sh --describe`）；
2. **确认限流配置已清理**。迁移过程中会在 broker 上启用 `leader.replication.throttled.rate` / `follower.replication.throttled.rate`，并在 topic 上设置 `leader.replication.throttled.replicas` / `follower.replication.throttled.replicas`；若残留，会**长期限制正常副本追赶速度**，表现为"平时正常，一旦落后就再也追不上"。

```bash
# 查看并清理 broker 级限流
kafka-configs.sh --bootstrap-server broker1:9092 --describe --entity-type brokers --entity-name 1
kafka-configs.sh --bootstrap-server broker1:9092 --alter --entity-type brokers --entity-name 1 \
  --delete-config follower.replication.throttled.rate
# 查看并清理 topic 级限流
kafka-configs.sh --bootstrap-server broker1:9092 --describe --entity-type topics --entity-name order-topic
kafka-configs.sh --bootstrap-server broker1:9092 --alter --entity-type topics --entity-name order-topic \
  --delete-config follower.replication.throttled.replicas
```

> [!warning] 重分配的三个代价
> 1. **磁盘占用临时翻倍**：迁移期间同一分区同时存在于源与目标 broker，容量规划必须预留；
> 2. **网络与磁盘 IO 上升**：即使限流，也会挤占正常请求的资源，**避开业务高峰**执行；
> 3. **期间该分区的副本分布是"中间态"**：如果恰逢 broker 故障，可用性可能比正常态更脆弱。逐分区/逐 topic 分批做，做完一批验证一批。

### 4.3 优先副本与 leader 均衡

- 每个分区的 AR（Assigned Replicas）列表里**第一个副本**称为**优先副本（preferred replica）**；正常情况下它应该是 leader，这样 leader 分布与副本分布一致，负载才均衡。
- broker 重启、故障切换后，leader 可能落到非优先副本上，造成"某台 broker 承担了远超比例的 leader 流量"（leader 承载所有读写，follower 只拉取）。
- 相关配置：

| 参数 | 默认 | 说明 |
|---|---|---|
| `auto.leader.rebalance.enable` | true | 是否允许 controller 自动把 leader 切回优先副本 |
| `leader.imbalance.check.interval.seconds` | 300 | 检查不均衡的间隔 |
| `leader.imbalance.per.broker.percentage` | 10 | 单 broker 的 leader 不均衡率阈值，超过才触发自动均衡 |

- 监控指标：`kafka.controller:type=KafkaController,name=PreferredReplicaImbalanceCount`（> 0 说明有分区 leader 不在优先副本上）、`kafka.server:type=ReplicaManager,name=LeaderCount`（各 broker 的 leader 数是否接近）。
- 手动触发优先副本选举：

```bash
# 单分区
kafka-leader-election.sh --bootstrap-server broker1:9092 \
  --election-type PREFERRED --topic order-topic --partition 0
# 所有分区（低峰期执行，会引发大量 leader 切换）
kafka-leader-election.sh --bootstrap-server broker1:9092 \
  --election-type PREFERRED --all-topic-partitions
```

- `--election-type UNCLEAN`：在 ISR 为空（没有可用副本）时强制把某个非同步副本选为 leader。**会丢数据**，只在"宁可丢一部分也要恢复可用"的极端场景下用，且 broker 侧 `unclean.leader.election.enable` 必须为 true。
- 关闭 `auto.leader.rebalance.enable` 的理由：leader 切换有**秒级不可用窗口**，某些团队选择在低峰手动执行，避免业务高峰被自动均衡"打冷枪"。代价是需要自己监控不均衡度。

## 六、监控指标

采集方式：broker 通过 `export JMX_PORT=9999` 暴露 JMX，再由 Prometheus JMX Exporter / `kafka_exporter` 之类转成时序指标；客户端（producer/consumer）通过 `-Dcom.sun.management.jmxremote.*` 或应用内 `KafkaClientMetrics`（Micrometer）上报。

MBean 命名规律：broker 端是 `kafka.server:` / `kafka.network:` / `kafka.log:` / `kafka.controller:`；客户端是 `kafka.producer:` / `kafka.consumer:`，且都带 `client-id` 维度。

### 6.1 Broker 指标

| 指标（MBean → 属性） | 含义 | 不健康的样子 | 处置方向 |
|---|---|---|---|
| `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions` | 副本数不足 ISR 的分区数 | **> 0 且持续数分钟** | 查磁盘 IO、网络、`num.replica.fetchers`、`replica.lag.time.max.ms` |
| `kafka.server:type=ReplicaManager,name=UnderMinIsrPartitionCount` | ISR 数量低于 `min.insync.replicas` 的分区数 | > 0 → 这些分区的写入**已被拒绝**（`NotEnoughReplicas`） | 立即恢复副本；期间生产者会重试/失败 |
| `kafka.controller:type=KafkaController,name=OfflinePartitionsCount` | 没有任何可用 leader 的分区数 | **> 0 即最高级告警** | 数据不可用，见第十节 |
| `kafka.controller:type=KafkaController,name=ActiveControllerCount` | 本 broker 是否为 active controller | 集群内**总和必须恒为 1**；出现 0 → 无 controller（元数据操作全停）；出现 2 → 脑裂 | 重启异常节点，检查元数据存储 |
| `kafka.server:type=ReplicaManager,name=IsrShrinksPerSec` / `IsrExpandsPerSec` | ISR 收缩/扩张速率 | 长期非零 | follower 追不上，优先查磁盘与网络 |
| `kafka.server:type=ReplicaManager,name=PartitionCount` | 本 broker 承载的分区数 | 显著高于其他节点 → 不均衡 | 重分配/规划问题 |
| `kafka.server:type=ReplicaManager,name=LeaderCount` | 本 broker 的 leader 分区数 | 节点间差异大 | 优先副本选举（4.3） |
| `kafka.server:type=ReplicaFetcherManager,name=MaxLag,clientId=Replica` | follower 落后的最大消息数 | 持续增大 | 副本同步受阻 |
| `kafka.server:type=KafkaRequestHandlerPool,name=RequestHandlerAvgIdlePercent` | IO 线程平均空闲率 | **持续 < 0.3** | 请求处理饱和：加 broker/分区，或查磁盘与慢请求；**不要先加线程** |
| `kafka.network:type=SocketServer,name=NetworkProcessorAvgIdlePercent` | 网络线程平均空闲率 | 持续 < 0.3 | 网络处理饱和 |
| `kafka.network:type=RequestMetrics,name=TotalTimeMs,request=Produce`（及 `FetchConsumer`、`FetchFollower`） | 各请求类型的处理耗时分布（`Mean` / `99thPercentile` / `Max`） | P99 抬升、Max 出现尖刺 | 定位是哪个请求路径变慢 |
| `kafka.server:type=BrokerTopicMetrics,name=MessagesInPerSec` | 消息写入速率 | 突增/骤降 | 结合 lag 判断是流量问题还是故障 |
| `kafka.server:type=BrokerTopicMetrics,name=BytesInPerSec` / `BytesOutPerSec` | 入/出流量 | 出流量远超预期 | `BytesOut` 通常高于 `BytesIn`（多消费者 × RF） |
| `kafka.server:type=BrokerTopicMetrics,name=BytesRejectedPerSec` | 被拒字节数 | **> 0** | 超出 `socket.request.max.bytes` 或消息过大 |
| `kafka.server:type=BrokerTopicMetrics,name=FailedProduceRequestsPerSec` / `FailedFetchRequestsPerSec` | 失败的请求数 | 持续 > 0 | 权限、配额、副本不足、leader 切换 |
| `kafka.log:type=LogFlushStats,name=LogFlushRateAndTimeMs` | 刷盘速率与耗时 | 开了强制刷盘时耗时显著上升 | 确认是否误开了 `log.flush.*` |
| `kafka.controller:type=ControllerEventManager,name=EventQueueSize` | controller 事件队列积压 | 持续增长 | controller 处理不过来：分区过多、元数据操作风暴 |
| `kafka.controller:type=KafkaController,name=PreferredReplicaImbalanceCount` | leader 不在优先副本上的分区数 | > 0 | 手动/自动优先副本选举 |
| `kafka.server:type=DelayedOperationPurgatory,name=PurgatorySize,delayedOperation=Produce` | 生产者等待 `acks` 的挂起请求数 | 持续高 | 副本同步慢导致确认延迟 |
| `kafka.server:type=KafkaServer,name=BrokerState` | broker 状态（3 = Running） | 长时间非 3 | 启动异常、正在关闭、隔离中 |

### 6.2 Producer 指标（`kafka.producer:type=producer-metrics,client-id=X`）

| 指标 | 含义 | 不健康的样子 |
|---|---|---|
| `record-error-rate` | 发送失败速率 | **持续 > 0**：消息在丢（重试耗尽） |
| `record-retry-rate` | 重试速率 | 明显上升 → 超时/leader 切换/副本不足 |
| `request-latency-avg` / `request-latency-max` | 请求往返延迟 | P99 上升 → broker 慢或网络问题 |
| `record-queue-time-avg` | 记录在客户端缓冲区的等待时间 | 上升 → 发送端排队（broker 慢，或 `linger.ms`/批量配置过大） |
| `record-send-rate` | 发送速率 | 骤降 → 上游或 broker 异常 |
| `batch-size-avg` | 平均批量大小 | 远小于 `batch.size` → 批量效率低，可调 `linger.ms` |
| `compression-rate-avg` | 压缩率 | 变差 → 压缩算法/数据类型变化，带宽与磁盘成本上升 |
| `buffer-available-bytes` | 可用缓冲 | 接近 0 → 后续 `send()` 会阻塞，最终 `max.block.ms` 超时抛异常 |
| `buffer-exhausted-rate` | 缓冲耗尽快慢 | > 0 说明生产快于发送 |
| `waiting-threads` | 阻塞在缓冲上的线程数 | > 0 需关注 |
| `metadata-age` | 元数据年龄 | 过大说明元数据长期未刷新（可能是连接问题） |

### 6.3 Consumer 指标

`kafka.consumer:type=consumer-fetch-manager-metrics,client-id=X`：

| 指标 | 含义 | 不健康的样子 |
|---|---|---|
| `records-lag-max` | 所有分区中最大的 lag | 持续增长（注意：它基于客户端 fetch position 计算，**不等于** `kafka-consumer-groups.sh` 的 LAG，详见 [[4-消费者与Rebalance]]） |
| `records-lag`（带 topic/partition 维度） | 单分区 lag | 个别分区独高 → 分区热点/key 倾斜 |
| `records-lead-min` | 最小 lead | 异常（尤其为负）说明见到过的数据在 broker 上已不存在（日志被截断，如非清洁选举后回退） |
| `fetch-latency-avg` / `fetch-latency-max` | fetch 往返延迟 | 上升 → 服务端慢（磁盘饱和、页缓存不足）或网络问题 |
| `bytes-consumed-rate` / `records-consumed-rate` | 消费速率 | 骤降 → 处理阻塞或 broker 慢 |
| `fetch-rate` / `fetch-size-avg` | fetch 频次与大小 | fetch 频繁但很小 → 服务端攒批不足或 `fetch.min.bytes` 太小 |

`kafka.consumer:type=consumer-coordinator-metrics,client-id=X`：

| 指标 | 含义 | 不健康的样子 |
|---|---|---|
| `commit-latency-avg` / `commit-latency-max` | 位移提交延迟 | 上升 → coordinator 所在 broker 慢（`__consumer_offsets` 压力） |
| `commit-rate` | 提交频次 | 异常升高 → 提交过频（可加大批量） |
| `assigned-partitions` | 本成员持有的分区数 | 成员之间差异大 → 分配不均衡 |
| `rebalance-latency-avg` / `rebalance-latency-max` | 单次 rebalance 耗时 | 数十秒以上 → 组内处理阻塞或成员过多 |
| `rebalance-total` / `rebalance-rate-per-hour` | rebalance 累计/频率 | **每小时数十次以上 = rebalance 风暴** |
| `failed-rebalance-total` | 失败的 rebalance 次数 | > 0 需排查 |
| `last-rebalance-seconds-ago` | 距上次 rebalance 的秒数 | 长期接近 0 → 一直在 rebalance |
| `join-rate` / `join-time-avg` / `sync-time-avg` | 加入/同步的频次与耗时 | 高 → 大组或大量分区 |
| `heartbeat-rate` / `heartbeat-response-time-max` | 心跳频次与最大响应时间 | 响应时间高 → coordinator 慢或网络抖动 |
| `last-heartbeat-seconds-ago` | 距上次心跳的秒数 | 增大 → 心跳异常（可能被踢出组） |

### 6.4 告警基线（起点，按业务调整）

| 级别 | 条件 |
|---|---|
| P0（立即介入） | `OfflinePartitionsCount > 0`；`ActiveControllerCount` 总和 ≠ 1；磁盘使用率 > 85%；`underMinIsrPartitionCount > 0` |
| P1（15 分钟内） | `UnderReplicatedPartitions > 0` 持续 5 分钟；`BytesRejectedPerSec > 0`；`rebalance-rate-per-hour` 超阈值；消费 lag 持续增长超过 N 分钟 |
| P2（当班处理） | `RequestHandlerAvgIdlePercent < 0.3`；`fetch-latency-avg` P99 抬升；生产 `record-error-rate > 0`；`PreferredReplicaImbalanceCount > 0` |
| P3（计划处理） | 分区数不均衡、leader 数不均衡、批量大小偏小、磁盘水位 > 70% |

## 八、集群升级与滚动重启

### 8.1 升级顺序与版本兼容

- **先升 broker，再升客户端**（也可以反过来，但要保证跨版本兼容窗口）。Kafka 保证相邻版本之间 broker 与客户端双向兼容，因此滚动升级过程中新旧混跑是正常的。
- **不要跨多个大版本一次性升级**：一次一个 minor（如 3.6 → 3.7 → 3.8），每步都验证。
- ZK 模式（旧版本）的双阶段升级：先把所有 broker 的**二进制**升级完，再调整 `inter.broker.protocol.version`（以及早期版本的 `log.message.format.version`）让新协议生效——这一步才是真正"不可回退"的分界线，必须在全部 broker 升完后进行。
- **KRaft 模式**用 `metadata.version` 管理协议演进（`kafka-features.sh describe` 查看、`upgrade` 升级），不再需要手工设置 `inter.broker.protocol.version` 这类参数。
- 升级前必须读目标版本的 release notes 中的 **"Notable changes" / 破坏性变更**（如默认值变化、移除的配置、协议版本要求）。

### 8.2 滚动重启（单机重启）标准步骤

```text
① 前置健康检查
   - UnderReplicatedPartitions = 0
   - OfflinePartitionsCount     = 0
   - ActiveControllerCount 总和 = 1
   - 无进行中的 kafka-reassign-partitions 任务
   - 目标 broker 磁盘水位安全，无 log dir failure
   - kafka-topics.sh --describe 抽查关键 topic 的 ISR 是否满员
        │
        ▼
② 重启一台：停止 → 启动（保持配置一致）
   - controlled.shutdown.enable=true（默认）会让 broker 先让出 leader 再退出
   - 等待：ISR 恢复满员、URP 回到 0、该 broker 的请求正常
        │
        ▼
③ 确认健康后再动下一台（不要并行重启多台！）
        │
        ▼
④ 全部完成后统一做一次回归：冒烟生产消费 + 关键 topic ISR + lag 检查
```

要点与坑：

| 项 | 说明 |
|---|---|
| `controlled.shutdown.enable` | 默认 **true**：关闭前把 leader 让给其他副本，缩短分区不可用窗口。`controlled.shutdown.max.retries`（默认 3）与 `controlled.shutdown.retry.backoff.ms`（默认 5000）控制让位重试。**不要关掉它** |
| 分区不可用窗口 | leader 切换期间该分区有**秒级**不可用（客户端需刷新元数据并重新选 leader）。频繁切换会放大这个窗口 |
| ISR 只剩 leader 的分区 | 若某分区其他副本都落后（ISR 里只有 leader），重启该 broker 会导致这个分区**直接 offline**，直到它回来。所以重启前必须确认 ISR 满员 |
| 不要同时重启同分区的两台副本持有者 | RF=2 或 `min.insync.replicas=2` 时，同时重启两台会让分区**不可写**（生产者收到 `NotEnoughReplicas` / `NotEnoughReplicasAfterAppend`） |
| controller 节点 | ZK 模式：controller 由 broker 竞选，重启 controller 会触发一次 controller 切换（秒级~分钟级，取决于分区数）；**优先重启非 controller 节点，或接受一次切换**。KRaft 模式：先重启 broker 角色节点，最后再逐台重启 controller 节点，确保 quorum 不丢多数 |
| ZK 模式的 ZK 集群 | 升级 Kafka 前先确认 ZooKeeper 集群自身健康（3 节点或 5 节点，不过半不可用） |
| 版本回退 | **跨版本回退非常危险**（新版本写入的元数据/协议旧版本可能不认）。不要依赖回退，先在同规格预发环境演练 |
| 消费者侧 | 消费者滚动重启建议配合静态成员与协作式协议，减少 rebalance 次数（见 [[4-消费者与Rebalance]]） |

### 8.3 机架感知与故障域

- `broker.rack` 设置为机架或可用区标识；创建/重分配副本时 Kafka 会尽量让同一分区的副本分布在不同 rack。
- 效果：单机架断电不会导致分区完全不可用（只要其他 rack 的副本在 ISR 内）。
- 限制：**只影响新的副本分配**，已有分区不会自动重排，需要显式重分配。
- KRaft 下 controller quorum 也应跨机架，避免整个 quorum 随一个机架消失（3 节点 quorum 丢 2 台即不可用）。
- 云环境注意：跨 AZ 的副本流量有延迟与费用；RF=3 跨 3 个 AZ 是最常见也最稳妥的配置。

## 九、KRaft 运维要点

> **重要事实：ZooKeeper 在 Kafka 4.0 被彻底移除**，`zookeeper.connect` 与 ZK 模式属于 legacy。新集群一律用 KRaft；3.x 里 ZK 模式仍可用，并提供 ZK→KRaft 的迁移路径，但流程复杂、必须先在预发完整演练。

### 9.1 角色与 quorum

| 配置 | 说明 |
|---|---|
| `process.roles` | `broker` / `controller` / `broker,controller`。**生产必须分离角色**（`broker,controller` 只用于开发/测试） |
| `node.id` | 每个节点唯一的整数 ID |
| `controller.quorum.voters` | `id@host:port,...` 形式的静态 quorum 成员列表 |
| `controller.listener.names` | controller 监听器名字（如 `CONTROLLER`），controller 间通信使用独立端口 |
| `metadata.log.dir` | controller 元数据日志目录（默认取 `log.dirs` 的第一个目录）。纯 controller 节点也需要它 |
| `broker.session.timeout.ms` | broker 向 controller 注册会话的超时（默认 9000） |
| `broker.heartbeat.interval.ms` | broker 到 controller 的心跳间隔（默认 2000） |

**quorum 大小怎么选**（多数派原则，与 ZooKeeper 一致）：

| controller 数 | 容忍故障数 | 说明 |
|---|---|---|
| 1 | 0 | 只能开发/测试 |
| 3 | 1 | **生产推荐的最小配置** |
| 4 | 1 | 不划算（容错与 3 相同，成本更高） |
| 5 | 2 | 高可用要求高时使用 |
| 6 | 2 | 不划算 |

### 9.2 元数据日志与快照

- KRaft 把集群元数据（topic、分区、ISR、配置、ACL 等）存放在一个**单分区的内部日志 `__cluster_metadata`** 中，由 controller quorum 通过 Raft 复制。
- 该日志会不断追加，靠**快照**控制体积：
  - `metadata.log.max.record.bytes.between.snapshots`：累积多少字节的元数据变更后打快照（默认量级为 20 MB）；
  - `metadata.log.max.snapshot.interval.ms`：最长多久打一次快照（默认 1 小时量级）；
  - 快照与日志位于 `metadata.log.dir` 下的 `__cluster_metadata-0/` 目录。
- **分区数越多，快照越大、controller 重启加载越慢**。这是 KRaft 时代"分区数上限"的主要约束（而不是 ZK 的写放大）。
- 运维工具：

```bash
# 生成 cluster id 并格式化存储目录（新集群初始化 / 新增节点）
kafka-storage.sh random-uuid
kafka-storage.sh format -t <cluster-id> -c config/kraft/server.properties

# 查看 quorum 状态与复制情况
kafka-metadata-quorum.sh --bootstrap-server broker1:9092 describe --status
kafka-metadata-quorum.sh --bootstrap-server broker1:9092 describe --replication

# 查看 / 升级元数据特性版本
kafka-features.sh --bootstrap-server broker1:9092 describe

# 浏览元数据日志与快照（排障：某个 topic/分区到底注册成了什么样）
kafka-metadata-shell.sh --bootstrap-server broker1:9092
```

### 9.3 动态 quorum 与迁移

- **动态 quorum（KIP-853，4.0 正式提供）**支持在线增加/移除 controller 节点，无需停机重建集群：

```bash
# 在启用动态 quorum 的集群上增删 controller
kafka-metadata-quorum.sh --bootstrap-server broker1:9092 add-controller \
  --dynamic-quorum --controller <id>@<host>:<port>
kafka-metadata-quorum.sh --bootstrap-server broker1:9092 remove-controller \
  --dynamic-quorum --controller <id>
```

- **ZK → KRaft 迁移（3.5+）**：官方提供在线迁移路径（先在 ZK 集群开启迁移、再逐步引入 controller 角色、最后切换为纯 KRaft）。虽然设计为在线，但涉及元数据双写与角色切换，**任何生产迁移都必须先在同等规模的预发环境完整走一遍**，并准备好回退方案。
- **升级/重启 controller 时的注意点**：一次只重启一个 controller，重启后确认 `describe --status` 显示该节点已追上且 quorum 有 leader，再动下一个；不要同时重启多数节点导致 quorum 失去多数派。

## 十、故障处理速查表

| 现象 | 可能原因 | 处置动作 |
|---|---|---|
| `OfflinePartitionsCount > 0`；`kafka-topics.sh --describe` 显示某分区 `Leader: none` | 该分区所有副本都不在 ISR（或所在 broker 全下线）；ISR 收缩到空后 leader 被清空 | 1) 先恢复 broker（重启/修盘）；2) 若 broker 无法恢复且必须恢复可用，评估后用 `kafka-leader-election.sh --election-type UNCLEAN` 强制选举（**会丢数据**，需 `unclean.leader.election.enable=true`）；3) 恢复到可用后立刻做副本重分配补齐 |
| 生产者报 `LEADER_NOT_AVAILABLE` / `UNKNOWN_TOPIC_OR_PARTITION` | leader 正在选举中；topic 被删；元数据尚未同步；`auto.create.topics.enable=false` 时 topic 不存在 | 确认 topic 是否存在；等待 leader 选举完成；若是刚重启的 broker，给客户端几秒刷新元数据；检查是否真的从未创建该 topic |
| `UnderReplicatedPartitions > 0` 长时间不恢复（副本不同步） | follower 磁盘 IO 饱和、网络带宽打满、`num.replica.fetchers` 不足、`replica.lag.time.max.ms` 过小导致 ISR 抖动、**残留的迁移限流配置**、超大消息拉高单次 fetch 成本 | 用 `kafka-log-dirs.sh` 看磁盘；用 `kafka-configs.sh --describe` 查残留限流（这是最容易被忽略的一项）；必要时临时调大 `num.replica.fetchers`；确认消息大小链路（3.5）。注意副本 fetch 的两个上限都是**软限**，所以"消息太大把副本彻底卡死"在现代版本不是首要怀疑对象 |
| 磁盘写满 / 某 log dir 报错 / 部分分区离线 | 保留策略过长、流量增长、残留 segment 未删、`retention.bytes` 未设置 | 1) 立刻扩容或临时缩短 `retention.ms`（`kafka-configs.sh --alter --add-config`）；2) 用 `kafka-log-dirs.sh --describe` 定位哪些 broker 的哪些目录满；3) 磁盘恢复后确认受影响的 log dir 是否已恢复（log dir failure 只影响该目录，但需要重启或修复才能恢复使用） |
| broker 频繁掉线 / 反复重新注册 | 长 GC 停顿（堆过大或内存不足）、OOM、磁盘 IO 长时间卡死、网络抖动、`vm.swappiness` 导致 swap | 看 GC 日志与堆 dump；确认堆没超过 8 GB 量级；`vm.swappiness=1`；查系统日志有无 OOM killer；必要时调大 `broker.session.timeout.ms` |
| 消费 lag 飙升 | 生产突增、消费者掉线/rebalance、分区热点、下游变慢、分区数不足、broker 端 fetch 变慢 | 按 [[4-消费者与Rebalance]] 的十步排查表逐项排除；同时看 broker 的 `TotalTimeMs,request=FetchConsumer` 与磁盘利用率 |
| Rebalance 风暴（`rebalance-rate-per-hour` 高） | 消费者处理超过 `max.poll.interval.ms`、心跳超时、滚动重启、扩分区、组内订阅不一致、静态成员 ID 冲突 | 看消费者日志区分 `poll timeout` 与 `heartbeat expiration`；调大 `max.poll.interval.ms`、调小 `max.poll.records`；启用静态成员与 `CooperativeStickyAssignor`；详见 [[4-消费者与Rebalance]] |
| 生产者报 `NotEnoughReplicas` / `NotEnoughReplicasAfterAppend` | `acks=all` 且可用副本数 < `min.insync.replicas`（常见于同时重启多台、或副本落后被踢出 ISR） | 恢复副本到 ISR；避免同时重启同一分区的多个副本持有者；评估是否临时降低 `min.insync.replicas`（**会降低持久性保证，慎用**）；长期方案是保证 RF=3 且 `min.insync.replicas=2` |
| 生产者报 `RecordTooLargeException` / `MESSAGE_TOO_LARGE` | 单条消息超过生产者 `max.request.size`、topic `max.message.bytes` 或 `socket.request.max.bytes` | 按 3.5 的链路表逐项放大；优先考虑拆消息或外置大 payload |
| 生产者报 `TimeoutException` / `RequestTimedOut` | broker 端处理慢（`RequestHandlerAvgIdlePercent` 低）、网络问题、副本确认慢、`request.timeout.ms` 过小 | 看 broker 的 `TotalTimeMs` 与磁盘利用率；排查副本同步；适度调大 `request.timeout.ms` 与 `retries`（但根因是 broker 慢） |
| 消费者报 `CoordinatorNotAvailableException` / `NOT_COORDINATOR` / `CommitFailedException` | coordinator 迁移（`__consumer_offsets` 分区 leader 切换）；broker 抖动；代际失效（rebalance 期间提交） | 短暂错误会自动重试恢复；频繁出现说明承载 `__consumer_offsets` 的 broker 有问题（磁盘/GC）；`CommitFailedException` 通常意味着已发生 rebalance，应检查处理耗时是否超过 `max.poll.interval.ms` |
| `Too many open files` | `ulimit -n` 不足（分区/段数多、副本多、连接多） | 提升 `nofile` 限制并重启 broker；核对 1.4 的句柄估算 |
| 客户端连不上 / 认证失败 | listener 配置、`advertised.listeners` 不可达、SASL/SSL 配置不一致、防火墙 | 用 `kafka-broker-api-versions.sh --bootstrap-server` 验证连通性；确认 `advertised.listeners` 是客户端能访问的地址；对齐 `--command-config` |

> [!tip] 排障的通用心法
> 1. **先看 broker 端指标**（`OfflinePartitionsCount` → `UnderReplicatedPartitions` → 磁盘水位 → `RequestHandlerAvgIdlePercent`），再看客户端；
> 2. **先看"是否可用"，再看"是否快"**；
> 3. **区分"集群整体慢"与"某个分区慢"**：前者查资源（磁盘/网络/CPU），后者查热点与副本分布；
> 4. 任何"改配置救急"的操作都要写下回滚方式，并在事后用容量/规划（第一节）解决根因。
