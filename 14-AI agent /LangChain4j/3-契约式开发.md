# LangChain4j 契约式开发（AiServices）

> [!info] 这份笔记管什么
> **LangChain4j 最核心、也最有辨识度的部分**：一个接口 + 注解 = 一个 AI 能力。
> 覆盖注解全表、返回值形态、流式、**结构化输出的真实机制（⭐ 实测与厂商标称不同）**、护栏 Guardrail、以及 5 个构建期就报错的配置陷阱。
> 所有代码在 **1.23.0** 编译通过；带 ⭐ 的行为由"脚本化假模型"实跑 `AiServices` 内部流程得出，**不依赖 API Key**。
> 注意：**§5 的结构化输出结论**是依据"框架实际发出的请求"得出的，真实模型的配合程度（是否遵守 schema）仍需有 Key 时再验一次，已在 §5 标注。

---

## 1. 为什么叫"契约式"

### 1.1 两种写法对比

**Spring AI（管道式）**——你描述"调用过程"：

```java
String answer = chatClient.prompt()
        .system("你是 Java 专家")
        .user(question)
        .call()
        .content();
```

**LangChain4j（契约式）**——你描述"我要的能力"，框架生成实现：

```java
interface JavaExpert {
    @SystemMessage("你是 Java 专家，回答简洁")
    String answer(@UserMessage String question);
}

JavaExpert expert = AiServices.create(JavaExpert.class, model);
String answer = expert.answer(question);
```

### 1.2 这个设计带来了什么

| 收益 | 说明 |
|---|---|
| **业务代码干净** | 业务层只依赖接口，像调 Repository 一样调 AI |
| **可测试** | 接口可以 Mock；也能用"假模型"回放（本笔记 §6） |
| **天然可组合** | 一个接口里可以放多个能力方法，共享系统提示词与记忆 |
| **可治理** | 护栏、监听器、工具统一挂在 `AiServices.builder` 上 |
| **主键友好** | `@MemoryId` 让一个 Spring 单例服务所有会话 |

> [!warning] 代价
> 隐式魔法多：**注解写错在构建期才炸**、方法参数没法在 IDE 里跳转看提示词、调试要看调试日志。所以下面 §6 的"构建期错误清单"很重要。

## 2. 注解全表

| 注解 | 位置 | 作用 | 易错点 |
|---|---|---|---|
| `@SystemMessage` | 方法 / 接口 | 系统提示词，支持 `{{var}}` | 接口级和 builder 级同时存在时的优先级以文档为准，**统一用一种** |
| `@UserMessage` | 方法 / 参数 | 用户消息模板 | 放**方法上**时，无注解参数会被填入 `{{it}}` |
| `@V("name")` | 参数 | 模板变量名 | 名字必须和模板里 `{{name}}` 一致，否则构建期报错 |
| `@MemoryId` | 参数 | 会话 id | **必须配 `chatMemoryProvider`** |
| `@UserName` | 参数 | 用户名 | 一般用于审计/提示词 |
| `@Tool` | 方法 | 暴露为工具（见 [[5-Agent工具调用]]） | 描述是给模型看的，别写成 JavaDoc 风格废话 |
| `@Moderate` | 方法 | 用 `ModerationModel` 校验 | 国内模型多不支持，少用 |

### 2.1 模板变量三种写法

```java
interface Rewriter {
    // ① 无注解参数 + 方法级 @UserMessage：参数自动填入 {{it}}
    @UserMessage("把这句话翻译成英文：{{it}}")
    String toEn(String text);

    // ② 多个命名变量
    @UserMessage("以 {{style}} 的风格重写：{{text}}")
    String rewrite(@V("text") String text, @V("style") String style);

    // ③ 接口级系统提示词 + 用户参数直传
    @SystemMessage("你是" + "法律顾问，回答需引用法条")
    String legal(@UserMessage String question);
}
```

> [!tip] 提示词放哪
> - **短规则** → 注解里
> - **长提示词 / 需要版本管理 / 需要 A/B** → 放资源文件或配置中心，用 `String` 常量拼进 `@SystemMessage`（注解值是编译期常量即可）
> - **需要按租户差异化** → `AiServices.builder(...).systemMessageProvider(ctx -> ...)` 更灵活

## 3. 返回值形态（**方法签名就是输出契约**）

| 返回类型 | 含义 | 什么时候用 |
|---|---|---|
| `String` | 纯文本 | 对话、摘要 |
| `ExtractedPOJO` | 结构化对象 | 分类、抽取、表单填充 |
| `Result<T>` | 对象 + 元信息（tokenUsage、sources、toolExecutions、finishReason） | **需要审计/计费/回查来源时** |
| `TokenStream` | 流式 | SSE 打字机 |
| `void` | 流式回调模式（配合 `@Streaming`） | 只用回调时 |
| `boolean` / `int` / `enum` / `List<String>` | 简单类型 | 有专门 OutputParser |

```java
interface Service {
    String chat(String q);
    Ticket classify(String q);              // 结构化
    Result<Ticket> classifyWithMeta(String q); // 结构化 + 元信息
    TokenStream stream(String q);           // 流式
}
```

> [!note] `Result<T>` 是被低估的能力
> `r.tokenUsage()` 能**按调用精确计费**；`r.sources()` 能**把 RAG 命中的原始片段带回**做"引用溯源"；`r.toolExecutions()` 能审计 Agent 到底调了什么工具。
> 生产里建议**业务方法统一返回 `Result<T>`**，把 Answer 模板类一个 `@Bean` 统一为 `Result<T>` 后处理。

## 4. 流式：`TokenStream`

```java
TokenStream ts = assistant.stream("用 3 句话介绍 LangChain4j");

ts.onPartialResponse(token -> out.print(token))
  .onCompleteResponse(r -> out.println("\n[done] usage=" + r.tokenUsage()))
  .onError(Throwable::printStackTrace)
  .start();                      // ⚠️ 必须显式 start()
```

| 回调 | 说明 |
|---|---|
| `onPartialResponse` | 文本增量 |
| `onPartialToolCall` / `onCompleteToolCall` | 流式下的工具调用片段（需要正确处理拼接） |
| `onCompleteResponse` | 完整响应（含用量） |
| `onError` | 异常 |
| `onRetrieved(...)` | RAG 命中片段先于生成吐出，可用于"先展示来源" |

> [!danger] 三个流式坑
> 1. **忘了 `.start()`** → 什么都不发生，且不报错
> 2. **回调里做阻塞 IO** → 拖慢整条流；要下沉到线程池
> 3. **接 SSE 时没处理断连** → 用户关页面后模型还在生成、继续计费。要么取消（可取消的运行句柄），要么用 `onError`/前端心跳兜底

## 5. ⭐ 结构化输出的真实机制（别被宣传误导）

**结论先行**：在 `langchain4j-core 1.23.0` + `AiServices` 里，**直接声明返回 POJO，框架不会自动要求模型开启 JSON 模式**。我们用"假模型"记录每次请求的 `responseFormat()` 得到：

```text
[structured] result=Ticket[customerName=张三, priority=P1, keywords=[扣费, 投诉]]
[structured] json-mode=false | raw=[false] tools=[0] rf=[null]     ← 模型的 responseFormat 是 null
[structured] schema=JsonSchema { name = "Ticket", rootElement = JsonObjectSchema {
               properties = {customerName=JsonStringSchema{...}, priority=JsonStringSchema{...},
                             keywords=JsonArraySchema{ items = JsonStringSchema{...} }},
               required = [], additionalProperties = null } }
```

**解读**：

1. 框架能**从 Java 类型推导出 JSON Schema**（`JsonSchemas.jsonSchemaFrom(Ticket.class)`）——这个很有用，你可以自己拿去做"提示词里贴 schema"或"校验"
2. 但 `AiServices` 把这套 schema 变成了**输出解析（OutputParser）**，**没有强制传给模型**
3. 结果是模型可能返回**被 Markdown 代码围栏包裹**、夹带解释、或缺字段的文本 → 解析失败 → 重试或抛错

> [!important] 实践结论
> - **能用原生 JSON/Schema 模式的模型**：在 `ChatModel` 的 builder 上显式设 `responseFormat(ResponseFormat.JSON)` 或 `strictJsonSchema(true)`（OpenAI builder 有这两个 key，实测存在）
> - **提示词里显式给 schema**：把 `JsonSchemas.jsonSchemaFrom(X.class)` 渲染进 `@SystemMessage`，比只给"返回 JSON"稳得多
> - **字段越少越好**：POJO 字段一多，小模型必定漏字段；用 `List<String>` 而不是嵌套对象
> - **枚举是好东西**：模型最容易在"自由文本分类"上出错的，用 `enum` 直接约束

```java
// 调试第一招：先把 schema 打印出来看看长什么样
JsonSchemas.jsonSchemaFrom(Ticket.class).ifPresent(s -> log.info("schema={}", s));
```

### 5.1 结构化输出模板（可复制）

```java
public record Ticket(String customerName, Category category, Priority priority,
                     boolean needHuman, List<String> keywords) {}
public enum Category { BILLING, BUG, FEATURE_REQUEST, COMPLAINT, OTHER }
public enum Priority { P0, P1, P2, P3 }

interface Classifier {
    @UserMessage("分析下面的客服工单，输出结构化结果：\n\n{{ticket}}")
    Ticket classify(@V("ticket") String ticket);
}
```

- `record` 可直接用（Jackson 支持下，1.23.0 实测解析成功）
- 枚举、`List<String>` 都支持
- 若返回类型解析失败，会抛 `RuntimeException`（输出解析异常），**要 try-catch 并降级**（例如降为人工）

## 6. ⭐ 构建期就报错的配置（实测清单）

这些错误**不是运行期**，而是 `AiServices.builder(...).build()` 时就抛 `IllegalConfigurationException`：

| # | 错误 | 原因 | 修法 |
|---|---|---|---|
| 1 | `In order to use @MemoryId, please configure the ChatMemoryProvider on ...` | 接口里有 `@MemoryId` 但没给 provider | `.chatMemoryProvider(id -> MessageWindowChatMemory.builder().id(id).maxMessages(20).build())` |
| 2 | `@V` 变量名与模板不匹配 | `{{text}}` 写成 `{{txt}}` | 改名对齐（文档描述行为，本机未复现） |
| 3 | `@Tool` 重复工具名 | 多个 bean 里同名方法 | 用 `@Tool(name = "...")` 显式命名（文档描述行为） |
| 4 | 返回类型不支持 | 自定义泛型/嵌套复杂结构 | 简化 POJO，或用 `Result<T>` 包装 |

> [!warning] 一个容易踩的"语义"坑（⭐ 实测）
> 接口里一旦有方法用了 `@MemoryId`，**同一接口下的所有方法都会被要求"能配记忆"**——校验是按接口做的。
> 现象：`interface Bot { String chat(@MemoryId String uid, ...); Ticket classify(String q); }`，builder 没配 provider 时报的仍是**第 1 条的 `@MemoryId` 错误**，指不到真正的问题。
> 缓解：**把"要记忆"和"不要记忆"的能力拆成不同接口**（`ChatBot` / `Classifier`），职责也更清楚。

> [!tip] 把校验当成好事
> 构建期报错 = **启动就崩，而不是上线后才崩**。在 Spring 里这意味着容器启动失败，K8s 会自动回滚。
> 所以「把 AiService 定义成 `@Bean` 让容器启动时构建」其实是**免费的配置校验**。

## 7. 护栏 Guardrail（生产必备）

### 7.1 两个接口

```java
public interface InputGuardrail {
    InputGuardrailResult validate(UserMessage userMessage);     // 输入检查
}
public interface OutputGuardrail {
    OutputGuardrailResult validate(AiMessage aiMessage);        // 输出检查
}
```

### 7.2 结果类型（决定后续行为）

| Input 返回 | 行为 |
|---|---|
| `success()` | 继续 |
| `fatal(msg)` | **立即终止**，抛 `GuardrailException`，不调用模型（省钱） |

| Output 返回 | 行为 |
|---|---|
| `success()` | 采用 |
| `retry(msg)` | **让模型重生成一次**（带反馈） |
| `reprompt(repromptMsg, ...)` | 用改写后的重新提问 |
| `failureWithMessageRemoval()` | 丢弃违规消息 |
| `fatal(msg)` | 终止并抛错 |

### 7.3 示例：注入拦截 + 敏感信息防泄露

```java
static class PromptInjectionGuardrail implements InputGuardrail {
    static final List<Pattern> BLOCK = List.of(
        Pattern.compile("(?i)ignore (all )?previous instructions"),
        Pattern.compile("忽略(之前|上面|以上)的?(所有)?(指令|要求)"),
        Pattern.compile("(?i)system prompt|你的系统提示词"));
    public InputGuardrailResult validate(UserMessage m) {
        for (Pattern p : BLOCK) if (p.matcher(m.singleText()).find()) return fatal("疑似提示词注入");
        return success();
    }
}

static class NoLeakOutputGuardrail implements OutputGuardrail {
    public OutputGuardrailResult validate(AiMessage r) {
        if (r.text().contains("sk-") || r.text().contains("password"))
            return retry("回答中疑似包含敏感信息，请重新组织语言");
        return success();
    }
}

SafeAssistant ai = AiServices.builder(SafeAssistant.class)
        .chatModel(model)
        .chatMemory(MessageWindowChatMemory.withMaxMessages(10))
        .inputGuardrails(new PromptInjectionGuardrail())
        .outputGuardrails(new NoLeakOutputGuardrail())
        .build();
```

> [!warning] 护栏不是万能的
> 正则拦截只能挡住"教科书式"注入。真正靠谱的分层是：**护栏（挡明显攻击）+ SystemMessage（定边界）+ 权限收敛（工具不带越权能力）+ 人工兜底**。
> 与 Spring AI 相比，LangChain4j 的护栏是**一等公民**（Spring AI 需要自己做 Advisor），这是它在大企业落地上的一个加分项。

## 8. 观察与拦截：监听器

```java
AiServices.builder(Assistant.class)
    .chatModel(model)
    .registerListener((AiServiceStartedEvent e) -> log.info("start"))
    .registerListener((AiServiceCompletedEvent e) -> log.info("done"))
    .afterToolExecution(e -> metrics.recordTool(e.request().name(), e.duration()))
    .beforeToolExecution(e -> audit.log(e.request()))
    .build();
```

- 1.x 有统一的 `AiServiceEvent` 事件体系（`registerListener`）
- 工具维度还有 `beforeToolExecution` / `afterToolExecution`（**实测可拿到 name / arguments / result**）
- 生产建议：把事件接到 Micrometer / OpenTelemetry，做到"每次调用一条 trace"，和 [[面试准备/专业技能/01-AI应用工程化|AI 应用工程化]] 里"稳定、成本、延迟、可观测、安全"五字诀对应

## 9. 用"假模型"做单元测试 ⭐

**这是 LangChain4j 契约式设计最大的红利**：接口可测。

> 前置说明：`ScriptedChatModel` 是**测试替身**，只为验证框架编排逻辑；它不产生真实智能，不能代替评测。

```java
public class ScriptedChatModel implements ChatModel {
    private final Deque<AiMessage> script = new ArrayDeque<>();

    public ScriptedChatModel thenText(String t) { script.add(AiMessage.from(t)); return this; }
    public ScriptedChatModel thenToolCall(String id, String name, String argsJson) {
        script.add(AiMessage.from(ToolExecutionRequest.builder()
                .id(id).name(name).arguments(argsJson).build()));
        return this;
    }

    @Override
    public ChatResponse doChat(ChatRequest request) {
        AiMessage next = script.poll();
        if (next == null) throw new IllegalStateException("脚本已用完");
        return ChatResponse.builder().aiMessage(next).build();
    }
}

// 测试
var model = new ScriptedChatModel().thenText("答案：42");
var assistant = AiServices.create(MyAssistant.class, model);
assertEquals("答案：42", assistant.ask("终极问题"));
```

⭐ 实测输出（记忆隔离 + 工具循环都在这个模式下一次跑完）：

```text
[tool-loop] answer=你的订单 A1001 已发货，顺丰 SF1234。 | tool.calls=1
[tool-loop] 调用次数=2 第二次消息数=4 工具数=[1, 1]
[tool-loop] 第二次模型看到的消息=[A1001 到哪了, [tool-result] SHIPPED|SF1234]
[memory] 会话u1第2次消息数=4 会话u2首次消息数=2
[memory] u2 看到=[我叫什么]
```

> [!success] 这对面试很有用
> 当被问"你怎么测 AI 功能？"——答"用脚本化假模型验证**框架编排逻辑**（消息序列、记忆隔离、工具回灌），用小样本评测集验证**模型效果**"，比"我们人工点点"高一个层级。

## 10. 完整示意外壳（可直接改）

```java
public class AssistantDemo {

    interface Assistant {
        @SystemMessage("""
                你是「小助」，企业知识库助手。
                规则：只基于事实回答；不确定就说不知道；不超过 120 字。
                """)
        String chat(String userMessage);

        @UserMessage("用 {{style}} 的语气说一遍：{{text}}")
        String rewrite(@V("text") String text, @V("style") String style);

        @SystemMessage("你能记住之前的对话")
        String chatWith(@MemoryId String chatId, @UserMessage String message);

        TokenStream streamChat(String message);
    }

    public static void main(String[] args) {
        ChatModel model = OpenAiChatModel.builder()
                .baseUrl(System.getenv("DEEPSEEK_BASE_URL"))
                .apiKey(System.getenv("DEEPSEEK_API_KEY"))
                .modelName("deepseek-chat")
                .build();

        Assistant a = AiServices.builder(Assistant.class)
                .chatModel(model)
                .streamingChatModel(streamingModel)   // 单独构建：OpenAiStreamingChatModel.builder() 同配置
                .chatMemoryProvider(id -> MessageWindowChatMemory.builder().id(id).maxMessages(20).build())
                .build();

        System.out.println(a.chat("什么是 Embedding？"));
        System.out.println(a.rewrite("系统明早八点维护", "正式"));
        System.out.println(a.chatWith("u001", "我叫 Vic"));
        System.out.println(a.chatWith("u002", "我叫什么？"));
    }
}
```

> 上面这份示例**编译通过**（本机 JDK 17 + langchain4j 1.23.0），但涉及真实调用的部分未跑（无 Key），见索引 §3 的验证说明。
