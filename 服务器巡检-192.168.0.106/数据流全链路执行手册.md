## 〇、先建立 5 个心智模型（读懂后面所有内容的前提）

| # | 模型 | 一句话 | 在哪一跳体现 |
|---|---|---|---|
| 1 | **数据有三种形态** | 消息（Kafka）→ 文件（HDFS）→ 表（Hive），每跳都是一次形态转换 | 全链路 |
| 2 | **数据与元数据分离** | HDFS 上的文件 = 数据；Hive Metastore 里的分区记录 = 元数据。**有数据 ≠ 能查到** | 第 3 跳 |
| 3 | **分区就是目录** | `dt=2026-10-08/hr=10` 既是 HDFS 目录名，也是 Hive 分区值，两者必须一字不差 | 第 2、3 跳 |
| 4 | **checkpoint 是可见性开关** | Flink 写 HDFS 时先写 `.inprogress`（Hive 看不见），checkpoint 成功后才改名转正 | 第 2 跳 |
| 5 | **幂等 = 可重跑** | `INSERT OVERWRITE` 分区 + ODS 永不被改写 → 任何一步失败都能重跑 | 第 4 跳 |

## 一、链路全景

```text
① 生产              ② 流处理               ③ 落盘               ④ 挂载             ⑤ 加工
KafkaDataGenerator   Dinky → Flink SQL      HDFS staging         ODS 外部表         DWD 内表
（Mac, mini-cluster）（k3s Flink 1.20）    （文件系统）         （元数据登记）      （ORC 精加工）
     │                    │                     │                    │                 │
     ▼                    ▼                     ▼                    ▼                 ▼
topic flink-demo    KafkaSource → FileSink   dt=…/hr=…/         ADD PARTITION     INSERT OVERWRITE
   :9092              每 60s checkpoint       part-*.json        LOCATION 映射      去重/CAST/解析时间
```

| 跳 | 数据形态变化 | 状态/进度载体 | 失败后重跑代价 |
|---|---|---|---|
| ① 生产 | Java 对象 → JSON 消息 | Kafka offset（分区内递增） | 无（继续产生） |
| ② 消费+落盘 | 消息 → JSON 文件 | consumer group offset + Flink checkpoint | 从 checkpoint/offset 续 |
| ③ 挂载 | 文件 → 表可见 | Hive Metastore 里的分区记录 | 补一条 ADD PARTITION |
| ④ 加工 | 原始表 → 精加工表 | DWD 分区（OVERWRITE） | 重跑该分区，幂等 |
| ⑤ 查询 | 表 → 结果 | 无（无状态） | 重查 |

## 二、第 1 跳：消息生产 → Kafka

### 2.1 要解决什么问题

把业务事件（订单）变成**可被多方消费的流**。生产者和消费者解耦：生产端只管发，谁消费、消费到哪，由 Kafka 的 offset 机制管。

### 2.2 底层机制（三个必懂概念）

**① topic / partition / offset**
- `flink-demo` 是 topic；它被切成 partition（你这里是 1 个：partition 0）
- 每条消息在分区内有一个**递增编号 = offset**，它是消息的"身份证"
- 查看当前最大 offset（= 已写入多少条）：

```bash
docker exec kafka kafka-get-offsets.sh --bootstrap-server localhost:29092 --topic flink-demo --time -1
# 输出: flink-demo:0:2263385   ← topic:partition:最大offset
```

**② consumer group（消费组）——断点续传的载体**

| 概念 | 含义 |
|---|---|
| group.id | 一个"读者"的编号，例如 `flink_hdfs_sink` |
| committed offset | 该组"已读到哪"的记录，存在 Kafka 内部 topic `__consumer_offsets` |
| LAG | 最大 offset − 已提交 offset = **还没读的数量** |

```bash
docker exec kafka kafka-consumer-groups.sh --bootstrap-server localhost:29092 \
  --describe --group flink_hdfs_sink
# CURRENT-OFFSET=已读  LOG-END-OFFSET=总量  LAG=积压
```

**③ 时间戳是绝对时间**
- 代码里 `System.currentTimeMillis()` 返回的是 **epoch 毫秒**（1970-01-01 UTC 起的毫秒数）
- **它和时区无关**——同一时刻在任何时区都是同一个 epoch 值。时区只影响"人类怎么读它"（详见第七章，这里埋了一个真实的坑）

### 2.3 启动与验证

```bash
cd /Users/vic/workspace-202606/ruoyi/flink
./start.sh produce          # 日志: /tmp/flink_produce.log

# 验证 1：作业在跑
grep "RUNNING" /tmp/flink_produce.log | tail -1
# 验证 2：offset 在涨（隔 10 秒执行两次，差值 ≈ 50）
docker exec kafka kafka-get-offsets.sh --bootstrap-server localhost:29092 --topic flink-demo --time -1
```

### 2.4 易错点

| 现象 | 原因 | 对策 |
|---|---|---|
| 容器内操作超时 | 用了 9092（EXTERNAL listener，广播宿主机 IP） | 容器内一律 `localhost:29092` |
| 外部客户端连不上 | advertised listeners 没配宿主机 IP | 检查 `KAFKA_CFG_ADVERTISED_LISTENERS` |
| 同一个 offset 被读两遍 | group 没有位点且 `auto.offset.reset=earliest` | 见第 2 跳的 startup.mode 三种语义 |
| 消息重复 | 生产者重试（`retries>0`，可能重复发送） | 下游去重（第 4 跳的 orderId 去重就是为此） |

## 三、第 2 跳：Flink 消费 + 写 HDFS

### 3.1 要解决什么问题

**持续地**从 Kafka 读、**可靠地**写进 HDFS，并且**知道自己读到哪了**（故障后不丢不重）。

### 3.2 底层机制

**① KafkaSource 的位点策略（`scan.startup.mode`）**

| 取值 | 语义 | 什么时候用 |
|---|---|---|
| `earliest-offset` | 从 topic 最早开始（忽略是否有位点） | 首次补历史 |
| `latest-offset` | 只消费启动之后的新消息 | 只要增量 |
| `group-offsets`（默认） | 从 group 已提交位点续读；**没有位点时报错**（除非配 auto.offset.reset） | 生产标准姿势 |

> 你踩过的坑：`group-offsets` + 新 group（无位点）+ 未配 `auto.offset.reset` → `NoOffsetForPartitionException`。**"位点在 Kafka 侧，不在你的脚本参数里"**——这是生产上"换个参数重跑却无效"的常见原因。

**② FileSink 的滚动与"文件转正"（模型 4 的落地）**

```text
写入中:  .part-<uuid>-0.inprogress.<checkpointId>   ← 文件名以 . 开头 → Hive 天然忽略（隐藏文件规则）
checkpoint 成功 → 改名:  part-<uuid>-0                ← 普通文件 → Hive 可读
```

因此：
- **没有 checkpoint 的作业，文件永远停在 `.inprogress`，Hive 永远查不到**
- `execution.checkpointing.interval = 60s` 不只是容错配置，**它决定了数据的可见延迟**
- `sink.rolling-policy.rollover-interval` 决定文件滚动（文件太大/太碎影响后续查询）

**③ checkpoint 是什么**

Flink 周期性给所有算子拍"快照"（barrier 对齐 → 各自保存状态 → JM 汇总）。对 KafkaSource，checkpoint 成功后会把 offset 提交回 Kafka（所以 `__consumer_offsets` 里的位点是 checkpoint 驱动的）。

### 3.3 作业 SQL 逐行详解

```sql
SET execution.checkpointing.interval = 60s;    -- 每 60 秒一次 checkpoint（文件转正 + offset 提交）

CREATE TABLE kafka_src ( ...字段... ) WITH (
  'connector'='kafka',                                    -- 选 connector 实现（工厂）
  'topic'='flink-demo',
  'properties.bootstrap.servers'='192.168.0.106:9092',    -- Pod 走外部 listener
  'properties.group.id'='flink_hdfs_sink',                -- 位点载体
  'scan.startup.mode'='earliest-offset',                  -- 首次补历史
  'json.ignore-parse-errors'='true',                      -- 跳过脏消息（历史里有非 JSON 实验数据）
  'format'='json');

CREATE TABLE hdfs_ods ( ...字段..., dt STRING ) PARTITIONED BY (dt) WITH (
  'connector'='filesystem',
  'path'='hdfs://192.168.0.106:8020/data/staging/flink-demo',   -- 必须写 IP：k3s Pod 解析不了 docker 别名 hadoop
  'format'='json',
  'sink.rolling-policy.rollover-interval'='15 min');

INSERT INTO hdfs_ods
SELECT *, DATE_FORMAT(TO_TIMESTAMP_LTZ(`timestamp`,3), 'yyyy-MM-dd') AS dt FROM kafka_src;
--        ↑ 毫秒 epoch → 时间戳；DATE_FORMAT 按 Flink 会话时区渲染（→ 第七章的坑）
```

### 3.4 验证

```bash
# 作业状态
curl -s http://localhost:30081/jobs
# checkpoint 是否在成功（completed 数增长才算健康）
curl -s http://localhost:30081/jobs/<jobId>/checkpoints | python3 -c "import sys,json;d=json.load(sys.stdin);print(d['counts'])"
# 文件是否转正（不带 inprogress 的才是成品）
docker exec hadoop hdfs dfs -ls -R /data/staging/flink-demo | grep -v inprogress
```

### 3.5 你踩过的坑（都是生产级故障模式）

| 故障 | 根因 | 文档 |
|---|---|---|
| `CatalogStoreHolder cannot be null` | Dinky 1.14 变体执行器 + Flink 1.20 API 断层 | [[Dinky修复方案]] |
| `ExtendedParser` / kafka factory 找不到 | Dinky 类路径缺 jar（编译在 Dinky JVM） | 同上 |
| 作业反复重启 `Failed to deserialize` | 脏消息 + checkpoint 未成功 → 无限重试同一条 | [[Kafka入Hive实操手册]] |
| `could only be written to 0 of 1 minReplication` | DN 注册 docker 内网 IP + 端口未发布 + UFW 拦截 | [[Flink-on-K8s-vs-YARN]] |

## 四、第 3 跳：HDFS → ODS（外部表挂载）

### 4.1 要解决什么问题

让 Hive **认识**HDFS 上那堆文件：文件是数据，Hive 要读它需要"元数据"告诉它——哪些列、什么格式、哪个目录、哪些分区。

### 4.2 底层机制

**① 外部表 vs 内表**

| | EXTERNAL TABLE（ODS 用） | 普通表（DWD 用） |
|---|---|---|
| `DROP TABLE` 时 | 只删元数据，**文件保留** | 元数据和数据一起删 |
| 数据生命周期 | Hive 不管，归数据本身 | Hive 管 |
| 适合 | 原始层、可重放数据 | 加工产物 |

**② 分区 = 目录（模型 3）**

```text
HDFS 目录:  /data/staging/flink-demo-stream/dt=2026-10-07/hr=15/part-xxx.json
Hive 表:    PARTITIONED BY (dt STRING, hr STRING)
            LOCATION '/data/staging/flink-demo-stream'
分区值:     dt='2026-10-07', hr='15'   ← 必须与目录名逐字一致
```

**③ 隐藏文件规则**：Hive 读取时**忽略以 `.` 或 `_` 开头的文件**——这就是为什么 `.inprogress` 未完成文件天然不会被查到（模型 4 的配合机制）。

**④ JsonSerDe 按列名映射**：JSON 的 key 必须与表列名一致（`orderId` 对 `orderId`）。多了不管，少了为 NULL。

### 4.3 命令与验证

```sql
ALTER TABLE ods.flink_demo_hi ADD IF NOT EXISTS PARTITION (dt='2026-10-08', hr='10');
SHOW PARTITIONS ods.flink_demo_hi;
SELECT COUNT(*) FROM ods.flink_demo_hi WHERE dt='2026-10-08' AND hr='10';
```

```bash
# 目录与分区对照自查（目录必须有，且层数与分区列数一致）
docker exec hadoop hdfs dfs -ls -R /data/staging/flink-demo-stream
```

### 4.4 易错点

| 现象 | 根因 | 对策 |
|---|---|---|
| 文件在 HDFS 但 `COUNT=0` | 忘 ADD PARTITION | 补挂；或 `MSCK REPAIR TABLE` 批量扫描 |
| 建表报 `file:/… is not a directory` | LOCATION 被解析到容器本地 FS（缺 core-site.xml） | 已修：hive 容器挂 core-site.xml |
| 分区挂上仍查不到数据 | 目录层级与分区列不匹配（如 dt+hr 表指向 dt 单级目录） | 见第九章"对齐自查" |
| 中文乱码 / 字段全 NULL | 编码不是 UTF-8 / JSON key 与列名不一致 | 统一 UTF-8；核对列名 |

## 五、第 4 跳：ODS → DWD（加工层）

### 5.1 要解决什么问题

ODS 是"能查到"，DWD 是"能信任"：解决**重复**、**精度**、**类型**、**时间语义**四类问题。

### 5.2 四类问题对应四种加工

```sql
INSERT OVERWRITE TABLE dwd.flink_demo_hi PARTITION (dt='2026-10-08', hr='10')
SELECT
  orderId, userId, product,
  CAST(amount AS DECIMAL(12,2)),                       -- ① 精度：DOUBLE → DECIMAL
  city, platform,
  FROM_UNIXTIME(CAST(`timestamp`/1000 AS BIGINT))      -- ② 类型：毫秒 BIGINT → TIMESTAMP
FROM (
  SELECT *, ROW_NUMBER() OVER (                         -- ③ 重复：按 orderId 去重
           PARTITION BY orderId ORDER BY `timestamp` DESC) AS rn
  FROM ods.flink_demo_hi
  WHERE dt='2026-10-08' AND hr='10'                     -- ④ 分区裁剪：只扫目标分区
) t
WHERE rn = 1;
```

**逐条讲透**：

| # | 问题 | 为什么会有 | 加工动作 |
|---|---|---|---|
| ① | 金额精度 | DOUBLE 二进制浮点无法精确表示 0.2 类小数 | `CAST` 成 DECIMAL(12,2)（详见第八章） |
| ② | 类型/可读性 | 消息里是毫秒 epoch（BIGINT） | 除 1000 取秒 → `FROM_UNIXTIME`（**必须先 CAST 成 BIGINT**，Hive 4 只收 int/long） |
| ③ | 重复数据 | Flink at-least-once + 生产者重试 + 多条路径重复灌数据 | `ROW_NUMBER() PARTITION BY orderId` 取最新一条 |
| ④ | 扫描成本 | 大表全扫会拖垮单节点 | WHERE 分区谓词（生产可开 `hive.mapred.mode=strict` 强制） |

**为什么用 `INSERT OVERWRITE` 而不是 `INSERT INTO`**：OVERWRITE 是**分区级替换**——同一分区无论跑多少次，结果都一样（幂等，模型 5）。用 INSERT INTO 则每跑一次追加一次，重跑即产生重复。

### 5.3 验证与对账

```sql
-- ODS 原始行数 vs DWD 去重行数（差值 = 重复量，正常存在）
SELECT (SELECT COUNT(*) FROM ods.flink_demo_hi WHERE dt='2026-10-08' AND hr='10') AS ods_cnt,
       (SELECT COUNT(*) FROM dwd.flink_demo_hi WHERE dt='2026-10-08' AND hr='10') AS dwd_cnt;

-- 主键唯一性（DWD 必须为 0）
SELECT COUNT(*) FROM (
  SELECT orderId FROM dwd.flink_demo_hi WHERE dt='2026-10-08' AND hr='10'
  GROUP BY orderId HAVING COUNT(*)>1) t;
```

## 七、★ 时间与时区专题（本环境实测，存在真实偏移）

### 7.1 事实

| 组件 | 实测值 |
|---|---|
| Hive 容器时区 | **UTC**（`date` 输出 UTC，`TZ` 为空） |
| `FROM_UNIXTIME(1791368003)` | `2026-10-07 10:13:23` |
| 该 epoch 的真实北京时间 | `2026-10-07 18:13:23`（UTC+8） |

**结论：DWD 里的 `event_time` 比北京时间少 8 小时**——因为 `FROM_UNIXTIME` 按 Hive 服务端时区（UTC）渲染。

### 7.2 三处时区，各管各的

```text
生成器: System.currentTimeMillis()   → epoch 绝对值，与时区无关 ✓
Flink:  TO_TIMESTAMP_LTZ + DATE_FORMAT → 按 table.local-time-zone 渲染 → 决定 dt/hr 落到哪个分区
Hive:   FROM_UNIXTIME                  → 按 Hive 服务端时区渲染 → 决定 event_time 显示
路径A:  python datetime.fromtimestamp  → 按脚本 TZ（脚本里 export TZ=Asia/Shanghai）→ CST 分桶
```

**隐藏风险**：路径 A（脚本，CST 分桶）与路径 B（Flink，默认 UTC 渲染）**可能把同一时刻的数据分到不同的 dt/hr**——跨路径混用时会像"数据错位"。

### 7.3 修复（三选一，推荐前两个）

```sql
-- 方案 A：DWD 加工时显式转北京时间（不动任何服务配置，最省事）
FROM_UTC_TIMESTAMP(FROM_UNIXTIME(CAST(`timestamp`/1000 AS BIGINT)), 'Asia/Shanghai')

-- 方案 B：给 Hive 容器设置时区（治本，一次到位）
# docker-compose.yml 的 hive-server / hive-metastore 加：
#   environment: [ "TZ=Asia/Shanghai" ]

-- 方案 C：Flink 作业会话设置本地时区（统一 Flink 侧分桶）
SET 'table.local-time-zone' = 'Asia/Shanghai';
```

### 7.4 验证方法

```sql
-- 1) 看 Hive 当前时区与渲染结果
SELECT CURRENT_TIMESTAMP, FROM_UNIXTIME(CAST(1791368003 AS BIGINT));
-- 2) 与北京时间对照（宿主机执行）
date -d @1791368003
```

## 八、金额精度专题（DOUBLE vs DECIMAL）

### 8.1 原理

| | DOUBLE | DECIMAL(p,s) |
|---|---|---|
| 存储 | IEEE 754 二进制浮点 | 十进制定点（整数+小数位） |
| `358.2` 实际存 | `358.19999999999998863…` | `358.20`（精确） |
| 累加 995 条后 | `511058.11999999994` | `511058.12` |
| 适用 | 科学计算、允许误差的指标 | **金额、费率、对账** |

### 8.2 分层策略（本环境实测类型）

| 层 | 表 | amount 类型 | 说明 |
|---|---|---|---|
| ODS | `ods.flink_demo_hi` | `double` | ✅ **原样原则**：忠实保存消息里的原始值，便于回溯 |
| DWD | `dwd.flink_demo_hi` / `dwd.flink_demo_di` | **`decimal(12,2)`** | ✅ 精度在此收敛，聚合/对账都用这层 |

### 8.3 使用规则

```sql
-- ✓ 正确：DWD 上聚合（精确）
SELECT SUM(amount) FROM dwd.flink_demo_di WHERE dt='2026-10-08';
-- ✓ 允许：ODS 上临时看，但要显式转精度
SELECT ROUND(SUM(amount),2) FROM ods.flink_demo_di WHERE dt='2026-10-08';
-- ✗ 禁止：DOUBLE 上 SUM 后直接对账
SELECT SUM(amount) FROM ods.flink_demo_di;   -- 会出现 11999999994 尾巴
```

## 九、分区与目录对齐自查（表 ↔ 目录 ↔ 作业输出）

### 9.1 三处必须一致

```text
Flink sink 的 path + PARTITIONED BY      →  写出的目录结构
Hive 表的 LOCATION + PARTITIONED BY      →  声明的目录结构
两者必须逐一对应，否则"数据在，查不到"
```

### 9.2 现状问题（待你决策）

| 运行中的 Flink 作业输出 | ODS 表指向 | 是否对齐 |
|---|---|---|
| `/data/staging/flink-demo`（dt 单级） | `ods.flink_demo_di` LOCATION `/data/staging/flink-demo`（dt 单级） | ✅ 对齐 |
| 同上 | `ods.flink_demo_hi` LOCATION `/data/staging/flink-demo-stream`（dt+hr 双级） | ❌ **不对齐**（所以 `ods.flink_demo_hi` = 0 行） |

**二选一**：
- 方案 1（简单）：把作业 sink path 改成 `/data/staging/flink-demo-stream` 且 `PARTITIONED BY (dt, hr)`，与 `_hi` 表对齐
- 方案 2：放弃 `_hi` 表，只用 `_di`（路径 A 已是这个结构，数据也最多）
