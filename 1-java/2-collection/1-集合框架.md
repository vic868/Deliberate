## 一、集合体系与选型总览

### 1.1 两条主干

Java 集合只有两条主干，其余全是工程变体：

```text
Iterable
└── Collection
    ├── List      有序、可重复、有下标
    ├── Set       去重（语义上的"集合"）
    └── Queue     队列语义（FIFO / 优先级 / 双端）
        └── Deque 双端队列

Map（不继承 Collection！）
├── HashMap / LinkedHashMap / TreeMap / Hashtable
└── ConcurrentHashMap / ConcurrentSkipListMap
```

> [!warning] `Map` 不是 `Collection`
> 这是最常见的口误。`Map` 是独立的顶层接口，所以 `Collection` 的所有工具方法（`Collections.sort`、`removeIf`）都不作用于 `Map`；`Map` 要用 `entrySet()` 转成 `Set<Map.Entry>` 才能借道 `Collection`。

### 1.2 语义差异：一句话说清 List / Set / Queue / Map

| 维度 | List | Set | Queue/Deque | Map |
| --- | --- | --- | --- | --- |
| 元素身份 | 下标位置 | 元素本身 | 元素本身 | key 唯一 |
| 允许重复 | 是 | 否 | 是 | key 不重复，value 可重复 |
| 有序定义 | 插入序 + 下标 | 看实现（无序/插入序/排序） | FIFO 或优先级 | 看实现 |
| 典型用途 | 有序结果集、分页 | 去重、存在性判断 | 缓冲、任务队列 | 映射、缓存、索引 |
| 去重依据 | 不去重 | `hashCode`+`equals` 或比较器 | 不去重 | $key 的 `hashCode`+`equals` |

> [!important] Set 的"去重"和 TreeSet 的"去重"不是一回事
> `HashSet` 用 `hashCode` + `equals` 判断重复；`TreeSet`/`TreeMap` 用 **`compareTo`/`compare` 是否返回 0** 判断"相等"，**完全不看 equals**。所以一个"按 id 排序但 id 相同时字段不同"的 Comparator 会让 TreeSet 静默丢数据。这是生产事故级细节，见第十二节。

### 1.3 选型总表

| 实现 | 有序性 | 可重复 | null | 线程安全 | 底层结构 | 随机访问 | 增删 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `ArrayList` | 插入序 | 是 | 允许 | 否 | 动态数组 | **O(1)** | 尾部摊还 O(1)，中间 O(n) |
| `LinkedList` | 插入序 | 是 | 允许 | 否 | 双向链表 | O(n) | 定位 O(n)，定位后 O(1) |
| `Vector` | 插入序 | 是 | 允许 | 是（方法级 synchronized） | 动态数组 | O(1) | 同 ArrayList + 锁开销 |
| `CopyOnWriteArrayList` | 插入序 | 是 | 允许 | 是（写时复制） | 数组快照 | O(1) | 写 O(n) 且内存翻倍 |
| `HashMap` | 无序 | key 唯一 | 允许 1 个 null key、null value | 否 | 数组+链表+红黑树 | — | 均摊 O(1) |
| `LinkedHashMap` | 插入序/访问序 | 同上 | 同上 | 否 | HashMap + 双向链表 | — | 均摊 O(1) |
| `TreeMap` | key 排序 | 同上 | 不允许 null key（自然序） | 否 | 红黑树 | — | O(log n) |
| `Hashtable` | 无序 | 同上 | **不允许** | 是（全表锁） | 数组+链表 | — | 均摊 O(1) |
| `ConcurrentHashMap` | 无序 | 同上 | **不允许** | 是（CAS + 桶级锁） | 数组+链表+红黑树 | — | 均摊 O(1) |
| `HashSet` | 无序 | 否 | 允许 1 个 null | 否 | 内部 `HashMap` | — | O(1) |
| `LinkedHashSet` | 插入序 | 否 | 允许 1 个 null | 否 | 内部 `LinkedHashMap` | — | O(1) |
| `TreeSet` | 排序 | 否 | 不允许 null | 否 | 内部 `TreeMap` | — | O(log n) |
| `ArrayDeque` | 插入序 | 是 | **不允许** | 否 | 循环数组 | 仅两端 | 两端摊还 O(1) |
| `PriorityQueue` | 堆序（非全局有序） | 是 | **不允许** | 否 | 二叉堆（数组） | 仅堆顶 O(1) | O(log n) |

### 1.4 复杂度速记（含隐藏常数）

面试答"O(1)"是不够的，要看**常数**与**内存局部性**：

| 操作 | ArrayList | LinkedList | HashMap |
| --- | --- | --- | --- |
| 尾部追加 | 摊还 O(1)，扩容时 1 次 memcpy | O(1)，但要 new 节点 | 均摊 O(1)，可能 resize |
| 随机访问 `get(i)` | 1 次寻址 | O(n/2) 指针跳转 | — |
| 中间插入 | O(n) 的 `System.arraycopy`（约 GB/s） | O(n) 定位 + O(1) 断链 | — |
| 删除元素 | O(n) 搬移 | O(n) 定位 + O(1) | 均摊 O(1) |
| 内存/元素 | 4/8 字节引用 + 最多 50% 空槽 | 每节点一个对象（≈24–40 字节） | 每 Node ≈32 字节 + 数组空槽 |

## 二、ArrayList 与 LinkedList

### 2.1 底层结构

```java
// JDK 8 ArrayList
transient Object[] elementData;
private int size;
private static final int DEFAULT_CAPACITY = 10;
private static final Object[] DEFAULTCAPACITY_EMPTY_ELEMENTDATA = {};

public ArrayList() { this.elementData = DEFAULTCAPACITY_EMPTY_ELEMENTDATA; } // 不分配数组
public ArrayList(int initialCapacity) {
    if (initialCapacity > 0) this.elementData = new Object[initialCapacity]; // 立刻分配
    else if (initialCapacity == 0) this.elementData = EMPTY_ELEMENTDATA;
    else throw new IllegalArgumentException("Illegal Capacity: " + initialCapacity);
}
```

注意：**无参构造是惰性的**（第一次 `add` 才分配 10），但 `new ArrayList<>(n)` 会立刻分配 `n` 长度的数组 —— 传一个巨大数字会导致立刻占用内存。

```java
// JDK 8 LinkedList
private static class Node<E> {
    E item; Node<E> next; Node<E> prev;   // 双向链表
}
transient Node<E> first, last;
```

### 2.2 ArrayList 扩容机制

```java
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);   // 1.5 倍
    if (newCapacity - minCapacity < 0) newCapacity = minCapacity;
    if (newCapacity - MAX_ARRAY_SIZE > 0) newCapacity = hugeCapacity(minCapacity); // MAX_ARRAY_SIZE = Integer.MAX_VALUE - 8
    elementData = Arrays.copyOf(elementData, newCapacity);  // 分配新数组 + 全量拷贝
}
```

**为什么是 1.5 倍而不是 2 倍？** 这是时间与空间的折中：2 倍扩容次数更少、拷贝更少，但峰值内存（新旧数组同时存在）更高，且更容易产生无法复用的碎片；1.5 倍在"拷贝总量"和"浪费空间"之间更平衡（代价是 `k` 次扩容后容量是 $1.5^k$，比 2 的幂更"碎"，但这只影响数组本身，不影响索引）。**关键成本不在倍数，而在 `Arrays.copyOf` 是一次 O(n) 全量内存拷贝**。

> [!example] 扩容总量是可以算出来的
> 从容量 10 开始连续追加到 100 万元素，容量序列是 10→15→22→33…，总拷贝次数约等于 $\sum$ 每级容量 ≈ 3n。也就是说**追加 100 万元素，实际搬移了约 300 万个引用**。预知规模时用 `ensureCapacity` 一次搞定，能省掉这些搬移。

### 2.3 LinkedList 的"增删快"是有条件的

教材说"ArrayList 查快、LinkedList 增删快"，**这句话在后半段几乎总是错的**，原因是 `LinkedList.add(int, E)` 必须先定位：

```java
public void add(int index, E element) {
    checkPositionIndex(index);
    if (index == size) linkLast(element);
    else linkBefore(element, node(index));   // ← 关键：node(index) 是 O(n)
}

Node<E> node(int index) {
    if (index < (size >> 1)) {          // 从头部走
        Node<E> x = first;
        for (int i = 0; i < index; i++) x = x.next;
        return x;
    } else {                            // 从尾部走
        Node<E> x = last;
        for (int i = size - 1; i > index; i--) x = x.prev;
        return x;
    }
}
```

所以真实的复杂度是：

| 操作 | ArrayList | LinkedList |
| --- | --- | --- |
| `add(e)` 尾部 | 摊还 O(1)，数组连续写 | O(1)，但每次 `new Node` |
| `add(0, e)` 头部 | O(n) `arraycopy`（但 memmove 极快） | O(1)（定位成本为 0） |
| `add(i, e)` 中间 | O(n) 搬移，内存连续，缓存友好 | **O(n) 遍历定位**，指针追逐，缓存不友好 |
| `get(i)` | O(1) | O(n/2) |
| `remove(i)` | O(n) 搬移 | O(n) 定位 + O(1) 断链 |

**结论：只有在"已经持有节点位置"或"只在两端操作"时，链表的 O(1) 才成立。** 通过下标做中间增删，LinkedList 通常会**比 ArrayList 更慢**——因为它每跳一步都是一次可能 cache miss 的指针解引用，而 ArrayList 的 `arraycopy` 是单指令优化的连续内存移动。实测在几千到几十万元素规模下，ArrayList 的中间插入常常反超。

### 2.4 内存与 CPU 缓存

- **LinkedList 更费内存**：每个元素额外一个 `Node` 对象（对象头 12 字节 + 3 个引用，64 位压缩指针下约 24 字节，元素对象本身另算），而 ArrayList 只需要数组里一个 4/8 字节引用。
- **缓存友好性**：ArrayList 是连续内存，CPU 预取器有效，顺序遍历几乎零 cache miss；LinkedList 每次 `next` 都可能 miss（DRAM 延迟约 100ns 级，L1 约 1ns）。
- 这也是为什么很多"链表更好"的直觉在真实 JVM 上是反的——**算法的复杂度相同，常数差一个数量级**。

### 2.5 ensureCapacity 与 trimToSize

```java
// 已知要放 100 万条：一次性预分配，避免 ~20 次扩容搬移
List<Order> orders = new ArrayList<>(1_000_000);
// 或者：list.ensureCapacity(1_000_000);

// 大批量删除后，回收多余数组空间（否则数组一直占着峰值容量）
list.subList(0, list.size() - 10).clear();
((ArrayList<Order>) list).trimToSize();
```

> [!tip] 两个方法的使用时机
> `ensureCapacity(n)`：**批量写入之前**调用，把 20 次扩容变成 1 次分配，是"数据同步/批量查询结果装配"场景最廉价的优化之一。
> `trimToSize()`：**大批量删除之后**调用。它不是"内存泄漏修复"，而是主动把容量降到 `size`，避免一个"曾经装过 100 万条、现在只剩 10 条"的列表长期占着几十 MB。

> [!danger] ArrayList 并发 add 的真实后果
> `elementData[size++] = e` 不是原子操作。多线程并发 `add` 会：①两个线程读到同一个 `size`，其中一个的写入被覆盖（**丢数据**）；②`size` 自增了两次但只有一个元素写入，导致后续 `get` 读到 `null`；③A 线程扩容还没完成、B 线程已经拿着旧数组写 → `ArrayIndexOutOfBoundsException`。**ArrayList 没有任何并发保护，且失败方式是静默的。** 需要并发 List 时用 `CopyOnWriteArrayList`（读多写极少）或外层加锁。

### 2.6 实践结论

> [!important] 一句话结论
> **默认永远选 `ArrayList`**；只有在"高频在两端插入删除"时选 `ArrayDeque`，几乎不存在应该选 `LinkedList` 的场景。JDK 官方文档也直接写明：`ArrayDeque` 作为栈和队列比 `LinkedList` 更快。`LinkedList` 在现代 Java 里的主要价值是"实现 `Deque` 接口且允许 null 元素"。

## 三、HashMap 的底层结构

### 3.1 数组 + 链表 + 红黑树

```java
// JDK 8 HashMap 关键字段
transient Node<K,V>[] table;              // 桶数组，长度永远是 2 的幂
transient int size;                       // 键值对数量
int threshold;                            // 扩容阈值 = capacity * loadFactor
final float loadFactor;                   // 默认 0.75
static final int TREEIFY_THRESHOLD = 8;   // 链表 → 红黑树
static final int UNTREEIFY_THRESHOLD = 6; // 红黑树 → 链表
static final int MIN_TREEIFY_CAPACITY = 64;

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;      // 缓存 hash，避免每次比较都重算
    final K key;
    V value;
    Node<K,V> next;
}
```

查找的三级退化路径：**数组下标 → 链表 → 红黑树**。这样设计的原因是：绝大多数 key 的 hash 分布均匀，桶长度 0/1/2，数组就够；只有极端碰撞（或恶意构造的 key）才需要红黑树兜底，把最坏 O(n) 拉回 O(log n)。

### 3.2 为什么树化阈值是 8（泊松分布）

JDK 8 源码注释直接给出了推导：**理想情况下（hash 完全随机），每个桶内节点数服从参数 λ≈0.5 的泊松分布**（0.5 = 默认负载因子 0.75 下的平均桶长），$P(k)=\frac{e^{-0.5}0.5^k}{k!}$：

| 桶内节点数 k | 概率 |
| --- | --- |
| 0 | 0.60653066 |
| 1 | 0.30326533 |
| 2 | 0.07581633 |
| 3 | 0.01263606 |
| 4 | 0.00157952 |
| 5 | 0.00015795 |
| 6 | 0.00001316 |
| 7 | 0.00000094 |
| **8** | **0.00000006**（不到千万分之一） |

也就是说：**链表长度到 8 的概率本身就小于千万分之一**。既然这么罕见，说明一旦发生就大概率是"hash 被恶意构造"或"hashCode 实现极差"，此时必须把 O(n) 的链表换成 O(log n) 的红黑树。选 8 而不是 4：4 太常见（1.5% 概率），频繁树化/退化本身有成本（TreeNode 大小约为 Node 的两倍）；选 8 则"平时几乎不会树化，一旦树化就是异常信号"。

### 3.3 为什么退化阈值是 6（留一个缓冲带）

**不是 7，是 6**，故意和 8 之间留了一个"滞后区间"（hysteresis）。原因是如果树化阈值和退化阈值都是 8（或 7），那么在长度 7↔8 反复抖动时会不停地 `treeifyBin` / `untreeify`，而这两个操作都是 O(n) 的结构重建。留出 6↔8 的空档，就避免了边界抖动带来的抖动开销。

### 3.4 树化的前置条件：容量 ≥ 64

```java
final void treeifyBin(Node<K,V>[] tab, int hash) {
    int n, index; Node<K,V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)
        resize();                 // ← 容量不足 64 时，先扩容而不是树化
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // ... 真正转 TreeNode
    }
}
```

**为什么？** 桶长达到 8 有两种可能：①hash 真的差 → 树化；②**只是表太小**（容量 16 时只有 4 位参与索引，高位全被丢掉，必然大量碰撞）→ 这时候扩容比树化更划算：扩容能把元素分散开，且扩容是 O(n)，树化也是 O(n) 但换来的是一棵更耗内存的树。所以"**table 长度不到 64 时，优先扩容，不树化**"。

> [!tip] 这条对调优的直接指导
> 如果监控到某个 `HashMap` 频繁树化，先看它的容量是不是只有 16/32——很可能只是初始容量没设，而不是 hashCode 有问题。

### 3.5 hash 扰动函数

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

**为什么要把高 16 位异或到低 16 位？** 因为索引只取低 log2(n) 位（`(n-1) & hash`，容量 16 时只取低 4 位）。如果直接用 `hashCode()`，那些"高位不同、低位相同"的 key（典型如 `Integer`/短字符串/自增 ID 拼接）就会全部落进同一个桶。

```text
hashCode()        = 1111 0000 1010 1010 0000 0000 0000 0101
hashCode() >>> 16 = 0000 0000 0000 0000 1111 0000 1010 1010
XOR 结果           = 1111 0000 1010 1010 1111 0000 1010 1111
                                                  ↑ 低位现在混入了高位的熵
```

代价只有一次移位和一次异或，却把"高位信息"带进了低位索引，显著减少碰撞。**注意 JDK 1.7 的扰动更重**（4 次移位 + 4 次异或，还有一个 `hashSeed` 随机种子），1.8 因为引入了红黑树兜底，就把扰动简化成一次——**用树化成本换取了 hash 计算成本**，这是 1.8 的一个明确取舍。

### 3.6 为什么容量必须是 2 的幂

因为需要 `(n - 1) & hash` 等价于 `hash % n`：

- **只有当 n 是 2 的幂时**，`n-1` 的二进制才是低位全 1 的掩码（如 15 = `0000 1111`），此时 `&` 的结果恰好落在 `[0, n-1]`，与取模等价。
- `&` 是 1 个 CPU 周期，`%` 是几十个周期（除法指令）；对每次 `get/put` 都要做的操作，这个差距是实打实的。
- 更重要的一点：**对于负数的 hashCode，`&` 天然给出非负下标**（只保留低位），而 `h % n` 在 Java 里可能为负，还得 `Math.floorMod`。这就是 HashMap 从不需要 `Math.abs(hash)` 的原因。
- 附带好处：容量是 2 的幂时，扩容只需把 `n-1` 的掩码多取一位，元素要么留在原位置、要么移动到 `原位置 + oldCap`（见 4.3）。

**代价**：容量只能是 2 的幂，`new HashMap<>(17)` 实际会得到 32，空间利用率略低；这是它换取的索引速度。

### 3.7 tableSizeFor：向上取 2 的幂

```java
static final int tableSizeFor(int cap) {
    int n = cap - 1;          // 先减 1，保证 cap 本身是 2 的幂时不会翻倍
    n |= n >>> 1;
    n |= n >>> 2;
    n |= n >>> 4;
    n |= n >>> 8;
    n |= n >>> 16;            // 右移累加，把最高位 1 后面全部填成 1
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

原理：`n |= n >>> 1` 把最高位 1 复制到它的下一位，`>>> 2` 复制 2 位，`>>> 4` 复制 4 位……像"传播"一样，5 次之后最高位 1 之后的 32 位全变 1，最后 `+1` 进位成 2 的幂。

| 输入 cap | cap-1 | 填满后 | 返回 |
| --- | --- | --- | --- |
| 0 | -1 | -1（负数） | 1 |
| 1 | 0 | 0 | 1 |
| 17 | 16 = `10000` | `11111` = 31 | 32 |
| 64 | 63 = `111111` | 63 | 64 |
| 1000 | 999 | 1023 | 1024 |

> [!note] 现代 JDK 的写法
> JDK 11 起 `tableSizeFor` 改成了 `-1 >>> Integer.numberOfLeadingZeros(cap - 1)` 再加边界处理，语义完全一致，只是借助了硬件指令（LZCNT/CLZ）更快。面试讲清楚"向上取 2 的幂"这个语义就够了。

### 3.8 为什么负载因子是 0.75

源码注释原话是"在时间和空间成本之间提供了良好的折中"。具体权衡：

| loadFactor | 效果 |
| --- | --- |
| 0.5 | 桶更空、碰撞更少、查询更快，但数组一半是空的，内存浪费大、扩容更频繁 |
| **0.75** | 桶平均 0.75 个元素，碰撞概率与空间占用的平衡点 |
| 1.0 | 空间最省，但桶普遍偏长，链表/树查找变慢，扩容前的性能断崖明显 |
| > 1 | 基本退化成链表，失去 hash 表意义 |

> [!warning] 0.75 还有一个隐藏作用：它和泊松分布的 λ 直接挂钩
> 3.2 节里的 λ=0.5 就是"负载因子 0.75、理想随机 hash"下的平均桶长。改动负载因子会同时改变树化阈值的统计学依据。

## 四、HashMap 的 put / get / resize

### 4.1 putVal 全流程（JDK 8 源码）

```java
public V put(K key, V value) {
    return putVal(hash(key), key, value, false, true);
}

final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;                       // ① 懒初始化（首次 put 才分配 16）
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);          // ② 桶为空：直接放，一次 CAS 级别写入
    else {
        Node<K,V> e; K k;
        if (p.hash == hash &&
            ((k = p.key) == key || (key != null && key.equals(k))))
            e = p;                                         // ③ 命中桶首节点（先比 hash，再比 ==，最后 equals）
        else if (p instanceof TreeNode)
            e = ((TreeNode<K,V>)p).putTreeVal(this, tab, hash, key, value);   // ④ 走红黑树
        else {
            for (int binCount = 0; ; ++binCount) {         // ⑤ 遍历链表
                if ((e = p.next) == null) {
                    p.next = newNode(hash, key, value, null);   // 尾插（1.8）★
                    if (binCount >= TREEIFY_THRESHOLD - 1)      // 插入第 8 个节点
                        treeifyBin(tab, hash);                  // ⑥ 尝试树化
                    break;
                }
                if (e.hash == hash &&
                    ((k = e.key) == key || (key != null && key.equals(k))))
                    break;                                 // 链中找到相同 key
                p = e;
            }
        }
        if (e != null) {                                   // ⑦ key 已存在 → 覆盖 value
            V oldValue = e.value;
            if (!onlyIfAbsent || oldValue == null) e.value = value;
            afterNodeAccess(e);                            // LinkedHashMap 在这里调整顺序
            return oldValue;
        }
    }
    ++modCount;
    if (++size > threshold) resize();                      // ⑧ 先加 size 再判扩容
    afterNodeInsertion(evict);                             // LinkedHashMap 在这里做 LRU 淘汰
    return null;
}
```

几个容易被追问的细节：

1. **判等顺序是 `hash` → `==` → `equals`**。`==` 指的是引用相等，命中同一对象时可以跳过 `equals` 调用，这是纯粹的快速路径优化（对 `Integer`/`String` 常量池里的 key 命中率不低）。
2. **`size` 是"先自增再比较"**：`++size > threshold`。所以默认配置下容量 16、阈值 12，第 13 个元素 put 进去之后触发扩容，**元素数达到 13 时桶数组已经变成 32**。
3. **树化发生在插入之后、且用的是 `binCount >= 7`**：`binCount` 从 0 开始，走到 7 说明当前是第 8 个节点（前 7 个 + 新插入的 1 个）。所以严格说是"链表长度达到 8 时尝试树化"，而 `treeifyBin` 内部还有容量 ≥ 64 的前置条件。
4. **`afterNodeAccess` / `afterNodeInsertion` 是模板方法钩子**：`HashMap` 里是空实现，`LinkedHashMap` 重写它们来实现访问序和 LRU 淘汰。这是继承式模板方法模式在 JDK 里的典型用法。

### 4.2 getNode

```java
final Node<K,V> getNode(int hash, Object key) {
    Node<K,V>[] tab; Node<K,V> first, e; int n; K k;
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (first = tab[(n - 1) & hash]) != null) {           // 桶为空 → 直接 null，不做任何比较
        if (first.hash == hash && ((k = first.key) == key || (key != null && key.equals(k))))
            return first;                                  // 命中首节点（约 30%+ 的命中都在这里）
        if ((e = first.next) != null) {
            if (first instanceof TreeNode)
                return ((TreeNode<K,V>)first).getTreeNode(hash, key);
            do {
                if (e.hash == hash && ((k = e.key) == key || (key != null && key.equals(k))))
                    return e;
            } while ((e = e.next) != null);
        }
    }
    return null;
}
```

面试要点：**get 的时间复杂度 = O(1) 的平均 + O(log n) 的树上界 + O(n) 的链表上界**。红黑树的存在保证了即使 hash 被恶意构造，也不会退化到 O(n) 的拒绝服务（这正是引入红黑树的直接动机之一）。

### 4.3 resize：扩容与高低位拆分

这是 1.8 相比 1.7 最漂亮的一处优化。

```java
final Node<K,V>[] resize() {
    Node<K,V>[] oldTab = table;
    int oldCap = (oldTab == null) ? 0 : oldTab.length;
    int oldThr = threshold;
    int newCap, newThr = 0;
    if (oldCap > 0) {
        if (oldCap >= MAXIMUM_CAPACITY) { threshold = Integer.MAX_VALUE; return oldTab; } // 已到上限，不再扩容
        else if ((newCap = oldCap << 1) < MAXIMUM_CAPACITY && oldCap >= DEFAULT_INITIAL_CAPACITY)
            newThr = oldThr << 1;                    // 容量与阈值都翻倍
    } else if (oldThr > 0) newCap = oldThr;          // 构造时指定过初始容量
    else { newCap = DEFAULT_INITIAL_CAPACITY; newThr = (int)(DEFAULT_LOAD_FACTOR * DEFAULT_INITIAL_CAPACITY); }
    if (newThr == 0) {
        float ft = (float)newCap * loadFactor;
        newThr = (newCap < MAXIMUM_CAPACITY && ft < (float)MAXIMUM_CAPACITY) ? (int)ft : Integer.MAX_VALUE;
    }
    threshold = newThr;
    Node<K,V>[] newTab = (Node<K,V>[])new Node[newCap];
    table = newTab;
    if (oldTab != null) {
        for (int j = 0; j < oldCap; ++j) {
            Node<K,V> e;
            if ((e = oldTab[j]) != null) {
                oldTab[j] = null;
                if (e.next == null)
                    newTab[e.hash & (newCap - 1)] = e;                       // 单节点：直接重算下标
                else if (e instanceof TreeNode)
                    ((TreeNode<K,V>)e).split(this, newTab, j, oldCap);       // 红黑树拆分
                else {                                                       // 链表：高低位拆分 ★
                    Node<K,V> loHead = null, loTail = null, hiHead = null, hiTail = null, next;
                    do {
                        next = e.next;
                        if ((e.hash & oldCap) == 0) {          // 只看 oldCap 这一位
                            if (loTail == null) loHead = e; else loTail.next = e;
                            loTail = e;
                        } else {
                            if (hiTail == null) hiHead = e; else hiTail.next = e;
                            hiTail = e;
                        }
                    } while ((e = next) != null);
                    if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
                    if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
                }
            }
        }
    }
    return newTab;
}
```

**高低位拆分为什么成立？** 设旧容量 `oldCap = 2^k`，新容量 `newCap = 2^(k+1)`：

- 旧索引 = `hash & (2^k - 1)`，只看低 k 位。
- 新索引 = `hash & (2^(k+1) - 1)`，多看一位，也就是 **第 k 位**（这一位的权值恰好就是 `oldCap`）。
- 因此：`(hash & oldCap) == 0` → 新索引等于旧索引（低位链表 `lo`，放回 `newTab[j]`）；否则新索引 = 旧索引 + `oldCap`（高位链表 `hi`，放到 `newTab[j + oldCap]`）。

结果就是**完全不需要重新计算 hash 和取模**，每个元素只做一次位与判断。附带一个安全收益：1.8 的迁移是**尾插**（`loTail.next = e`），保持了每个桶内节点的相对顺序，而 1.7 的头插会**反转链表**——这正是 1.7 死循环的直接原因（见 5.2）。

> [!example] 一个具体例子
> `oldCap = 16`，`oldCap - 1 = 15 = 01111`，`newCap = 32`，`newCap - 1 = 31 = 11111`。
> - `hash = 01010`（第 4 位为 0）→ 旧索引 10，新索引 10（落在 `lo`）。
> - `hash = 11010`（第 4 位为 1）→ 旧索引 10，新索引 26 = 10 + 16（落在 `hi`）。

### 4.4 扩容的代价与初始容量建议

**扩容的成本 = 分配一个 2 倍大的数组 + 遍历所有桶重新分配节点**，同时峰值内存是旧数组 + 新数组（2 倍容量的数组）。对 100 万条数据的 map，一次扩容就是几十 MB 的分配与全量遍历，并且**扩容发生在 put 的调用线程上，表现为一次显著的延迟尖刺（长尾）**。

> [!danger] `new HashMap<>(expectedSize)` 是错的
> 构造参数是**容量**，不是元素个数。阈值 = 容量 × 0.75，所以 `new HashMap<>(1000)` 只能无扩容地放 750 个元素，第 751 个就触发扩容到 2048。正确做法：
> ```java
> int expected = 1000;
> Map<String, Object> map = new HashMap<>((int) (expected / 0.75f) + 1); // → 容量 2048? 不，tableSizeFor(1334)=2048
> // 想精确一点：
> int cap = (int) Math.ceil(expected / 0.75);
> ```
> Guava 的 `Maps.newHashMapWithExpectedSize(n)` 就是干这个的，并且对 n<3 做了特判。
>
> **还有个更隐蔽的坑**：`new HashMap<>(0)` 时 `tableSizeFor(0)` 返回 1，阈值算出来是 `(int)(1*0.75) = 0`，于是第 1 次 put 就要扩容到 2、第 2 次扩容到 4——**放两个元素扩容两次**。小 map 别用 0/1 做初始容量。

## 五、1.7 与 1.8 的关键差异

### 5.1 对比表

| 维度 | JDK 1.7 | JDK 1.8 |
| --- | --- | --- |
| 节点类型 | `Entry<K,V>`（含 `next`） | `Node<K,V>` / `TreeNode<K,V>` |
| 数据结构 | 数组 + 链表 | 数组 + 链表 + **红黑树** |
| 插入方式 | **头插法** | **尾插法** |
| 扰动函数 | 4 次移位 + 4 次异或（`hash()` + `hashSeed`） | 1 次移位 + 1 次异或 |
| 扩容迁移 | 对每个节点**重新计算索引** `indexFor` | **高低位拆分**，不重算 hash |
| 扩容后链表顺序 | 反转 | 保持相对顺序 |
| 并发扩容风险 | **可能形成环形链表 → CPU 100%** | 仍不安全（丢数据、size 不准），但不再死循环 |
| 索引函数 | `indexFor(h, length)` = `h & (length-1)` | 内联 `(n-1) & hash` |

### 5.2 1.7 头插法死循环：完整成因

JDK 1.7 的迁移代码（`transfer`）是头插：

```java
// JDK 1.7 HashMap.transfer —— 头插法
void transfer(Entry[] newTable, boolean rehash) {
    int newCapacity = newTable.length;
    for (Entry<K,V> e : table) {
        while (null != e) {
            Entry<K,V> next = e.next;              // ← ① 先记下 next，然后可能被挂起
            if (rehash) e.hash = (null == e.key) ? 0 : hash(e.key);
            int i = indexFor(e.hash, newCapacity);
            e.next = newTable[i];                  // ← ② 头插
            newTable[i] = e;
            e = next;
        }
    }
}
```

假设原桶 `table[i]` 中是 `A → B → null`，两个线程同时 put 触发扩容到新表 `newTable[i]`（扩容后 A、B 仍在同一个新桶里）：

| 步骤 | 线程 1 | 线程 2 | 新表状态 |
| --- | --- | --- | --- |
| 1 | 执行 `e=A`，`next=B`，**在此被挂起** | — | 空 |
| 2 | 挂起 | 完整跑完迁移：`newTable[i]=B`，`B.next=A`，`A.next=null` | `B → A → null` |
| 3 | **恢复**：`A.next = newTable[i]` = **B**；`newTable[i] = A`；`e = next = B` | 结束 | `A → B → A`（**成环**） |
| 4 | `e = B`，`next = B.next = A`；`B.next = newTable[i] = A`；`newTable[i] = B`；`e = A` | — | 环仍在 `A → B → A` |
| 5 | `e = A`，`next = A.next = B`；`A.next = newTable[i] = B`；… **永远循环** | — | 迁移线程自身卡死 |

**结果**：新桶里出现 `A.next = B` 且 `B.next = A` 的环。之后任何 `get` 一个落在该桶、又不在环上的 key，`getNode` 的 `do/while` 永远走不到 `null` → **该线程死循环，CPU 打满 100%**，而且从 jstack 上看线程就卡在 `HashMap.getEntry`，是那种"看起来没死锁、但 CPU 一直高"的经典事故。

> [!danger] 这个 bug 的复盘要点
> 1. 根本原因是**并发扩容**，不是"用了 HashMap"本身——单线程绝不会成环。
> 2. 触发条件其实不难凑齐：多个线程共享一个 HashMap，且**同时发生 put 且恰好触发扩容**。压力测试和线上"偶发 CPU 100%"都可能撞上。
> 3. 1.8 改成尾插 + 高低位拆分后，**成环问题消失了，但线程不安全依然成立**（丢数据、`size` 不准、可能读到 `null`）。所以"升级到 1.8 就安全了"是错误结论。
> 4. 正确修法是换 `ConcurrentHashMap`，而不是"给 HashMap 加个 synchronized 包一层"就完事（见 6.2）。

## 六、HashMap 的线程不安全

### 6.1 三种典型表现

| 表现 | 成因 |
| --- | --- |
| **丢数据** | 两个线程同时 put 到同一个空桶，后写的覆盖先写的（`tab[i] = newNode(...)` 不是 CAS） |
| **size 不准** | `++size` 是"读-改-写"，非原子；`++modCount` 同样 |
| **读到 null / 死循环（1.7）** | 链表中途结构被另一个线程改动；1.7 的并发扩容成环 |
| **扩容期读到旧表/新表不一致** | `table` 引用切换与 `threshold` 更新没有 happens-before 保证，其他线程可能看到中间态 |

### 6.2 Hashtable / synchronizedMap / ConcurrentHashMap 怎么选

| 方案 | 锁粒度 | 允许 null | 并发性能 | 结论 |
| --- | --- | --- | --- | --- |
| `Hashtable` | **整张表**（每个方法 `synchronized`） | 否（NPE） | 最差，读写互斥 | **已过时，永远不要用** |
| `Collections.synchronizedMap` | 整张表（一个 mutex 对象） | 是 | 差，且**迭代必须手动 `synchronized`**，否则照样 CME | 只在"低并发 + 需要 null 值"时勉强可用 |
| `ConcurrentHashMap` | 1.8：CAS + 单个桶的锁 | 否 | 好，读几乎无锁 | **并发场景默认选择** |

> [!warning] synchronizedMap 的两个陷阱
> ①**复合操作不是原子的**：`if (!map.containsKey(k)) map.put(k, v);` 在 synchronizedMap 上依然会竞态，必须 `synchronized (map) { ... }` 或改用 `putIfAbsent`（`Map` 接口的默认方法在 synchronizedMap 上是有同步的）。
> ②**遍历必须自己加锁**，否则别的线程 put 会导致 `ConcurrentModificationException`：
> ```java
> Map<String, String> m = Collections.synchronizedMap(new HashMap<>());
> synchronized (m) {                     // ← 少了这行就是个定时炸弹
>     for (Map.Entry<String, String> e : m.entrySet()) { ... }
> }
> ```

## 七、hashCode / equals 契约

### 7.1 契约内容

`Object` 的 Javadoc 规定：

1. **自反**：`x.equals(x)` 恒为 true。
2. **对称**：`x.equals(y)` 与 `y.equals(x)` 一致。
3. **传递**：`x.equals(y) && y.equals(z)` ⇒ `x.equals(z)`。
4. **一致**：只要参与比较的状态没变，多次调用结果不变。
5. **`equals` 相等 ⇒ `hashCode` 必须相等**；`hashCode` 相等不要求 `equals` 相等（哈希碰撞是允许的）。

**为什么第 5 条对 HashMap 是致命的？** `HashMap` 用 `hashCode` 定位桶、用 `equals` 在桶内匹配。如果两个"业务上相等"的对象 `hashCode` 不同，它们会落进不同的桶，`get` 永远找不到 —— 表现为"**put 进去了，get 返回 null**"。

### 7.2 常见错误实现

```java
// ❌ 错误 1：只重写 equals，不重写 hashCode
class UserId {
    final String id;
    UserId(String id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof UserId && ((UserId) o).id.equals(id);
    }
    // 没有 hashCode() → 两个"相等"的对象用默认 identityHashCode，落进不同桶
}

// ❌ 错误 2：hashCode 用了可变字段
class Order {
    String status;                    // 参与 hashCode
    @Override public int hashCode() { return Objects.hash(status); }
    @Override public boolean equals(Object o) { /* 也比 status */ }
}
Map<Order, String> map = new HashMap<>();
Order o = new Order(); o.status = "NEW";
map.put(o, "x");
o.status = "PAID";                    // 改完之后 hash 变了
map.get(o);                           // → null！元素永远"丢"在旧桶里，还泄漏内存

// ✅ 正确写法（IDE/Lombok 生成的就是这个）
@Override public int hashCode() { return Objects.hash(id); }
@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    return Objects.equals(id, ((UserId) o).id);
}
```

> [!danger] 可变对象做 key 的后果比"找不到"更严重
> ① `get` 返回 null → 业务逻辑按"不存在"处理，可能重复写入；② `remove` 也删不掉 → **该 Entry 永远留在桶里，成为内存泄漏**；③ 如果它还是 `LinkedHashMap` 的 LRU key，顺序链表也一起错乱。
> **规则：作为 Map key 的对象必须是不可变的（`String`、`Integer`、枚举、record 或 final 字段组成的值对象）。** JDK 16+ 的 `record` 自动生成符合契约的 `equals`/`hashCode`，是做 key 的推荐形态。

> [!tip] `Objects.hash` 的一个性能细节
> `Objects.hash(a, b, c)` 内部是 `Arrays.hashCode(new Object[]{a,b,c})` —— **每次调用都会分配一个数组**，在高频场景（比如把它当 HashMap key 每秒调几百万次）会有可观的 GC 压力。热点路径上推荐手写：
> ```java
> @Override public int hashCode() {
>     int result = id.hashCode();
>     result = 31 * result + type.hashCode();   // 31 是奇素数，编译器可优化成移位减法
>     return result;
> }
> ```

## 八、遍历与 ConcurrentModificationException

### 8.1 entrySet 还是 keySet？

```java
// ❌ 慢：keySet 遍历拿到 key 后，还要再用 key 查一次表（重新算 hash + 定位 + 比较）
for (String key : map.keySet()) {
    Object v = map.get(key);        // 第二次查找，约 2 倍开销
}

// ✅ 快：entrySet 直接拿 Node，一次定位
for (Map.Entry<String, Object> e : map.entrySet()) {
    String k = e.getKey();
    Object v = e.getValue();        // 零额外查找
}

// ✅ JDK 8 推荐：forEach（本质也是遍历 table，但代码更短）
map.forEach((k, v) -> { ... });
```

`keySet()` 的成本差距在"map 很大 + value 是热点"的场景下非常可观，**这是最常见的低成本性能优化之一**。注意：`values()` 遍历同样是一次定位，不存在二次查找，也不慢。

### 8.2 为什么遍历时修改会抛 CME

`HashMap` 和 `ArrayList` 都在结构变更时递增 `modCount`，迭代器在创建时记录 `expectedModCount`，每次 `next()` 前校验：

```java
// HashMap.HashIterator
abstract class HashIterator {
    Node<K,V> next; Node<K,V> current;
    int expectedModCount;
    HashIterator() { expectedModCount = modCount; ... }

    final Node<K,V> nextNode() {
        Node<K,V>[] t; Node<K,V> e = next;
        if (modCount != expectedModCount)          // ★ 校验点
            throw new ConcurrentModificationException();
        if (e == null) throw new NoSuchElementException();
        ...
    }
}
```

```java
// ArrayList.Itr（AbstractList 体系同样思路）
public E next() {
    checkForComodification();     // if (modCount != expectedModCount) throw new ConcurrentModificationException();
    ...
}
```

所以 CME 的本质是**"迭代器检测到结构被改过，为了避免返回不确定的结果，主动失败"**，它叫 **fail-fast（快速失败）**，而不是"检测到了并发"——**单线程里在 for-each 中 `list.remove(x)` 一样会抛**。

> [!important] fail-fast 不是线程安全的保证
> `modCount` **不是 volatile**，不同线程之间的修改不保证立即可见。所以：
> - 单线程违反规则 → 几乎必然抛 CME（确定性）。
> - 多线程 → **可能抛、也可能不抛，甚至可能遍历出错误结果而不报错**。
> 因此绝不能用"没抛 CME"来推断并发下没问题。**fail-fast 是 bug 检测机制，不是并发控制机制。**

### 8.3 正确的删除姿势

```java
// ❌ 单线程下也必抛 CME（除非恰好删的是倒数第二个元素，所以更危险：有时"看起来能跑"）
for (String k : map.keySet()) {
    if (k.startsWith("tmp")) map.remove(k);
}

// ✅ 方式一：显式 Iterator + iterator.remove()
Iterator<Map.Entry<String, Object>> it = map.entrySet().iterator();
while (it.hasNext()) {
    Map.Entry<String, Object> e = it.next();
    if (e.getKey().startsWith("tmp")) it.remove();   // 同步 expectedModCount = modCount
}

// ✅ 方式二（推荐）：JDK 8+ 的 removeIf
map.entrySet().removeIf(e -> e.getKey().startsWith("tmp"));
list.removeIf(item -> item.isExpired());
map.values().removeIf(Objects::isNull);

// ✅ 方式三：用 ConcurrentHashMap 的弱一致性迭代器（不抛 CME，但不保证看到最新状态）
ConcurrentHashMap<String, Object> chm = new ConcurrentHashMap<>();
chm.forEach((k, v) -> { if (k.startsWith("tmp")) chm.remove(k); });   // 不会抛，但语义是弱一致的
```

`Iterator.remove()` 之所以安全，是因为它删完之后会重新同步：`expectedModCount = modCount;`。**注意 `Arrays.asList(...)`、`List.of(...)`、`Collections.unmodifiableList(...)` 的迭代器 `remove()` 会抛 `UnsupportedOperationException`**，因为底层集合本身不支持删除。

## 九、ConcurrentHashMap 要点

细节放到 [[6-JUC并发工具]]，这里只讲"和 HashMap 对比时必须答对"的部分。

### 9.1 1.7：分段锁 Segment

```java
// JDK 1.7：默认 16 个 Segment，每个 Segment 继承 ReentrantLock，内部是一个 HashEntry[]
final Segment<K,V>[] segments;
static final class Segment<K,V> extends ReentrantLock implements Serializable {
    transient volatile HashEntry<K,V>[] table;
    transient volatile int count;
}
```

定位分两步：`segmentFor(hash)` 用 hash 的**高若干位**选段，段内再用低位定位桶。默认并发度 16，理论上最多 16 个线程同时写。**局限**：并发度在构造时就固定了（`concurrencyLevel`），段内仍然是链表（没有红黑树），且 `size()` 的实现需要在段上反复 tryLock 统计（最多重试 2 次，失败则全段加锁）。

### 9.2 1.8：CAS + synchronized 锁单个桶

```java
transient volatile Node<K,V>[] table;
private transient volatile long baseCount;
private transient volatile CounterCell[] counterCells;

final V putVal(K key, V value, boolean onlyIfAbsent) {
    if (key == null || value == null) throw new NullPointerException();   // ★ 不允许 null
    ...
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();                       // CAS 设置 sizeCtl，只初始化一次
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break;                               // ★ 空桶：无锁 CAS 写入
        }
        else if ((fh = f.hash) == MOVED)             // 正在扩容（ForwardingNode）
            tab = helpTransfer(tab, f);              // ★ 协助迁移，多线程并发扩容
        else {
            synchronized (f) {                       // ★ 只锁这一个桶的头节点
                ...
            }
        }
    }
    addCount(1L, binCount);
    return null;
}
```

关键区别：

| 维度 | 1.7 | 1.8 |
| --- | --- | --- |
| 锁粒度 | Segment（默认 16 段） | **单个桶的头节点**（锁数量 = 桶数量） |
| 空桶写入 | 需加段锁 | **CAS 无锁** |
| 扩容 | 单线程、持段锁 | **多线程协助迁移**（`helpTransfer` + `ForwardingNode`） |
| 链表 → 树 | 不支持 | 支持（`TreeBin`，同样阈值 8） |
| 读操作 | `get` 不加锁（`HashEntry.value` 是 volatile） | `get` 不加锁（`Node.val`/`next` 是 volatile） |

### 9.3 size() 为什么不再是"精确的一次读取"

高并发下维护一个精确的 `size` 需要全局同步，代价太大。1.8 的做法是**分散计数 + 汇总**：

```java
public int size() {
    long n = sumCount();                       // baseCount + 所有 CounterCell 求和
    return ((n < 0L) ? 0 : (n > (long)Integer.MAX_VALUE) ? Integer.MAX_VALUE : (int)n);
}
public long mappingCount() { long n = sumCount(); return (n < 0L) ? 0L : n; }   // ★ 推荐：不会被 int 截断
```

`addCount` 先尝试 CAS `baseCount`，竞争失败就通过 `CounterCell[]`（思想来自 `LongAdder` 的分散热点）把增量散到不同 cell 上。**因此 `size()` 返回的是"某个瞬间的近似值"**，`sumCount()` 过程中还有并发写入也无法保证一致。**需要精确计数时必须自己维护 `LongAdder` 或用 `mappingCount()` 至少避免溢出。**

### 9.4 为什么 ConcurrentHashMap 不允许 null key/value

这**不是"技术上做不到"，而是刻意的设计决策**：并发场景下 `get(key)` 返回 `null` 具有二义性——到底是"这个 key 不存在"还是"这个 key 存在但值是 null"？

单线程的 `HashMap` 可以用 `containsKey` 补一刀来区分，但**在并发下 `containsKey` + `get` 不是原子的**：两次调用之间状态可能已经变了，任何依赖这两步结果的判断都是错的。既然无法提供可靠的语义，索性禁止 null，逼调用方显式表达"缺失"（用 `Optional`、哨兵对象或 `containsKey` + 加锁）。

> [!note] 顺带一句
> `Hashtable` 也不允许 null，但它是历史包袱；`ConcurrentHashMap` 的禁止是**明确的设计取舍**，面试时把"二义性 + 无法原子地组合两次调用"说出来，比"CHM 不允许 null"这个结论值钱得多。

### 9.5 复合操作必须用原子 API

**`ConcurrentHashMap` 只保证单个操作原子，不保证"检查-然后-动作"的组合原子**：

```java
// ❌ 竞态：两个线程可能都通过 containsKey 检查，然后都 put，后者覆盖前者
if (!chm.containsKey(k)) chm.put(k, createExpensiveValue());

// ✅ 方式一：putIfAbsent（注意 createExpensiveValue() 每次都会被求值！）
chm.putIfAbsent(k, createExpensiveValue());

// ✅ 方式二：computeIfAbsent —— 只在其正缺失时调用 mappingFunction
chm.computeIfAbsent(k, key -> createExpensiveValue());

// ✅ 其他原子复合操作
chm.compute(k, (key, old) -> old == null ? 1 : old + 1);   // 原子自增
chm.merge(k, 1, Integer::sum);                             // 原子累加（最简洁）
chm.replace(k, oldV, newV);                                // CAS 语义
chm.computeIfPresent(k, (key, old) -> old + 1);
```

> [!danger] computeIfAbsent 的两个坑
> ① **mappingFunction 里不要做耗时操作**（远程调用、大查询）。1.8 的实现会对该桶加锁，耗时函数会**长时间阻塞同一个桶上的其他线程**。
> ② **不要在 mappingFunction 里再修改同一个 map**（递归/重入）。这会造成未定义行为或死锁。
> 另外 JDK 8 的 `HashMap.computeIfAbsent` 在映射函数内部修改 map 时会抛 `ConcurrentModificationException`（后续版本已修复），所以**本地 `HashMap` 里用 computeIfAbsent 更要保证映射函数是纯函数**。
> ③ `putIfAbsent` 的参数**总会被求值**，所以"贵"的值一定要放进 `computeIfAbsent` 的 lambda 里。

### 9.6 选型结论

| 场景 | 选择 |
| --- | --- |
| 单线程 / 方法栈内局部变量 | `HashMap`（最轻，无同步开销） |
| 多线程只读、初始化后不再改 | `HashMap` + 安全发布（`final`/`static final`、不可变），或 `Map.copyOf` |
| 多线程读写 | **`ConcurrentHashMap`** |
| 多线程 + 需要 null value | `ConcurrentHashMap` 里存 `Optional`/哨兵对象，而不是回去用 `Hashtable` |
| 多线程 + 有序 | `ConcurrentSkipListMap`（跳表，无锁读；注意 `TreeMap` **没有**并发版本） |
| 需要 LRU 且并发 | `ConcurrentHashMap` + 自己维护链表，或直接用 **Caffeine** |

## 十、LinkedHashMap 与 LRU

### 10.1 结构：HashMap + 双向链表

```java
public class LinkedHashMap<K,V> extends HashMap<K,V> implements Map<K,V> {
    static class Entry<K,V> extends HashMap.Node<K,V> {
        Entry<K,V> before, after;      // ★ 在所有 Entry 之间串一条双向链表
    }
    transient LinkedHashMap.Entry<K,V> head, tail;
    final boolean accessOrder;         // false=插入序（默认），true=访问序
}
```

它**继承 `HashMap`**，所以底层桶数组、hash 扰动、扩容逻辑完全复用，只在节点上加两个指针并用 `head/tail` 维护全序。两个钩子方法是关键：

- `afterNodeAccess(e)`：`accessOrder=true` 时，把刚访问的节点**移到链表尾部**（标记为最近使用）。
- `afterNodeInsertion(evict)`：插入后调用 `removeEldestEntry(head)`，返回 true 就删掉链表头（最久未使用的）。

### 10.2 accessOrder 的差异

| 构造 | 迭代顺序 | `get` 的副作用 |
| --- | --- | --- |
| `new LinkedHashMap<>()` | 插入顺序 | 无（`afterNodeAccess` 直接返回） |
| `new LinkedHashMap<>(16, .75f, true)` | **访问顺序**：每次 `get`/`put` 命中的 key 移到尾部 | **`get` 会修改链表结构**，即读操作带写副作用 |

> [!warning] accessOrder=true 的 `get` 不是纯读
> 意味着：① 并发 `get` 也会产生数据竞争；② 迭代顺序会随读取行为变化，不能用来做"稳定输出"；③ 在"多线程只读"的假设下用它缓存是错的。

### 10.3 用 LinkedHashMap 实现 LRU（完整代码）

```java
import java.util.LinkedHashMap;
import java.util.Map;

/**
 * 线程不安全的 LRU 缓存：容量满时淘汰最久未使用的条目。
 * 注意：LinkedHashMap 的迭代/淘汰都是在调用线程上同步执行的。
 */
public class LruCache<K, V> extends LinkedHashMap<K, V> {

    private final int capacity;

    public LruCache(int capacity) {
        super(capacity, 0.75f, true);   // ★ accessOrder = true 是 LRU 的关键
        this.capacity = capacity;
    }

    /** 返回 true 表示"请删除链表头部（最久未使用）的那个节点" */
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;       // 只在 put 之后被调用
    }

    public static void main(String[] args) {
        LruCache<Integer, String> cache = new LruCache<>(3);
        cache.put(1, "a");
        cache.put(2, "b");
        cache.put(3, "c");
        System.out.println(cache.keySet());   // [1, 2, 3]
        cache.get(1);                         // 访问 1 → 1 变成"最近使用"，链表变成 [2, 3, 1]
        System.out.println(cache.keySet());   // [2, 3, 1]
        cache.put(4, "d");                    // 超容，淘汰链表头 2
        System.out.println(cache.keySet());   // [3, 1, 4]
    }
}
```

关键点：

1. **`removeEldestEntry` 只在 `put` 之后触发**（`afterNodeInsertion` 由 `putVal` 调用）。所以"淘汰"永远不会发生在 `get` 上，只是 `get` 会改变谁被淘汰。
2. **它创建时不会触发淘汰**，一次 put 最多淘汰一个（`size` 每次只 +1）。
3. **需要让子类可见的修饰符**：`removeEldestEntry` 是 `protected`，`super(capacity, 0.75f, true)` 里的 `accessOrder` 必须显式传 true，**漏了就退化成 FIFO**（这是最常见的实现 bug）。

> [!danger] 生产环境别直接用这个 LRU
> ① **线程不安全**：`get` 会改链表（accessOrder=true），并发下会破坏链表结构，甚至形成环让迭代死循环。用 `Collections.synchronizedMap` 包也不行——**遍历仍要手动同步，且 `get` 变成串行化，吞吐塌方**。
> ② **没有过期时间**（TTL），只有容量淘汰。
> ③ **没有统计**（命中率、淘汰数），线上无法调参。
> 生产实践：**Caffeine**（W-TinyLFU 淘汰算法，命中率显著优于 LRU，支持 TTL/TTI、异步加载、`recordStats()`）或 Guava Cache。手写 LRU 的价值在于**面试能讲清原理**，不在于上线。

### 10.4 一个被忽略的好处：迭代效率

`HashMap` 的迭代成本是 **O(容量)**——要遍历整个 `table` 数组，即使里面只有 3 个元素（如果你一开始 `new HashMap<>(1_000_000)` 只放了 3 个，遍历要扫 100 万个槽）。

`LinkedHashMap` 的迭代成本是 **O(size)**——直接沿 `head → after` 链表走。

> [!tip] 直接指导
> "元素少但容量预估过大"或者"需要频繁按序遍历"的场景，`LinkedHashMap` 的迭代性能可能比 `HashMap` 高好几个数量级。反过来，这也解释了为什么 `LinkedHashMap` 会多出两个指针的内存开销——**这是用空间换迭代顺序的确定性和效率**。

### 10.5 与 HashMap 的关系速查

| 维度 | HashMap | LinkedHashMap |
| --- | --- | --- |
| 继承关系 | — | `extends HashMap` |
| 节点 | `Node` | `Entry extends HashMap.Node`（多 before/after） |
| 迭代顺序 | 不可预测（随容量和 hash 变） | 插入序或访问序（确定） |
| 迭代成本 | O(容量) | O(size) |
| 内存 | 每节点 ≈32B | 每节点 ≈40B |
| 单次 get/put | 略快 | 略慢（要维护链表指针） |

## 十一、TreeMap

```java
public class TreeMap<K,V> extends AbstractMap<K,V>
        implements NavigableMap<K,V>, Cloneable, Serializable {
    private final Comparator<? super K> comparator;
    private transient Entry<K,V> root;
    // Entry: key, value, left, right, parent, color（红黑树节点）
}
```

- **底层是红黑树**（自平衡二叉搜索树），保证 `get/put/remove` 都是 **O(log n)**，最坏情况也不退化。
- **排序依据**：构造时传了 `Comparator` 就用它；否则要求 key 实现 `Comparable`，否则 `put` 时抛 `ClassCastException`（**注意是 put 时抛，不是 new 时抛**，因为 `TreeMap` 构造时不校验元素类型）。
- **不允许 null key**（自然排序下 `compareTo(null)` 直接 NPE；即使传了 Comparator，也要看 Comparator 能不能处理 null）。
- **去重依据是"比较结果为 0"**，与 `equals` 无关 —— 见 12.3 的坑。

### 11.1 NavigableMap 的独有能力

这是 `TreeMap` 相比 `HashMap` 唯一"无法替代"的地方：

```java
TreeMap<Integer, String> m = new TreeMap<>();
m.put(10, "a"); m.put(20, "b"); m.put(30, "c"); m.put(40, "d");

m.floorKey(25);        // 20  ≤25 的最大 key
m.ceilingKey(25);      // 30  ≥25 的最小 key
m.lowerKey(20);        // 10  <20  的最大 key
m.higherKey(20);       // 30  >20  的最小 key
m.firstKey();          // 10
m.lastKey();           // 40
m.firstEntry();        // 10=a
m.pollFirstEntry();    // 取出并删除最小项（可在循环里当优先队列用）
m.headMap(30);         // [10, 20)   左闭右开
m.tailMap(20);         // [20, 30, 40]
m.subMap(15, true, 35, true);   // [20, 30]  可指定开闭
m.descendingMap();     // 逆序视图
m.descendingKeySet();
m.navigableKeySet();
```

> [!example] 真实业务场景
> ① **区间定价/阶梯计费**：`priceMap.floorEntry(quantity).getValue()` 一行搞定，比一堆 if-else 清晰。
> ② **IP 段/时间窗口路由**：`subMap(from, to)` 取区间内所有规则。
> ③ **排行榜**：`descendingMap()` + `firstEntry()`。但高并发下应该用 `ConcurrentSkipListMap`，因为 `TreeMap` 没有并发版本。

### 11.2 TreeMap vs HashMap 怎么选

| 需求 | 选择 |
| --- | --- |
| 纯查找/写入，无顺序要求 | `HashMap`（O(1) 明显优于 O(log n)） |
| 需要按 key 排序遍历 | `TreeMap` |
| 需要范围查询 / 前驱后继（floor/ceiling） | `TreeMap`（**唯一选择**） |
| 并发 + 有序 | `ConcurrentSkipListMap` |
| 按插入顺序 | `LinkedHashMap` |
| 按优先级取最小/最大 | `PriorityQueue`（不需要全序，成本更低） |

> [!note] 为什么有序并发 map 是跳表不是红黑树
> 红黑树的平衡靠**旋转**，旋转要改动多个节点的父子指针和颜色，很难做到无锁。跳表（`ConcurrentSkipListMap`）的插入只在（多层）链表上做指针的 CAS，天然更适合无锁并发。**"为什么不用 ConcurrentTreeMap"的标准答案是：红黑树旋转难以无锁化。**

## 十二、Set 家族

### 12.1 三个实现，本质都是 Map 的包装

| Set | 内部持有 | 去重依据 | 顺序 | null 元素 | 复杂度 |
| --- | --- | --- | --- | --- | --- |
| `HashSet` | `HashMap`（value 是常量 `PRESENT`） | `hashCode` + `equals` | 无序 | 允许 1 个 | O(1) |
| `LinkedHashSet` | `LinkedHashMap`（插入序） | `hashCode` + `equals` | 插入序 | 允许 1 个 | O(1) |
| `TreeSet` | `TreeMap`（value 是 `PRESENT`） | **`compareTo`/`compare` == 0** | 排序 | **不允许**（NPE） | O(log n) |
| `CopyOnWriteArraySet` | `CopyOnWriteArrayList` | `equals` | 插入序 | 允许 | 读 O(n)，写 O(n) |
| `ConcurrentSkipListSet` | `ConcurrentSkipListMap` | `compareTo` | 排序 | 不允许 | O(log n) |

```java
// HashSet 的核心就是这个 dummy value
private static final Object PRESENT = new Object();
public boolean add(E e) { return map.put(e, PRESENT) == null; }   // put 返回 null 说明是新增
```

**面试点**：`HashSet.add` 返回 `boolean`（是否新增），而 `HashMap.put` 返回旧 value —— `HashSet` 正是靠 `put` 返回 `null` 来判断"这个 key 之前不存在"。

### 12.2 经典用法

```java
// 去重
Set<String> unique = new HashSet<>(list);
// 保持去重后的插入顺序（比 stream().distinct() 更明确）
Set<String> ordered = new LinkedHashSet<>(list);
// 去重后排序
Set<String> sorted = new TreeSet<>(list);
// 交并差
Set<String> a = new HashSet<>(...), b = new HashSet<>(...);
Set<String> inter = new HashSet<>(a); inter.retainAll(b);
Set<String> union = new HashSet<>(a); union.addAll(b);
Set<String> diff  = new HashSet<>(a); diff.removeAll(b);
```

### 12.3 TreeSet / TreeMap 最危险的坑

```java
class Person {
    String id; String name;                 // id 相同但 name 不同
}
Comparator<Person> byId = Comparator.comparing(p -> p.id);

TreeSet<Person> set = new TreeSet<>(byId);
set.add(new Person("1", "Alice"));
set.add(new Person("1", "Bob"));
System.out.println(set.size());            // 1！Bob 被静默丢弃
```

原因就在红黑树的插入逻辑：

```java
// TreeMap.put 的查找部分
int cmp = compare(key, t.key);
if (cmp < 0) t = t.left;
else if (cmp > 0) t = t.right;
else return t.setValue(value);             // ★ cmp == 0 就直接覆盖，完全不看 equals
```

> [!danger] 三处连带影响
> ① **丢元素**：比较器认为"相等"的对象被覆盖。
> ② **反向的坑**：如果比较器/`compareTo` 与 `equals` 不一致（`equals` 为 true 但 `compareTo` 非 0），`TreeSet` 里会出现"看起来重复"的两个元素。
> ③ **契约要求**：`Comparable` 的 Javadoc 强烈建议 `compareTo` 与 `equals` 保持一致（"strongly recommended"），否则基于 `SortedMap`/`SortedSet` 的行为会与直觉不符。**写业务代码时，比较器必须包含所有参与唯一性判断的字段。**

### 12.4 选型速查

```text
只需要去重、要最快              → HashSet
需要去重 + 保持插入顺序          → LinkedHashSet
需要去重 + 有序 / 范围查询       → TreeSet
读多写极少 + 需要并发           → CopyOnWriteArraySet
并发 + 有序                     → ConcurrentSkipListSet
```

## 十三、Queue / Deque

### 13.1 ArrayDeque vs LinkedList（队列场景）

| 维度 | `ArrayDeque` | `LinkedList` |
| --- | --- | --- |
| 底层 | **循环数组**（容量 2 的幂，默认 16） | 双向链表 |
| 两端插入/删除 | 摊还 O(1) | O(1)，但每次 new/GC 节点 |
| 随机访问 | 无（不是 List） | 有（但 O(n)） |
| null 元素 | **不允许**（`offer(null)` 抛 NPE） | 允许 |
| 缓存友好 | 好（连续数组） | 差 |
| 内存/元素 | 一个引用（约 4/8 字节） | 一个 Node 对象（约 24 字节） |
| 作为栈 | `push/pop` 比 `Stack` 快 | 也可以，但更重 |

```java
// 队列：FIFO
Deque<Task> q = new ArrayDeque<>();
q.offerLast(t1);            // 入队尾部（队尾）
Task t = q.pollFirst();     // 出队头部（队首），空时返回 null
// 或用 offer / poll（等价于 offerLast / pollFirst）

// 栈：LIFO（优于 java.util.Stack，后者继承 Vector，方法全同步）
Deque<Frame> stack = new ArrayDeque<>();
stack.push(f1);             // = addFirst
Frame f = stack.pop();      // = removeFirst，空时抛 NoSuchElementException
Frame p = stack.peek();     // 空时返回 null
```

> [!important] 为什么不用 `java.util.Stack`
> `Stack extends Vector`，所有方法都 `synchronized`（**单线程场景白付锁开销**），而且继承 `Vector` 让它能通过 `get(i)`/`insertElementAt` 被随机访问，破坏了"只能操作栈顶"的语义封装。**JDK 文档明确推荐用 `ArrayDeque` 实现栈。**

**两套 API 必须记清**（面试常问区别）：

| 操作 | 抛异常 | 返回特殊值（推荐） |
| --- | --- | --- |
| 入队 | `add(e)` → `IllegalStateException`（有界队列满） | `offer(e)` → `false` |
| 出队 | `remove()` → `NoSuchElementException` | `poll()` → `null` |
| 查看队首 | `element()` → `NoSuchElementException` | `peek()` → `null` |

> [!warning] `poll()` 返回 null 的二义性
> 队列里**允许存 null**（`LinkedList` 允许）时，`poll() == null` 无法区分"队列空"和"队首就是 null"。这是 `ArrayDeque` 禁止 null 的动机之一。**用 `ArrayDeque` 就是要在类型层面消除这个二义性。**

### 13.2 PriorityQueue：二叉堆

```java
// 小顶堆（默认，按自然序）
PriorityQueue<Integer> minHeap = new PriorityQueue<>();
// 大顶堆
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());

// topK：求"最大的 k 个"用容量为 k 的【小顶堆】
PriorityQueue<Integer> topK = new PriorityQueue<>(k);   // 堆顶是当前 k 个里最小的
for (int x : nums) {
    if (topK.size() < k) topK.offer(x);
    else if (x > topK.peek()) { topK.poll(); topK.offer(x); }   // 比堆顶大才替换
}
// 求"最小的 k 个"则反过来用大顶堆
```

要点：

- **底层是数组实现的二叉堆**，`offer`/`poll` 是 O(log n) 的上浮/下沉，`peek` 是 O(1)。
- **`iterator()` 不保证有序**（只有堆序：父 ≤ 子，兄弟之间无序）。想按顺序输出必须连续 `poll()`，或者 `toArray` 后排序。
- **默认容量 11**，动态扩容。
- **不允许 null 元素**。
- **不是稳定排序**：比较相等的元素顺序不确定。
- `PriorityQueue` **不是线程安全的**；需要并发用 `PriorityBlockingQueue`。

### 13.3 BlockingQueue 家族（细节见 [[5-线程池]]）

| 实现 | 有界性 | 锁结构 | 特点 |
| --- | --- | --- | --- |
| `ArrayBlockingQueue` | **有界**（必须指定容量） | 单锁 + `notEmpty`/`notFull` 两个条件 | 数组实现，支持公平模式；读写互相阻塞 |
| `LinkedBlockingQueue` | 可选（**默认 `Integer.MAX_VALUE`**） | **双锁**（takeLock/putLock）+ `AtomicInteger count` | 吞吐更高，但默认无界 → **线程池里是 OOM 隐患** |
| `SynchronousQueue` | 容量 0 | 无存储 | 生产者直接"移交"给消费者；`newCachedThreadPool` 用它 |
| `PriorityBlockingQueue` | **无界**（逻辑上） | 单锁 | 带优先级的阻塞队列，**无界所以 put 永不阻塞** |
| `DelayQueue` | 无界 | 单锁 + 优先级队列 | 元素实现 `Delayed`，到期才能取出；定时任务 |
| `LinkedTransferQueue` | 无界 | 无锁（CAS） | `transfer()` 能同步移交，适合高吞吐传递 |

> [!danger] 线程池 + 无界队列 = 内存炸弹
> `Executors.newFixedThreadPool(n)` 内部用的是 `new LinkedBlockingQueue<Runnable>()`（默认无界）。当任务提交速度长期大于处理速度时，队列会**无上限堆积**，最终 `OutOfMemoryError: Java heap space`（或大量对象导致 GC 长暂停）。**生产必须显式 `new ThreadPoolExecutor(..., new ArrayBlockingQueue<>(capacity), ...)` 并配合拒绝策略**，详见 [[5-线程池]]。

## 十四、fail-fast 与 fail-safe

### 14.1 概念对照

| 维度 | fail-fast（快速失败） | fail-safe（安全失败）/弱一致 |
| --- | --- | --- |
| 代表 | `ArrayList`、`HashMap`、`HashSet`、`TreeMap` 的迭代器 | `CopyOnWriteArrayList`、`ConcurrentHashMap`、`CopyOnWriteArraySet` |
| 遍历中修改 | **抛 `ConcurrentModificationException`** | 不抛 |
| 实现机制 | `modCount != expectedModCount` 校验 | 快照数组（COW）或 volatile 指针（CHM） |
| 数据一致性 | 无（直接失败） | **弱一致**：可能看到旧数据，也可能看到部分新数据 |
| 是否保证线程安全 | 否（只是 bug 检测） | 是（对自身结构而言） |
| 适用 | 单线程 + 快速暴露 bug | 并发场景 + 可接受最终一致 |

> [!important] "fail-safe"这个名字有点误导
> 它**不意味着你在遍历时看到的一定是一份稳定快照**。区别在于：
> - `CopyOnWriteArrayList` 的迭代器持有**创建时的数组引用**，是**真快照**：遍历期间的写入完全不可见，也不会影响这次遍历。
> - `ConcurrentHashMap` 的迭代器是**弱一致**的：`next()` 沿着当时的链表/树走，**可能看到遍历开始后新增的节点，也可能看不到**，但**绝不会抛 CME，也不会重复**。
> 面试时把这个差别讲出来，比笼统说"fail-safe"高一个档次。

### 14.2 CopyOnWriteArrayList 的写时复制

```java
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();                                  // ★ 写操作互斥
    try {
        Object[] elements = getArray();
        int len = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);   // ★ 复制整个数组
        newElements[len] = e;
        setArray(newElements);                    // ★ volatile 写，一次性发布
        return true;
    } finally {
        lock.unlock();
    }
}

final void setArray(Object[] a) { array = a; }    // array 是 volatile
public E get(int index) { return elementAt(getArray(), index); }   // ★ 读完全无锁
```

**成本分析（必须算清）**：

| 操作 | 复杂度 | 说明 |
| --- | --- | --- |
| `get` / 迭代 | O(1)，无锁 | 读性能接近 `ArrayList` |
| `add` / `remove` | **O(n) 复制 + 内存翻倍峰值** | 每次写都 `Arrays.copyOf` 整个数组 |
| 连续写 n 次 | **O(n²)** | 这是致命的 |
| 内存 | 写瞬间持有两份数组 | 大数组会带来明显的 GC 压力 |

**结论**：`CopyOnWriteArrayList` 只适合"**读极多、写极少，且元素数量不大**"的场景：

- ✅ 事件监听器列表、拦截器链、路由表、白名单配置（启动时写入，运行期只读或极少刷新）。
- ❌ 当作高并发队列用、频繁 add/remove 的缓存、大列表（几万以上）频繁更新。

> [!warning] 两个额外注意点
> ① **`CopyOnWriteArrayList` 的迭代器不支持 `remove`/`set`/`add`**，会抛 `UnsupportedOperationException`（因为它在快照上操作，改快照没有意义）。
> ② **多个写操作之间的"读-改-写"仍然不安全**：`if (!list.contains(x)) list.add(x);` 在两个线程下都可能插入。要用 `addIfAbsent`（它在锁内做检查）。

## 十五、Collections 与 Arrays 的坑

### 15.1 `Arrays.asList` 返回的是定长视图

```java
List<String> list = Arrays.asList("a", "b", "c");
list.set(0, "z");            // ✅ 可以改（会写回底层数组）
list.add("d");               // ❌ UnsupportedOperationException（定长）
list.remove(0);              // ❌ UnsupportedOperationException

String[] arr = {"a", "b"};
List<String> view = Arrays.asList(arr);
view.set(0, "z");
System.out.println(arr[0]);  // "z" —— 是同一个数组，双向可见
```

**本质**：`Arrays.asList` 返回 `java.util.Arrays$ArrayList`（`Arrays` 的私有内部类，**不是 `java.util.ArrayList`**），它直接包装传入的数组，**不拷贝**。它能 `set` 是因为数组本身可变，但**长度固定**所以不能增删。

> [!danger] 原始类型数组的惊天大坑
> ```java
> int[] nums = {1, 2, 3};
> List<int[]> bad = Arrays.asList(nums);   // 注意泛型是 int[] 而不是 Integer！
> System.out.println(bad.size());          // 1  ← 整个数组被当成一个元素
> System.out.println(bad.get(0).length);   // 3
> ```
> 原因：`asList(T... a)` 的形参是**对象数组**，`int[]` 不是 `Object[]`，所以编译器把它整体作为**单个元素**装进 `Object[]`。要得到 3 个元素，必须用 `Integer[]` 或先装箱：`Arrays.stream(nums).boxed().collect(Collectors.toList())`。
> **推论**：`List.of(nums)`、`Stream.of(nums)` 也有同样的行为。

### 15.2 `List.of` / `Map.of`（JDK 9+）不可变

```java
List<String> l = List.of("a", "b");
l.add("c");                  // ❌ UnsupportedOperationException
List.of("a", null);          // ❌ NullPointerException —— 连构造都不允许 null
Map.of("k1", 1, "k2", 2);    // 不可变，且 key/value 都不允许 null
Map.ofEntries(Map.entry("k", 1));
List.copyOf(coll);           // 拷贝成不可变副本（源改了也不影响）

// Arrays.asList vs List.of
Arrays.asList("a", null);    // ✅ 允许 null，且 set 可变
List.of("a", null);          // ❌ NPE
```

**选择建议**：接口返回"不该被调用方修改"的集合时，用 `List.of`/`Map.of`（JDK 9+）或 `Collections.unmodifiableList`。**注意 `List.of` 的不可变是"不可变"，不是"不可修改视图"**：它真的没有可变的后备集合；而 `Collections.unmodifiableList(inner)` 只是**视图**，`inner` 变了它也跟着变。

### 15.3 `subList` 是视图，不是拷贝

```java
List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5));
List<Integer> sub = list.subList(1, 4);       // 视图 [2, 3, 4]
System.out.println(sub);                      // [2, 3, 4]

sub.set(0, 20);
System.out.println(list);                     // [1, 20, 3, 4, 5] ← 原列表被改

list.add(6);                                  // 结构性修改原列表
System.out.println(sub);                      // ❌ ConcurrentModificationException
```

三个必须记住的结论：

1. **`subList` 返回的是 `AbstractList.SubList` 视图**，读写都作用于原列表（**这其实很好用**）：
   ```java
   // 优美地"删除区间"
   list.subList(from, to).clear();     // 等价于循环 remove，但只搬移一次数组
   ```
2. **原列表的结构性修改会让子列表失效**（`SubList` 通过父列表的 `modCount` 检测，抛 CME）。反过来，**通过 subList 修改父列表也会让原来的 `Iterator` 失效**。
3. **内存泄漏**：`subList` 持有对父列表 `root` 的强引用。只保留一个 10 元素的小视图，却会把整个 100 万元素的父列表钉在堆上。

```java
// ✅ 想真正截取一段独立数据
List<Integer> copy = new ArrayList<>(list.subList(1, 4));   // 拷贝一份，与原列表脱钩
```

### 15.4 其他常用工具

| 方法 | 说明 | 注意 |
| --- | --- | --- |
| `Collections.unmodifiableList(l)` | **视图**包装 | 底层 `l` 变了它也跟着变；不是深拷贝 |
| `Collections.synchronizedList(l)` | 每个方法加同一个 mutex | **遍历仍需手动 `synchronized (list)`** |
| `Collections.emptyList()` | 共享的不可变空列表 | 比 `new ArrayList<>()` 省内存，但**不可修改** |
| `Collections.singletonList(x)` | 单元素不可变列表 | 同样不可修改 |
| `Collections.sort(list)` | 稳定排序（TimSort），原地 | 比较器必须满足契约 |
| `Collections.binarySearch(list, k)` | O(log n) | **必须先排序**，否则结果未定义 |
| `Collections.reverse/shuffle/swap/rotate` | 原地操作 | `shuffle` 可传 `Random` 以获得可复现的洗牌 |
| `Collections.frequency(c, o)` | 计数 | O(n) |
| `Collections.nCopies(n, o)` | n 个相同元素的不可变列表 | 共享同一引用 |
| `list.toArray(new String[0])` | 推荐写法 | JDK 11+ 可用 `toArray(String[]::new)`；不要传 `size()` 长度（多分配一个数组且无收益） |

> [!tip] `Collections.sort` 的"契约"异常
> 如果比较器违反自反/传递/对称，`sort` 可能抛：
> `java.lang.IllegalArgumentException: Comparison method violates its general contract!`
> 这是 TimSort 主动做的契约检查（为了早暴露 bug），**不是 JDK 的 bug**。典型误用：`(a, b) -> a.score > b.score ? -1 : 1`（缺少"相等返回 0"分支，且不满足反对称性）。正确写法：`Comparator.comparingInt(x -> x.score)`。

## 十六、选型速查与必答

### 16.1 决策树（背这一张就够）

```text
需要 key-value 映射？
├── 是 → 需要并发吗？
│        ├── 是 → ConcurrentHashMap（有序用 ConcurrentSkipListMap）
│        └── 否 → 需要排序/范围查询吗？
│                 ├── 是 → TreeMap
│                 ├── 需要插入序/LRU → LinkedHashMap
│                 └── 否 → HashMap  ★ 默认
└── 否 → 需要去重吗？
         ├── 是 → 需要顺序吗？
         │        ├── 排序 → TreeSet
         │        ├── 插入序 → LinkedHashSet
         │        └── 无所谓 → HashSet  ★ 默认
         └── 否 → 只在两端操作吗？
                  ├── 是 → ArrayDeque  ★ 队列/栈首选
                  ├── 需要按下标随机访问 → ArrayList  ★ 默认
                  ├── 需要按优先级取极值 → PriorityQueue
                  └── 需要线程安全 → 视读写比选 CopyOnWriteArrayList / 加锁 / BlockingQueue
```

### 16.2 一页纸对照

| 需求 | 首选 | 不要用 |
| --- | --- | --- |
| 通用列表 | `ArrayList` | `Vector`、`LinkedList` |
| 队列/栈 | `ArrayDeque` | `Stack`、`LinkedList` |
| 通用映射 | `HashMap` | `Hashtable` |
| 并发映射 | `ConcurrentHashMap` | `Collections.synchronizedMap`（高并发下） |
| LRU 缓存 | Caffeine | 手写 `LinkedHashMap`（并发下） |
| 排序 map | `TreeMap` | 手动 `sort` 后再 `HashMap` |
| 读多写极少并发列表 | `CopyOnWriteArrayList` | `ArrayList` + 锁 |
| topK | `PriorityQueue` | 全量排序 |

### 16.3 「必答」三连

> [!important] 必答 1：HashMap 的 put 与扩容原理
> **put**：① `hash(key) = h ^ (h>>>16)` 扰动；② `(n-1) & hash` 定位桶；③ 桶空直接放；④ 否则比 `hash`→`==`→`equals`，命中则覆盖 value，未命中则链表尾插（1.8）/红黑树插入；⑤ 链表长度到 8 且容量 ≥ 64 则树化，容量 < 64 则改为扩容；⑥ `++size > threshold` 则扩容。
> **扩容**：容量和阈值都翻倍，遍历旧桶，单节点重算下标、树节点 `split`、链表按 `(hash & oldCap)` 拆成低位（留原下标 `j`）和高位（放到 `j + oldCap`）两条链，**无需重算 hash 和取模**。默认 16/0.75，即第 13 个元素触发扩容到 32。

> [!important] 必答 2：为什么 HashMap 线程不安全
> ① **1.7 的并发扩容会形成环形链表**：头插法 + 两个线程同时 `transfer`，线程 1 在 `next = e.next` 之后被挂起，线程 2 完成反转，线程 1 恢复后把 `A.next` 指回 B，形成 `A↔B` 环，之后 `get` 落到该桶就死循环，**CPU 100% 且 jstack 显示卡在 `HashMap.getEntry`**。
> ② **1.8 消除了成环（尾插 + 高低位拆分保序），但仍然不安全**：空桶写入不是 CAS → 丢数据；`++size`/`++modCount` 非原子 → size 不准；`table`/`threshold` 无 happens-before → 可能读到中间态。
> ③ 修法：并发场景用 `ConcurrentHashMap`；`Hashtable` 全表锁已淘汰；`Collections.synchronizedMap` 高并发下性能差且迭代要手动加锁。
> ④ 顺带一句加分项：`ConcurrentHashMap` 出于**"null 值会让 get 的二义性无法原子地消解"**而禁止 null。

> [!important] 必答 3：ArrayList 与 LinkedList 怎么选
> **默认永远 ArrayList。** "LinkedList 增删快"只在"已持有节点位置"或"只在两端操作"时成立；按下标做中间插入时，`node(index)` 的 O(n) 遍历 + 指针追逐的 cache miss，通常比 ArrayList 的 `arraycopy`（连续内存 memmove）更慢。加上 LinkedList 每元素一个 Node 对象（约 24 字节额外开销）且缓存不友好，**除了"实现 Deque 且允许 null 元素"之外，几乎没有选择它的理由**；栈和队列优先 `ArrayDeque`。
