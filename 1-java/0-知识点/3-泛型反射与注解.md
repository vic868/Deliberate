## 一、泛型：为什么需要，以及它到底被擦成了什么

### 1.1 没有泛型的世界

```java
// Java 5 之前
List list = new ArrayList();
list.add("hello");
list.add(42);                     // 编译器不拦

String s = (String) list.get(1);  // 编译通过
// 运行时：java.lang.ClassCastException: java.lang.Integer cannot be cast to java.lang.String
```

两个问题：

1. **类型不安全**：容器可以装任何东西，错误只能在运行期暴露，且**离出错点很远**（可能是别的模块塞进去的）。
2. **到处都是强转**：调用方必须知道具体类型，代码噪音大，且强转本身可能失败。

泛型带来三件事：

| 收益 | 说明 |
| --- | --- |
| 编译期类型检查 | `List<String>.add(42)` 直接编译失败 |
| 消除显式强转 | `String s = list.get(0);` 由编译器插入 `checkcast` |
| 更好的 API 表达力 | `Map<String, List<Order>>` 一眼可读，替代文档注释里的"这里放 String" |

> [!important] 一个必须先建立的认知
> Java 的泛型是**编译期的类型检查工具**，不是运行期的类型信息。`List<String>` 和 `List<Integer>` 在运行期是**同一个类** `java.util.ArrayList`。所有泛型相关的坑，根因都是这一条。

### 1.2 类型擦除：擦到什么程度

**擦除规则（JLS 定义）**：

| 类型参数声明 | 擦除后 |
| --- | --- |
| 无界 `<T>` | `Object` |
| `<T extends Number>` | `Number`（第一个边界） |
| `<T extends Number & Comparable<T>>` | `Number`（只保留第一个，其余作为编译期约束） |
| `<T extends Comparable<? super T>>` | `Comparable` |

```java
public class Box<T> { private T value; public T get() { return value; } public void set(T v) { value = v; } }
public class NumBox<T extends Number> { private T value; public T get() { return value; } }
```

`javap -s` 的真实输出（关键看描述符）：

```text
Box:                                        NumBox:
  Object get()   descriptor: ()Ljava/lang/Object;     Number get()  descriptor: ()Ljava/lang/Number;
  void set(Object) descriptor: (Ljava/lang/Object;)V  Number value  descriptor: Ljava/lang/Number;
  Object value   descriptor: Ljava/lang/Object;
```

**结论**：类型参数 `T` 在字节码里根本不存在，字段/参数/返回值全部落到了上界（无界就是 `Object`）。javac 会在**取值处**插入 `checkcast`，在**传值处**插入必要的装箱：

```java
Box<String> box = new Box<>();
box.set("hi");
String s = box.get();
```

```text
// 等价字节码（简化）
new Box / dup / invokespecial Box.<init>:()V / astore_1
aload_1 / ldc "hi" / invokevirtual Box.set:(Ljava/lang/Object;)V   // 无检查，String 直接当 Object
aload_1 / invokevirtual Box.get:()Ljava/lang/Object;
checkcast     #7    // class java/lang/String      ← 强转是编译器插的
astore_2
```

> [!note] 擦除是"完全"的吗？——不是
> **类文件里保留了泛型签名（Signature 属性）**。`javap -v` 能看到：
> ```text
> Signature: #12  // Ljava/lang/Object;Lcom/example/Box<Ljava/lang/String;>;
> ```
> 反射可以通过 `getGenericSuperclass()`、`getGenericReturnType()`、`getTypeParameters()` 拿到这些信息，返回 `ParameterizedType` / `TypeVariable` 等。**但局部变量和方法调用点的类型实参没有保留**（局部变量表在调试信息里，且只有擦除后的描述符）。
> 这就是 `TypeToken` / `ParameterizedTypeReference` 能工作的原理——**必须把泛型信息"写进"某个类的签名里**（字段、方法参数/返回值、父类），才能在运行期读回来。

### 1.3 擦除带来的限制

| 限制 | 编译错误 / 行为 | 规避方式 |
| --- | --- | --- |
| 不能 `new T()` | `type parameter T cannot be instantiated directly` | 传 `Supplier<T>` / `Class<T>` 反射创建 |
| 不能 `new T[n]` | `generic array creation` | `(T[]) new Object[n]`（unchecked 警告）或用 `List<T>` |
| 不能 `new List<String>[10]` | `generic array creation` | `new List<?>[10]`，或 `List<List<String>>` |
| 不能 `instanceof T` | `illegal generic type for instanceof` | `clazz.isInstance(obj)` |
| 不能 `T.class` / `List<String>.class` | 编译错误（只有 `int.class`、`List.class`） | 把 `Class<T>` 作为参数传入 |
| 静态成员不能用类型参数 | `static T x;` 报错（静态方法可以声明自己的 `<T>`） | 静态方法自带独立类型参数 |
| 不能 `catch (T e)` / 泛型异常类 | `generic class may not extend Throwable` | 用具体异常类型 |
| 不能重载 `f(List<String>)` / `f(List<Integer>)` | `name clash: have the same erasure` | 改方法名或加参数 |
| 基本类型不能做实参 | 不能写 `List<int>` | `List<Integer>`（装箱）+ 泛型特化缺失的性能代价 |

```java
// 「擦除导致重载冲突」的经典报错
public void f(List<String> l) {}
public void f(List<Integer> l) {}   // 编译错误：both methods have same erasure

// 「不能 new T[]」的正确写法
static <T> T[] newArray(int n, Class<T> type) {
    return (T[]) Array.newInstance(type, n);   // java.lang.reflect.Array
}

// 「不能 new T()」的正确写法
static <T> T create(Supplier<T> factory) { return factory.get(); }
```

> [!danger] 泛型数组 + 可变参数 = 堆污染（heap pollution）
> ```java
> @SafeVarargs
> static <T> List<T> of(T... items) { return new ArrayList<>(Arrays.asList(items)); }
>
> static <T> void dangerous(List<T>... lists) {        // 编译警告 unchecked
>     Object[] raw = lists;                            // 泛型数组被当 Object[] 用
>     raw[0] = List.of("not a T");                     // 塞进去了
> }
> ```
> 因为泛型数组在运行期不知道元素类型，**类型检查被绕过**，错误会在很久之后以 `ClassCastException` 的形式爆出来（见第八节）。

### 1.4 为什么 Java 选了擦除，而不是 C# 那样的具化泛型

这是**面试深挖题**，答案是历史包袱 + 工程折衷。

| 维度 | Java 擦除式泛型 | C# 具化（reified）泛型 |
| --- | --- | --- |
| 运行期是否保留类型实参 | 否 | 是 |
| `List<int>` | 不支持（只有 `List<Integer>`） | 支持，且有值类型特化，无装箱 |
| 能否 `new T()` / `typeof(T)` | 不能 | 能 |
| 与旧版本的二进制兼容 | **完全兼容**：老 class 文件、老 jar 无需改动 | 需要新的运行时 |
| 实现代价 | 只改编译器，JVM 几乎不动 | CLR 需要支持泛型实例化，代码可能膨胀 |
| 性能 | 所有引用类型共享同一份代码，无膨胀；基本类型要装箱 | 值类型有专门代码，无装箱，性能更好 |

**Java 的现实约束**：2004 年 Java 5 发布时，世界上已经有海量 `java.util.List`/`Hashtable` 的使用者和已编译的 class 文件。如果引入具化泛型，意味着：

1. **源代码兼容**：`List list = new ArrayList()` 必须继续能编译（靠 raw type + unchecked 警告）。
2. **二进制兼容**：老的、已编译的 jar 里的 `List.add(Object)` 必须继续能被新代码调用。所以 `List<E>.add(E)` 擦除后必须**恰好**是 `add(Object)`，否则老 jar 与新 JDK 之间就断裂了。
3. **JVM 改动最小**：不需要为泛型改字节码格式、改验证器、改 GC。

擦除是"**在不动虚拟机的前提下，给编译器加一层类型检查**"的最小代价方案。代价就是运行期没有泛型信息——这个代价被 `Signature` 属性 + 反射 API 部分弥补回来。

> [!tip] 答题模板
> "Java 选擦除主要是为了**向后二进制兼容**：泛型必须能和老的非泛型字节码无缝互操作，所以 `List<E>` 擦除后必须就是 `List<Object>` 的方法签名，JVM 层面几乎不用改。这带来了零代码膨胀的好处，代价是运行期拿不到类型实参、基本类型必须装箱、不能 `new T[]`。C# 是后来设计的语言，没有这个包袱，所以可以做成具化泛型，支持 `List<int>` 和 `typeof(T)`。"

## 二、通配符与 PECS

### 2.1 为什么需要通配符：泛型是不变的

**数组是协变的，泛型是不变的**：

```java
Object[] arr = new String[1];    // 编译通过（数组协变）
arr[0] = 42;                     // 编译通过，运行期 ArrayStoreException —— 类型漏洞

List<Object> l = new ArrayList<String>();   // 编译失败！泛型不变
```

Java 有意把泛型设计成**不变（invariant）**，就是为了堵住上面这个漏洞。但不变带来的问题是：**"只能装 String 的 List" 不能被当成 "能读出 Object 的 List"**。于是需要**通配符**来表达"方向明确的可变性"。

### 2.2 `extends` 与 `super` 的能力差异

```java
List<? extends Number> producer = new ArrayList<Integer>();   // 上界
List<? super Integer> consumer = new ArrayList<Number>();     // 下界
```

| 操作 | `List<? extends Number>` | `List<? super Integer>` | `List<?>` |
| --- | --- | --- | --- |
| 读元素（`get`） | 可以，静态类型是 `Number` | 可以，静态类型只能是 `Object` | 可以，静态类型 `Object` |
| 写元素（`add`） | **不可以**（除 `null`） | 可以，可以放 `Integer` 及其子类 | **不可以**（除 `null`） |
| 语义 | **生产者**（我只从里面读） | **消费者**（我只往里写） | 只读或只当"任意类型" |
| 别名 | 上界通配符 | 下界通配符 | 无界通配符 |

```java
// 为什么 extends 不能写？
List<? extends Number> l = new ArrayList<Integer>();
l.add(1);          // 编译错误！编译器只知道"元素是 Number 的某个子类型"，
                   // 但不知道具体是 Integer 还是 Double，写任何值都可能破坏类型安全
Number n = l.get(0);   // OK，读出来至少是 Number

// 为什么 super 不能安全地读？
List<? super Integer> c = new ArrayList<Number>();
c.add(1);              // OK
Object o = c.get(0);   // 只能拿到 Object，因为里面可能是 Number 或 Object
```

### 2.3 PECS 记忆法与判断步骤

> [!important] PECS = **P**roducer **E**xtends, **C**onsumer **S**uper
> **如果参数化类型是"数据的来源"（你从它读），用 `? extends T`；如果是"数据的去处"（你往它写），用 `? super T`；如果既读又写，就别用通配符，直接用 `T`。**

判断步骤（三步法）：

1. 在这个集合上，我主要是**读**还是**写**？
2. 读 → `? extends T`，T 取"我需要的**最粗**的上界"？
3. 写 → `? super T`，T 取"我要放进去的**具体**类型"。

**JDK 里的标准示范**：

```java
// 只读（生产者）：src 里每个元素都能当 T 用
public static <T> void copy(List<? super T> dest, List<? extends T> src) { ... }

// 只读：max 需要元素之间互相比较，这里还有递归边界
public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)

// 只写（消费者）：addAll 往 this 里写 E 及其子类
boolean addAll(Collection<? extends E> c);

// 既读又写：Comparator 是消费者（它消费 T 去比较）
public static <T> void sort(List<T> list, Comparator<? super T> c);
```

> [!question] 为什么 `Collections.sort` 用 `Comparator<? super T>` 而不是 `Comparator<T>`？
> 因为"能比较 Object 的比较器"当然也能比较 String。如果写成 `Comparator<T>`，那么 `Comparator<Object>` 就不能传给 `sort(List<String>, ...)` —— 白白损失了灵活性。这正是 PECS 的 `super`：**比较器消费 T**。
> 同理 `TreeMap<K,V>` 的构造器签名是 `Comparator<? super K>`。

### 2.4 无界通配符 `<?>` vs 原始类型 raw type

| 维度 | `List<?>` | `List`（raw） |
| --- | --- | --- |
| 类型检查 | 保持开启，只能读为 `Object`、不能写 | **全部关闭**，可以随便 `add`，产生 unchecked 警告 |
| `get()` 返回 | `Object` | `Object` |
| `add(x)` | 编译错误（除 `null`） | 编译通过（警告），运行期可能炸 |
| 用途 | "我不关心元素类型，只做通用操作"（`size()`、`clear()`、`isEmpty()`） | 只用于与遗留代码互操作 |

```java
// 参数是 List<?> 时，调用方可以传 List<String>、List<Integer>，且方法内部安全
static void printSize(List<?> list) { System.out.println(list.size()); }

// 反例：参数是 raw List，方法内部可以 add 任何东西，类型安全被破坏
static void bad(List list) { list.add(42); }   // 调用方传 List<String> 就会被污染
```

> [!warning] 类字面量
> `List.class` 合法（raw）；`List<?>.class` 和 `List<String>.class` 都**不合法**。需要"带泛型的类型引用"时必须用 `ParameterizedTypeReference` / `TypeToken` 这类技巧（见 4.5）。

## 三、桥接方法（bridge method）

### 3.1 问题：重写 + 擦除 = 签名不再匹配

```java
class Node<T> {
    private T data;
    public void setData(T data) { this.data = data; }
    public T getData() { return data; }
}

class MyNode extends Node<Integer> {
    @Override public void setData(Integer data) { super.setData(data); }
    @Override public Integer getData() { return super.getData(); }
}
```

**擦除后**：

| 类 | 方法 | 擦除后签名 |
| --- | --- | --- |
| `Node` | `setData(T)` | `setData(Object)` |
| `MyNode` | `setData(Integer)` | `setData(Integer)` |
| `Node` | `getData()` | `getData(): Object` |
| `MyNode` | `getData()` | `getData(): Integer` |

矛盾出现了：

- 从 **Java 源码语义**看，`MyNode.setData(Integer)` 是**重写**了 `Node.setData(T)`；
- 从 **JVM 方法标识**看（`name + descriptor`），`setData(Object)` 和 `setData(Integer)` 是**两个不同的方法**，不构成重写。

如果就这么编译，`Node<Integer> n = new MyNode(); n.setData(1);` 会调用 `Node.setData(Object)`（vtable 槽位是 `Object`），**永远不会进入 `MyNode` 的重写实现**——多态直接失效。

### 3.2 解法：编译器生成桥接方法

javac 在 `MyNode` 里额外生成一个**桥接方法**，把擦除后的签名转调到真正的实现：

```text
// javap -p -c MyNode 的真实输出（节选）
public void setData(java.lang.Integer);
  Code:
     0: aload_0
     1: aload_1
     2: invokespecial #7   // Method setData:(Ljava/lang/Integer;)V
     5: return

public void setData(java.lang.Object);
  flags: ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
  Code:
     0: aload_0
     1: aload_1
     2: checkcast     #13  // class java/lang/Integer
     5: invokevirtual #15  // Method setData:(Ljava/lang/Integer;)V
     8: return

public java.lang.Integer getData();
  Code: ... ireturn

public java.lang.Object getData();
  flags: ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
  Code:
     0: aload_0
     1: invokespecial #19  // Method getData:()Ljava/lang/Integer;
     4: areturn
```

桥接方法做了三件事：

1. **签名对齐**：方法名 + 描述符与父类擦除后的方法**完全一致**，从而落入同一个 vtable 槽位，多态恢复。
2. **类型转换**：参数方向做 `checkcast` 把 `Object` 转成 `Integer`（这样如果传错类型，会在这里抛 `ClassCastException`）。
3. **转调**：`invokevirtual`/`invokespecial` 到真正的实现。

两个标记位：

| 标志 | 含义 |
| --- | --- |
| `ACC_BRIDGE` | 编译器生成的桥接方法 |
| `ACC_SYNTHETIC` | 源码中不存在，对源码级工具"不可见" |

> [!danger] 桥接方法带来的真实陷阱
> 1. **反射会扫到重复方法**：`getDeclaredMethods()` 里既有 `setData(Integer)` 又有 `setData(Object)`。如果你在写框架（比如自己实现类似 MyBatis 的映射、或者做注解扫描），**必须用 `Method.isBridge()` 或 `isSynthetic()` 过滤**，否则同一个逻辑方法会被处理两次。Spring、Jackson、Hibernate 里都有这类过滤代码。
> 2. **`instanceof` 与强转**：`Object o = new MyNode(); ((Node<String>) o).setData("x")` 编译通过（unchecked），运行期在桥接方法的 `checkcast` 处抛 `ClassCastException`。
> 3. **"方法被调用两次"的假象**：AOP 环绕、性能统计、日志切面如果同时拦截了桥接方法和真实方法，会出现重复记录。

### 3.3 桥接方法不止出现在泛型里

**协变返回类型**同样会生成桥接方法：

```java
class Parent { Object get() { return "p"; } }
class Child extends Parent { @Override String get() { return "c"; } }
// Child 里会多出：Object get() { return this.get(); }  ← ACC_BRIDGE | ACC_SYNTHETIC
```

因为 vtable 槽位是按 `get(): Object` 布局的，需要一个返回 `Object` 的入口来转调返回 `String` 的实现。**所以"桥接方法是泛型专属"是错误认知。**

> [!tip] 一句话总结桥接方法
> **擦除让"源码上的重写"在字节码层面变成了"两个不相干的方法"。桥接方法是编译器为了让 vtable 语义与源码语义保持一致而生成的转发层——它用一次 `checkcast` + 一次转调，换回了多态。**

## 四、反射

### 4.1 `Class` 对象的四种获取方式

| 方式 | 写法 | 是否触发类初始化 | 典型场景 |
| --- | --- | --- | --- |
| 类字面量 | `Foo.class` | **否**（只加载，不初始化） | 编译期已知类型、注解属性 |
| `Object.getClass()` | `obj.getClass()` | 否（对象已存在，类必然已加载） | 已有实例 |
| `Class.forName(String)` | `Class.forName("com.x.Foo")` | **是**（默认 `initialize=true`） | JDBC 驱动注册、配置驱动的框架 |
| `ClassLoader.loadClass(String)` | `loader.loadClass("com.x.Foo")` | **否** | 框架延迟加载、自定义加载器 |

### 4.2 `Class.forName` vs `ClassLoader.loadClass`

```java
// Class.forName(String) 的实现等价于：
Class.forName(name, true, callerClassLoader);   // resolve = true

// ClassLoader.loadClass(String) 默认：
loadClass(name, false);                         // resolve = false → 不链接、不初始化
```

| 对比项 | `Class.forName` | `ClassLoader.loadClass` |
| --- | --- | --- |
| 是否执行静态代码块 | **会** | 不会 |
| 是否初始化静态字段 | **会** | 不会 |
| 默认类加载器 | 调用方的类加载器 | 指定的加载器（不传就是当前 loader） |
| 典型用途 | `Class.forName("com.mysql.cj.jdbc.Driver")` 触发驱动自注册 | 容器/框架按需加载类（Tomcat、Spring 的 `ClassUtils.forName` 内部会做缓存和降级） |

**"类初始化"到底做了什么**：执行静态字段赋值与静态代码块（`<clinit>`）。所以：

```java
class Config {
    static { System.out.println("Config 初始化"); }
    static final String URL = load();       // 有副作用
}

Class.forName("Config");                    // 打印"Config 初始化"
ClassLoader.getSystemClassLoader().loadClass("Config");   // 不打印
```

> [!warning] 经典面试陷阱
> ```java
> Class.forName("com.mysql.jdbc.Driver");              // 触发 Driver 的静态块 → 注册到 DriverManager
> ClassLoader.getSystemClassLoader().loadClass("com.mysql.jdbc.Driver");  // 不注册，后面 getConnection 报 "No suitable driver"
> ```
> 这是 JDBC 时代最常见的"驱动加载失败"根因。现代 JDBC 4.0+ 通过 `META-INF/services/java.sql.Driver` 的 SPI 机制自动加载，已经不需要手写 `Class.forName`。

**类加载的三个阶段（详见 [[7-JVM内存与GC]]）**：

```text
加载(Loading) → 链接(Linking: 验证 → 准备 → 解析) → 初始化(Initialization)
getClass()/Foo.class/loadClass()  只到"加载"（loadClass 默认不解析）
forName(name, true, loader)       一直推进到"初始化"
```

### 4.3 反射 API 的核心分组

| API | 作用范围 | 关键差异 |
| --- | --- | --- |
| `getMethods()` | **本类 + 继承**的所有 `public` 方法 | 含接口的 default 方法；含桥接方法 |
| `getDeclaredMethods()` | **仅本类**声明的所有方法（含 private/protected） | 不含继承；含合成方法与桥接方法 |
| `getFields()` / `getDeclaredFields()` | 同上规则，作用于字段 | 顺序**无规范保证** |
| `getConstructors()` / `getDeclaredConstructors()` | 同上 | `getConstructor()` 只找 public |
| `getSuperclass()` / `getInterfaces()` | 父类/接口 | `getGenericSuperclass()` 才有泛型信息 |
| `getAnnotation(X.class)` | 本元素的注解（遵循 `@Inherited`） | `getDeclaredAnnotation` 不看继承 |
| `getAnnotationsByType(X.class)` | **支持 `@Repeatable`** 的批量获取 | Java 8+ |
| `isAnnotationPresent` / `isAssignableFrom` / `isInstance` | 判定 | `isAssignableFrom` 是"我能不能接收它" |

```java
// 一个不漏地遍历并过滤掉编译器产物
for (Method m : clazz.getDeclaredMethods()) {
    if (m.isBridge() || m.isSynthetic()) continue;   // 跳过桥接/合成方法
    System.out.println(m.getName());
}

// 泛型信息的读取（只有写进 Signature 的才能读到）
Type superType = clazz.getGenericSuperclass();
if (superType instanceof ParameterizedType pt) {
    Type actual = pt.getActualTypeArguments()[0];   // 真实的类型实参
}
```

### 4.4 反射的性能问题与优化

| 环节 | 开销来源 | 缓解 |
| --- | --- | --- |
| `getDeclaredMethods()` / `getMethods()` | 每次返回**新数组** + 拷贝 Method **对象**（内部 `copyMethod`） | **把 `Method`/`Field`/`Constructor` 缓存到 `static final` 或 `ConcurrentHashMap`** |
| `setAccessible(true)` | 首次关闭访问检查有一定开销，但之后每次调用都省掉检查 | 在静态初始化块里对缓存的成员调用一次 |
| 参数装箱 / 可变参数数组 | `invoke(Object, Object...)` 每次都要新建 `Object[]`，基本类型要装箱 | 用 `MethodHandle.invokeExact` 可以避免部分开销 |
| 调用本身 | 反射调用是**间接调用**，JIT 难以内联，且要处理类型检查与异常包装 | 参数字节码生成 / `MethodHandle` / 直接调用 |
| 异常包装 | 目标方法抛的异常被包进 `InvocationTargetException` | 记得 `getCause()`，别只打外层 |

**HotSpot 的反射调用演进（描述行为）**：

- **较早期版本**：`Method.invoke` 有"膨胀（inflation）"机制——前 N 次（`sun.reflect.inflationThreshold`，默认 15）走 `NativeMethodAccessorImpl`（JNI 调用，启动快但每次调用慢），超过阈值后动态生成字节码的 `GeneratedMethodAccessorImpl`（生成慢但调用快）。
- **较新版本（JDK 18 起）**：核心反射改为基于**方法句柄**实现，膨胀机制被移除，性能更稳定、更容易被 JIT 内联。

> [!tip] 反射优化的三条实践
> ```java
> private static final Method HANDLE;
> static {
>     try {
>         HANDLE = Target.class.getDeclaredMethod("run", String.class);
>         HANDLE.setAccessible(true);        // 只做一次
>     } catch (NoSuchMethodException e) {
>         throw new ExceptionInInitializerError(e);
>     }
> }
> // 热路径直接复用
> HANDLE.invoke(target, arg);
> ```
> 1. **缓存句柄**：把 `Method`/`Field` 缓存进静态常量或 ConcurrentHashMap（key 用 `Class + name + 参数类型`）。
> 2. **一次 `setAccessible(true)`**：放在静态初始化里。
> 3. **能不用就不用**：极热路径考虑 `MethodHandle`、`VarHandle`，或者干脆用接口/`LambdaMetafactory` 生成直接调用。

**为什么反射会阻碍 JIT 内联**：

1. `Method.invoke` 的接收者与参数类型在运行期才确定，编译器看不到内联目标。
2. 即使能解析出唯一目标，还要保留"类型不匹配抛出异常"的语义，内联后无法安全去优化（需要 guard）。
3. 生成的 accessor 类属于运行期动态类，还可能触发额外的类加载/去优化。

结果是：反射调用通常比直接调用慢**一个数量级起步**，在优化后能收敛到 2~5 倍，但**很难与直接调用/方法句柄持平**。

### 4.5 反射的典型应用

| 应用 | 用反射做什么 |
| --- | --- |
| **Spring IoC** | 读 `@Autowired`/构造器参数 → `getDeclaredConstructor().newInstance()` 实例化 Bean → `Field.set`/`Method.invoke` 注入依赖 → 扫描 `@Component` 注解 |
| **Spring AOP** | JDK 动态代理（`Proxy.newProxyInstance`）+ `Method.invoke` 调用目标 |
| **MyBatis** | 从 `ResultSet` 读列 → 反射 `setter`/字段赋值；`MapperProxy` 用 JDK 代理实现接口 |
| **Jackson / Gson** | 反射读字段/`getter` 做序列化；`TypeReference`/`TypeToken` 从匿名子类签名里读回泛型 |
| **JUnit** | 反射查找 `@Test` 方法、`@BeforeEach` 方法，绕过 `private` |
| **JDK 自身** | `Class.forName` 加载驱动、`ServiceLoader` SPI、`java.lang.invoke`、`VarHandle` |

**"泛型信息只在签名里"的实战价值**：

```java
// Gson 的 TypeToken / Spring 的 ParameterizedTypeReference 原理：
// 用匿名子类把泛型实参"烧"进 class 文件的 Signature 属性
Type type = new TypeToken<List<Order>>() {}.getType();
// 反射读取匿名子类的 getGenericSuperclass() → ParameterizedType → List<Order>

// Spring 的 ResolvableType 是这套逻辑的增强版，能处理嵌套泛型、通配符、类型变量解析
ResolvableType t = ResolvableType.forMethodReturnType(method);
```

### 4.6 反射与模块化：强封装

**问题**：反射 + `setAccessible(true)` 可以突破 `private`，这意味着 JDK 内部的实现细节（`sun.misc.Unsafe`、`java.util` 内部类、`java.lang` 私有字段）都可能被外部代码依赖，一旦 JDK 改动就大面积炸。

**JDK 的做法（说明行为，不追具体版本号）**：

| 阶段 | 行为 |
| --- | --- |
| JDK 9 引入模块系统 | 模块未 `opens` 的包，反射访问内部 API 会有**警告**，但默认仍允许（过渡期） |
| 过渡期结束（JDK 16 起） | **默认拒绝**（等价于 `--illegal-access=deny`），对未开放包调用 `setAccessible(true)` 抛 `InaccessibleObjectException` |
| 后续版本 | 移除 `--illegal-access` 这个过渡开关，强封装成为常态 |

```java
Field f = String.class.getDeclaredField("value");
f.setAccessible(true);
// JDK 16+：java.lang.reflect.InaccessibleObjectException:
//   Unable to make field private final byte[] java.lang.String.value accessible:
//   module java.base does not "opens java.lang" to unnamed module @1b6d3586
```

**合法绕行方式**（都要显式声明，属于"我知道我在做什么"）：

| 方式 | 说明 |
| --- | --- |
| `--add-opens java.base/java.lang=ALL-UNNAMED` | 启动参数开放指定包（Spring/Netty/序列化框架的常见要求） |
| `module-info.java` 里 `opens com.x.internal to spring.core;` | 模块作者主动开放 |
| `MethodHandles.privateLookupIn(...)` | 需要目标模块对调用方 `opens` |
| `trySetAccessible()` | 不抛异常的探测形式，先判断能不能访问 |

> [!warning] 从 JDK 8 升到 JDK 17 最常见的启动报错
> ```text
> java.lang.reflect.InaccessibleObjectException: Unable to make ... accessible:
>   module java.base does not "opens java.lang" to unnamed module
> ```
> 根因就是某个框架在反射 JDK 内部类。**正确处理是升级框架**（新版 Spring/Netty/Jackson 都已适配），把 `--add-opens` 当临时缓解手段。堆一堆 `--add-opens` 只是把技术债藏起来——而且它会随 JDK 版本继续收紧。

## 五、注解

> [!note] 一句话定位
> **注解是一种"能被工具读取的元数据"**：编译期可以被 APT/编译器读，运行期可以被反射读。它本身不产生任何行为，行为来自**读取它的代码**（框架、切面、注解处理器）。

### 5.1 元注解

| 元注解 | 取值 | 语义 |
| --- | --- | --- |
| `@Retention` | `SOURCE` | 只在源码阶段，编译后丢弃。给 APT、Lombok、编译器用的 |
| | `CLASS` | 保留在 class 文件，但 JVM 运行期不读取（**默认值**）。给字节码工具/编译期织入用 |
| | `RUNTIME` | 保留到运行期，可被反射读取。框架注解基本都是这个 |
| `@Target` | `TYPE`、`FIELD`、`METHOD`、`PARAMETER`、`CONSTRUCTOR`、`LOCAL_VARIABLE`、`ANNOTATION_TYPE`、`PACKAGE`、`TYPE_PARAMETER`、`TYPE_USE`、`MODULE` 等 | 限定可标注的位置，写错地方直接编译失败 |
| `@Inherited` | — | **只对类有效**：子类会"继承"父类（沿父类链向上）的注解，**接口上的注解不会被实现类继承** |
| `@Documented` | — | 进入 Javadoc |
| `@Repeatable` | 指向容器注解 | 允许同一位置重复标注，Java 8+ |
| `@Native` | — | 提示该常量可能被 native 代码引用（生成头文件用） |

```java
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
@Inherited
@Documented
public @interface Logged {
    String value() default "";
    Level level() default Level.INFO;      // 枚举
    Class<?>[] excludes() default {};      // Class 数组
}
```

> [!danger] `@Retention` 不写，默认是 `CLASS`
> 这是极其常见的事故：
> ```java
> public @interface MyAnno { }             // 默认 CLASS！
>
> @MyAnno
> class Foo { }
>
> Foo.class.getAnnotation(MyAnno.class);   // 返回 null，不报错，静默失效
> ```
> 自定义注解**想被反射读到就必须显式写 `@Retention(RUNTIME)`**。因为它不报错，只表现为"切面/校验不生效"，排查成本很高。

`@Repeatable` 的机制：

```java
@Retention(RUNTIME) @Repeatable(Schedules.class)
public @interface Schedule { String cron(); }

@Retention(RUNTIME)
public @interface Schedules { Schedule[] value(); }   // 容器注解

@Schedule(cron = "0 0 1 * * ?")
@Schedule(cron = "0 0 2 * * ?")     // 编译后其实是 @Schedules({@Schedule(...), @Schedule(...)})
class Job { }

// 读取：用 getAnnotationsByType 才能拿到两个
Schedule[] arr = Job.class.getAnnotationsByType(Schedule.class);   // 长度 2
```

### 5.2 注解的本质：接口 + 动态代理

这一点是**深挖题的核心**。

**源码层面**：

```java
@Retention(RUNTIME) @Target(TYPE)
public @interface Author { String name(); int year() default 2026; }
```

**字节码层面**：`@interface` 被编译成**接口**，成员方法被编译成**无参抽象方法**：

```text
// javap -p Author
public interface Author extends java.lang.annotation.Annotation {
    public abstract java.lang.String name();
    public abstract int year();
}
```

注意：`default 2026` **不是** Java 接口的 `default` 方法，而是存在 `AnnotationDefault` 属性里的默认值：

```text
public abstract int year();
  descriptor: ()I
  AnnotationDefault:
    default_value: I#9(2026)
```

**运行期层面**：JVM 并不为注解创建一个"注解类"。当类文件加载时，`RUNTIME` 注解被解析成一个实现了该注解接口的**动态代理对象**，其 `InvocationHandler` 是 `sun.reflect.annotation.AnnotationInvocationHandler`，内部持有一个 `Map<String, Object> memberValues`（成员名 → 值）。

```java
// 概念上的等价实现（真实实现在 JDK 内部，这里是为了理解）
class AnnotationInvocationHandler implements InvocationHandler {
    private final Map<String, Object> memberValues;   // {"name" -> "vic", "year" -> 2026}

    public Object invoke(Object proxy, Method method, Object[] args) {
        switch (method.getName()) {
            case "equals":         // 逐成员比较，且要求注解类型相同
            case "hashCode":       // 成员名 hash 与值 hash 的异或和（JLS 明确规定）
            case "toString":       // @Author(name=vic, year=2026)
            case "annotationType": return special(method, proxy, args);
            default:               // 其余方法直接查 Map，取不到就回落到注解默认值
                Object v = memberValues.get(method.getName());
                return v != null ? v : method.getDefaultValue();
        }
    }
}
```

由此可以推出几个**很能体现理解的结论**：

| 结论 | 原因 |
| --- | --- |
| `author.name()` 每调用一次只查一次 Map，没有"解析开销" | 值在类加载时就解析好放进 Map 了 |
| 相同注解在不同元素上是不同的代理对象，但 `equals` 相等 | `AnnotationInvocationHandler.equals` 按成员值比较 |
| 注解的 `hashCode` 有明确定义（成员名 hash 与值 hash 的异或和） | JLS 规定，所以可以安全地放进 `HashSet` |
| 注解不能有 `throws`、不能有参数、不能是泛型方法 | 接口方法被规定不能带参数/类型参数（编译器强制） |
| 注解成员类型受限 | 只能是基本类型、`String`、`Class`、枚举、注解、以及它们的数组 |
| 注解实例是**不可变**的 | 代理背后的 Map 不暴露修改入口 |
| 运行时改注解值只能靠改这个 Map（JDK 不允许） | 这也是为什么"动态修改注解"必须用字节码/反射黑魔法 |

> [!important] 面试标准答法
> "注解在字节码层面就是一个继承了 `java.lang.annotation.Annotation` 的接口，成员是抽象方法，默认值存在 `AnnotationDefault` 属性里。运行期 JVM 为每个使用点生成一个实现了该接口的**动态代理**，handler 内部是一个成员名到值的 Map；调用注解成员方法其实就是查这个 Map，`equals`/`hashCode`/`toString`/`annotationType` 被 handler 特殊处理。"

### 5.3 自定义注解 + 反射读取的完整示例

```java
// 1) 定义注解
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface RateLimit {
    int permitsPerSecond() default 100;
    String key() default "";
}

// 2) 使用
public class OrderApi {
    @RateLimit(permitsPerSecond = 50, key = "create-order")
    public void createOrder() { }
}

// 3) 读取并生效（简化版 AOP 的 Advisor 匹配）
public class RateLimitProcessor {
    public void register(Object bean) throws Exception {
        for (Method m : bean.getClass().getDeclaredMethods()) {
            if (m.isBridge() || m.isSynthetic()) continue;          // 过滤编译器产物
            RateLimit rl = m.getAnnotation(RateLimit.class);
            if (rl == null) continue;
            String key = rl.key().isEmpty() ? m.getName() : rl.key();
            limiterRegistry.register(key, rl.permitsPerSecond());   // 真正干活的代码
        }
    }
}
```

**Spring 里同一件事的真实形态**：`@Transactional` → `AnnotationTransactionAttributeSource` 读取注解 → 生成 `TransactionInterceptor` → 包成 `Advisor` → `BeanPostProcessor` 给 Bean 生成代理。注解本身什么都不做，**是 `BeanPostProcessor` + AOP 让它生效**（详见 [[13-Spring源码骨架]]）。

### 5.4 注解在 Spring / MyBatis / Lombok 中的角色

| 框架 | 注解 | Retention | 谁在什么时候读 |
| --- | --- | --- | --- |
| Spring | `@Component`/`@Service` | RUNTIME | `ClassPathScanningCandidateComponentProvider` 扫描类路径时读（`MetadataReader`，实际走 ASM 读字节码而非反射，性能更好） |
| Spring | `@Autowired`/`@Qualifier` | RUNTIME | `AutowiredAnnotationBeanPostProcessor` 在实例化后注入 |
| Spring | `@Transactional` | RUNTIME | `BeanPostProcessor` 阶段匹配 Advisor，运行期由事务拦截器读 |
| Spring | `@Configuration` | RUNTIME | `ConfigurationClassPostProcessor`（`BeanDefinitionRegistryPostProcessor`）；被 CGLIB 增强以拦截 `@Bean` 方法 |
| Spring | `@RequestMapping` | RUNTIME | `RequestMappingHandlerMapping` 启动时扫描并建立 URL → 方法的映射表 |
| MyBatis | `@Mapper`/`@Select` | RUNTIME | `MapperScannerConfigurer` 扫描接口；方法上的 SQL 注解在 `MapperAnnotationBuilder` 里解析 |
| MyBatis | — | — | Mapper 接口的实现由 **JDK 动态代理**（`MapperProxy`）在运行期生成 |
| Lombok | `@Data`/`@Builder`/`@Slf4j` | **SOURCE** | **编译期**由注解处理器直接修改 AST，生成代码后注解被丢弃 |
| Jackson | `@JsonProperty` | RUNTIME | 序列化/反序列化时读取 |
| JUnit 5 | `@Test`/`@BeforeEach` | RUNTIME | 测试引擎反射扫描 |

> [!warning] Lombok 与"运行时注解"是两种完全不同的机制
> - **运行时注解**（Spring/MyBatis）：注解保留到运行期，靠反射读，靠框架代码产生行为。
> - **Lombok**：`RetentionPolicy.SOURCE`，运行期**完全消失**。它在**编译期**通过 javac 的注解处理机制 + 内部 API 直接**修改抽象语法树**，把 `getter`/`setter`/构造器"写"进字节码。
>
> 这也是 Lombok 的几个著名副作用的原因：
> - 需要 IDE 插件支持（否则 IDE 看到的是"没有 getter 的类"）；
> - 依赖 javac 内部实现，JDK 升级容易不兼容（虽然现在支持良好）；
> - 调试时"断点跳到了不存在的方法"；
> - **不要用它生成 `equals/hashCode` 参与 JPA 实体主键比较**（`@Data` 在双向关联上会导致无限递归 `toString`/`hashCode`）。

### 5.5 注解处理器（APT）

**编译期读取注解的标准机制**：

```java
@SupportedAnnotationTypes("com.example.Builder")
@SupportedSourceVersion(SourceVersion.RELEASE_17)
public class BuilderProcessor extends AbstractProcessor {
    @Override
    public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment env) {
        for (Element e : env.getElementsAnnotatedWith(Builder.class)) {
            // 生成代码：processingEnv.getFiler().createSourceFile(...)
        }
        return true;   // 声明已处理，避免其他处理器重复处理
    }
}
```

**关键机制**：

| 概念 | 说明 |
| --- | --- |
| `Round`（轮次） | 编译器反复调用处理器，直到没有新的源文件产生为止。生成的代码又会被处理，所以要防死循环 |
| `ProcessingEnvironment` | 提供 `Filer`（写文件）、`Messager`（报错/警告）、`Elements`/`Types`（模型查询） |
| 注册方式 | `META-INF/services/javax.annotation.processing.Processor`，或用 `@AutoService` 生成 |
| 保留策略 | 处理器读的注解通常是 `SOURCE` 或 `CLASS`，处理完就丢弃 |

**与运行期反射的关键区别**：

| 维度 | APT（编译期） | 运行期反射 |
| --- | --- | --- |
| 时机 | 编译时 | 运行时 |
| 性能开销 | **零**（代码已生成并编译进 class） | 每次反射调用都有开销 |
| 能力 | 生成新源码/资源；能访问完整的类型信息 | 只能读运行期存在的信息 |
| 典型用户 | Lombok、MapStruct、Dagger、AutoValue、Room | Spring、MyBatis、Jackson |
| 局限 | 看不到运行期状态；不能修改已有类的字节码（Lombok 是**打了 javac 内部的擦边球**） | 受强封装限制；有性能成本 |

> [!tip] MapStruct 是"用 APT 消灭反射"的范例
> 属性拷贝如果用 `BeanUtils.copyProperties`（反射），大对象上性能差；MapStruct 在编译期为每个映射生成**直接的 `setter`/`getter` 调用**，运行期零反射。这也是选型时"高性能映射"的标准答案。

## 六、动态代理

### 6.1 JDK 动态代理

**前提**：目标**必须实现至少一个接口**。生成的代理类是接口的实现类。

```java
public interface UserService {
    String findName(long id);
}

public class UserServiceImpl implements UserService {
    public String findName(long id) { return "u" + id; }
}

public class TimingHandler implements InvocationHandler {
    private final Object target;
    public TimingHandler(Object target) { this.target = target; }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        long t0 = System.nanoTime();
        try {
            return method.invoke(target, args);           // 转发给真实对象
        } catch (InvocationTargetException e) {
            throw e.getCause();                           // 别把异常包一层丢掉
        } finally {
            System.out.printf("%s -> %d ns%n", method.getName(), System.nanoTime() - t0);
        }
    }
}

UserService proxy = (UserService) Proxy.newProxyInstance(
        UserService.class.getClassLoader(),
        new Class<?>[]{ UserService.class },              // 代理要实现的接口集合
        new TimingHandler(new UserServiceImpl()));
proxy.findName(1);
```

**实现要点（高频追问）**：

| 问题 | 答案 |
| --- | --- |
| 代理类是怎么来的？ | JDK 8：`ProxyGenerator` 用 `sun.misc.ProxyGenerator.generateProxyClass()` 生成字节码（类名形如 `com.sun.proxy.$Proxy0`），再 `defineClass`。JDK 9+：为适配模块系统，代理类被定义在**动态模块**（如 `jdk.proxy1`）中，核心语义不变 |
| 代理类长什么样？ | `public final class $Proxy0 extends Proxy implements UserService`，每个接口方法体是 `super.h.invoke(this, m3, new Object[]{...})` |
| 为什么必须基于接口？ | 代理类**已经 `extends Proxy`**，Java 单继承，无法再继承目标类。这是语言层面的硬约束 |
| `equals`/`hashCode`/`toString` 也会被拦截吗？ | **会**。所以在 `invoke` 里对 `proxy` 调用 `toString()` 会递归死循环；日志里打印 `proxy` 要小心 |
| 能代理 `final` 方法吗？ | 接口方法不存在 "final"（接口方法都是抽象/默认），可以代理。但 `final` **类**不能被代理（不是接口） |
| 异常怎么传？ | `method.invoke` 把目标异常包进 `InvocationTargetException`，必须 `getCause()` 并原样抛出，否则业务异常类型（如 `@Transactional` 回滚依赖的 `RuntimeException`）会变味 |
| 代理对象的 `getClass()` | 是 `$ProxyN`，不是目标类；`instanceof` 要用接口判断 |

### 6.2 CGLIB

**原理**：用 ASM 在运行期生成目标类的**子类**，子类重写目标方法并在其中回调 `MethodInterceptor`。

```java
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserServiceImpl.class);        // 继承目标类
enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
    long t0 = System.nanoTime();
    try {
        return proxy.invokeSuper(obj, args);          // 调 super，即原实现
    } finally {
        System.out.println(method.getName() + " cost " + (System.nanoTime() - t0));
    }
});
UserServiceImpl p = (UserServiceImpl) enhancer.create();   // 无参构造 → 调用父类无参构造器
```

| 限制 | 说明 |
| --- | --- |
| `final` 类不能被代理 | 无法生成子类 |
| `final` / `private` / `static` 方法不能被拦截 | 无法重写 |
| 需要能调用父类构造器 | 所以 Spring 用 **Objenesis** 绕过（不依赖无参构造器）就能创建代理实例 |
| 生成类更重 | 类数量、Metaspace 占用、首次生成耗时都高于 JDK 代理 |
| 不能代理包可见性问题 | 需要注意生成的代理类与目标类的包/模块可见性 |

### 6.3 对比与选型

| 维度 | 静态代理 | JDK 动态代理 | CGLIB |
| --- | --- | --- | --- |
| 接口要求 | 无（手写实现接口） | **必须有接口** | 无（基于继承） |
| 类要求 | 无 | 无 | **不能 final**；方法不能 final/private/static |
| 类数量 | 手写一个 | 一个 `$ProxyN` 可代理同一接口集合 | 每个目标类一个生成子类 |
| 是否走构造器 | 手写 | 不调目标构造器（无目标实例，只是转发） | 需要（可用 Objenesis 绕过） |
| 自调用（`this.f()`） | 不经过代理 | 不经过代理 | 不经过代理 |
| 性能（现代 JDK） | 最快（编译期确定） | 与 CGLIB 基本相当 | 早期 JDK 上通常更快 |
| 与 Spring AOP 的关系 | `AspectJ` 编译期/加载期织入可视为最彻底的"静态代理" | 有接口时的默认选择 | 无接口时；或 Spring Boot 默认（`proxyTargetClass=true`） |

> [!important] Spring 的选择逻辑
> 1. 目标类实现了接口且未强制 `proxyTargetClass` → 用 **JDK 动态代理**（历史默认）。
> 2. 目标类没有接口 → 用 **CGLIB**。
> 3. `proxyTargetClass=true`（Spring Boot 的 AOP 自动配置默认如此） → **强制 CGLIB**。
>
> Spring Boot 之所以默认 CGLIB：避免"按具体类注入时拿到 JDK 代理导致 `ClassCastException`/`BeanNotOfRequiredTypeException`"这类常见坑。代价是**目标类不能是 `final`、方法不能是 `final`**。详见 [[13-Spring源码骨架]]。

> [!danger] 三个必踩的坑
> 1. **自调用失效**：同类内 `this.other()` 直接走原始对象，不经过代理，`@Transactional`/`@Cacheable`/`@Async` 全部失效。修复：把方法拆到另一个 Bean、注入自身代理、或 `AopContext.currentProxy()`（需 `exposeProxy=true`）。
> 2. **`final` 方法静默失效**：CGLIB 场景下注解不生效，且**不报错**。
> 3. **异常吞掉**：`InvocationHandler` 里没有 `getCause()` 就 `throw new RuntimeException(e)`，会让 `@Transactional` 的 rollbackFor 判断错类型，事务该回滚却没回滚。

## 七、类加载与反射的关系（简述）

反射的所有入口都来自 `Class` 对象，而 `Class` 对象由**类加载器**产生：

```text
ClassLoader.loadClass(name)
   → findLoadedClass（已加载则直接返回）
   → parent.loadClass（双亲委派）
   → findClass(name)（自定义加载器重写这里）
   → defineClass(name, bytes, 0, len)   ← JVM 在此创建 Class 对象
```

| 要点 | 说明 |
| --- | --- |
| 每个类加载器 + 类名 = 唯一的 `Class` 对象 | 同一个类被两个加载器加载会得到两个 `Class`，**==** 为 false，`instanceof` 也可能失败 |
| 双亲委派 | 先委托父加载器，父加载器加载不了才自己加载。保证 `java.lang.String` 全局唯一 |
| 打破双亲委派的场景 | Tomcat 的 `WebappClassLoader`（webapp 优先）、OSGi、JDBC SPI（用线程上下文类加载器 `Thread.currentThread().getContextClassLoader()` 反向委托） |
| 反射与加载器的交互 | `Class.forName(name, true, loader)` 用指定加载器；`Proxy.newProxyInstance(loader, ...)` 的 loader 决定代理类可见性 |

类加载的完整生命周期、双亲委派细节、Metaspace、卸载条件见 [[7-JVM内存与GC]]，类加载异常的排查见 [[8-JVM调优与故障排查]]。

## 八、常见陷阱

### 8.1 泛型擦除导致 `ClassCastException` 延迟暴露

```java
public class HeapPollution {
    static void pollute(List<String> list) {
        List raw = list;              // 用 raw type 绕过检查（只会有 unchecked 警告）
        raw.add(42);                  // 塞进一个 Integer
    }

    public static void main(String[] args) {
        List<String> list = new ArrayList<>();
        pollute(list);                // 此处没有任何异常
        System.out.println("污染成功，还没炸");

        // 直到这里才炸，而且栈里看不到 pollute 的调用点
        for (String s : list) {       // 隐式 checkcast 在这里
            System.out.println(s);
        }
    }
}
// 输出：污染成功，还没炸
// java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String
```

**为什么延迟**：擦除后 `List.add` 接受 `Object`，插入不会检查；`checkcast String` 是编译器在**读取处**插入的，所以只有读的时候才炸。**这是所有泛型事故的共同形态：写入点无感，读取点爆炸，且栈信息指向的是受害者而不是凶手。**

**规避**：

| 做法 | 说明 |
| --- | --- |
| 用 `List<?>` 而不是 raw `List` 做参数 | 写操作编译期就被拦下 |
| 保持编译**零警告**，`-Werror` + `-Xlint:unchecked` | 把 unchecked 警告当错误处理 |
| 泛型集合作为 API 参数时用 `Collections.checkedList` | 运行期在写入点就检查类型 |
| 需要"运行期类型"时显式传 `Class<T>` | `new TypeToken<List<Order>>(){}` 或 `Class<T>` 参数 |

### 8.2 `setAccessible` 在 JDK 16+ 的强封装限制

见 4.6。要点：`InaccessibleObjectException` 不是 bug，是设计；优先升级框架，其次才是 `--add-opens`；`trySetAccessible()` 用来做能力探测。

```java
Field f = SomeClass.class.getDeclaredField("x");
if (f.trySetAccessible()) {          // 不抛异常的探测
    Object v = f.get(obj);
} else {
    // 降级路径：走公开 API、或明确报错提示需要 --add-opens
}
```

### 8.3 `getDeclaredFields` 的顺序不保证

**JLS/Javadoc 没有承诺**字段的返回顺序。HotSpot 通常按声明顺序返回，但：

- 不同 JVM 实现、不同版本行为可能不同；
- 编译期优化/字节码工具处理后顺序可能变；
- **不要把顺序当契约**。

```java
// 危险：依赖字段顺序做 CSV 列映射
Field[] fields = clazz.getDeclaredFields();
for (int i = 0; i < fields.length; i++) {
    columns[i] = fields[i].get(obj);      // 哪天顺序变了就静默错列
}

// 正确：用注解显式声明顺序
class User {
    @Column(order = 0) private Long id;
    @Column(order = 1) private String name;
}
```

同理，`@Autowired` 字段注入的**顺序**、多个 `BeanPostProcessor` 的执行顺序、`Set` 里 Bean 的迭代顺序，都不应依赖；需要顺序就显式声明（`@Order`、`Ordered` 接口）。

### 8.4 `@Retention(CLASS)` 运行时读不到

见 5.1。**自定义注解忘记写 `@Retention(RUNTIME)`** 是最常见的"注解静默失效"。

排查手段：`javap -v YourClass` 看 `RuntimeVisibleAnnotations`（RUNTIME）与 `RuntimeInvisibleAnnotations`（CLASS）：

```text
RuntimeInvisibleAnnotations:          ← CLASS 保留，反射读不到
  0: #33(#34=s#35)
```

### 8.5 `Method.invoke` 的异常被包一层

```java
try {
    method.invoke(target, args);
} catch (InvocationTargetException e) {
    throw e.getCause();               // 必须解包，否则业务异常类型丢失
}
```

`@Transactional` 默认只对 `RuntimeException` 回滚；如果把业务异常包成 `RuntimeException`，回滚行为可能"看起来对"，但如果包成受检异常，**事务不会回滚**——这是极为常见的生产事故。

### 8.6 反射 `Method` 对象缓存时的类加载器泄漏

把 `Class`/`Method` 缓存进**静态 Map** 时，key 若是 `Class` 对象，会阻止该类的类加载器被回收。

```java
// 危险：Tomcat 热部署时，webapp 的 ClassLoader 无法回收 → Metaspace OOM
private static final Map<Class<?>, Object> CACHE = new ConcurrentHashMap<>();

// 缓解：
// 1) key 用类名字符串而不是 Class 对象（配合弱引用）
// 2) 用 ClassValue（JDK 7+，专为"类级别的缓存"设计，随类卸载而自动清理）
private static final ClassValue<Method> METHODS = new ClassValue<>() {
    @Override protected Method computeValue(Class<?> type) { return lookup(type); }
};
```

`ClassValue` 是 JDK 提供的正确解法：它内部用弱引用关联 `Class`，类卸载时缓存项自动失效。

### 8.7 陷阱速查表

| # | 陷阱 | 现象 | 规避 |
| --- | --- | --- | --- |
| 1 | raw type 混用 | `ClassCastException` 在读取处才炸 | 保持零 unchecked 警告 |
| 2 | 泛型数组/可变参数 | 堆污染，编译警告被忽略 | 加 `@SafeVarargs`（静态/final/private 方法）并确认实现安全 |
| 3 | `@Retention` 默认 CLASS | 注解反射读不到，静默失效 | 显式 `RUNTIME` |
| 4 | 桥接方法未过滤 | 框架里同一方法被处理两次 | `isBridge()` / `isSynthetic()` 过滤 |
| 5 | `getDeclaredFields` 顺序 | 列映射错位 | 注解显式声明顺序 |
| 6 | `InvocationTargetException` 未解包 | 业务异常类型丢失、事务不回滚 | `getCause()` 原样抛出 |
| 7 | 自调用不进代理 | `@Transactional` 失效 | 拆 Bean / 注入自身代理 |
| 8 | CGLIB + `final` | 注解静默失效 | 别用 final 类/方法，或用接口 + JDK 代理 |
| 9 | `setAccessible` 被拒 | JDK 16+ `InaccessibleObjectException` | 升级框架；`--add-opens` 兜底；`trySetAccessible` 探测 |
| 10 | `Class.forName` 触发初始化 | 静态块副作用、驱动重复注册 | 用 `forName(name,false,loader)` 或 `loadClass` |
| 11 | 静态缓存 `Class`/`Method` | 类加载器泄漏、Metaspace OOM | 用 `ClassValue` 或弱引用 |
| 12 | 反射热点未缓存 | CPU 飙高、GC 压力 | 缓存句柄 + 一次 `setAccessible` + 考虑 MethodHandle |
| 13 | `List<int>` 不存在 | 装箱开销 | 高吞吐场景考虑基本类型特化库或数组 |

## 九、面试速查

> [!question] 高频追问链
> 1. **什么是类型擦除？擦成什么？**
>    → 无界擦成 `Object`，有界擦成第一个上界；编译器插入 `checkcast`；`Signature` 属性保留泛型签名。
> 2. **为什么 Java 用擦除？**
>    → 向后二进制兼容：`List<E>` 擦除后必须就是老的 `List.add(Object)`；JVM 几乎不用改；零代码膨胀。代价：运行期无类型实参、不能 `new T[]`、基本类型要装箱。
> 3. **PECS 是什么？**
>    → Producer Extends, Consumer Super。读用 `extends`，写用 `super`；判断依据是"数据流向"。
> 4. **桥接方法是什么？为什么需要？**
>    → 擦除让源码上的重写变成字节码上的两个不同方法；编译器生成 `ACC_BRIDGE|ACC_SYNTHETIC` 的转发方法，带 `checkcast`，把擦除签名转调到真实实现，从而保住 vtable 多态。协变返回类型同样会生成桥接方法。
> 5. **`Class.forName` 和 `ClassLoader.loadClass` 的区别？**
>    → 前者默认 `initialize=true`，执行静态块；后者不初始化。
> 6. **反射为什么慢？怎么优化？**
>    → 间接调用难内联 + 每次 `getMethods` 拷贝 + 参数装箱 + 异常包装；优化 = 缓存句柄、一次 `setAccessible`、必要时 MethodHandle；较新 JDK 用方法句柄重写了核心反射，性能更稳定。
> 7. **注解的本质是什么？**
>    → 接口（继承 `Annotation`）+ 运行期由 `AnnotationInvocationHandler` 支持的动态代理，成员值存在 Map 里，`AnnotationDefault` 提供默认值。
> 8. **JDK 动态代理和 CGLIB 的区别与选型？**
>    → 接口 vs 继承；`final` 限制；Spring 的选择规则；Spring Boot 默认 CGLIB 的原因。
> 9. **`@Retention(CLASS)` 的注解能读吗？**
>    → 不能。它在 class 文件里（`RuntimeInvisibleAnnotations`），只给编译器/字节码工具用。
> 10. **怎么在运行期拿到 `List<Order>` 的 `Order`？**
>    → 局部变量里拿不到。必须把泛型信息写进签名（字段/方法返回值/父类），用 `ParameterizedType`、`TypeToken`、`ResolvableType` 读。
