## 一、三大特性深挖

### 1.1 封装：边界在哪

封装的目标不是"所有字段都加 `getter/setter`"，而是**让不变量（invariant）无法被破坏**。

```java
// 反例：getter/setter 全裸 → 等于 public 字段，一封装都没封
public class Order {
    private BigDecimal amount;
    public BigDecimal getAmount() { return amount; }
    public void setAmount(BigDecimal v) { this.amount = v; }   // 允许负数！
    public List<Item> getItems() { return items; }             // 交出内部集合引用！
}
```

| 反模式 | 后果 | 修复方向 |
| --- | --- | --- |
| 无脑 getter/setter | 外部可以把对象改成非法状态 | 去掉不必要的 setter；用有业务含义的方法（`pay()`、`cancel()`） |
| 返回可变内部集合 | 外部可随意增删，绕过校验 | 返回 `List.copyOf(...)` / `Collections.unmodifiableList` / 防御性拷贝 |
| 返回可变内部对象 | 外部改其字段 | 内部对象也做成不可变，或返回副本 |
| 构造器/方法不校验参数 | 非法状态流进系统深处才炸 | 入口处 `Objects.requireNonNull` + 业务校验，失败即抛 `IllegalArgumentException` |
| 暴露实现类型 | 换实现即破坏兼容 | 返回接口/抽象类型 |

> [!tip] 封装的现代判据
> 问自己：**"如果外部只能通过我暴露的方法操作这个对象，我能不能保证它永远处于合法状态？"** 能，才叫封装。
> Java 的记录类（`record`）给了另一个极端答案：全字段不可变 + 自动 `equals/hashCode/toString`，从语言层面消灭"裸 setter"。

### 1.2 继承的问题：为什么"组合优于继承"

**继承是最强的耦合**。子类依赖父类的**实现细节**，而不仅仅是接口。

```java
// 经典反例：HashSet 没有"统计插入次数"的语义，用继承实现就会出错
public class CountingSet<E> extends HashSet<E> {
    private int addCount = 0;
    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }
}
```

问题：`HashSet.addAll` 的**实现**内部是循环调用 `add`，于是 `addAll` 一次调用把计数加了两遍。这是 Josh Bloch 的经典例子，根因是**子类假设了父类的实现方式**，而父类的实现是私有细节，随时可能变。

```java
// 正解：组合 + 转发
public class CountingSet<E> implements Set<E> {
    private final Set<E> delegate = new HashSet<>();
    private int addCount = 0;
    @Override public boolean add(E e) { addCount++; return delegate.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size(); return delegate.addAll(c);
    }
    // ...其余方法转发（或用 Guava 的 ForwardingSet 省掉样板）
}
```

| 维度 | 继承 | 组合 |
| --- | --- | --- |
| 耦合度 | 强（依赖父类实现） | 弱（只依赖接口） |
| 封装 | 破坏（`protected` 成员暴露给子类） | 保持 |
| 运行期替换 | 不可能 | `setDelegate(...)` 可换 |
| 方法冲突 | 父类新增方法可能撞子类方法 | 无 |
| 复用粒度 | 整个类 | 只复用需要的那部分 |
| 适用 | 真正的 is-a + 父类**为继承而设计**（有文档、有钩子、构造器自用安全） | 绝大多数"想复用代码"的场景 |

> [!important] 判断标准
> **"子类是不是父类的一种（is-a）"不够。** 还要问：父类的作者是否为继承做了设计（文档说明可重写的方法、允许调用的钩子、不暴露内部实现）？
> 如果父类只是一个"恰好有些方法能用"的类，就用组合。
> **实践法则：优先组合、优先接口。继承只用于"框架的回调契约"（如 `HttpServlet`、`AbstractList`）或真正的类型层级。**

### 1.3 多态的代价

多态本身不慢（vtable 索引是常数级），代价在三处：

| 代价 | 说明 | 缓解 |
| --- | --- | --- |
| **无法静态内联** | 直到 JIT 观察到单态/双态才能内联；超多态（megamorphic）退回查表 | 热路径控制同一调用点的实现种类数 |
| `invokeinterface` 比 `invokevirtual` 贵 | 需要 itable 查找（现代 JIT 会缓存） | 影响很小，不要为此牺牲设计 |
| 语义成本 | 调试要追到实际类型；"grep 方法名"找不到调用者 | 良好命名 + IDE 的 "Find Usages" / "Call Hierarchy" |

真正需要警惕的是**把多态用在数据上**：为每种类型建一个子类，只为了区分"类型标签"，而不是行为差异。这时用枚举 + 策略表更合适。

## 二、抽象类 vs 接口（DEEP）

### 2.1 能力对照表

| 维度 | 抽象类 | 接口 |
| --- | --- | --- |
| 关键字 | `abstract class` | `interface` |
| 能否有构造器 | **有**（供子类 `super()` 调用，不能 `new`） | **没有** |
| 实例字段 | 可以（任意访问级别） | 只能有 `public static final` 常量（隐式） |
| 静态方法 | 可以 | Java 8 起可以；Java 9 起可以 `private static` |
| 默认方法 | 无此概念（本来就是具体方法） | Java 8 起 `default`；Java 9 起 `private` 供内部复用 |
| 方法访问级别 | 任意 | 隐式 `public`（`default`/`static`/`private` 除外） |
| 继承/实现数量 | 类只能 `extends` **一个** | 可以 `implements` **多个**；接口可以 `extends` 多个接口 |
| 多态分派 | vtable | itable（`invokeinterface`） |
| 能否有自己的状态 | 能 | **不能**（只能靠静态常量） |
| 设计语义 | **is-a**，共享实现与状态 | **can-do**，声明能力契约 |
| 演进性 | 加具体方法安全、加抽象方法破坏所有子类 | 加 `default` 方法**相对**安全；加抽象方法破坏所有实现类 |

> [!note] 接口字段的"隐式"细节
> ```java
> interface C {
>     int X = 1;                          // 隐式 public static final
>     void f();                           // 隐式 public abstract
>     default void g() {}                 // Java 8
>     static void h() {}                  // Java 8
>     private void k() {}                 // Java 9，仅接口内部可调用
>     private static void m() {}          // Java 9
> }
> ```
> `X` 是**编译期常量**，用它的代码会被内联（见 [[1-语言基础与面向对象]] 的 `static final` 内联陷阱）。

### 2.2 default 方法与"菱形继承"冲突解决

Java 8 让接口可以有方法体，等价于引入了 C++ 的多重继承问题。JLS 给了三条**优先级规则**：

1. **类优先**：类（或其父类）中的具体方法，优先于任何接口的 `default` 方法。
2. **更具体的接口优先**：若 `interface B extends A`，则 `B` 的 `default` 胜过 `A` 的。
3. **仍然冲突 → 编译错误**：实现类必须显式重写，并用 `接口名.super.方法()` 指定调用哪一个。

```java
interface A { default String hello() { return "A"; } }
interface B { default String hello() { return "B"; } }

class C implements A, B {
    @Override public String hello() { return A.super.hello() + B.super.hello(); }  // 必须显式
}

interface D extends A { @Override default String hello() { return "D"; } }
class E implements D, A {}       // OK：D 更具体，选 D 的实现
// class F implements A, B {}    // 编译错误：inherits unrelated defaults for hello()
```

真实的菱形场景：一个类实现了 `Collection` 和某个自定义接口，两者都有 `default removeIf` 之类的方法，或者 `List` 与 `Set` 同时被一个类实现时的 `spliterator`。

> [!warning] default 方法不是"多重继承"
> 接口仍**不能有实例状态**。所以 `default` 方法只能在其他抽象方法之上做编排，无法维护"每个实现类各自的计数器"——需要状态就必须用抽象类或组合。

### 2.3 什么时候用哪个

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 多个实现共享**状态 + 骨架流程** | 抽象类 | 模板方法需要 `protected` 钩子 + 字段 |
| 声明"具备某种能力"（`Comparable`、`Serializable`、`Closeable`） | 接口 | can-do，且一个类需要多种能力 |
| 需要被**多个不相关**的类实现 | 接口 | 抽象类会占掉唯一的继承名额 |
| 需要**演进**已有类型体系，向后兼容地加方法 | 接口 + `default` | 加抽象方法会打断所有实现类（Java 8 给 `Collection` 加 `stream()` 就是靠 default） |
| 框架回调（`HttpServlet`、`AbstractList`） | 抽象类 | 提供大量默认实现 + 少量抽象钩子 |
| 需要 `private` 辅助方法且不想污染 API | Java 9 接口 `private` 或抽象类 | 都行，接口更轻 |

> [!tip] 组合拳：接口声明契约 + 抽象类提供骨架
> 标准做法是**接口 + 抽象基类**（`Skeletal Implementation`）：
> `List`（接口）+ `AbstractList`（骨架）；`Set` + `AbstractSet`；`Comparator` + `Comparator` 的静态工厂。
> 这样既保留了"多实现"的自由，又给实现者省掉样板代码。**如果你想同时给"能力"和"骨架"，就写两个类型。**

## 三、重载与重写的规则边界

### 3.1 重载解析的完整顺序

编译期按**三个阶段**依次尝试，任一步找到唯一可行方法就停止（详见 [[1-语言基础与面向对象]] 的静态分派一节）：

| 阶段 | 允许的转换 | 例子 |
| --- | --- | --- |
| 1. 严格调用（不装箱） | 子类型向上转型、基本类型拓宽 | `f(long)` 接受 `int` |
| 2. 宽松调用（允许装箱/拆箱） | 装箱、拆箱、再拓宽 | `f(Object)` 接受 `int`（经 `Integer`） |
| 3. 可变参数调用 | `T...` | `f(int...)` |

```java
static void f(long x)    { print("long"); }
static void f(Integer x) { print("Integer"); }
f(1);                                  // long（阶段 1 拓宽 ＞ 阶段 2 装箱）

static void g(Object o)  { print("Object"); }
static void g(int... a)  { print("varargs"); }
g(1);                                  // Object（装箱在阶段 2，先于阶段 3）
```

**三条硬规则**：

1. **返回类型不参与重载**。同一类中 `int f()` 与 `String f()` 是编译错误（虽然 JVM 层面 descriptor 包含返回类型，能区分）。
2. **泛型擦除后签名相同 → 编译错误**。`void f(List<String>)` 与 `void f(List<Integer>)` 不能共存（详见 [[3-泛型反射与注解]]）。
3. **`null` 参数的歧义**：多个候选类型之间若存在子类型关系，选**最具体**的；若互不相关，编译错误。

```java
static void p(String s) {}
static void p(Object o) {}
p(null);              // → String（String 是 Object 的子类型，更具体）

static void q(String s) {}
static void q(Integer i) {}
q(null);              // 编译错误：reference to q is ambiguous
```

> [!danger] 最贵的重载 bug：`equals`
> ```java
> public class User {
>     private String name;
>     // 少了 @Override，参数写成 User 而不是 Object → 这是【重载】不是【重写】
>     public boolean equals(User other) { return Objects.equals(name, other.name); }
> }
> ```
> `Object.equals(Object)` 未被覆盖，`HashSet<User>`/`HashMap` 依然用引用相等。**加上 `@Override` 会立刻编译失败**——这就是 `@Override` 最重要的价值。

### 3.2 重写规则表

| 规则 | 允许的变化 | 违反后果 |
| --- | --- | --- |
| 方法名 + 参数列表 | 必须完全相同 | 变成重载（静默失效） |
| 返回类型 | **协变**：可以是父类返回类型的子类型 | 编译错误 |
| 访问权限 | **不能变窄**（可 `protected` → `public`，不能 `public` → `protected`） | 编译错误 |
| 受检异常 | **不能变宽**：可以不抛、抛子类、或抛任意非受检异常 | 编译错误 |
| `final` / `static` / `private` 方法 | 不能被重写 | `static` 是**隐藏（hiding）**，不是重写 |
| 构造器 | 不能被重写 | — |

**协变返回类型会生成桥接方法**：

```java
class Parent { Object get() { return "p"; } }
class Child extends Parent { @Override String get() { return "c"; } }
// javac 在 Child 里额外生成：
//   Object get() { return this.get(); }   ← 加了 ACC_BRIDGE | ACC_SYNTHETIC
```

因为 `Parent.get()` 擦除/原始签名的返回类型是 `Object`，vtable 槽位需要一条返回 `Object` 的入口，桥接方法负责转调。**桥接方法不是泛型专属**，协变返回同样会产生。

**`static` 方法是"隐藏"不是"重写"**：

```java
class P { static void f() { print("P"); } }
class C extends P { static void f() { print("C"); } }

P p = new C();
p.f();     // 输出 P！ 静态方法在编译期按【引用类型】选定
```

> [!warning] 在实例方法里调静态方法，始终看"写在哪个类里"
> 这会导致**工具类里的静态方法无法被多态替换**。Spring 的 `TransactionSynchronizationManager`、`AopUtils` 大量使用静态方法，测试时无法 mock 就是这个原因（需要 PowerMock/`mockStatic` 之类的字节码手段）。设计上，**需要被替换的行为不要写成静态方法**。

### 3.3 `@Override` 的实际价值

1. **编译期校验**：拼错名字、参数类型写错（`equals(User)`）、返回类型不兼容，立刻报错。
2. **防重构漏改**：父类接口改名，所有重写点全部报错，不会静默变成新方法。
3. **可读性**：一眼看出这个方法来自父类型契约。
4. **接口的 `default` 方法也建议加**：能立刻发现"我以为在重写，其实签名不匹配"。

## 四、SOLID 原则

| 原则 | 一句话定义 | 核心症状 | 重构方向 |
| --- | --- | --- | --- |
| **S**RP 单一职责 | 一个类**只有一个变化的理由**（只对一个角色负责） | 类名里有 `And`/`Manager`/`Util`；改 A 功能影响 B 功能 | 按"变化的原因"拆类 |
| **O**CP 开闭 | 对扩展开放，对修改关闭 | 加一个类型要改多处 `if/else`/`switch` | 抽象 + 多态；策略 + 注册表 |
| **L**SP 里氏替换 | 子类型必须能替换父类型而不破坏正确性 | 子类抛 `UnsupportedOperationException`；调用方要 `instanceof` 判断 | 重新审视继承关系，改组合或重构层级 |
| **I**SP 接口隔离 | 客户端不应依赖它不用的方法 | 胖接口 + 大量空实现 | 拆成多个小接口 |
| **D**IP 依赖倒置 | 高层与低层都依赖抽象；抽象不依赖细节 | Service 直接 `new` 具体实现 / 依赖具体工具类 | 面向接口编程 + 构造器注入 |

> [!important] 一句话记住它们的"病灶"
> - SRP 治**"改一处、炸一片"**
> - OCP 治**"每加一个类型就要动老代码"**
> - LSP 治**"父类引用指向子类后行为不对"**
> - ISP 治**"实现类被迫写空方法"**
> - DIP 治**"高层被低层实现绑死、没法换、没法测"**

### 4.1 SRP：不是"只做一件事"

"只做一件事"太模糊。真正的判据是**"谁（哪个角色）会要求这个类改变"**。

```java
// 反例：一个类同时服务三个角色
public class Employee {
    BigDecimal calculatePay() { ... }     // 财务部门要改
    String   reportHours()   { ... }      // 人事部门要改
    void     save()          { ... }      // DBA/持久化要改
}
```

三个角色共用一个类 ⇒ 财务改工时计算 → 意外影响报表 → 需要全量回归。拆成 `PayCalculator` / `HourReporter` / `EmployeeRepository`，各自独立演进。

### 4.2 OCP：反例与重构

```java
// 反例：每加一种支付方式就要改这个方法（而且可能改错已有分支）
public BigDecimal pay(String type, BigDecimal amount) {
    if ("alipay".equals(type))      return amount.multiply(new BigDecimal("0.99"));
    else if ("wechat".equals(type)) return amount;
    else if ("card".equals(type))   return amount.add(new BigDecimal("2"));
    throw new IllegalArgumentException("unknown: " + type);
}

// 重构：策略 + 注册表，新增渠道 = 新增一个类 + 注册，老代码不动
public interface PayChannel { String code(); BigDecimal calc(BigDecimal amount); }

@Component
public class PayChannelRegistry {
    private final Map<String, PayChannel> map;
    public PayChannelRegistry(List<PayChannel> channels) {   // Spring 注入所有实现
        this.map = channels.stream().collect(Collectors.toMap(PayChannel::code, Function.identity()));
    }
    public BigDecimal pay(String code, BigDecimal amount) {
        PayChannel c = map.get(code);
        if (c == null) throw new IllegalArgumentException("unknown: " + code);
        return c.calc(amount);
    }
}
```

> [!warning] OCP 不是"禁止 if"
> 不是所有 `if` 都要消除。`if (obj == null)`、参数校验、三四个**永不增长**的固定分支，写成 `if` 完全合理。
> OCP 的判据是**"这个分支集合会不会持续增长"**。会增长 → 抽象；不会 → 别过度设计。

### 4.3 LSP：契约不能被悄悄削弱

LSP 的形式化表述（Bertrand Meyer）：

- **前置条件不能加强**（子类不能要求更多）
- **后置条件不能减弱**（子类不能保证更少）
- **不变量必须保持**
- **历史约束（history constraint）**：子类不能允许父类禁止的状态变化

**正方形继承矩形的经典反例**：

```java
class Rectangle {
    protected int w, h;
    public void setWidth(int w)  { this.w = w; }
    public void setHeight(int h) { this.h = h; }
    public int area() { return w * h; }
}
class Square extends Rectangle {
    @Override public void setWidth(int w)  { this.w = this.h = w; }   // 被迫同时改高
    @Override public void setHeight(int h) { this.w = this.h = h; }
}

void test(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;      // Square 传进来时 → 16，断言失败
}
```

数学上"正方形是矩形"，但**行为契约上不是**：`Rectangle` 隐含的后置条件是"改宽不影响高"，`Square` 削弱了它。

> [!tip] 为什么这个反例重要
> 它证明 **is-a 必须按"行为契约"判断，不能按"现实世界分类"判断**。
> 修复方向：
> 1. 让 `Rectangle` **不可变**（`withWidth()` 返回新对象）→ 可变性契约消失，正方形可以安全继承。
> 2. 抽取公共接口 `Shape { int area(); }`，两者平级。
> 3. 用组合：`Square` 内部持有一个 `Rectangle`。

**Java 标准库里的 LSP 争议**：

| 例子 | 是否违反 | 说明 |
| --- | --- | --- |
| `Collections.unmodifiableList(list).add(...)` | 有争议 | 父类 `List` 的 `add` 契约没有承诺"一定成功"，返回不可变列表是合法实现；但调用方通常假设可写，因此是**实践上的** LSP 破坏 |
| `Arrays.asList(...).add(...)` | 同上 | 定长视图 |
| 数组协变 `Object[] a = new String[1]; a[0] = 1;` | **确实违反** | 编译期通过，运行期 `ArrayStoreException` —— 协变数组是 Java 的类型系统缺陷 |
| `List<Integer>.add(null)` vs `List.of()` | 同上 | 不可变集合拒绝 null |

### 4.4 ISP：接口要小而专

```java
// 反例：胖接口
public interface Worker {
    void work();
    void eat();
    void sleep();
}
// 机器人实现类被迫写：
class Robot implements Worker {
    public void work()  { ... }
    public void eat()   { throw new UnsupportedOperationException(); }
    public void sleep() { throw new UnsupportedOperationException(); }
}
```

拆成 `Workable` / `Feedable` / `Sleepable`，或更常见的做法是**按调用方视角拆分**：调用方只需要 `work()`，就只依赖 `Workable`。这样 `Robot` 只需实现一个接口，测试替身也只需实现一个接口。

### 4.5 DIP：依赖倒置

```java
// 反例：高层策略依赖低层细节
public class OrderService {
    private final MySQLOrderRepository repo = new MySQLOrderRepository();  // 写死
    private final AliyunSmsSender sms = new AliyunSmsSender();             // 写死
}

// 正解：高层定义抽象（接口位于高层所属的包里），低层实现它
public interface OrderRepository { void save(Order o); }
public interface Notifier { void send(String to, String msg); }

public class OrderService {
    private final OrderRepository repo;    // 构造器注入
    private final Notifier notifier;
    public OrderService(OrderRepository repo, Notifier notifier) { ... }
}
```

**"倒置"倒的是什么**：传统分层里高层调用低层、编译期依赖低层；DIP 让**低层反过来实现高层定义的接口**，源码依赖方向与调用方向相反。收益是高层可编译、可测试（换内存实现）、可替换（换 DB、换短信厂商）。

> [!example] 在 Spring 里的体现
> `@Autowired` / 构造器注入本身就是 DIP 的基础设施：容器负责把实现"注入"进高层。
> 但要注意：**注入了接口不等于 DIP 做对了**。如果接口是照着某个具体实现 1:1 抠出来的（`MySQLOrderRepository` → `OrderRepository` 方法签名完全一致），那只是换了个名字，抽象仍然泄漏了细节（如返回 MyBatis 的 `Page` 对象）。

## 五、创建型模式

### 5.1 单例的五种写法（速览，深挖见第六节）

| # | 写法 | 线程安全 | 延迟加载 | 防反射 | 防反序列化 | 评价 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 饿汉式 `static final` | 是（类初始化保证） | 否 | 否 | 否（加 `readResolve` 可防） | 最简单，无脑可靠 |
| 2 | 懒汉式 + `synchronized` | 是 | 是 | 否 | 否 | 每次取实例都加锁，**不要用** |
| 3 | DCL + `volatile` | 是 | 是 | 否 | 否 | 经典，但**漏了 volatile 就危险** |
| 4 | 静态内部类 Holder | 是 | 是 | 否 | 否 | 兼顾延迟与简洁，**推荐** |
| 5 | 枚举 | 是 | 是（首次访问时初始化） | **是** | **是** | 最安全，Josh Bloch 推荐 |

```java
// ④ 静态内部类：利用类加载的初始化锁，天然线程安全
public class HolderSingleton {
    private HolderSingleton() {}
    private static class Holder { static final HolderSingleton INSTANCE = new HolderSingleton(); }
    public static HolderSingleton getInstance() { return Holder.INSTANCE; }
}

// ⑤ 枚举：JVM 保证每个枚举常量只被实例化一次
public enum EnumSingleton {
    INSTANCE;
    public void doSomething() { }
}
```

### 5.2 工厂方法 vs 抽象工厂

| 维度 | 工厂方法 | 抽象工厂 |
| --- | --- | --- |
| 意图 | 定义创建对象的接口，让子类决定实例化哪个类 | 创建**一族相关产品**，不指定具体类 |
| 产品数量 | 一种 | 一族（多个相互配套） |
| JDK 例子 | `Collection.iterator()`、`Calendar.getInstance()`、`NumberFormat.getInstance()` | `DocumentBuilderFactory`、`SAXParserFactory`、`TransformerFactory` |
| Spring 例子 | `FactoryBean.getObject()` | `BeanFactory` + 各级 `*Factory` |
| 使用场景 | 调用方不知道/不该知道具体实现类 | 实现需要成套切换（如 XML/JSON 解析器族、跨平台 UI 控件族） |
| 常见误用 | 只为"隐藏一个 `new`"而造工厂，增加了无谓的间接层 | 产品族其实只有一个实现，抽象工厂变成了样板 |

> [!note] 简单工厂不是 GoF 模式
> `if (type.equals("a")) return new A();` 这种"简单工厂/静态工厂"不在 23 种模式里，但它是**最实用**的一种。判断标准：产品族不增长、创建逻辑简单、不需要多态切换实现 → 就用简单工厂，别硬套抽象工厂。

### 5.3 建造者（Builder）

**意图**：把"构造一个复杂对象"的过程与表示分离，支持**分步、可读、可选参数**的构造。

| 场景 | 不用 Builder 的痛 | 用 Builder |
| --- | --- | --- |
| 可选参数多（>4 个） | 构造器爆炸 或 长参数列表全是 `null` | 链式设置，只写需要的 |
| 需要不可变对象 | setter 破坏不可变性 | Builder 收集 → `build()` 一次性构造 final 对象 |
| 需要校验 | 校验散落在 setter | `build()` 统一校验 |
| 需要"同一个模板造多个变体" | 复制粘贴 | `builder.toBuilder()` 派生 |

**真实例子**：

- `StringBuilder` / `StringBuffer`：**宽泛意义**上的 builder（逐步构建字符序列）。
- `Stream.Builder`：`Stream.builder().add(a).add(b).build()`。
- `UriComponentsBuilder`、`WebClient.builder()`、`HttpClient.newBuilder()`。
- **Lombok `@Builder`**：编译期生成静态内部类 `XxxBuilder`（注意它不是运行时注解，见 [[3-泛型反射与注解]]）。
- `AlertDialog.Builder`、`NotificationCompat.Builder`（偏 Android）。

> [!warning] Builder 的代价
> 多一个类、多一次对象分配、`toString`/调试路径变长。**参数少于 4 个时不值得**。另外 Lombok `@Builder` 会让类**失去全参构造器**（除非同时加 `@AllArgsConstructor`），与 Jackson 反序列化、JPA 实体经常打架。

### 5.4 原型（Prototype）

**意图**：通过**复制已有实例**来创建新对象，避免重复昂贵的初始化。

| 实现方式 | 说明 |
| --- | --- |
| `Object.clone` | 原生但坑多（浅拷贝、绕过构造器、需 `Cloneable`），详见 [[1-语言基础与面向对象]] |
| 拷贝构造器 / 静态工厂 | 推荐，语义清晰、能走完整校验 |
| 序列化 | 天然深拷贝，慢，要求 `Serializable` |
| Spring 的 `prototype` scope | "每次 `getBean` 返回新实例"，本质是容器管理的原型 |

**使用场景**：初始化代价高（加载大配置、建复杂对象图）、需要大量相似对象只改少数字段、需要"模板 + 微调"。
**常见误用**：把 `clone` 当深拷贝用（引用字段共享），或者在不必要的地方引入原型模式（普通 `new` 更快）。

## 六、单例模式深挖

### 6.1 DCL 为什么必须加 volatile

```java
public class DclSingleton {
    private static volatile DclSingleton instance;   // volatile 不可省
    private DclSingleton() {}
    public static DclSingleton getInstance() {
        if (instance == null) {                       // 第一次检查（无锁快路径）
            synchronized (DclSingleton.class) {
                if (instance == null) {               // 第二次检查（持锁后再确认）
                    instance = new DclSingleton();
                }
            }
        }
        return instance;
    }
}
```

**`new` 在字节码层面是三条指令**：

```text
new           #2   // 1. 分配内存，字段全为默认值（0/null）
dup
invokespecial #3   // 2. 调用 <init>，执行构造器（字段被赋真实值）
putstatic     #4   // 3. 把引用写入静态字段 instance
```

步骤 2 和 3 **之间没有数据依赖**，JIT/CPU 可以**重排序**：先执行 3（让 `instance` 指向那块内存），再执行 2（构造函数体）。

于是另一个线程可能在第一次检查时看到 **`instance != null` 但对象尚未初始化完成**，直接返回一个"半成品"对象，用它就 NPE 或读到错误数值。

`volatile` 的两个作用正好对症：

1. **禁止重排序**：写 `instance` 这个 volatile 变量的操作，不能与它之前的写操作重排（这里就是构造器里的字段写入），保证"看到引用的同时也看到了完整初始化的状态"。
2. **保证可见性**：一个线程写、另一个线程立刻能读到最新值，不会因为读到 CPU 缓存里的旧值而重复创建。

> [!note] 为什么在 x86 上很难复现
> x86 是 TSO（全存储定序）内存模型，**写-写不会重排**，且 `volatile` 读写在 x86 上编译为普通 `mov` + 编译屏障，几乎没有硬件开销。所以这个 bug 在 x86 上"看起来没问题"，换到 ARM、或者 JIT 做了激进优化后才暴露。
> 面试加分点：**"在 x86 上难复现不等于没有 bug——JMM 允许它发生，代码就不能依赖实现。"**

### 6.2 三把刀：反射、反序列化、类加载器

**(1) 反射破坏单例**

```java
Constructor<DclSingleton> c = DclSingleton.class.getDeclaredConstructor();
c.setAccessible(true);                       // 关掉访问检查
DclSingleton s2 = c.newInstance();           // 又一个实例！
```

**防护**：在私有构造器里加"已初始化"标志。

```java
private static boolean created = false;
private DclSingleton() {
    synchronized (DclSingleton.class) {
        if (created) throw new IllegalStateException("单例已被创建");
        created = true;
    }
}
```

注意：标志位要在构造器**最开头**判断，而且 DCL 里的 `instance` 赋值在构造器返回之后，不能只靠 `instance != null` 判断（反射场景下这个顺序不成立）。

**枚举为什么免疫**：`Constructor.newInstance` 内部有明确检查——

```java
if ((clazz.getModifiers() & Modifier.ENUM) != 0)
    throw new IllegalArgumentException("Cannot reflectively create enum objects");
```

所以 `EnumSingleton.class.getDeclaredConstructor()` 拿不到无参构造器（枚举的构造器是 `(String,int)` 形式），即使拿到也会被显式拒绝。

**(2) 反序列化破坏单例**

任何实现 `Serializable` 的普通单例，反序列化时**不调用构造器**，而是走 `ObjectInputStream` 的特殊路径，产生一个新对象。

**防护**：

```java
private Object readResolve() { return getInstance(); }   // 返回规范实例，丢弃刚反序列化的对象
```

`readResolve` 是 JVM 在反序列化后自动调用的钩子。**枚举免疫**：枚举的序列化只写 `name`，反序列化通过 `Enum.valueOf` 查找已存在的常量，天然返回同一个实例（这也是为什么枚举单例不需要 `readResolve`）。

**(3) 类加载器破坏单例**

单例的实现基础是"**同一个 ClassLoader 下，这个类只被初始化一次**"。若同一个单例类被**两个 ClassLoader** 分别加载，就得到两个 `Class` 对象、两个静态字段、两个实例。

| 场景 | 说明 |
| --- | --- |
| Web 容器多应用 | Tomcat 里每个 webapp 一个 `WebappClassLoader`，同类在各自的 loader 里各有一份 |
| 热部署 / 热加载 | 重新加载后旧实例可能仍被别处引用 |
| OSGi / 插件化 | 每个 bundle 一个 loader |
| 自定义加载器做隔离 | 框架常见做法 |

**防护**：把单例类放在**共享的父加载器**（容器的共享 lib、JDK 层）；或改用容器管理的单例（Spring 的 singleton bean 由容器统一持有）。

> [!important] 单例的现代定位
> 手写单例在业务代码里应该越来越少：
> - 需要**依赖注入**的东西 → 交给 Spring 的默认 singleton scope（它内部就是 `DefaultSingletonBeanRegistry` 的 `singletonObjects` map）。
> - 需要**全局配置常量** → 静态常量或配置中心。
> - 需要**有状态全局对象** → 大概率是设计问题，先想想能不能把它降级成无状态服务 + 外部存储。
>
> 手写单例最适合的场景：**工具类性质的、无状态、无依赖**的组件（如全局 ID 生成器的内存缓冲、指标注册表）。

## 七、结构型模式

### 7.1 代理（与 Spring AOP 强相关）

| 维度 | 静态代理 | JDK 动态代理 | CGLIB 动态代理 |
| --- | --- | --- | --- |
| 前提 | 手写代理类 | **目标类必须实现接口** | **目标类不能是 final**，方法不能 `final` |
| 生成方式 | 编译期手写 | 运行期生成 `$Proxy0` 实现全部接口 | 运行期 ASM 生成目标类的**子类** |
| 织入点 | 手动 | `InvocationHandler.invoke` | `MethodInterceptor.intercept` |
| 方法拦截范围 | 手写的那些 | 接口中声明的方法 | 所有**可重写**的 public/protected 方法 |
| 构造器 | 无要求 | 无要求 | 需调用父类构造器（Spring 用 Objenesis 绕过无参构造限制） |
| `this` 调用的自调用 | 无 | **不经过代理**（`this.f()` 是原始对象） | 同左 |
| 性能（现代 JDK） | 最快（编译期确定） | 与 CGLIB 大致相当 | 早期 JDK 上通常更快；生成类更重 |
| 依赖 | 无 | JDK 自带 | 需要 ASM（Spring 已 shaded 内置） |

```java
// JDK 动态代理最小实现
public class MapperProxy implements InvocationHandler {
    private final Map<Class<?>, Object> targets = new HashMap<>();
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        long start = System.nanoTime();
        try {
            return method.invoke(targets.get(method.getDeclaringClass()), args);
        } finally {
            System.out.printf("%s cost %dns%n", method.getName(), System.nanoTime() - start);
        }
    }
}
// 使用
MyService proxy = (MyService) Proxy.newProxyInstance(
        MyService.class.getClassLoader(),
        new Class<?>[]{ MyService.class },
        new MapperProxy());
```

**JDK 9+ 的模块化变化（说明行为）**：为支持模块系统，JDK 动态代理生成的 `$ProxyN` 类被定义在**动态模块**（如 `jdk.proxy1`）里，不再是 JDK 8 那种直接 `defineClass` 到应用类加载器。但"**必须基于接口 + 转发给 `InvocationHandler`**"的核心语义没变。这也带来一个实践后果：反射遍历 `proxy.getClass().getInterfaces()` 或用 `getClass().getName()` 做判断时，不要假设它是 `com.sun.proxy.$Proxy0`。

**Spring AOP 的选择规则**：

| 条件 | 使用的代理 |
| --- | --- |
| 目标实现了接口，且 `proxyTargetClass=false`（Spring 传统默认） | JDK 动态代理 |
| 目标没实现接口 | CGLIB |
| `proxyTargetClass=true` | 强制 CGLIB（**Spring Boot 的 AOP 自动配置默认就是 true**） |

Spring Boot 默认使用 CGLIB 的原因：避免"注入了具体类但实际是 JDK 代理导致 `ClassCastException`"这类问题（JDK 代理的实例不是目标类的子类型）。细节见 [[13-Spring源码骨架]]。

> [!danger] 两个真会踩的坑
> 1. **自调用失效**：`this.otherMethod()` 不经过代理，`@Transactional`/`@Cacheable` 不生效。原因见上表"`this` 调用"。修复：注入自身代理、`AopContext.currentProxy()`、或拆分 Bean。
> 2. **`final` 方法失效**：CGLIB 无法重写 `final` 方法，注解静默不生效。JDK 代理则不受 `final` 影响（接口方法由代理类实现）。
> 3. **代理类型判断**：`instanceof` 用接口判断，别强转成实现类。

### 7.2 适配器 / 装饰器 / 外观 / 桥接 / 组合 / 享元

| 模式 | 意图 | 与本表其他模式的区别 | JDK / Spring 例子 |
| --- | --- | --- | --- |
| **适配器** Adapter | 转换**已有接口**成客户端期望的接口 | 改变接口；被适配者是现成的、不能改的 | `InputStreamReader`（字节流→字符流）、`Arrays.asList`（数组→List）、`Collections.list`（Enumeration→ArrayList）、Spring MVC 的 `HandlerAdapter` |
| **装饰器** Decorator | 在**同一接口**上动态叠加职责 | 不改变接口，可层层嵌套，顺序敏感 | `BufferedInputStream(new FileInputStream(...))`、`Collections.unmodifiableList/synchronizedList/checkedList`、`HttpServletRequestWrapper` |
| **外观** Facade | 为子系统提供**统一简化入口** | 不改变子系统接口，只是收敛调用 | SLF4J（外观 + 桥接）、`JdbcTemplate`、`RestTemplate`、Tomcat 的 `*Facade` 类 |
| **桥接** Bridge | 把**抽象**与**实现**分离，各自独立变化 | 强调两个维度的正交演进 | JDBC：`java.sql.Driver` 抽象 vs 各数据库实现；AWT `Component` vs `ComponentPeer`；日志门面 + 绑定 |
| **组合** Composite | 把"单个"与"整体"统一对待，树形递归 | 处理**整体-部分**层次 | `java.awt.Container#add`、MyBatis 的 `MixedSqlNode`/`SqlNode`、文件系统、组织架构树 |
| **享元** Flyweight | 共享**不可变的内在状态**，外部状态由调用方传入 | 目的是**省内存**，共享的对象必须无状态 | `Integer.valueOf` 缓存、`String` 常量池、`Boolean.TRUE`、`Long.valueOf`、字体/图标缓存 |

> [!warning] 别把"对象池"叫成享元
> - **享元**：多个使用者**同时**共享同一个不可变对象，对象没有独占状态。
> - **对象池**（数据库连接池、线程池）：对象是**可变**的，同一时刻只能被一个使用者独占，用完归还。
> 面试里说错这个区分，会被认为只是背了名词。

**装饰器的顺序很重要**：

```java
// 缓冲能显著加速，但必须包在底层流外面；反过来会失去缓冲意义
new BufferedInputStream(new FileInputStream(f));       // 缓冲生效
new DataInputStream(new BufferedInputStream(...));     // 也可以，读语义正确

// 反例：把缓冲放在过滤流里面，每次过滤读都要穿透到底层
new BufferedInputStream(new DataInputStream(new FileInputStream(f)));   // 可以工作但语义混乱
```

## 八、行为型模式

### 8.1 重点模式详述

#### 策略（Strategy）

**意图**：把一族可互换的算法各自封装，让它们可以互相替换。
**结构**：`Context` 持有 `Strategy` 接口引用；具体策略实现接口。
**真实例子**：

| 位置 | 说明 |
| --- | --- |
| `Comparator<T>` | 排序策略，`List.sort(cmp)` / `Stream.sorted(cmp)` |
| `RejectedExecutionHandler` | 线程池拒绝策略（4 个内置实现），见 [[5-线程池]] |
| `ThreadFactory` | 线程创建策略 |
| Spring `ResourceLoader` / `ResourcePatternResolver` | 资源定位策略 |
| `PasswordEncoder` | 密码编码策略（`BCrypt`/`Argon2`） |

**使用场景**：同一问题有多种算法且需要运行期切换；算法里有大量条件分支。
**常见误用**：策略只有 1 个实现（等同于凭空造接口）；把"数据"当策略（用 Map 查表更简单）。

#### 模板方法（Template Method）

**意图**：父类定义算法骨架，把可变步骤延迟到子类。
**结构**：抽象类里 `final` 的模板方法 + `protected abstract` 钩子 + 可选 `protected` 钩子（提供默认空实现）。
**真实例子**：

| 位置 | 骨架方法 | 钩子 |
| --- | --- | --- |
| `AbstractList` | `indexOf`/`addAll` 等 | `get(int)`、`size()` |
| `JdbcTemplate` | `execute`（获取连接、异常翻译、释放资源） | `StatementCallback`/`RowMapper` |
| `HttpServlet` | `service`（按 HTTP 方法分发） | `doGet`/`doPost` |
| `AbstractApplicationContext` | `refresh()` | `onRefresh()`、`postProcessBeanFactory()` |
| `InputStream` | `read(byte[],int,int)` 默认实现 | `read()` |

**使用场景**：多个流程 90% 相同、只有少数步骤不同；框架给使用者留扩展点。
**常见误用**：骨架里又调用了可被重写的方法（对应 [[1-语言基础与面向对象]] 的"构造器调重写方法"同类问题——**父类在骨架执行前假设了子类状态**）；或者子类重写了不该重写的方法，破坏了骨架的 `final` 语义。

#### 观察者（Observer）

**意图**：一对多依赖，主题状态变化时自动通知所有观察者。
**真实例子**：

- Spring 事件：`ApplicationEventPublisher.publishEvent()` + `ApplicationListener` / `@EventListener`（同步）或配合 `@Async`（异步）。
- JDK：`java.util.Observer`（**已废弃**，因为 `Observable` 是类，无法与已有继承体系兼容）、`PropertyChangeListener`、`java.util.concurrent.Flow`（Java 9 引入的响应式发布-订阅）。
- Swing/JavaFX 的 listener 体系。

**使用场景**：模块间解耦、状态变更广播。
**常见误用**：

- 通知在**同步**链路上执行，某个监听器抛异常会中断整个发布流程（Spring 默认就是同步的；需要隔离必须显式 `@Async` 或换线程池）。
- **内存泄漏**：监听器被主题长期持有，忘记注销。`ApplicationListener` 由容器管理生命周期还好；手写注册表必须提供 `remove`。
- 通知风暴 / 循环通知（A 变更触发 B，B 又触发 A）。

#### 责任链（Chain of Responsibility）

**意图**：把请求沿处理者链传递，直到被处理或走完全链。
**真实例子**：

| 位置 | 形态 |
| --- | --- |
| `javax.servlet.Filter` | `FilterChain.doFilter` 显式调用下一个，可在前后各加逻辑 |
| Netty `ChannelPipeline` | `ChannelHandlerContext.fireChannelRead` 沿链传播 |
| Spring MVC `HandlerInterceptor` | `preHandle`/`postHandle`/`afterCompletion` |
| Spring Security `SecurityFilterChain` | 一组固定顺序的 filter |
| MyBatis `InterceptorChain` | 插件链，环绕 `Executor`/`StatementHandler` |

**使用场景**：多个处理者按顺序处理同一请求（鉴权、限流、日志、加解密）；处理者集合可配置。
**常见误用**：链上某个节点忘了调用 `chain.doFilter()`（请求静默"断头"）；异常处理位置不对导致响应已提交后又写响应。

#### 状态 / 命令 / 迭代器

| 模式 | 意图 | 真实例子 | 常见误用 |
| --- | --- | --- | --- |
| **状态** State | 把状态与状态相关行为拆成独立类，使迁移显式化 | 订单/审批状态机、连接状态机、Spring StateMachine | 状态类与上下文双向强耦合；迁移逻辑散落各处（应集中到一张迁移表） |
| **命令** Command | 把请求封装成对象，以支持排队/撤销/日志/事务边界 | `Runnable`/`Callable` + `ExecutorService.submit`、`javax.swing.Action`、CQRS 的 Command | 只想异步却硬造 `XxxCommand` 层级（lambda + `CompletableFuture` 更省事） |
| **迭代器** Iterator | 顺序访问聚合元素而不暴露内部表示 | `Iterator`/`Iterable`、`ListIterator`、Stream（内部迭代） | 遍历中结构性修改；误把 fail-fast 当成并发安全的保证 |

> [!note] 迭代器的 fail-fast 机制
> `ArrayList.Itr` 保存 `expectedModCount`，每次 `next()` 与 `modCount` 比对，不一致就抛 `ConcurrentModificationException`。它是 **best-effort** 检查：既不保证一定检测到，也不提供任何并发安全保证。需要并发遍历时用 `CopyOnWriteArrayList` 或显式加锁。

#### 中介者 / 备忘录 / 访问者（简述）

| 模式 | 意图 | 真实例子 |
| --- | --- | --- |
| **中介者** Mediator | 用中介对象封装一组对象的交互，减少网状引用 | 消息中间件（生产者/消费者不互相知道）、`ExecutorService`（任务与线程解耦）、Spring 容器本身（Bean 之间通过容器查找）、`java.util.Timer` |
| **备忘录** Memento | 在不破坏封装的前提下保存/恢复对象状态 | 编辑器撤销重做、事务回滚快照、`Serializable` 状态快照、版本化配置 |
| **访问者** Visitor | 在不改元素类的前提下为元素族添加新操作；靠**双分派**实现 | `javax.lang.model.element.ElementVisitor`（注解处理器）、ASM `ClassVisitor`、`java.nio.file.FileVisitor`、Spring `BeanDefinitionVisitor` |

> [!note] 访问者的"双分派"
> `element.accept(visitor)` 第一次分派选**元素的类型**，`visitor.visitXxx(this)` 第二次分派选**访问者的实现**。两次动态分派后才定位到方法，这就是它能在不修改元素类的前提下扩展操作的原因。
> 代价：元素的类型集合必须**封闭**（新增元素类型要改所有 visitor），且元素类必须提供 `accept`。

## 九、设计模式面试答题方法

> [!important] 不要背 23 个模式
> 面试官问"你熟悉哪些设计模式"时，**背名词是最差的答案**。他要听的是"你在什么约束下、做了什么取舍、拿到了什么收益"。
> 正确策略：**讲 3~5 个你真用过的，每个都带背景 + 冲突 + 取舍 + 可量化收益。**

### 9.1 话术模板

```text
【背景】我们那个 XX 系统（一句话说清业务和规模，如"日订单 200 万、对接 12 家支付渠道"）
【问题】当时的痛点是……（具体到会咬人的程度：如"每接一家新渠道要改支付核心的 if-else，
        回归测试要全量跑，一次上线要 3 天"）
【取舍】我考虑过 A 和 B（说清为什么不选另一个：如"想过用继承，但渠道差异既有算法差异
        也有参数差异，继承会让类爆炸且不能运行期切换"）
【方案】最终用了【策略 + 注册表】/【责任链】/……，关键设计点是……（说清边界、扩展点、
        异常与降级）
【收益】上线后接入新渠道从 3 天降到 0.5 天，支付核心代码零修改；
        并且通过 SPI/Spring 自动注册，新渠道的 jar 独立发布
【复盘】后来的教训是……（真诚的反思最能加分：如"注册表用了静态 Map，
        导致单测之间互相污染，后来改成容器注入"）
```

### 9.2 高频"你项目里用过什么"的对应关系

| 面试官想看的能力 | 推荐讲这个模式 | 因为 |
| --- | --- | --- |
| 会不会做**扩展点设计** | 策略 + 注册表 / SPI | 最能体现 OCP，且能说清"新增不改老代码" |
| 懂不懂**框架/中间件**原理 | 代理 + 责任链 + 模板方法 | Spring AOP、Filter、Netty、JdbcTemplate 全靠它们 |
| 会不会做**状态复杂**的业务 | 状态机（状态模式） | 订单/审批/工单场景普遍，能讲迁移表和并发控制 |
| 会不会做**解耦** | 观察者（事件驱动） | 能讲同步/异步、事务边界、幂等、消息丢失 |
| 会不会做**性能优化** | 享元 / 对象池 / 缓存 | 能讲清共享与池化的区别、GC 压力 |

> [!tip] 反向加分项
> 主动说"**这个场景我最后没有用设计模式**"也是加分项。例如：
> "一开始我按策略模式设计，但发现渠道只有 3 个且业务方明确说不会再加，就退回成了简单工厂 + 一张配置表，少了一个接口和三个类。"
> 这说明你有**判断力**，而不是照本宣科。

## 十、反模式与过度设计

### 10.1 常见反模式

| 反模式 | 症状 | 修复 |
| --- | --- | --- |
| **上帝类** God Class | 一个类几千行，什么都管 | 按职责/角色拆分 |
| **贫血模型** Anemic Model | 实体只有字段 + getter/setter，业务逻辑全在 Service | 把与状态强相关的行为移回实体（`order.pay()`） |
| **事务脚本满地** | 每个 Service 方法都是长的过程式代码 | 识别重复流程，抽模板方法/领域服务 |
| **过度分层** | Controller→Service→Manager→Helper→Util，每个只透传一行 | 合并只做转发的层 |
| **坏味道：`instanceof` 分发** | 到处 `if (x instanceof A)` | 多态 + 访问者 |
| **坏味道：长参数列表** | 8 个参数，调用处全是 `true, false, null` | 参数对象 / Builder |
| **坏味道：`Util` 类黑洞** | `CommonUtils` 上千个静态方法 | 按领域拆，或提炼成有名字的类 |
| **坏味道：`static` 全局状态** | 无法测试、无法并发 | 依赖注入 |
| **循环依赖** | A 依赖 B，B 依赖 A | 抽取共同抽象 / 事件解耦 / 重新划分边界 |
| **模式套模式** | 工厂 + 策略 + 模板 + 访问者堆在一个 20 行的功能上 | 回到最简单能用的实现 |

### 10.2 什么时候**不该**用模式

> [!warning] 五条克制原则
> 1. **只有一个实现时不要抽接口**（除非有明确的测试替身需求或跨模块解耦需求）。
> 2. **变化还没出现时不要抽象**。`YAGNI`——抽象的成本是立刻要付的，收益是可能永远不来的。
> 3. **分支集合封闭时不要用策略**。3 个固定枚举值用 `switch` 表达式更清晰、更安全（编译器能检查穷尽性）。
> 4. **不要为了"看起来像框架"而分层**。多一层间接就多一层调试难度、多一次跳转、多一份理解成本。
> 5. **不要用模式命名代码**。`XxxStrategyFactoryImpl` 这种类名是味道；好的抽象用**业务语言**命名（`PayChannel`、`RiskRule`）。

### 10.3 "模式是重构出来的，不是设计出来的"

```text
第一次：写 if/else 把功能跑通（简单、直接、能交付）
   ↓ 当第 3 个分支出现，且可以预见还会增长
第二次：识别出"变化点"，把分支体抽成独立类
   ↓ 当分支的创建逻辑也开始复杂（要按配置/环境选）
第三次：引入注册表或工厂
   ↓ 当分支需要环绕逻辑（日志、重试、事务）
第四次：引入装饰器/代理/责任链
```

每一步都是**被真实需求推着走**的，而不是一开始就画好 23 个类的图。

> [!important] 本篇的答题定位
> 设计模式考的不是"知不知道"，而是**判断力**：
> - 能不能识别出代码里真正的**变化点**（这是所有模式的前提）；
> - 能不能说清某个模式的**代价**（多一层间接、更难调试、类数量膨胀）；
> - 能不能在"过度设计"和"硬编码 if-else"之间找到当下最合适的落点。
> 把这句话讲出来，比背完 23 个模式更有分量。
