## 一、基本类型与包装类

### 1.1 8 种基本类型

Java 的基本类型是**值语义**的、非对象的，JVM 层面直接对应局部变量表的 slot 或栈上的一格（`int`/`float`/引用占 1 slot，`long`/`double` 占 2 slot）。它们的位数在规范里是**强制固定**的——这是 Java 比 C 更"安全"的核心原因之一：跨平台不会出现 `int` 是 16 位还是 32 位的分歧。

| 类型 | 位数 | 包装类 | 取值范围 | 默认值 | 典型陷阱 |
| --- | --- | --- | --- | --- | --- |
| `byte` | 8 | `Byte` | -128 ~ 127 | 0 | 做位运算前需 `& 0xFF` |
| `short` | 16 | `Short` | -32768 ~ 32767 | 0 | 几乎不用 |
| `int` | 32 | `Integer` | -2^31 ~ 2^31-1 | 0 | 溢出静默回绕 |
| `long` | 64 | `Long` | -2^63 ~ 2^63-1 | 0L | `int * int` 先溢出再赋给 long |
| `float` | 32 | `Float` | IEEE 754 单精度 | 0.0f | 精度约 7 位十进制 |
| `double` | 64 | `Double` | IEEE 754 双精度 | 0.0d | `0.1 + 0.2 != 0.3` |
| `char` | 16 | `Character` | 0 ~ 65535（UTF-16 码元） | '\u0000' | 表示不了增补平面字符 |
| `boolean` | 规范未定义 | `Boolean` | true/false | false | JVM 内实现为 int，数组为 byte |

> [!warning] 三个反直觉点
> 1. **`long` 溢出**：`long ms = 365 * 24 * 3600 * 1000;` 右边全是 `int` 运算，先溢出成负数再拓宽，结果 `1471228928`。必须写 `365L * 24 * ...`。这类 bug 常出现在"计算 N 天后的时间戳"。
> 2. **`boolean` 的字节数没有规范定义**，HotSpot 里单变量用 int、数组用 byte——所以别在序列化协议里依赖 `boolean` 的宽度。
> 3. **`char` ≠ 一个字符**。emoji 等增补字符需要两个 `char`（代理对），`"😀".length() == 2`。真正的"字符"计数要用 `codePointCount`。

### 1.2 自动装箱 / 拆箱与 Integer 缓存

自动装箱是**编译期语法糖**：`Integer i = 1;` 被 javac 翻译成 `Integer.valueOf(1)`；`int j = i;` 翻译成 `i.intValue()`。**关键在 `valueOf` 不是 `new`**。

```java
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);
}
```

`IntegerCache.low` 固定为 `-128`，`high` 默认 `127`，可用 `-XX:AutoBoxCacheMax=N` 抬高上界（会写入 `java.lang.Integer.IntegerCache.high` 系统属性）。

| 写法 | 结果 | 原因 |
| --- | --- | --- |
| `Integer a=127,b=127; a==b` | `true` | 命中缓存，同一对象 |
| `Integer a=128,b=128; a==b` | `false` | 各自 `new`，不同对象 |
| `new Integer(1)==new Integer(1)` | `false` | 显式绕过缓存 |
| `Integer a=200; a==200` | `true` | 一侧是字面量，触发**拆箱**后比 int |
| `Integer a=null; a==0` | **NPE** | 拆箱调用 `intValue()` |

| 包装类 | 缓存范围 | 可调 |
| --- | --- | --- |
| `Byte` | -128 ~ 127（全覆盖） | 否 |
| `Short` | -128 ~ 127 | 否 |
| `Integer` | -128 ~ 127 | 是（`AutoBoxCacheMax`） |
| `Long` | -128 ~ 127 | 否 |
| `Character` | 0 ~ 127 | 否 |
| `Boolean` | `TRUE`/`FALSE` 两个常量 | 否 |
| `Float` / `Double` | **无缓存** | 否 |

> [!danger] 最阴的 NPE 形态
> 三目运算符的类型合并会**悄悄拆箱**：
> ```java
> Integer a = null;
> Integer b = (a == null) ? 0 : a;   // 这里 0 是 int，整个表达式被提升为 int
> // 只要 a 为 null 且分支走到 a，就会 NPE
> ```
> 更常见的变体是把 `Map<String,Integer>` 的值直接参与 `+`、`>` 比较，`get` 返回 null 时立刻 NPE。规范做法：`Objects.requireNonNullElse` 或显式判空。

**性能视角**：在 hot loop 里 `Integer sum = 0; sum += i;` 每轮都可能装箱 + 拆箱。JIT 的逃逸分析**有时**能标量替换掉，但一旦对象逃逸（被存进字段、被传给非内联方法）就会退化成真实的堆分配，同时给 GC 增加压力。

### 1.3 equals / hashCode 契约

`Object` 的默认实现：

```java
public boolean equals(Object obj) { return (this == obj); }
public native int hashCode();          // 默认由对象地址/随机种子派生（与地址无强绑定）
```

**契约（JLS/Javadoc 强制）**：

| 性质 | 含义 |
| --- | --- |
| 自反性 | `x.equals(x)` 必须 true |
| 对称性 | `x.equals(y) == y.equals(x)` |
| 传递性 | x=y 且 y=z ⇒ x=z |
| 一致性 | 只要参与比较的状态没变，结果不能变 |
| 非空性 | `x.equals(null)` 必须 false（不能抛 NPE） |
| **与 hashCode 的一致性** | `x.equals(y)` ⇒ `x.hashCode()==y.hashCode()` |

反过来不要求：hash 相等可以 equals 不等（哈希冲突）。**违反 hash 契约的后果**：`HashMap` 先用 `hash` 定位桶，再用 `equals` 比较。两个"相等"的对象若 hash 不同，会被放进不同的桶，`map.get(k2)` 永远拿不到 `k1` 的值——表现为"存进去了但取不出来"，而且不报错，极难排查。

```java
// 标准写法（注意参数类型必须是 Object，写成重载会静默失效）
@Override
public boolean equals(Object o) {
    if (this == o) return true;                       // 快路径
    if (o == null || getClass() != o.getClass()) return false;  // 或用 instanceof（见下）
    User u = (User) o;
    return age == u.age && Objects.equals(name, u.name);
}
@Override
public int hashCode() { return Objects.hash(name, age); }
```

> [!question] `getClass()` 还是 `instanceof`？
> - `getClass()`：严格，子类和父类实例不相等。适合**值对象**，能保住对称性。
> - `instanceof`：允许子类相等，但会**破坏对称性**——父类 `equals` 认可子类，子类的 `equals` 若不认可父类就会出现 `a.equals(b)!=b.equals(a)`。Hibernate 代理场景常用，但要在文档里写清楚，或用 `canEqual` 模式显式约束。
>
> 只在子类不增加"参与相等的状态"时用 `instanceof` 才安全。

> [!tip] 别用可变字段做 hashCode 的输入
> 对象作为 `HashMap` 的 key 之后修改了参与 hash 计算的字段，桶位置就"错位"了，`get` 失败、`remove` 失败、内存泄漏。要么让 key 不可变（推荐：`String`、包装类、record），要么把字段设成 final。

### 1.4 BigDecimal 与浮点精度

`0.1 + 0.2 == 0.30000000000000004` 的根因是**二进制无法精确表示十进制小数**。`0.1` 的二进制是 `0.0001100110011...`（1100 循环），IEEE 754 double 只有 52 位尾数，舍入后就已经不等于 0.1 了；两个舍入误差相加再舍入，结果再偏一点。

```java
System.out.println(0.1 + 0.2);       // 0.30000000000000004
System.out.println(0.1f + 0.2f);     // float 精度更低
System.out.println(1.0 - 0.9);       // 0.09999999999999998
```

**正确姿势**：

| 场景 | 做法 |
| --- | --- |
| 金额/计费 | 用 `BigDecimal`，或用 `long` 存最小单位（分） |
| 比较浮点 | 不要 **==**；用 `Math.abs(a-b) < EPS`，或 `Double.compare(a,b)==0` |
| 排序/装箱比较 | `Double.compare` / `Float.compare`（能正确处理 NaN、-0.0） |
| 科学计算 | 明确接受误差，用 Kahan 求和等数值算法控制累积误差 |

**BigDecimal 的两个大坑**：

```java
new BigDecimal(0.1);            // 0.1000000000000000055511151231257827021181583404541015625
new BigDecimal("0.1");          // 0.1   ← 用字符串
BigDecimal.valueOf(0.1);        // 0.1   ← 内部就是 Double.toString 再构造

// 坑 1：equals 比较 scale
new BigDecimal("1.0").equals(new BigDecimal("1.00"));    // false
new BigDecimal("1.0").compareTo(new BigDecimal("1.00")); // 0

// 坑 2：除法不指定舍入会抛异常
new BigDecimal("1").divide(new BigDecimal("3"));
// ArithmeticException: Non-terminating decimal expansion; no exact representable decimal result
new BigDecimal("1").divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP); // 0.33
```

> [!danger] 金额比较只用 compareTo
> `equals` 把 **value 和 scale 一起比**，`1.0` 与 `1.00` 不相等。用 `HashSet`/`HashMap` 装 BigDecimal 做"金额去重"时，`1.0` 和 `1.00` 是两个不同的 key —— 这是真实出现过的对账 bug。需要统一标度时用 `setScale(n, RoundingMode.HALF_UP)` 归一化，不要靠 `stripTrailingZeros()` 兜底（Java 8 才修掉 `0.00.stripTrailingZeros()` 返回 `0.00` 的历史行为，且负标度仍会带来意外）。

> [!warning] `RoundingMode` 不是随便选的
> 银行/电商常见口径是 `HALF_UP`（四舍五入）或 `HALF_EVEN`（银行家舍入，`BigDecimal` 的"标准"口径，能减少系统性偏差）。选错口径会导致**对账差额**：单笔看不出来，百万笔汇总差几毛钱。这不是代码 bug，是业务口径 bug，上线前必须和财务对齐。

## 二、String 体系

### 2.1 为什么 String 不可变

`String` 被声明为 `final class`，内部存字符数据的字段是 `private final`，且**不提供任何修改方法**（`replace`/`substring` 都返回新对象）。

> [!note] Java 9 的底层变化
> Java 8 及更早：`private final char[] value;`，Latin-1 字符也占 2 字节。
> Java 9 起改为**紧凑字符串（Compact Strings）**：`private final byte[] value; private final byte coder;`。`coder` 为 `LATIN1` 时每字符 1 字节，为 `UTF16` 时 2 字节。收益是**纯 ASCII 场景堆占用几乎减半**，代价是每次访问要按 coder 分支。这是"行为描述"，不是语言语义变化——你的代码不用改。

不可变带来四个真实收益：

| 收益 | 原理 |
| --- | --- |
| 常量池共享 | 相同字面量可以指向同一个对象，省内存 |
| 线程安全 | 状态不可变 ⇒ 天然无需同步，可安全当 `HashMap` key、可跨线程发布 |
| hash 缓存 | `private int hash;` 懒计算，第二次 `hashCode()` 直接返回，热路径（HashMap 查找）显著更快 |
| 安全性 | 类名、文件路径、SQL、URL 不会在传给下游校验之后被别的线程偷偷改掉 |

**"不可变"的边界**：`String` 对象本身不可变，但**引用可变**；`final char[]` 若通过反射拿到仍是可改的（`setAccessible` 后可以改 `value` 数组）——所以"绝对不可变"只对普通代码成立，对反射/`Unsafe` 不成立。

### 2.2 常量池与 intern()

```java
String a = "abc";                    // 字面量 → 常量池
String b = "abc";                    // 复用同一个对象
String c = new String("abc");        // 堆上新建对象，value 仍指向池内容
String d = c.intern();               // 返回池中的规范对象

System.out.println(a == b);          // true
System.out.println(a == c);          // false
System.out.println(a == d);          // true
```

**`intern()` 语义**：若池中已有 `equals` 相等的字符串，返回池中那个；否则把**当前对象放入池**并返回它。

> [!note] 池在哪：JDK 7 是分界线
> JDK 6 及更早，字符串常量池在**永久代（PermGen）**，`intern()` 滥用 → `OutOfMemoryError: PermGen space`。
> **JDK 7 起，池被移到堆中**（本质是 `StringTable` 这张哈希表存的是堆内对象的引用），因此可以随堆扩容，本地变量指向的字符串 `intern()` 后也能被 GC（只要没有别的强引用）。
> 到 JDK 8 永久代整体被 Metaspace 取代，但字符串池**从 JDK 7 起就已经在堆里**了——面试里"字符串池在 Metaspace"是常见错误回答。

**什么时候真的需要 `intern()`**：大量重复的外部字符串（如日志里的枚举型字段、JSON 里的固定 key）常驻内存时，`intern()` 可以把 N 份副本收敛成 1 份。但要注意：

- `StringTable` 默认桶数偏小，可用 `-XX:StringTableSize=` 调大（建议取质数），否则 `intern()` 本身成为热点（桶内链表遍历）。
- 池里的字符串**几乎永不回收**（需要 Full GC 且相应 ClassLoader 被回收），滥用等于制造内存泄漏。

### 2.3 String / StringBuilder / StringBuffer

| 维度 | `String` | `StringBuilder` | `StringBuffer` |
| --- | --- | --- | --- |
| 可变性 | 不可变 | 可变 | 可变 |
| 线程安全 | 安全（因不可变） | **不安全** | 安全（方法 `synchronized`） |
| 性能 | 频繁拼接差 | 最好 | 比 StringBuilder 差（锁开销） |
| 首次出现 | 1.0 | **Java 5** | 1.0 |
| 底层 | `byte[]`（9+）/ `char[]` | `AbstractStringBuilder` 的 `byte[]` | 同左，但方法加锁 |
| 选型 | 不变的内容、Map key | 单线程拼接（默认选择） | 极少用；局部变量拼接收缩到线程内时用 StringBuilder 更好 |

**扩容策略**：默认容量 16；`ensureCapacity` 时新容量 = `old * 2 + 2`，然后用 `Arrays.copyOf` 全量复制。因此**预知长度时一定要给初值**：

```java
// 反例：一个 1MB 的 JSON 拼接会触发 ~17 次扩容，产生几十 MB 的临时垃圾
StringBuilder sb = new StringBuilder();
for (Item it : items) sb.append(it.toString());

// 正例：按量估算，或者干脆先算
StringBuilder sb2 = new StringBuilder(items.size() * 64);
```

> [!tip] 现代 Java 的替代品
> `String.join(",", list)`（Java 8）、`Collectors.joining(",")`、`StringJoiner` 都比手写"最后一个不加逗号"的逻辑更短更安全。

### 2.4 字符串拼接：编译期 vs 运行期

```java
// ① 编译期常量折叠：javac 直接算成 "abc"，字节码里只有一条 ldc
String s1 = "a" + "b" + "c";

// ② final 的"常量变量"也参与折叠（只要它是基本类型或 String 的直接字面量）
final String P = "a";
String s2 = P + "b";      // 等价于 "ab"

// ③ 运行期：javac 在 JDK 8 生成 StringBuilder
String s3 = a + b + c;    // new StringBuilder().append(a).append(b).append(c).toString()
```

**循环内 `+` 的坑**：JDK 8 下每轮循环都会 `new StringBuilder`，整体复杂度从 O(n) 退化成 O(n²)，且产生大量临时对象。

```java
// 反例
String r = "";
for (int i = 0; i < n; i++) r += i;      // 每轮一个新 StringBuilder + 一个新 String

// 正例
StringBuilder sb = new StringBuilder(n * 4);
for (int i = 0; i < n; i++) sb.append(i);
String r2 = sb.toString();
```

> [!important] `final String` 不总是被折叠
> 只有当它是**编译期常量表达式**（`static final String X = "a";` 或 `final String x = "a" + "b";`）才折叠成 `ldc`。`static final String X = someMethod();` 不是常量变量，运行期才赋值，拼接走 StringBuilder/indy。

### 2.5 JDK 9+ 的 invokedynamic 拼接

从 Java 9 开始，javac 对字符串拼接不再生成 `StringBuilder` 调用序列，而是生成一条 `invokedynamic` 指令，指向 `java.lang.invoke.StringConcatFactory.makeConcatWithConstants`。**引导方法（bootstrap）在类首次链接该调用点时执行一次**，返回一个 `CallSite`，之后每次执行走 `MethodHandle`。

| 维度 | JDK 8（StringBuilder） | JDK 9+（invokedynamic） |
| --- | --- | --- |
| 字节码体积 | 每处拼接一串 `new`/`append`/`toString` | 一条 `invokedynamic` + 引导常量 |
| 运行期实现 | 固定 | 可被 JVM/参数替换策略，默认精确分配目标长度 |
| 临时对象 | 有中间 `StringBuilder` 和 char 数组 | 默认策略直接算准长度一次分配，通常更少 |
| 循环内 `+` | O(n²) | **仍然 O(n²)** |

> [!warning] 别把 indy 当成"循环拼接的免罪符"
> 优化掉的是**单次拼接的常数因子**，不是算法复杂度。循环里的 `s += x` 依然是每轮新建一个 String 并整段复制。这一点从 Java 8 到 Java 21 都没变。

## 三、final / static 与初始化顺序

### 3.1 final 的四种语义

| 修饰对象 | 语义 | 易误解点 |
| --- | --- | --- |
| `final class` | 不可被继承 | `String`、`Integer`、`System` 都是 |
| `final` 方法 | 不可被重写（`private` 方法天然不可重写） | JIT 可据此**去虚化**并内联；但字节码层面仍是 `invokevirtual`，不是 `invokespecial` |
| `final` 字段 | 只能赋值一次（声明处 / 构造器 / 初始化块） | 若是引用类型，**只是引用不可变，对象内容仍可变** |
| `final` 参数 | 方法内不能重新赋值 | 不影响调用方 |

**final 字段的内存语义（JMM）**：`final` 字段在构造器结束时被"冻结"，JMM 保证**正确构造（构造器内没有把 this 逸出）的对象**在被其他线程看到时，`final` 字段的值一定已经写入。这条规则让"不可变对象可以安全发布"成立——`String`、`Integer` 那些"无锁线程安全"的论证都依赖它。**代价**：任何让 `this` 在构造完成前逸出（构造器里注册监听器、启动线程、调用可被重写的方法）都会破坏这个保证。

### 3.2 static 与类初始化顺序

```java
class Parent {
    static { System.out.println("1 父静态块"); }
    { System.out.println("3 父实例块"); }
    Parent() { System.out.println("4 父构造器"); }
}
class Child extends Parent {
    static { System.out.println("2 子静态块"); }
    { System.out.println("5 子实例块"); }
    Child() { System.out.println("6 子构造器"); }
}
// new Child() 输出：1 2 3 4 5 6
```

**完整规则**：

1. 类加载 → 链接 → 初始化的**触发时机**：首次 `new`、访问静态字段/静态方法、反射 `Class.forName`（带 `initialize=true`）、初始化子类时先初始化父类。
2. 初始化阶段按源码顺序执行父类静态字段赋值/静态块，再执行子类静态字段赋值/静态块。
3. 实例化时：先执行父类实例字段赋值/实例块，再执行父类构造器；然后子类实例字段赋值/实例块，最后子类构造器。

> [!note] 为什么子类实例块排在父类构造器之后？
> javac 把实例字段初始化和实例块**内联进每一个构造器**，紧跟在 `super(...)` 调用之后。所以真实顺序是：`super()` 内部完成父类一切 → 回到子类构造器 → 子类字段/实例块 → 子类构造器体。这也是"父类构造器里调用被子类重写的方法会看到子类字段仍是默认值"的根因。

```java
class Base {
    Base() { print(); }             // 动态分派！调到子类实现
    void print() { System.out.println("base"); }
}
class Sub extends Base {
    private int v = 42;
    @Override void print() { System.out.println("sub v=" + v); }  // 输出 v=0
}
new Sub();   // sub v=0  ← 子类字段还没初始化
```

> [!danger] 构造器里永远不要调用可被重写的方法
> 上面这段是**真实事故模板**：父类在构造器里注册回调/发布事件，子类重写的方法读到未初始化的字段，得到 `null` → NPE。`Thread` 的子类在 `start()` 前被注册、Spring Bean 在构造器里 `publishEvent`，都是这个陷阱的变体。

**`static final` 常量的编译期内联**：

```java
// module-a
public class Consts { public static final int TIMEOUT = 3000; }

// module-b （编译时把 3000 直接写进了自己的字节码）
int t = Consts.TIMEOUT;   // → ldc 3000 / bipush
```

后来把 `TIMEOUT` 改成 `5000`，**只重新编译 module-a 并替换 jar，module-b 不重编译就依然用 3000**。这是"改配置没生效"的经典根因。

- 只有**基本类型或 `String` 的常量表达式**才会内联。
- `public static final Integer TIMEOUT = 3000;` **不内联**（不是常量变量），每次都 `getstatic`。
- 规避：改用 `static final` + getter、枚举、`Properties`/配置中心，或保证全量重编译。

## 四、equals vs ==、浅拷贝与深拷贝

### 4.1 **==** 与 `equals` 的分工

| 比较对象 | **==** 语义 | `equals` 语义 |
| --- | --- | --- |
| 基本类型 | 值比较 | 不适用（会装箱） |
| 引用类型 | **引用是否指向同一对象**（地址比较） | 由实现决定，`Object` 默认也是地址比较 |

真正要区分的是**值语义 vs 引用语义**：`String`、包装类、`BigDecimal`、`LocalDate` 重写了 `equals`，是值语义；自定义实体默认是引用语义（除非你重写）。

### 4.2 Object.clone 的坑

```java
public class Order implements Cloneable {
    private List<Item> items;
    @Override public Order clone() {
        try { return (Order) super.clone(); }        // 浅拷贝：items 仍是同一个 List
        catch (CloneNotSupportedException e) { throw new AssertionError(e); }
    }
}
```

| 问题 | 说明 |
| --- | --- |
| 必须实现 `Cloneable` | 否则 `super.clone()` 抛 `CloneNotSupportedException`。`Cloneable` 是**标记接口**，连 `clone` 方法都没声明 |
| 默认是浅拷贝 | 引用字段共享同一对象，改副本影响原件 |
| 绕过构造器 | `Object.clone` 是 native 实现，不会执行你的构造器 → 构造器里的校验、注册、状态初始化全部被跳过 |
| `final` 字段 | 无法在 clone 后再赋值，深拷贝要谨慎设计 |
| 返回值协变 | Java 5 起可以返回具体类型，但必须自己转型 |

**深拷贝的可行方案**：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 手工递归 `clone` | 快、可控 | 字段一多就漏，图结构/循环引用处理麻烦 |
| 拷贝构造器 / 静态工厂 | 语义清晰，能走完整初始化 | 要手写 |
| 序列化（Java 原生 / JSON / Kryo） | 天然深拷贝，能处理复杂图 | 慢 1~2 个数量级；要求 `Serializable`；`transient` 字段丢失 |
| `CopyOnWrite` 思路 | 无锁读、快照稳定 | 写放大；只适合读多写极少 |
| 不可变对象 | 根本不需要拷贝，共享引用即可 | 要求设计成不可变 |

**CopyOnWrite 的核心思想**（见 `CopyOnWriteArrayList`、`Arrays.copyOf`、`String` 的每次拼接）：

```java
// 读：直接返回当前数组引用，无锁；写：复制 + 修改 + 原子替换引用
Object[] old = array;
Object[] copy = Arrays.copyOf(old, old.length + 1);
copy[old.length] = newItem;
array = copy;                  // volatile 写，发布新快照
```

读线程要么看到**旧快照**要么看到**新快照**，永远不会看到"改了一半"的数组。代价是每次写都全量复制，内存翻倍。适用场景：监听器列表、配置缓存、白名单——**读远多于写**。

## 五、异常体系

### 5.1 层次结构

```
Throwable
├── Error                    ← 不要 catch：JVM 级别，程序无力恢复
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   └── NoClassDefFoundError / ExceptionInInitializerError
└── Exception
    ├── RuntimeException     ← 非受检（unchecked）
    │   ├── NullPointerException / IndexOutOfBoundsException
    │   └── IllegalArgumentException / IllegalStateException
    └── 其他                 ← 受检（checked）
        ├── IOException / SQLException
        └── InterruptedException / ClassNotFoundException
```

| 维度 | 受检异常 | 非受检异常 |
| --- | --- | --- |
| 编译器强制 | 必须 catch 或 throws | 不强制 |
| 设计意图 | 调用方**可恢复**的外部故障（网络、文件、DB） | **编程错误**或不可恢复状态 |
| 典型代表 | `IOException`、`SQLException` | `NPE`、`IllegalArgumentException` |
| 主要问题 | 污染签名、跨层传染、容易被"catch+吞"、**无法用于 lambda/Stream** | 容易被忽略，缺少显式契约 |

> [!important] 现代 Java 的取舍共识
> 大部分团队（含 Spring）倾向**少用受检异常**：Spring 把 `SQLException` 统一翻译成 `DataAccessException`（非受检），只保留少量受检异常（如 `IOException`）。
> 理由一：受检异常在 lambda 里根本用不了——`Function<T,R>` 的 `apply` 不声明异常，你只能包一层 `try/catch` 转 `RuntimeException`。
> 理由二：跨层传染。底层加一个受检异常，上层调用链全要改签名，破坏封装。
> 理由三：实践中 90% 的 `catch` 块只是 `log.error` 然后继续，反而制造"异常被吞"。

### 5.2 try-with-resources 与 AutoCloseable

```java
// Java 7 之前：手写 finally，嵌套三层，还容易漏判 null
InputStream in = null;
try { in = open(); ... } finally { if (in != null) try { in.close(); } catch (IOException ignore) {} }

// Java 7+：反编译后语义等价，但更安全
try (InputStream in = open(); OutputStream out = open2()) {   // 分号分隔
    copy(in, out);
}
```

**关键语义（高频深挖）**：

1. 关闭顺序是**声明的逆序**（后申请的先关），因为资源常有依赖关系。
2. 资源变量**隐式 final**，不能在块内重新赋值。
3. 只有实现了 `AutoCloseable` 才能用；`Closeable extends AutoCloseable`，把 `close()` 的异常类型从 `Exception` 收窄成 `IOException`。
4. **抑制异常**：若 try 块体抛异常 A，关闭时又抛异常 B，则 B 被 `A.addSuppressed(B)` 挂上去，最终抛出的是 A，`A.getSuppressed()` 能拿到 B。这修复了手写 finally 里"关闭异常覆盖业务异常"的经典问题。

> [!warning] `catch` 与资源的顺序
> ```java
> try (Resource r = new Resource()) {
>     throw new RuntimeException("业务失败");
> } catch (Exception e) {
>     // 这里拿到的是"业务失败"；如果 r.close() 也抛了，它挂在 suppressed 里
> }
> ```
> 只 `e.printStackTrace()` 或只打 `e.getMessage()` 会**丢掉 suppressed 信息**，排查时要打完整 `e`（日志框架的 `log.error("msg", e)` 会打印 suppressed）。

### 5.3 finally 与 return 的执行顺序

```java
// ① finally 的 return 会覆盖 try 的 return，并且吞掉异常（编译告警/静态检查会报）
static int f1() { try { return 1; } finally { return 2; } }        // 2

// ② return 的表达式值在 finally 之前就已求值并暂存
static int f2() { int x = 1; try { return x; } finally { x++; } } // 1（返回的是副本）

// ③ 但如果 finally 里也 return 同一个变量，就是新求值
static int f3() { int x = 1; try { return x; } finally { return ++x; } } // 2

// ④ finally 抛异常会覆盖 try 里正在抛的异常
static int f4() { try { throw new RuntimeException("A"); } finally { throw new RuntimeException("B"); } }
// 最终只看到 B，A 丢失（不是 suppressed，是彻底丢失）
```

> [!danger] 永远不要在 finally 里写 return / break / continue / throw
> 字节码层面，javac 会把 `finally` 代码块**复制到每一条退出路径上**（正常出口 + 每个 catch 出口），所以它的副作用在每条路径上都会执行。在 `finally` 里 `return` 不仅是代码风格问题，它会**静默吞掉异常**，让 bug 变成"返回值莫名其妙不对"。IDE/`ErrorProne` 应该把这条列为 error。

**受检异常与 `InterruptedException`**：捕获后必须恢复中断状态（`Thread.currentThread().interrupt()`）或向上抛，否则线程池里的线程"中断信号被吃掉"，`shutdownNow` 无法及时停止任务。详见 [[5-线程池]]。

### 5.4 异常的性能开销

| 开销来源 | 量级 | 说明 |
| --- | --- | --- |
| `fillInStackTrace` | 微秒级 | 遍历整个调用栈并填充 `StackTraceElement[]`，是绝对大头 |
| 对象分配 | 纳秒级 | 一个异常对象 + 栈数组 |
| JIT 影响 | 间接 | 频繁 throw 会让方法难以内联（异常边是"冷"路径，但有阈值） |

```java
// ① 不需要栈轨迹时显式关掉（Java 7+）
public class BizException extends RuntimeException {
    public BizException(String msg) { super(msg, null, false, false); } // 禁用抑制 + 禁用栈轨迹
}

// ② JIT 的 fast-throw：热点方法里的隐式异常会被优化成"无栈轨迹"
//    -XX:+OmitStackTraceInFastThrow（默认开启）
//    现象：同一个 NPE 抛了几万次后，日志里突然只剩 "java.lang.NullPointerException" 没有行号
//    排查：加 -XX:-OmitStackTraceInFastThrow 复现第一次的完整栈
```

**结论**：异常是**控制流的例外路径**，不要用来做业务分支（如"用 `NumberFormatException` 判断字符串是不是数字"）。高频业务失败应返回结果对象（`Result<T>`）。

## 六、面向对象三大特性与多态底层

（本节只简述，继承/组合/接口设计等细节放在 [[2-面向对象与设计模式]]）

| 特性 | 一句话 | 底层支撑 |
| --- | --- | --- |
| 封装 | 隐藏实现、暴露契约 | 访问修饰符 + 编译期检查（注意反射可绕过） |
| 继承 | 复用 + 建立 is-a 关系 | 字段布局叠加、方法表继承 |
| 多态 | 同一调用在不同运行期类型上表现不同 | **虚方法表 + 动态分派** |

### 6.1 虚方法表与动态分派

每个类在方法区（JDK 8+ 在 Metaspace）里有一张**虚方法表（vtable）**，`itable` 用于接口方法。对象头里的 `klass` 指针指向类元数据，类元数据里有 vtable 槽位数组，槽位在**类加载链接阶段就填好了**。

```java
Animal a = new Dog();
a.speak();
```

```text
// 字节码
aload_1
invokevirtual #5   // Method Animal.speak:()V
```

`invokevirtual` 的执行：从操作数栈顶拿到实际对象 → 取其 `klass` → 按方法在 vtable 里的**固定索引**取出真正的实现入口 → 跳转。**这是一次数组索引 + 跳转，常数级**，所以"多态很慢"是误解。真正慢的是**无法内联**。

| JVM 指令 | 分派方式 | 用途 |
| --- | --- | --- |
| `invokestatic` | 静态 | 静态方法 |
| `invokespecial` | 静态 | 构造器、`private` 方法、`super.` 调用、`final` 类的实例方法优化 |
| `invokevirtual` | **动态** | 普通实例方法（含 `final` 方法，javac 仍用此指令） |
| `invokeinterface` | **动态** | 接口方法，需要 itable 查找，比 vtable 稍贵 |
| `invokedynamic` | 动态 | Lambda、字符串拼接（JDK 9+）、`record` 的 `equals/hashCode` 引导 |

> [!tip] JIT 如何干掉多态开销
> 1. **单态内联（monomorphic inline cache）**：某调用点只见过一种接收者类型 → 直接内联该实现 + 一个类型检查（guard）。
> 2. **双态/多态内联**：见过 2~4 种 → 生成类型判断链，各分支分别内联。
> 3. **超多态（megamorphic）**：超过阈值（HotSpot 默认约 2~4 种，超了进 megamorphic 缓存）→ 退回查表，**不再内联**。
>
> 实践含义：在极热的内层循环里让同一个调用点被几十种类型打散，会直接掉出内联优化。这也是"接口滥用导致性能下降"的真实机理，而不是"虚方法调用慢"。

### 6.2 重载（静态分派）vs 重写（动态分派）—— 高频深挖

| 维度 | 重载 Overload | 重写 Override |
| --- | --- | --- |
| 决定时机 | **编译期** | **运行期** |
| 依据 | 方法名 + 参数列表（静态类型） | 对象的实际类型 |
| 返回类型 | **不参与**（不能靠返回类型区分） | 可以是协变类型（子类型） |
| 访问权限 | 无限制 | 不能变窄 |
| 异常 | 无限制 | 不能变宽（不能抛更多/更宽的受检异常） |
| 绑定机制 | 编译期选定描述符，字节码里写死 | `invokevirtual` + vtable |
| 别名 | 静态分派（static dispatch） | 动态分派（dynamic dispatch） |

```java
static class A {}
static class B extends A {}

static void f(A a) { System.out.println("A"); }
static void f(B b) { System.out.println("B"); }

public static void main(String[] args) {
    A x = new B();
    f(x);              // 输出 A  ← 编译期按 A 类型选定
    f((B) x);          // 输出 B  ← 强转改变了静态类型
}
```

**重载解析的三个阶段（JLS 规定的优先级顺序）**：

1. **不装箱、不自动拓宽**的精确匹配（含子类型向上转型）。
2. **允许自动装箱/拆箱**的匹配（`int` → `Integer`）。
3. **允许可变参数**的匹配（`f(int...)`），必须放在最后。

```java
static void g(long x)  { System.out.println("long"); }
static void g(Integer x) { System.out.println("Integer"); }
g(1);   // → long（阶段 1 拓宽优先于阶段 2 装箱）

static void h(int... x) { System.out.println("varargs"); }
static void h(int x)    { System.out.println("exact"); }
h(1);   // → exact（阶段 3 才考虑可变参数）
```

> [!danger] `null` 参数的重载陷阱
> ```java
> static void p(String s) {}
> static void p(Object o) {}
> p(null);   // → String（更具体的类型胜出）
>
> static void q(String s) {}
> static void q(Integer i) {}
> q(null);   // 编译错误：ambiguous，两者互不构成子类型关系
> ```
> 更阴的是 `p(String)` 和 `p(StringBuilder)` 这种"兄弟类型"，调用方传 `null` 直接编译失败；如果传的是某个共同父类型的变量，就会静默选错分支。**新增重载时，务必确认没有 `null`/`Object` 的模糊调用点。**

> [!important] 字节码层面的"实锤"
> 方法在 class 文件里的唯一标识是 `name + descriptor`，`descriptor` **包含返回类型**：
> `f()V` 和 `f()Ljava/lang/String;` 是**两个不同的方法**，字节码可以共存，但 Java 源码不允许（"method is already defined"）。
> JVM 规范允许，Java 语言禁止 —— 这正是 **桥接方法（bridge method）** 能存在的前提。详见 [[3-泛型反射与注解]]。

## 七、内部类与 Lambda

### 7.1 四种内部类与字节码形态

| 类型 | 声明位置 | 字节码类名 | 是否有外部实例引用 | 能否有静态成员 |
| --- | --- | --- | --- | --- |
| 成员内部类 | 类体中，非 static | `Outer$Inner` | **有**（合成字段 `this$0`） | 仅 `static final` 常量（Java 16 起允许 static 成员） |
| 静态嵌套类 | 类体中，`static` | `Outer$Inner` | 无 | 可以 |
| 局部内部类 | 方法体内 | `Outer$1Inner` | 有（若引用了外部实例） | 否 |
| 匿名内部类 | 表达式位置 | `Outer$1`、`Outer$2`…按出现顺序编号 | 有（若引用外部实例） | 否 |

```java
public class Outer {
    private int x = 1;
    class Inner {                 // Outer$Inner，合成字段 this$0
        int get() { return x; }
    }
    static class Nested {}        // Outer$Nested，无外部引用
}
```

**合成成员的演化（说明行为，不追版本号细节）**：

- JDK 8 及更早：内部类访问外部私有成员，javac 会生成 `static synthetic access$000(Outer)` 之类的**包级静态桥接方法**，并在调用处升级为 `invokespecial`/`invokestatic`。反射 `getDeclaredMethods()` 能扫到这些 `access$xxx`，是"反射结果比源码多方法"的常见原因。
- 引入 **Nestmate（嵌套类友元）** 机制后：同一个顶层类下的所有嵌套类互为 nestmate，可以直接访问彼此的私有成员，`access$xxx` 桥接方法基本消失。这改变的是字节码细节，源码语义不变。

> [!warning] 内部类持有外部引用 = 内存泄漏
> 非静态内部类的实例**强引用外部实例**。只要内部类实例被长生命周期容器持有（`ThreadLocal`、静态缓存、监听器列表），外部实例（可能是个很大的 Service 或 Activity）就无法回收。
> 规避：不需要外部状态时一律用 `static` 嵌套类；确实需要时注意生命周期边界。

### 7.2 匿名内部类 vs Lambda

```java
Runnable r1 = new Runnable() {          // 生成 Outer$1.class
    @Override public void run() { System.out.println(this); }   // this = 匿名类实例
};
Runnable r2 = () -> System.out.println(this);                  // this = 外部类实例
```

| 维度 | 匿名内部类 | Lambda |
| --- | --- | --- |
| 编译产物 | 独立的 `.class` 文件（`Outer$1`） | **不生成 .class**；编译期只有 `invokedynamic` 引导 |
| 运行期实现 | 直接 new 该类的实例 | 首次执行时由 `LambdaMetafactory` 引导，生成/复用一个隐藏类 |
| `this` | 指向匿名类自身 | 指向**外围实例** |
| 能否声明字段/方法 | 可以 | 不可以（表达式，不是类） |
| 能否引用外部非 final 局部变量 | 不可以（必须 effectively final） | 不可以（必须 effectively final） |
| 实例复用 | 每次 `new` 都是新对象 | 无捕获的 lambda **可能**被缓存复用，同一实例 |
| 变量遮蔽 | 可以遮蔽外部变量名 | 参数不能与外部局部变量同名（编译错误） |
| 序列化 | 可行（外围可序列化时） | 需要显式转型为 `Serializable` 且捕获需可序列化 |
| 抽象方法数量 | 可多（实现多个方法 / 抽象类） | 必须恰好是**函数式接口**（一个抽象方法） |

**`invokedynamic` + `LambdaMetafactory` 做了什么**：引导方法接收"目标接口的方法签名""实现方法句柄""捕获参数类型"等信息，返回 `CallSite`。之后每处 lambda 求值就是一次 `getTarget().invokeExact(capturedArgs)`，JIT 能把这条链内联掉，所以 lambda 通常比匿名类**更快**（少一层类 + 更易内联）。

### 7.3 为什么局部变量必须 effectively final

```java
int base = 10;
Function<Integer,Integer> f = x -> x + base;   // base 被"捕获"
// base = 20;  // 编译错误：必须是 final 或 effectively final
```

**根因**：Java 的闭包是**按值捕获**。javac 把 `base` 的当前值**复制**进 lambda 的合成字段（或作为 `invokedynamic` 的捕获参数传给 `LambdaMetafactory`）。如果允许后续修改，就会出现"lambda 里的 `base` 和外面的 `base` 是两个变量"，语义混乱且与人的直觉不符。

语言设计者选了最简单一致的做法：**禁止修改**，让"复制"和"引用原变量"在观察上不可区分。

因此想在 lambda 里累加计数不能写：

```java
int[] count = {0};                       // 数组引用 effectively final，但元素可变
list.forEach(x -> count[0]++);

// 更好：用 Stream 的归约，或 AtomicInteger（并发时）
long n = list.stream().filter(...).count();
```

## 八、值传递：Java 只有值传递

**结论**：Java **永远按值传递**。对引用类型，传递的是**引用的副本**（可以理解为"对象地址的副本"）。

```java
public static void main(String[] args) {
    StringBuilder sb = new StringBuilder("hello");
    modify(sb);
    System.out.println(sb);        // helloworld  ← 对象内容被改了
    reassign(sb);
    System.out.println(sb);        // helloworld  ← 引用没被改
}
static void modify(StringBuilder s)    { s.append("world"); }  // 通过副本指向同一对象
static void reassign(StringBuilder s)  { s = new StringBuilder("new"); }
```

**交换失败的经典证明**：

```java
static void swap(Object a, Object b) { Object t = a; a = b; b = t; }  // 完全无效
```

两个形参只是调用方引用的副本，交换副本不影响调用方的变量。

> [!example] 三句话讲清这道题
> 1. Java 的参数传递机制是**值传递**，没有"引用传递"这种机制。
> 2. 对对象参数，传的是**引用的值**（地址副本），所以方法内**能改对象内容**（指向同一对象）。
> 3. 方法内**重新赋值形参**只改副本，调用方的引用不变；方法无法让调用方指向另一个对象。
>
> 因此"Java 到底是值传递还是引用传递"的正确答题姿势是：**它是值传递；对对象而言，传递的是引用的值，所以表现出'能改内容、不能改指向'的双重效果。**

## 九、常见陷阱速查表

| # | 陷阱 | 现象 | 规避 |
| --- | --- | --- | --- |
| 1 | `Integer` 缓存 | **==** 在 127/128 处行为突变 | 包装类一律 `equals` 或先拆箱 |
| 2 | 包装类拆箱 | `Integer` 为 null 时参与运算/比较 → NPE | 显式判空；避免三目混用 int |
| 3 | `String` 相等 | `new String("a") == "a"` 为 false | 一律 `equals` / `Objects.equals` |
| 4 | `finally` 覆盖 return | 返回值不对、异常被吞 | 禁止在 `finally` 里 return/throw |
| 5 | `switch` 穿透 | 漏写 `break` 继续执行后续 case | 用 `switch` 表达式（带 `->`）或全加 `break` |
| 6 | 浮点相等 | `0.1+0.2 == 0.3` 为 false | `BigDecimal` / 误差阈值 / `Double.compare` |
| 7 | `Arrays.asList` 定长 | `add`/`remove` 抛 `UnsupportedOperationException` | 需要可变用 `new ArrayList<>(Arrays.asList(...))` |
| 8 | `Arrays.asList(int[])` | 返回**长度为 1** 的 `List<int[]>` | 用 `Arrays.stream(arr).boxed().collect(...)` |
| 9 | `List.of()` / `Collections.unmodifiableList` | 不可变，`add` 抛异常 | 明确可变性契约；注意 `unmodifiableList` 只是**视图**，原 list 变了它也变 |
| 10 | `subList` 是视图 | 改子表影响原表；原表结构性修改后子表抛 `ConcurrentModificationException` | 需要独立副本用 `new ArrayList<>(list.subList(...))` |
| 11 | 增强 for 中删除元素 | `ConcurrentModificationException` | 用 `Iterator.remove()` / `removeIf` |
| 12 | `SimpleDateFormat` 线程不安全 | 偶发解析出错、日期错乱（内部 `Calendar` 共享可变状态） | 每线程新建 / `ThreadLocal` / `DateTimeFormatter`（不可变、线程安全） |
| 13 | `long` 运算溢出 | `365*24*3600*1000` 得负数 | 第一个操作数写成 `L` |
| 14 | `BigDecimal.equals` | `1.0` 与 `1.00` 不相等 | 比较用 `compareTo`，存储前 `setScale` 归一 |
| 15 | `Arrays.asList`/`Arrays.sort` 与可变对象 | 排序后 `HashMap` 里查不到 | 不要用可变字段参与 hash |
| 16 | 集合转数组 | `list.toArray()` 返回 `Object[]`，强转 `String[]` 抛 `ClassCastException` | `list.toArray(new String[0])` |
| 17 | `final` 引用 | 以为对象也不可变 | 引用不可变 ≠ 内容不可变 |
| 18 | `static final` 常量内联 | 改了常量值但下游没生效 | 全量重编译 / 改用非编译期常量 |
| 19 | 构造器调用可重写方法 | 子类字段为默认值 → NPE | 构造器只做"安全"初始化 |
| 20 | 内部类持有外部引用 | 内存泄漏 | 优先 `static` 嵌套类 |
| 21 | `OmitStackTraceInFastThrow` | 热路径异常突然没有栈轨迹 | 排查期用 `-XX:-OmitStackTraceInFastThrow` |
| 22 | `try-with-resources` 只打 message | suppressed 异常丢失 | `log.error(msg, e)` 打完整异常 |
| 23 | `String` 循环拼接 | O(n²) + 大量临时对象 | `StringBuilder` 并预估容量 |
| 24 | `char` 计数 | emoji 的 `length()` 是 2 | `codePointCount` |
| 25 | `Objects.hash` 装箱 | 高频调用产生垃圾 | 热点路径手写 hash 计算 |
