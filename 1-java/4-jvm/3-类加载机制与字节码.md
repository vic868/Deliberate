## 一、类加载的时机与生命周期

### 1.1 七个阶段总览

```text
                 ┌──────────────────────────────────────────────────┐
                 │              类加载的完整生命周期                 │
                 └──────────────────────────────────────────────────┘

   磁盘/网络/.class
        │
        ▼
   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌──────────┐   ┌──────┐   ┌──────┐
   │  加载  │──▶│  验证  │──▶│  准备  │──▶│  解析  │──▶│  初始化  │──▶│ 使用 │──▶│ 卸载 │
   └────────┘   └────────┘   └────────┘   └────────┘   └──────────┘   └──────┘   └──────┘
   读字节流      保证合法     分配内存     符号引用→    执行 <clinit>
   生成 Class    保证安全     赋零值       直接引用     赋真值 / static 块
                                                ▲
                                                └── 解析可以延迟到初始化之后（动态绑定）
```

| 阶段 | 一句话 | 关键动作 | 谁触发 |
|---|---|---|---|
| **加载 Loading** | 把字节流变成方法区里的数据结构 + 堆里的 `Class` 对象 | 通过全限定名获取二进制字节流；把静态存储结构转成方法区运行时数据结构；在**堆**中生成 `java.lang.Class` 对象作为访问入口 | 第一次主动使用 |
| **验证 Verification** | 保证字节流合法、不会危害虚拟机 | 文件格式 / 元数据 / 字节码 / 符号引用 四类验证 | 加载后 |
| **准备 Preparation** | 给**静态变量**分配内存并赋**零值** | `static int a = 10` 在此时 `a` 是 **0**，不是 10 | 验证后 |
| **解析 Resolution** | 常量池里的**符号引用**替换为**直接引用** | `#7 = Class java/lang/Object` → 指向方法区真实地址的指针 | 可延迟 |
| **初始化 Initialization** | 真正执行类中定义的 Java 代码 | 执行编译器生成的 `<clinit>()`，静态变量赋真值、执行 static 块 | 主动使用 |
| **使用 Using** | 正常 `new` / 调用 | —— | —— |
| **卸载 Unloading** | 类元信息从方法区回收 | 三个条件同时满足（见 §八） | GC |

> [!important] 最容易答错的一点：准备阶段赋零值
> `static int a = 10;` 在**准备**阶段 `a` 是 `0`，把 `a` 改成 10 是在**初始化**阶段由 `<clinit>` 完成的。
> 但 **`static final int A = 10;`（编译期常量）在准备阶段直接就是 10**——因为它被 `ConstantValue` 属性标记，不走 `<clinit>`。这是面试里区分"背过"和"理解过"的经典分界线。

### 1.2 加载阶段：谁在"读字节流"

"通过一个类的全限定名获取描述该类的二进制字节流"这句话里，**"获取"的方式是开放的**，这正是类加载器存在的意义，也是各种"黑科技"的入口：

| 字节流来源 | 典型场景 |
|---|---|
| 本地 `.class` 文件 | 常规编译产物 |
| ZIP/JAR 包 | `-cp app.jar`、fat jar |
| 网络 | Applet、远程类加载、RMI |
| 运行时动态生成 | **CGLIB / ASM / Javassist 生成的代理类**、Groovy 脚本类 |
| 加密文件 | 类加密保护（自定义加载器解密后再 `defineClass`） |
| JSP 编译产物 | Tomcat 把 JSP 编译成 Servlet `.class` 再加载 |

**数组类不通过类加载器创建**，由 JVM 直接在内存中构建；但其**元素类型**要靠类加载器加载——这一点是 §1.6 数组不触发初始化的根源。

### 1.3 验证阶段概览

四类验证的内容放在 §十一 详述。这里只记住它的**目标**：保证 `.class` 文件的字节流中包含的信息符合规范，不会危害虚拟机自身安全。因为 `.class` 不一定来自 javac——完全可以是手工构造的、恶意的字节码。

### 1.4 准备阶段：分配内存与零值

准备阶段为**类变量（static）**在方法区（JDK 8+ 是元空间）分配内存并设零值。**实例变量不在此列**——实例变量随对象在堆上分配，在 `<init>` 中初始化。

| 数据类型 | 零值 |
|---|---|
| `int` | 0 |
| `long` | 0L |
| `short` | 0 |
| `char` | `'\u0000'` |
| `byte` | 0 |
| `boolean` | **false** |
| `float` | 0.0f |
| `double` | 0.0d |
| 引用类型 | **null** |

### 1.5 准备阶段的"例外"：编译期常量

```java
public class Prepare {
    public static int a = 10;                  // 准备: 0  →  <clinit>: 10
    public static final int B = 20;            // 准备: 20（ConstantValue 直接赋值，无 <clinit> 代码）
    public static final String S = "abc";      // 准备: "abc"（字面量常量）
    public static final String S2 = "a" + "b"; // 准备: "ab"（编译期折叠）

    public static final int C = new java.util.Random().nextInt(); // 准备: 0  →  <clinit>
    public static final Object O = new Object();                  // 准备: null → <clinit>
    public static final String S3 = new String("abc");            // 准备: null → <clinit>
}
```

**判定标准只有一个：能否在编译期确定值。** 能确定的，javac 会在字段属性表里写一个 `ConstantValue`，JVM 在准备阶段直接赋值；不能确定的，编译进 `<clinit>`。

用 `javap -v` 可以肉眼区分：

```text
public static final int B;
  descriptor: I
  flags: ACC_PUBLIC, ACC_STATIC, ACC_FINAL
  ConstantValue: int 20          <-- 有这行 = 准备阶段赋真值

public static final int C;
  descriptor: I
  flags: ACC_PUBLIC, ACC_STATIC, ACC_FINAL
  （没有 ConstantValue）          <-- 值在 <clinit> 里算
```

> [!warning] 实战坑：编译期常量被"内联"进调用方的常量池
> ```java
> // 库 A 的 Constants.java
> public class Constants { public static final int TIMEOUT = 3000; }
>
> // 业务 B
> int t = Constants.TIMEOUT;   // 编译后 B.class 里 ldc 3000，与 A 无关
> ```
> 只改 A 重新编译、**不重新编译 B**，B 用的还是 3000。这就是"改了常量配置不生效"的真实原因。要避免就把常量放到配置文件，或改成 `static final` 但非编译期常量（如 `Integer.valueOf(3000)`）。
> 同样的机制导致：**引用编译期常量不会触发定义该常量的类的初始化**（§1.6）。

### 1.6 解析阶段：为什么可以延迟

解析是把常量池内的**符号引用**替换为**直接引用**的过程：符号引用是字面量（`java/lang/Object`、`<init>`、`(I)V` 这样的字符串），直接引用是能直接定位到内存地址的指针/偏移量。

JVMS 允许解析发生在**初始化之后**，这是为了支持 **Java 的动态绑定（晚期绑定）**：只有到真正执行到那一条字节码时，才知道该解析成哪个方法。所以才有：

- `invokedynamic` 的调用点可以在第一次执行时才绑定（lambda、字符串拼接，见 §10.6）
- 接口方法调用可以在运行时才确定实现类
- 这也是 `NoSuchMethodError` 会在**运行了几天之后**突然爆出来的原因：某条字节码第一次被执行时才去解析，此时类路径上的 jar 已被换过版本

### 1.7 初始化：六种"主动使用"

**有且仅有**这六种情况会触发类的初始化（JVMS 5.5）：

| # | 触发场景 | 对应字节码 |
|---|---|---|
| 1 | `new` 一个对象、读取或设置一个类的静态字段（**被 final 修饰的编译期常量除外**）、调用一个类的静态方法 | `new` / `getstatic` / `putstatic` / `invokestatic` |
| 2 | 使用 `java.lang.reflect` 包对类进行**反射调用**（如 `Class.forName("X")`） | 反射 API |
| 3 | 初始化一个类时，若其**父类还没初始化**，先初始化父类 | —— |
| 4 | 虚拟机启动时，用户指定的**主类**（含 `main` 的类） | —— |
| 5 | JDK 7+ 动态语言支持：`MethodHandle` 解析结果为 `REF_getStatic` / `REF_putStatic` / `REF_invokeStatic` 时 | `invokevirtual` on MethodHandle |
| 6 | JDK 8+：接口中定义了 **default 方法**时，其实现类的初始化会先触发该接口的初始化 | 接口 `<clinit>` |

### 1.8 三种"被动引用"——不触发初始化

这三个是面试原题的固定考点，必须能**解释机制**而不是背结论。

**场景 A：通过子类引用父类的静态字段，不初始化子类**

```java
class Parent { static { System.out.println("Parent init"); } static int VALUE = 1; }
class Child  extends Parent { static { System.out.println("Child init"); } }

public class Demo {
    public static void main(String[] args) {
        System.out.println(Child.VALUE);
    }
}
// 输出：Parent init / 1
// "Child init" 永远不会打印
```

机制：`Child.VALUE` 这条引用在编译后就是 `getstatic Parent.VALUE`，字节码里**根本没有出现 `Child` 这个常量池项**。加载 `Child` 类本身可能发生（比如为了解析继承链），但**初始化不会发生**。只有 `new Child()` 或 `Child.someChildStatic` 才触发。

**场景 B：通过数组定义引用类，不初始化该类**

```java
Parent[] arr = new Parent[10];   // 不会打印 "Parent init"
```

机制：`newarray` / `anewarray` 创建的是数组类 `[LParent;`，由 JVM 直接生成；数组的元素类型 `Parent` 只需要被**加载**（要确定元素大小与布局），不需要**初始化**。

**场景 C：引用编译期常量，不初始化定义常量的类**

```java
class Const { static { System.out.println("Const init"); } static final int X = 100; }
System.out.println(Const.X);     // 不打印 "Const init"
```

机制：`Const.X` 在编译期被内联进调用方的常量池（`ldc 100`），字节码里没有 `Const` 的符号引用，自然不需要初始化它。把 `X` 从 `static final int` 改成 `static final int X = f()`（非编译期常量），立刻就会打印。

## 二、`<clinit>` 与 `<init>`

### 2.1 `<clinit>` 的生成规则

`<clinit>()` 是**类初始化方法**，不是构造器。它的内容由编译器收集：

1. **所有静态变量的赋值语句**
2. **所有 `static {}` 静态代码块**

两者被**按源码出现顺序合并**，静态代码块只能访问定义在其**之前**的变量（但可以赋值不能读取，读取编译报错）。

```java
public class ClinitOrder {
    static int a = 1;                       // ①
    static { a = 2; b = 3; }                // ②  b 可以先赋值
    static int b = 4;                       // ③  覆盖成 4
    static { System.out.println(a + "," + b); } // ④ 输出 2,4
}
// 最终 a=2, b=4
```

对应的 `<clinit>`（示意）：

```text
static {};
  Code:
     0: iconst_1
     1: putstatic     #2    // a = 1                 ①
     4: iconst_2
     5: putstatic     #2    // a = 2                 ②
     8: iconst_3
     9: putstatic     #3    // b = 3（此处是 3）
    12: iconst_4
    13: putstatic     #3    // b = 4                 ③ 覆盖
    16: getstatic     #4    // System.out
    ...
```

**一个类可以没有 `<clinit>`**：如果它既没有静态变量赋值也没有 static 块，javac 不生成该方法。接口的 `<clinit>` 只会处理非编译期常量的字段。

### 2.2 父类 `<clinit>` 先于子类

JVM 保证在子类 `<clinit>` 执行**之前**，父类的 `<clinit>` 已经执行完毕。这带来一个著名陷阱：

```java
class Parent {
    static int A = 10;
    static { A = 20; }
}
class Child extends Parent {
    static int B = A;   // 读父类静态字段
}
// 若父类未初始化，先跑 Parent.<clinit>，A 变成 20，然后 B = 20
// 如果 Child 的 <clinit> 抢先执行（不可能），B 就会是 10
```

> [!danger] 父类 `<clinit>` 中调用被子类重写的方法
> ```java
> class Parent {
>     Parent() { print(); }          // 构造器里调用可重写方法
>     void print() { System.out.println("parent"); }
> }
> class Child extends Parent {
>     int value = 100;
>     Child() { super(); }
>     @Override void print() { System.out.println("child: " + value); }
> }
> new Child();   // 输出 "child: 0"——value 还没被赋值（<init> 中初始化）
> ```
> 这是"构造器里不要调用可重写方法"的经典理由，和类初始化是同源的：**初始化顺序决定字段可见值**。

### 2.3 线程安全与类初始化锁

**JVM 保证 `<clinit>` 在多线程环境下被正确地加锁同步**。如果多个线程同时初始化一个类，只有一个线程执行 `<clinit>`，其余线程阻塞等待，执行完后其他线程不会再执行。这是 java 语言规范**自 Java 1.0 起就有的保证**，也是"静态内部类单例"能成立的基础：

```java
public class Singleton {
    private Singleton() {}
    private static class Holder {                 // 类加载器保证线程安全
        private static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

**优雅之处**：`getInstance()` 调用时才初始化 `Holder`，实现了**懒加载**；而线程安全由 JVM 的类初始化锁**免费**提供，不需要任何 `synchronized`。对比双重检查锁（DCL），后者还必须给 `instance` 加 `volatile` 否则有指令重排问题（见 [[4-多线程与内存模型]]）。

### 2.4 类初始化死锁——真实生产事故

正因为 `<clinit>` 执行时要持有**该类对应的初始化锁**并且**线程会阻塞等待**，两个类的静态初始化互相引用时就会死锁。

```java
// 类 A
public class A {
    static {
        try { Thread.sleep(1000); } catch (InterruptedException ignored) {}
        System.out.println("A: " + B.value);   // 触发 B 的初始化
    }
    static int value = 1;
}

// 类 B
public class B {
    static {
        System.out.println("B: " + A.value);   // 触发 A 的初始化
    }
    static int value = 2;
}

// main 里两个线程分别触发
new Thread(() -> { A.value = 1; System.out.println(A.value); }).start();  // 线程1 持有 A 的锁，等 B 的锁
new Thread(() -> { B.value = 2; System.out.println(B.value); }).start();  // 线程2 持有 B 的锁，等 A 的锁
```

**现象**：应用启动就卡住，线程 dump 里能看到两个线程停在 `<clinit>` 上，栈顶是类初始化相关的帧。典型形态（JDK 8 示意）：

```text
"Thread-0" ... waiting on condition
   at com.demo.B.<clinit>(B.java:5)
   at com.demo.A.<clinit>(A.java:4)     <-- 持有 A 的初始化锁，等 B

"Thread-1" ... waiting on condition
   at com.demo.A.<clinit>(A.java:4)
   at com.demo.B.<clinit>(B.java:5)     <-- 持有 B 的初始化锁，等 A
```

**真实案例**：日志框架的静态初始化里去做类扫描、SPI 加载；工具类的 static 块里调用了另一个模块的静态方法，而那个模块反过来又引用了本类。**排查方式**：`jstack` 看到 `<clinit>` 互相等待时，直接按类名查找静态初始化里的跨类调用，或临时用 `-Xlog:class+load` / `-verbose:class` 看是谁先加载的。

**修复手段**：把静态初始化里的跨类调用改成惰性（首次使用时才初始化），或者显式指定初始化顺序（在一个入口类里按序触发）。

### 2.5 `<init>` 与构造器

`<init>()` 是**实例构造器**，由 javac 生成，对应源码里的构造器 + 实例变量初始化 + 实例代码块。

| 对比项 | `<clinit>` | `<init>` |
|---|---|---|
| 触发时机 | 类初始化阶段，**一次** | 每次 `new`，**多次** |
| 是否有参数 | 无参（JVM 规定） | 与源码构造器签名一致，可有参 |
| 是否必须 | 可有可无 | 有构造器就有 |
| 线程安全 | JVM 加锁保证 | 不保证（对象未逸出时才安全） |
| 父类调用 | JVM 自动保证父类先执行 | 字节码里显式 `invokespecial` 父类 `<init>` |

`<init>` 的字节码顺序：`aload_0` → `invokespecial Object.<init>` → 实例变量赋值 → 实例代码块 → 构造器体。**父类构造器一定在最前面**，这也解释了 §2.2 里 `value` 打印为 0 的现象。

## 三、类加载器

### 三.0 本节定位

类加载器 = "通过全限定名获取字节流"的**实现者**。它的层次结构、委派机制、以及被打破的方式，构成了 Java 模块化与隔离能力的基础。

### 3.1 三层类加载器

| 加载器 | 实现语言 | 加载范围 | JDK 8 类名 | JDK 9+ 类名 | `getClassLoader()` |
|---|---|---|---|---|---|
| **启动类加载器 Bootstrap** | **C++（HotSpot 内）** | `JAVA_HOME/lib` 下的核心库、`-Xbootclasspath` 指定路径；JDK 9+ 是 `java.base` 等少数核心模块 | 无 Java 类 | 无 Java 类 | **null** |
| **平台/扩展类加载器** | Java | JDK 8：`JAVA_HOME/lib/ext`、`java.ext.dirs`；JDK 9+：平台类加载器，加载 `java.sql`、`java.desktop` 等平台模块 | `sun.misc.Launcher$ExtClassLoader` | `PlatformClassLoader` | 非 null |
| **应用程序类加载器** | Java | `-classpath` / `-cp` / `CLASSPATH`，即应用与第三方 jar | `sun.misc.Launcher$AppClassLoader` | `AppClassLoader` | 非 null |

> [!note] 版本差异要记住的两点
> 1. **JDK 8 → 9**：`ExtClassLoader` 被 `PlatformClassLoader` 取代（扩展机制被模块化取代，`lib/ext` 不再有意义）。
> 2. **JDK 16/17 起 JDK 内部 API 被强封装**（`jdk.internal.*` 默认不允许反射访问），所以"用反射改 `ClassLoader` 内部字段"这类技巧在 17+ 上基本失效，需要显式 `--add-opens`。这是从 8 升级到 17 时最常见的破坏性变更之一。
> 3. **Bootstrap 加载器是 C++ 实现，在 Java 里表现为 `null`**，所以 `String.class.getClassLoader()` 返回 `null`，而不是某个对象。这也意味着 bootstrap 加载的类**永远不可能被卸载**。

### 3.2 `ClassLoader` 核心 API

| 方法 | 作用 | 是否建议覆盖 |
|---|---|---|
| `loadClass(String)` | **委派模型入口**，`protected`，先查已加载→委派父→自己 `findClass` | ❌ 覆盖它会破坏双亲委派 |
| `findClass(String)` | 父加载器失败后，自己去加载字节流 | ✅ **推荐覆盖点** |
| `defineClass(String, byte[], int, int)` | 把字节数组定义成 `Class`，**final** | ❌ 不能覆盖，只能调用 |
| `findLoadedClass(String)` | 查自己已加载的类（缓存） | ❌ |
| `resolveClass(Class)` | 链接指定的类 | 一般不用 |
| `getParent()` | 拿父加载器（不是继承关系，是**组合**） | ❌ |
| `getClassLoadingLock(String)` | 取加载该类时的锁（支持并行加载） | ❌ |

### 3.3 自定义类加载器：正确写法

```java
public class DiskClassLoader extends ClassLoader {

    private final Path root;

    public DiskClassLoader(Path root, ClassLoader parent) {
        super(parent);                 // 显式指定父加载器，保持委派链
        this.root = root;
    }

    /** 只覆盖 findClass：仍然走双亲委派，父加载器找不到时才轮到自己 */
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        byte[] bytes = readBytes(name);
        if (bytes == null) {
            throw new ClassNotFoundException(name);
        }
        return defineClass(name, bytes, 0, bytes.length);
    }

    private byte[] readBytes(String binaryName) {
        String relative = binaryName.replace('.', '/') + ".class";
        Path file = root.resolve(relative);
        if (!Files.isRegularFile(file)) return null;
        try {
            return Files.readAllBytes(file);
        } catch (IOException e) {
            return null;
        }
    }
}
```

关键点：

1. **`defineClass` 是 `final`**，不允许覆盖，它是唯一的"字节数组 → Class 对象"入口。
2. **同一个加载器实例对同一个全限定名只能 `defineClass` 一次**，第二次抛 `LinkageError: attempted duplicate class definition for name: xxx`。
3. **JDK 11+ 禁止定义 `java.*` 包下的类**，`defineClass("java.lang.Foo", ...)` 会抛 `SecurityException: Prohibited package name: java.lang`（JDK 8 时代可以通过 `-Xbootclasspath` 绕过，现在不行了）。
4. 想**重载**同一个类，必须 `new` 一个新的加载器实例——这是热部署的根基（§6.5）。

### 3.4 `findClass` vs `loadClass`：一字之差，委派存亡

| | 覆盖 `findClass` | 覆盖 `loadClass` |
|---|---|---|
| 双亲委派 | **保留**（父类 `loadClass` 的委派逻辑仍然生效） | **破坏**（取决于你怎么实现） |
| 代码量 | 只需写"读字节 + defineClass" | 要自己实现缓存、委派、加锁、resolve |
| 典型用途 | 从磁盘/网络/数据库加载类；Tomcat 的 `WebappClassLoader`（内部） | Servlet 规范要求 Web 应用优先；热部署；OSGi |
| 风险 | 低 | 高，容易漏掉 `findLoadedClass` 缓存导致重复定义 |

**覆盖 `loadClass` 的标准反面教材**：

```java
// 错误示范：完全绕开父加载器
@Override
public Class<?> loadClass(String name) throws ClassNotFoundException {
    byte[] b = readBytes(name);            // 直接自己加载
    return defineClass(name, b, 0, b.length);
}
```

后果：`java.lang.String` 也会被这个加载器尝试加载，导致 **`ClassCastException` 满天飞**，甚至因为定义了 `java.*` 包而直接失败。**正确姿势**是保留核心类的委派：

```java
@Override
protected Class<?> loadClass(String name, boolean resolve) throws ClassNotFoundException {
    // 1. 核心类必须交给父加载器，否则类型系统会崩
    if (name.startsWith("java.") || name.startsWith("javax.") || name.startsWith("sun.")
        || name.startsWith("jdk.") || name.startsWith("org.w3c.") || name.startsWith("org.xml.")) {
        return super.loadClass(name, resolve);
    }
    // 2. 先查自己有没有加载过，避免 duplicate class definition
    Class<?> c = findLoadedClass(name);
    if (c != null) return c;
    // 3. 自己先加载（打破双亲委派的"自己优先"）
    try {
        c = findClass(name);
    } catch (ClassNotFoundException e) {
        c = super.loadClass(name, resolve);   // 4. 失败再委派
    }
    if (resolve) resolveClass(c);
    return c;
}
```

> [!warning] `findLoadedClass` 不是可选项
> 用 `loadClass` 自定义时**必须先 `findLoadedClass`**。JVM 层面同一个加载器 + 同一个名字只能有一个"定义类"，第二次 `defineClass` 会抛 `LinkageError`（见 §七）。很多人写自定义加载器时漏掉这一步，在"类被引用两次"时就炸。另外：**`loadClass` 的委派不是继承来的，是 `super.loadClass` 里的逻辑**，你覆盖时它就不存在了。

### 3.5 用代码验证父加载器链

```java
public class LoaderChain {
    public static void main(String[] args) throws Exception {
        print("java.lang.String", String.class.getClassLoader());
        print("java.sql.Driver", java.sql.Driver.class.getClassLoader());
        print("com.demo.LoaderChain", LoaderChain.class.getClassLoader());
        print("int[]", int[].class.getClassLoader());
        print("String[]", String[].class.getClassLoader());
    }

    private static void print(String label, ClassLoader cl) {
        StringBuilder sb = new StringBuilder();
        while (cl != null) {
            sb.append(cl.getClass().getName()).append(" -> ");
            cl = cl.getParent();
        }
        sb.append("null(Bootstrap)");
        System.out.printf("%-24s %s%n", label, sb);
    }
}
```

JDK 17 上的输出（示意）：

```text
java.lang.String          null(Bootstrap)
java.sql.Driver           jdk.internal.loader.ClassLoaders$PlatformClassLoader -> null(Bootstrap)
com.demo.LoaderChain      jdk.internal.loader.ClassLoaders$AppClassLoader -> jdk.internal.loader.ClassLoaders$PlatformClassLoader -> null(Bootstrap)
int[]                     null(Bootstrap)
String[]                  null(Bootstrap)          <-- 数组类型随元素类型，String 由 Bootstrap 加载
```

注意 `java.sql.Driver` 在 JDK 9+ 由 **Platform** 加载器加载，而 JDK 8 是 **ExtClassLoader** 加载——这是升级时"看起来一样的 API，实际加载器变了"的一个真实例子，直接影响 SPI 的行为（§6.1）。

## 四、双亲委派模型

### 4.1 流程

```text
                        loadClass("com.demo.Foo")
                                 │
                                 ▼
        ┌────────────────────────────────────────────────┐
        │ 1. findLoadedClass  ← 自己加载过就直接返回       │
        └────────────────────────────────────────────────┘
                                 │ 没有
                                 ▼
        ┌────────────────────────────────────────────────┐
        │ 2. parent.loadClass  ← 交给父加载器（递归）      │
        │    parent == null 时 → findBootstrapClassOrNull │
        └────────────────────────────────────────────────┘
                                 │ 父加载器也找不到
                                 ▼
        ┌────────────────────────────────────────────────┐
        │ 3. findClass(name)   ← 终于轮到自己加载         │
        └────────────────────────────────────────────────┘
                                 │ 还是找不到
                                 ▼
                     throw ClassNotFoundException
```

**顺序关键点：自底向上检查是否已加载，自顶向下尝试加载。** 也就是"先委派、后自己"。

### 4.2 源码（`java.lang.ClassLoader#loadClass`，JDK 8/17 逻辑一致）

```java
protected Class<?> loadClass(String name, boolean resolve)
        throws ClassNotFoundException {
    synchronized (getClassLoadingLock(name)) {
        // 1) 是否已加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            long t0 = System.nanoTime();
            try {
                // 2) 委派给父加载器
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器找不到，继续往下
            }
            if (c == null) {
                long t1 = System.nanoTime();
                // 3) 自己加载
                c = findClass(name);
                // 统计与记录（此处省略）
            }
        }
        if (resolve) {
            resolveClass(c);
        }
        return c;
    }
}
```

两个细节值得讲：

- **`getClassLoadingLock(name)`**：JDK 7+ 引入，只有"具备并行能力"（`registerAsParallelCapable`）的加载器才会按类名分锁，否则退化为锁 `this`。这直接影响**类加载死锁**：非并行加载器在并发加载时会互相阻塞。
- **`findBootstrapClassOrNull`**：`parent == null` 时说明委派链已经到顶，去问 C++ 的 Bootstrap。

### 4.3 两个好处（以及"为什么需要它"）

| 好处 | 机制 | 反面例子（没有委派会怎样） |
|---|---|---|
| **保证核心类库的类型安全** | `java.lang.String` 无论如何都只能由 Bootstrap 加载，用户自定义加载器无法用同名类替换 JDK 的 `String` | 恶意代码可以自定义 `java.lang.String` 注入后门；`instanceof`/强转全部失效 |
| **避免类的重复加载** | 同一个类通过委派链最终只有一个定义加载器，全局唯一 | 同一个类被多个加载器各加载一份，`ClassCastException`、静态变量出现多份副本、内存爆炸 |

**"为什么需要"的深层原因**：Java 的**类型系统建立在"类的运行时身份 = 定义加载器 + 全限定名"之上**。双亲委派是保证这个身份**稳定且唯一**的最简单规则。打破委派不是"错误"，而是必须付出代价去换取隔离/优先/动态性。

> [!tip] 面试标准答法
> 先给流程（自底向上检查、自顶向下加载），再给两个好处（安全 + 去重），最后主动补一句"但它不是强制的规范，只是推荐实现，因为它解决不了 SPI 这种『父加载器要加载子加载器路径下的类』问题"——这句话是引出打破委派的最佳钩子。

## 五、打破双亲委派的真实场景

这是本篇的**重点**。面试里能讲清下面 3 个以上场景，就已经超过绝大多数候选人。

### 5.1 SPI / JDBC：父加载器要加载子加载器路径下的类

**问题**：

- `java.sql.DriverManager` 在 `java.sql` 模块里，由 **Platform（JDK 8 是 Ext）** 加载。
- 具体驱动如 `com.mysql.cj.jdbc.Driver` 在**应用 classpath** 里，由 **App** 加载。
- 按双亲委派，Platform 的父是 Bootstrap，**它永远看不到 App 加载器路径下的驱动**。
- 但 `DriverManager` 又必须在初始化时把驱动注册进来。

**解法：线程上下文类加载器（Thread Context ClassLoader，TCCL）**

```java
// java.sql.DriverManager 静态初始化里（JDK 8 简化版）
static {
    loadInitialDrivers();
}

private static void loadInitialDrivers() {
    // 关键：用 TCCL 去加载 "app classpath 下的实现类"
    ServiceLoader<Driver> loadedDrivers =
            ServiceLoader.load(Driver.class);       // 内部：Thread.currentThread().getContextClassLoader()
    Iterator<Driver> driversIterator = loadedDrivers.iterator();
    while (driversIterator.hasNext()) {
        driversIterator.next();                     // 触发驱动静态块 → 向 DriverManager 注册
    }
}
```

`ServiceLoader.load(Class)` 的实现（核心一行）：

```java
public static <S> ServiceLoader<S> load(Class<S> service) {
    ClassLoader cl = Thread.currentThread().getContextClassLoader();  // ★ 打破委派的钥匙
    return new ServiceLoader<>(service, cl);
}
```

TCCL 是"父加载器借用子加载器视野"的标准后门：**加载器本身还在用父的，但"用谁来加载"这件事被参数化了**。所以：

| 要点 | 说明 |
|---|---|
| 默认值 | 子线程默认继承父线程的 TCCL；主线程默认是 App 加载器 |
| 线程池陷阱 | `ThreadPoolExecutor` 的线程是复用的，**TCCL 不会随任务切换自动还原**，会造成类加载器泄漏（§八） |
| 正确姿势 | 框架里用 `ClassLoaderUtils.getDefaultClassLoader()`，或保存/恢复 TCCL；Spring 的 `ClassUtils.getDefaultClassLoader()` 就是先取 TCCL，为空再退到本类的加载器 |

**JDBC 4 之后为什么能自动发现驱动**：JDBC 4 起驱动 jar 里带有 **`META-INF/services/java.sql.Driver`** 文件，内容是实现类全限定名。`ServiceLoader` 读取它并实例化，驱动在静态块里调 `DriverManager.registerDriver(new Driver())`（或由 ServiceLoader 帮它注册）。所以 `Class.forName("com.mysql.jdbc.Driver")` 这行"经典代码"在 JDBC 4+ 已经**不必要**了——但很多老项目还在写，因为 JDBC 3 的驱动没有 SPI 文件。

> [!example] 直接验证 SPI
> ```text
> unzip -p mysql-connector-j-8.x.jar META-INF/services/java.sql.Driver
> com.mysql.cj.jdbc.Driver
> ```
> 再看 JDK 自带的：`java.sql.Driver` 模块 `java.sql` 中的 `META-INF/services/java.sql.Driver`，JDK 8 里内容是 `sun.jdbc.odbc.JdbcOdbcDriver`（JDK 8 后已移除）。

### 5.2 Tomcat：Web 应用优先 + 应用隔离

**为什么每个 Web 应用一个 `WebappClassLoader`**：

| 需求 | 如果共用一个加载器会怎样 |
|---|---|
| **应用隔离** | 应用 A 用 Spring 4，应用 B 用 Spring 5，同名类 `org.springframework.core.X` 只能有一份，必然冲突 |
| **静态变量隔离** | 单例对象在容器级别只有一份，两个应用的"单例"会互相污染（这是最难查的一类 bug） |
| **热部署** | 无法单独卸载某个应用的类（类卸载要求它的加载器先被回收） |

Tomcat 的加载器层次：

```text
Bootstrap (JVM)
   │
   ├── System / App ClassLoader  （Tomcat 启动脚本的 classpath：bootstrap.jar）
   │
   └── Common ClassLoader （catalina.properties 的 common.loader：Tomcat 自身 + 公共库）
          │
          ├── Catalina ClassLoader   （Tomcat 内部类，对 Web 应用不可见）
          │
          └── Shared ClassLoader     （所有 Web 应用共享，默认存在但通常留空）
                 │
                 └── WebappClassLoader × N   （每个 <Context> 一个，加载 WEB-INF/classes 与 WEB-INF/lib/*.jar）
                        │
                        └── JasperLoader  （JSP 编译产物，支持 JSP 单独热加载）
```

**打破委派的地方**：`WebappClassLoaderBase#loadClass` 的顺序（默认 `delegate = false`）：

```text
1. findLoadedClass             ← 本地缓存
2. JVM 的 Bootstrap/JRE 类      ← 硬编码优先，保证 java.* 不被 Web 应用覆盖
3. 如果 delegate == true 或 资源被 filter 匹配 → 委派给 parent（Common/Shared）
4. findClass  ← ★ 先自己找（WEB-INF/classes、WEB-INF/lib）
5. 委派给 parent（兜底）
6. 抛 ClassNotFoundException
```

也就是**第 4 步在第 5 步之前**——"我用我的，你没有我再用你的"。这就打破了"先委派父类"的规则。

**与热部署的关系**：Tomcat 重载一个应用时，做的是：

1. 停止该 Context（销毁 Servlet、Filter、Listener）
2. **丢弃（不再引用）`WebappClassLoader` 实例**
3. GC 回收该加载器 → 触发其加载的所有类卸载 → 释放元空间
4. 新建 `WebappClassLoader`，重新加载

所以**热部署失败/内存增长**的根因永远是"老加载器还被引用着"，而不是"类没被卸载"（§八）。Tomcat 提供 `<Loader delegate="true"/>` 切回严格委派，也提供 `WebappClassLoaderBase.clearReferences()` 在销毁时清掉 TCCL、JDBC 驱动、`ThreadLocal` 等引用。

### 5.3 OSGi 与模块化：网状委派

OSGi 里每个 **Bundle** 有自己的类加载器，但委派不是树，而是一张**图**：

```text
                 ┌──────────────┐
                 │  Bootstrap   │
                 └───────┬──────┘
                         │
                 ┌───────▼──────┐
                 │  Framework   │
                 └───────┬──────┘
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   ┌─────────┐      ┌─────────┐     ┌─────────┐
   │Bundle A │◀────▶│Bundle B │◀───▶│Bundle C │
   └─────────┘ Import/Export Package  └─────────┘
        │                                   ▲
        └───────────────────────────────────┘
```

| 规则 | 说明 |
|---|---|
| 委派对象不是"固定父加载器" | 而是按 `Import-Package` / `Require-Bundle` 声明的**导出者**决定 |
| 包级可见性 | 同一个包可以同时存在于多个 Bundle，只有导出的包可见 |
| 启动顺序无关 | 依赖关系由框架在运行时解析 |
| 好处 | 真正的模块隔离 + 版本共存（同一个包的两个版本同时在线） |

OSGi 是"打破委派"最激进的形式，代价是复杂度极高（类加载失败类问题难排查），所以主流业务系统很少直接用，但 **Java 9 的 JPMS 模块系统**吸收了它的思想（`module-info.java` 的 `requires` / `exports`），只是 JPMS 的委派仍然是**严格的层次结构**（模块图是有向无环图，不是网状）。

### 5.4 Spring Boot 的 `LaunchedURLClassLoader` 与 fat jar

**问题**：Spring Boot 的可执行 jar 把依赖 jar 放在自己的 `BOOT-INF/lib/` 目录下，标准 `URLClassLoader` 只能加载 `jar:file:/app.jar!/` 这一层，**无法加载 jar 里的 jar**。

**解法**：Spring Boot 实现了一套自定义的 `URL` 协议 + 类加载器。

| 组件 | 作用 |
|---|---|
| `JarLauncher` / `WarLauncher` | 可执行 jar 的 `Main-Class`，先建加载器再反射调用真正的 `main` |
| `LaunchedURLClassLoader` | 继承 `URLClassLoader`，URL 列表是 `BOOT-INF/classes/` 和每个 `BOOT-INF/lib/*.jar` |
| `org.springframework.boot.loader.jar.Handler` | 注册 `jar:` 协议处理器，支持 `jar:file:/app.jar!/BOOT-INF/lib/dep.jar!/com/Foo.class` 这样的**嵌套 URL** |
| `LaunchedClassLoader` | Spring Boot 3.2 起的类名（包结构有调整），能力相同 |

`JarLauncher` 的核心逻辑（简化）：

```java
protected void launch(String[] args) throws Exception {
    // 1. 注册嵌套 jar 的 URL 协议处理器
    JarFile.registerUrlProtocolHandler();
    // 2. 创建只加载 BOOT-INF/classes 与 BOOT-INF/lib 的加载器，
    //    父加载器是 AppClassLoader（保证 java.* 与 -cp 里的类走父）
    ClassLoader classLoader = createClassLoader(getClassPathArchives());
    // 3. 用新加载器反射调用业务 main，避免与启动器自己的类混在一起
    launch(args, getMainClass(), classLoader);
}
```

**委派行为**：`LaunchedURLClassLoader` **并没有打破双亲委派**，它只是扩展了"自己"能加载哪些 URL。所以 Spring Boot 应用里如果 `-cp` 和 `BOOT-INF/lib` 有同名类，**`-cp` 里的会赢**——这解释了很多"依赖冲突但只在一台机器上出现"的诡异问题（比如某些容器把 `-cp` 设成了通用目录）。

> [!tip] 为什么 Spring Boot 要自己做而不直接让 JVM 支持嵌套 jar
> 标准 `URLClassLoader` 的 URL 只能指向文件系统或单层 jar，改成支持嵌套需要改 JDK。Spring Boot 选择了"自己实现协议"，代价是启动器与业务类必须**隔离加载**，因此才有 `JarLauncher` 反射 `main` 这一步。

### 5.5 热部署 / 热替换

**核心事实：同一个全限定名，被两个不同的加载器加载，就是两个不同的 `Class` 对象。** 这是热部署能成立的唯一原因。

| 方案 | 原理 | 能力边界 |
|---|---|---|
| **重启 ClassLoader（Spring Boot DevTools / Tomcat reload）** | 丢弃整个加载器，重建 | 只能"重载应用类"，库类走父加载器不受影响；**不能修改类结构后保留对象状态** |
| **JRebel / 商业工具** | 用自己的加载器 + 字节码增强，避免重建加载器 | 可保留状态，成本高 |
| **`Instrumentation.retransformClasses`** | Agent 在运行时**替换已加载类的方法体** | **真正的"热替换"**，但受限制：不能增删字段/方法、不能改签名（多数情况下） |
| **`-XX:+TraceClassUnloading` 观察** | 看类是否真被卸载 | —— |

最小的"热替换"演示（用新加载器加载同一个类）：

```java
public class HotSwap {
    public static void main(String[] args) throws Exception {
        DiskClassLoader l1 = new DiskClassLoader(Path.of("/tmp/v1"));
        DiskClassLoader l2 = new DiskClassLoader(Path.of("/tmp/v2"));

        Class<?> c1 = l1.loadClass("com.demo.Plugin");
        Class<?> c2 = l2.loadClass("com.demo.Plugin");

        System.out.println(c1 == c2);                 // false  ← 两个不同的类
        System.out.println(c1.getName().equals(c2.getName())); // true
        System.out.println(c1.getClassLoader() == c2.getClassLoader()); // false

        Object o1 = c1.getDeclaredConstructor().newInstance();
        try {
            // 用 c2 的类型去接收 c1 的实例：ClassCastException
            Object o2 = c2.cast(o1);
        } catch (ClassCastException e) {
            System.out.println("CCE: " + e.getMessage());
        }
    }
}
```

## 六、类的唯一性

### 6.1 定义

> **在 JVM 中，一个类的"运行时唯一身份" = 定义它的类加载器实例 + 类的全限定名。**

这句话是理解 `ClassCastException`、`LinkageError`、`instanceof` 异常的**唯一钥匙**。注意两个细节：

1. 是**加载器实例**（对象身份 **==**），不是加载器的类名。两个 `new DiskClassLoader(...)` 就是两个不同的命名空间。
2. 是**定义加载器（defining loader）**，不是"最先尝试加载的加载器"。双亲委派下，真正 `defineClass` 的是层级更高的那个。

### 6.2 `ClassCastException`：同名类不同加载器

```text
类加载器 L1 ──定义──▶ com.demo.Plugin  (记为 Plugin@L1)
类加载器 L2 ──定义──▶ com.demo.Plugin  (记为 Plugin@L2)

Plugin@L1 与 Plugin@L2 是两个完全独立的类型：
  · 不能互相强转
  · 不能作为同一个方法参数互相传递
  · 不能放进同一个强类型集合
  · 静态变量各有一份
```

典型线上现象：

```text
java.lang.ClassCastException: com.demo.Plugin cannot be cast to com.demo.Plugin
```

**这行报错的"诡异点"在于两个类名一模一样。** 新人看到会以为是 JDK bug。真正的原因是：对象来自 `WebappClassLoaderA`，而接收方的方法签名属于 `WebappClassLoaderB`——通常发生在：

- 应用把某个类放在 `WEB-INF/lib` 里，而容器（或 `-cp`）里也有一份同名类，Part 走父加载器、Part 走自己
- 两个不同版本的同一个工具包被不同加载器加载
- 用 `-cp` 同时包含了某个 jar 和它的 shaded 版本
- 线程池里的任务由 A 应用提交、B 应用的加载器执行

**排查手段**：在异常处打印 `obj.getClass().getClassLoader()` 与目标参数的加载器，对比是否相同。或者 `jmap -clstats` 看这个类名是否被多个加载器加载。

### 6.3 `LinkageError` 家族

| 异常 | 触发条件 | 典型场景 |
|---|---|---|
| `LinkageError: attempted duplicate class definition for name: X` | 同一个加载器对同一个名字 `defineClass` 两次 | 自定义加载器漏了 `findLoadedClass` 缓存 |
| `NoClassDefFoundError` | 编译期存在、运行时找不到定义（或类初始化失败过） | **比 `ClassNotFoundException` 更常见的"依赖冲突"表现**；上次初始化抛异常后，第二次访问直接报这个 |
| `ClassNotFoundException` | `Class.forName` / `loadClass` 显式加载时找不到 | 类名拼错、jar 缺失 |
| `NoSuchMethodError` / `NoSuchFieldError` | 解析符号引用时目标不存在 | **jar 版本不一致**（编译用 A 版本，运行用 B 版本）——最典型的"运行几天后突然爆" |
| `IncompatibleClassChangeError` | 类结构发生不兼容变化（如接口变抽象类） | 升级 jar 时未重新编译依赖方 |
| `VerifyError` | 字节码验证失败 | 字节码增强/插桩工具生成的字节码不合法 |
| `ExceptionInInitializerError` | `<clinit>` 抛出异常 | 静态块里 `NullPointerException`、配置读取失败 |
| `UnsatisfiedLinkError` | native 库找不到 | JNI 库路径、平台不匹配 |

> [!important] `NoClassDefFoundError` 与 `ExceptionInInitializerError` 的连锁关系
> 如果类 `X` 的 `<clinit>` 第一次执行时抛了异常，JVM 会把 `X` 标记为**初始化失败（erroneous）**，此后所有对 `X` 的主动使用都会直接抛 `NoClassDefFoundError`（cause 是首次的 `ExceptionInInitializerError`），**不会**再尝试初始化。
> 这是线上"重启前一直报、重启后好了"的常见根因：静态块里读了还没就绪的下游依赖。排查时一定要看 **`Caused by`**，别只看最外层。

### 6.4 `instanceof` 与 `equals` 的跨加载器行为

| 操作 | 跨加载器（两个同名类）的结果 | 原因 |
|---|---|---|
| `obj instanceof Foo` | **false**（或编译期就报错） | `instanceof` 比较的是**运行时类型身份**，两者不同 |
| `(Foo) obj` | **ClassCastException** | 同上 |
| `Object.equals` | false | 默认实现就是 **==**（引用比较） |
| 自定义 `equals` 里用了 `instanceof` / `getClass()` | **大概率返回 false** | 类型判断失败 |
| `hashCode` | 可能相同 | 只跟字段内容有关，与类身份无关 |
| `Object.equals(x, y)`（JDK 7+） | false | 内部先 `x == y` 再 `x.equals(y)` |

**实务结论**：跨加载器传递对象时，**只能通过 JDK 接口或共享父加载器能看到的接口**。这就是插件化框架为什么要把"插件 API"放在父加载器（如 `SharedClassLoader`）、并要求插件只通过接口通信的原因。

## 七、类的卸载

### 7.1 三个条件（必须同时满足）

1. **该类的所有实例都已被回收** —— 堆中不存在任何 `X` 或其子类的对象
2. **加载该类的 `ClassLoader` 已被回收** —— 这一步是最难的
3. **该类的 `java.lang.Class` 对象没有被任何地方引用** —— 包括反射缓存、`Class` 的静态字段、注解、JNI 全局引用、`MethodHandle`

JVM 规范**不要求**类必须被卸载，HotSpot 的实现是：**只有通过 GC 才能卸载类**，而且要求该类的定义加载器整体不可达。所以：

> **"类卸载"的实际触发条件 = 定义它的加载器被回收。**

**辅助开关**：

| 参数 / 命令 | 作用 |
|---|---|
| `-Xnoclassgc` | 关闭类卸载（**不要用**，会加速元空间泄漏） |
| `-XX:+TraceClassUnloading`（JDK 8） | 打印被卸载的类 |
| `-Xlog:class+unload=info`（JDK 9+） | 同上 |
| `jcmd <pid> GC.class_stats` | 各加载器的类数量与元空间占用（需 `-XX:+UnlockDiagnosticVMOptions`） |
| `jmap -clstats <pid>` | 同上，命令行更友好 |

> [!note] Bootstrap 加载的类永远不卸载
> `java.lang.String`、`java.util.HashMap` 这些由 Bootstrap（C++ 实现、无 Java 加载器对象）加载的类，其"加载器"永远可达，所以**永远不会被卸载**。可卸载的只有自定义加载器加载的类。这也解释了为什么"热部署泄漏的一直是应用类"。

### 7.2 为什么自定义加载器容易泄漏（高频生产事故）

只要有任何一条**强引用**指向加载器（或其加载的类、类的静态字段、其实例），第 2 个条件就不成立，加载器连同其所有类都无法卸载，元空间持续增长。

| 泄漏源 | 机制 | 修复 |
|---|---|---|
| **线程上下文类加载器（TCCL）** | `Thread` 对象持有 `contextClassLoader`；线程池线程长期存活 → 加载器被钉死 | 使用前保存、使用后 `setContextClassLoader(original)` 还原 |
| **`ThreadLocal`** | `ThreadLocalMap` 的 value 引用加载器内的对象；线程复用时 value 不清理 | 用完 `remove()`（这是"线程池里必须 remove ThreadLocal"的内存视角原因） |
| **`Timer` / 定时任务线程** | 线程未 `cancel()`，一直存活并持有 Runnable → Runnable 的类 → 加载器 | 显式 `cancel()` + `purge()` |
| **JDBC 驱动** | 驱动注册到 `DriverManager`（Bootstrap/Platform 层的静态集合），驱动类持有对 Webapp 加载器的引用 | 容器调用 `DriverManager.deregisterDriver` |
| **框架的全局静态缓存** | 比如 `LoggerFactory`、`CGLIB` 的 `ClassLoader` 缓存、ThreadLocal 化的 `ApplicationContext` | 不用时清缓存 |
| **`java.util.logging`** 的 `LogManager` | 应用类注册的 Handler 被全局持有 | 销毁时移除 |
| **JNI 全局引用 / `MethodHandle` / `DirectByteBuffer` 的 cleaner** | 各自持有类或加载器引用 | 谨慎使用，及时释放 |
| **`Instrumentation` / `retransform` 的缓存** | Agent 持有的 `Class` 列表 | Agent 生命周期管理 |

**Tomcat 的应对**：`WebappClassLoaderBase#clearReferences()` 在 Context 停止时主动把上面这些引用清一遍，包括：

```text
clearReferencesThreads()      -- 找还在跑的应用线程，检查 TCCL，必要时中断
clearReferencesThreadLocals() -- 清掉应用自己的 ThreadLocal
clearReferencesJdbc()         -- 注销 DriverManager 里的驱动
clearReferencesRmiTargets()   -- 清理 RMI
clearReferencesStopTimerThread()  -- 停掉 java.util.Timer
```

**这就是"Tomcat 热部署后必然看到内存慢慢涨"的根本原因**：只要应用里漏了一个 `ThreadLocal.remove()` 或一个没停的定时任务，老加载器就永远活着。

### 7.3 与 Metaspace OOM 的关系

```text
java.lang.OutOfMemoryError: Metaspace
```

**根因分类**：

| 根因 | 特征 | 排查 |
|---|---|---|
| **动态类生成爆炸**（最常见） | 元空间持续单向增长，与流量正相关 | `jmap -clstats` 看哪个加载器类数最多；`-Xlog:class+load` 找重复类名 |
| **热部署/加载器泄漏** | 每次重部署后类数量上一个台阶，老加载器不消失 | `jcmd GC.classloader_stats` 对比不同时间点 |
| **`-XX:MaxMetaspaceSize` 设得过小** | 直接 OOM，CPU 也高（频繁 Full GC 尝试卸载） | 调大或去掉上限 |
| **反射/代理滥用** | 大量 `$Proxy`、`$$EnhancerByCGLIB`、`GeneratedMethodAccessor` | 开 `-Dsun.reflect.inflationThreshold`，或加反射访问器缓存 |

**动态类爆炸的真实案例**：

- **CGLIB 代理缓存键用了新加载器**：每次热部署新加载器 → 缓存未清理 → 新代理类不断生成
- **表达式引擎 / 脚本引擎**：每次 `eval` 生成一个新类（Groovy、OGNL、SpEL 的某些用法）
- **`MethodHandles.Lookup.defineClass` / 序列化框架**：动态生成访问器
- **反射的 `GeneratedMethodAccessor`**：JDK 用字节码生成加速反射调用，本身是"类爆炸"的一个来源（有 inflate 阈值 15 次后生成，且数量受 `sun.reflect.noInflation` 控制）

> [!warning] 元空间 OOM 不等于"内存不够"
> 元空间默认**不受上限约束**（`MaxMetaspaceSize` 默认是平台最大值），所以"元空间 OOM"往往是**先吃光了机器物理内存**或者**容器 memory limit** 被触发。真正的排查顺序是：确认是**泄漏**（加载器活着）还是**爆炸**（动态类太多），再去看是谁持有。
> 具体排查步骤见 [[7-JVM故障排查实战]]，参数怎么设见 [[6-JVM参数与调优实战]]。

## 八、字节码结构

### 8.1 `.class` 文件结构表

`.class` 是一段**严格的、无填充的二进制流**，由 JVMS 第 4 章定义：

| 顺序 | 名称 | 长度 | 说明 |
|---|---|---|---|
| 1 | `magic` 魔数 | u4 | 固定 **0xCAFEBABE**，用于识别"这是不是一个 class 文件" |
| 2 | `minor_version` 次版本号 | u2 | 一般 0 |
| 3 | `major_version` 主版本号 | u2 | **52=Java 8，61=Java 17，65=Java 21，69=Java 25** |
| 4 | `constant_pool_count` 常量池计数 | u2 | **从 1 开始**，索引 0 被保留（"不引用任何常量池项"） |
| 5 | `constant_pool` 常量池 | cp_info[] | 共 `count-1` 项，**变长**，每项第一个字节是 tag |
| 6 | `access_flags` 访问标志 | u2 | `ACC_PUBLIC`/`ACC_FINAL`/`ACC_SUPER`/`ACC_INTERFACE`/`ACC_ABSTRACT`/`ACC_SYNTHETIC`/`ACC_ANNOTATION`/`ACC_ENUM`/`ACC_MODULE` |
| 7 | `this_class` 类索引 | u2 | 指向常量池的 `CONSTANT_Class_info` |
| 8 | `super_class` 父类索引 | u2 | 只有 `java.lang.Object` 是 0 |
| 9 | `interfaces_count` + `interfaces[]` | u2 + u2[] | 实现的接口 |
| 10 | `fields_count` + `fields[]` | u2 + field_info[] | 字段表 |
| 11 | `methods_count` + `methods[]` | u2 + method_info[] | 方法表 |
| 12 | `attributes_count` + `attributes[]` | u2 + attribute_info[] | 属性表（类级） |

**字段表 `field_info`**：

| 项 | 长度 | 说明 |
|---|---|---|
| `access_flags` | u2 | `ACC_PUBLIC`/`PRIVATE`/`PROTECTED`/`STATIC`/`FINAL`/`VOLATILE`/`TRANSIENT`/`SYNTHETIC`/`ENUM` |
| `name_index` | u2 | 指向常量池的字段名 |
| `descriptor_index` | u2 | 指向常量池的字段描述符 |
| `attributes_count` + `attributes[]` | u2 + [] | 常见：`ConstantValue`、`Signature`、`RuntimeVisibleAnnotations` |

**方法表 `method_info`**：结构同上（名字 + 描述符 + 属性），但属性更丰富：

| 属性 | 内容 |
|---|---|
| **`Code`** | 方法体的核心：`max_stack`、`max_locals`、`code[]`、`exception_table[]`、`LineNumberTable`、`LocalVariableTable`、**`StackMapTable`** |
| `Exceptions` | `throws` 声明的受检异常 |
| `MethodParameters` | 参数名（需 `-parameters` 编译） |
| `Signature` | 泛型签名 |
| `RuntimeVisibleAnnotations` / `ParameterAnnotations` | 注解 |
| `Synthetic` / `Deprecated` | 标记 |

**`Code` 属性内部**：

| 项 | 说明 |
|---|---|
| `max_stack` | 操作数栈最大深度（验证与执行都要用） |
| `max_locals` | 局部变量表槽数（`long`/`double` 占 2 个槽） |
| `code_length` + `code[]` | 字节码指令序列 |
| `exception_table_length` + `exception_table[]` | 每条含 `start_pc` / `end_pc` / `handler_pc` / `catch_type` |
| `attributes` | `LineNumberTable`（行号，用于异常栈打印）、`LocalVariableTable`（调试用）、`StackMapTable`（**JDK 6+ 类型检查的基础**） |

### 8.3 常量池（Constant Pool）的意义

常量池是 class 文件的"资源库"，存放两大类内容：

| 类别 | 说明 | 常量类型 |
|---|---|---|
| **字面量（Literal）** | 源代码里的常量值 | `CONSTANT_Integer`、`Float`、`Long`、`Double`、`String`、`Utf8` |
| **符号引用（Symbolic Reference）** | 对类/字段/方法的"名字描述" | `CONSTANT_Class`、`Fieldref`、`Methodref`、`InterfaceMethodref`、`NameAndType`、`MethodHandle`、`MethodType`、`Dynamic`、`InvokeDynamic` |

| tag | 类型 | 含义 |
|---|---|---|
| 1 | `Utf8` | 字符串（名字、描述符都用它） |
| 3 / 4 | `Integer` / `Float` | 4 字节数值 |
| 5 / 6 | `Long` / `Double` | **占 2 个常量池索引位**（后一个位置空着） |
| 7 | `Class` | 类或接口的符号引用（指向一个 Utf8） |
| 8 | `String` | 字符串字面量（指向一个 Utf8） |
| 9 / 10 / 11 | `Fieldref` / `Methodref` / `InterfaceMethodref` | 字段/方法引用（指向 Class + NameAndType） |
| 12 | `NameAndType` | 名字与描述符 |
| 15 / 16 | `MethodHandle` / `MethodType` | 方法句柄（`invokedynamic` 用） |
| 17 / 18 | `Dynamic` / `InvokeDynamic` | 动态调用点（lambda、字符串拼接） |
| 19 / 20 | `Module` / `Package` | 模块化（JDK 9+） |

> [!important] 为什么需要常量池
> 1. **去重**：同一个 `java/lang/Object` 只存一次，所有引用它的地方都指 `#4`
> 2. **解耦**：class 文件里存的是"名字"，实际内存地址在**解析阶段**才绑定——这是动态链接、可替换 jar、装完还能跑的物理基础
> 3. **对应运行时常量池**：class 文件的常量池在类加载后进入方法区的**运行时常量池**，`String` 字面量还会进堆里的**字符串常量池**（JDK 7 起从永久代移到堆，见 [[1-JVM内存区域与对象布局]]）

### 8.4 描述符（Descriptor）读法

| Java 类型 | 描述符 | 助记 |
|---|---|---|
| `void` | `V` | Void |
| `boolean` | `Z` | 最后剩下的字母 |
| `byte` | `B` | Byte |
| `char` | `C` | Char |
| `short` | `S` | Short |
| `int` | `I` | Int |
| `long` | `J` | 别人占了 L |
| `float` | `F` | Float |
| `double` | `D` | Double |
| 对象 `com.demo.Foo` | `Lcom/demo/Foo;` | `L` + 全限定名（`/` 分隔）+ `;` |
| 数组 `int[]` | `[I` | 每个维度一个 `[` |
| 数组 `String[]` | `[Ljava/lang/String;` | |
| 数组 `int[][]` | `[[I` | |

**方法描述符 = `(参数列表)返回值`**：

| Java 签名 | 描述符 |
|---|---|
| `void main(String[])` | `([Ljava/lang/String;)V` |
| `int add(int, int)` | `(II)I` |
| `String getName()` | `()Ljava/lang/String;` |
| `Object get(int, String)` | `(ILjava/lang/String;)Ljava/lang/Object;` |
| `<init>(String)` 构造器 | `(Ljava/lang/String;)V`（**返回类型固定为 V**） |

> [!tip] 一个高频面试小题
> `String.valueOf(char)` 的描述符是什么？→ `(C)Ljava/lang/String;`
> `Arrays.copyOf(int[], int)` 呢？→ `([II)[I`
> 会读描述符的直接收益：**看 `javap` 输出时一眼分清"调的是哪个重载"**，以及理解为什么 lambda 的描述符是 `()V` 这类"擦除后"的形态。

## 九、字节码指令实战

### 9.1 `i++` 与 `++i`

```java
public class IncDemo {
    public int post(int i) { return i++; }   // 先取值，再自增
    public int pre(int i)  { return ++i; }   // 先自增，再取值
}
```

```bash
javap -c -p IncDemo.class
```

```text
public int post(int);
  Code:
     0: iload_1        // 把局部变量表 slot1（参数 i）压入操作数栈
     1: iinc          1, 1   // 直接把 slot1 自增 1（iinc 不操作栈！）
     4: ireturn        // 返回栈顶 —— 仍是自增前的旧值

public int pre(int);
  Code:
     0: iinc          1, 1   // 先自增 slot1
     3: iload_1        // 再把新值压栈
     4: ireturn        // 返回新值
```

**核心认知：`iinc` 是一条"直接改局部变量表"的指令，它不经过操作数栈。** 因此"压栈"和"自增"的先后顺序决定了返回值，这就是 `i++`/`++i` 差异的全部机制。

由此可以推导出经典题目：

```java
int i = 1;
i = i++;      // 结果 i = 1
System.out.println(i);
```

汇编（示意）：

```text
   0: iconst_1
   1: istore_1          // i = 1
   2: iload_1           // 压栈旧值 1
   3: iinc          1, 1  // i = 2
   6: istore_1          // 把栈顶的 1 写回 i  → i 又被改回 1
   7: getstatic ...
```

**字节码里 `istore` 发生在 `iinc` 之后**，赋值把自增结果覆盖了。所以 `i = i++` 等于 `i = i`。

再推导 `i = i++ + ++i` 这类题时，只要按字节码顺序推操作数栈即可，不需要背。

### 9.2 `try-finally` 的字节码形态

```java
public class FinallyDemo {
    static int f() {
        try {
            return 1;
        } finally {
            System.out.println("cleanup");
        }
    }
}
```

```text
static int f();
  Code:
     0: getstatic     #7    // Field java/lang/System.out:Ljava/io/PrintStream;
     3: ldc           #13   // String cleanup
     5: invokevirtual #15   // Method java/io/PrintStream.println:(Ljava/lang/String;)V
     8: iconst_1
     9: ireturn

    10: astore_0             // ★ 异常路径的 finally 拷贝
    11: getstatic     #7
    14: ldc           #13
    16: invokevirtual #15
    19: aload_0
    20: athrow              // 重新抛出原异常

  Exception table:
     from    to  target type
         0     8    10   any      <-- 捕获"任意异常"，跳到 finally 拷贝
```

**三条关键结论**：

1. **`finally` 块被复制成两份**：正常路径一份、异常路径一份（`javac` 级别的代码复制，不是 JVM 的"finally 魔法"）。
2. **异常表里的 `type = any`**：表示捕获所有异常（对应源码语义"无论怎样 finally 都执行"）。
3. **正常路径在 `finally` 之后才 `ireturn`**：说明"返回值已经确定，但 finally 仍会执行"。

对于**非常量返回值**，`javac` 会把待返回的值先存进一个临时局部变量槽：

```java
static int h(int x) {
    try {
        return x;
    } finally {
        x = 100;
    }
}
```

```text
static int h(int);
  Code:
     0: iload_0
     1: istore_1        // ★ 把 x 的当前值备份到临时槽 slot1
     2: bipush        100
     4: istore_0        // finally: x = 100
     5: iload_1         // 取回备份值
     6: ireturn

     7: astore_2
     8: bipush        100
    10: istore_0
    11: aload_2
    12: athrow

  Exception table:
     from    to  target type
         0     2     7   any
```

**这就解释了"在 finally 里修改局部变量不影响返回值"**——返回值早在进入 finally 之前就被快照进临时槽了。

**为什么 `finally` 里的 `return` 会吞掉异常**：

```java
static int g() {
    try {
        throw new RuntimeException("boom");
    } finally {
        return 42;                 // ★ 异常被丢弃
    }
}
```

```text
static int g();
  Code:
     0: new           #7    // class java/lang/RuntimeException
     3: dup
     4: ldc           #9    // String boom
     6: invokespecial #11   // Method java/lang/RuntimeException."<init>":(Ljava/lang/String;)V
     9: athrow              // 抛出异常

    10: astore_0            // finally 的异常处理器入口
    11: bipush        42
    13: ireturn            // ★★ 直接返回，没有 athrow —— 异常对象随栈帧一起丢弃

  Exception table:
     from    to  target type
         0    10    10   any
```

**机制**：异常路径的处理器**本应以 `athrow` 结尾重新抛出**，但当 `finally` 里有 `return` 时，`javac` 生成的是 `ireturn` 而不是 `athrow` —— **待抛出的异常对象还在局部变量表里（`astore_0` 存了它），但没有任何指令再引用它**，异常就这样被静默丢弃。

| `finally` 中的语句 | 处理器结尾 | 结果 |
|---|---|---|
| 无返回（普通语句） | `aload_0` + `athrow` | 异常正常传播 |
| `return value` | `ireturn` | **异常被吞**，返回 value |
| `throw new Y()` | `athrow`（抛 Y） | **原异常被替换成 Y**，原始堆栈丢失 |

> [!danger] 生产禁忌
> `finally` 里 **绝对不要写 `return`**（会吞异常，让故障静默）、不要写 `throw`（会覆盖原始异常，丢掉最关键的现场）。
> 需要记录日志时，用 try-with-resources（JDK 7+，编译器生成 `addSuppressed`，不会吞异常）或把清理逻辑抽成独立方法。
> 另外注意 **`return` 在 `try` 里、`finally` 里也有 `return` 时**，编译期就能通过（除非用 `-Werror`），运行期以 `finally` 为准——IDE 通常给出 warning，不要忽略它。

### 9.3 `synchronized` 的字节码

```java
public class SyncDemo {
    private final Object lock = new Object();

    public void block() {
        synchronized (lock) {
            System.out.println("in");
        }
    }

    public synchronized void method() { }
}
```

**同步代码块：`monitorenter` / `monitorexit` + 异常表**

```text
public void block();
  Code:
     0: aload_0
     1: getfield      #2    // Field lock:Ljava/lang/Object;
     4: dup                  // ★ 复制一份引用：一份用于 monitorenter，一份留给 monitorexit
     5: astore_1             // 存到 slot1（局部变量表，保证异常时也能拿到锁对象）
     6: monitorenter         // 获取监视器锁
     7: getstatic     #3     // System.out
    10: ldc           #4     // String in
    12: invokevirtual #5     // println
    15: aload_1
    16: monitorexit          // 正常路径释放锁
    17: goto          25
    20: astore_2             // ★ 异常路径
    21: aload_1
    22: monitorexit          // 异常路径也要释放锁
    23: aload_2
    24: athrow               // 再抛出
    25: return

  Exception table:
     from    to  target type
         7    17    20   any   <-- 保证异常时锁一定被释放
```

| 观察点 | 含义 |
|---|---|
| `dup` + `astore_1` | 锁对象引用必须先备份到局部变量表，否则异常时拿不到它来解锁 |
| **两个 `monitorexit`** | 一个在正常路径，一个在异常处理器里——这是 `synchronized` 的"自动释放"在字节码层面的实现 |
| `exception_table` 的 `any` | 同 `finally` 的形态：**编译器把"释放锁"当成了 finally 语义** |
| 显式 `synchronized` 块**没有** ACC 标志 | 同步语义完全由指令表达 |

**同步方法：`ACC_SYNCHRONIZED` 访问标志**

```text
public synchronized void method();
  descriptor: ()V
  flags: (0x0021) ACC_PUBLIC, ACC_SYNCHRONIZED     <-- 0x0020
  Code:
     0: return
```

方法级同步**没有 `monitorenter`/`monitorexit`**，而是靠方法访问标志 `ACC_SYNCHRONIZED`（0x0020）。JVM 在方法调用时检查该标志，自动加锁/解锁（等价于对 `this`（实例方法）或 `Class` 对象（静态方法）加监视器锁）。

| 对比 | 同步代码块 | 同步方法 |
|---|---|---|
| 实现 | `monitorenter` / `monitorexit` + 异常表 | `ACC_SYNCHRONIZED` 标志 |
| 锁对象 | 显式指定，可精细控制 | 实例方法锁 `this`，静态方法锁 `Class` 对象 |
| 粒度 | 更小，推荐 | 整个方法体 |
| 能否看到指令 | 能 | 不能（只有标志） |

> [!note] 只讲到这里
> `synchronized` 的**语义**（可见性、happens-before、锁升级、偏向锁/轻量级锁的历史演进）属于 [[4-多线程与内存模型]] 的范围。本篇只负责回答"**字节码长什么样、JVM 靠什么指令实现**"。
> 面试里如果问"为什么同步方法没有 monitorenter"，答案就是 `ACC_SYNCHRONIZED` 标志——这是一个很能体现"真的看过字节码"的细节。

### 9.4 字符串拼接：Java 8 与 Java 9+ 的分水岭

```java
public String concat(String a, String b) {
    return a + "-" + b;
}
```

**Java 8（`javap -c`）**：

```text
public java.lang.String concat(java.lang.String, java.lang.String);
  Code:
     0: new           #2    // class java/lang/StringBuilder
     3: dup
     4: invokespecial #3    // Method java/lang/StringBuilder."<init>":()V
     7: aload_1
     8: invokevirtual #4    // StringBuilder.append:(Ljava/lang/String;)Ljava/lang/StringBuilder;
    11: ldc           #5    // String -
    13: invokevirtual #4
    16: aload_2
    17: invokevirtual #4
    20: invokevirtual #6    // StringBuilder.toString:()Ljava/lang/String;

```

**Java 9+（`javap -c`）**：

```text

  Code:
     0: aload_1
     1: aload_2
     2: invokedynamic #7,  0  // InvokeDynamic #0:makeConcatWithConstants:(Ljava/lang/String;Ljava/lang/String;)Ljava/lang/String;
     7: areturn
```

对应的 `BootstrapMethods` 属性：

```text
BootstrapMethods:
  0: #22 REF_invokeStatic java/lang/invoke/StringConcatFactory.makeConcatWithConstants:
        (Ljava/lang/invoke/MethodHandles$Lookup;Ljava/lang/String;Ljava/lang/invoke/MethodType;
         Ljava/lang/String;Ljava/lang/String;[Ljava/lang/Object;)Ljava/lang/invoke/CallSite;
    Method arguments:
      #23 \u0001-\u0001            <-- 模板：占位符 \u0001 表示"下一个参数"
```

| 维度 | Java 8 | Java 9+ |
|---|---|---|
| 机制 | 编译期生成 `StringBuilder` 调用序列 | `invokedynamic` + `StringConcatFactory` |
| 优化时机 | **编译期固定** | **运行期**：JVM 可以选择最优策略（`StringBuilder` 拼接 / `MethodHandle` 组合 / 甚至直接构造 `byte[]`） |
| 是否需要预热 | 不需要 | 需要（首次调用要引导 bootstrap 方法，生成 `CallSite`） |
| 循环里的拼接 | **每次迭代 new 一个 StringBuilder** | 每次迭代一次 indy 调用 |
| 空值处理 | `StringBuilder.append(null)` → `"null"` | 语义保持一致 |

> [!important] 高频实战题："循环里用 `+` 拼接字符串有性能问题吗"
> **要分场景回答**：
> 1. **单条语句内的多个 `+`**（`a + b + c`）：Java 8 也只创建一个 `StringBuilder`，**没有性能问题**，不必手写成 `StringBuilder`。
> 2. **循环体里的 `+`**：
>    ```java
>    String s = "";
>    for (String x : list) { s = s + x; }   // ★ 每次迭代 new StringBuilder + toString()
>    ```
>    编译后的字节码里 `new StringBuilder` 在**循环体内部**，每次迭代都创建新对象并复制整个已累积的字符串 → **O(n²)**。这里必须改成循环外的 `StringBuilder`（或 `StringJoiner`）。
> 3. **Java 9+ 的循环内 `+`** 同样每次迭代生成新的拼接调用，问题性质相同（虽然单次调用更快）。
> **判断标准：`javac` 的优化作用域是"一条语句"，不是"一个循环"。** 用 `javap -c` 看一眼循环体里有没有 `new`，就能确定。

### 9.5 自动装箱 / 拆箱

```java
public class BoxDemo {
    public Integer box(int i) {
        return i;                 // 装箱
    }
    public int unbox(Integer i) {
        return i;                 // 拆箱
    }
    public int sum(Integer a, Integer b) {
        return a + b;             // 两次拆箱 + 一次加法 + 一次装箱/拆箱
    }
}
```

```text
public java.lang.Integer box(int);
  Code:
     0: iload_1
     1: invokestatic  #7    // Method java/lang/Integer.valueOf:(I)Ljava/lang/Integer;   ★ 装箱
     4: areturn

public int unbox(java.lang.Integer);
  Code:
     0: aload_1
     1: invokevirtual #13   // Method java/lang/Integer.intValue:()I                     ★ 拆箱
     4: ireturn

public int sum(java.lang.Integer, java.lang.Integer);
  Code:
     0: aload_1
     1: invokevirtual #13   // Integer.intValue
     4: aload_2
     5: invokevirtual #13   // Integer.intValue
     8: iadd
     9: ireturn
```

**装箱走的是 `valueOf` 而不是 `new Integer`**，这一点极其重要：

```java
Integer a = 100, b = 100;
System.out.println(a == b);        // true   ← IntegerCache 缓存 -128..127

Integer c = 1000, d = 1000;
System.out.println(c == d);        // false  ← 超出缓存范围，各自 new

Integer e = 100;
Long    f = 100L;
System.out.println(e.equals(f));   // false  ← 类型不同；注意 Integer.equals 会先 instanceof 检查
```

| 包装类 | 缓存范围 | 说明 |
|---|---|---|
| `Byte` / `Short` / `Integer` / `Long` | **-128 ~ 127** | `Integer` 的上限可用 `-XX:AutoBoxCacheMax=` 调大 |
| `Character` | `'\u0000'` ~ `'\u007F'` | 0 ~ 127 |
| `Boolean` | `TRUE` / `FALSE` | 两个常量 |
| `Float` / `Double` | **无缓存** | 值域太大，缓存没意义 |

**拆箱的经典 NPE（生产级陷阱）**：

```java
Map<String, Integer> map = new HashMap<>();
Integer v = map.get("not-exist");     // null
int result = v;                        // ★ NullPointerException：Integer.intValue() on null
```

字节码证据：`invokevirtual Integer.intValue:()I` 作用在 `null` 上 → NPE。这类问题的排查难点在于**报错行看起来是个普通赋值**，异常信息通常在 `Integer.intValue()` 或 `Long.longValue()` 上。**规范做法**：三元表达式、`if` 判断、`Optional`，或统一用基本类型。特别注意三元表达式的**类型提升**：

```java
Integer a = null;
Boolean flag = true;
int x = flag ? a : 0;      // ★ NPE：三元表达式两端类型统一为 int，a 被拆箱
// 换成 flag ? a : Integer.valueOf(0) 就不会
```

### 9.6 lambda 的 `invokedynamic` 与 `LambdaMetafactory`

```java
public class LambdaDemo {
    public static void main(String[] args) {
        Runnable r = () -> System.out.println("hi");
        r.run();
    }
}
```

```text
public static void main(java.lang.String[]);
  Code:
     0: invokedynamic #7,  0   // InvokeDynamic #0:run:()Ljava/lang/Runnable;
     5: astore_1
     6: aload_1
     7: invokeinterface #11,  1  // InterfaceMethod java/lang/Runnable.run:()V
    12: return

private static void lambda$main$0();          <-- ★ 编译器生成的私有静态合成方法
  Code:
     0: getstatic     #15   // System.out
     3: ldc           #17   // String hi
     5: invokevirtual #19   // println
     8: return

BootstrapMethods:
  0: #29 REF_invokeStatic java/lang/invoke/LambdaMetafactory.metafactory:
        (Ljava/lang/invoke/MethodHandles$Lookup;Ljava/lang/String;Ljava/lang/invoke/MethodType;
         Ljava/lang/invoke/MethodType;Ljava/lang/invoke/MethodHandle;Ljava/lang/invoke/MethodType;)
        Ljava/lang/invoke/CallSite;
    Method arguments:
      #30 ()V                                                     <-- 接口方法签名 run()V
      #31 REF_invokeStatic LambdaDemo.lambda$main$0:()V           <-- lambda 体
      #30 ()V                                                     <-- 擦除后的签名
```

**`invokedynamic` 的执行过程**：

```text
第一次执行 invokedynamic
        │
        ▼
  解析出 BootstrapMethods 里的引导方法（LambdaMetafactory.metafactory）
        │
        ▼
  调用引导方法，返回一个 CallSite
        │
        ▼
  CallSite 被链接并缓存（此后每条 invokedynamic 只走缓存，不再走引导方法）
        │
        ▼
  CallSite 的 target 是一个"实现 Runnable 的合成类"的构造器 MethodHandle
        │
        ▼
  运行时生成（或复用）一个实现 Runnable 的类，实例化并返回
```

**与匿名内部类对比**：

| 维度 | lambda（JDK 8+） | 匿名内部类 |
|---|---|---|
| 生成 class 文件 | ❌ 不生成（运行时用 `MethodHandle` 生成，或直接复用） | ✅ 生成 `LambdaDemo$1.class` |
| 字节码指令 | `invokedynamic` | `new` + `dup` + `invokespecial <init>` |
| 捕获的 `this` | 只在需要时捕获 | **总是**隐式持有外部类引用（`this$0`） |
| 内存占用 | 更小（无捕获时是静态单例） | 每次都 new 一个对象 |
| 序列化 | 需要额外处理 | 天然可序列化（如果外部类可） |
| 能否有状态字段 | ❌ 不能 | ✅ 可以 |
| `this` 的含义 | 外层实例的 `this` | 匿名类自己的 `this` |

**无捕获 lambda 的"单例"特性**：

```java
Runnable r1 = () -> System.out.println("hi");   // 无捕获
Runnable r2 = () -> System.out.println("hi");
System.out.println(r1 == r2);    // true（HotSpot 上通常 true，非规范保证）

int n = 1;
Runnable r3 = () -> System.out.println(n);       // 捕获了 n
Runnable r4 = () -> System.out.println(n);
System.out.println(r3 == r4);    // false（每次生成新实例）
```

**这解释了一个性能细节**：无捕获的 lambda 不会造成对象分配，因为它被缓存在 `CallSite` 里；有捕获的 lambda 每次求值都要实例化。但对 JIT 来说，**有捕获的 lambda 在 C2 里可以被逃逸分析消除**（见 [[5-JIT编译与运行时优化]]），所以真实开销往往比字节码看起来小。

**方法引用是同一机制的语法糖**：

```java
list.forEach(System.out::println);
// 等价于 invokedynamic + LambdaMetafactory，MethodHandle 指向 PrintStream.println
```

> [!tip] 为什么 lambda 要用 `invokedynamic` 而不是直接生成匿名类
> 因为**编译期不需要决定实现方式**。这为运行期优化留了空间：
> - 无捕获时直接复用单例
> - 有捕获时可以生成更紧凑的形态
> - 未来 JVM 可以整体改成别的实现（如 GraalVM 上可以更激进地内联）
> 这与 Java 9 用 `StringConcatFactory` 替换 `StringBuilder` 是同一个设计思路：**把决策推迟到运行期**。

### 10.1 四类验证

| 类别 | 验证时机 | 检查什么 | 失败抛出 |
|---|---|---|---|
| **文件格式验证** | 加载阶段，**基于二进制字节流** | 魔数是否 `0xCAFEBABE`；主次版本号是否在当前 JVM 支持范围；常量池中的 tag 是否合法；常量池索引是否越界；`Utf8` 是否有非法字符；`Class` 常量是否指向合法名字 | 直接抛 `ClassFormatError`（不进入方法区） |
| **元数据验证** | 准备阶段前，**基于方法区中的数据结构** | 是否有父类（除 `Object`）；父类是否继承了自己（循环继承）；是否为 `final` 类却被继承；抽象方法是否都实现了；字段/方法是否与父类产生矛盾（如覆盖了 `final` 字段、方法签名不兼容） | `IncompatibleClassChangeError` 等 |
| **字节码验证** | **最复杂**，对 `Code` 属性的指令流做数据流分析 | 操作数栈是否溢出/下溢；指令类型是否与操作数匹配（如 `iload` 不能加载引用）；跳转目标是否落在方法内且是合法指令边界；局部变量表使用是否越界；`StackMapTable` 的类型检查（JDK 6+ 用类型推导替代旧的"类型推断"流程） | **`VerifyError`** |
| **符号引用验证** | **解析阶段**（可延迟到初始化之后） | 符号引用中全限定名能否找到对应类；指定类中是否存在符合描述符的字段/方法；可访问性（`private`/`protected`/`package`）是否合法 | `NoSuchFieldError`、`NoSuchMethodError`、`IllegalAccessError`、`NoClassDefFoundError` |

### 10.2 为什么需要验证

1. **防御恶意字节码**：`.class` 可以由任意工具生成。如果 JVM 直接信任它，一段构造的字节码可以跳出类型系统、直接读写内存、破坏虚拟机。验证是把"字节码"变成"可信代码"的守门人。
2. **保证类型安全与内存安全**：Java 的语言级安全性（没有指针越界、没有非法强转）**主要靠验证阶段在运行期兜底**，而不是靠 `javac`——因为 class 文件可以绕过 javac。
3. **减轻运行期检查负担**：有了 StackMapTable 与验证，JIT 编译时可以省掉大量类型检查，从而生成更快的代码（这是"验证换性能"的体现）。

**历史上被验证拦下的著名案例**：1997 年前后广泛报道的一系列 JVM 实现缺陷，攻击者用特制字节码实现"类型混淆"从而逃逸沙箱；JDK 后续的 `VerifyError` 与 StackMapTable 就是为了堵死这类路径。

### 10.3 `-Xverify:none` 的风险

| 参数 | 说明 |
|---|---|
| `-Xverify:none` / `-noverify` | 关闭类验证，**加载更快、启动稍快** |
| 代价 | **任何非法字节码都会导致 JVM 崩溃（SIGSEGV）而不是抛异常**——因为违规访问会直接落到 native 层 |
| 现状 | JDK 13 起被标记废弃；较新版本（17+）上该开关已被弱化/忽略，或需要额外开关才能生效。**不要在生产上使用** |
| 唯一合理的剩余用途 | 确定某个类验证是性能瓶颈时的**一次性对比实验**，且必须立刻恢复 |

> [!danger] 不要用 `-Xverify:none` 换启动速度
> 现代 JDK 的启动优化方向是 **CDS（Class Data Sharing）/ AppCDS**（JDK 12+ 默认开启默认归档）和 **AOT 缓存**，这些手段能在**不放弃验证**的前提下缩短启动。想优化启动时间应该往这些方向走，而不是关闭安全防线。启动优化见 [[6-JVM参数与调优实战]]。

## 十一、动手验证：常用命令与观察点

### 11.1 `javap`——静态看字节码

```bash
# 最常用的组合：常量池 + 私有的 + 反汇编
javap -v -p -c Demo.class

# 只看方法签名的描述符（看重载、看泛型擦除）
javap -s -p Demo.class

# 显示编译期常量（会打印 static final 的真实值）
javap -constants -p Demo.class

# 从 jar 里直接看
javap -c -p -cp app.jar com.demo.Demo

# 带行号表，把字节码偏移和源码行对应
javap -l -c -p Demo.class
```

| 参数 | 作用 |
|---|---|
| `-c` | 反汇编出字节码指令 |
| `-p` | 显示 `private` 成员（**不加就看不到私有方法，很多字节码细节会漏**） |
| `-v` | 详细信息：常量池、版本号、访问标志、StackMapTable、BootstrapMethods |
| `-s` | 打印描述符 |
| `-l` | 打印 LineNumberTable / LocalVariableTable |
| `-constants` | 显示 `static final` 常量的实际值 |
| `-sysinfo` | 显示类文件路径、大小、校验和 |

**观察清单**：

| 想验证什么 | 看哪里 |
|---|---|
| 编译期常量是否内联 | `-constants` 有没有值；调用方 `javap -c` 里是 `ldc 常量` 还是 `getstatic` |
| 泛型是否擦除 | `javap -s`：`List<String>` 字段/参数的描述符是 `Ljava/util/List;` |
| lambda 是否生成 class | `ls *.class` 有没有 `Outer$1.class`；`javap -v` 有没有 `BootstrapMethods` |
| 循环内拼接是否多次 new | `javap -c` 看 `new StringBuilder` 在循环体内还是外 |
| 是否被内联（JIT） | `javap` 看不到，要看 `-XX:+PrintInlining`（见 [[5-JIT编译与运行时优化]]） |

### 11.2 `jdeps`——看类依赖与 JDK 内部 API 使用

```bash
# 汇总依赖的包
jdeps -summary app.jar

# 逐个类显示依赖
jdeps -verbose:class -cp "libs/*" app.jar

# ★ 检查是否使用了 JDK 内部 API（升级 17 的关键检查）
jdeps --jdk-internals -cp "libs/*" app.jar

# 检查模块化是否可行
jdeps --module-path mods -recursive --check com.demo
```

`--jdk-internals` 是**从 Java 8 升级到 17 时最有价值的命令**：它会列出所有对 `sun.*`、`jdk.internal.*` 的依赖，这些在 17 上默认被强封装，会直接抛 `IllegalAccessError` 或 `InaccessibleObjectException`。

### 11.3 `jmap -clstats`——看类加载器与类数量

```bash
jmap -clstats <pid>
```

输出形态（示意）：

### 11.4 类加载日志

**JDK 8**：

```bash
# 打印加载与卸载（注意：输出量巨大，只适合短时排查）
java -XX:+TraceClassLoading -XX:+TraceClassUnloading -jar app.jar

# 只看加载到的类的来源
java -verbose:class -jar app.jar
```

**JDK 9+（统一日志框架 `-Xlog`）**：

```bash
# 加载日志，只输出 info 级别，写到文件
java -Xlog:class+load=info:file=classload.log -jar app.jar

# 只看卸载
java -Xlog:class+unload=info -jar app.jar

# 同时输出到控制台和文件，并带时间戳与标签
java -Xlog:class+load=info:classload_%p.log:uptime,level,tags -jar app.jar

# 看类加载相关的所有事件（含 class+load、class+unload、class+resolve、class+init）
java -Xlog:class*=debug -jar app.jar
```

| 日志标签 | 内容 |
|---|---|
| `class+load` | 每次类加载：类名、来源（jar / jrt / 生成） |
| `class+unload` | 类卸载 |
| `class+resolve` / `class+init` | 解析、初始化（debug 级才有） |

**日志里能看出的关键信息**：

```text
[0.123s][info][class,load] com.demo.Plugin source: file:/opt/app/plugins/p1.jar
[0.456s][info][class,load] java.lang.String source: jrt:/java.base        <-- JDK 内置
[2.345s][info][class,unload] unloading class com.demo.Plugin$1 0x00000007c0123456
```

- **同一个类名出现多次**：说明被多个加载器加载 → 查找 `ClassCastException` 根因
- **来源路径**：确认类到底从哪个 jar 来的 → 解决依赖冲突（"我明明改了，为什么没生效"）
- **卸载记录**：确认热部署后老类是否真的释放

> [!tip] 一份"够用"的最小工具集
> **静态看结构**：`javap -v -p -c`、`jdeps --jdk-internals`
> **运行期看类**：`jmap -clstats`（是否多个 live 加载器）、`jcmd <pid> GC.class_stats`、`-Xlog:class+load` / `class+unload`
> 热部署后元空间持续增长的完整排查流程属于故障排查的范畴，见 [[7-JVM故障排查实战]]；相关参数取值见 [[6-JVM参数与调优实战]]。

## 十二、必答

> [!question] 1. 双亲委派是什么？为什么需要？怎么打破？
> **流程**：`loadClass` 先 `findLoadedClass` 检查自己是否加载过；没有则委派 `parent.loadClass`（父为 null 时走 Bootstrap）；父加载器全部失败后，才调用自己的 `findClass`。即"自底向上检查是否已加载，自顶向下尝试加载"。
> **为什么需要**：① **安全**——`java.lang.*` 等核心类永远由 Bootstrap 加载，用户无法用同名类替换；② **去重**——同一个类在全局只有一个定义加载器，避免类型系统崩溃。
> **怎么打破**：① **SPI / JDBC** 用 **TCCL**（`Thread.currentThread().getContextClassLoader()`）让父加载器加载子路径下的实现类；② **Tomcat** 的 `WebappClassLoader` 改为"先自己（`WEB-INF/classes`、`WEB-INF/lib`）后父类"，实现应用优先与隔离；③ **OSGi** 按 `Import-Package`/`Export-Package` 组成网状委派；④ **热部署/热替换** 用新加载器重新加载同一个全限定名；⑤ **JDK 9+ 模块化** 用 `module-info` 精确控制可见性。
> 追问钩子：打破委派的代价是**类的唯一性"命名空间"被拆开**，由此引出 §六 的 `ClassCastException`。

> [!question] 2. 类的唯一性由什么决定？
> **类加载器实例 + 全限定名**。是"实例"（**==**），不是类名。因此同一个 `com.demo.Foo` 被两个加载器加载后，是两个**互不相容**的类型：强转 → `ClassCastException: com.demo.Foo cannot be cast to com.demo.Foo`；`instanceof` → false；静态变量各一份。
> 推论：跨加载器传递对象只能通过共享父加载器可见的接口（插件化框架为什么把 API 放在父加载器）。

> [!question] 3. `i++` 和 `++i` 的字节码区别？
> `iinc` 是**直接修改局部变量表**、不经过操作数栈的指令。`i++` = 先 `iload` 压入旧值、再 `iinc`；`++i` = 先 `iinc`、再 `iload` 压入新值。所以 `i = i++` 编译后是 `iload; iinc; istore`，`istore` 把自增值覆盖回去，最终 `i` 不变。

> [!question] 4. 为什么 `finally` 里的 `return` 会吞掉异常？
> 因为 `javac` 把 `finally` 复制到了**正常路径**和**异常路径**两处。异常路径的处理器正常应以 `athrow` 结尾重新抛出；一旦 `finally` 里有 `return`，编译器生成的是 `ireturn` 而不是 `athrow`——原异常对象虽然被 `astore` 存进了局部变量表，但再无任何指令引用它，于是被静默丢弃。同理 `finally` 里 `throw` 新异常会替换原异常、丢失原始堆栈。
> **证据**：`javap -c` 看异常表 `any` 对应的处理器结尾是 `ireturn` 而非 `athrow`。
> **规范做法**：`finally` 里不写 `return`/`throw`，用 try-with-resources。

> [!question] 5. `<clinit>` 和 `<init>` 有什么区别？
> `<clinit>` 是**类初始化方法**：由静态变量赋值 + static 块按源码顺序合并而成，无参、由 JVM 在类初始化阶段调用**一次**，**JVM 保证线程安全**（初始化锁）。父类 `<clinit>` 一定先于子类执行。
> `<init>` 是**实例构造器**：每次 `new` 都调用，字节码里父类 `<init>` 一定在最前面，随后是实例变量赋值、实例代码块、构造器体。
> 两个陷阱：① 静态初始化里跨类互相引用 → **类初始化死锁**（两个线程各持一把初始化锁），`jstack` 能看到 `<clinit>` 互相等待；② 父类构造器里调用被子类重写的方法 → 读到字段零值。

> [!question] 6. Metaspace 泄漏是怎么来的？
> 类卸载要求**三个条件同时满足**：类的实例全部回收、**定义它的 `ClassLoader` 被回收**、`Class` 对象无引用。因此实际触发条件是**加载器先死**。而自定义加载器只要被以下任一强引用钉住就永远活着：**线程上下文类加载器（TCCL）**、**ThreadLocal**（value 引用加载器内的对象）、未 `cancel` 的 `Timer`、注册到 `DriverManager` 的 JDBC 驱动、框架的全局静态缓存、JNI 全局引用、`Instrumentation` 缓存。
> 典型场景是**热部署**：每次重部署新建一个加载器，老加载器被应用里某个残留引用钉住 → 类无法卸载 → 元空间单调增长 → `OutOfMemoryError: Metaspace`。
> **验证手段**：`jmap -clstats` 看是否有多个同类型的 `live` 加载器；`-Xlog:class+unload` 看类是否真的被卸载；`jcmd <pid> GC.class_stats` 看类数量变化。
> Tomcat 的 `WebappClassLoaderBase#clearReferences()` 就是在做"主动切断这些引用"。

> [!question] 7. 准备阶段为什么要有"零值"这一步？
> 因为**静态变量的内存在准备阶段就分配好了**，而它的真实赋值语句可能依赖其他类（`static int a = Other.getValue()`），此时 `Other` 可能还没初始化。如果准备阶段不先给一个确定的零值，JVM 就可能读到未初始化的内存。零值保证了"**任何静态字段在初始化前都有一个确定的、类型正确的默认值**"，这也是"静态字段可以先赋值后声明"（§2.1）能成立的原因。

> [!question] 8. 怎么用一条命令看出程序用了 JDK 内部 API？
> ```bash
> jdeps --jdk-internals -cp "libs/*" app.jar
> ```
> 这是 Java 8 → 17 升级前最有价值的一步检查。JDK 16/17 起 `sun.*`、`jdk.internal.*` 默认被强封装，未加 `--add-opens`/`--add-exports` 会在运行期抛 `InaccessibleObjectException` 或 `IllegalAccessError`。
