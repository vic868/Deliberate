## 一、运行时数据区

### 1.1 五块区域

```
┌───────────────────────────── JVM 运行时数据区 ─────────────────────────────┐
│  线程私有                        │  线程共享                                 │
│  ┌──────────────────────┐        │  ┌────────────────────────────────────┐  │
│  │ 程序计数器 (PC)       │        │  │ 堆 (Heap)                          │  │
│  │  → 当前字节码行号      │        │  │  → 对象实例、数组                   │  │
│  ├──────────────────────┤        │  │  → 分代: 新生代(Eden+S0+S1) + 老年代 │  │
│  │ 虚拟机栈 (VM Stack)   │        │  ├────────────────────────────────────┤  │
│  │  → 栈帧: 局部变量表、  │        │  │ 方法区 (Method Area, JDK8+ 元空间)  │  │
│  │    操作数栈、动态链接、│        │  │  → 类元信息、常量、静态变量、JIT 代码│  │
│  │    返回地址           │        │  └────────────────────────────────────┘  │
│  ├──────────────────────┤        │                                          │
│  │ 本地方法栈            │        │  （另有直接内存 Direct Memory，不在      │
│  └──────────────────────┘        │   运行时数据区规范内，但受堆外参数约束）   │
└───────────────────────────────────────────────────────────────────────────┘
```

| 区域 | 线程 | 存放内容 | 会 OOM 吗 | 关键异常 |
|---|---|---|---|---|
| **程序计数器** | 私有 | 当前线程执行的字节码行号 | **不会** | —— |
| **虚拟机栈** | 私有 | 栈帧（局部变量表/操作数栈/动态链接/返回地址） | 会 | `StackOverflowError`（递归过深）、`OutOfMemoryError`（无法扩栈） |
| **本地方法栈** | 私有 | native 方法调用 | 会 | 同上 |
| **堆** | **共享** | 对象实例、数组 | 会 | `OutOfMemoryError: Java heap space` |
| **方法区** | **共享** | 类元信息、运行时常量池、静态变量、JIT 编译代码 | 会 | JDK8+：`OutOfMemoryError: Metaspace` |

> [!important] JDK 8 的分水岭：永久代 → 元空间
> JDK 7 及之前方法区的实现叫**永久代（PermGen）**，在**堆内**，受 `-XX:MaxPermSize` 限制；
> **JDK 8 起改为元空间（Metaspace）**，移到**本地内存（堆外）**，受 `-XX:MaxMetaspaceSize` 限制（默认不限制，所以元空间泄漏会吃光机器内存）。
> 迁移原因：永久代大小难以预估、字符串常量池在 JDK 7 已移到堆、以及为 JRockit 合并铺路。
> 面试常问："**字符串常量池在哪**"——JDK 7 起**移到堆中**。

### 1.2 栈帧里有什么

| 组成 | 作用 | 常见问题 |
|---|---|---|
| 局部变量表 | 存方法参数与局部变量（基本类型值、对象引用） | 变量作用域过大导致无法回收（**只要还在局部变量表里就不算不可达**） |
| 操作数栈 | 字节码运算的工作区 | —— |
| 动态链接 | 指向运行时常量池中该方法的符号引用 | —— |
| 返回地址 | 方法退出后回到哪里 | —— |

> [!tip] 一个实用的排查认知
> `StackOverflowError` 几乎都是**无限递归**或**递归太深**；`-Xss` 只能调每线程栈大小，**真正的解法是改算法（比如改成循环）**。

### 1.3 JVM 内存 vs JMM（两个"内存模型"别混）

| | JVM 运行时数据区 | JMM（Java 内存模型） |
|---|---|---|
| 是什么 | **物理上的内存区域划分**（堆/栈/方法区…） | **抽象的并发规范**（主内存/工作内存、happens-before） |
| 解决什么问题 | 对象存在哪、怎么分配 | 多线程下**可见性、有序性、原子性**的语义 |
| 相关参数 | `-Xmx`/`-Xmn`/`-Xss`… | 由 `volatile`/`synchronized`/final 等语言构件保证 |

详见 [[4-多线程与内存模型]]。

## 二、对象的创建与内存布局

### 2.1 创建过程（`new` 做了什么）

| 步骤 | 说明 |
|---|---|
| 1. 类加载检查 | 检查常量池能否定位到类的符号引用，且类已加载/解析/初始化；否则先触发类加载 |
| 2. 分配内存 | **指针碰撞**（堆规整时）或**空闲列表**（堆不规整时）；并发安全靠 **CAS + 失败重试** 或 **TLAB** |
| 3. 初始化零值 | 把分配到的内存置零（保证实例字段有默认值） |
| 4. 设置对象头 | 写入 Mark Word、类型指针（Klass Pointer） |
| 5. 执行构造器 | 执行 `<init>`，按代码赋真正的初值 |

### 2.2 对象在内存中的三部分

| 部分 | 内容 |
|---|---|
| **对象头** | **Mark Word**（哈希码、GC 分代年龄、锁状态标志、偏向线程 ID）+ **类型指针**（指向类元数据）+（数组才有）数组长度 |
| **实例数据** | 真正的字段值；**字段重排序**：按类型宽度排列以节省空间（父类字段在前） |
| **对齐填充** | 补齐到 8 字节整数倍（**对象大小必然是 8 的倍数**） |

```java
// 用 JOL 观察对象布局（面试/排查时很有用）
// System.out.println(org.openjdk.jol.info.ClassLayout.parseInstance(new Object()).toPrintable());
```

> [!note] Mark Word 与锁升级的接口
> Mark Word 的位被复用：不同锁状态下它表示不同含义（偏向锁存线程 ID、轻量级锁存指向栈中锁记录的指针、重量级锁存指向 monitor 的指针）。
> **锁升级的机制见 [[4-多线程与内存模型]]**——两者是同一块内存的两种讲法。

### 2.3 内存分配策略

| 策略 | 规则 | 为什么 |
|---|---|---|
| **对象优先在 Eden 分配** | 大多数对象在新生代 Eden 出生 | 新生代回收成本低（**朝生夕死**） |
| **大对象直接进老年代** | 超过 `-XX:PretenureSizeThreshold` 的大对象直接老年代 | 避免在 Eden/Survivor 之间反复复制 |
| **长期存活对象晋升** | 在 Survivor 中每熬过一次 Minor GC 年龄 +1，达 `-XX:MaxTenuringThreshold`（默认 15）晋升 | 分代思想 |
| **动态年龄判定** | Survivor 中**同年龄对象总和 > Survivor 空间一半**时，该年龄及以上的直接晋升 | 避免 Survivor 装不下 |
| **空间分配担保** | Minor GC 前检查老年代剩余空间是否够容纳晋升对象，不够则先触发 Full GC | 防止晋升失败 |

> [!tip] TLAB 是什么
> **Thread Local Allocation Buffer**：每个线程在 Eden 中预先划一小块私有区域，分配对象时在自己的 TLAB 内"指针碰撞"，**无需同步**。
> 只有 TLAB 用完或对象过大时才走共享 Eden（需要 CAS）。这是 JVM 让"高并发分配对象"变快的核心优化之一。

## 三、垃圾判定

### 3.1 为什么不用引用计数

引用计数无法解决**循环引用**（两个对象互相引用但都不可达，计数却都不为 0）。Python 用引用计数 + 额外机制，JVM **不用**。

### 3.2 可达性分析（JVM 的选择）

从一组 **GC Roots** 出发向下遍历引用链，**不可达**的对象判定为可回收。

| GC Roots 包括 | 说明 |
|---|---|
| 虚拟机栈中局部变量表引用的对象 | 最主体（正在被使用） |
| 方法区中**静态变量**引用的对象 | `static` 字段 |
| 方法区中**常量**引用的对象 | 常量池 |
| 本地方法栈中 JNI 引用的对象 | native 引用 |
| 活跃线程、同步锁持有的对象 | 被 monitor 持有 |
| JVM 内部引用（基本类型的 Class、常驻异常、系统类加载器） | —— |

> [!warning] "不可达"不等于"立刻被回收"
> 对象被判定不可达后还要经历**两次标记**：若重写了 `finalize()` 且未被调用过，会被放入 `F-Queue` 等待执行（**不保证执行完**）。执行后若仍未与 GC Roots 建立关联，才真正回收。
> 实践：**不要依赖 `finalize()` 做资源释放**，用 `try-with-resources` 或 `Cleaner`。

### 3.3 各种引用

| 引用类型 | 回收时机 | 典型用途 |
|---|---|---|
| **强引用** | 永不回收（除非不可达） | 普通 `new` |
| **软引用** `SoftReference` | **内存不足时**回收 | 缓存（内存敏感） |
| **弱引用** `WeakReference` | **下次 GC 必回收** | `ThreadLocalMap` 的 key、`WeakHashMap` |
| **虚引用** `PhantomReference` | 无法通过它访问对象，仅用于回收通知 | 堆外内存回收（`DirectByteBuffer` 的 `Cleaner`） |

## 四、垃圾回收算法

| 算法 | 过程 | 优点 | 缺点 | 用在哪 |
|---|---|---|---|---|
| **标记-清除** | 标记可达 → 清除未标记 | 简单 | **产生内存碎片**、标记与清除效率都不高 | 老年代（CMS 的并发清除） |
| **标记-复制** | 把存活对象复制到另一半，清空原半区 | 无碎片、分配快（指针碰撞） | **浪费一半空间**、存活多时复制成本高 | **新生代**（Eden + 两个 Survivor） |
| **标记-整理** | 标记 → 把存活对象向一端移动 → 清理边界外 | 无碎片 | 移动对象需 STW，成本高 | **老年代**（Serial Old、Parallel Old） |

> [!important] 新生代为什么用复制算法
> 新生代对象**绝大多数朝生夕死**（经验上约 98% 可回收），所以不需要 1:1 划分。HotSpot 用 **Eden : S0 : S1 = 8 : 1 : 1**，每次只浪费 10%，且复制量很小。
> 一次 Minor GC 的流程：Eden + 当前 Survivo r 中的存活对象 → **复制到另一个 Survivor** → 清空 Eden 与原来的 Survivor → **两个 Survivor 角色互换**。

### 4.1 分代收集

| 分代 | 特点 | 触发 | 常用算法 |
|---|---|---|---|
| **新生代** | 对象朝生夕死、回收频繁 | **Minor GC / Young GC**（Eden 满） | 复制 |
| **老年代** | 存活率高、回收少 | **Major/Full GC** | 标记-清除或标记-整理 |

**跨代引用问题**：老年代对象可能引用新生代对象，若 Minor GC 要扫描整个老年代就白干了。
解法是 **记忆集（Remembered Set）**，HotSpot 用 **卡表（Card Table）**——把老年代分成 512 字节的卡，只记录"哪些卡里有跨代引用"，Minor GC 只扫脏卡。

## 五、垃圾收集器

### 5.1 全景（按代与特性）

| 收集器 | 作用区域 | 算法 | 停顿特点 | 适用 |
|---|---|---|---|---|
| **Serial** | 新生代 | 复制 | **单线程 STW** | 客户端/小内存 |
| **ParNew** | 新生代 | 复制 | 多线程 STW | 曾与 CMS 搭配 |
| **Parallel Scavenge** | 新生代 | 复制 | 多线程 STW，**关注吞吐量** | 后台批处理 |
| **Serial Old** | 老年代 | 标记-整理 | 单线程 STW | 客户端/CMS 后备 |
| **Parallel Old** | 老年代 | 标记-整理 | 多线程 STW，**关注吞吐量** | 与 Parallel Scavenge 搭配 |
| **CMS** | 老年代 | 标记-清除（并发） | **低延迟**，但有碎片与 Concurrent Mode Failure | JDK9 起废弃、14 移除 |
| **G1** | 整堆（分 Region） | 复制 + 标记-整理 | **可预测停顿**，JDK9+ 默认 | 大堆、低延迟 |
| **ZGC** | 整堆 | 并发标记-整理（染色指针 + 读屏障） | **极低停顿（毫秒级）** | 超大堆、极低延迟 |
| **Shenandoah** | 整堆 | 并发整理（Brooks 指针） | 低停顿 | 与 ZGC 定位类似 |

> [!important] 吞吐量 vs 低延迟的取舍（面试常问）
> - **吞吐量优先**：`Parallel Scavenge + Parallel Old`。GC 总时间占比小，但单次 STW 可能较长 → 适合**离线批处理**。
> - **低延迟优先**：`G1` / `ZGC`。单次停顿短，但 GC 占用更多 CPU 与内存 → 适合**在线服务**。
> **没有最好的收集器，只有匹配业务 SLA 的收集器。**

### 5.2 CMS 的四个阶段（理解"并发收集"的经典样本）

| 阶段 | 是否 STW | 做什么 |
|---|---|---|
| 初始标记 | **是**（很短） | 只标记 GC Roots **直接关联**的对象 |
| 并发标记 | 否 | 从直接关联对象开始遍历整个对象图（**耗时最长，与用户线程并发**） |
| 重新标记 | **是**（较短） | 修正并发标记期间因用户线程运行而变动的记录（用增量更新/原始快照） |
| 并发清除 | 否 | 清除不可达对象 |

**CMS 的三大问题**：① **内存碎片**（标记-清除不整理）→ 可能触发 `Concurrent Mode Failure` 退化为 Serial Old；② **并发阶段占用 CPU**；③ **浮动垃圾**（并发清除期间新产生的垃圾只能留到下次）。

### 5.3 G1 的核心思想

| 概念 | 说明 |
|---|---|
| **Region** | 把堆分成大小相等的 Region（1～32MB），每个 Region 动态扮演 Eden/Survivor/Old/**Humongous**（大对象） |
| **可预测停顿模型** | 通过 `-XX:MaxGCPauseMillis` 设定目标停顿，G1 在**回收收益最高**的 Region 集合（Collection Set）上做回收 |
| **Young GC / Mixed GC** | 先回收新生代；根据**全局并发标记**结果，挑选"垃圾最多"的老年代 Region 一起回收 |
| **SATB** | Snapshot-At-The-Beginning，并发标记用**原始快照**解决对象消失问题 |
| **记忆集更精细** | 每个 Region 维护 RSet（谁引用了我），避免全堆扫描 |

> [!tip] G1 的关键参数
> `-XX:MaxGCPauseMillis`（目标停顿，**不要设得过小**，否则会退化为频繁小回收）、`-XX:G1HeapRegionSize`、`-XX:InitiatingHeapOccupancyPercent`（触发并发标记的堆占用阈值）、`-XX:G1NewSizePercent`/`G1MaxNewSizePercent`。

### 5.4 ZGC 的一句话原理

**染色指针（Colored Pointers）** 把标记信息存在**指针的闲置位**里，配合 **读屏障** 在访问对象时"顺带修正引用"，从而让标记、转移、重定位**几乎全阶段并发**，停顿与堆大小基本无关（目标 < 10ms）。
代价：需要 64 位、内存占用更高（多色指针与转发表）、早期版本不支持压缩指针（`-XX:-UseCompressedOops`）等。

## 六、GC 日志怎么读

```bash
# JDK 9+ 统一日志框架（推荐）
-Xlog:gc*:file=/var/log/gc.log:time,uptime,level,tags:filecount=5,filesize=50m

# JDK 8 及之前
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/var/log/gc.log
```

**关键指标**：

| 指标 | 含义 | 关注点 |
|---|---|---|
| `GC` / `Pause Young` | 一次 Young GC | **频率**（过频说明新生代太小或分配速率过高） |
| `Pause Full` | 一次 Full GC | **频率**（频繁 Full GC 是核心告警） |
| `Eden->...` | 回收前后各代占用 | 判断晋升速率是否异常 |
| `real=...` | **真实停顿时间** | 与 SLA 对比 |
| `Allocation Failure` | 触发原因（Eden 满了） | 最常见，正常 |
| `Metadata GC Threshold` | 元空间触发 | 可能是类加载过多（动态代理、热部署） |
| `Ergonomics` | JVM 自动决策的参数 | 看最终生效的堆大小与收集器 |

> [!warning] 三个必须进监控的 GC 信号
> ① **Full GC 次数与总耗时**（持续增长说明有泄漏或参数不合理）；
> ② **单次 STW 最大值**（超过 SLA 要告警）；
> ③ **老年代占用趋势**（Full GC 后若仍居高不下 → 很可能真的泄漏，见 [[8-JVM调优与故障排查]]）。

## 七、类加载机制

### 7.1 加载过程（五个阶段）

| 阶段 | 做什么 | 要点 |
|---|---|---|
| **加载** | 读取字节码，生成 `Class` 对象 | 可由自定义类加载器参与 |
| **验证** | 文件格式/元数据/字节码/符号引用验证 | 保证安全 |
| **准备** | 为**静态变量**分配内存并设**零值** | `static int a = 1` 此时 `a=0`；但 **`static final` 常量在此直接赋真值**（编译期常量） |
| **解析** | 符号引用 → 直接引用 | 可在初始化后再做（动态绑定） |
| **初始化** | 执行 `<clinit>`（静态变量赋值 + 静态代码块） | **懒加载**：首次主动使用才触发 |

**六种主动使用**（触发初始化）：`new`/读写静态字段（非 final 常量）/调用静态方法/反射/初始化子类（父类先初始化）/作为启动类（main）。
**不触发**：通过子类访问父类静态字段、`Class` 数组定义、常量引用（编译期已内联）。

### 7.2 三大类加载器与双亲委派

| 加载器 | 加载什么 |
|---|---|
| **Bootstrap ClassLoader** | `JAVA_HOME/lib` 核心类（`java.lang.*` 等），C++ 实现 |
| **Extension / Platform ClassLoader** | `JAVA_HOME/lib/ext`（JDK9+ 为平台类加载器） |
| **Application ClassLoader** | 应用 classpath |

**双亲委派模型**：收到加载请求先**委派给父加载器**，父加载不了才自己加载。

| 好处 | 说明 |
|---|---|
| **安全** | 防止自定义 `java.lang.String` 冒充核心类 |
| **避免重复加载** | 同一个类只被一个加载器加载 |

> [!tip] 为什么要打破双亲委派
> - **SPI 场景**（JDBC）：核心类 `DriverManager` 由 Bootstrap 加载，却要加载应用 classpath 里的驱动实现 → 用**线程上下文类加载器** `Thread.currentThread().getContextClassLoader()` 反向委派。
> - **热部署/OSGi**：需要同一类被不同加载器加载成不同 `Class` 对象（**类的唯一性 = 类加载器 + 全限定名**）。

### 7.3 类的唯一性

> [!important] 一句话记住
> 两个类相等的条件是：**同一个类加载器 + 同一个全限定名**。
> 所以"同名类被不同加载器加载"会导致 `ClassCastException`（看似类型相同），这是热部署与插件化框架的经典坑。

## 八、JIT 编译与逃逸分析

| 概念 | 说明 |
|---|---|
| **解释器 + JIT 混合** | 启动用解释器（快启动），热点代码由 JIT 编译成机器码（快执行） |
| **热点探测** | 基于**计数器**（方法调用计数器 + 回边计数器） |
| **C1 / C2** | C1 编译快、优化浅；C2 编译慢、优化深（激进） |
| **分层编译** | JDK7+ 默认：先 C1 快速编译，热点足够再 C2 深度优化 |
| **逃逸分析** | 分析对象是否逃出方法/线程作用域 |
| **栈上分配 / 标量替换** | 不逃逸的对象可以**不进堆**（拆成标量放在栈上），减少 GC 压力 |
| **锁消除** | 不逃逸对象的同步操作可被消除 |

> [!warning] 常见误解
> **"对象一定分配在堆上"** 在 JIT 优化后并不绝对——栈上分配与标量替换让部分对象不落堆。
> 但要注意：**逃逸分析是 JIT 的优化，不改变 Java 语义**（你仍然不能依赖它，也不能因此认为对象没有重量）。

## 九、本篇必答

> [!question] 面试官可能这样问
> **Q：JVM 内存区域怎么划分？**
> A：线程私有的**程序计数器、虚拟机栈、本地方法栈**；线程共享的**堆、方法区**。另有**直接内存**不在规范内。JDK8 起方法区实现为**元空间**（移到本地内存，取代永久代）。
>
> **Q：怎么判断对象可以回收？**
> A：**可达性分析**：从 **GC Roots**（栈中局部变量引用的对象、静态变量、常量、JNI 引用、活跃线程等）出发遍历，不可达的判定可回收。**不用引用计数**，因为它解决不了循环引用。注意对象还要经历 `finalize` 的两次标记才真正回收。
>
> **Q：新生代为什么用复制算法？**
> A：新生代对象**朝生夕死**（绝大多数可回收），复制算法只需复制少量存活对象且**没有内存碎片、分配可用指针碰撞**。HotSpot 用 **Eden:S0:S1 = 8:1:1**，只浪费 10% 空间。
>
> **Q：GC 收集器怎么选？**
> A：**吞吐优先**（离线批处理）用 `Parallel Scavenge + Parallel Old`；**低延迟优先**（在线服务）用 **G1**（JDK9+ 默认，可设 `MaxGCPauseMillis` 目标停顿），超大堆且要求毫秒级停顿用 **ZGC**。CMS 已废弃/移除。选型依据是**业务的延迟 SLA 与堆规模**。
>
> **Q：双亲委派是什么？为什么需要？**
> A：类加载请求先委派父加载器，父加载不了才自己加载。好处是**安全**（防止核心类被冒充）与**避免重复加载**。SPI（如 JDBC）与热部署场景需要**打破**它，靠线程上下文类加载器或自定义加载器实现。
>
> **Q：一个对象创建时发生了什么？**
> A：类加载检查 → 分配内存（指针碰撞/空闲列表，并发用 **TLAB** 或 CAS）→ 内存置零 → 设置对象头（Mark Word + 类型指针）→ 执行构造器。对象在内存中分**对象头、实例数据、对齐填充**三部分，大小是 **8 字节的整数倍**。
