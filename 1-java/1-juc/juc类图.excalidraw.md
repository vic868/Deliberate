AbstractOwnableSynchronizer（AOS）：独占锁归属的基类
AbstractOwnableSynchronizer 是 JUC 并发框架底层的一个非常小巧但至关重要的抽象类。 ^Lbg3PH6m

3. AOS 的关键作用 ^4I7kxHIu

1、实现可重入性（Reentrancy）判断：
当一个线程尝试调用 lock() 时，AQS 的独占逻辑（如 tryAcquire）会通过 getExclusiveOwnerThread() == Thread.currentThread() 判断当前线程是否就是锁的持有者：

如果是同一线程，则认定为重入，直接对 state 计数累加，无需阻塞排队。

如果不是，则进入 CAS 竞争或加入等待队列。 ^oXkxEkX5

2、死锁排查与线程监控（Diagnostics）：
由于 AOS 明确记录了具体是哪个 Thread 占有了锁，JVM 诊断工具（如 VisualVM、JConsole、jstack）在导出 Thread Dump 时，能够精确打印出当前锁被哪个线程独占（例如 Locked ownable synchronizers: <0x...> 标识），极大地方便了线上排查死锁与高耗时卡顿。 ^s9mXqBfO

ReadWriteLock：读写分离的高效并发锁
ReadWriteLock 是一个读写锁的门面接口，维护了一对关联锁：一个用于只读操作的读锁（ReadLock），一个用于写入操作的写锁（WriteLock）。 ^VUPCMbOm

4. 适用场景
适用于“读多写少”的业务场景（如系统的基础配置缓存、用户白名单列表等），能将单纯排他的读吞吐量提升数倍。 ^91fUgWPP

What（什么是 AQS） ^sgqjDMZ7

本质：它是一个用来构建显式锁和同步器的通用底层框架与骨架。 ^NXWg3zka

实现载体：AQS 完全在 Java API 层面构建，区别于依赖 JVM 字节码和 C++ 管程实现的 synchronized 关键字。 ^Cp4Djfn2

Why（为什么需要 AQS） ^P8syEcNz

在 AQS 出现之前，Java 开发者只能依靠 synchronized 内置锁或手写并发同步，存在诸多痛点： ^crvYa6yK

规避内置锁的功能局限：synchronized 无法实现获取锁时的超时放弃（tryLock）、响应中断（lockInterruptibly），也不支持可定制的公平性调度。 ^OihUdg9e

消除重复造轮子：实现一个线程安全的锁极度困难（涉及多线程高并发抢占、原子状态维护、线程安全入队、超时重试、精准挂起与唤醒等细节）。AQS 将这些通用的底层排队、调度和状态流转封装为标准模板，开发者无需重新编写复杂的队列算法。 ^huGdqF7L

Who（谁持有、谁管理、面向谁） ^miDJ2oli

管理对象（管理谁）：并发竞争同步资源的 Thread（线程）。未拿到资源的线程被包装为 AQS 的 Node 节点进行排队。 ^ouYsJZ5D

持有者记录（谁持有）：通过其父类 AbstractOwnableSynchronizer 维护 exclusiveOwnerThread 变量，明确标记当前独占资源的线程（方便重入判断及死锁诊断）。 ^Tt0w03XP

使用者（面向谁）：

下游组件：面向 JUC 核心同步工具（ReentrantLock、ReentrantReadWriteLock、Semaphore、CountDownLatch 等），它们通过内部静态类继承 AQS 落地具体功能。

开发者/架构师：面向需要自研高性能并发组件或自定义分布式/本地同步器的框架开发者（如 RPC 框架中的异步转同步栅栏）。 ^1Pa5Ft9T
