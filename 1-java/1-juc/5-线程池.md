## 一、为什么需要线程池

### 1.1 不用线程池的代价

| 问题 | 具体表现 | 后果 |
| --- | --- | --- |
| **创建/销毁开销** | 每次 `new Thread()` 都要向 OS 申请内核线程、分配栈（默认约 1MB 地址空间）、注册到调度器 | 单次约几十微秒~上百微秒，QPS 上万时全耗在创建上 |
| **无界创建 → OOM / 崩机** | 请求量等于线程数，瞬间创建上万线程 | `OutOfMemoryError: unable to create new native thread`，或直接拖垮机器 |
| **无法控制并发** | 下游 DB/第三方接口被打爆 | 连接池耗尽、被限流封禁、雪崩 |
| **无法统一管理** | 没有线程名、没有监控指标、无法优雅关闭 | 线上排查时 `jstack` 里全是 `Thread-12345`，看不出是谁 |
| **上下文切换放大** | 线程数远超核数时，CPU 大量时间花在切换而非计算 | 吞吐下降（典型的"加线程反而变慢"） |

### 1.2 线程池带来的四个能力

1. **复用**：线程创建一次反复使用，摊薄创建成本。
2. **限流/控制并发**：`corePoolSize` / `maximumPoolSize` / 队列容量共同决定系统的并发上限，是**保护下游**的第一道闸门。
3. **可管理**：线程命名、统一异常处理、活跃数/队列长度/拒绝数等指标可观测。
4. **可编排**：定时、延迟、周期、分治（ForkJoin）都能基于它构建。

> [!important] 一句话定位
> **线程池不是"让程序更快的工具"，而是"把不可控的并发变成可观测、可限制、可退让的资源池"的工具。** 面试时先答这句话，再展开参数与源码。

## 二、`ThreadPoolExecutor` 七大参数

### 2.1 构造器

```java
public ThreadPoolExecutor(int corePoolSize,                      // ① 核心线程数
                          int maximumPoolSize,                   // ② 最大线程数
                          long keepAliveTime,                    // ③ 空闲存活时间
                          TimeUnit unit,                         // ④ 时间单位
                          BlockingQueue<Runnable> workQueue,     // ⑤ 工作队列
                          ThreadFactory threadFactory,           // ⑥ 线程工厂
                          RejectedExecutionHandler handler) {    // ⑦ 拒绝策略
    if (corePoolSize < 0 ||
        maximumPoolSize <= 0 ||
        maximumPoolSize < corePoolSize ||
        keepAliveTime < 0)
        throw new IllegalArgumentException();
    if (workQueue == null || threadFactory == null || handler == null)
        throw new NullPointerException();
    this.acc = System.getSecurityManager() == null ? null : AccessController.getContext();
    this.corePoolSize = corePoolSize;
    this.maximumPoolSize = maximumPoolSize;
    this.workQueue = workQueue;
    this.keepAliveTime = unit.toNanos(keepAliveTime);
    this.threadFactory = threadFactory;
    this.handler = handler;
}
```

注意构造器里就做了校验：`maximumPoolSize >= corePoolSize`、`keepAliveTime >= 0`、队列/工厂/策略不能为 null。

### 2.2 逐个讲透

| 参数 | 含义 | 关键行为 | 常见误区 |
| --- | --- | --- | --- |
| `corePoolSize` | 核心线程数，**常驻**线程数 | 默认即使空闲也不回收；提交任务时优先创建到 core | ❌ 以为"核心线程一开始就全建好" → 默认是**懒创建**（来任务才建），除非调 `prestartAllCoreThreads()` |
| `maximumPoolSize` | 线程数上限 | **只有在队列满了之后才会用到** | ❌ 以为它是"并发上限" → 队列无界时它**永远不生效** |
| `keepAliveTime` | 超出 core 的空闲线程存活多久后被回收 | 仅在 `getTask` 用 `poll(keepAliveTime)` 时生效 | ❌ 以为对核心线程无效 → 配合 `allowCoreThreadTimeOut(true)` 就对核心线程生效 |
| `unit` | `keepAliveTime` 的单位 | — | 用 `TimeUnit.SECONDS` 而不是裸数字，避免单位歧义 |
| `workQueue` | 任务队列 | 决定 `maximumPoolSize` 是否有意义 | ❌ 用 `LinkedBlockingQueue()` 无参构造 → 无界队列，OOM 元凶 |
| `threadFactory` | 线程创建工厂 | 命名、是否 daemon、优先级、`UncaughtExceptionHandler` | ❌ 用默认工厂 → 线程名是 `pool-N-thread-M`，排查时认不出业务 |
| `handler` | 拒绝策略 | 队列满 + 线程数达 max 时触发 | ❌ 用默认 `AbortPolicy` 却没接异常 → 任务静默丢失且调用方拿到 `RejectedExecutionException` |

### 2.3 三个参数之间的"耦合关系"（比单独背参数重要得多）

```
                 workQueue 的容量
                  │
   ┌──────────────┴───────────────┐
   │                              │
 有界小                          无界
   │                              │
   ▼                              ▼
 队列很快满 → 触发扩容到 max      队列永不满 → 永远只用 core 个线程
 → max 是真正的"突发并发上限"     → maximumPoolSize 形同虚设（这是最坑的一点）
   │                              │
   └──────────┬───────────────────┘
              ▼
        真正的并发上限 = min(max, 下游能承受的并发)
```

**结论**：`corePoolSize` 决定**稳态并发度**，`workQueue` 容量决定**能容忍多少突发**，`maximumPoolSize` 决定**突发时愿意为下游扛多少额外并发**。三者必须一起设计，单独设任何一个都没有意义。

## 三、任务提交的完整决策流程

### 3.1 四步决策（必须背下来）

```
submit(task) / execute(task)
        │
        ▼
┌───────────────────────────────────┐
│ ① 当前线程数 < corePoolSize ?      │──是──▶ 创建核心线程执行该任务
└───────────────┬───────────────────┘
                │否
                ▼
┌───────────────────────────────────┐
│ ② 工作队列未满？                    │──是──▶ 任务入队，等待已有线程来取
└───────────────┬───────────────────┘
                │否（队列已满）
                ▼
┌───────────────────────────────────┐
│ ③ 当前线程数 < maximumPoolSize ?   │──是──▶ 创建非核心线程执行该任务
└───────────────┬───────────────────┘
                │否
                ▼
┌───────────────────────────────────┐
│ ④ 执行拒绝策略 handler              │
└───────────────────────────────────┘
```

### 3.2 **"先入队再扩容"这个反直觉顺序**（高频追问点）

大多数人的直觉是："核心满了就扩到 max，max 也满了才排队"。**真实逻辑恰好相反：核心满了先排队，队列满了才扩到 max。**

这个顺序导致的直接后果：

| 场景 | 实际行为 | 后果 |
| --- | --- | --- |
| `core=4, max=64, queue=10000`（大队列） | 队列几乎不会满 → 线程数**几乎永远是 4** | `max=64` 写了跟没写一样；请求全部在队列里排队，**RT 线性膨胀**，直到超时 |
| `core=4, max=64, queue=10`（小队列） | 队列一满立刻扩容到 64 | 线程数剧烈波动；64 个线程同时打下游，容易打爆 DB 连接池 |
| `core=4, max=64, queue=SynchronousQueue` | 队列容量 0，一提交就"满" | 等效于"来任务就建线程直到 64，然后拒绝"（这就是 `newCachedThreadPool` 的形态） |

> [!danger] 最典型的线上事故
> `new ThreadPoolExecutor(8, 8, 0, SECONDS, new LinkedBlockingQueue<>())` —— 无界队列 + max 等于 core。
> 现象：接口 RT 从 50ms 慢慢涨到 3s、5s……最终大面积超时；`jstack` 看线程只有 8 个，每个都在干活；**队列长度（`getQueue().size()`）持续增长，内存持续上涨**，最后 `OutOfMemoryError: Java heap space`（任务对象把堆撑爆）。
> 排查：JVM 内存曲线缓慢上升 + 线程数不变 + 队列长度飙升 = 生产速率持续大于消费速率，**这是容量问题不是 bug**。要么扩 core、要么限流、要么给队列加上界让拒绝策略生效（快速失败优于慢性死亡）。

### 3.3 `execute` 源码（每一行都对应上面的流程图）

```java
public void execute(Runnable command) {
    if (command == null)
        throw new NullPointerException();

    int c = ctl.get();
    // ① 工作线程数 < corePoolSize → 直接新建一个核心线程来跑这个任务
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true))
            return;
        c = ctl.get();          // 创建失败（如线程池已关闭/并发竞争）→ 重新读 ctl 走后面的逻辑
    }
    // ② 线程池还在 RUNNING 且入队成功 → 走"入队"路径
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        // ③ 入队后二次检查：线程池可能在这两步之间被 shutdown 了
        if (!isRunning(recheck) && remove(command))
            reject(command);                 // 已关闭且成功把刚入队的任务摘出来 → 拒绝
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);          // ⚠️ 关键防御：core=0 或线程都已退出 → 至少留一个线程消费队列
    }
    // ④ 队列已满（或线程池非 RUNNING）→ 尝试扩容到 maximumPoolSize
    else if (!addWorker(command, false))
        reject(command);                     // 扩容也失败 → 拒绝
}
```

三个容易忽略的细节：

1. **`addWorker(null, false)` 那个 `else if` 是干什么的**：如果 `corePoolSize = 0`（比如 `newCachedThreadPool`），第一次 `addWorker(command, true)` 一定失败（因为 `workerCountOf(c) < 0` 不成立，实际是 `wc >= corePoolSize` 成立），此时如果队列里有任务却**没有任何线程**在消费，就会永远饿死。这两行是保证"队列非空时至少存在一个工作线程"的兜底。
2. **`remove(command)`**：把刚入队但线程池已关闭的任务摘出来，只有摘成功了才拒绝（避免任务既没执行也没被拒绝）。
3. **`offer` 而不是 `put`**：`execute` 永远不阻塞调用方线程，队列满了立刻返回 false 走扩容/拒绝。

## 四、`ctl`：32 位整数如何同时存状态和线程数

### 4.1 位运算设计

```java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));

private static final int COUNT_BITS = Integer.SIZE - 3;              // 32 - 3 = 29
private static final int CAPACITY   = (1 << COUNT_BITS) - 1;         // 低 29 位全 1 = 536870911

// 高 3 位表示运行状态
private static final int RUNNING    = -1 << COUNT_BITS;   // 111
private static final int SHUTDOWN   =  0 << COUNT_BITS;   // 000
private static final int STOP       =  1 << COUNT_BITS;   // 001
private static final int TIDYING    =  2 << COUNT_BITS;   // 010
private static final int TERMINATED =  3 << COUNT_BITS;   // 011

private static int runStateOf(int c)     { return c & ~CAPACITY; }   // 取高 3 位
private static int workerCountOf(int c)  { return c &  CAPACITY; }   // 取低 29 位
private static int ctlOf(int rs, int wc) { return rs | wc; }
```

```
 ctl（一个 AtomicInteger，32 位）
 ┌───┬─────────────────────────────┐
 │ 3 │            29               │
 │位 │           位                │
 └───┴─────────────────────────────┘
  运行状态          工作线程数（最大 536870911 ≈ 5.36 亿）

 位布局示例（RUNNING）：
 111 00000000000000000000000000000
 ↑↑↑ ↑
 状态  线程数=0
```

> [!tip] 为什么要这么设计
> 一次 CAS 就能同时校验"状态没变"并"线程数 +1"，避免了对两个字段分别加锁。这就是 `addWorker` 里 `compareAndIncrementWorkerCount(c)` 能成立的前提：**状态与计数在同一次 CAS 里原子地检查与更新**。把两个字段拆开，就必须上锁——这也是 Doug Lea 的经典手法。

### 4.2 五个状态与流转

| 状态 | 值 | 含义 | 是否接受新任务 | 是否处理队列任务 | 是否中断在跑的任务 |
| --- | --- | --- | --- | --- | --- |
| `RUNNING` | 111 | 正常运行 | ✅ | ✅ | ❌ |
| `SHUTDOWN` | 000 | 调用了 `shutdown()` | ❌ | ✅（**队列里的任务会跑完**） | ❌ |
| `STOP` | 001 | 调用了 `shutdownNow()` | ❌ | ❌（**队列被丢弃并返回**） | ✅ |
| `TIDYING` | 010 | 所有任务已终止、workerCount 为 0，即将调用 `terminated()` | ❌ | ❌ | ❌ |
| `TERMINATED` | 011 | `terminated()` 钩子执行完毕 | ❌ | ❌ | ❌ |

```
   RUNNING ──shutdown()────▶ SHUTDOWN ──队列空 & 线程数 0──▶ TIDYING ──▶ TERMINATED
      │                          │                              ▲
      └────shutdownNow()────▶ STOP ──线程数 0───────────────────┘
```

状态流转的实现（`tryTerminate` 是核心，每次 worker 退出时调用）：

```java
final void tryTerminate() {
    for (;;) {
        int c = ctl.get();
        // 还在 RUNNING / 已 TIDYING / 已 TERMINATED → 什么都不做
        if (isRunning(c) ||
            runStateAtLeast(c, TIDYING) ||
            // SHUTDOWN 但队列非空 → 还有任务要处理，不能终止
            (runStateOf(c) == SHUTDOWN && !workQueue.isEmpty()))
            return;
        if (workerCountOf(c) != 0) {   // 还有线程 → 只中断一个空闲线程，让它去传递中断
            interruptIdleWorkers(ONLY_ONE);
            return;
        }
        final ReentrantLock mainLock = this.mainLock;
        mainLock.lock();
        try {
            if (ctl.compareAndSet(c, ctlOf(TIDYING, 0))) {
                try {
                    terminated();                              // 钩子
                } finally {
                    ctl.set(ctlOf(TERMINATED, 0));
                    termination.signalAll();                   // 唤醒 awaitTermination 的线程
                }
                return;
            }
        } finally {
            mainLock.unlock();
        }
        // CAS 失败 → 重试
    }
}
```

### 4.3 `shutdown` vs `shutdownNow`（面试必问）

| 维度 | `shutdown()` | `shutdownNow()` |
| --- | --- | --- |
| 新状态 | `SHUTDOWN` | `STOP` |
| 拒绝新任务 | ✅ | ✅ |
| 队列中已有任务 | **继续执行完** | **丢弃**，`drainQueue()` 返回未执行的任务列表 |
| 正在执行的任务 | 不中断 | **中断**（`interruptWorkers()`，对所有 worker） |
| 返回值 | `void` | `List<Runnable>`（未执行的任务，**必须自己处理，不能直接扔**） |
| 适用 | 优雅停机（推荐） | 紧急停止 / 超时兜底 |

```java
public void shutdown() {
    final ReentrantLock mainLock = this.mainLock;
    mainLock.lock();
    try {
        checkShutdownAccess();
        advanceRunState(SHUTDOWN);
        interruptIdleWorkers();     // ⚠️ 只中断"空闲"的 worker
        onShutdown();               // ScheduledThreadPoolExecutor 的钩子
    } finally {
        mainLock.unlock();
    }
    tryTerminate();
}

public List<Runnable> shutdownNow() {
    List<Runnable> tasks;
    final ReentrantLock mainLock = this.mainLock;
    mainLock.lock();
    try {
        checkShutdownAccess();
        advanceRunState(STOP);
        interruptWorkers();         // ⚠️ 中断"所有已启动"的 worker（包括正在跑任务的）
        tasks = drainQueue();       // 把队列里剩下的任务全部取出
    } finally {
        mainLock.unlock();
    }
    tryTerminate();
    return tasks;
}
```

> [!warning] `shutdownNow` 的两个坑
> 1. **返回的任务列表被忽略 = 任务静默丢失**。返回的 `List<Runnable>` 必须落库/写日志/进补偿队列，否则就是数据丢失。
> 2. **中断不等于停止**：`shutdownNow` 只是给线程打上中断标志，如果任务代码里没有检查中断（没有 `isInterrupted()` 检查、没有可中断的阻塞调用、甚至 `catch (InterruptedException e) {}` 吞掉），**任务会继续跑完**。这就是"调了 `shutdownNow` 但进程还是停不下来"的原因。

## 五、源码主线：`execute` → `addWorker` → `runWorker` → `getTask`

### 5.1 `addWorker`：CAS 增计数 + 建线程 + 启动

```java
private boolean addWorker(Runnable firstTask, boolean core) {
    retry:
    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // ① 状态检查：
        //    - 已经是 STOP/TIDYING/TERMINATED → 直接失败
        //    - 是 SHUTDOWN 时，只有"firstTask == null 且队列非空"这种补给线程的情况才允许
        if (rs >= SHUTDOWN &&
            !(rs == SHUTDOWN && firstTask == null && !workQueue.isEmpty()))
            return false;

        for (;;) {
            int wc = workerCountOf(c);
            // ② 上限检查：超过 29 位容量，或超过 core/max（取决于第二个参数）
            if (wc >= CAPACITY ||
                wc >= (core ? corePoolSize : maximumPoolSize))
                return false;
            // ③ 一次 CAS：同时校验状态并让线程数 +1
            if (compareAndIncrementWorkerCount(c))
                break retry;
            c = ctl.get();                                  // CAS 失败，重读
            if (runStateOf(c) != rs)
                continue retry;                             // 状态变了 → 从头再来
            // 否则只是计数竞争失败 → 内层循环重试
        }
    }

    boolean workerStarted = false, workerAdded = false;
    Worker w = null;
    try {
        w = new Worker(firstTask);                          // ④ 创建 Worker（内部通过 ThreadFactory 建线程）
        final Thread t = w.thread;
        if (t != null) {
            final ReentrantLock mainLock = this.mainLock;
            mainLock.lock();                                // ⑤ workers 集合是 HashSet，必须加锁
            try {
                int rs = runStateOf(ctl.get());
                if (rs < SHUTDOWN ||
                    (rs == SHUTDOWN && firstTask == null)) {
                    if (t.isAlive()) throw new IllegalThreadStateException();
                    workers.add(w);
                    int s = workers.size();
                    if (s > largestPoolSize) largestPoolSize = s;   // 记录历史峰值
                    workerAdded = true;
                }
            } finally {
                mainLock.unlock();
            }
            if (workerAdded) {
                t.start();                                  // ⑥ 启动线程 → 进入 runWorker
                workerStarted = true;
            }
        }
    } finally {
        if (!workerStarted)
            addWorkerFailed(w);                             // ⑦ 失败回滚：从 workers 移除 + 计数 -1 + tryTerminate
    }
    return workerStarted;
}
```

> [!note] 两个锁的区分（很容易讲混）
> - **`mainLock`**：`ThreadPoolExecutor` 自己的 `ReentrantLock`，用来保护 `workers` 这个 `HashSet` 以及与状态流转相关的临界区（`addWorker`、`runWorker` 退出、`interruptIdleWorkers`、`tryTerminate`）。
> - **`Worker` 的 AQS 锁**：每个 worker 自己的一把**不可重入独占锁**，用来标识"这个线程此刻是否正在执行任务"。
> 两者完全独立，不要混为一谈。

### 5.2 `Worker`：为什么继承 AQS（深挖点）

```java
private final class Worker extends AbstractQueuedSynchronizer implements Runnable {
    final Thread thread;          // 执行任务的线程（由 ThreadFactory 创建）
    Runnable firstTask;           // 首个任务（可能为 null，表示"只来消费队列"）
    volatile long completedTasks; // 该 worker 累计完成的任务数

    Worker(Runnable firstTask) {
        setState(-1);             // ⚠️ 初始 state = -1：禁止在 runWorker 之前被中断
        this.firstTask = firstTask;
        this.thread = getThreadFactory().newThread(this);
    }

    public void run() { runWorker(this); }

    // ===== AQS 部分 =====
    protected boolean isHeldExclusively() { return getState() != 0; }

    // ⚠️ 注意：不检查 owner，直接 CAS 0→1 → 这是一把【不可重入】锁
    protected boolean tryAcquire(int unused) {
        if (compareAndSetState(0, 1)) {
            setExclusiveOwnerThread(Thread.currentThread());
            return true;
        }
        return false;
    }
    protected boolean tryRelease(int unused) {
        setExclusiveOwnerThread(null);
        setState(0);              // 无条件写 0，不能用 CAS（volatile 写，保证可见性）
        return true;
    }

    public void lock()        { acquire(1); }
    public boolean tryLock()  { return tryAcquire(1); }
    public void unlock()      { release(1); }
    public boolean isLocked() { return isHeldExclusively(); }

    void interruptIfStarted() {
        Thread t;
        if (getState() >= 0 && (t = thread) != null && !t.isInterrupted()) {
            try { t.interrupt(); } catch (SecurityException ignore) { }
        }
    }
}
```

**为什么需要这把 AQS 锁？** 核心用途只有一个：**标识"这个 worker 是否正在执行任务"，从而让 `shutdown` 只中断空闲线程、不中断正在跑任务的线程。**

看 `interruptIdleWorkers` 就明白了：

```java
private void interruptIdleWorkers(boolean onlyOne) {
    final ReentrantLock mainLock = this.mainLock;
    mainLock.lock();
    try {
        for (Worker w : workers) {
            Thread t = w.thread;
            // w.tryLock() 成功 == 这个 worker 此刻没有在执行任务（没有 lock 住自己）
            if (!t.isInterrupted() && w.tryLock()) {
                try {
                    t.interrupt();     // 打断它阻塞在 workQueue.take() 上的等待
                } catch (SecurityException ignore) {
                } finally {
                    w.unlock();
                }
            }
            if (onlyOne) break;
        }
    } finally {
        mainLock.unlock();
    }
}
```

**设计精妙之处**：

| 问题 | 用 AQS 锁怎么解决 |
| --- | --- |
| 怎么区分"空闲线程"和"正在跑任务的线程"？ | `runWorker` 在跑任务前 `w.lock()`、跑完 `w.unlock()`；`interruptIdleWorkers` 用 `w.tryLock()` **尝试获取**——拿到说明它空闲 |
| 为什么不用 `synchronized` 或普通 volatile 标志？ | AQS 提供非阻塞的 `tryLock`（不阻塞调用方），且基于 CAS，成本低；同时天然支持 `isHeldExclusively` 这类查询 |
| 为什么要**不可重入**？ | 重入会让 `tryLock` 在"已经持有"时也返回 true，就无法区分"空闲"与"正在跑"了。**不可重入是这里的硬需求** |
| 为什么初始 `setState(-1)`？ | `interruptIfStarted()` 检查 `getState() >= 0`。初始为 -1 表示"线程还没启动（或还没进入 runWorker）"，此时**不允许中断**，避免在 `t.start()` 之前/刚启动时被打断导致状态错乱。`runWorker` 开头会 `w.unlock()` 把 state 从 -1 变成 0 |

这就是"**`Worker` 继承 AQS 是为了用不可重入的独占锁标识执行状态，为 `shutdownNow`/`shutdown` 的中断策略服务**"的完整解释。

### 5.3 `runWorker`：主循环

```java
final void runWorker(Worker w) {
    Thread wt = Thread.currentThread();
    Runnable task = w.firstTask;
    w.firstTask = null;
    w.unlock();                      // ① 允许中断：state 从 -1 → 0
    boolean completedAbruptly = true;
    try {
        // ② 循环：先跑 firstTask，之后不断从队列取任务；取不到（超时）就退出
        while (task != null || (task = getTask()) != null) {
            w.lock();                // ③ 上锁 = 标记"我正在执行任务"（此刻 shutdown 不会中断我）
            // ④ 如果线程池已经 STOP，确保当前线程是中断状态（处理"刚上锁才发现要停"的竞态）
            if ((runStateAtLeast(ctl.get(), STOP) ||
                 (Thread.interrupted() && runStateAtLeast(ctl.get(), STOP))) &&
                !wt.isInterrupted())
                wt.interrupt();
            try {
                beforeExecute(wt, task);        // ⑤ 扩展点 1
                Throwable thrown = null;
                try {
                    task.run();                 // ⑥ 执行用户任务
                } catch (RuntimeException x) {
                    thrown = x; throw x;
                } catch (Error x) {
                    thrown = x; throw x;
                } catch (Throwable x) {
                    thrown = x; throw new Error(x);
                } finally {
                    afterExecute(task, thrown); // ⑦ 扩展点 2（无论成败都调用）
                }
            } finally {
                task = null;
                w.completedTasks++;
                w.unlock();                     // ⑧ 解锁 = 回到空闲
            }
        }
        completedAbruptly = false;
    } finally {
        processWorkerExit(w, completedAbruptly);  // ⑨ 退出清理：移出 workers、按需补充线程
    }
}
```

关键点：

1. **`w.unlock()` 在循环之前**：把 `state` 从 -1 改成 0，这样空闲等待时可以被 `interruptIdleWorkers` 中断。
2. **`w.lock()` 在 `task.run()` 之前**：这就是"正在执行任务"的标记。
3. **`completedAbruptly`**：区分"正常退出（getTask 返回 null）"和"任务抛异常导致 worker 死亡"。后者需要补一个新线程（`processWorkerExit` 里 `addWorker(null, false)`，前提是线程池还在 RUNNING），否则**异常会永久减少一个工作线程**——这是"线程池越跑越少"的根因。

> [!danger] 任务抛异常会吃掉一个线程
> `task.run()` 抛出的异常会一路穿透 `runWorker`（虽然会调用 `afterExecute`），最终线程终止。`ThreadPoolExecutor` 的兜底是 `processWorkerExit` 里补建线程，所以"能用但会抖动"；**如果用 `submit()` 提交，异常被包进 `FutureTask` 吞掉了，不调用 `get()` 就永远发现不了**。
> 生产建议：① 任务体自己 `try/catch` 全包；② 用自定义 `ThreadFactory` 设置 `UncaughtExceptionHandler` 作为最后一道网；③ 用 `submit` 时一定要 `get()` 或者改用 `execute`。

### 5.4 `getTask`：阻塞取任务与空闲回收

```java
private Runnable getTask() {
    boolean timedOut = false;        // 上一轮 poll 是否超时

    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // ① 线程池已停止：STOP 及以上直接退；SHUTDOWN 且队列空也退
        if (rs >= SHUTDOWN && (rs >= STOP || workQueue.isEmpty())) {
            decrementWorkerCount();
            return null;
        }

        int wc = workerCountOf(c);

        // ② 是否使用"带超时的拉取"：
        //    只要 allowCoreThreadTimeOut=true，或者当前线程数 > core，就用 poll(超时)
        boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;

        // ③ 该退出了：线程数超了 max，或者上一轮 poll 已经超时
        //    且（线程数 > 1 或者队列为空）—— 保证至少留一个线程消费队列
        if ((wc > maximumPoolSize || (timed && timedOut))
            && (wc > 1 || workQueue.isEmpty())) {
            if (compareAndDecrementWorkerCount(c))
                return null;
            continue;
        }

        try {
            // ④ 核心线程：take() 无限阻塞；非核心线程：poll(keepAliveTime) 超时返回 null
            Runnable r = timed ?
                workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS) :
                workQueue.take();
            if (r != null)
                return r;
            timedOut = true;          // poll 超时 → 下一轮循环走 ③ 退出
        } catch (InterruptedException retry) {
            timedOut = false;         // 被中断不算超时（可能是 shutdown 在叫醒我）
        }
    }
}
```

**`allowCoreThreadTimeOut(true)` 的意义**：

| | 默认（`false`） | `true` 时 |
| --- | --- | --- |
| 核心线程空闲时 | `workQueue.take()` 无限阻塞，**永不回收** | `workQueue.poll(keepAliveTime)` 超时后被回收 |
| 结果 | 即使流量低谷也长期占着 core 个线程（每个 ~1MB 栈） | 流量低谷时线程数可降到 0，**省钱但下次要重建**（有抖动） |
| 适用 | 高频稳定的池（大部分业务池） | 低频、突发的池（定时任务池、后台批处理池） |
| 副作用 | — | `wc > corePoolSize` 在 wc 降到 0 后为 false，但 `allowCoreThreadTimeOut` 为 true 时 `timed` 仍为 true，逻辑自洽 |

## 六、四种拒绝策略

### 6.1 内置的四种

| 策略 | 行为 | 优点 | 风险 | 适用场景 |
| --- | --- | --- | --- | --- |
| `AbortPolicy`（**默认**） | 抛 `RejectedExecutionException` | 快速失败，调用方立刻知道 | 如果调用方没接异常 → **任务静默丢失**（异常被上层吞掉） | 核心业务，宁可失败也不降级；但**必须**在调用层捕获并处理 |
| `CallerRunsPolicy` | **由提交任务的线程自己执行** | **天然反压**：调用方（如 Tomcat 线程）被占用 → 上游变慢 → 自然限流，任务不丢 | 如果调用方是 IO/网络线程，会阻塞它；如果调用方本身是线程池线程，可能引发连锁阻塞 | **Web 请求处理池的首选**（压力回传给上游） |
| `DiscardPolicy` | **静默丢弃**，什么都不做 | 无异常、无阻塞 | **任务消失且无任何痕迹**，事故排查时是灾难 | 极少数可丢场景（如采样日志、非关键心跳） |
| `DiscardOldestPolicy` | 丢弃队列中**最旧**的一个任务，然后重新提交当前任务 | 保证新任务能进队 | 被丢的旧任务同样是静默消失；且"重新提交"在池已关闭时会失败 | 只关心最新数据的场景（如行情推送） |

```java
// AbortPolicy：默认策略，源码就是抛异常
public static class AbortPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        throw new RejectedExecutionException("Task " + r.toString() +
                                             " rejected from " + e.toString());
    }
}

// CallerRunsPolicy：在调用方线程直接 run()；注意池已关闭时会静默丢弃
public static class CallerRunsPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            r.run();            // ⚠️ 同步执行，会阻塞提交者
        }
    }
}

// DiscardOldestPolicy：丢掉队首再重试
public static class DiscardOldestPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            e.getQueue().poll();        // 丢最旧的
            e.execute(r);               // 重新提交（可能又失败，但不再递归调用本策略？——
                                        // 实际上 execute 会再次走完整流程，可能再次被拒绝）
        }
    }
}
```

> [!warning] `DiscardOldestPolicy` 的隐含递归
> `e.execute(r)` 会重新走一遍完整提交流程：如果队列又满了且线程数已达 max，会**再次调用拒绝策略**。理论上有递归风险（实践中因为每次都丢掉一个任务，所以能推进，但确实会有多次 `poll()` 的连锁）。

### 6.2 自定义拒绝策略（生产推荐）

核心诉求：**拒绝必须可观测、可追溯、可降级**。静默丢弃是最大的敌人。

```java
public class MonitoredRejectHandler implements RejectedExecutionHandler {

    private static final Logger log = LoggerFactory.getLogger(MonitoredRejectHandler.class);

    private final LongAdder rejectedCount = new LongAdder();   // 暴露给监控系统
    private final String poolName;
    private final RejectedFallback fallback;                   // 降级回调，可为 null

    public MonitoredRejectHandler(String poolName, RejectedFallback fallback) {
        this.poolName = poolName;
        this.fallback = fallback;
    }

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        rejectedCount.increment();

        // ① 指标：Micrometer / Prometheus counter
        Metrics.counter("thread_pool_rejected_total", "pool", poolName).increment();

        // ② 结构化日志：一定要打出池名、当前状态、任务信息，便于定位
        log.error("线程池[{}]拒绝任务。poolSize={}, activeCount={}, queueSize={}, completed={} | task={}",
                poolName, e.getPoolSize(), e.getActiveCount(),
                e.getQueue().size(), e.getCompletedTaskCount(), r);

        // ③ 现场快照（只在第一次拒绝或按比例采样时 dump，否则日志会打爆磁盘）
        if (rejectedCount.sum() == 1) {
            ThreadDumpUtils.dumpOnce(poolName);
        }

        // ④ 降级：落库重试 / 写 Kafka 异步补偿 / 返回兜底结果
        if (fallback != null) {
            fallback.onRejected(r);
        } else {
            throw new RejectedExecutionException("pool[" + poolName + "] is saturated");
        }
    }

    public long getRejectedCount() { return rejectedCount.sum(); }
}
```

**降级方案选择表**：

| 降级方式 | 适用 | 注意 |
| --- | --- | --- |
| 抛异常给上游 | 同步 RPC 接口 | 上游要有明确错误码，不能变成 500 |
| 落库/MQ 异步补偿 | 可延迟的业务（通知、报表） | 要防"补偿本身也打爆下游" |
| 返回兜底值/缓存 | 查询类接口 | 要保证兜底结果不误导业务 |
| 阻塞等待一小会再重试 | 短时突发 | 必须带超时，否则拖垮调用方 |
| **`CallerRunsPolicy`** | Web 请求池 | 最简单有效的反压，零代码 |

## 七、工作队列的选择

### 7.1 常见队列对比

| 队列 | 是否有界 | 底层结构 | 特点 | 对线程池的影响 |
| --- | --- | --- | --- | --- |
| `ArrayBlockingQueue` | **有界**（构造必须指定容量） | 数组 + 单锁 + 两个 `Condition` | 内存紧凑，入队出队共用一把锁 | **生产首选**：容量明确 → `maximumPoolSize` 真正生效 |
| `LinkedBlockingQueue` | **默认无界**（`Integer.MAX_VALUE`） | 链表 + 两把锁（`putLock`/`takeLock`） | 无参构造 = 无界；吞吐略高于 `ArrayBlockingQueue` | ⚠️ **OOM 元凶**；无界时 `max` 永远不生效。要用就显式传容量 |
| `SynchronousQueue` | 容量 0 | 不存储，直接把手 | `put` 必须等一个 `take`（或反之） | 等效"有任务就建线程" → 配合 `max=MAX_VALUE` 就是 `newCachedThreadPool`（线程爆炸） |
| `PriorityBlockingQueue` | **无界**（逻辑上） | 二叉堆 + 单锁 | 按优先级/`Comparator` 出队 | 无界 → max 失效；且**同优先级任务的顺序不确定**（不稳定排序），不能依赖 FIFO |
| `DelayQueue` | **无界** | 优先队列 + 延迟 | 只有到期元素才能出队 | 无界 → max 失效；用于延迟任务（`ScheduledThreadPoolExecutor` 内部用的是它的变体 `DelayedWorkQueue`） |
| `LinkedTransferQueue` | 无界 | 链表 | 有 `transfer()` 直接把元素交给消费者 | 无界 → max 失效 |

### 7.2 队列容量对线程池行为的决定性影响（重点）

```
           corePoolSize = 8, maximumPoolSize = 64

  队列容量 = 10                       队列容量 = 10000（或无界）
  ──────────────                     ────────────────────────
  8 线程忙 → 队列存 10 个              8 线程忙 → 队列存 10000 个
  → 队列满 → 扩到 64                    → 队列远不会满
  → 再有任务 → 拒绝                     → 永远只有 8 个线程
                                        → max=64 完全无效
  表现：线程数上得快，拒绝来得早，       → 请求排队 RT 线性膨胀
        但不会堆积内存                   → 最终内存堆积 + 全部超时
  适合：容忍快速失败的核心链路
                                      表现：慢性死亡（最危险）
```

> [!danger] 用无界队列会让 `maximumPoolSize` 形同虚设（必须记住）
> `maximumPoolSize` 的触发条件是"**队列已满**"。队列无界 ⇒ 永不满 ⇒ `maximumPoolSize` **永远不会被使用**。
> 所以：**`maximumPoolSize` 只是一个"在有界队列满时的应急扩容上限"，它与队列容量是强耦合的一对参数。** 只设 `max` 而不设队列容量，等于什么都没设。
> 检查方法：上线后用 `executor.getQueue().remainingCapacity()` 观察，或者干脆断言 `workQueue.remainingCapacity() != Integer.MAX_VALUE`。

### 7.3 队列选型决策表

| 业务特征 | 推荐队列 | 理由 |
| --- | --- | --- |
| Web 请求处理、同步 RPC | `ArrayBlockingQueue`（容量 = 能容忍的排队数，如 `core × 10`） | 有界、可控、超限快速失败/反压 |
| 短任务、高吞吐、CPU 密集 | `ArrayBlockingQueue` | 避免无界堆积 |
| 任务提交速率极高且要求极低延迟、允许拒绝 | `SynchronousQueue` | 不经队列，直接扩充线程；必须配合合理的 `max`（如 `2 × core`） |
| 明确的优先级业务（VIP 通道） | `PriorityBlockingQueue` | 但要注意无界 + 不稳定排序 |
| 延迟/定时任务 | `DelayQueue` 或直接用 `ScheduledThreadPoolExecutor` | — |
| **真的想无界** | 别用。改成大容量有界队列 | 无界 = 把 OOM 当"背压"，是设计缺陷 |

## 八、`Executors` 的四个工厂方法的坑（面试高频）

### 8.1 源码级看穿了什么

```java
// ① 固定大小：core == max，队列无界
public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(nThreads, nThreads,
                                  0L, TimeUnit.MILLISECONDS,
                                  new LinkedBlockingQueue<Runnable>());   // ⚠️ 无界！
}

// ② 单线程：同样是 1 个线程 + 无界队列
public static ExecutorService newSingleThreadExecutor() {
    return new FinalizableDelegatedExecutorService
        (new ThreadPoolExecutor(1, 1,
                                0L, TimeUnit.MILLISECONDS,
                                new LinkedBlockingQueue<Runnable>()));    // ⚠️ 无界！
}

// ③ 缓存线程池：max 是 Integer.MAX_VALUE，队列是 SynchronousQueue
public static ExecutorService newCachedThreadPool() {
    return new ThreadPoolExecutor(0, Integer.MAX_VALUE,                   // ⚠️ 无上限！
                                  60L, TimeUnit.SECONDS,
                                  new SynchronousQueue<Runnable>());      // ⚠️ 不存储
}

// ④ 定时任务池：底层是 DelayedWorkQueue（无界）
public static ScheduledExecutorService newScheduledThreadPool(int corePoolSize) {
    return new ScheduledThreadPoolExecutor(corePoolSize);
}
// ScheduledThreadPoolExecutor 构造器内部：
//     super(corePoolSize, Integer.MAX_VALUE, 0, NANOSECONDS, new DelayedWorkQueue());
```

### 8.2 四个坑逐条对照

| 工厂方法 | 坑 | 触发条件 | 后果 | 现场特征 |
| --- | --- | --- | --- | --- |
| `newFixedThreadPool` | `LinkedBlockingQueue` **无界** | 消费速度 < 生产速度 | 任务在队列里无限堆积 → **堆内存 OOM**；且 `maximumPoolSize` 无意义 | 线程数恒定（=n），队列长度单调上升，`jmap -histo` 里大量任务对象 |
| `newSingleThreadExecutor` | 同上，且只有 1 个线程 | 单线程消费不过来 | 除了 OOM，还有**单点**：一个任务卡住，后面全部饿死 | 队列长度上升 + 1 个线程长期 `RUNNABLE`/`WAITING` |
| `newCachedThreadPool` | `max = Integer.MAX_VALUE` | 提交速度 > 处理速度 | 线程数无上限增长 → **`OutOfMemoryError: unable to create new native thread`**；大量线程导致上下文切换爆炸 | 线程数飙升（几百上千）、CPU 大量花在 sys、机器 load 极高 |
| `newScheduledThreadPool` | `DelayedWorkQueue` 无界 + `max = Integer.MAX_VALUE` | 定时任务堆积（任务执行慢于周期） | 任务堆积 OOM；`maximumPoolSize` 无意义 | 队列堆积；注意 `ScheduledThreadPoolExecutor.maximumPoolSize` **本身就是无意义的字段** |

### 8.3 `newSingleThreadExecutor` 的额外两个细节

1. **返回的是 `FinalizableDelegatedExecutorService` 包装类**，不是裸的 `ThreadPoolExecutor`。所以 `(ThreadPoolExecutor) Executors.newSingleThreadExecutor()` 会 `ClassCastException`，也**无法调用 `setCorePoolSize` 之类的方法**。
2. `FinalizableDelegatedExecutorService` 重写了 `finalize()`，在对象被 GC 时调用 `shutdown()`——这是"忘了关闭线程池"的兜底。**不要依赖它**（`finalize` 已被废弃，且 GC 时机不确定）。

```java
static class FinalizableDelegatedExecutorService extends DelegatedExecutorService {
    FinalizableDelegatedExecutorService(ExecutorService executor) { super(executor); }
    protected void finalize() { super.shutdown(); }
}
```

### 8.4 结论：生产必须手动 `new ThreadPoolExecutor`

```java
// ✅ 生产标准写法
private static final ThreadPoolExecutor ORDER_POOL = new ThreadPoolExecutor(
        16,                                              // core：按压测确定的稳态并发
        32,                                              // max：突发上限，且不能打爆下游
        60L, TimeUnit.SECONDS,                           // 非核心线程空闲 60s 回收
        new ArrayBlockingQueue<>(500),                   // ✅ 有界队列：容量明确，max 才会生效
        new NamedThreadFactory("order-pool-"),           // ✅ 有语义的线程名
        new MonitoredRejectHandler("orderPool", null)    // ✅ 自定义拒绝：可观测 + 可降级
);

// ✅ 有语义的线程工厂（这是"能不能排查问题"的分水岭）
public class NamedThreadFactory implements ThreadFactory {
    private final AtomicInteger seq = new AtomicInteger(1);
    private final String prefix;
    private final boolean daemon;

    public NamedThreadFactory(String prefix) { this(prefix, false); }
    public NamedThreadFactory(String prefix, boolean daemon) {
        this.prefix = prefix;
        this.daemon = daemon;
    }

    @Override
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r, prefix + seq.getAndIncrement());
        t.setDaemon(daemon);
        t.setUncaughtExceptionHandler((th, e) ->
                log.error("未捕获异常，线程={}, 线程池={}", th.getName(), prefix, e));
        return t;
    }
}
```

**为什么线程名这么重要？** `jstack` 里出现 `order-pool-7` 你能立刻知道是订单池出了问题；出现 `pool-3-thread-17` 你只能在十几个池里猜。**生产排查效率的一半取决于命名规范。**

> [!important] 面试标准答法
> "为什么不用 `Executors`？因为它把两个最危险的参数写死了：`newFixedThreadPool`/`newSingleThreadExecutor` 用无界 `LinkedBlockingQueue`，任务堆积会导致堆 OOM，而且无界队列让 `maximumPoolSize` 失效；`newCachedThreadPool` 的 `maximumPoolSize` 是 `Integer.MAX_VALUE`，会无限制创建线程导致 `unable to create new native thread`；`newScheduledThreadPool` 用的 `DelayedWorkQueue` 也是无界的。
> 所以生产上必须手动 `new ThreadPoolExecutor`，明确给出**有界队列 + 合理的 max + 可见的拒绝策略 + 有语义的线程名**。"

## 九、线程数怎么定

### 9.1 经典公式

```
CPU 密集型：N_threads ≈ N_cpu + 1
             （+1 是为了在某线程偶发缺页/暂停时仍能占满 CPU）

IO 密集型： N_threads ≈ N_cpu × U_cpu × (1 + W / C)
             其中 U_cpu = 目标 CPU 利用率（0~1）
                  W    = 单次请求中等待时间（IO、RPC、DB、锁）
                  C    = 单次请求中计算时间

统一形式（Brian Goetz 的公式）：
             N_threads = N_cpu × U_cpu × (1 + W / C)
```

```java
int cpu = Runtime.getRuntime().availableProcessors();   // 获取可用核数

// CPU 密集型
int cpuBound = cpu + 1;

// IO 密集型：先压测拿到 W 和 C
// 例：单请求 RT 50ms，其中 DB 40ms + Redis 5ms 等待 = 45ms（W），计算 5ms（C）
double w = 45, c = 5, u = 0.8;                          // 目标 CPU 利用率 80%
int ioBound = (int) Math.ceil(cpu * u * (1 + w / c));   // 8 核 → 8×0.8×10 = 64
```

### 9.2 这个公式的三个局限（必须说，否则显得只会背书）

| 局限 | 说明 | 应对 |
| --- | --- | --- |
| **真实瓶颈往往不在 CPU** | 算出来 64，但 DB 连接池只有 20、下游限流 100 QPS → 加线程只会让**排队从线程池转移到连接池**，RT 更差 | 先找到瓶颈（连接池、下游 QPS、锁），**线程数不能超过瓶颈容量** |
| **W/C 是平均值，不是分布** | 平均 RT 50ms 可能掩盖了 P99 800ms；长尾请求会拖住线程 | 用 P95/P99 估 W，并给长尾做超时/隔离 |
| **系统是动态的** | 流量、下游性能、GC 都在变 | 不要一次调死；配合监控 + 动态调参 + 压测回归 |

> [!tip] 实操顺序（比公式重要）
> 1. **粗算**：用公式得到初值（数量级正确即可）；
> 2. **压测**：固定 QPS 逐步加压，观察 **QPS / RT / CPU / 队列长度 / 拒绝数** 五条曲线；
> 3. **找拐点**：QPS 不再上升而 RT 开始陡增的那个点，就是当前配置的容量上限；
> 4. **留余量**：按拐点的 70%~80% 定 `corePoolSize`；
> 5. **定 max 与队列**：`max` 由"下游能承受的最大并发"决定（不是由 CPU 决定），队列容量由"能容忍多长的排队时间"决定（`队列容量 / QPS ≈ 排队时长`）；
> 6. **上线后回归**：验证拒绝率和 P99。

### 9.3 混合型任务的拆分思路

一个请求同时包含 CPU 计算和 IO 等待时，把它塞进一个池，会让"IO 等待的线程"和"CPU 计算的线程"互相挤占。

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| **按任务类型拆分** | `computePool`（core = 核数+1）+ `ioPool`（core 大得多） | 最常用。CPU 任务不因 IO 阻塞而饿死 |
| **阶段拆分（流水线）** | 阶段 1 用 IO 池拉数据 → 阶段 2 用计算池处理 → 阶段 3 用 IO 池写回 | 计算与 IO 比例稳定时效果好 |
| **对下游限流而非加线程** | 用 `Semaphore` 限制进入下游的并发；线程池可以大，但并发信号量小 | 保护下游的最直接手段 |
| **异步化** | `CompletableFuture` 编排，让 IO 等待不占线程（理想；或直接用虚拟线程） | 复杂的多下游扇出场景 |

```java
// 用信号量做"并发漏斗"，把线程池规模和下游并发解耦
private static final Semaphore DB_LIMIT = new Semaphore(20);   // DB 连接池 20

public Order query(long id) throws InterruptedException {
    DB_LIMIT.acquire();
    try {
        return orderMapper.selectById(id);
    } finally {
        DB_LIMIT.release();
    }
}
```

### 9.4 一个"订单服务线程池配置"的实例

**背景**：4C8G 的订单服务，`createOrder` 接口。
压测数据：单请求 P95 RT 50ms，其中 MySQL 写 25ms + Redis 15ms + 下游库存 RPC 5ms（合计 W ≈ 45ms），本地计算/序列化 C ≈ 5ms。
瓶颈：MySQL 连接池 `maximumPoolSize=30`，库存服务压测上限 200 QPS。

```java
@Configuration
public class OrderThreadPoolConfig {

    /** 订单异步处理线程池：承担写库、发消息、通知等异步环节 */
    @Bean("orderAsyncExecutor")
    public ThreadPoolExecutor orderAsyncExecutor() {
        int cpu = Runtime.getRuntime().availableProcessors();   // 4

        // 公式粗算：4 × 0.8 × (1 + 45/5) = 32
        // 但 MySQL 连接池只有 30 → 再多的线程只会排队在连接池上，
        // 所以 core 取 24（连接池的 80%），给其他 DB 调用留出余量。
        int core = 24;
        int max  = 32;   // 突发上限：即使打满也比连接池略大一点，作为短暂排队的缓冲

        return new ThreadPoolExecutor(
                core,
                max,
                60L, TimeUnit.SECONDS,
                // 队列容量：QPS 上限约 500，希望排队时长 ≤ 2s → 容量 ≈ 1000。
                // 取 500（1s 排队）避免"排队过久后即使执行也早已超时"的无效任务。
                new ArrayBlockingQueue<>(500),
                new NamedThreadFactory("order-async-"),
                // CallerRunsPolicy：把压力回传给 Tomcat 线程，
                // 让上游感知到变慢（反压），而不是静默丢弃订单
                new ThreadPoolExecutor.CallerRunsPolicy()
        );
    }
}
```

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `corePoolSize` | 24 | 公式给出 32，但真实瓶颈是 **MySQL 连接池 30**；取 24 留余量，避免线程全部堵在连接池上 |
| `maximumPoolSize` | 32 | 只略高于 core：允许短突发，但不至于把连接池打穿（超出的部分靠队列缓冲） |
| `keepAliveTime` | 60s | 非核心线程（8 个）空闲 1 分钟回收，应对流量的日内波动 |
| `workQueue` | `ArrayBlockingQueue(500)` | **有界**；容量对应约 1s 的排队（500 / 500QPS）——超过 1s 的排队对订单接口没有意义 |
| `threadFactory` | `order-async-` 前缀 | `jstack` 一眼定位；带 `UncaughtExceptionHandler` 兜底 |
| `handler` | `CallerRunsPolicy` | 反压而非丢弃（订单不能丢）；同时监控拒绝/回退次数 |
| `allowCoreThreadTimeOut` | 不开启 | 订单是全天高频接口，核心线程常驻更划算 |

> [!warning] 配置的"为什么"比"数字"重要
> 面试时不要背数字，要讲清楚**每个数字背后的约束**：
> - `core` 由"公式初值 ∩ 下游瓶颈"决定；
> - `max` 由"能承受的突发"决定，不能打爆下游；
> - `queue` 由"能容忍的排队时长"反推（`容量 / QPS ≈ 排队秒数`）；
> - `handler` 由"任务能不能丢"决定。
> 这四条讲清楚，比说"我们配了 8/16"有说服力得多。

## 十、线程池监控与故障排查

### 10.1 需要观测什么

| 指标 | API | 含义 | 异常信号 |
| --- | --- | --- | --- |
| 当前线程数 | `getPoolSize()` | 池中线程总数（含空闲） | 长期等于 max → 可能该扩了 |
| 活跃线程数 | `getActiveCount()` | **近似值**，正在执行任务的线程数（遍历 workers 估算，需要 `mainLock`，有开销且有误差） | 长期接近 max → 饱和 |
| 队列长度 | `getQueue().size()` | 排队任务数 | **持续增长 = 生产 > 消费**，最关键的告警指标 |
| 队列剩余容量 | `getQueue().remainingCapacity()` | 还能排多少 | 接近 0 → 即将触发扩容/拒绝 |
| 已完成任务数 | `getCompletedTaskCount()` | 累计完成 | 增长停滞但队列在涨 → 卡住了 |
| 总任务数 | `getTaskCount()` | 累计提交（近似） | `getTaskCount - getCompletedTaskCount` ≈ 未完成 |
| 历史最大线程数 | `getLargestPoolSize()` | 峰值 | 判断 max 是否设小了 |
| **拒绝数** | 无内置 API！需自定义 handler 计数 | 被拒绝的任务数 | **> 0 就必须告警** |
| 任务执行耗时 | 需 `beforeExecute`/`afterExecute` 埋点 | 单个任务的排队 + 执行时间 | P99 恶化 |

> [!note] `getActiveCount()` 为什么是近似值
> 源码里是遍历 `workers` 集合并调用 `w.isLocked()` 统计，需要持有 `mainLock`。高并发下频繁调用会与 `addWorker`/`processWorkerExit` 争锁；同时统计过程中线程状态在变，所以是近似值。**做监控时用它足够，但不要拿它做精确的业务判断，也不要高频调用。**

### 10.2 扩展 `ThreadPoolExecutor` 做监控

```java
public class MonitoredThreadPoolExecutor extends ThreadPoolExecutor {

    private final String poolName;
    private final LongAdder submitted  = new LongAdder();
    private final LongAdder completed  = new LongAdder();
    private final LongAdder rejected   = new LongAdder();
    private final LongAdder totalCostNanos = new LongAdder();
    private final ThreadLocal<Long> startTime = new ThreadLocal<>();

    public MonitoredThreadPoolExecutor(String poolName, int core, int max, long keepAlive,
                                       TimeUnit unit, BlockingQueue<Runnable> queue,
                                       RejectedExecutionHandler handler) {
        super(core, max, keepAlive, unit, queue,
              new NamedThreadFactory(poolName + "-"), handler);
        this.poolName = poolName;
    }

    @Override
    public void execute(Runnable command) {
        submitted.increment();
        super.execute(command);
    }

    @Override
    protected void beforeExecute(Thread t, Runnable r) {
        super.beforeExecute(t, r);                 // ⚠️ 一定先调父类（虽然父类实现是空的，
                                                   //    但保持习惯，避免未来版本有逻辑）
        startTime.set(System.nanoTime());
    }

    @Override
    protected void afterExecute(Runnable r, Throwable t) {
        try {
            Long start = startTime.get();
            if (start != null) {
                // 注意：这里统计的是"执行耗时"，不含入队排队时间
                Metrics.timer("thread_pool_task_duration", "pool", poolName)
                       .record(System.nanoTime() - start, TimeUnit.NANOSECONDS);
            }
            // ⚠️ submit() 提交时异常被包在 FutureTask 里，第二个参数 t 恒为 null
            if (r instanceof Future<?> && ((Future<?>) r).isDone()) {
                try {
                    ((Future<?>) r).get();         // 主动 get 才能把异常暴露出来
                } catch (CancellationException ignore) {
                } catch (ExecutionException e) {
                    log.error("线程池[{}]任务执行异常", poolName, e.getCause());
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
            if (t != null) {
                log.error("线程池[{}]任务异常退出", poolName, t);
            }
            completed.increment();
        } finally {
            startTime.remove();                    // ⚠️ ThreadLocal 必须清理
            super.afterExecute(r, t);
        }
    }

    @Override
    protected void terminated() {
        log.warn("线程池[{}]已终止。submitted={}, completed={}, rejected={}",
                 poolName, submitted.sum(), completed.sum(), rejected.sum());
        super.terminated();
    }

    /** 供监控端点调用：把内部状态导成指标 */
    public void exportMetrics() {
        Metrics.gauge("thread_pool_size",         poolName, getPoolSize());
        Metrics.gauge("thread_pool_active",       poolName, getActiveCount());
        Metrics.gauge("thread_pool_queue_size",   poolName, getQueue().size());
        Metrics.gauge("thread_pool_queue_remain", poolName, getQueue().remainingCapacity());
        Metrics.gauge("thread_pool_completed",    poolName, getCompletedTaskCount());
        Metrics.gauge("thread_pool_largest",      poolName, getLargestPoolSize());
        Metrics.gauge("thread_pool_rejected",     poolName, rejected.sum());
    }
}
```

> [!warning] `afterExecute` 里拿不到 `submit()` 提交任务的异常
> 这是一个经典陷阱：`execute(Runnable)` 提交时，任务抛出的异常会作为 `afterExecute(r, t)` 的第二个参数传进来；但 `submit(Callable/Runnable)` 提交时，任务被包进 `FutureTask`，`FutureTask.run()` 内部把异常捕获并 set 到 Future 里，**不会向外抛**，所以 `t` 永远是 `null`。
> 这就是"用 `submit` 提交、不 `get()`，任务异常完全静默"的原因。**要么统一用 `execute`，要么在 `afterExecute` 里主动 `((Future) r).get()`**（如上面的代码）。

### 10.4 动态调参

`ThreadPoolExecutor` 提供了两个运行时 setter：

```java
public void setCorePoolSize(int corePoolSize) {
    if (corePoolSize < 0) throw new IllegalArgumentException();
    int delta = corePoolSize - this.corePoolSize;
    this.corePoolSize = corePoolSize;
    if (workerCountOf(ctl.get()) > corePoolSize)
        interruptIdleWorkers();               // ① 线程数超了 → 中断空闲线程让它们自行退出
    else if (delta > 0) {
        // ② 需要扩容：只补建到"队列中实际任务数"那么多，不无脑建满
        int k = Math.min(delta, workQueue.size());
        while (k-- > 0 && addWorker(null, true)) {
            if (workQueue.isEmpty()) break;
        }
    }
}

public void setMaximumPoolSize(int maximumPoolSize) {
    if (maximumPoolSize <= 0 || maximumPoolSize < corePoolSize)
        throw new IllegalArgumentException();
    this.maximumPoolSize = maximumPoolSize;
    if (workerCountOf(ctl.get()) > maximumPoolSize)
        interruptIdleWorkers();               // 超了就中断空闲线程（正在跑任务的不受影响）
}
```

**三个必须注意的语义细节**：

| 细节 | 说明 |
| --- | --- |
| **调小 `corePoolSize` 只中断"空闲"线程** | 正在执行任务的线程会继续跑完，**不会立即回收**；之后它们执行完回到 `getTask` 时，因为 `wc > corePoolSize` 走 `poll(keepAliveTime)` 超时退出 |
| **调小 `maximumPoolSize` 同理** | "改小 max 不会立即回收线程"就是这个原因 |
| **调大 `corePoolSize` 是"按需补建"** | 只补建到队列里现有任务数量，不会一次性把 core 个线程都建出来（避免空转浪费） |

> [!tip] 动态线程池（美团思路）的要点
> 核心就是"**把上面两个 setter + 队列容量变成配置中心的动态配置**"，并配套：
> 1. **动态队列容量**：JDK 原生不支持改队列容量 → 需要自己继承 `LinkedBlockingQueue` 或 `ArrayBlockingQueue`，把 `capacity` 变成可变字段并重写 `offer`/`put`/`remainingCapacity`；
> 2. **配置变更监听**：Nacos/Apollo 监听 → 校验（`core <= max`、`queueCapacity > 0`）→ 调 setter → **记录变更审计日志**（谁在什么时候把 core 从 8 改成 200）；
> 3. **治理闭环**：队列长度/活跃度/拒绝数上报 → 告警 → 人工或自动决策；
> 4. **风险控制**：变更要有限幅（一次最多翻倍）、要有回滚、要避开大促。
>
> **风险提示**：动态调参能把 core 瞬间调大，但如果下游（DB/第三方）没跟着扩，就是把故障从"线程池拒绝"变成"下游被打爆"。所以动态调参必须和**下游容量、限流**一起考虑。

## 十一、优雅关闭

### 11.1 标准模板

```java
public class GracefulShutdown {

    /**
     * 标准优雅关闭：
     * 1) shutdown() 停止接收新任务，但让已入队的任务跑完
     * 2) awaitTermination 等待一个上限
     * 3) 超时则 shutdownNow() 兜底，并把未执行的任务取出来处理
     */
    public static List<Runnable> shutdownGracefully(ThreadPoolExecutor pool,
                                                   long timeout, TimeUnit unit) {
        if (pool == null || pool.isShutdown()) return Collections.emptyList();

        pool.shutdown();                                   // ① 不再接收新任务
        try {
            if (pool.awaitTermination(timeout, unit)) {
                log.info("线程池优雅关闭完成");
                return Collections.emptyList();
            }
            // ② 超时：强制中断
            List<Runnable> dropped = pool.shutdownNow();
            log.warn("线程池超时未关闭，强制中断，丢弃/待补偿任务数={}", dropped.size());

            // ③ 再给一次机会等它真的停（中断不是立刻生效）
            if (!pool.awaitTermination(timeout, unit)) {
                log.error("线程池仍未终止，可能存在不响应中断的任务");
            }
            return dropped;                                // ⚠️ 交给上层落库/补偿
        } catch (InterruptedException e) {
            // ④ 自己在等待时被中断 → 立刻强制关闭，并恢复中断标志
            List<Runnable> dropped = pool.shutdownNow();
            Thread.currentThread().interrupt();
            return dropped;
        }
    }
}
```

**关闭的三个阶段与注意点**：

| 阶段 | 动作 | 注意 |
| --- | --- | --- |
| 停止接收 | `shutdown()` | 后续 `execute` 会走拒绝策略（注意：关闭中也会调用 handler） |
| 等待完成 | `awaitTermination(timeout)` | **必须设超时**，不能无限等 |
| 强制兜底 | `shutdownNow()` + 处理返回值 | 返回值不能丢；还要再 `awaitTermination` 一次 |

### 11.2 关闭时不要丢失队列中的任务

```java
@Component
public class OrderExecutorLifecycle implements DisposableBean {

    private final ThreadPoolExecutor orderPool;

    @Override
    public void destroy() {
        List<Runnable> abandoned = GracefulShutdown.shutdownGracefully(
                orderPool, 30, TimeUnit.SECONDS);

        // ✅ 未执行的任务必须补偿，不能只打日志
        for (Runnable task : abandoned) {
            if (task instanceof OrderTask) {
                OrderTask ot = (OrderTask) task;
                try {
                    // 落库为"待重试"，由另一个系统的补偿任务重新投递
                    retryRepository.savePending(ot.getOrderId(), ot.getPayload());
                } catch (Exception e) {
                    log.error("任务补偿落库失败，orderId={}", ot.getOrderId(), e);
                    // 落库都失败了 → 至少要落到本地文件/日志，保证可人工找回
                    localSpillWriter.append(ot);
                }
            }
        }
    }
}
```

> [!danger] `shutdownNow()` 的返回值是任务丢失的最后一道防线
> 直接 `pool.shutdownNow();` 而忽略返回值 = **队列里的任务全部静默消失**。这在发布/重启/扩缩容时**每次都会发生**，是最常见也最容易被忽视的数据丢失来源。
> 检查清单：
> - [ ] 每个线程池都有对应的 `destroy()`/`@PreDestroy` 关闭逻辑
> - [ ] `shutdownNow()` 的返回值有处理（落库、写 MQ、写本地文件）
> - [ ] 关闭超时时间 < 容器给的优雅停机时间（否则容器会 SIGKILL）
> - [ ] 业务任务里检查中断标志，能及时退出

### 11.3 Spring Boot 关闭时的要点

| 事项 | 做法 |
| --- | --- |
| Web 容器优雅停机 | Spring Boot 2.3+ 支持 `server.shutdown=graceful`，配合 `spring.lifecycle.timeout-per-shutdown-phase=30s`：先停止接收新请求，等处理中的请求结束，再销毁 Bean |
| Bean 销毁顺序 | 自定义线程池的 `@PreDestroy` 会在容器关闭阶段执行，**但要确认它在"业务流量已停止"之后**，否则会出现"还有请求在提交任务，池已关闭"的拒绝日志（这属于正常现象，但要做好监控） |
| Executor 生命周期 | Spring 自带的 `ThreadPoolTaskExecutor` 本身实现了 `DisposableBean`，但**默认 `waitForTasksToCompleteOnShutdown=false`**，需要显式打开：`setWaitForTasksToCompleteOnShutdown(true)` + `setAwaitTerminationSeconds(30)`，否则关闭时会丢弃排队任务 |
| 异步注解 | `@Async` 用的池要显式配置（`@EnableAsync` + 自定义 `Executor` Bean），否则默认是 `SimpleAsyncTaskExecutor`（**每次新建线程，不池化**）或容器默认的 `applicationTaskExecutor` |

```yaml
# application.yml：Spring Boot 优雅停机
server:
  shutdown: graceful          # 先停止接收新请求，等处理中请求结束
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

```java
// ThreadPoolTaskExecutor：必须显式打开"等待任务完成"，否则关闭时丢任务

public ThreadPoolTaskExecutor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(16);
    executor.setMaxPoolSize(32);
    executor.setQueueCapacity(500);
    executor.setThreadNamePrefix("async-");
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(true);   // ✅ 关键
    executor.setAwaitTerminationSeconds(30);              // ✅ 不能无限等
    executor.initialize();
    return executor;
}
```

## 十二、`ForkJoinPool`：分治与工作窃取

### 12.1 核心思想

`ForkJoinPool` 是 `ExecutorService` 的另一个实现，专为**可递归分解、无阻塞、CPU 密集**的任务设计。

```java
// RecursiveTask<V>：有返回值
public class SumTask extends RecursiveTask<Long> {
    private static final int THRESHOLD = 10_000;      // 阈值：小到一定程度就直接算
    private final long[] array;
    private final int lo, hi;

    public SumTask(long[] array, int lo, int hi) {
        this.array = array; this.lo = lo; this.hi = hi;
    }

    @Override
    protected Long compute() {
        if (hi - lo <= THRESHOLD) {                    // 终止条件：直接算
            long sum = 0;
            for (int i = lo; i < hi; i++) sum += array[i];
            return sum;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left  = new SumTask(array, lo, mid);
        SumTask right = new SumTask(array, mid, hi);

        left.fork();                                   // ① 把左半部分"推"到队列（异步）
        long rightResult = right.compute();            // ② 右半部分在当前线程同步算（避免多一次调度）
        long leftResult  = left.join();                // ③ 等左半部分结果（会帮助窃取执行）
        return leftResult + rightResult;
    }

    public static void main(String[] args) {
        long[] array = new long[10_000_000];
        Arrays.fill(array, 1L);
        ForkJoinPool pool = new ForkJoinPool();        // 默认并行度 = 核数
        long sum = pool.invoke(new SumTask(array, 0, array.length));
        System.out.println(sum);
    }
}
```

`fork()` / `join()` 语义：

| 方法 | 语义 |
| --- | --- |
| `fork()` | 把任务推入**当前工作线程自己的双端队列**（不阻塞，异步） |
| `join()` | 等待结果；**等待期间会去帮忙执行其他任务**（工作窃取的关键） |
| `invoke()` | 提交并等待结果（同步） |
| `compute()` | 子类实现；`RecursiveTask` 返回值，`RecursiveAction` 返回 void |

### 12.2 工作窃取（work-stealing）

```
        Worker-1 的 deque                Worker-2 的 deque
   ┌──────────────────────────┐     ┌──────────────────────────┐
   │ 头 → [T5][T4][T3][T2][T1] │     │ 头 → [t2][t1]            │
   │        ↑ 自己 fork/push   │     │                          │
   │        ↓ 自己 pop（LIFO）  │     │                          │
   │                          │◀────│  尾部窃取（FIFO，从别的队列尾部拿）
   └──────────────────────────┘     └──────────────────────────┘
```

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| **每个 worker 一个双端队列** | `ForkJoinPool` 内部为每个工作线程维护一个 `WorkQueue` | 避免全局队列的竞争 |
| **自己从头部取（LIFO）** | 最后 fork 的任务最先执行 | 局部性好（数据可能还在缓存里），且能快速推进递归的"近端"子树 |
| **窃取者从尾部取（FIFO）** | 空闲线程从别人队列的**尾部**拿 | ① 尾部通常是最大的（最早 fork 的）任务，粒度大，偷一次够干很久；② 减少与队列主人的竞争（一个头一个尾） |
| **窃取失败就扫别人** | 轮询所有队列 | 负载均衡 |
| **`join()` 期间帮忙干活** | 等待子任务时，线程不闲着，去执行别的任务 | 避免线程空等，是"分治 + 并行"效率的关键 |

**`ForkJoinPool` vs `ThreadPoolExecutor`**：

| 维度 | `ThreadPoolExecutor` | `ForkJoinPool` |
| --- | --- | --- |
| 队列结构 | 所有线程共享一个队列 | 每个线程一个双端队列 + 窃取 |
| 任务关系 | 任务相互独立 | 任务可以**派生子任务**并等待其完成 |
| 适合 | 独立、可能阻塞的异构任务（IO、RPC） | **可递归分解、无阻塞、CPU 密集** |
| 任务等待 | 等待即阻塞，线程闲着（可能死锁） | 等待时"帮忙干活"，不会闲着 |
| 不适合 | 大量递归分治 | **有 IO 阻塞的任务**（会占满工作线程，且阻塞会拖慢窃取） |

> [!warning] 不要用 `ForkJoinPool` 跑 IO 任务
> `ForkJoinPool` 的并行度默认等于核数，它的设计前提是"任务不阻塞"。一旦提交阻塞任务（DB、RPC、`Thread.sleep`），工作线程被占住，**窃取机制失效**，整体退化成比小线程池还差的形态。
> IO 任务请用 `ThreadPoolExecutor`（大 core + 有界队列）或虚拟线程。

### 12.3 `commonPool` 被占满的坑（重点）

```java
// 并行流的默认执行者是谁？
list.parallelStream().map(...).collect(...);      // ← 底层用 ForkJoinPool.commonPool()
CompletableFuture.supplyAsync(() -> ...);         // ← 没有传 Executor 时，也用 commonPool
```

- `commonPool` 的**并行度默认 = `Runtime.getRuntime().availableProcessors() - 1`**（至少为 1）。可通过系统属性 `java.util.concurrent.ForkJoinPool.common.parallelism` 调整。
- `commonPool` 是**整个 JVM 全局共享**的。

**事故形态**：

```java
// ❌ 事故代码：在 commonPool 里提交阻塞任务
CompletableFuture<Void> f = CompletableFuture.runAsync(() -> {
    // 这个任务会阻塞 10 秒（DB 查询 / 远程调用 / sleep）
    remoteService.call();
});
```

现象：某个业务用了并行流，但吞吐诡异下降、甚至完全卡住；`jstack` 里看到 `ForkJoinPool.commonPool-worker-N` 全部停在 `socketRead0` / `Unsafe.park`；而并行流的任务在等这些 worker 释放。

**根因**：`commonPool` 的工作线程被阻塞任务占满 → 并行流的任务**没有线程可以执行** → 排队等待 → 表现为"并行流变串行甚至卡死"。

**正确做法**：

```java
// ✅ 1) 阻塞任务用专用池，绝不占用 commonPool
private static final ExecutorService IO_POOL = new ThreadPoolExecutor(
        32, 64, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(200),
        new NamedThreadFactory("io-"), new ThreadPoolExecutor.CallerRunsPolicy());

CompletableFuture.supplyAsync(() -> remoteService.call(), IO_POOL);

// ✅ 2) 并行流要显式指定池（用 try/finally 保证恢复，避免污染别的调用方）
ForkJoinPool custom = new ForkJoinPool(16);
try {
    List<R> result = custom.submit(() ->
            list.parallelStream().map(this::heavyCompute).collect(Collectors.toList())
    ).get();
} finally {
    custom.shutdown();
}

// ✅ 3) 或者干脆用顺序流 + 显式分批提交到自己的池（可控性最好）
```

> [!danger] 三点必须记住
> 1. **`commonPool` 是全局共享的**：你污染它，影响的是整个 JVM 里所有用并行流和 `CompletableFuture`（未指定 Executor 的）的代码——包括框架和第三方库。
> 2. **不要在业务代码里直接提交阻塞任务到 `commonPool`**。
> 3. **`parallelStream` 不保证顺序、也不保证线程安全**：`forEach` 用 `Collectors.toList()` 是安全的，但 `forEach(sb::append)` 之类的就一定错。另外它默认的**公共池在容器里按宿主核数算**（老版本 JDK 读 `/proc/cpuinfo` 而不是 cgroup 限制），容易开出一堆线程——这在容器环境下是经典坑。

## 十三、`ScheduledThreadPoolExecutor` 与 `Timer`

### 13.1 与 `Timer` 的对比（`Timer` 为什么被淘汰）

| 维度 | `Timer` / `TimerTask` | `ScheduledThreadPoolExecutor` |
| --- | --- | --- |
| 线程模型 | **单线程** | 线程池（core 个线程） |
| 任务并行性 | **所有任务串行执行** | 多任务并行 |
| 任务抛异常 | **未捕获异常会终止整个 Timer 线程**，之后所有任务永久不再执行（且毫无提示！） | 只影响该次任务，池继续工作（并由 `processWorkerExit` 补线程） |
| 时间基准 | `System.currentTimeMillis()`（**墙上时钟**）→ 改系统时间会影响调度 | `System.nanoTime()`（**单调时钟**）→ 不受系统时间调整影响 |
| 精度/实现 | `TaskQueue`（`Object.wait` 轮询） | `DelayedWorkQueue`（堆）+ `leader-follower` 模式 |
| 调度能力 | 固定延迟、固定频率 | 固定延迟、固定频率、单次延迟 |
| 生产可用度 | ❌ 不推荐 | ✅ 推荐 |

```java
// Timer 的致命缺陷演示
Timer timer = new Timer();
timer.schedule(new TimerTask() {
    @Override public void run() { throw new RuntimeException("boom"); }
}, 0, 1000);
timer.schedule(new TimerTask() {         // ❌ 这个任务永远不会再执行
    @Override public void run() { System.out.println("never printed"); }
}, 0, 1000);
// 原因：TimerThread.run() 的 mainLoop 里，异常会向上抛，
//       而 TimerThread 是 Thread 的子类，没有 try/catch 保护 → 线程死掉 → 整个 Timer 静默失效
```

> [!danger] `Timer` 的"静默死亡"
> 一个任务抛异常 → `TimerThread` 终止 → **所有后续已排期的任务全部不再执行，且没有任何日志/异常提示**。
> 线上表现：某个定时任务从某天起就再也没跑过，查日志也查不到错误。这是"用 `Timer` 写定时任务"最典型的翻车方式，也是必须换成 `ScheduledThreadPoolExecutor` 的首要原因。

### 13.2 `scheduleAtFixedRate` vs `scheduleWithFixedDelay`

| 方法 | 基准点 | 语义 | 任务超时（执行时间 > 周期）时的行为 |
| --- | --- | --- | --- |
| `scheduleAtFixedRate(task, initialDelay, period, unit)` | 上一次任务的**开始时间** | 按**固定频率**执行（每 period 至少尝试触发一次） | **下一次会立即开始**（追赶）；但**不会并发执行同一个任务**，也不会堆积多个待执行实例 |
| `scheduleWithFixedDelay(task, initialDelay, delay, unit)` | 上一次任务的**结束时间** | 按**固定间隔**执行（两次执行之间至少间隔 delay） | 下一次 = 本次结束时间 + delay，天然不会有追赶问题 |

```
周期 1s，任务耗时 200ms：
 scheduleAtFixedRate:   |--200ms--|.........|--200ms--|.........
                        0s        1s        2s        3s         ← 每隔 1s 开始
 scheduleWithFixedDelay: |--200ms--|...800ms...|--200ms--|...
                         0s       1.0s        2.0s                  ← 结束后再等 1s

任务耗时 1.5s > 周期 1s：
 scheduleAtFixedRate:    |====== 1.5s ======||====== 1.5s ======|
                         0s                1.5s              3.0s   ← 结束即开始（追赶，实际周期变成 1.5s）
 scheduleWithFixedDelay: |====== 1.5s ======|..delay 1s..|======...
                         0s               1.5s         2.5s        ← 间隔稳定
```

> [!important] `scheduleAtFixedRate` 不会并发执行同一任务
> 这一点常被误解：`ScheduledThreadPoolExecutor` 保证**同一个周期性任务在队列中只有一个实例**。如果一次执行还没结束，下一次的触发会被"跳过并顺延"（而不是并发跑两份或堆积多份）。
> 所以"固定频率"的准确性会被任务耗时侵蚀：**任务耗时 > period 时，实际频率退化到 `1 / 任务耗时`**。
> 需要严格按周期触发的业务（如每分钟一次的结算）要保证任务耗时远小于周期，否则应该：① 增大 `corePoolSize` 让不同任务并行；② 用 `scheduleWithFixedDelay` 并接受漂移；③ 加超时与跳过逻辑。

### 13.3 `ScheduledThreadPoolExecutor` 的三个使用要点

```java
ScheduledThreadPoolExecutor scheduler = new ScheduledThreadPoolExecutor(
        4,                                       // corePoolSize：决定不同定时任务的并行度
        new NamedThreadFactory("scheduler-"),
        new ThreadPoolExecutor.AbortPolicy());

scheduler.setRemoveOnCancelPolicy(true);         // ⚠️ 关键：取消任务时从队列中移除

// ① 单次延迟任务
scheduler.schedule(() -> sync(), 5, TimeUnit.SECONDS);

// ② 固定频率（以上次开始时间为基准）
scheduler.scheduleAtFixedRate(() -> report(), 0, 60, TimeUnit.SECONDS);

// ③ 固定间隔（以上次结束时间为基准）
scheduler.scheduleWithFixedDelay(() -> poll(), 0, 10, TimeUnit.SECONDS);
```

| 要点 | 说明 |
| --- | --- |
| `maximumPoolSize` **无意义** | 内部用的是无界的 `DelayedWorkQueue`，队列永不满 → 线程数永远不会超过 `corePoolSize`。**并发度完全由 `corePoolSize` 决定**，不要指望 max |
| **`setRemoveOnCancelPolicy(true)`** | 默认 `false`：`cancel()` 掉的任务**仍留在延迟队列里**，直到它的延迟时间到期才被清理。如果大量创建+取消短任务（如每个请求建一个延迟任务做超时控制），队列会持续膨胀造成内存问题。设为 `true` 后立即移除 |
| **任务内部必须自己 try/catch** | 任务抛异常时，该周期任务会被**取消**（不再重复执行），线程池本身继续工作。所以每个周期任务都应该包一层 `try/catch`，避免一次偶发异常导致定时任务永久停摆 |
| **不要用 `shutdownNow` 期望停掉周期任务** | `shutdownNow` 会尝试中断，但周期任务如果不在阻塞点上就不响应中断；正确做法是先 `cancel()` 相关 `ScheduledFuture`，再 `shutdown()` |

```java
// ✅ 周期任务的标准写法：包一层异常保护 + 加超时
scheduler.scheduleAtFixedRate(() -> {
    try {
        doReport();
    } catch (Throwable t) {                 // ⚠️ 必须 catch Throwable：一次异常会让周期任务被取消
        log.error("报表任务执行异常，本次跳过", t);
    }
}, 0, 60, TimeUnit.SECONDS);
```

> [!note] 分布式调度
> `ScheduledThreadPoolExecutor` 是**单机**调度：多实例部署时每个实例都会跑一遍（重复执行），且进程重启会丢失调度状态。
> 需要"集群内只跑一次""失败重试""分片""可视化"时，应该用 **Quartz（配合数据库锁）/ XXL-JOB / ElasticJob / PowerJob** 这类分布式调度框架，不要用 `ScheduledThreadPoolExecutor` 硬扛。

## 十四、虚拟线程（Java 21+）

### 14.1 定位（一句话）

**虚拟线程是 Java 21 起正式支持的特性**，面向**高并发 IO 密集型**场景，用来替代"用超大线程池硬扛阻塞"的思路：让每个请求占一个虚拟线程，阻塞时自动卸载载体线程，从而用极少的平台线程支撑海量并发连接。细节与版本演进见 `[[9-Java版本特性]]`。

### 14.2 与平台线程的关键差异

| 维度 | 平台线程 | 虚拟线程 |
| --- | --- | --- |
| 调度者 | 操作系统 | **JVM**（M:N 调度到载体线程） |
| 栈 | 固定大小（`-Xss`，约 1MB 保留） | **存储在堆上**，按需增长（KB 级起步） |
| 创建成本 | 高（内核对象 + 栈） | **极低** |
| 数量级 | 数千（再多就 OOM / 调度崩） | **百万级**理论上可行 |
| 阻塞行为 | 占住内核线程 | 阻塞在 IO 上时**卸载（unmount）**，释放载体线程 |
| 线程身份 | 昂贵资源，需池化 | 廉价对象，**不需要池化** |
| 适用 | CPU 密集、需要固定并行度 | **IO 密集、高并发、任务彼此独立** |

```java
// Java 21+ 的两种用法
// ① 每个任务一个虚拟线程（推荐）
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i ->
            executor.submit(() -> {
                var result = remoteCall(i);       // 阻塞时自动卸载，不占载体线程
                return result;
            }));
}

// ② 精细控制（名称、是否守护等）
ThreadFactory factory = Thread.ofVirtual().name("vt-", 0).factory();
Thread vt = factory.newThread(() -> System.out.println("virtual"));
vt.start();

// ③ 直接用平台线程池的写法 ❌ 反模式
Executors.newFixedThreadPool(200, Thread.ofVirtual().factory());   // 池化虚拟线程 = 画蛇添足
```

### 14.3 "不要池化虚拟线程"的完整理由

| 池化的目的是什么 | 虚拟线程是否满足 |
| --- | --- |
| 复用**昂贵的**创建成本 | ❌ 不满足：虚拟线程创建成本极低，池化的收益接近于零 |
| 控制**稀缺的**并发资源 | 部分：真正稀缺的是**下游资源**（DB 连接、文件句柄、第三方 QPS），而不是线程 |
| 减少 GC 压力 | ❌ 不满足：池化反而让虚拟线程长期存活，增大内存占用（每个虚拟线程有自己的栈对象） |

**正确做法**：

```java
// ✅ 用虚拟线程 + Semaphore 控制对下游的并发（限流的是资源，不是线程）
private static final Semaphore DB_PERMITS = new Semaphore(50);   // 对应连接池上限

try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> {
        DB_PERMITS.acquire();
        try {
            return orderMapper.selectById(id);
        } finally {
            DB_PERMITS.release();
        }
    });
}
```

### 14.4 三个容易踩的坑

| 坑 | 说明 | 应对 |
| --- | --- | --- |
| **Pinning（载体线程被固定）** | 虚拟线程在 `synchronized` 块内阻塞、或执行 native/foreign 调用时，**无法卸载载体线程**，载体被"钉住"。大量 pinning 会让调度器失去并行能力 | 在虚拟线程代码里把 `synchronized` 换成 `ReentrantLock`；较新版本的 JDK 已经改进了 `synchronized` 场景下的 pinning 问题，但仍应避免在 `synchronized` 里做阻塞 IO |
| **`ThreadLocal` 被放大** | 每个虚拟线程都有自己的 `ThreadLocalMap`。百万虚拟线程 × 每个存几个大对象 = 内存爆炸 | 虚拟线程场景避免用 `ThreadLocal` 存大对象；JDK 正在推进 `ScopedValue`（预览特性）作为更合适的替代 |
| **CPU 密集任务用虚拟线程无意义** | 虚拟线程只解决"阻塞时让出载体"；纯计算任务不阻塞，拿不到任何好处，还会因为调度开销略慢 | CPU 密集仍用"平台线程池（核数+1）"或 `ForkJoinPool` |

> [!warning] 虚拟线程不是"免费的性能提升"
> - 它不会让你的代码变快，它解决的是"**阻塞式代码写起来简单，但又不想用巨型线程池**"的矛盾；
> - 用了虚拟线程后，**限流、超时、连接池依然是必需的**——瓶颈会从"线程不够"转移到"下游扛不住"；
> - 虚拟线程的调度器本身基于 `ForkJoinPool`（载体线程池），可以通过 `jdk.virtualThreadScheduler.parallelism` / `jdk.virtualThreadScheduler.maxPoolSize` 等系统属性调整，**默认不要乱改**；
> - 老代码（用 `ThreadLocal` 传上下文、依赖线程绑定的框架如某些 JDBC 驱动/`synchronized` 密集的库）迁移到虚拟线程前要做充分压测。

## 十五、必答与速查

> [!question] 必答 1：线程池参数与执行流程
> **七大参数**：`corePoolSize`（核心线程数，常驻）、`maximumPoolSize`（上限，**只在队列满后才生效**）、`keepAliveTime` + `unit`（非核心线程空闲回收时间，配合 `allowCoreThreadTimeOut` 也能管核心线程）、`workQueue`（**必须用有界队列**）、`threadFactory`（命名 + 异常兜底）、`handler`（拒绝策略）。
> **执行流程（四步）**：
> ① 线程数 < `core` → 建核心线程执行；
> ② 否则**先入队**（`workQueue.offer`）；
> ③ 队列满且线程数 < `max` → 建非核心线程；
> ④ 再满 → 执行拒绝策略。
> **必须强调"先入队再扩容"**：这个顺序意味着 `maximumPoolSize` 只有在队列满时才生效，所以**无界队列会让 `max` 完全失效**。
> 补一句 `ctl` 设计：一个 32 位 `AtomicInteger`，高 3 位存状态（RUNNING/SHUTDOWN/STOP/TIDYING/TERMINATED），低 29 位存线程数，一次 CAS 同时完成状态校验与计数更新，避免加锁。

> [!question] 必答 2：为什么不用 `Executors`
> 因为它把危险的默认值写死了：
> - `newFixedThreadPool` / `newSingleThreadExecutor`：`LinkedBlockingQueue` **无界** → 任务堆积 → **堆 OOM**，且 `max` 失效（等于 core）；`newSingleThreadExecutor` 还是单点。
> - `newCachedThreadPool`：`maximumPoolSize = Integer.MAX_VALUE` + `SynchronousQueue` → **线程无上限增长** → `OutOfMemoryError: unable to create new native thread`，上下文切换爆炸。
> - `newScheduledThreadPool`：`DelayedWorkQueue` 也是无界的。
> **生产必须手动 `new ThreadPoolExecutor`**，明确给出：**有界队列 + 合理的 core/max + 有语义的线程名 + 可观测可降级的拒绝策略**。
> 顺带提一句 `newSingleThreadExecutor` 返回的是 `FinalizableDelegatedExecutorService` 包装类，不能强转成 `ThreadPoolExecutor` 调参。

> [!question] 必答 3：线程数怎么定
> - **CPU 密集**：`N_cpu + 1`（+1 用于在线程偶发暂停时仍占满 CPU）。
> - **IO 密集**：`N_cpu × U_cpu × (1 + W/C)`，`W` 是等待时间（DB/RPC/IO），`C` 是计算时间，`U_cpu` 是目标利用率。
> - `Runtime.getRuntime().availableProcessors()` 拿核数。
> - **但公式只是初值**，三个局限必须说：① 真实瓶颈常在连接池/下游而非 CPU，线程数不能超过瓶颈容量；② W/C 用平均值会掩盖长尾；③ 系统是动态的。
> - **实操**：公式粗算 → 压测看 QPS/RT/CPU/队列长度/拒绝数 → 找 QPS 不再上升而 RT 陡增的拐点 → 按拐点 70%~80% 定 `core`；`max` 由"下游能承受的最大并发"定（不是 CPU）；队列容量由"能容忍的排队时长"反推（`容量 / QPS ≈ 排队秒数`）。
> - 最好给一个带理由的实例（见 §9.4 的订单服务配置）。

> [!question] 必答 4：线程池里的任务抛异常会怎样？
> - 用 `execute()` 提交：异常会传到 `runWorker` → `afterExecute(task, t)` 拿到异常 → 任务抛异常导致 worker 线程终止（`completedAbruptly = true`）→ `processWorkerExit` 会补建一个新线程（池还在 RUNNING 时），**所以池不会永久少线程，但会有抖动**。
> - 用 `submit()` 提交：任务被包成 `FutureTask`，`FutureTask.run()` 内部捕获异常塞进 Future，**不会向外抛** → `afterExecute` 的 `t` 参数恒为 `null` → **不调用 `get()` 就永远发现不了异常**。
> - 对策：① 任务体自己 `try/catch` 全包；② `ThreadFactory` 里设 `UncaughtExceptionHandler` 兜底（对 `execute` 有效）；③ `afterExecute` 里对 `Future` 主动 `get()`；④ 统一规范用 `execute` 而非 `submit`。

> [!question] 必答 5：`Worker` 为什么继承 AQS？
> 为了用一把**不可重入的独占锁**标识"这个 worker 是否正在执行任务"：
> - `runWorker` 里执行任务前 `w.lock()`、执行完 `w.unlock()`；`interruptIdleWorkers` 用 `w.tryLock()` 判断是否是空闲线程——**只有空闲线程才被中断**，正在跑任务的不受影响，这正是 `shutdown()` 语义的实现基础。
> - **必须不可重入**：可重入会让 `tryLock` 在"已持有"时也返回成功，就无法区分空闲与忙。
> - `Worker` 构造时 `setState(-1)`，配合 `interruptIfStarted()` 的 `getState() >= 0` 判断，保证线程真正进入 `runWorker` 之前不被中断。
> - 注意别和 `ThreadPoolExecutor` 自己的 `mainLock`（保护 `workers` 集合）搞混，两者独立。
