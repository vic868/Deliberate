# AI 开发环境搭建与发布流程

> [!abstract] 目标
> 建立一套可复现的 Python AI 开发环境：用 Conda 管理 Python 和依赖，用 PyCharm 管理项目与解释器，通过依赖锁定、测试、镜像构建和部署配置完成发布。本文以 macOS/Linux 命令为主；Windows 用户将激活命令替换为 `conda activate <环境名>`，路径按系统调整。

## 1. 先明确三个环境概念

| 概念 | 负责什么 | 典型工具/文件 |
| --- | --- | --- |
| Conda 环境 | 为一个项目隔离 Python 版本和 Python 包 | `conda`、`environment.yml` |
| PyCharm 项目解释器 | 告诉 IDE 使用哪个 Python 可执行文件 | Conda 环境中的 `python` |
| 发布运行环境 | 让应用在服务器/容器中按固定配置运行 | Docker、镜像仓库、部署平台 |

Conda 管理环境；PyCharm 选择并使用环境；发布时重新构建干净的运行环境。不要把 PyCharm 自己的设置当作依赖清单，也不要把个人电脑上的整个 Conda 环境目录直接拷到服务器。

## 2. 安装与配置 Conda

### 2.1 选择发行版

- **Miniforge**：轻量、社区维护，默认使用 conda-forge；适合希望用开放社区渠道的个人开发环境。
- **Miniconda**：轻量安装器，默认配置 Anaconda 官方渠道。
- **Anaconda Distribution**：预装较多包，体积大；只有确实需要其预装工具时再选。

在一台机器上尽量只保留一个主要 Conda 安装，避免 `PATH` 中出现多套 `conda` 导致解释器和包来源混乱。按操作系统和 CPU 架构从所选项目的官方安装说明获取安装包。

安装后重新打开终端，确认：

```bash
conda --version
conda info --base
conda config --show channels
```

### 2.2 配置渠道与优先级

渠道是 Conda 查找包的仓库。一个项目尽量使用一致的渠道组合；不要在遇到安装问题时随意叠加多个来源。

如果选择 Miniforge/conda-forge，可查看配置并设置严格优先级：

```bash
conda config --show-sources
conda config --set channel_priority strict
```

如果要明确只用 conda-forge，可通过项目环境文件定义渠道（见下节），也可在用户配置中设置，但先检查已有 `.condarc`，避免覆盖团队或组织已有设置。用 `conda config --remove channels <渠道>` 删除渠道前，先确认该渠道不是其他项目的依赖。

常用配置检查：

```bash
conda config --show
conda config --show-sources
conda env list
```

> [!warning] 镜像源
> 企业网络或地区网络确实需要镜像时，使用组织批准且可信的镜像，并记录渠道来源。不要为了“加速”随手复制来源不明的 `.condarc`；渠道混用可能造成二进制包冲突。

### 2.3 终端初始化

如果新终端找不到 `conda`，运行对应 Shell 的初始化，然后重启终端：

```bash
conda init zsh
```

Bash 用户使用 `conda init bash`。若希望终端启动时不自动进入 `base`：

```bash
conda config --set auto_activate_base false
```

这只影响交互终端默认状态，不会删除 `base` 环境。开发项目时应显式激活项目环境。

## 3. 创建可复现的项目环境

### 3.1 选 Python 版本

先确认依赖和目标部署平台支持的 Python 版本，再为项目选定一个版本。不要默认追最新版本；AI 相关依赖（例如深度学习框架、向量库客户端）常受 Python、操作系统和硬件版本约束。把选定版本写入环境文件，并记录模型/硬件依赖的特殊要求。

### 3.2 创建环境

在项目根目录创建 `environment.yml`，例如：

```yaml
name: ai-assistant
channels:
  - conda-forge
dependencies:
  - python=3.11
  - pip
  - pip:
      - httpx
      - pydantic
      - python-dotenv
```

创建、激活并核实解释器：

```bash
conda env create -f environment.yml
conda activate ai-assistant
which python
python --version
python -m pip --version
```

使用 `python -m pip` 可以确保 pip 安装到当前激活的解释器中。新增 Conda 包时更新 YAML 的 Conda dependencies；新增 pip 包时更新 `pip:` 列表，然后重建或更新环境：

```bash
conda env update -f environment.yml --prune
```

`--prune` 会移除环境中不再声明的包；对共享或重要环境执行前要确认该行为符合预期。

### 3.3 环境文件与锁定文件

- `environment.yml`：跨机器的环境定义，适合团队维护；提交到版本库。
- Conda 显式规格或锁文件：固定平台相关的解析结果，适合要求更高的复现；按团队选用的锁定工具和目标平台生成。
- `pip freeze`：导出当前环境已安装的 pip 包快照，适合排查/短期复现，不应不加审查地当作跨平台的唯一依赖定义。

导出当前 Conda 环境供排查：

```bash
conda env export --from-history > environment.yml
```

`--from-history` 只导出显式安装的 Conda 包，不会完整记录所有 pip 包；手动检查并补齐 `pip:` 部分。提交前在一个全新环境中验证文件可成功创建。对部署项目，还应使用锁定文件或镜像摘要固定实际运行依赖。

## 4. PyCharm 配置

PyCharm 版本和菜单名称可能变化；核心原则是为项目选择正确的 Conda Python，而不是让 IDE 使用系统 Python。

### 4.1 打开项目

1. 用 **Open** 打开含有 `environment.yml` 的项目根目录。
2. 确认 Project 根目录下能看到依赖文件、源码目录和 README。
3. 不要把 Conda 安装目录或环境目录当作项目根目录。

### 4.2 选择 Conda 解释器

在 PyCharm 的项目 Python Interpreter 设置中，添加或选择 Conda 环境：

- 已有环境：选择 Existing environment，定位环境中的 Python 可执行文件。
- 新建环境：可在 IDE 中创建，但建议让 `environment.yml` 仍作为团队共享的环境定义。
- macOS/Linux 常见路径：`<conda安装目录>/envs/ai-assistant/bin/python`。
- Windows 常见路径：`<conda安装目录>\\envs\\ai-assistant\\python.exe`。

终端运行 `conda activate ai-assistant && which python`，将该路径与 PyCharm Interpreter 显示的路径对照。IDE 运行、IDE 内置终端和外部终端应使用同一项目环境。

### 4.3 配置运行与调试

- 创建 Run/Debug Configuration，指定模块或脚本、工作目录和参数。
- 环境变量在本地 Run Configuration 中设置，或通过本地 `.env` 文件加载；不要把真实密钥写进共享配置。
- 为测试配置单独的工作目录和测试命令，确保相对路径不会依赖 IDE 的偶然默认值。
- 在 PyCharm Terminal 中验证 `python --version`、`python -m pip list`，再运行最小程序。

### 4.4 项目文件建议

```text
project/
├── src/                       # 应用代码
├── tests/                     # 自动化测试
├── environment.yml            # 环境定义
├── .env.example               # 非敏感配置名与占位值
├── .gitignore
├── Dockerfile                 # 需要容器发布时
└── README.md
```

`.idea/` 通常包含个人 IDE 状态。团队可按约定提交共享代码风格/运行配置，但不要提交本机绝对路径、凭据或个人工作区设置。

## 5. 项目依赖与配置管理

### 5.1 忽略本地文件

至少检查 `.gitignore` 包含：

```gitignore
.env
.env.*
!.env.example
__pycache__/
.pytest_cache/
.mypy_cache/
.ruff_cache/
.idea/
*.py[cod]
```

如果项目确实需要共享部分 `.idea` 配置，可精确放行团队需要的文件，而不是整体提交本地目录。

### 5.2 密钥与环境配置

`.env.example` 只写变量名和假值：

```dotenv
MODEL_API_KEY=replace-me
MODEL_BASE_URL=https://example.invalid/v1
MODEL_NAME=replace-me
```

本地 `.env` 应被 Git 忽略。生产环境从部署平台的 Secret/环境变量注入密钥；不要把密钥写到源码、镜像层、日志、截图或知识库。若密钥曾提交，删除文件并不够，必须在供应方撤销并轮换密钥。

### 5.3 开发与生产依赖

区分运行依赖与开发依赖（测试、格式化、静态检查）。启动命令、依赖安装方式、配置项和健康检查写进 README。不要把某台电脑上的路径、代理、GPU 驱动和凭据隐含为项目必要条件。

## 6. 本地开发到发布的完整流程

```mermaid
flowchart LR
    A[创建/更新依赖声明] --> B[干净环境安装]
    B --> C[格式检查/静态检查/测试]
    C --> D[本地集成验证]
    D --> E[构建制品或容器镜像]
    E --> F[登记版本与配置要求]
    F --> G[部署测试环境]
    G --> H[健康检查/冒烟验证]
    H --> I[分批发布或切换流量]
    I --> J[观察指标/回滚准备]
```

### 阶段 A：提交前

1. 更新 `environment.yml` 或锁文件，确认依赖来源可信。
2. 从干净环境安装依赖，避免依赖开发机上未声明的包。
3. 运行格式/静态检查和自动化测试；记录命令与结果。
4. 检查配置和密钥，不提交本地 `.env`、测试数据中的敏感内容或模型凭据。
5. 更新 README、接口/配置说明和版本记录。

### 阶段 B：构建制品

1. 从指定 Git commit 构建，记录 commit ID、应用版本、Python 版本、依赖锁定版本。
2. 容器化项目构建 Docker 镜像；非容器项目构建 wheel 或其他经过定义的制品。
3. 使用唯一版本标签；生产发布最好再记录镜像 digest，避免可变标签被覆盖。
4. 在 CI 中执行同一套测试和构建，确保制品来自可审计的源码版本。

### 阶段 C：部署与验证

1. 将制品推到受控镜像/制品仓库。
2. 在目标环境注入密钥和环境配置，确认网络、模型供应方、向量库及存储访问权限。
3. 部署到测试环境，检查进程启动、健康检查、日志、依赖连接和一条最小 AI 请求。
4. 生产采用平台支持的滚动、蓝绿或分批发布策略；具体方式取决于运行平台。
5. 观察错误率、延迟、资源、模型调用失败和成本变化；异常时回滚到上一个已知可用制品。

### 发布版本记录模板

```markdown
## Release <版本>
- Git commit：
- Python/Conda 环境版本：
- 依赖锁定文件版本或摘要：
- Docker 镜像 tag/digest 或制品地址：
- 配置/数据库变更：
- 测试和冒烟结果：
- 发布人/时间/环境：
- 监控观察：
- 回滚版本与操作：
```

## 7. Docker 发布示例

以下为基础模式示例，需按项目入口、依赖和安全要求调整。容器构建不直接复制本地 Conda 环境，而是在镜像中安装声明的依赖。

```dockerfile
FROM python:3.11-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt
COPY src ./src

RUN useradd --create-home --uid 10001 appuser
USER appuser

EXPOSE 8000
CMD ["python", "-m", "src"]
```

构建和本地启动示例：

```bash
docker build -t ai-assistant:0.1.0 .
docker run --rm -p 8000:8000 --env-file .env ai-assistant:0.1.0
```

实际发布时，不要把 `.env` 复制进镜像；`--env-file` 只适合本地演示。生产密钥应由容器编排或发布平台的 Secret 管理机制注入。正式项目还应固定基础镜像版本/摘要、使用锁定依赖、配置健康检查、资源限制、日志策略和非 root 用户。若使用 PyTorch/CUDA 等 GPU 依赖，按目标 GPU、驱动和运行时兼容矩阵另行选择基础镜像，不能直接套用 CPU 示例。

## 8. 常见故障排查

| 现象 | 常见原因 | 排查方法 |
| --- | --- | --- |
| `conda: command not found` | Shell 未初始化或 PATH 未加载 | 运行 `conda init <shell>`，重启终端，查看安装位置 |
| PyCharm 找不到包，终端却能运行 | IDE 选了另一个解释器 | 对照 PyCharm Interpreter 与 `which python`/`where python` |
| pip 安装到了错误环境 | 直接调用了另一个 `pip` | 激活环境后用 `python -m pip install ...` |
| 环境解析冲突 | Python 版本或渠道不兼容，混用仓库 | 检查 `conda config --show-sources`，减少渠道并验证版本约束 |
| 本地正常、CI/服务器失败 | 未声明依赖、平台差异、配置缺失 | 在干净环境重建；检查锁定文件、架构、环境变量和运行命令 |
| 模型请求超时/认证失败 | 网络、代理、密钥或端点配置问题 | 检查脱敏后的配置、DNS/TLS、请求 ID、超时与供应方状态 |
| 容器能启动但无法对外访问 | 应用只绑定 `127.0.0.1` 或端口未映射 | 服务监听 `0.0.0.0`，检查容器端口和平台网络策略 |

## 9. 发布前检查清单

- [ ] Python 版本、Conda 渠道和依赖已明确声明。
- [ ] 新环境可从环境定义/锁文件创建成功。
- [ ] PyCharm、IDE Terminal、外部终端使用同一个项目解释器。
- [ ] `.env` 和凭据已忽略；生产密钥由 Secret 管理。
- [ ] 自动化测试、最小 AI 请求和发布冒烟验证通过。
- [ ] 制品关联到唯一 Git commit 和不可混淆的版本。
- [ ] 生产配置、健康检查、日志、监控和回滚方式明确。
- [ ] GPU/模型/向量数据库等外部依赖的目标环境兼容性已核实。
