## 核心知识点

> [!important] ★ 本章必记
> ==Coding Agent + 文件系统== · ==代码是元能力== · ==可验证性最强== · ==故障恢复三问== · ==致命三要素 + 持久记忆==

> [!warning] ⚠ 口径提醒
> Simon Willison 的致命三要素（私有数据 / 不受信任内容 / 外部通信）之外，本章加第四个：**持久记忆**。

### 5.1 通用 Agent 的架构（p130–134）

> [!tip] 💡 大白话
> 让 Agent 自己写代码、自己跑，再给它一块硬盘放代码和数据——PPT、网页、报告最后都能落成代码，所以这是通用解（把 [[04-第4章 工具|第 4 章]] 的工具变成能自己造的）。

> 以开放任务为目标的通用 Agent = **Coding Agent（自主编写、修改、执行代码）+ 文件系统**（存代码、数据、记忆、中间结果的工作空间）。

Manus → Open Claw 都遵循这一范式；它们把 Deep Research、Computer Use、Coding 三大能力融合，但**核心是 Coding**——因为几乎所有高效的内容生成最终都要落到代码上（PPT、网页、报告……）。

为什么代码能担此重任：

- **思考上**：形式化代码让思考高度严谨——「年龄大于 18 且已实名认证」用自然语言有多种理解，写成代码毫无歧义；
- **表达上**：一段能跑通的代码本身就是逻辑自洽的证明，执行结果提供**客观的对错标准**。

**整体流程**（p133 图 5-2）：① 项目文档化（`read_file`）→ ② 需求理解（`ask_user`）→ ③ 设计文档（`write_file`）→ ④ 编码与测试（`edit_file`）→ ⑤ 审查与交付（`bash`）。配套：Agent 状态栏（`cwd`、git branch、未暂存变更）、工具输出头尾截断、持久化终端会话。三条纪律：**计划先于行动 · 验证贯穿始终 · 文档与代码共同演化**。

### 5.1.4–5.1.5 Harness 与故障恢复（p135–137）

> [!tip] 💡 大白话
> 光会跑不够，还得知道「卡住了怎么发现、发现后怎么办、什么时候必须停手」，否则一个小错能烧掉一整晚预算。

Coding Agent 是**最能受益于 Harness 工程**的领域，因为代码编写是所有 Agent 任务中**可验证性最强**的。此处回到第 1 章五要素：上下文管理 + 工具接口 + 约束 + 验证 + 纠正。

故障与错误恢复系统回答三个问题：生产级 Harness 会遇到哪些故障？如何检测与恢复？**什么时候必须终止**？伏笔来自第 1 章消融实验——仅缺失一条工具结果反馈就足以让 Agent 陷入无限循环，而真实故障远比实验多样。

**实现技巧**（5.1.6）：并行工具调用、流式执行、**级联中止**——在保证思考质量的前提下提速、降上下文消耗，是第 2 / 4 章通用技术在编程领域的落地。

**两个具体工具设计**：

- 搜索工具（5.1.7）：`glob` / `grep` / 语义检索等互补方式按任务性质选择；
- 文件编辑工具（5.1.8，图 5-4 对比五种方案）：`Diff + Apply Model`、`Old String → New String`、行号定位、类 Vim 命令、首尾匹配——难点不在操作本身，而在**如何让 LLM 高效可靠地表达「改哪里、怎么改」**，是自然语言与机器精确执行之间的根本张力。

**安全**（5.1.9）：威胁模型 → 沙盒隔离（网络出口、文件系统、资源限额）→ 执行期防御（命令语义解析、让安全检查「隐形」的**推测性执行**）→ 信任与忠诚（多方委托下 Agent 为谁效忠、为何要把信任边界下移到数据层）。

### 5.2 代码作为元能力：六个方向（p144–158）

> [!tip] 💡 大白话
> 代码是「能造工具的工具」：给了这台万能机床，Agent 就能现做 PPT、报表、可视化，不必提前把每样都备齐。

元能力 = **能创造其他能力的能力**。

| 方向 | 要点 |
|---|---|
| **5.2.1 思考工具** | LLM 思考是概率性、近似的；数学/符号/严格逻辑要求确定性。用可执行代码补足精确计算与集合推导 |
| **5.2.2 业务规则约束** | 直接回应 Harness 原则「**约束：编码化而非文档化**」——把「什么是合理的退款请求」从自然语言转成可执行代码，使规则成为强制约束而非建议性指南 |
| **5.2.3 多媒体生成** | PPT / 报告 / 交互应用底层都是 HTML+CSS+JS 等结构化数据；GUI 所见即所得对 Agent 反而不直观（需视觉理解与精确坐标），代码生成绕开这一层 |
| **5.2.4 系统适配器** | 外部服务没 SDK、文档缺失、返回格式漂移时，Agent 当场读文档或观察一两条真实响应，**即时生成适配代码** |
| **5.2.5 生成式 UI** | 动态生成表单、交互图表甚至完整界面，替代冗长的纯文本问答 |
| **5.2.6 Agent 自举** | 推向极限：Agent 能不能用代码生成能力**创造另一个 Agent** |

书中反复用**提议者—审核者**机制（PPT 生成、视频编辑、日志可视化）。思考题 4 指出其风险：Reviewer 审美与目标用户不一致时，反馈循环会收敛到错误的局部最优。

> **致命三要素**（Simon Willison）：访问私有数据、暴露于不受信任内容、具备外部通信能力。本章在此基础上加第四个：**持久记忆**（思考题 7）。

## 思考题（原题精选，PDF p160）

> [!question] 自测 · 先自己答，再回 `_原文/` 核对原题

1. ★★ 代码执行引入漏洞 / 无限循环 / 资源耗尽，沙盒隔离又限制能力（无法访问网络或文件系统）——如何找安全与能力的最优平衡？
2. ★★★ Agent 自举每次都可能引入偏差，错误会在代际间**累积**吗？如何防止退化？
3. ★★ Agent 能自动跟随日志格式演化，但若变化是 bug 而非预期改动，适应性反而**掩盖了问题**——如何区分「需要适应的变化」与「需要报告的异常」？
4. ★★ 把经验沉淀为系统提示词规则会让规则集不断膨胀，如何对规则做「**垃圾回收**」？为什么一次成功的代码修改还不能直接视为第 9 章所说的持续进化？
5. ★★★ 同时面对致命四要素的生产环境，如何设计安全策略？
