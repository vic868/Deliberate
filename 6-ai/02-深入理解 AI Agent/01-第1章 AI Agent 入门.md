## 核心知识点

### 1.1 两个公式，不是两套骨架（p15 / p26 / p35）

```
Agent = LLM + 上下文 + 工具          ← 全书结构骨架，只描述 Agent 边界之内
Agent = Model + Harness              ← 同一事物在生产形态下的展开
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment                  ← 环境不在公式里，是被交互的对象
```

- 前者是**组件划分**，后者是**职责划分**：把「上下文 + 工具」细分为五要素，再加上三层保障机制。原文明确说二者「不是与它并列的另一套划分」（p35）。
- Harness 的精确边界：**Agent 边界内、模型之外的运行与治理层**，负责协调 Model 与 Environment 的交互，但不包括环境本身。
- 全书结构：第 2–6 章构建，第 7–9 章评估与进化，第 10 章协作。**第 6 章不属于五要素**——它扩展的是观察/动作空间的模态与时机。

### 1.1.1 观察空间与动作空间（p16）

Harness 把环境返回的**观察**转成模型能处理的上下文，把模型选择的**行动**转成对环境的工具调用。两句关键判断：

- 没通过观察通道进入上下文的信息，对模型来说就像不存在；
- 没被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。

> 由此得到全书的能力杠杆：**模型固定时，重新定义或扩展观察空间与动作空间，往往比换模型更有效**。

### 1.1.2 五类工具（p18）

| 类别 | 方向 | 例子 |
|---|---|---|
| 感知 | 环境 → Agent | 搜索、文件读取、API / 数据库 |
| 执行 | Agent → 环境 | 代码执行、文件操作、系统命令 |
| 协作 | Agent ↔ Agent / 人类 | 子 Agent 委托、人工确认 |
| 事件触发 | 外部输入驱动 | 新邮件、定时器、Webhook（**非 Agent 主动调用**） |
| 用户沟通 | Agent → 用户 | 文字、语音、邮件等跨渠道触达 |

第 4 章展开前三类，第 6 章展开后两类（依赖异步运行时）。

### 1.1.4 上下文的五部分（p21）

从 API 视角，每次调用 LLM 时上下文由五部分构成：

1. **系统提示词**（开发者编写，全程不变，含跨会话用户记忆与环境状态）
2. **工具定义**（名称 / 描述 / 参数格式）
3. **用户消息**（可能含 RAG 动态注入的外部知识）
4. **模型回复**（`reasoning` + `content` + `tool_calls`，三者不一定同时出现）
5. **工具执行结果**（下一步思考的直接依据）

> 前两项构成**静态前缀**——这是第 2 章 KV Cache / Prompt Cache 设计的基础；2026 年以来生产框架也可把完整 schema 动态追加到上下文末尾而不破坏前缀。

### 1.1.5 ReAct 循环（p22）

`ReAct = Reasoning + Acting`。骨架就是一个 `while` 循环：模型看轨迹 → 决定调工具还是给答案 → 宿主执行工具 → 结果回灌轨迹 → 再请求模型。第 1 章的消融实验指出：**仅缺失「工具结果反馈」一条，就足以让 Agent 反复重试直到耗尽迭代预算**。

### 1.2 Harness 工程与三条核心原则（p26 / p28–29）

工程范式演进：**提示工程 → 上下文工程 → Loop 工程（Harness 工程）**。动机是 Demo 与可靠产品之间的鸿沟：幻觉、选错工具、遇错无法自恢复。

Anthropic 的三条原则（p29）：

1. **保持简单** —— 直接 API 调用优于复杂框架，每多一层抽象都是调试盲区；
2. **保持透明** —— 显式展示规划、日志、决策轨迹，黑箱错误外部无法定位；
3. **设计好工具接口 ACI** —— 从 Agent 视角而非程序员视角设计接口，用「防呆（Poka-yoke）」让误用在设计上无法发生。

编排顺序的实用建议：**先优化提示词 → 再考虑工作流 → 最后才引入自主 Agent**。护栏按被绕过的难度分三层：**上下文层 / 执行层 / 数据层**，安全是架构问题，不是上线前打补丁。

### 1.3 五个贯穿全书的设计模式（p36）

| 模式 | 定义 | 后续出现 |
|---|---|---|
| 提议者—审核者 | 产出与评判由**不共享上下文**的两个角色承担；评判方只看产物 | 第 3/4/5/7/9/10 章 |
| 渐进式披露 | 先给可检索目录，按需加载细节；同时优化预算与选择精度 | Skills、分层检索、主动工具发现 |
| 只增不改 | 状态只追加、不回改；换来可缓存、可重放、可审计 | KV Cache 前缀、事件式记忆 |
| 边界集 + 保留集 | 每次修改同时在「应改变」与「不应影响」两批样本上验证 | 评估与持续进化 |
| 最小 diff + 可回滚 | 一次改动尽量小且可撤销 | 知识更新、Coding Agent |

> 提议者—审核者成立的前提是**自审不可靠**：同一上下文中的模型难以发现自己的认知盲区，也很难判断自己是否已被注入。

## 结论与金句

> 「Agent = 大脑 + 眼睛 + 手脚：LLM 是大脑，上下文是眼睛，工具是手脚。三者缺一不可。」（p36）

> 「扩展眼睛和手脚是最主要的能力杠杆。」（p36）

> 「安全问题从第一行代码就要考虑，而不是上线前打补丁。」（p37）

本章末尾明确交代：第 2 章深入 Harness 最核心的组件——上下文工程；传统 RL 与现代 LLM Agent 的对比放到第 8 章。

## 思考题（原题精选，PDF p37）

1. ★★ 只能增加一项能力（更强模型 / 更丰富上下文 / 更多工具）时选哪个？什么条件下会改变？
2. ★★★ ReAct 循环中累计缓存读取量随轮数近似**二次方增长**，如何降低？
3. ★★ 「模型即 Agent」让模型更自主，为何 Harness 工程的重要性反而在增加？
4. ★★ 除工具结果缺失外，还有哪些情况会让 Agent 陷入重试循环？如何检测与终止？
5. ★★★ 工具风险随参数组合变化（删普通文件 vs 删系统文件），如何设计**动态**风险评估？
6. ★★ 受限动作空间在什么场景下反而优于开放式？
