## 核心知识点

### 4.2 从 API 封装到 ACI（p112–114）

早期做法是把每个 API 端点包成一个工具，**粒度过细**，Agent 要协调好几个工具才能完成一个目标。更成熟的思路是 **ACI（Agent-Computer Interface）**：工具应对应 **Agent 的目标**，而不是底层 API 操作——对标 HCI 提出。

**能力的表达形式是一条谱系**（4.2.1）：同一件「部署应用」可以做 `deploy_app` 专用工具、拆成构建/打包/部署三个细工具、或干脆只写一份 Skill 文档让 Agent 用 bash 逐步执行。

> 默认**往通用的一端靠**，只在四种情况退回专用工具：**安全权限、参数复杂、使用频率极高、平台差异**。

**两个易错点**：

- **工具描述**（4.2.2）核心是让 LLM 知道「**什么时候用**」，而不只是「能做什么」。说「搜索相关内容」远不如「当需要获取实时信息或查找未知事实时使用」；边界同样要写明（如文件搜索只匹配文件名、不能搜内容）。
- **参数传递的保真性**（4.2.3）：警惕**静默输入转换**——工具在执行前悄悄「修正」模型参数，导致实际操作偏离意图。书中举例 Cursor 2026 年初某版本把 `old_string` / `new_string` 里的中文弯引号在传参层转换掉，造成匹配失败。这比功能缺失更隐蔽。

### 4.3 两条分发渠道（p115）

| 渠道 | 解决什么 | 代价 |
|---|---|---|
| **MCP** | 统一不同框架（OpenAI function calling / Anthropic tool use / LangChain Tool）的工具定义格式 | 接入成本降到一条命令 |
| **Skill Hub** | 用包管理器分发 `SKILL.md` | 同上 |

两者都**扩大了信任边界**，因此必须：审查描述与版本、隔离凭证、保证「模型看到的参数」与「工具真正执行的参数」一致。

### 4.4 工具爆炸：一次让模型看见多少（p117–122）

规模本身伤害正确性：**工具数超过一百个时，即使最先进的模型也容易选错**；仅 5 个 MCP 服务器就可能引入**数万 token** 的工具定义开销，在 200K 窗口里还没开始对话就吃掉近三成。

四级递进：

1. **层次化组织 + 按需加载**（4.4.1）：把工具描述同步到文件夹，Agent 默认只看到**工具名称索引**，需要时再查定义（Cursor 验证过，有 A/B 数据）。
2. **检索式预筛选**：按初始查询做语义匹配，但内在局限是**一次性匹配**——「Debug the file」这类请求可能牵出文件访问、代码分析、命令执行等多步骤跨领域工具链，任务开始时无法预见。
3. **模型原生的主动工具发现**（4.4.2）：让 Agent 从被动接受者变成执行过程中主动发现者。
4. **Skills 把工具发现变成「按需查阅」**（4.4.3）：这是第 1 章「渐进式披露」在工具侧的变体，**不再需要「嵌入索引 + 语义匹配」那套基础设施**。

> 一句话：把「**选哪个工具**」变成「**查哪条资料**」。

### 4.5–4.7 三类主动工具

| 类别 | 关键设计 |
|---|---|
| **感知** | 返回信息常远超处理能力，工具层集成上下文感知压缩；分页与**显式截断**；只读性使其天然适合缓存与并行。多模态三条路径：模型原生处理（上限最高）/ 自动提取为文本 / 把多模态模型封装成工具 |
| **执行** | 错误代价极高（误删、服务中断、真实财务损失）。**层次化防护**：输入验证 → 权限 → 提议者-审核者（事前审批 + 事后验证，Sidecar 是只读变体） |
| **协作** | 子 Agent 生命周期原语（创建 / 消息 / 取消 / 发现）、任务 ID 异步取结果、`request_human_approval` / `request_human_input`（支持超时与默认行为）、通知工具 |

## 结论与金句

> 「工具设计决定 Agent 的能力上限。第一个决策是能力用什么形式表达……它与『一次让模型看见多少条能力』是**两个独立的决策**，前者定每条能力的常驻成本，后者定同时暴露多少条。」（p129）

> 「本章聚焦 Agent 如何使用工具，下一章要回答一个更基本的问题：**Agent 能不能通过写代码来创造工具？**」（p129）

## 思考题（原题精选，PDF p129）

1. ★★ MCP 把工具定义从框架解耦，但流式输出、双向通信、有状态会话难以表达——MCP 最需要扩展什么能力？
2. ★★ 多个 MCP 服务器提供功能高度重叠的工具（同名但一个返回摘要、一个返回全文），Agent 能否感知并利用差异？
3. ★★ 「执行后立即自动验证」（如写完代码跑 linter）还能用于哪些场景？是否存在**验证成本/风险超过操作本身**而不可行的情况？
4. ★★ 面对数千工具，除主动发现外还有哪些方案？可参考人类专家面对大量工具时的策略。
