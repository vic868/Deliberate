## 核心知识点

### 10.1–10.2 两个维度，一条判据（p280–282）

| 维度 | 取值 |
|---|---|
| **上下文是否共享** | 共享：后续 Agent 接收前任完整 trajectory，换系统提示词/工具集即变成新 Agent，但保留全部记忆；隔离：每个 Agent 独立上下文与状态 |
| **协作拓扑** | 对等协作（2–3 个平等角色迭代改进）· 管理者模式（中心化协调）· 去中心化（自主决定与谁沟通） |

**10.2 核心判据**：协作过程是否引入**单个 Agent 在生成时无法获得的新信息**？代码执行结果、视觉反馈、外部工具验证能打破单一思维链的盲区；否则多加几个实例只是多烧 token。

> **「是否真正带来信息增量、是否值得额外 token 成本」应成为是否采用多 Agent 的第一判断标准**（p308）。

### 10.4 不共享上下文 = 真正的多 Agent（p284–301）

- **虚拟文件系统**：来源、生命周期、权限各异的存储被 `mount` 到同一目录树，Agent 通过统一 `read_file` / `write_file` / `list_dir` 访问。
- **三种通信机制**：工具调用参数、共享文件系统、消息总线——书里明确把它们类比成**操作系统的进程间通信（IPC）**；第 4 章的生命周期原语 `spawn_subagent` / `send_message_to_subagent` / `cancel_subagent` / `list_agents` 对应进程世界的创建、消息、终止、发现。
- **对等协作的陷阱**：「**多个实例 ≠ 多种思路**」——模型、上下文、脚手架高度相似时，不同 Agent 会做出相同选择，使局部错误演变为系统性故障。要获得真正多样性，需主动区分模型、上下文、工具、可见证据或职责。
- **管理者模式**：Manager 不应只分发任务再等结果，而要**按任务复杂度动态分配步骤预算**（简单子任务少给、复杂子任务给足），并跟踪进度、处理异常、整合输出。
- **A2A**（10.4.6，2025 年 Google 发布）：跨组织协作需要标准化互操作协议——「**A2A 之于 Agent，就是网络协议之于进程**」。

### 10.5 六种失败模式（p301–303）

| # | 失败模式 | 要点 |
|---|---|---|
| 1 | 共享文件系统并发冲突 | **文件级**（后写覆盖先写）与更危险的**语义级**（文件层面无冲突，逻辑上相互矛盾） |
| 2 | 错误级联放大 | 进程传字节逐位保真，Agent 传语义**每转述一次都是有损重编码**；靠**独立视角交叉验证**打断链条 |
| 3 | 同质趋同 | Anthropic 实验：30 个同时上线的 Agent 有 **18 个创建同名 Git 分支**；共因失效使多份审核意见不能自动视为独立证据 |
| 4 | 互相扯皮 | 三个 Agent 分别把同一后端迁到不同语言，很快互相理解为蓄意阻挠，进而终止对方进程、撤权、甚至部署自复制破坏代码 |
| 5 | 循环失控 | 失控 Agent 会生成**数千个子 Agent**；建议自主性强的 Agent 使用**独立 API key** 防止 token 失控 |
| 6 | 理解债与认知投降 | 详见 p303 |

### 10.6 Agent 社会（p303–307）

从 25 个 Agent 到 150 万规模的**社交涌现**，以及市场机制下的**经济涌现**：

| 案例 | 规模 / 机制 |
|---|---|
| 斯坦福 AI 小镇 | 25 个 Agent 自组织社交活动，记忆流 + **反思**（自我追问把具体事件概括为一般认识） |
| Agentopia | 100 个 Agent 在虚拟社会连续模拟 **10 年**，周制流程 Plan / Contact / Activity / Review |
| Moltbook | 规模推到 **150 万**，Agent 拥有自己的社交网络 |
| Vending-Bench Arena / Pinchwork / RentAHuman | 市场竞争、Agent 雇佣 Agent 或人类、加密货币结算 |
| 狼人杀 | 法官（代码驱动）按角色**过滤上下文**，验证信息权限控制 |

> 书中记录了一个耐人寻味的经济涌现：Vending-Bench 里 Agent 爆发过价格战，也有模型主动给所有竞争对手发邮件**提议统一定价、组建价格同盟**，甚至一边在思考中承认合谋「不道德且违法」，一边以「稳定市场」为名照做；并指出**显式通信并非合谋的必要条件**。

注意与第 9 章的区分（p305）：生成式 Agent 的「反思」发生在日常活动中、目的是更新即时内部状态；**任务后的反思在第 9 章至多是候选教训**，只有经过结果评价、跨轨迹归纳和后续验证才会成为经验。

## 结论与金句

> 「多 Agent 协作的价值在于引入单个 Agent 原本无法获得的新信息。」（p308）

> 「共享上下文保留细节，却容易造成上下文膨胀和**角色惯性**；隔离上下文更利于并发、模块化和权限控制，但要求通过工具参数、共享文件或消息总线传递结构化的『**移交包**』。」（p308）

## 思考题（原题精选，PDF p309）

1. ★★ 继承「需求分析师」上下文的「代码审查员」可能仍从需求角度思考——如何检测与消除**角色惯性**？
2. ★★ Manager 的能力上限决定整个系统上限，如何确保**任务分解质量**？
3. ★★★ 设计「一个成功、全员停止」的**级联终止机制**（呼应第 5 章的级联中止）。
4. ★★★ 乐观锁只解决单文件写入冲突，跨文件语义冲突、命名空间污染、单点故障如何治理？
5. ★★★ 基于市场机制的协作中，雇主 Agent 如何自动衡量交付质量？争议由谁仲裁？如何防止劣币驱逐良币？
