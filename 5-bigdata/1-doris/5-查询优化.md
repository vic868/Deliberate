# ⚡ 五、查询优化

> 本篇回答一个核心问题：**一条 SQL 交给 Doris 之后，到底发生了什么，以及我该动哪一层才能让它变快。**
> 内容覆盖执行流程与优化器、`EXPLAIN` / `PROFILE` 的读法、分区与分桶裁剪、索引体系、Join 四种实现、统计信息、物化视图、点查与高并发治理、慢查询速查表。
> 建表层面的设计（分桶键、分区、索引声明）见 [[3-表设计]] 与 [[4-建表与分区分桶]]；集群级参数与 Compaction 见 [[8-运维与调优]]；原理层见 [[1-架构与原理]]。

## 一、查询执行流程总览

### 1.1 从 SQL 到结果：五个阶段

一条 SQL 在 Doris 里的生命周期：

| 阶段 | 发生位置 | 做什么 | 出问题时的典型症状 |
|---|---|---|---|
| **① 解析（Parse）** | FE | SQL 文本 → AST，语法/语义校验、权限检查 | 语法报错、表/列不存在 |
| **② 分析与改写（Analyze & Rewrite）** | FE | 绑定元数据、类型推导、谓词下推、常量折叠、子查询去关联 | 谓词没下推、函数包裹导致裁剪失效 |
| **③ 优化（Optimize）** | FE | RBO 规则 + CBO 代价模型，枚举 join 顺序与分布方式，选出"最优"物理计划 | 选错 join 方式、广播大表、统计信息过期 |
| **④ 计划分发（Plan Fragment）** | FE → BE | 把物理计划切成 **PlanFragment**，按分区分桶信息下发给对应 BE | 数据倾斜（某几个 BE 数据量远大于其他） |
| **⑤ 执行与汇总（Execute & Merge）** | BE | 各 BE 本地扫描/聚合，必要时通过 **Exchange（shuffle）** 交换中间数据，最终汇聚到一处输出 | Exchange 数据量爆炸、算子长尾 |

> [!important] 记住这条主线
> **查询慢，90% 的情况要么是"扫得太多"（阶段②③，裁剪/索引/谓词问题），要么是"搬得太多"（阶段④⑤，shuffle/倾斜问题）。**
> 排查时先判断属于哪一类，再动手——不要一上来就调并行度。

### 1.2 MPP 架构：FE 与 BE 的分工

Doris 是 **MPP（Massively Parallel Processing）+ 火山模型/流水线** 的架构：

| 角色 | 职责 | 与查询优化相关的点 |
|---|---|---|
| **FE（Frontend）** | 解析、优化、生成计划、元数据管理、事务 | **优化器在这里**，所以"计划不好"要去 FE 看 `EXPLAIN`；FE 的统计信息质量直接决定 CBO 效果 |
| **BE（Backend）** | 存储 + 计算，执行 PlanFragment，做 Scan/Agg/Join/Sort | 数据倾斜、Exchange 代价、Compaction 状态都发生在 BE |

**关键设计**：BE 既存数据也算数据，**计算尽可能靠近数据**。这就是为什么：

- **分区裁剪 / 分桶裁剪 / 前缀索引** 能极大提速——它们在 Scan 阶段就把数据砍掉了，连网络都不用走。
- **Colocate Join** 能"零 shuffle"——两张表数据本来就在同一批 BE 上，不需要跨节点搬运。

### 1.3 FE 优化器：RBO + CBO

Doris 的优化器是**两段式**的：

| 类型 | 全称 | 依赖 | 作用 | 例子 |
|---|---|---|---|---|
| **RBO** | Rule-Based Optimizer | 固定规则，不需要数据信息 | 确定性的等价改写，一定不会变差 | 谓词下推、常量折叠、`LIMIT` 下推、投影裁剪（列裁剪）、子查询去关联 |
| **CBO** | Cost-Based Optimizer | **统计信息**（行数、NDV、数据大小） | 在多条等价计划里挑代价最小的 | join 顺序、join 方式（broadcast/shuffle/colocate）、聚合方式 |

> [!warning] 这是面试最爱问的因果链
> **CBO 的输入是统计信息 → 统计信息不准 → 代价估算错 → 计划退化 → 查询突然变慢。**
> 所以"昨天还好好的，今天这条 SQL 变成 30 分钟"的第一嫌疑对象，通常是**统计信息过期**（数据量涨了、分区新增了），而不是硬件。
> 修复动作很简单：`ANALYZE TABLE ...`（见 §六）。

### 1.4 3.x 的 Nereids 优化器

- Doris **2.x 后期引入、3.x 默认启用** 新一代优化器 **Nereids**（基于 Cascades 框架的 CBO），替代了老的 "legacy planner"。
- 老优化器在 3.x 已不是主线（`enable_nereids_planner` 这类开关在 3.x 语义已变化，新版本中 Nereids 是唯一/默认路径），**不要再按老优化器的行为去理解计划**。
- Nereids 带来的实际差异：
  - 更完整的 **CBO + 统计信息驱动**，支持更复杂的子查询去关联、更多 join 重排；
  - `EXPLAIN` 里的算子树结构、join 分布方式的展示更规范；
  - 但也有坑：**统计信息缺失时，Nereids 的估算可能比老优化器更激进**，出现"原本能跑的计划变成全表广播"。

> [!tip] 版本认知（3.x vs 4.x）
> - **3.x**：Nereids 默认、存算分离（3.0 引入）、异步物化视图成熟、倒排索引体系完善。**本篇以 3.x 为基线。**
> - **4.x**：继续在存算分离、湖仓、倒排索引与点查方向上增强，优化器与执行引擎进一步演进。**大多数优化原则（裁剪、Join 选型、MV、统计信息）在两代之间是通用的**，只有具体参数名/开关可能不同——遇到参数不确定时先 `SHOW VARIABLES LIKE '%xxx%'` 确认。

## 二、怎么看执行计划

### 2.1 EXPLAIN 家族一览

| 命令 | 输出什么 | 什么时候用 |
|---|---|---|
| `EXPLAIN <query>` | 优化后的**物理执行计划**（算子树的缩进文本） | 日常排查第一选择 |
| `EXPLAIN VERBOSE <query>` | 计划 + 每个算子的**详细属性**（join 条件、分布方式、runtime filter、扫描表、下推谓词等） | 需要确认 join 类型 / 裁剪是否生效 |
| `EXPLAIN GRAPH <query>` | **DOT 格式的图**，可渲染成可视化计划图 | 复杂多 join SQL 看整体形状 |
| `EXPLAIN LOGICAL <query>` | 逻辑计划（改写后、优化前/后的逻辑树） | 想确认"谓词有没有被下推/子查询有没有被去关联" |
| `SET enable_profile=true;` + 执行查询 + FE Web UI 的 **QueryProfile** | **真实运行时**：各算子耗时、行数、内存、Exchange 数据量 | 计划看起来没问题但就是慢 |

```sql
-- 最常见的两条
EXPLAIN SELECT o.dt, sum(o.amount)
FROM dwd_order o
WHERE o.dt = '2024-01-01' AND o.user_id = 1001
GROUP BY o.dt;

EXPLAIN VERBOSE SELECT ... ;   -- 要多看 join 细节时用这个
```

### 2.2 EXPLAIN 输出怎么读

`EXPLAIN` 是**缩进的算子树**，大致长这样（**示意**，具体算子名与字段随版本演进，以实际输出为准）：

```
+--------------------------------------------------------------------------+
| Explain String                                                           |
+--------------------------------------------------------------------------+
| PLAN FRAGMENT 0                                                          |
|   OUTPUT EXPRS: ...                                                      |
|   PARTITION: UNPARTITIONED                                               |
|                                                                          |
|   VAGGREGATE (merge finalize)                                            |
|   |  output: sum(partial_sum(amount))                                    |
|   |  cardinality=1                                                      |
|   |                                                                      |
|   VEXCHANGE                                                              |
|   |  offset: 0                                                           |
|   |                                                                      |
|   VAGGREGATE (update serialize)                                          |
|   |  output: sum(amount)                                                 |
|   |                                                                      |
|   1:VHASH_JOIN                                                           |
|   |  join op: INNER JOIN                                                 |
|   |  equal join conjunct: o.user_id = u.id                               |
|   |  runtime filters: RF000[bloom] <- u.id                               |
|   |                                                                      |
|   0:VOLAP_SCAN                                                           |
|   |  table: dwd_order                                                    |
|   |  partitions=1/365                                                     |
|   |  tablets=8/64                                                         |
|   |  tabletList=...                                                       |
|   |  cardinality=...                                                      |
|   |  pushdown predicates: dt = '2024-01-01'                              |
+--------------------------------------------------------------------------+
```

**读计划时按这个顺序看（从底往上、从扫描往上）：**

| 优先级 | 看什么 | 判断标准 | 不理想时怎么办 |
|---|---|---|---|
| ① | **扫描的分区数 / 分片(tablet)数** | `partitions=1/365`、`tablets=8/64` 说明裁剪生效 | 检查谓词是否直接作用在分区列/分桶键上 |
| ② | **扫描的估算行数 / 数据量** | 估算值应接近真实值；若远小于真实值 → 统计信息过期 | `ANALYZE TABLE` |
| ③ | **下推谓词（pushdown predicates）** | 过滤条件应当出现在 Scan 节点上，而不是上层 | 检查函数包裹、`OR`、隐式类型转换 |
| ④ | **join 方式与分布** | 小表 broadcast、大表 shuffle、能 colocate 就 colocate | 见 §五 |
| ⑤ | **是否有 Exchange** | 每个 `VEXCHANGE` 都意味着一次网络搬运 + 序列化 | 减少 shuffle：改分桶/colocate/预聚合 |
| ⑥ | **最终输出的行数估算** | 输出行数不该显著大于上游过滤后的行数 | 检查聚合是否被下推 |

> [!tip] "读计划"的实操口诀
> **先看最底层 Scan 砍掉了多少数据，再看中间 Exchange 搬了多少数据，最后看最上层 TopN/聚合的代价。**
> 这三件事能覆盖绝大多数慢查询。

### 2.3 EXPLAIN VERBOSE：多看这些字段

`EXPLAIN VERBOSE` 相比 `EXPLAIN` 会展开更多属性，重点关注：

| 关注点 | 在输出里找什么 | 含义 |
|---|---|---|
| **join 分布方式** | join 节点上的 distribution / `BROADCAST` / `SHUFFLE` / `COLOCATE` 等标识 | 直接告诉你走的是哪一种 join（§5.6） |
| **runtime filter** | `build runtime filters: RFxxx[...] <- 列` 与 `runtime filters: RFxxx[...]` | 是否生成了 RF、rf 类型是 bloom 还是 min/max（§5.4） |
| **join 重排结果** | 两个 join 输入子树的顺序与 `cardinality` | CBO 选出的 join 顺序是否合理（小表驱动大表） |
| **投影裁剪** | scan 节点上 `output` 列是否被裁到最小集合 | `SELECT *` 会在这里暴露出来（列裁剪失效） |
| **agg 是否两阶段** | 是否出现 `partial` / `merge` | 两阶段聚合能减少 shuffle 数据量 |

### 2.4 EXPLAIN GRAPH：可视化

Doris 支持输出 **DOT 格式**的计划图。在 FE Web UI 上可以直接把计划渲染成图；也可以在客户端拿到 DOT 文本后用 Graphviz 渲染。

```
EXPLAIN GRAPH SELECT ... ;
```

**适用场景**：多表 join（4 张表以上）时，文本计划已经很难看出"哪张表被广播了什么"。图能一眼看出：

- 哪些节点是 **broadcast 的扇出**（一个小圆圈连出 N 条边，通常就是危险信号：广播了大表）；
- 哪些地方发生了**多级 shuffle**（节点层层 exchange）；
- 是否有**孤立的叶子节点**（可能是笛卡尔积/未使用的表）。

### 2.5 PROFILE：真实运行时才是真相

`EXPLAIN` 是**估算**，`PROFILE` 是**实测**。两者不一致时，永远信 PROFILE。

```sql
SET enable_profile = true;
-- 执行你的查询
SELECT ... ;
-- 然后查看 profile 列表与具体某个 profile
SHOW PROFILELIST;
SHOW QUERY PROFILE "/path/to/profile";   -- 或直接在 FE Web UI 的 QueryProfile 页面看
```

> [!warning] `enable_profile = true` 是有代价的
> 打开后会收集每个算子的运行时统计，**有额外开销，也可能因为聚合统计信息而放大内存**。
> **不要全局默认打开**，只在排查时按会话打开。

**PROFILE 里要看的东西（这才是"为什么慢"的答案）：**

| 指标 | 含义 | 诊断结论 |
|---|---|---|
| **各算子耗时（含子节点耗时）** | 整棵树的耗时分布 | 找出**占比最大的那个算子**，它就是瓶颈 |
| **Scan 的实际行数 / 读取字节数** | `RowsReturned` / `BytesRead` | 与 `EXPLAIN` 估算对比：差一个数量级 → 统计信息问题 |
| **Exchange 的发送/接收行数** | `BytesSent` / `RowsSent` | 某次 shuffle 搬了上亿行 → 该考虑 pre-aggregation 或改 join 方式 |
| **各 instance 的行数/耗时分布** | `InstanceNum` 之间是否均衡 | **最大值 / 平均值** 明显偏离 → **数据倾斜**（长尾） |
| **峰值内存** | `PeakMemoryUsage` | 判断是否触到 `exec_mem_limit`，是否会 spill / OOM |
| **等待时间** | wait / 排队相关耗时 | 可能是 runtime filter 等待、可能是资源组队列、可能是磁盘 IO |

> [!example] 一个真实的定位过程（典型模式）
> 现象：一条 join + group by 的 SQL 平时 3s，今晚 4 分钟。
> 1. `EXPLAIN VERBOSE` 看扫描分区数：`partitions=1/365` —— 裁剪正常。
> 2. 看 join：小表 side 的 `cardinality` 估算只有几千，但 PROFILE 里实际读了几千万行 —— **统计信息过期**。
> 3. 因为估算严重偏小，CBO 选择了 **BROADCAST**，把这"实际几千万行"的表广播到了所有 BE。
> 4. 修复：`ANALYZE TABLE` 刷新统计信息 → 计划自动改回 SHUFFLE / 或者手动用 join hint 固定顺序。
> **结论：表面现象是"网络/内存爆炸"，根因是"统计信息"。**

### 2.6 读计划的检查清单

排查一条慢 SQL 时，按这张表逐项过：

- [ ] Scan 节点：**分区裁剪了吗？分桶裁剪了吗？前缀索引/ZoneMap 命中了吗？**
- [ ] Scan 节点：**估算行数和实际行数差多少？**（差很多 → `ANALYZE`）
- [ ] Scan 节点：**谓词全部下推了吗？有没有函数包裹分区列？**
- [ ] 投影：**是不是 `SELECT *` 导致读了一堆用不上的列？**
- [ ] Join：**方式对不对？有没有广播大表？**
- [ ] Join：**该 colocate 的有没有 colocate？**
- [ ] 中间层：**有几个 Exchange？搬运量多大？**
- [ ] 聚合：**是不是两阶段聚合？shuffle 前有没有先做 partial 聚合？**
- [ ] 排序/limit：**是 TopN 还是全量 Sort？limit 有没有下推？**
- [ ] PROFILE：**是哪个算子耗时最长？各 instance 是否均衡（倾斜）？**

## 三、分区裁剪与分桶裁剪

### 3.1 分区裁剪（Partition Pruning）

**原理**：Doris 表按分区列（通常是时间）做 Range/List 分区，每个分区是独立的物理目录。如果 SQL 的 `WHERE` 能**静态确定**需要哪些分区，FE 在生成计划时只把命中的分区交给 BE——**没命中的分区连元数据都不用取**。

**触发条件**：

| 条件 | 说明 |
|---|---|
| 谓词**直接**作用在**分区列**上 | `WHERE dt = '2024-01-01'`、`WHERE dt >= '2024-01-01' AND dt < '2024-02-01'` |
| 是**常量**或**运行时可求值**的表达式 | 例如 `WHERE dt = DATE_SUB(NOW(), INTERVAL 1 DAY)` 里的 `NOW()` 是运行时常量，仍可裁剪 |
| 分区列**没有**被函数/表达式包裹 | 这是最常见的破坏方式 |

### 3.2 最常见的"破坏裁剪"写法与改写

| 错误写法 | 问题 | 正确改写 |
|---|---|---|
| `WHERE DATE_FORMAT(dt, '%Y%m%d') = '20240101'` | 对分区列做了函数运算，分区列变成一个普通表达式 → **无法裁剪**（全分区扫描） | `WHERE dt = '2024-01-01'`（把常量格式化成和分区列同类型） |
| `WHERE SUBSTR(dt, 1, 7) = '2024-01'` | 同上，截断后无法映射到分区边界 | `WHERE dt >= '2024-01-01' AND dt < '2024-02-01'` |
| `WHERE CAST(dt AS DATE) = '2024-01-01'` | 隐式/显式转换破坏裁剪 | 保证分区列与常量同类型 |
| `WHERE dt + INTERVAL 1 DAY = '2024-01-02'` | 分区列参与算术 | `WHERE dt = '2024-01-01'` |
| `WHERE dt = '2024-01-01' OR dt = '2024-01-02'` | 其实**可以**裁剪（OR 在分区列上仍能推导分区集合）；但若 OR 的另一支不涉及分区列，则**整体失效** | 拆成两段 `UNION ALL`，或确保 OR 每一支都约束分区列 |
| 分区列上做**隐式类型转换**（如分区列是 `DATE`，传字符串且有歧义格式） | 可能退化为函数比较 | 显式写标准日期字面量 |
| 用**子查询**返回分区值：`WHERE dt IN (SELECT dt FROM ...)` | 运行时才能确定，无法静态裁剪（可能退化为运行时裁剪或全扫） | 尽量改成常量集合，或先在应用层查出分区列表 |

> [!danger] 一个真实会踩的坑
> 数仓里 `dt` 存的是 `DATE` 类型，报表系统传参习惯是 `'20240101'` 这种 8 位字符串。
> 有人为了"兼容"写成 `WHERE DATE_FORMAT(dt,'%Y%m%d') = '20240101'`。
> **这条 SQL 会把 365 个分区全扫一遍**——因为分区列被函数包裹了。
> 正确做法是在**应用层把 `'20240101'` 格式化成 `'2024-01-01'`**，SQL 里保持 `WHERE dt = '2024-01-01'`。

**如何验证裁剪生效**：看 `EXPLAIN` 的 Scan 节点，找分区/分片计数字段，形如 `partitions=N/M`（N 为命中的分区数，M 为总分区数）。**`partitions=1/365` 就是裁剪成功；`partitions=365/365` 就是裁剪失效。**

> [!note] 运行时裁剪（Runtime Partition Pruning）
> 对于 join 中"分区列来自另一张表"的情况，Doris 可以在运行时根据 build side 的实际值来裁剪 probe side 的分区。
> 这属于**运行时优化**，计划阶段看不出来，要靠 PROFILE 验证。**但不要依赖它兜底**——能在 SQL 层写成常量条件就写成常量条件。

### 3.3 分桶裁剪（Bucket Pruning）

**原理**：一张表按分桶键（`DISTRIBUTED BY HASH(k1, k2) BUCKETS N`）把数据 hash 到 N 个 tablet 上，每个 tablet 分布在不同 BE。如果谓词能**唯一确定**某些分桶，就可以只扫这些 tablet。

**触发条件（比分区裁剪苛刻得多）**：

| 条件 | 说明 |
|---|---|
| 谓词是**等值**条件 | `k1 = 5`；范围条件 `k1 > 5` 无法裁剪（hash 打散了顺序） |
| 字段正是**分桶键**（或分桶键的**全部列**都能被等值约束） | 多列分桶键时，只对其中一列等值通常**不能**裁剪 |
| 分桶列没有被函数包裹 | 同分区裁剪 |

**对比表**：

| 维度 | 分区裁剪 | 分桶裁剪 |
|---|---|---|
| 谓词类型 | 等值、范围、IN 都可以 | **只支持等值**（hash 分布天然不支持范围） |
| 作用于 | 分区列 | 分桶键 |
| 粒度 | 通常天/月 | tablet 级（比分区更细） |
| 收益 | **数量级**（少扫几个月的数据） | 通常是 **1/N** 级别（少扫几分之一到几十分之一） |
| 常见于 | 时间维度的报表查询 | 按用户 ID / 订单 ID 的点查与明细查询 |

> [!important] 这直接影响建表设计
> 分桶键的选择要在两个矛盾的目标之间权衡：
> 1. **点查/明细查询** 希望按高频过滤列分桶（利于分桶裁剪）；
> 2. **Join** 希望按 join 键分桶（利于 Bucket Shuffle / Colocate Join，见 §五）。
> **分桶键一旦定下，改的成本很高（需要重分布数据）。** 所以建表时的取舍分析见 [[3-表设计]]，分桶数怎么算见 [[4-建表与分区分桶]]。

> [!warning] 分桶数不合理也会伤查询
> - **分桶数太少**：单个 tablet 太大，扫描粒度粗，并行度上不去，compaction 压力集中。
> - **分桶数太多**：元数据和调度开销变大，小文件/小版本问题加剧，点查反而可能变慢（见 [[8-运维与调优]]）。
> 一般按"单 tablet 数据量在几百 MB 级别"来估，而不是拍脑袋定。

## 四、索引体系与生效条件

Doris 的"索引"分好几层，各自解决不同问题。**理解它们的分工，才能判断"为什么我建了索引还是不生效"。**

| 索引/机制 | 本质 | 最适合 | 生效前提 |
|---|---|---|---|
| **前缀索引** | 排序文件上的稀疏索引（最左前缀） | 前缀列上的等值/范围/排序 | 谓词命中 **key 列的最左前缀** |
| **ZoneMap** | 每个数据块的 min/max 统计 | 范围过滤、`IS NULL`、宽表任意列的粗过滤 | 列上数据有局部聚集性（有序或半有序） |
| **Bloom Filter** | 列级布隆过滤器 | **高基数列的等值**查询 | 建表时显式声明 `bloom_filter_columns` |
| **倒排索引** | 列级倒排（分词/精确值） | **全文检索**、等值、`IN`、范围 | 3.x 的 `USING INVERTED`，需显式建 |

### 4.1 前缀索引（Prefix Index）

Doris 的存储是**按 key 列排序**的（Unique/Aggregate 表按 key 列排序，Duplicate 表按指定的排序列）。基于这个有序性，Doris 对每批数据构建**前缀索引**：取每行的**最左若干字节**（受配置控制，稳定行为是"每行前缀的固定字节数"）作为索引项。

**关键结论：前缀索引是"最左前缀"语义，和 MySQL 联合索引完全一样的直觉。**

| 表的 key 列顺序 | 能加速的谓词 | 不能加速的谓词 |
|---|---|---|
| `(dt, user_id, order_id)` | `dt = ?`、`dt = ? AND user_id = ?`、`dt > ?` | `user_id = ?`（跳过 dt）、`order_id = ?` |
| `(user_id, dt)` | `user_id = ?`、`user_id = ? AND dt = ?` | `dt = ?`（跳过 user_id） |

> [!important] 面试常考："我按 user_id 查询，为什么没用上索引？"
> 因为**建表时 key 列的第一列不是 `user_id`**。前缀索引只认最左前缀。
> 解法有两个方向：
> 1. 调整 key 列顺序（**代价大，等于重写数据**，需评估）；
> 2. **在 `user_id` 上建倒排索引或 Bloom Filter**（成本低，3.x 推荐做法）。
> **这就是"为什么 3.x 大力推倒排索引"的原因**——它解决了"只能有一个最左前缀"这个结构性缺陷。

> [!note] 几个细节
> - 前缀索引对**定长类型**效率最高（`INT`、`BIGINT`、`DATE`）；对 `VARCHAR` 会按字节截断。
> - 前缀索引索引的是**前缀字节**，所以前缀列特别长的字符串（比如长 URL）靠前的部分才有区分度，后面的部分进不了索引。
> - `Duplicate` 表也可以指定排序键来获得前缀索引能力。

### 4.2 ZoneMap

**原理**：Doris 列存按**数据块（page / 行组）**组织，每个块为每列记录 **min/max**（以及 `has_null`）。查询时如果谓词区间与块的 min/max **不相交**，就整块跳过。

**特点**：

| 项 | 说明 |
|---|---|
| **自动生效，无需声明** | 所有列都有 |
| **对任意列都有效** | 不像前缀索引只认最左前缀 |
| **效果取决于数据聚集度** | 数据按 key 有序 → 每块区间窄 → 过滤率高；数据随机分布 → 每块 min/max 都覆盖全值域 → 几乎无效 |
| **对等值查询也有效** | `col = 5` 只要某块 min/max 不含 5 就跳过 |

> [!tip] 怎么榨干 ZoneMap
> ZoneMap 的价值来自**局部有序**。所以：
> - 把**过滤频率最高的列放在排序键（key 列）靠前位置**，数据自然按它聚簇；
> - 对写入时天然有时间顺序的表，按时间做**分区 + 排序**，能显著提高 ZoneMap 过滤率；
> - 观察方法：`EXPLAIN` 里看 Scan 节点的**过滤后行数估算**，或者在 PROFILE 里看实际扫描的块数 / 行数。

### 4.3 Bloom Filter

**原理**：对指定列建立布隆过滤器，可以**确定性地回答"这个值一定不在这个数据块里"**（存在假阳性，不存在假阴性）。

```sql
CREATE TABLE dwd_user (
  user_id BIGINT NOT NULL,
  dt      DATE   NOT NULL,
  name    VARCHAR(64)
)
UNIQUE KEY(user_id, dt)
DISTRIBUTED BY HASH(user_id) BUCKETS 16
PROPERTIES (
  "replication_num" = "3",
  "bloom_filter_columns" = "name"    -- 对 name 建 Bloom Filter
);
```

| 适用 | 不适用 |
|---|---|
| **高基数列的等值查询**（`name = 'xxx'`、`email = 'x@y.com'`） | 低基数列（基数低，过滤率差，白占空间） |
| 列值较长、前缀区分度不高的列 | 范围查询（Bloom Filter 不支持区间） |
| 点查/明细精确匹配 | 频繁更新的列（维护成本） |

> [!warning] 不要给所有列都建 Bloom Filter
> - 每个 Bloom Filter 都要占存储、要多写元数据；
> - 低基数列上几乎不起作用；
> - **对分区列、分桶键建 Bloom Filter 基本是浪费**——分区/分桶裁剪已经把它们过滤掉了。

### 4.4 倒排索引（Inverted Index，3.x 重点）

倒排索引是 3.x 索引体系的**核心增强**，把"搜索"能力引进了 OLAP：

```sql
-- 建表时声明
CREATE TABLE dwd_log (
  ts       DATETIME NOT NULL,
  level    VARCHAR(16),
  service  VARCHAR(64),
  msg      TEXT,
  INDEX idx_level   (level)   USING INVERTED,
  INDEX idx_service (service) USING INVERTED,
  INDEX idx_msg     (msg)     USING INVERTED PROPERTIES("parser" = "chinese")
)
DUPLICATE KEY(ts)
DISTRIBUTED BY HASH(service) BUCKETS 16
PROPERTIES ("replication_num" = "3");

-- 也支持后加
CREATE INDEX idx_level ON dwd_log(level) USING INVERTED;
ALTER TABLE dwd_log ADD INDEX idx_level (level) USING INVERTED;
SHOW INDEX FROM dwd_log;
```

**倒排索引能做什么**：

| 能力 | 支持的条件 | 说明 |
|---|---|---|
| **等值查询** | `level = 'ERROR'` | 替代 Bloom Filter 的强化版 |
| **`IN` / 多值** | `service IN ('a','b','c')` | 倒排天然适合多值 |
| **范围查询** | `ts > '2024-01-01'`（数值/时间列） | 3.x 的数值倒排支持区间 |
| **全文检索** | `MATCH_ANY(msg, 'timeout error')` | 分词后任一词命中 |
| **全文 AND** | `MATCH_ALL(msg, 'timeout error')` | 分词后所有词都命中 |
| **短语检索** | `MATCH_PHRASE(msg, 'connection refused')` | 按顺序的短语匹配 |

```sql
-- 全文检索示例
SELECT ts, service, msg
FROM dwd_log
WHERE ts >= '2024-01-01 00:00:00'
  AND MATCH_ALL(msg, 'timeout connection')
  AND level = 'ERROR'
LIMIT 100;
```

> [!important] 倒排索引解决了什么结构性问题
> **前缀索引只能有一个最左前缀。** 一张表如果有 10 个高频过滤列，前缀索引最多服务其中一两个。
> 倒排索引**每个列一个索引、彼此独立**，所以可以同时支持多个列的过滤、以及全文检索——这让 Doris 从"纯 OLAP 报表引擎"扩展到"日志/可观测性/搜索"场景。
> 3.x 对倒排索引做了**索引与数据解耦**（不随数据重写而重建），写放大和 compaction 代价显著改善。

**倒排索引不生效的情况**：
- 对列做了函数运算（如 `upper(service) = 'A'`）；
- 使用了分词器不认识的语言/未指定合适 parser；
- **选择性太差**（比如 `level` 只有 3 个值且每个值占 1/3）时，优化器可能判断走索引还不如顺序扫——这是合理的，不是 bug。

### 4.5 索引"失效"的通用原因清单

按发生频率排序：

1. **谓词被函数包裹** —— 索引只能匹配"裸列 vs 常量"。
2. **隐式类型转换** —— `BIGINT` 列比字符串、`DATE` 列比非标准格式字符串。
3. **不满足最左前缀**（前缀索引）。
4. **范围条件**用在 Bloom Filter 列上（Bloom 不支持区间）。
5. **`OR` 连接不同列**：`a = 1 OR b = 2` 无法分别用两个索引做交集（可能退化为全扫）。
6. **`NOT` / `!=` / `<>`**：负向条件难以用前缀索引/Bloom 过滤。
7. **统计信息过期**：优化器认为索引不划算而主动放弃。
8. **表达式在 join 条件里**：`ON a.x = b.y + 1` —— 无法用等值 join，也难以裁剪。

## 五、Join 优化（重点）

### 5.1 四种 join 实现

Doris 的 join 执行方式本质上是**决定"哪张表的数据要跨网络搬"以及"搬多少"**。

| 方式 | 做法 | shuffle 量 | 适用条件 |
|---|---|---|---|
| **Broadcast Join** | 把小表**完整复制**到所有参与 join 的 BE | 小表 × BE 数 | 一侧表很小（能放进内存）；**最怕广播大表** |
| **Shuffle Join** | 两张表都按 join 键 hash 重分布，同键落到同一 BE | 两表全部数据 | 通用兜底方案；大表 join 大表 |
| **Bucket Shuffle Join** | **只 shuffle 右表**，按左表的**分桶方式**重分布 | 只搬一张表 | 左表 join 列 == 左表**分桶键** |
| **Colocate Join** | **两张表都不搬**，因为数据本来就在同一 BE 上 | **零 shuffle** | 两表在**同一 colocate group**，**分桶键与分桶数完全相同**，且 join 列覆盖分桶键 |

**补充：`BUCKET_SHUFFLE` 的精确前提**

- 左表的 **join 列是左表的分桶键**（或分桶键的前缀）；
- 左表是 probe side 且数据量较大（通常是事实表）；
- 右表按左表的分布方式重分布。

这样**只搬右表**，比 Shuffle Join 省一半网络。

### 5.2 四种方式对比

| 维度 | Broadcast | Shuffle | Bucket Shuffle | Colocate |
|---|---|---|---|---|
| **网络开销** | 小表×N | 两表全量 | 一表全量 | **0** |
| **对建表的要求** | 无 | 无 | 左表 join 列 = 分桶键 | **同 colocate group + 同分桶键 + 同分桶数** |
| **稳定性** | 差（估算错就炸） | 好 | 好 | 好（但依赖表设计） |
| **适用规模** | 小表 ↔ 大表 | 大表 ↔ 大表 | 事实表 ↔ 维表（事实表已按 join 键分桶） | 事实表 ↔ 事实表 / 宽表级联 join |
| **典型场景** | 维表 join 事实表（维表很小） | 临时分析型 join | 订单表 join 用户表（订单按 user_id 分桶） | 星型模型里事实表与明细表反复 join |
| **风险** | **广播大表 → BE OOM / 网络打满** | 网络成为瓶颈 | 需左表分桶键恰好是 join 键 | 表设计锁死，改分桶键代价大 |

### 5.3 Colocate Join 与建表设计的关系

**这是本篇最重要的"回头看建表"的一节。**

```sql
-- 表 A：订单明细，按 user_id 分桶
CREATE TABLE dwd_order (
  order_id BIGINT,
  user_id  BIGINT,
  amount   DECIMAL(18,2),
  dt       DATE
)
UNIQUE KEY(order_id, user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 32
PROPERTIES (
  "replication_num" = "3",
  "colocate_with" = "group_user"     -- 加入名为 group_user 的 colocate group
);

-- 表 B：用户维表，同样按 user_id 分桶、同 colocate group
CREATE TABLE dim_user (
  user_id BIGINT,
  city    VARCHAR(64),
  level   INT
)
UNIQUE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 32   -- 分桶数必须相同
PROPERTIES (
  "replication_num" = "3",
  "colocate_with" = "group_user"
);
```

```sql
-- 这个 join 可以走 Colocate Join（零 shuffle）
SELECT o.dt, u.city, sum(o.amount)
FROM dwd_order o JOIN dim_user u ON o.user_id = u.user_id
WHERE o.dt = '2024-01-01'
GROUP BY o.dt, u.city;
```

**Colocate 的硬性要求**：

| 要求 | 说明 |
|---|---|
| 同一 **colocate group** | 通过 `"colocate_with" = "group_name"` 声明 |
| **分桶键列一致且顺序一致** | 两表的 `DISTRIBUTED BY HASH(...)` 必须相同 |
| **分桶数一致** | `BUCKETS` 相同 |
| **副本数一致** | `replication_num` 相同（否则分布对不齐） |
| join 列覆盖分桶键 | join 条件必须是分桶键的等值条件 |
| 属于同一 **database** | 跨库不能 colocate |

```sql
-- 查看 colocate group 状态
SHOW PROC '/colocation_group';
-- 检查某个 group 是否健康/是否所有表都对齐
```

> [!warning] Colocate 的经典坑
> 1. **扩容后不均衡**：加了 BE 之后新数据按新分桶分布，但老数据没动 → group 内分布不一致 → join 退化。需要关注 group 的健康状态。
> 2. **一个表被 `ALTER` 改了分桶数** → 整个 group 失效。
> 3. **为了 colocate 强行让所有表用同一个分桶键** → 结果点查走不了分桶裁剪、前缀索引也不合适，**为了 join 优化牺牲了点查**。
>
> **正确的心智模型**：colocate 是"用建表时的约束换运行时的网络开销"。**只有当这张表的 join 是核心高频链路时才值得**，不要全库推广。

### 5.4 Runtime Filter

**问题**：大表 join 小表时，大表先被完整扫描出来，再拿去做 join 过滤——**大量数据被读出来又丢掉**。

**解法**：在 build side（小表）构建 hash 表时，**顺便生成一个过滤器**，下推到 probe side（大表）的**扫描阶段**，让大表在 Scan 时就把不可能匹配的行过滤掉。

```sql
-- 观察 runtime filter 是否生效
EXPLAIN VERBOSE
SELECT o.*, u.city
FROM big_fact o JOIN small_dim u ON o.user_id = u.user_id;
-- 在输出中找 build/runtime filters 相关行，形如：
--   build runtime filters: RF000[bloom] <- u.user_id
--   runtime filters: RF000[bloom] <- u.user_id
```

**相关会话变量**：

| 变量 | 作用 |
|---|---|
| `runtime_filter_mode` | RF 开关与范围：`OFF` / `LOCAL` / `GLOBAL` |
| `runtime_filter_type` | 生成哪几类 RF（`IN`、`BLOOM_FILTER`、`MIN_MAX`、组合） |
| `runtime_filter_wait_time_ms` | probe 侧等待 RF 构建的最长时间（**等不到就继续扫，宁可慢不可错**） |
| `runtime_filter_max_in_num` | `IN` 型 RF 的元素上限（超过就退化/不生成） |

| RF 类型 | 适合 | 说明 |
|---|---|---|
| **`IN`** | build side 基数**小**的等值 join | 最精准，直接把值集合下发；基数是关键——太大就退化 |
| **`BLOOM_FILTER`** | build side 基数**中等偏大** | 空间效率高，有假阳性但无假阴性 |
| **`MIN_MAX`** | build side 在 join 列上**范围集中** | 用 min/max 做区间过滤，成本最低，效果看数据分布 |

> [!tip] RF 等待时间是一个经典权衡
> - 等太久：probe 侧空转等待，查询变慢；
> - 不等：RF 还没建好就开始扫，过滤失效。
> `runtime_filter_wait_time_ms` 就是这两者的平衡点。**实践中"查询变慢"有时反而是 RF 等待时间设得过大导致的**，别只盯着数据量。

### 5.5 Join 顺序与大小表

CBO 会重排 join 顺序，目标是**尽早把中间结果缩小**。基本原则：

| 原则 | 原因 |
|---|---|
| **小表做 build side** | build side 要建 hash 表，内存压力大；小表建表快、可广播 |
| **高选择性的过滤条件尽量靠前** | 先过滤再 join，中间结果小 |
| **多表 join 时，先 join 结果集缩小最多的两个** | 减少后续 join 的输入 |
| **能先聚合再 join，就不要先 join 再聚合** | 聚合能数量级地减少行数 |

**当 CBO 判断错误时**，可以用 join hint 干预（语法与支持度随版本演进，用前先在目标版本上 `EXPLAIN` 验证生效）：

```sql
-- 强制某种 join 方式（示例写法，实际可用性请在目标版本验证）
SELECT /*+ BROADCAST(u) */ o.*, u.city
FROM dwd_order o JOIN dim_user u ON o.user_id = u.user_id;

SELECT /*+ SHUFFLE(o, u) */ ...
SELECT /*+ COLOCATE(o, u) */ ...
```

> [!warning] hint 是"止血"不是"治病"
> hint 一旦写进代码，就会**长期固化一个可能已经过时的计划**。
> 优先做的是：`ANALYZE TABLE` 修正统计信息 → 检查分桶设计 → 最后才考虑 hint。
> 用了 hint 一定要加注释说明原因和复查条件。

### 5.6 在 EXPLAIN 里识别 join 类型

`EXPLAIN VERBOSE` 下，join 节点上会**明确标出分布方式**。识别要点：

| 你看到的标识 | 结论 | 风险判断 |
|---|---|---|
| 出现 `BROADCAST` / 广播语义 | Broadcast Join | **检查被广播的那侧估算行数，如果是大表 → 立刻怀疑统计信息** |
| 出现 `SHUFFLE` / `PARTITIONED` | Shuffle Join | 通用；看交换数据量 |
| 出现 `BUCKET_SHUFFLE` | Bucket Shuffle Join | 好；说明左表分桶键用上了 |
| 出现 `COLOCATE` / local join 语义 | Colocate Join | 最好；零 shuffle |
| join 节点下**两个子树都有 EXCHANGE** | 两侧都在重分布 | Shuffle Join，成本最高 |
| join 节点下**一个子树有 EXCHANGE** | 单侧重分布 | Broadcast 或 Bucket Shuffle |
| join 节点下**没有 EXCHANGE** | 本地 join | Colocate 或单分片情形 |

**实操**：拿到 `EXPLAIN VERBOSE` 后，从最上层的 join 往下看，**每个 join 节点问三个问题**：① 什么 join 方式？② 有没有 EXCHANGE？③ 被广播/重分布的那侧估算多少行？

## 六、统计信息

### 6.1 为什么 CBO 离不开统计信息

CBO 需要一个**代价函数**，而代价函数的核心输入是：

| 统计量 | 用途 |
|---|---|
| **行数（row count）** | 估算 scan 输出规模 |
| **NDV（不同值个数）** | 估算 join 的选择率、聚合的输出行数 |
| **NULL 值比例** | refine 选择率 |
| **数据大小 / 平均列宽** | 估算内存与网络传输代价 |

> [!important] 一句话因果
> **统计信息 → 选择率估算 → 各候选计划代价 → 选中哪个 join 方式。**
> 统计信息错一个数量级，join 方式就可能从 SHUFFLE 错成 BROADCAST —— 这就是"计划退化"的完整链条。

### 6.2 `ANALYZE TABLE` 的用法

```sql
-- 收集全表统计信息（异步任务）
ANALYZE TABLE dwd_order COMPUTE STATISTICS;

-- 只收集指定列（列很多时更省资源）
ANALYZE TABLE dwd_order COMPUTE STATISTICS FOR COLUMNS dt, user_id, amount;

-- 整库
ANALYZE DATABASE my_db COMPUTE STATISTICS;

-- 同步执行（想立刻看到效果时用，会阻塞）
ANALYZE TABLE dwd_order COMPUTE STATISTICS WITH SYNC;

-- 查看收集任务状态
SHOW ANALYZE;
SHOW ANALYZE TASK STATUS <job_id>;

-- 查询已有的列统计信息
SHOW COLUMN STATS dwd_order;
SHOW TABLE STATS dwd_order;
```

### 6.3 什么时候必须手动 ANALYZE

| 时机 | 原因 |
|---|---|
| **大批量导入之后** | 行数、NDV 都变了，旧统计信息严重低估 |
| **新增分区之后** | 新分区的数据对查询可见，但统计信息里没有它 |
| **发现 `EXPLAIN` 估算行数与 PROFILE 实际行数差距大** | 最直接的信号 |
| **同一条 SQL 突然变慢且计划变了** | 典型"统计信息过期"现场 |
| **新建的 colocate / 分桶表开始承载查询前** | 让 CBO 一开始就有正确认知 |

### 6.4 自动收集与它的边界

Doris 支持**自动统计信息收集**：FE 会在后台周期性地为表收集统计信息，并在导入/变更后触发。会话变量 `enable_auto_analyze` 控制是否启用（**具体行为与默认值随版本演进，用 `SHOW VARIABLES LIKE 'enable_auto_analyze'` 确认你所在版本的实际值**）。

> [!warning] 不要完全依赖自动收集
> 自动收集有自己的调度周期和采样策略，**在高频导入的场景下永远慢半拍**。
> 实践建议：
> - 核心大表（尤其是参与高频 join 的）**在 T+1 批量导入完成后显式 `ANALYZE`**，把它当成 ETL 流程的一步；
> - 表非常多时，用 `ANALYZE DATABASE` 做兜底；
> - **表特别大时避免全表全列收集**，按需 `FOR COLUMNS` 指定参与 join/filter 的列即可。

## 七、物化视图（Materialized View）

MV 的本质是**用存储换计算**：把"需要反复算的聚合/连接结果"预先算好存起来，查询时直接读预计算结果。

### 7.1 同步 MV（rollup）：透明改写

**特点：对用户完全透明**——查询 SQL 不用改，优化器自动判断"能不能用 MV 回答这个问题"。

```sql
-- 在明细表上建一个按天的聚合 rollup
-- 注意：同步 MV 的列必须能在基表中找到，且聚合方式要能被查询复用
ALTER TABLE dwd_order ADD ROLLUP rpt_daily (
  dt,
  user_id,
  amount SUM
);

-- 查看基表上的 rollup
DESC dwd_order ALL;
SHOW ALTER TABLE ROLLUP;
```

**透明改写的匹配条件**：

| 条件 | 说明 |
|---|---|
| 查询用到的列**都在 MV 里** | 少一列都不能改写 |
| **聚合可以上卷** | 查询按 `dt, city` 分组，MV 按 `dt, city, user_id` 分组 → 可以（上卷）；反之不行 |
| 聚合函数**可兼容** | `sum` ← `sum`；`count` ← `sum(count)`；`avg` 通常要拆成 `sum/count` 才能复用 |
| 谓词能被 MV 覆盖 | 查询的过滤条件在 MV 有对应列 |
| 优化器判断**改写后更便宜** | 这是 CBO 决定的，**不是有 MV 就一定用** |

> [!tip] 一个常被忽略的事实
> **建了 MV 不等于查询会用它。** 如果 MV 的行数比基表少不了多少，或者基表已经很小，CBO 可能认为直接查基表更划算。
> 所以"我建了 MV 但查询没变快"的第一件事是：**`EXPLAIN` 看计划里读的是基表还是 MV**。

### 7.2 异步 MV（3.x 增强）：跨表、可调度

异步 MV 不依赖基表的 rollup 机制，**是一条独立的物化查询**，因此可以：

- **跨表 join**（如把事实表 + 维表 join 后物化）；
- **定时/触发刷新**；
- 支持**分区增量刷新**（基表分区新增时只刷新对应分区）；
- 用于**分层预聚合**（ODS→DWD→DWS 的物化）。

```sql
-- 异步物化视图（示意语法，具体关键字随版本演进，建前请以目标版本文档为准）
CREATE MATERIALIZED VIEW mv_order_city_daily
BUILD IMMEDIATE
REFRESH AUTO ON SCHEDULE EVERY 1 HOUR
DISTRIBUTED BY HASH(dt) BUCKETS 8
PROPERTIES ("replication_num" = "3")
AS
SELECT o.dt, u.city, count(*) AS order_cnt, sum(o.amount) AS gmv
FROM dwd_order o JOIN dim_user u ON o.user_id = u.user_id
GROUP BY o.dt, u.city;

-- 手动刷新
REFRESH MATERIALIZED VIEW mv_order_city_daily AUTO;      -- 增量（若支持）
REFRESH MATERIALIZED VIEW mv_order_city_daily COMPLETE;  -- 全量

-- 管理
SHOW MATERIALIZED VIEWS;
SHOW MATERIALIZED VIEWS FROM my_db;
CANCEL MATERIALIZED VIEW TASK <task_id>;
```

**刷新触发方式对比**：

| 触发方式 | 语义 | 适用 |
|---|---|---|
| `ON MANUAL` | 只能手动 `REFRESH` | 上游调度系统已经统一编排时（推荐，避免两套调度打架） |
| `ON SCHEDULE EVERY ...` | Doris 内建定时刷新 | 简单的周期性预聚合 |
| `ON COMMIT` | **基表数据变更后自动刷新** | 要求数据**近实时**一致；**代价大，慎用**——高频导入会把刷新打爆 |
| **分区增量刷新** | 只刷新变化的基表分区 | **分区表 + 大数据量的正确选择**（全量刷新不可接受） |

### 7.3 用 MV 做预聚合与数据分层

| 用法 | 做法 | 收益 |
|---|---|---|
| **预聚合加速** | 对高频的"按天/按维度 group by"建 MV | 报表查询从"扫亿级明细"变成"扫百万级聚合结果" |
| **宽表物化** | 把多表 join 结果物化 | 消除运行时 join 和 shuffle |
| **数据分层** | DWD 明细 MV → DWS 轻度汇总 MV → ADS 结果 MV | 每层只算增量，查询逐层变快 |
| **高并发保险** | 为大屏/BI 建专用 MV | 避免大屏每次穿透到明细表打爆集群 |

> [!important] MV 与 Colocate/分桶的配合
> MV 本身也是表，**也要选分桶键**。如果 MV 的消费方式是"按城市维度聚合查询"，那么按 `dt` 分桶、按 `city` 再做一层优化会更合适。
> **MV 的分桶设计经常被忽略，结果 MV 建了但查询还是 shuffle。**

### 7.4 MV 的代价（别忘了它要花钱）

| 代价 | 说明 |
|---|---|
| **存储成本** | MV 是真实存储的数据，多一层就多一份空间 |
| **写入放大** | **基表每导入一次，MV 都要跟着刷新**——高频导入 + 多层 MV = 写放大灾难 |
| **Compaction 压力** | MV 刷新本身产生新的数据版本，加剧 compaction（见 [[8-运维与调优]]） |
| **刷新窗口** | 全量刷新可能跑很久，期间 MV 是"陈旧"的，报表可能读到旧值 |
| **计划复杂度** | MV 太多会让优化器改写阶段变慢，也可能选错 MV |

### 7.5 什么时候不该用 MV

> [!danger] 这些场景别用 MV
> 1. **基表高频更新（秒级/分钟级导入）** 且 MV 用 `ON COMMIT` —— 写放大和 compaction 会先把你拖死。
> 2. **查询模式高度不确定**（ad-hoc 探索）—— MV 命不中就是纯浪费。
> 3. **基表本身已经很小**（几百万行）—— 直接查比维护 MV 便宜。
> 4. **只是为了避免写复杂 SQL** —— 用视图（View）就够了，视图不存数据。
> 5. **需要实时精确结果** —— MV 是有刷新延迟的，别把它当实时表用。

## 八、高并发点查优化

**场景特征**：QPS 高（几千到几万），每次查询只按主键取**一行或几行**，比如"根据订单号查订单详情"。

**矛盾点**：Doris 是列存 + 向量化执行，为"扫大量行、算少量列"优化；而点查是"精确定位一行、取全部列"——天然不匹配。

### 8.1 关键手段

| 手段 | 做法 | 原理 |
|---|---|---|
| **Unique 模型 + Merge-on-Write** | 建表 `UNIQUE KEY(...)` 且 `"enable_unique_key_merge_on_write" = "true"` | MoW 在写入时就把同主键的数据合并好，**读取时不需要在线 merge 多个版本** |
| **行存（`store_row_column`）** | `"store_row_column" = "true"` | 额外存一份**按行组织**的数据，点查时一次读一行，避免列存要拼装多列 |
| **PreparedStatement** | JDBC 走 MySQL 协议，启用服务端预处理 | 省去重复的解析/优化开销，**点查短路径的前提** |
| **点查短路径** | 满足条件时走"轻量级执行路径"，绕过完整的 FE 优化 + 分布式调度 | 大幅降低单次查询的固定开销（相关开关随版本不同，需在目标版本确认） |
| **减少并发事务开销** | 避免点查走复杂事务路径 | 降低延迟抖动 |

```sql
-- 适合点查的表
CREATE TABLE dim_order_detail (
  order_id  BIGINT NOT NULL,
  user_id   BIGINT,
  status    VARCHAR(32),
  amount    DECIMAL(18,2),
  detail    VARCHAR(2048),
  update_dt DATETIME
)
UNIQUE KEY(order_id)
DISTRIBUTED BY HASH(order_id) BUCKETS 32
PROPERTIES (
  "replication_num" = "3",
  "enable_unique_key_merge_on_write" = "true",   -- 写入时合并
  "store_row_column" = "true"                    -- 行存，服务点查
);

-- 也可以后续开启（注意：这是 schema change，有资源开销）
ALTER TABLE dim_order_detail SET ("store_row_column" = "true");
```

```java
// JDBC 点查：务必启用服务端预处理
String url = "jdbc:mysql://fe-host:9030/my_db"
           + "?useServerPrepStmts=true"        // 服务端 PreparedStatement
           + "&cachePrepStmts=true"
           + "&rewriteBatchedStatements=false"; // 点查不需要批量重写

try (Connection conn = DriverManager.getConnection(url, "user", "pwd");
     PreparedStatement ps = conn.prepareStatement(
         "SELECT order_id, status, amount, detail FROM dim_order_detail WHERE order_id = ?")) {
    ps.setLong(1, 202410090001L);
    try (ResultSet rs = ps.executeQuery()) {
        if (rs.next()) {
            // 单行点查，走行存 + 短路径
        }
    }
}
```

### 8.2 点查的选型判断

| 你的 QPS 量级 | 建议 |
|---|---|
| **< 几百** | 普通列存查询完全够用，不需要行存 |
| **几千** | MoW + 行存 + PreparedStatement，基本能扛 |
| **几万以上** | 除了上面这些，必须配合**资源组隔离**和**查询队列**，并接受"用专门的 Doris 集群/资源组承载点查" |
| **十万级以上 + 强事务** | **该考虑 OLTP 数据库（如 MySQL/Redis）而不是 Doris** —— 别让 OLAP 引擎干 OLTP 的活 |

> [!warning] 行存不是免费的
> `store_row_column` 会让**存储放大**（列存 + 行存双份），并且**写入路径更重**。
> 只对**确有高并发点查需求**的表开，不要全库开。

## 九、资源与并发治理

### 9.1 Workload Group：把负载隔离开

**问题**：一个 ad-hoc 大查询（比如全表扫描 3 年数据）能把整个集群的 CPU 和内存吃光，导致所有报表、大屏、点查一起超时。

**解法**：`Workload Group` 给不同来源的查询划分资源池。

```sql
CREATE WORKLOAD GROUP etl_group
PROPERTIES (
  "max_cpu_percent"     = "40",     -- CPU 软上限（百分比，集群视角）
  "min_cpu_percent"     = "20",     -- CPU 保障下限
  "max_memory_percent"  = "30",     -- 内存软上限
  "min_memory_percent"  = "10",     -- 内存保障下限
  "max_concurrency"     = "10",     -- 最大并发查询数
  "max_queue_size"      = "50",     -- 超限后的排队长度
  "queue_timeout_ms"    = "60000"   -- 排队超时
);

SHOW WORKLOAD GROUPS;
DROP WORKLOAD GROUP etl_group;
```

**把查询绑定到资源组**：

```sql
-- 会话级绑定
SET workload_group = 'etl_group';

-- 之后这个会话里的查询都受 etl_group 的配额约束
SELECT ...;
```

| 治理目标 | 手段 |
|---|---|
| **保护在线报表不被离线任务拖垮** | 给离线任务单独的资源组，`max_cpu_percent` 卡住 |
| **防止点查被大查询挤死** | 点查用高优先级资源组，`min_cpu_percent` 保底 |
| **限制单用户/单应用的并发** | `max_concurrency` + `queue_timeout_ms`（排队而不是直接失败） |
| **多租户隔离** | 每个业务一个资源组 |

> [!important] 资源组是"软限制"的思维
> `max_cpu_percent` 是**百分比配额**而非硬墙。当集群空闲时，某组的查询仍可能用到更多资源——这让资源利用率更高。
> 但要清楚：**资源组不能替代"把 SQL 写好"**。它是防止雪崩的保险，不是性能优化手段。

### 9.2 查询超时与内存限制

| 变量 | 作用 | 调大的风险 |
|---|---|---|
| `query_timeout` | 单条查询的最长执行时间（秒） | 调大 → 慢查询长期占用资源，故障时影响面扩大 |
| `exec_mem_limit` | 单个查询实例的内存上限 | 调大 → 单查询更容易 OOM 其他查询；调小 → 大查询直接失败 |
| `parallel_fragment_exec_instance_num` | 旧版并行度参数 | **3.x 已由 `parallel_pipeline_task_num` 取代**，不要再依赖旧参数 |
| `parallel_pipeline_task_num` | 流水线并行度（新参数） | 不是越大越好，超过 BE 核数只会加剧调度开销 |
| `enable_profile` | 是否收集 profile | 生产环境**默认关**，排查时临时开 |

```sql
-- 会话级设置（只影响当前连接）
SET exec_mem_limit = 8589934592;              -- 8GB
SET query_timeout = 600;                       -- 600 秒
SET parallel_pipeline_task_num = 8;
SET enable_profile = false;

-- 查看当前会话变量实际值（版本差异时以这里为准）
SHOW VARIABLES LIKE '%mem_limit%';
SHOW VARIABLES LIKE '%timeout%';
SHOW VARIABLES LIKE '%parallel%';
```

### 9.3 大查询拖垮集群的治理路径

按顺序做，不要跳步：

1. **先定位**：`SHOW PROC '/current_queries';` 看谁在跑、跑了多久、消耗多少内存；
2. **止血**：`KILL <query_id>;` 杀掉失控查询（先确认业务影响）；
3. **隔离**：给这类查询建独立 Workload Group，限制 CPU/内存/并发；
4. **限时**：给这类查询的会话设较小的 `query_timeout` 和 `exec_mem_limit`；
5. **治本**：改 SQL（分区裁剪、预聚合、MV）、改表设计（分桶、索引）；
6. **兜底**：加资源组的 `max_queue_size` 与告警，防止再次雪崩。

> [!danger] 最常见的错误治理顺序
> 出问题时第一反应是"**加 BE / 加内存**"。
> 但如果是**分区裁剪失效**导致的慢查询，加机器只是让全表扫描跑得快一点，问题还在，成本却翻倍。
> **先看 `EXPLAIN`，再决定加不加机器。**

## 十、常见慢查询速查表

| 现象 | 根因 | 改写 / 优化手段 |
|---|---|---|
| **扫了全部历史分区** | 分区列被函数包裹（`DATE_FORMAT(dt,...)`）或类型不匹配 | 把常量格式化成与分区列同类型；保持分区列"裸列 vs 常量" |
| **join 时内存暴涨 / BE OOM** | 统计信息过期导致 CBO 选择广播大表 | `ANALYZE TABLE` 刷新统计；必要时用 join hint 止血；检查是否真的需要那张大表参与 |
| **读了很多用不上的列** | `SELECT *` | **显式列出需要的列**；列存下"少读一列"就是少一次 IO |
| **`COUNT(DISTINCT)` 特别慢** | 高基数列去重需要大量内存和 shuffle | 用近似去重 `APPROX_COUNT_DISTINCT`（可接受误差时）；或先按维度预聚合/建 MV |
| **非 colocate 的超大 join** | 两张大表都 shuffle | 若为高频固定链路 → 改分桶键建 colocate group；否则考虑预聚合/宽表物化 |
| **结果行数异常巨大** | **笛卡尔积**：join 条件写漏或写在 `WHERE` 里被优化器当过滤条件 | 检查 join `ON` 条件；`EXPLAIN` 里 join 节点看不到等值条件就是警告 |
| **`OR` 条件让查询退化为全扫** | `OR` 两侧不同列，无法用单一索引/前缀 | 拆成 `UNION ALL`，或对涉及的列建倒排索引 |
| **子查询没下推** | 关联子查询/聚合子查询未去关联，逐行执行 | 改写为 `JOIN` / `LEFT JOIN` + 聚合；用 `EXPLAIN` 确认是否还有逐行的子查询算子 |
| **排序/`limit` 大结果集慢** | 全量 `SORT` 而非 `TopN`；`ORDER BY` 无可用有序性 | 用 `LIMIT` 配合 `ORDER BY`（触发 TopN 优化）；把排序列放进排序键让数据天然有序 |
| **数据倾斜导致长尾** | 分桶键某几个值数据量远超其他 | 换更高基数的分桶键；对倾斜值做特殊处理（加盐/单独路由）；**看 PROFILE 各 instance 行数比** |
| **导入后查询变慢** | 小文件/小版本过多，Scan 要打开大量文件 | 见 [[8-运维与调优]]：检查 compaction、合并小版本 |
| **点查 QPS 上不去** | 走列存拼装 + 每次完整优化 | MoW + `store_row_column` + PreparedStatement 短路径（§八） |
| **同一条 SQL 时快时慢** | 统计信息/数据量漂移、资源竞争、compaction 争抢 | 看 PROFILE 的等待时间；`ANALYZE`；用资源组隔离 |
| **`IN` 列表特别长** | 大 `IN` 列表要走优化与执行两遍 | 改成 join 一张临时表；或落成维表后用 join |

> [!tip] 速查表的使用姿势
> 这张表的"根因"列才是重点。**同一个现象可能有多个根因**，不要看到"慢"就直接套结论——先用 `EXPLAIN` + `PROFILE` 确认，再对应到表里的某一行。

## 十一、必答问题

> [!question] 必答：一条慢 SQL 你会怎么排查？
> 我会按"**先定位、再分层、后动手**"的顺序，具体是：
>
> **第 0 步：确认现象边界。** 是一直慢还是突然变慢？是所有 SQL 慢还是这一条？单表查询慢还是 join 慢？——这决定了后面查什么。
>
> **第 1 步：`EXPLAIN VERBOSE` 读计划。** 重点四件事：
> ① Scan 节点的**分区/分片数**（形如 `partitions=1/365`，看裁剪是否生效）；
> ② Scan 节点的**估算行数**（和真实量级比，判断统计信息是否过期）；
> ③ 每个 join 的**分布方式**（BROADCAST / SHUFFLE / BUCKET_SHUFFLE / COLOCATE），以及有没有广播大表；
> ④ 计划里有几个 **EXCHANGE**（每个都是一次网络搬运）。
>
> **第 2 步：`SET enable_profile=true` 跑一次，看 PROFILE。** 计划只是估算，PROFILE 是实测：
> ① 找出**耗时占比最大的算子**（通常就是瓶颈）；
> ② 对比 Scan 的**实际行数 vs 估算行数**——差距大就是统计信息问题；
> ③ 看各 **instance 行数是否均衡**——最大值/平均值偏高就是**数据倾斜**；
> ④ 看 **Exchange 的搬运行数/字节数**——判断是不是 shuffle 太大。
>
> **第 3 步：按层归因并动手。**
> - 如果瓶颈在 **Scan**：查分区裁剪、分桶裁剪、前缀索引/Bloom/倒排索引、谓词是否被函数包裹、是否 `SELECT *`。
> - 如果瓶颈在 **Join**：先 `ANALYZE TABLE` 修正统计信息，再看能不能走 Bucket Shuffle / Colocate，最后才考虑 hint。
> - 如果瓶颈在 **Exchange**：说明 shuffle 太大 → 考虑预聚合、物化视图、或改分桶设计。
> - 如果瓶颈在 **Aggregate**：看是否两阶段聚合、`COUNT(DISTINCT)` 能否换成近似去重。
> - 如果 **instance 不均衡**：是数据倾斜，治分桶键。
> - 如果**每个算子都不慢但总时间很长**：看等待时间（RF 等待、资源组排队、compaction 争抢）。
>
> **第 4 步：治理与兜底。** 如果这条 SQL 属"业务必须但很重"，用 **Workload Group** 把它隔离，卡住 `max_cpu_percent` / `max_concurrency`，并设合理的 `query_timeout`，避免它拖垮整个集群；同时用 **物化视图** 把高频聚合结果固化下来。
>
> **一句话总结**：`EXPLAIN` 告诉我"计划长什么样"，`PROFILE` 告诉我"实际跑成什么样"，**两者不一致的地方就是问题所在**。

> [!question] 必答：为什么我建了索引还是没生效？
> 因为 Doris 的"索引"分好几层，各自的生效条件不同：
> - **前缀索引**只认**最左前缀**，你的过滤列如果不是 key 列的第一列（或前缀），就用不上；
> - **Bloom Filter** 只支持**等值**，不支持范围；而且低基数列上过滤率差，优化器可能主动放弃；
> - **倒排索引**在列被函数包裹、或选择性太差时也不会用；
> - **ZoneMap** 依赖数据**局部有序**，如果数据随机分布，每块的 min/max 都覆盖全值域，等于没过滤。
>
> 更常见的"没生效"原因其实是**谓词本身被破坏了**：分区列被 `DATE_FORMAT` 包裹、隐式类型转换、`OR` 连接了不同列。
> **先看 `EXPLAIN` 里 Scan 节点上有没有这个谓词、扫了多少分区/分片，再谈索引。**

> [!question] 必答：Broadcast Join 和 Shuffle Join 怎么选？
> | | Broadcast | Shuffle |
> |---|---|---|
> | 网络开销 | 小表 × BE 数 | 两表全量重分布 |
> | 适用 | 一侧确实很小（能舒服放进内存） | 通用，尤其大表 join 大表 |
> | 风险 | **估算错 → 广播大表 → OOM / 网络打满** | 网络可能成为瓶颈 |
>
> 选择权主要在 **CBO**，它依据统计信息决定。**实践中最常见的故障不是"选错"，而是"统计信息过期导致选错"** —— 你以为是小表，实际涨到了几千万行。
> 所以选型的前提是：**统计信息准确**。之后才轮到"能不能走 Bucket Shuffle / Colocate 进一步省掉网络"。

> [!question] 必答：Colocate Join 对建表有什么要求？值得为了它改分桶键吗？
> **要求**：同一 `colocate_with` group、**分桶键列与顺序完全一致**、**分桶数一致**、**副本数一致**、**同一 database**，且 join 条件必须是分桶键的等值条件。
> **值不值得**：只有当**这条 join 是核心高频链路**时才值得。因为分桶键一旦定下，改的成本很高（要重分布数据），而且**为了 colocate 强行统一分桶键，往往会牺牲点查的分桶裁剪和前缀索引效果**——你在优化 A 链路的同时可能把 B 链路搞坏了。
> 我的判断顺序是：先看这条 join 到底占了多少资源（PROFILE 里 Exchange 的搬运量），值不值得动表设计；能靠**预聚合/物化视图**消除 join 的，优先消除 join 而不是优化 join。

> [!question] 必答：`EXPLAIN` 和 `PROFILE` 的区别是什么？
> | | EXPLAIN | PROFILE |
> |---|---|---|
> | 时机 | 查询**执行前** | 查询**执行后** |
> | 内容 | 优化器选出的计划（**估算**） | 各算子真实耗时、行数、内存（**实测**） |
> | 开销 | 几乎为零 | **有开销**，需显式 `SET enable_profile=true` |
> | 用途 | 判断裁剪、join 方式、下推是否合理 | 定位真实瓶颈、发现倾斜、验证估算是否准确 |
>
> **两者必须结合看**：只看 EXPLAIN 会被错误估算误导，只看 PROFILE 又不知道计划本来想干什么。**估算与实际差距最大的那个算子，就是根因所在。**

> [!question] 必答：物化视图能加速查询，为什么不能随便建？
> 因为 MV 的加速是**用写入放大和存储成本换来的**：
> - 基表每导入一次，MV 都要跟着刷新（`ON COMMIT` 在高频导入下会直接打满集群）；
> - MV 本身占存储，多层 MV 存储成本成倍；
> - MV 刷新产生新数据版本，**加剧 compaction 压力**（见 [[8-运维与调优]]）；
> - MV 有刷新延迟，报表可能读到旧值；
> - **命中是有条件的**（列覆盖、聚合可上卷、CBO 认为划算），ad-hoc 查询基本命不中。
>
> 所以我的判断标准是：**查询模式稳定 + 查询频率高 + 基表数据量大**，这三个同时满足才建 MV；否则先用好分区裁剪和索引。
