# 📐 三、表设计

> 本篇回答一个很具体的问题：**拿到一个业务需求，怎么一步步设计出一张正确的 Doris 表**——模型怎么选、key 怎么排、分区和分桶怎么定、索引加不加、副本给几个，以及哪些看起来合理的设计会在半年后变成事故。

## 一、表设计的总流程

### 1.1 为什么"表设计"值得单独一篇

因为**表设计是 Doris 上唯一一件"改起来代价极高"的事**：

| 变更 | 代价 |
| --- | --- |
| 加一个普通列 | 轻量级 schema change，通常可在线完成 |
| 改列类型（部分兼容） | 轻量级或重量级，看兼容性 |
| 改排序键 / 改模型 | 基本等于**重建表 + 重灌数据** |
| **改分桶数** | 官方手册明确：**分桶数一旦指定就不能修改**；对存量分区改分布要触发数据重分布 |
| 改分区粒度（天 → 月） | 重建分区 + 重灌 |

写入 SQL 写错了改一行就好，表结构设计错了可能要重灌 TB 级数据。所以表设计值得"设计前慢一点"。

### 1.2 八步设计流程

```text
① 明确查询模式     点查？范围扫描？聚合？明细导出？各占比多少？
        ↓
② 评估数据量与增长  现在多少行/多大、日增多少、要保留多久、增长斜率
        ↓
③ 选数据模型        Duplicate / Unique(MoW) / Aggregate   ← [[2-数据模型]]
        ↓
④ 选 KEY 与排序键   最常用的过滤维度 + 前缀索引最左前缀 + 分区列约束
        ↓
⑤ 选分区与分桶      分区切时间、分桶散数据；两者正交，配合使用
        ↓
⑥ 选索引           Bloom Filter → Bitmap → 倒排，按"便宜的先上"排序
        ↓
⑦ 定副本与属性       replication_num / storage_medium / MoW / 持久化索引
        ↓
⑧ 压测验证         造真实数据量 + 真实 SQL，看 EXPLAIN、扫描量、延迟
```

> [!tip] 第 ① 步是整条流程的地基
> 90% 的表设计错误，根源不是"不懂 Doris"，而是**没把查询模式问清楚**。设计前至少要能回答：
> - 这张表上跑得最多的 **3 条 SQL** 长什么样？（不是"大概会查"，是写出真实 SQL）
> - 是**点查**（`WHERE 主键 = ?`）多，还是**范围聚合**（`WHERE dt BETWEEN ? AND ? GROUP BY ...`）多？
> - 查询**并发高不高**？（高并发点查 vs 少数大报表，对分桶策略的要求相反）
> - 有没有**必须支持但现在还没提**的下钻维度？（决定了 Aggregate 的 key 要不要做宽）
>
> 问不出这三条 SQL 就别急着建表。最省事的兜底是：**先从明细模型（Duplicate/Unique）起步**，因为它保留了全部信息，后面加物化视图或改用例都还有退路。

### 1.3 一张速查：设计决策的因果链

| 你的选择 | 直接影响 | 间接影响 |
| --- | --- | --- |
| KEY 列顺序 | 前缀索引能否命中 | 查询扫描量 → 延迟 → 集群负载 |
| 分区列及粒度 | 分区裁剪效果 | FE 元数据量、导入延迟、compaction 并发 |
| 分桶数 | 单 tablet 大小、并行度 | tablet 总数 → FE 元数据、导入事务、扩容能力 |
| 分桶列 | 数据是否倾斜、点查扫几个桶 | JOIN 能否做 bucket shuffle 本地化 |
| 模型 | 存储语义正确性 | 写入/读取代价、是否可部分列更新 |
| 索引 | 过滤阶段能跳过多少数据 | 写入放大、磁盘占用、compaction 压力 |
| 副本数 | 容灾能力 | 存储成本 ×N、写入网络开销 ×N |

## 二、KEY 与排序键的设计

### 2.1 三条硬约束（先把红线划出来）

在谈"怎么排最好"之前，有几条 Doris 强加的约束，违反就直接建表失败：

> [!warning] KEY 设计的三条硬约束
> 1. **KEY 列必须排在所有普通列之前**（schema 顺序 == 声明顺序）。
> 2. **分区列必须是 KEY 列**；多列分区时，分区列的顺序要与它在 KEY 中的顺序一致。
> 3. **分桶列在 Aggregate / Unique 模型下必须是 KEY 列**；只有 Duplicate 模型允许用非 KEY 列做分桶列。
>
> 这三条叠在一起意味着一个很常见的结果：**你用 `dt` 做分区，`dt` 就必然占据排序键的第一位。** 于是"按 `order_id` 点查"天然吃不到前缀索引——这是设计时必须正面处理的问题，而不是建完表才发现。

### 2.2 排序原则：把最常用的过滤字段放最前面

前缀索引是**最左前缀**的（仅取排序键最左的连续若干列，累计长度约 36 字节，机制见 [[2-数据模型]] 第七节）。所以：

**原则一：把"几乎每条 SQL 都会带"的字段放第一位。** 在实践中这通常是**时间/分区列**——因为分区裁剪也依赖它，一份收益吃两次。

**原则二：在满足原则一的前提下，把选择性高（能过滤掉更多数据）的字段往前放。**

**原则三：不要为了"点查好看"把高基数随机列（UUID、session_id）放第一位。** 它会让前缀索引失去块内选择性，还会破坏其他列的物理聚集性（ZoneMap 失效）。

### 2.3 一个具体对比：`(dt, order_id)` vs `(order_id, dt)`

假设订单表，两类查询：

```sql
-- Q1：运营报表，按日期范围 + 状态过滤
SELECT order_status, count(*), sum(pay_amount)
FROM dim_order
WHERE dt BETWEEN '2026-10-01' AND '2026-10-09' AND order_status = 3
GROUP BY order_status;

-- Q2：接口点查，按订单号取整行
SELECT * FROM dim_order WHERE order_id = 202610090001;
```

| KEY 设计 | Q1（范围聚合） | Q2（点查） |
| --- | --- | --- |
| `UNIQUE KEY(dt, order_id)` | ✅ 分区裁剪 + 前缀索引命中 `dt`，只扫 9 个分区 | ⚠️ 前缀断裂，用不上前缀索引；靠 **Bloom Filter** 在各分区内跳过数据块。若 Q2 不带 `dt`，**所有分区都要扫一遍**（每个分区都被 Bloom Filter 过一遍） |
| `UNIQUE KEY(order_id, dt)` | ❌ `dt` 不在最左，前缀索引失效；**且分区列必须是 KEY 列且顺序一致 → 想用 `dt` 分区就得把 `dt` 放前面**，所以这个设计实际上要么不能按 `dt` 分区，要么行不通 | ✅ 前缀索引直接定位 |

**结论与解法**（这是真实项目里必须做的取舍）：

1. **优先选 `(dt, order_id)`**，并要求点查 SQL **尽量带上时间范围**（例如"最近 90 天"）。绝大多数订单点查业务本身就有时间上下文（前端页面通常带日期或"我的订单"按时间倒序）。这是成本最低的解法。
2. 如果点查**确实无法带时间**：在 Duplicate 模型上可以用 `ALTER TABLE ... ADD ROLLUP` 复制一份以 `order_id` 为排序键的 rollup；Unique 表对 rollup 的支持有限，通常改用**异步物化视图**或把点查交给 KV/缓存，Doris 只扛分析。
3. 若点查是"取整行"且 QPS 很高，再叠加**行存**（`store_row_column`，见 [[2-数据模型]] 第十节）。
4. 兜底手段是 **Bloom Filter**（`bloom_filter_columns`），它便宜、对高基数列有效，但**只能跳过数据块，不能像前缀索引那样二分定位**，所以它是"缓解"而非"等价替代"。

### 2.4 用 EXPLAIN 验证是否命中前缀索引

设计完不要凭感觉，用 `EXPLAIN` 对比：

```sql
-- 假设排序键是 (dt, order_id)
-- A：命中前缀索引
EXPLAIN SELECT count(*) FROM dim_order WHERE dt = '2026-10-09' AND order_id = 1;

-- B：前缀断裂，只能靠 Bloom Filter / 全分区扫描
EXPLAIN SELECT count(*) FROM dim_order WHERE order_id = 1;

-- C：分区裁剪彻底失效（列上套了函数）
EXPLAIN SELECT count(*) FROM dim_order WHERE date(dt) = '2026-10-09';
```

**怎么读**（定性判断法，比死记字段名更可靠）：

| 观察点 | 含义 |
| --- | --- |
| `partitions` / 扫描的分区数 | 分区裁剪是否生效。C 的写法通常会退化成全部分区 |
| `tabletList` / `tablets` | 命中的 tablet 数量。只扫少量 tablet 才算真正裁剪 |
| 各 ScanNode 的 `rows` / `bytes` 估算 | 扫描量估算；B、C 应明显大于 A |
| `PREDICATES` / `SHORT KEY` 相关信息 | 哪些条件下推到了存储层、哪些只在内存里过滤 |
| `EXPLAIN ANALYZE` 的 `RowsProduced` / 耗时 | 实际扫描行数与真实耗时，最终裁决 |

> [!danger] 最常见的"查询莫名很慢"元凶：条件里给列套了函数
> `WHERE date_format(dt, '%Y-%m-%d') = '2026-10-09'`、`WHERE cast(order_id as varchar) = '123'`、`WHERE dt + interval 1 day = ...` —— 这些写法会让**分区裁剪、前缀索引、ZoneMap 全部失效**，退化成全表扫描。正确写法是把函数套在**常量**上：`WHERE dt = '2026-10-09'`、`WHERE dt >= date_sub(now(), 7)`。
> 这也是为什么表设计要**让分区列和排序键列是与业务查询写法天然对齐的类型**：如果业务天天要按"周"过滤，而库里只有 `DATE`，用 `dt >= '周一起始日' AND dt <= '周日'` 这种闭区间写法，比 `week(dt) = 41` 快几个数量级。

### 2.5 key 里放多少列

| 放太多 key 列 | 放太少 key 列 |
| --- | --- |
| 前缀索引被 36 字节消耗殆尽，后面的列进不来 | 过滤时能用的块级裁剪手段少 |
| 排序开销更大，导入变慢 | Aggregate 表如果漏了维度就只能重刷 |
| 语义上"看起来"更像主键，容易误导使用者以为唯一 | — |

经验：
- **Duplicate**：`KEY` 取 3~5 列足够，通常是「分区列 + 时间列 + 主要过滤维度」。
- **Unique**：`KEY` **就是你业务上的主键**（必须保证 (key) 组合唯一），没法自由取舍——这时排序顺序的让步空间只在"谁排第一"。
- **Aggregate**：`KEY` 就是"聚合维度"，取舍标准是**未来半年可能的下钻维度要不要预留**。多留一列 key 的代价是分组变细、聚合后行数变多；少留一列的代价是**信息永久丢失、要重刷历史**。倾向是**宁可多留一列**（尤其是 `device`、`channel`、`ad_type` 这类常用下钻维度）。

## 三、分区设计

### 3.1 分区解决的问题：分区裁剪

分区是**表的物理子集**。查询条件命中分区列时，Doris 在 FE 侧就把不相关的分区**全部排除**，连 tablet 都不去碰——这是代价最低、收益最大的优化，因为它在"读任何数据之前"就生效了。

```text
表 dwd_user_action_log，按 dt 天分区，保留 90 天 = 90 个分区
查询 WHERE dt = '2026-10-09'
    → 只扫 1 个分区，另外 89 个分区的 tablet 完全不参与调度
```

没有分区裁剪会怎样？一张 5TB 的表，查"今天的数据"要扫 5TB 的元数据并逐个 tablet 判断——**再快的前缀索引也救不了**。

### 3.2 分区粒度怎么选

| 粒度 | 适用 | 风险 |
| --- | --- | --- |
| **按天** | 绝大多数日增明细表、行为日志（业界默认选择） | 保留 3 年 = 1000+ 分区，FE 元数据压力上升 |
| **按月** | 数据量小的表（日增百万行以下）、长周期归档表 | 单分区过大，扫描裁剪粒度粗，重分布/重刷代价高 |
| **按小时** | **极少用**，只有"单日数据量极大且查询必须小时级裁剪"时才考虑 | 分区爆炸：一天 24 个，一年 8760 个，FE 元数据和导入事务会顶不住 |
| **不分区（单分区）** | 小维表（几十万行以内） | 大表这么干等于放弃裁切 |

> [!warning] 分区数量的两个极端都有问题
> **分区太多（按小时 + 保留一年）**：FE 内存里要为每个分区维护元数据（分区 → tablet 映射、版本信息），每次导入要往命中的分区提交事务，分区越多导入的元数据开销越大；`SHOW PARTITIONS` 都会变慢。
> **分区太少（一张大表只有一个分区）**：查询无法裁剪，任何"看最近 7 天"的查询都在全表扫描；删除历史数据也只能整表 truncate。
>
> 判断经验：**分区数量控制在"FE 舒服、裁剪有效"的区间**，日粒度 + 保留 1~2 年是常态；如果要保留 5 年，考虑"近期按天、远期按月经压缩归档"的两级策略，或者用 3.x 的**冷热分层**（`storage_medium` / `storage_cooldown_time`）把老分区下沉到 HDD/对象存储而不是删掉。

### 3.3 动态分区：把"手动建分区"这件事自动化

手写分区定义的问题是**必须提前建**：忘了建明天分区，导入直接报 `no partition for this tuple`。动态分区让 FE 按配置**定期自动创建/删除**分区。

核心属性（逐项含义在 [[4-建表与分区分桶]] 展开）：

| 属性 | 作用 |
| --- | --- |
| `dynamic_partition.enable` | 总开关 |
| `dynamic_partition.time_unit` | `HOUR` / `DAY` / `WEEK` / `MONTH` / `YEAR`，创建**未来**分区的粒度 |
| `dynamic_partition.start` / `end` | 保留窗口（负数表示往前保留多久）与预建到未来多久 |
| `dynamic_partition.prefix` | 分区名前缀，最终形如 `p20261009` |
| `dynamic_partition.buckets` | 新分区的分桶数 |
| `dynamic_partition.create_history_partition` | 是否在启用时**回溯补齐**历史分区 |
| `dynamic_partition.replication_num` | 新分区副本数 |

收益很直接：**新表上线时不用一次性手写几十个分区定义，老数据到期自动清理**。

常见坑（在 [[4-建表与分区分桶]] 有对照表和排查步骤，这里只点风险）：

- **时区**：FE 的时区设置决定"今天"是哪天，跨时区业务/容器时区没设对，会出现"分区名是昨天"或"预建分区不够用"的现象。
- **`start` / `end` 写反**：`start` 是负数（往前），`end` 是正数（往后）。写反了表现为"分区要么不建、要么建到明年"。
- **历史分区没补**：`create_history_partition` 没开的话，动态分区只创建"从现在往后"的分区，历史数据导入直接失败。

### 3.4 分区与分桶的关系（不要混为一谈）

这是初学者最常见的概念混淆：

| 维度 | 分区（Partition） | 分桶（Bucket） |
| --- | --- | --- |
| 切分依据 | **连续值范围**（`RANGE`：时间、数值区间）或枚举（`LIST`） | **哈希取模**（`HASH`）或随机（`RANDOM`） |
| 目的 | **裁剪**：整块跳过不相关的数据 | **打散**：让数据均匀分布、让查询并行 |
| 物理单元 | 一个分区包含 N 个 tablet | 一个分区内每个桶 = 1 个 tablet |
| 能否改 | 可以 `ADD` / `DROP` / `TRUNCATE` 分区 | **分桶数基本不能改** |
| 数量级 | 几十 ~ 几千 | 单分区几个 ~ 几十个 |

> [!important] 一句话记住
> **分区 = 纵向切时间（减少要读的数据），分桶 = 横向切数据（提高并行度、决定点查扫几个 tablet）。**
> `Tablet 总数 = 分区数 × 分桶数`，这个乘积是所有元数据/导入/compaction 开销的基数。

### 3.5 冷热分层：不删数据也能省钱

```sql
ALTER TABLE dwd_user_action_log SET (
    "storage_medium" = "SSD",
    "storage_cooldown_time" = "2026-11-09 00:00:00"
);
```

思路：**热数据留 SSD，到期后自动下沉到更便宜的介质（HDD / 对象存储）**，而不是直接删分区。适合"近 30 天高频查、30 天前偶尔查、1 年后再删"的合规/审计类需求。3.0 起的存算分离架构下，冷数据下沉到对象存储的意义更大（见 [[7-湖仓一体]]）。

## 四、分桶设计

### 4.1 分桶要同时服务三件事

1. **并行度**：tablet 是 Doris 扫描的最小调度单元。分桶太少 → 并行度不够，大查询跑不满集群。
2. **点查效率**：等值条件包含**全部分桶列**时，只需要扫**一个 tablet**。分桶列选得好，高并发点查的 IO 冲突就小。
3. **数据均匀度**：哈希分布是否倾斜，决定了有没有"某个 BE 永远最忙"。

### 4.2 分桶列怎么选

**优先级从高到低：**

1. **高基数、分布均匀、且常用于等值过滤的列**（`order_id`、`user_id`、`ad_id`）。高基数保证哈希后分散得好，避免热点。
2. **常用于 JOIN 的列**。分桶列一致的 Join 有机会做 **bucket shuffle**（只在对应桶之间做 Join，省掉全量 shuffle），这是实打实的性能收益。
3. **在 Aggregate/Unique 模型下，分桶列必须是 KEY 列** —— 这条约束会直接限制你的选择范围。

> [!danger] 绝对不要用这些列做分桶键
> - **低基数列**（`status`、`city`、`is_click`）：只有几个值，哈希后大量数据挤在几个桶里，**必然倾斜**。
> - **UUID / 随机字符串**：看似"高基数很均匀"，但用字符串做哈希的代价高；如果是**有前缀规律**的 id（如 `order_no` 前 8 位是日期），哈希分布其实很差。另外，如果业务查询几乎不带这个列，分桶带来的是纯成本。
> - **自增主键**：某些自增场景（尤其写入集中在一段时间）会导致新数据堆在少数桶，典型表现是"导入时某个 BE 的 IO 打满"。
> - **会被更新的列**：Unique 表用 `update_time` 之类的列做分桶，一条记录更新后可能换桶，产生跨桶的重复，破坏唯一性语义（跨分区分桶的 key 唯一性无法保证）。

### 4.3 分桶数怎么定（最容易被问、也最容易做错）

先把官方手册里的几条硬事实列清楚（这是判断依据，不是经验）：

| 事实 | 含义 |
| --- | --- |
| `Tablet 总数 = 分区数 × 分桶数` | 定分桶数前先想清楚分区数，乘积才是真正的成本 |
| 单 tablet 数据量建议在 **1G ~ 10G** | 太小：聚合效果差、元数据压力大；太大：副本迁移/补副本慢，schema change / rollup 失败重试的粒度是 tablet，越重试越痛 |
| 不考虑扩容时，表的 tablet 总数**略多于集群磁盘总数**为宜 | 让每块盘都有活干，又不过度碎片化 |
| 数据量原则与 tablet 数量原则冲突时，**优先数据量原则** | 即"单 tablet 落在 1~10G"优先于"tablet 数 ≈ 磁盘数" |
| 分桶数**一旦指定基本不能改** | 必须预留扩容空间；分桶数定小了，加机器也提不了并发 |

**落地算法（可照做）：**

```text
1) 估算【单个分区】的压缩后数据量 S
   （日增行数 × 单行压缩后字节数；可用 SHOW DATA 对历史相似表实测）
2) 目标单桶大小 T：取 2~5G（落在 1~10G 区间内，偏中间更稳）
3) 分桶数 ≈ S / T
4) 向上取整到常见取值（2 的幂或 12/16/24/32 这类便于整除的数）
5) 检查：分桶数 × 分区数 是否让 tablet 总数明显大于"集群磁盘数"；
   检查单桶是否 *远小于* 1G（说明该用月分区或减少分桶）
6) 预留扩容：如果预计 1 年内数据量会涨 3 倍，分桶数可以直接按涨 3 倍定
```

**官方手册给的量级参考**（可以直接用来做数量级校验）：

| 单表/单分区数据量 | 分桶数量级 |
| --- | --- |
| 几百 MB | 4 ~ 8 |
| 5 GB 左右 | 8 ~ 16 |
| 50 GB 左右 | 32 |
| 500 GB 及以上 | **先分区**，让单分区约 50GB，每分区 16 ~ 32 个桶 |

> [!warning] 分桶数过多是最常见的"自作聪明"
> **症状**：表建了 200 个桶，单桶只有几十 MB。表现为：导入变慢（事务要操作大量 tablet）、compaction 任务数量爆炸（每个 tablet 都要 compact）、FE 元数据压力大、查询反而更慢（调度开销 > 扫描收益）。
> **判断方法**：`SHOW DATA FROM tbl` 拿到表大小，**除以副本数**得到真实数据量，再除以 `分区数 × 分桶数`，看单 tablet 是否远小于 1G。是 → 桶开多了。
> **例外**：新表刚上线时单 tablet 必然很小（没数据），这时看**预期**而不是当前值。

### 4.4 分桶数与"点查 vs 吞吐"的反直觉取舍

官方手册里有一条非常容易答错的取舍，值得单独记：

| 分桶列的选择 | 数据分布 | 点查行为 | 适合 |
| --- | --- | --- | --- |
| **多列**做分桶列 | 更均匀 | 查询只带部分桶列时，**要同时扫所有桶** | **高吞吐、低并发**（大报表） |
| **单列/少列**做分桶列 | 略粗 | 点查能精准落到**一个桶** | **高并发点查**（接口查询） |

> [!important] 面试常问："分桶是不是越多越好、列越多越好？"
> **不是。** 分桶列多、桶多 → 分布更均匀、并行度更高，但**点查会触发全桶扫描**，并发高时 IO 冲突严重。反之，分桶列少、桶少 → 点查精准落一个桶，并发友好，但大数据量下的并行吞吐会受限。**这是一个"吞吐 vs 并发"的取舍，取决于你的主要查询形态。**

### 4.5 `RANDOM` 分布与 `load_to_single_tablet`

如果没有明确的等值点查需求，Doris 也支持**随机分布**：

- **收益**：彻底规避数据倾斜（每批导入随机选 tablet 写）。
- **代价**：没有分桶列，查询**无法只扫部分桶**，任何查询都会扫命中分区的全部桶。适合"整表聚合分析"，**不适合高并发点查**。
- **配套技巧**：随机分布下导入时可以开 `load_to_single_tablet`（单 tablet 导入模式），一次导入只往一个 tablet 写，显著降低导入和 compaction 的写放大，提升导入吞吐与集群稳定性。这是**日志类大表**很实用的组合。

### 4.6 数据倾斜怎么发现与治理

| 发现手段 | 看什么 |
| --- | --- |
| `SHOW DATA FROM tbl` | 表/分区整体大小与行数 |
| `SHOW TABLETS FROM tbl` | **逐 tablet 的行数/大小**，直接看出哪个桶异常大 |
| BE 监控 / `SHOW BACKENDS` | 各 BE 的磁盘使用率、`DataSize`；某台明显高于其他 = 倾斜 |
| 导入监控 | 单个 BE 的 IO/CPU 持续打满，其他空闲 |
| 查询 profile | 某个 ScanNode 的耗时远高于同名其他实例 |

治理手段（按代价从低到高）：

1. **换分桶列**（如果还没上线，直接改设计）。换成基数更高、分布更均匀的列。
2. **加一列组合哈希**：`DISTRIBUTED BY HASH(user_id, city)`，用组合键稀释单一列的不均匀。
3. **改用 `RANDOM` 分布**（放弃点查精度换均匀度）+ `load_to_single_tablet`。
4. **换分桶数**：注意这可能要重建表/重分布，代价高。
5. **业务侧打散**：对极端热点 key（例如某个爬虫的固定 user_id）在上游加随机后缀再散列——这是最后手段，会破坏该 key 的等值定位能力。

## 五、副本与高可用

### 5.1 `replication_num` 怎么选

| 取值 | 场景 | 说明 |
| --- | --- | --- |
| `3` | **生产默认** | 容忍 1 台 BE 宕机仍可读写；`replication_allocation` 可替代写法 |
| `2` | 资源紧张的准生产 | 容忍 1 台宕机，但补副本窗口更窄；不推荐长期使用 |
| `1` | **单机测试 / Docker 体验 / 极不重要的临时表** | 单副本，BE 挂了数据就不可用 |

> [!danger] 生产环境 `replication_num=1` 意味着什么
> 那颗 tablet 只有一份。对应 BE 宕机/磁盘故障 → **这个 tablet 上的数据直接不可用**，查询报错；如果该 BE 的磁盘彻底损坏，数据**永久丢失**（没有第二个副本可以恢复）。
> 反过来说：**测试环境用 3 副本是纯浪费**（3 倍存储 + 3 倍写入网络开销），本地开发就该用 1。建表模板要按环境区分，别把测试配置带上生产。

### 5.2 副本的写入与修复代价

- 写入时，**每个副本都要写**，还要多数派确认才算成功。副本数从 1 提到 3，写入的网络与磁盘开销大致按副本数放大，导入延迟也会受影响（要等多数副本 ack）。
- 某个 BE 下线后，FE 会为该 BE 上的 tablet 触发**副本修复（replica repair）**，从其他副本拉数据补齐。修复是后台任务，会抢 IO/网络；大表 + 大量 tablet + 少的副本数会让修复窗口很长。
- 判断副本健康度：

```sql
-- 表级副本状态：看有无 unhealthy / 缺失副本
ADMIN SHOW REPLICA STATUS FROM dwd_user_action_log;

-- 查看各 tablet 的副本分布
SHOW TABLETS FROM dwd_user_action_log;

-- 查看 BE 节点状态与磁盘容量
SHOW BACKENDS;
```

### 5.3 机架感知与标签（`tag`）简述

副本全落在同一个机架/同一台物理机，等于"高可用只是纸面上的"——机架断电一次全丢。Doris 用**标签（tag）+ `replication_allocation`** 做位置感知：

```sql
-- 按标签数量指定副本分布（示意：默认标签下 3 副本）
ALTER TABLE dwd_user_action_log SET (
    "replication_allocation" = "tag.location.default:3"
);
```

| 概念 | 作用 |
| --- | --- |
| `tag.location.*` | 给 BE 打位置标签（机房、机架、磁盘类型） |
| `replication_allocation` | 按标签描述"每个标签下要几份副本"，比单纯的 `replication_num` 表达力强 |
| 多机房部署 | 用不同 location 标签做"同城两机房各一份 + 本地一份"这类布局 |

> [!note] 单机架/单机房的小集群
> 不必强行上标签体系；重点是**至少 3 个 BE 节点且分布在不同物理机**。真正的机架感知需要基础设施配合（给 BE 打标签），属于运维范畴，细节见 [[8-运维与调优]]。

### 5.4 存算分离下的副本

3.0 起支持**计算存储分离**（云原生模式）：数据放在共享存储（对象存储/HDFS）上，BE 变成无状态的计算节点，副本管理由共享存储自己负责，可以做到更低成本与秒级弹性。这时 `replication_num` 的语义与本地模式不同（通常是 1 份共享数据 + 本地缓存）。选型讨论放在 [[9-对比StarRocks与ClickHouse]]、湖仓场景见 [[7-湖仓一体]]。

## 六、索引设计

### 6.1 先想清楚"加索引是在买什么"

| 索引 | 买到的能力 | 付的成本 |
| --- | --- | --- |
| 前缀索引 | 排序键最左前缀的块级定位 | **免费**（自动维护） |
| ZoneMap | 任意列的 min/max 区间裁剪 | **免费**（自动维护，收益取决于列的局部聚集性） |
| **Bloom Filter** | 高基数列的等值/`IN` 过滤（块级跳过） | 极低（一小份位图）；对范围查询和 `LIKE` 无效 |
| **Bitmap 索引** | 低基数枚举列的等值过滤 | 低（低基数时）；高基数列会膨胀 |
| **倒排索引** | 等值、`IN`、全文检索、多条件交并 | **高**（写入放大 + 磁盘占用） |
| **NGRAM_BF** | `LIKE '%xx%'` 子串匹配 | 中（写入开销，可能误判） |
| **行存（`store_row_column`）** | 主键点查整行读取 | 高（双份存储 + 更重的写入/compaction） |

> [!tip] 加索引的推荐顺序
> **免费的先用满（前缀索引 + 分区分桶）→ 便宜的补上（Bloom Filter）→ 再考虑 Bitmap → 最后才为确有收益的列单独加倒排索引。**
> 每一步都要有证据：`EXPLAIN`/profile 显示某列的过滤阶段实际跳过了大量数据，才值得为它加索引。**不要"看到字符串列就加倒排"**。

### 6.2 判断该不该加

| 问题 | 该加什么 |
| --- | --- |
| 查询是 `WHERE 高基数列 = ?` 或 `IN (...)`，且该列不在排序键前缀里 | **Bloom Filter**（`bloom_filter_columns`） |
| 查询是 `WHERE 低基数列 = ?`（状态、城市、渠道） | **Bitmap 索引** |
| 查询是全文检索 / 多条件组合过滤 / 中文分词匹配 | **倒排索引**（配分词器） |
| 查询是 `LIKE '%关键词%'` | **NGRAM_BF 索引** |
| 查询是时间/数值**范围** | **不需要额外索引**，靠分区裁剪 + 前缀索引 + ZoneMap |
| 查询是 `WHERE 主键 = ?` 且 `SELECT *` | 考虑**行存**（但先评估存储成本） |

### 6.3 索引的运维现实

- 加索引会触发一次**异步 schema change**为存量数据补建，大表上耗时可能很长，期间有额外的 IO/CPU 开销（进度查看见 [[4-建表与分区分桶]]）。
- 倒排索引会**显著加重导入与 compaction 负担**，并且**索引本身也占磁盘**。给一张日增 10 亿行的日志表加 5 个倒排索引，导入吞吐可能明显下降。上线前务必用真实数据量压测。
- 索引加错了要能回退：`DROP INDEX` 是必须提前想好的动作。

## 七、常见表设计反模式

这张表建议对照检查自己的每一张表：

| # | 反模式 | 后果 | 正解 |
| --- | --- | --- | --- |
| 1 | 用 `DUPLICATE KEY` 却以为会去重 | CDC/重放场景**数据静默翻倍**，报表对不上，排查极其痛苦 | 需要唯一性就用 `UNIQUE KEY`；只能排序需求才用 Duplicate |
| 2 | 用 Aggregate 模型但业务其实要查明细 | 明细永远查不到；想加维度要**重刷全量历史** | 明细保留 Duplicate/Unique，聚合交给 Rollup/物化视图 |
| 3 | Unique 表不开 MoW | 读时合并 → Rowset 越堆越多，查询持续退化；且**不支持部分列更新** | 显式 `enable_unique_key_merge_on_write=true` |
| 4 | 分桶数过多（单桶远小于 1G） | 小文件/小 tablet 遍地，导入慢、compaction 任务爆炸、FE 元数据压力大 | 按"单 tablet 1~10G"反推分桶数，数据量原则优先 |
| 5 | 分区粒度过细（按小时） | 分区数爆炸：一天 24 个，一年 8760 个 → FE 元数据与导入事务顶不住 | 默认按天；只有单日数据量极大且必须小时裁剪才按小时 |
| 6 | 全表只有一个大分区 | **无法裁剪**，查"最近 7 天"等于全表扫描 | 按时间 Range 分区 + 动态分区 |
| 7 | 用高基数 UUID/字符串做分桶键 | 分布差（前缀有规律）→ 倾斜；点查也用不上（查询不带该列） | 选**高基数 + 分布均匀 + 常用于等值过滤/JOIN** 的列 |
| 8 | `VARCHAR(65533)` 一把梭 | 前缀索引被单列吃满，后面的列全进不来；过滤无块级裁剪能力；内存估算失真 | 按实际长度给；超长文本用 `STRING`，**不要进排序键** |
| 9 | 忘记 Bloom Filter，点查慢 | 排序键前缀断裂的列只能全分区扫描 | 给点查列配 `bloom_filter_columns`（便宜且有效） |
| 10 | 分区列上套函数查询 | 分区裁剪 + 前缀索引 + ZoneMap **全部失效** | 把函数套在常量上：`dt >= date_sub(now(),7)` |
| 11 | 生产用 `replication_num=1` | BE 故障即数据不可用，磁盘坏即**永久丢数据** | 生产 3 副本；1 副本只用于本地/测试 |
| 12 | 用会被更新的列做分区键（CDC 表） | 同一主键跑到多个分区，**跨分区重复** | 分区键选**不变**的业务时间（如下单时间、事件时间） |
| 13 | 给所有字符串列加倒排索引 | 导入吞吐下降、磁盘膨胀、compaction 压力翻倍 | 先 Bloom Filter，再用 profile 证明收益后逐个加 |
| 14 | Aggregate 表的过滤条件落在非 key 列 | 语义错误：聚合后的行无法判断是否包含某明细值 | 过滤条件只落在 key 列；需要按该列过滤就把它加进 key |
| 15 | 大表不分区却按时间查 | 每次查询全表扫 | 时间字段一定做分区列 |
| 16 | 把 `dt` 写成 `VARCHAR` 做分区列 | 分区边界比较、裁剪、函数处理都更容易出错或低效 | 用 `DATE`/`DATEV2`/`DATETIME` |

> [!danger] 反模式 1 的现场诊断流程（值得背下来）
> 报表数突然变成预期的 2~3 倍 → 怀疑重复：
> 1. `SELECT order_id, count(*) c FROM tbl GROUP BY order_id HAVING c > 1 LIMIT 10;` 确认是否真有重复；
> 2. 有重复 → `SHOW CREATE TABLE tbl;` 看模型。是 `DUPLICATE KEY` → 根因确认；
> 3. 检查上游：Flink 作业的 checkpoint/重启是否造成重放（[[6-数据导入与FlinkCDC]]）、Kafka 是否重复投递；
> 4. 修复：重建为 `UNIQUE KEY` + MoW 表并重灌（Doris 不支持直接改模型，只能重建）。

## 八、从业务到建表：三个完整实例

以下每个例子都按「**查询模式 → 模型 → KEY → 分区/分桶 → 索引 → 属性 → 结论与权衡**」走一遍。SQL 细节（分区边界写法等）见 [[4-建表与分区分桶]]。

### 8.1 实例一：订单实时明细 + 按订单号点查

**业务背景**：订单库通过 Flink CDC 同步到 Doris（链路见 [[6-数据导入与FlinkCDC]]）；运营看订单报表，同时有一个内部接口按订单号查订单详情。

**查询模式**：

| 查询 | 形态 | 占比估计 |
| --- | --- | --- |
| Q1 运营报表 | `WHERE dt BETWEEN ? AND ? AND order_status = ? GROUP BY ...` | 高 |
| Q2 订单详情接口 | `SELECT * FROM t WHERE order_id = ?` | 中（并发高） |
| Q3 用户订单列表 | `WHERE user_id = ? AND dt >= ? ORDER BY dt DESC` | 中 |

**设计决策**：

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 模型 | **Unique (MoW)** | 订单状态会变（待支付→已支付→已发货），CDC 会重复投递同一 `order_id`；Unique 天然接住"同主键覆盖" |
| KEY | `UNIQUE KEY(dt, order_id, user_id)` | `dt` 必须第一（分区列约束）；`order_id` 保证唯一性语义完整；`user_id` 放第三位服务 Q3（`dt` + `user_id` 时至少第一列命中前缀索引） |
| 分区 | `PARTITION BY RANGE(dt)` + 动态分区（天粒度，保留 90 天，预建 3 天） | 报表按天/区间查 → 分区裁剪；90 天覆盖绝大多数运营需求 |
| 分桶 | `DISTRIBUTED BY HASH(order_id) BUCKETS 32` | `order_id` 高基数、分布均匀、Q2 点查可精准落一个桶；32 个桶对应日增数据量的量级（按单桶 1~10G 反推） |
| 索引 | `bloom_filter_columns = "order_id,user_id"` | Q2/Q3 的列不在前缀索引最左，用 Bloom Filter 做块级跳过；成本极低 |
| 行存 | 先不开，Q2 的 P99 若不达标再开 | 行存要双份存储，先用 Bloom Filter + 分区裁剪验证够不够 |
| 属性 | `replication_num=3`、MoW、`enable_persistent_index=true`、`light_schema_change=true` | 3 副本保命；MoW 保读性能 + 支持部分列更新；持久化索引省内存（订单表 key 多，索引大） |

```sql
CREATE TABLE IF NOT EXISTS dim_order (
    `dt`           DATE          NOT NULL COMMENT '下单日期(分区列,不可变)',
    `order_id`     BIGINT        NOT NULL COMMENT '订单号',
    `user_id`      BIGINT        NOT NULL COMMENT '用户 id',
    `order_status` TINYINT                COMMENT '订单状态',
    `pay_amount`   DECIMAL(18, 2)         COMMENT '支付金额',
    `pay_time`     DATETIME               COMMENT '支付时间',
    `update_time`  DATETIME               COMMENT '业务更新时间'
)
ENGINE=OLAP
UNIQUE KEY(`dt`, `order_id`, `user_id`)
COMMENT '订单详情(CDC 同步)'
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`order_id`) BUCKETS 32
PROPERTIES (
    "replication_num" = "3",
    "enable_unique_key_merge_on_write" = "true",
    "enable_persistent_index" = "true",
    "light_schema_change" = "true",
    "bloom_filter_columns" = "order_id,user_id",
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-90",
    "dynamic_partition.end" = "3",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.buckets" = "32",
    "dynamic_partition.replication_num" = "3"
);
```

**结论与权衡**：

- **最大风险是"Q2 不带 `dt`"**。设计上 `dt` 抢占排序键第一位是分区约束逼出来的，代价是 Q2 无法用前缀索引，只能靠 Bloom Filter 在每个分区内跳块——如果保留 90 天分区，Q2 要过 90 个分区。**缓解**：接口层强制带时间范围（"近 90 天订单"），或把 Q2 的整行读取交给行存/缓存。
- **必须守住的一条纪律**：分区列用**下单日期**而不是 `update_time` 的日期。否则订单每天更新就跑一个新分区，同一 `order_id` 跨分区重复（跨分区不保证唯一）。
- **部分列更新**：状态变更这类高频小更新用 `partial_columns` 只更新 `order_status`/`update_time`，避免整行覆盖时把其他列写坏（用法见 [[6-数据导入与FlinkCDC]]）。

### 8.2 实例二：用户行为日志明细 + 按时间范围聚合

**业务背景**：App 埋点日志经 Kafka → Flink 落 Doris。产品要按天/小时看 PV/UV、按事件类型和页面下钻，偶尔要查某个用户的行为序列。

**查询模式**：

| 查询 | 形态 |
| --- | --- |
| Q1 大盘 | `WHERE dt = ? GROUP BY event` → PV/UV |
| Q2 页面下钻 | `WHERE dt BETWEEN ? AND ? AND page_id = ? GROUP BY event` |
| Q3 用户行为序列 | `WHERE user_id = ? AND dt = ? ORDER BY log_time` |
| Q4 事件类型多选过滤 | `WHERE dt = ? AND event IN (...)` |

**设计决策**：

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 模型 | **Duplicate** | 埋点日志要**保留每一次发生**，不能去重（同一用户可能重复触发同一事件）；也不要聚合（聚合掉 `page_id` 就没法下钻） |
| KEY | `DUPLICATE KEY(dt, log_time, user_id, event)` | `dt` 第一（分区约束）；`log_time` 第二让"时间范围扫描"和 `ORDER BY` 都能利用有序性；`user_id` 服务 Q3；`event` 是低基数列放最后 |
| 分区 | 按天 + 动态分区，保留 180 天 | 日志表分区裁剪是主要优化手段，必须按天 |
| 分桶 | `DISTRIBUTED BY HASH(user_id) BUCKETS 48` | 日志量最大，桶要够多保证并行度；`user_id` 高基数、分布均匀，Q3 只扫一个桶；同时为将来与用户维表 JOIN 留 bucket shuffle 的可能 |
| 索引 | `bloom_filter_columns = "user_id"` + `page_id` 上倒排（中文/长字符串则看情况） | Q3 的 `user_id` 不在前缀最左（`dt` 之后是 `log_time`），Bloom Filter 便宜有效；Q4/Q2 的 `event`/`page_id` 等值过滤可考虑 Bitmap（`event` 低基数）或倒排（`page_id` 多值） |
| 属性 | 3 副本、冷热分层（热 30 天 SSD，之后下沉）、`compression` 可选更高压缩比 | 日志是**只追加、不更新**的，压缩比高；保留 180 天存储成本大，用冷热分层换成本 |

```sql
CREATE TABLE IF NOT EXISTS dwd_user_action_log (
    `dt`          DATE         NOT NULL COMMENT '事件日期',
    `log_time`    DATETIME(3)  NOT NULL COMMENT '事件时间(毫秒)',
    `user_id`     BIGINT       NOT NULL COMMENT '用户 id',
    `event`       VARCHAR(32)  NOT NULL COMMENT '事件类型',
    `page_id`     VARCHAR(64)           COMMENT '页面 id',
    `device`      VARCHAR(32)           COMMENT '设备型号',
    `duration_ms` INT                   COMMENT '停留时长(ms)',
    `props`       VARIANT               COMMENT '扩展属性(半结构化)',
    INDEX idx_event (`event`) USING BITMAP,
    INDEX idx_page (`page_id`) USING INVERTED
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `log_time`, `user_id`, `event`)
COMMENT 'App 埋点行为日志'
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`user_id`) BUCKETS 48
PROPERTIES (
    "replication_num" = "3",
    "bloom_filter_columns" = "user_id",
    "storage_medium" = "SSD",
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-180",
    "dynamic_partition.end" = "3",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.buckets" = "48"
);
```

**结论与权衡**：

- **Q1/Q2 的 PV/UV 不该直接查这张明细表**：日增上亿行时，`count(distinct user_id)` 每次全扫分区，成本高且慢。正确做法是在上面叠一层 **DWS 聚合表**（Aggregate 模型 + `BITMAP_UNION`）或**异步物化视图**，明细表只服务"要细节"的查询。分层思路见 [[6-数据导入与FlinkCDC]]，MV 见 [[5-查询优化]]。
- **`props` 用 `VARIANT` 而不是 `VARCHAR(65533)`**：埋点扩展字段的 key 会不断新增，`VARIANT` 能自动展开子列并支持子字段过滤；用巨型 `VARCHAR` 则每次都要解析 JSON 且完全没有裁剪能力。但注意 `VARIANT` **不要放排序键**。
- **`event` 用 Bitmap 而不是倒排**：`event` 是低基数枚举，Bitmap 更省；`page_id` 基数较高且可能做模糊匹配，倒排更合适。**索引不是越多越好**——上线前一定要压测导入吞吐。

### 8.3 实例三：广告点击指标预聚合

**业务背景**：广告投放看板，展示每个广告位按天/城市/设备的曝光、点击、消耗、CTR、UV。查询量极大（BI 每 5 分钟刷新），几乎不看明细。

**查询模式**：

| 查询 | 形态 |
| --- | --- |
| Q1 广告维度报表 | `WHERE dt BETWEEN ? AND ? GROUP BY ad_id` |
| Q2 城市/设备下钻 | `GROUP BY ad_id, city, device` |
| Q3 大盘趋势 | `WHERE dt BETWEEN ? AND ? GROUP BY dt` |
| Q4 去重人数 | UV（需要精确去重） |

**设计决策**：

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 模型 | **Aggregate** | 指标口径已冻结（曝光/点击/消耗/UV），查询 QPS 高，预聚合收益是数量级的 |
| KEY | `AGGREGATE KEY(dt, ad_id, city, device, channel)` | **刻意做宽**：`city`/`device`/`channel` 都是已知的高频下钻维度，聚合掉就回不来了。`dt` 第一（分区约束） |
| 聚合函数 | `show_cnt`/`click_cnt`/`cost` 用 `SUM`；`uv` 用 `BITMAP_UNION`；首末时间用 `MIN`/`MAX` | UV 要精确 → `BITMAP_UNION`（比 `count(distinct)` 便宜且可增量合并）；`HLL_UNION` 更省空间但有误差，看口径能否接受 |
| 分区 | 按月分区，保留 3 年 | 聚合后单分区行数少（不再是明细量级），月分区足够裁剪，且分区数可控（36 个而不是 1095 个） |
| 分桶 | `DISTRIBUTED BY HASH(ad_id) BUCKETS 16` | 聚合后数据量小，桶数不必多；`ad_id` 分布均匀。分桶列必须是 KEY 列 —— 满足 |
| 索引 | 基本不需要额外索引 | key 全是等值/范围过滤且都在排序键前缀里，前缀索引 + 分区裁剪已足够；`BITMAP` 列不要加额外索引 |
| 属性 | 3 副本；如需更长保留期配冷热分层 | — |

```sql
CREATE TABLE IF NOT EXISTS dws_ad_click_1d (
    `dt`        DATE          NOT NULL COMMENT '统计日期',
    `ad_id`     BIGINT        NOT NULL COMMENT '广告 id',
    `city`      VARCHAR(32)   NOT NULL COMMENT '城市',
    `device`    VARCHAR(32)   NOT NULL COMMENT '设备类型',
    `channel`   VARCHAR(32)   NOT NULL COMMENT '渠道',
    `show_cnt`  BIGINT        SUM DEFAULT "0"       COMMENT '曝光次数',
    `click_cnt` BIGINT        SUM DEFAULT "0"       COMMENT '点击次数',
    `cost`      DECIMAL(18,2) SUM DEFAULT "0.00"    COMMENT '消耗金额',
    `uv`        BITMAP        BITMAP_UNION          COMMENT '去重用户数',
    `first_time` DATETIME     MIN                   COMMENT '首次曝光时间',
    `last_time`  DATETIME     MAX                   COMMENT '末次曝光时间'
)
ENGINE=OLAP
AGGREGATE KEY(`dt`, `ad_id`, `city`, `device`, `channel`)
COMMENT '广告点击日汇总'
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`ad_id`) BUCKETS 16
PROPERTIES (
    "replication_num" = "3",
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "MONTH",
    "dynamic_partition.start" = "-36",
    "dynamic_partition.end" = "1",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.buckets" = "16"
);
```

**结论与权衡**：

- **这个设计成立的前提是"口径冻结"**。如果下个月要加 `ad_type` 维度，Aggregate 表只能回 ODS 重刷。所以上面的 key 里**主动预留了 `channel`**——多一列 key 的代价（行数变多）远小于"重刷历史"的代价。
- **Q4 的 UV 要精确** → `BITMAP_UNION`。如果口径允许误差（例如"活跃用户数"只做趋势看），换 `HLL_UNION` 能显著省空间。
- **绝不能在这张表上写 `WHERE city = 'beijing'` 之外的"非 key 列过滤"语义**，例如"曝光次数大于 100 的广告"——那是聚合结果过滤（`HAVING`），不是行过滤，写错位置会得到错误结果。
- **CTR 这类比率不要存**。存 `SUM(click)` 和 `SUM(show)`，查询时再算 `click/show`。存比率会导致"比率的和"毫无意义（不可加），这是 Aggregate 表最经典的用法错误。

## 九、表设计 Checklist

建表前/评审时逐条过一遍：

**查询与模型**

- [ ] 我能写出这张表上最常用的 **3 条真实 SQL** 吗？
- [ ] 这张表需要**保留每一行原始数据**吗？（需要 → Duplicate；需要按主键覆盖 → Unique；只要指标 → Aggregate）
- [ ] 如果用了 Aggregate：未来半年的下钻维度都进 key 了吗？口径冻结了吗？
- [ ] 如果用了 Unique：开 MoW 了吗？主键索引会不会太大（要不要 `enable_persistent_index`）？
- [ ] 如果用了 Duplicate：我是否**清楚它不去重**，并且确认上游不会重复投递（或有幂等保证）？

**KEY / 排序键**

- [ ] KEY 列都排在普通列前面了吗？
- [ ] 排序键最左列是"几乎所有查询都会带"的字段吗（通常是分区列）？
- [ ] 最长的那条 SQL 的过滤条件从最左开始连续命中吗？断裂的那部分我准备用什么补（Bloom Filter / 行存 / MV）？
- [ ] 有没有把超长字符串或高基数随机列放进 KEY 前部？
- [ ] 用 `EXPLAIN` 验证过扫描量了吗？

**分区**

- [ ] 分区列是 KEY 列且顺序一致吗？是**不会变**的业务时间吗（CDC 表尤其要注意）？
- [ ] 分区粒度按天还是按月？总分区数在可接受范围吗（避免按小时导致分区爆炸）？
- [ ] 开动态分区了吗？`start` 是负数（往前）、`end` 是正数（往后）吗？时区确认了吗？
- [ ] 历史数据回灌需要 `create_history_partition` 吗？
- [ ] 大表是否配了冷热分层而不是一刀切删除？

**分桶**

- [ ] 分桶列是高基数、分布均匀、常用于等值过滤或 JOIN 的列吗？（Aggregate/Unique 下必须是 KEY 列）
- [ ] 分桶列里有没有低基数列、有前缀规律的 id、或会被更新的列？
- [ ] 按"单 tablet 1~10G"反推过桶数吗？预留扩容空间了吗？
- [ ] `分区数 × 分桶数` 这个 tablet 总数在集群磁盘数量的合理倍数内吗？
- [ ] 点查为主（少桶精准命中）还是大报表为主（多桶并行）？分桶列数与查询形态匹配吗？
- [ ] 用 `SHOW TABLETS FROM tbl` 看过实际 tablet 大小、确认不倾斜吗？

**索引**

- [ ] 前缀索引和分区裁剪这两个"免费的"用满了吗？
- [ ] 点查列（不在前缀最左的）加 `bloom_filter_columns` 了吗？
- [ ] 低基数枚举列要不要 Bitmap？全文/多条件过滤要不要倒排（且只为确有收益的列加）？
- [ ] `LIKE '%x%'` 的子串查询考虑过 NGRAM_BF 吗？
- [ ] 加索引前评估过导入吞吐与磁盘的代价吗？

**副本与属性**

- [ ] 生产 `replication_num=3`？（1 副本只允许出现在本地/测试）
- [ ] BE 分布在不同的物理机/机架吗？需要标签体系吗？
- [ ] 字符串长度按实际给了吗？金额用 `DECIMAL` 了吗？日期用 `DATE`/`DATETIME` 而不是 `VARCHAR` 了吗？
- [ ] 扩展字段是否用了 `VARIANT`/`JSONB`，而不是巨型 `VARCHAR`？

**验证**

- [ ] 用**真实数据量**和**真实 SQL** 压测过吗？（小数据量测不出问题）
- [ ] 导入吞吐符合预期吗（尤其加了倒排索引之后）？
- [ ] 主要查询的延迟和扫描量达标吗？`EXPLAIN ANALYZE` 看过了吗？
- [ ] 这张表**怎么删**（分区过期 or 冷热分层）想好了吗？

## 十、必答与自测

> [!important] 必答 1：给你一个业务，你怎么设计表？
> **不要直接开口说 SQL。** 按这个顺序讲，面试官能看出你有没有真的做过：
> 1. **先问查询模式**：这张表上最多的 SQL 是什么？点查、范围扫描、还是聚合？并发高不高？有没有必须支持的下钻维度？——这一步是地基，问不出来就别建表。
> 2. **再估数据量**：现在多少行、日增多少、保留多久、一年后多大。这决定了分区粒度和分桶数量级。
> 3. **选模型**：要保留每次发生 → Duplicate；要按主键保留最新（订单状态、CDC 同步）→ Unique + MoW；只要固定指标且口径冻结 → Aggregate。补充一句"**我通常把聚合层做成派生层，明细永远保留**"，体现工程判断。
> 4. **排 KEY**：分区列必须在 KEY 里且排最前（硬约束），所以通常是 `dt` 第一；然后把最常用的过滤维度按选择性往前放；提醒"前缀索引只吃最左前缀"。
> 5. **定分区**：按天 + 动态分区 + 保留窗口；说明分区裁剪是收益最大的优化；避免按小时导致分区爆炸。
> 6. **定分桶**：分桶列选高基数、分布均匀、常用于等值过滤或 JOIN 的列；分桶数按 **单 tablet 1~10G** 反推，并预留扩容（因为分桶数基本改不了）。
> 7. **加索引**：免费的先满（前缀索引/分区裁剪），再 Bloom Filter，最后才为确有收益的列加倒排；强调索引有写入放大代价。
> 8. **定副本与属性**：生产 3 副本、MoW、持久化索引、字符串长度按实际给、金额用 DECIMAL。
> 9. **最后必须说"压测验证"**：用真实数据量和真实 SQL 跑 `EXPLAIN`/`EXPLAIN ANALYZE`，别靠感觉。

> [!important] 必答 2：分桶数怎么定？
> 分点回答，把依据说清楚：
> - **先算乘积**：`tablet 总数 = 分区数 × 分桶数`。分桶数不能孤立地定，要先确定分区粒度。
> - **按数据量原则**：官方建议**单个 tablet 的数据量在 1G ~ 10G**。所以 `分桶数 ≈ 单分区数据量 ÷ 目标单桶大小(取 2~5G)`。小于 1G 说明桶开多了：导入事务要操作大量 tablet、compaction 任务数量爆炸、FE 元数据压力大，**而且查询不一定更快**。大于 10G 说明桶开少了：副本迁移/补齐慢，schema change/rollup 失败重试粒度是 tablet，代价很高。
> - **按集群规模校验**：不考虑扩容时，表的 tablet 总数**略多于集群磁盘总数**为宜，让每块盘都有活干。**两条原则冲突时，优先数据量原则。**
> - **必须预留扩容**：分桶数**一旦指定基本不能修改**（官方手册明确说明），所以定的时候要考虑未来一两年数据量增长；分桶数定小了，加机器也提不了并发。
> - **别忘分桶列的选择**：分桶列要**高基数、分布均匀、常用于等值过滤或 JOIN**（Aggregate/Unique 下还必须是 KEY 列）。分桶列**多** → 分布更均匀但点查要扫所有桶，适合**高吞吐低并发**；分桶列**少** → 点查精准落一个桶，适合**高并发点查**。低基数列或有前缀规律的 id 会导致倾斜。
> - **量级参考**：几百 MB → 4~8 个桶；5GB → 8~16；50GB → 32；500GB 以上**先分区**，让单分区约 50GB、每分区 16~32 个桶。
> - **落地校验**：`SHOW DATA` 拿到表大小（**除以副本数**才是真实数据量），`SHOW TABLETS` 看单个 tablet 实际大小与倾斜情况。
> 收尾一句加分：**"如果拿不准，我宁愿先用 `BUCKETS AUTO`（配合 `estimate_partition_size`）让 Doris 自动推算，跑一段时间后按实际 tablet 大小再调——但要注意自动分桶的估算基于写入时的信息，不是万能的。"**

> [!question] 自测清单
> 1. 为什么分区列必须放在排序键最前面？由此带来的"点查吃不到前缀索引"你怎么补？
> 2. 一张 CDC 同步的订单表，你会用哪一列做分区键？为什么不能用 `update_time` 的日期？
> 3. 单日 10 亿行日志、保留 1 年。你的分区粒度、分桶数是多少？依据是什么？
> 4. `SHOW DATA` 显示表大小 3TB，副本数 3，日分区 90 个、分桶 64。单 tablet 大概多大？这个设计有问题吗？
> 5. 你用 Aggregate 建了广告表，第二天老板要按 `device` 下钻。你怎么回答、怎么补救？
> 6. 为什么"高并发点查"和"高吞吐大报表"对分桶列数量的要求是相反的？
