## 一、八大必答题

### Q1. Doris 的架构是怎样的？一次查询怎么跑完？

> [!important] 得分骨架
> **FE + BE 两层**：FE 管元数据和查询规划（**Follower 参与选举与元数据写，Observer 只读、扩查询并发**），BE 管存储与计算。
> 数据分布四层：**表 → 分区 → 分桶(tablet) → 副本**。
> 执行链路：FE 解析 → CBO 优化（谓词下推/分区裁剪/Join 选择/Runtime Filter）→ 拆 Fragment 分发 → BE 并行执行（必要时 Shuffle）→ FE 汇总。

**追问：FE 元数据存在哪？**
Doris **自管理元数据**（FE 本地 + BDB JE 日志在 Follower 间同步），**不是存在 MySQL 里**——这是常见误解。因此 FE 必须做高可用（生产至少 3 个 Follower）。

**追问：Observer 有什么用？**
不参与选举、不增加元数据写的一致性开销，但能承担**查询规划和并发**，读多写少的场景加 Observer 性价比很高。

详见 [[1-架构与原理]]。

### Q2. 三种数据模型怎么选？`DUPLICATE KEY` 是唯一约束吗？

> [!important] 得分骨架
> | 模型 | 语义 | 场景 |
> |---|---|---|
> | **Duplicate** | 保留**所有**原始行，不去重不聚合 | 日志、明细、需保留原始数据 |
> | **Unique** | key 唯一，新数据**覆盖**旧数据 | 订单、维表、**CDC 同步** |
> | **Aggregate** | key 相同则按聚合函数合并 | 只要指标的预聚合表 |

**关键澄清**：**`DUPLICATE KEY` 不是唯一约束，它只是排序键**（决定物理排序与前缀索引），Duplicate 模型允许完全相同的多行存在。要唯一必须用 **Unique 模型**。

**追问：Unique 模型不是很慢吗？**
老版本是**读时合并（ROM）**，读时要把多个版本合并，确实慢。**1.2+ 引入 MoW（Merge-on-Write）**，写入时就合并，读时无需合并，性能大幅提升。生产应显式开启 `enable_unique_key_merge_on_write`。

**追问：Unique 模型能只更新部分列吗？**
能，用**部分列更新**（`partial_columns` / 导入时的 `partial_columns=true`），适合"多流写同一张宽表"的场景。

详见 [[2-数据模型]]。

### Q3. 分区和分桶有什么区别？分桶数怎么定？

> [!important] 得分骨架
> - **分区（PARTITION）**：按 RANGE/LIST 切（通常按时间），作用是**数据裁剪**——查询只扫相关分区。
> - **分桶（BUCKET）**：分区内按 `HASH` 切，作用是**数据打散与并行度**，一个分桶在一个分区里就是一个 **tablet**。
> - **tablet 总数 ≈ 分区数 × 分桶数 × 副本数**。

**分桶数怎么定**：按**数据量与单桶大小**估算，让每个桶大小处于合理区间；同时考虑并行度需求。**禁忌**：分桶数给得过大 → 大量小 tablet → 元数据与 Compaction 压力剧增；给得过小 → 并行度不足、单桶过大。

**追问：分桶键怎么选？**
选**高基数、分布均匀**且**常用于 Join** 的字段。高基数避免倾斜，用于 Join 则有机会做 **Colocate Join**（同组分桶键一致 → 零 Shuffle）。

**追问：建表后能改分桶数吗？**
能，但**代价大**（涉及数据重分布），属于重量级变更。**所以建表时就要估准**。

详见 [[3-表设计]]、[[4-建表与分区分桶]]。

### Q4. 一条 SQL 很慢，你怎么排查？

> [!important] 得分骨架（四步）
> 1. **`EXPLAIN` 看计划**：有没有**分区裁剪**？命中**前缀索引**吗？用的哪种 **Join**？有没有不必要的 **Shuffle**？扫描行数是否异常大？
> 2. **`PROFILE` 看真实耗时**：哪个算子最耗时、是否存在**数据倾斜**（某个 instance 行数远超其他）。
> 3. **对照常见反模式**：`SELECT *`（列裁剪失效）、分区列上套函数（裁剪失效）、`OR` 条件、非 colocate 的大表 Join、`COUNT(DISTINCT)` 高基数、没有统计信息导致 CBO 选错计划。
> 4. **对症处理**：改写 SQL、调整分区/分桶、加 Bloom Filter 或倒排索引、上**物化视图**预聚合、用 **Workload Group** 隔离资源。

**最经典的坑（一定要说）**：
```sql
-- ❌ 分区裁剪失效：对分区列做了函数运算
WHERE DATE_FORMAT(dt, '%Y%m%d') = '20261009'

-- ✅ 改成对常量做运算，或直接用分区列比较
WHERE dt = '2026-10-09'
```

详见 [[5-查询优化]]。

### Q5. Doris 有哪几种 Join？怎么优化 Join？

> [!important] 得分骨架
> | Join 方式 | 触发条件 | 特点 |
> |---|---|---|
> | **Broadcast Join** | 一侧表很小 | 小表广播到所有节点，避免大表 Shuffle |
> | **Shuffle Join** | 通用 | 两边按 join key 重分布，**网络开销大** |
> | **Bucket Shuffle Join** | 大表的分桶键 = join key | 只重分布一侧，减少 Shuffle |
> | **Colocate Join** | 两表**同 colocate group、分桶键与分桶数一致** | **本地 Join、零 Shuffle**，最快 |

**优化手段**：① 建表时让常 Join 的表**分桶键一致**以启用 Colocate；② 用 **Runtime Filter** 下推小表过滤；③ 保证**统计信息新鲜**（`ANALYZE TABLE`）让 CBO 选对顺序与方式；④ 大小表 join 尽量走 Broadcast。

**追问：Colocate Join 的前提是什么？**
同一个 **colocate group**、两表**分桶键与分桶数完全一致**、join 条件包含分桶键。这也是"建表时要为 Join 设计"的原因。

详见 [[5-查询优化]]、[[3-表设计]]。

### Q6. Flink 写 Doris 怎么保证不重不丢？

> [!important] 得分骨架（三段式）
> 1. **幂等靠 `label`**：每批数据带一个 label，**同一 label 重复提交被识别为同一事务**，不会写两次。
> 2. **不丢靠攒批 + 重试**：`DorisSink` 的 `sink.buffer-flush.max-rows` / `interval` 攒批，失败重试；配合 Flink **checkpoint** 保证可重放。
> 3. **精确一次靠两阶段提交**：`DeliveryGuarantee.EXACTLY_ONCE` + Doris 的 **2PC**，在 checkpoint 完成后才真正提交，label 保证重复提交幂等。

**关键细节**：
- **label 必须可推导且稳定**（常用 `labelPrefix + 分区/批次信息`）；如果用随机 UUID，幂等就失效了。
- **`max_filter_ratio` 设太大会静默丢数据**（脏数据被过滤掉却不报错），生产要谨慎。
- CDC 场景 sink 表用 **Unique 模型 + MoW**，语义与"主键最新状态"一致。

详见 [[6-数据导入与FlinkCDC]]。

### Q7. 什么是 `-235 too many versions`？怎么治理？

> [!important] 得分骨架
> **成因**：Doris 写入是**追加新版本**，读时合并。**高频小批导入**会让版本数快速堆积，**Compaction 追不上**，导致导入报错（`-235`）、查询变慢。
>
> **治理（治标 → 治本）**：
> | 手段 | 说明 |
> |---|---|
> | **客户端攒批**（治本） | 降低导入频率、增大单批（如 Flink sink 的 flush 间隔/条数） |
> | **调优 Compaction** | 调整 Cumulative/Base Compaction 相关参数与并发 |
> | **监控告警** | 盯 compaction score、tablet 版本数、导入失败率 |
> | **表设计优化** | 减少分桶数（减少 tablet 总数）、按需分区 |
>
> **一句话本质**：`-235` 几乎总是"写得太碎"导致的，**优先改写入方式，而不是只调参数**。

详见 [[8-运维与调优]]。

### Q8. Doris 怎么和数据湖配合？什么数据放 Doris、什么放湖？

> [!important] 得分骨架
> **Doris 提供 External Catalog 做联邦查询**（Hive / Iceberg / Hudi / Paimon / JDBC 等），可以直接查湖上的数据，不必搬进来。
>
> **放 Doris 的**：需要**高并发低延迟**查询、需要**主键更新**、需要**物化视图预聚合**、面向 BI/API 的 **DWS/ADS** 层。
> **放数据湖的**：**海量明细、低成本长期存储**、需要**多引擎共享**、需要**批流统一**与回溯的 **ODS/DWD** 层。
>
> **典型架构**：实时链路写 Doris 供 BI 与 API；明细全量落 Iceberg/Paimon 供离线与回溯；Doris 通过 External Catalog 直接查湖，避免重复搬运。

**追问：存算分离是什么？**
3.0 起支持，把**计算与存储解耦**：数据放共享存储（S3/HDFS），本地做缓存。好处是**弹性扩缩容 + 负载物理隔离 + 成本优化**；代价是远端读延迟与架构复杂度。详见 [[7-湖仓一体]]。

## 二、快问快答

| 问题 | 要点 |
|---|---|
| Doris 是什么类型的数据库？ | **MPP 列式 OLAP**，面向分析型，不适合高频单行事务 |
| FE 的角色？ | Follower（选举+元数据写）/ Observer（只读+扩并发） |
| BE 的角色？ | 数据存储 + 计算执行，tablet 落在 BE |
| tablet 是什么？ | **最小数据分片单位** = 一个分桶在一个分区里的一个副本 |
| 表数据分布几层？ | 表 → 分区 → 分桶(tablet) → 副本 |
| 什么决定前缀索引？ | **排序键（KEY）**，且**最左前缀匹配**（约前 36 字节） |
| Duplicate 模型会去重吗？ | **不会**，保留所有行 |
| Unique 模型怎么选？ | 需要按主键更新/CDC 同步时；**开 MoW** |
| Aggregate 模型限制？ | 聚合不可逆，**查不到明细** |
| ZoneMap 索引是什么？ | 每列 min/max，用于范围过滤 |
| Bloom Filter 用在哪？ | 高基数等值过滤（`bloom_filter_columns`） |
| 分区裁剪何时失效？ | 分区列上套函数/DATE 转换；应用分区列直接比较 |
| 一份数据几个副本？ | `replication_num`（生产常 3） |
| 数据怎么实时进 Doris？ | Kafka→**Routine Load**；Flink→**Doris Connector**（底层 Stream Load） |
| label 的作用？ | 导入事务**幂等标识**，同 label 重复提交视为同一事务 |
| 两阶段提交用在哪？ | Flink 写 Doris 的 `EXACTLY_ONCE`，配合 checkpoint |
| 为什么需要 Compaction？ | 写入产生多版本，读放大；合并以控制读性能 |
| `-235` 是什么？ | 版本堆积过多，多因高频小批导入 |
| 物化视图两类？ | 同步 MV（透明改写）/ 异步 MV（3.x 增强，可跨表/定时刷新） |
| Workload Group 干什么？ | CPU/内存/并发**资源隔离** |
| Doris 能查 Hive 吗？ | 能，External Catalog 联邦查询 |
| 存算分离何时引入？ | **3.0**，4.x 增强 |
| 高并发点查怎么优化？ | MoW + 行存（`store_row_column`）+ 主键等值条件 |
| 数据误删能恢复吗？ | `TRUNCATE` 不可回滚；靠 `BACKUP`/上层重灌，**不要承诺能恢复** |
| Doris 与 StarRocks 什么关系？ | 同源社区，架构相似、能力接近，选型看生态与团队 |
| 为什么不用 ClickHouse？ | 频繁更新、复杂 Join、运维复杂度是主要取舍点 |

## 三、易错陷阱 TOP 10

> [!danger] 这些答错比不答更扣分
> 1. **"`DUPLICATE KEY` 是唯一键"** —— 它只是排序键，不保证唯一。
> 2. **"Unique 模型一定慢"** —— MoW 之后读性能已大幅改善，且是 CDC 场景的标准选择。
> 3. **"分桶越多越快"** —— 分桶过多产生海量小 tablet，拖垮元数据与 Compaction。
> 4. **"分区列可以随便套函数"** —— 会让**分区裁剪失效**，是最常见的性能事故。
> 5. **"label 用 UUID 就行"** —— label 每次都变等于**放弃幂等**，重复提交会写两遍。
> 6. **"`max_filter_ratio` 调大没关系"** —— 脏数据被静默过滤，**会造成丢数据且不报错**。
> 7. **"Doris 元数据存在 MySQL"** —— 错，Doris **自管理元数据**（FE + BDB JE）。
> 8. **"开了 Flink EXACTLY_ONCE 就万无一失"** —— 还需 label 幂等 + 攒批 + 下游表模型匹配。
> 9. **"`-235` 调个参数就好"** —— 根因通常是**写得太碎**，要先改写入方式。
> 10. **"External Catalog 可以当数据仓库用"** —— 它能查湖，但**湖上小文件与远端延迟**会限制性能，关键指标表还是应落 Doris。

## 四、场景设计题

### 4.1 设计一个「MySQL 订单 → 实时看板」的 Doris 表

**答题框架**：
1. **查询模式**：按订单号点查 + 按时间范围做 GMV 聚合。
2. **模型**：**Unique + MoW**（订单会变更状态，需要按主键更新）。
3. **排序键**：`dt, order_id` —— 时间在前便于分区裁剪与范围扫描；或按点查需求调整为 `order_id` 优先。
4. **分区**：按 `dt` **日分区** + **动态分区**（自动建/删历史分区）。
5. **分桶**：`DISTRIBUTED BY HASH(order_id) BUCKETS n`，n 按数据量估算；`order_id` 高基数、分布均匀，且便于与其他表 Colocate。
6. **副本**：`replication_num=3`。
7. **索引**：点查字段加 **Bloom Filter** 或利用前缀索引。
8. **写入**：Flink Doris Connector，**攒批**（如 5～10 秒或 N 行一批）+ **label 幂等** + `EXACTLY_ONCE`。
9. **监控**：compaction score、版本数、导入失败率、查询 P99。

### 4.2 一个 Doris 集群查询越来越慢，怎么排查？

**要点**：
1. **看监控定位面**：是**个别查询**慢还是**整体**慢？整体慢 → 资源/Compaction；个别慢 → SQL/建模。
2. **整体慢**：查 **compaction score**（版本堆积）、BE 内存/磁盘、并发数、是否 OOM；查导入是否变成高频小批。
3. **个别慢**：`EXPLAIN` 看分区裁剪与 Join 方式；`PROFILE` 看算子耗时与倾斜。
4. **建模层面**：分桶数是否合理、是否缺索引、Join 是否可 Colocate、是否该上物化视图。
5. **治理**：攒批写入、调 Compaction、加资源组隔离、必要时扩 BE。

### 4.3 为什么选 Doris 而不是 ClickHouse？

**答题框架（别说"因为 Doris 更好"）**：
- **业务特征**：如果有**主键更新/CDC 同步**需求 → ClickHouse 的 `ReplacingMergeTree` 需要 `FINAL` 或等后台合并，**语义是最终一致**，不如 Doris 的 MoW 主键模型直接。
- **查询特征**：**多表复杂 Join、高并发 BI** → Doris 的 Join 优化（Colocate/Bucket Shuffle/Runtime Filter）更成熟。
- **运维特征**：ClickHouse 的分片扩容涉及数据重分布（resharding），**集群管理成本更高**；Doris 加 BE 即可。
- **反面**：如果是**海量日志明细、单表大宽表聚合为主**，ClickHouse 往往更省资源，**已有集群且满足场景就不该为迁而迁**。
- **收尾**：选型看**业务需求 + 团队熟悉度 + 运维成本**，三者权重高于纸面性能。

详见 [[9-对比StarRocks与ClickHouse]]。

## 五、面试前 10 分钟速记卡

> [!abstract] 记住这 10 句
> 1. Doris = MPP 列式 OLAP；**FE 管元数据与规划，BE 管存储与计算**。
> 2. 数据分布：**表 → 分区 → 分桶(tablet) → 副本**；tablet 数 = 分区 × 分桶 × 副本。
> 3. 模型三选一：**Duplicate（留原始）/ Unique+MoW（按主键更新）/ Aggregate（预聚合）**。
> 4. **`DUPLICATE KEY` 不是唯一约束**，它是排序键，决定前缀索引。
> 5. 分区管**裁剪**，分桶管**打散与并行**；分桶数别贪多。
> 6. 慢 SQL：**`EXPLAIN` 看计划，`PROFILE` 看真实耗时**；分区列套函数 = 裁剪失效。
> 7. Join 四式：Broadcast / Shuffle / Bucket Shuffle / **Colocate（零 Shuffle）**。
> 8. Flink 写 Doris 不重不丢：**label 幂等 + 攒批 + 2PC**。
> 9. `-235` = **版本堆积**，根因多为**写得太碎**，优先改写入方式。
> 10. 放 Doris 的是**要高并发/要更新/要预聚合**的层；海量明细落**数据湖**，用 External Catalog 联邦查询。
