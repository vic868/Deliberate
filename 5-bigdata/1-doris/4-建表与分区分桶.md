## 一、`CREATE TABLE` 语法骨架

### 1.1 骨架总览

```sql
CREATE [ TEMPORARY | EXTERNAL ] TABLE [ IF NOT EXISTS ] <table_name>
    ( <columns_definition> [ , <indexes_definition> ] )
    [ ENGINE = OLAP ]
    [ <key_type> KEY (<key_cols>)
        [ ORDER BY (<cluster_cols>) ]        -- 4.1+，仅 UNIQUE 模型
    ]
    [ COMMENT '<table_comment>' ]
    [ <partitions_definition> ]
    [ DISTRIBUTED BY { HASH (<distribute_cols>) | RANDOM }
        [ BUCKETS { <bucket_count> | AUTO } ]
    ]
    [ <roll_up_definition> ]
    [ PROPERTIES ( "<k>" = "<v>" [, ...] ) ]
```

把它拆成"从上到下依次要回答的 8 个问题"：

| 顺序 | 语法片段 | 你要回答的问题 |
| --- | --- | --- |
| 1 | `<columns_definition>` | 有哪些列、什么类型、哪些是 key |
| 2 | `<key_type> KEY (...)` | 用哪种数据模型、排序键是什么 |
| 3 | `COMMENT` | 表是干什么的（强烈建议写，半年后救命） |
| 4 | `PARTITION BY` | 按什么切分区（通常是时间） |
| 5 | `DISTRIBUTED BY ... BUCKETS` | 按什么散数据、散成几份 |
| 6 | `<indexes_definition>` | 要不要额外索引 |
| 7 | `PROPERTIES` | 副本、MoW、压缩、冷热分层、动态分区 |
| 8 | （隐含） | 顺序：**列 → key → 分区 → 分桶 → 属性**，这个顺序不能乱 |

### 1.2 逐段讲解

#### （1）`CREATE [ TEMPORARY | EXTERNAL ] TABLE [ IF NOT EXISTS ] <table_name>`

| 片段 | 说明 |
| --- | --- |
| `TEMPORARY` | 临时表，会话级，用于中间结果 |
| `EXTERNAL` | 外表（Hive/Iceberg/Hudi 等），**不写 `ENGINE=OLAP`**，也不管分区/分桶/副本 |
| `IF NOT EXISTS` | 幂等建表。**注意它只在表名冲突时静默跳过，不会校验列定义是否一致**——用它在 CI 里"保证表存在"是安全的，用它"保证表结构正确"是不安全的 |

> [!warning] `IF NOT EXISTS` 的隐藏陷阱
> 建表脚本里写 `CREATE TABLE IF NOT EXISTS ods_order (...很长的定义...)`，第一次跑成功了；后来有人手工改了这张表的列，脚本再跑**不会报错也不会修正**，于是"声明式建表"变成了假象。规范做法：CI 里用 `SHOW CREATE TABLE` 与期望 DDL 对比，而不是靠 `IF NOT EXISTS` 蒙过去。

#### （2）列定义

```sql
<col_name> <col_type>
    [ KEY ]                                        -- 显式声明为 key 列
    [ <col_aggregate_type> ]                       -- 仅聚合模型：SUM/MIN/MAX/REPLACE/...
    [ [ GENERATED ALWAYS ] AS (<expression>) ]     -- 生成列，由前面的列计算得出
    [ [NOT] NULL ]
    [ AUTO_INCREMENT(<start_value>) ]
    [ DEFAULT <default_value> ]
    [ ON UPDATE CURRENT_TIMESTAMP (<precision>) ]  -- 仅 UNIQUE 模型
    [ COMMENT '<col_comment>' ]
```

要点：

| 片段 | 说明 |
| --- | --- |
| `KEY` | 显式标记 key 列。聚合/唯一模型里通常靠 `KEY(...)` 子句统一声明；`ADD COLUMN` 时加 key 列**必须**写这个关键字 |
| `<col_aggregate_type>` | 只有**聚合模型**能用。写法是 `COUNT BIGINT SUM DEFAULT "0"`，聚合类型写在类型之后 |
| `[NOT] NULL` | 不写默认是 nullable。`NOT NULL` 的列在导入时遇到 NULL 会报错（或被过滤掉，取决于导入参数） |
| `DEFAULT` | 写入未提供该列时填什么。支持字面量、`CURRENT_DATE`、`CURRENT_TIMESTAMP`、`BITMAP_EMPTY()` 等；不显式设置时用 `NULL` 填充 |
| `GENERATED ALWAYS AS (...)` | 生成列，只能用**它前面已定义的列**做表达式，值会落盘 |
| `AUTO_INCREMENT(n)` | 自增列，导入时未指定值则自动分配表内唯一值 |
| `ON UPDATE CURRENT_TIMESTAMP` | 只在 UNIQUE 表可用；更新时若未指定该列则填当前时间 |

#### （3）三种模型的 `KEY` 声明差异（最容易写错的地方）

```sql
-- Duplicate：KEY 只是排序键，不是唯一约束
DUPLICATE KEY(`dt`, `log_time`, `user_id`)

-- Unique：KEY 是唯一约束
UNIQUE KEY(`dt`, `order_id`)

-- Aggregate：KEY 是聚合维度，value 列必须带聚合类型
AGGREGATE KEY(`dt`, `ad_id`, `city`)
```

| 模型 | `KEY` 语义 | value 列是否要聚合类型 | 分桶列限制 |
| --- | --- | --- | --- |
| `DUPLICATE KEY` | 排序键 | 不要 | **任意列**都可以做分桶列 |
| `UNIQUE KEY` | 唯一键 | 不要 | **必须是 KEY 列** |
| `AGGREGATE KEY` | 聚合维度 | **要**（`SUM`/`MIN`/`MAX`/`REPLACE`/`BITMAP_UNION`…） | **必须是 KEY 列** |

**共同硬约束**（官方手册原话：Doris 中 Key 列必须是表的**前 K 个列**）：

1. `KEY` 列必须**连续地排在最前面**，普通列只能跟在后面。
2. **分区列必须是 KEY 列的子集**（多列分区时顺序要与 KEY 中一致）。
3. 聚合模型的 value 列**必须**写聚合类型，否则该列语义按 `REPLACE` 处理（不同版本推断细节略有差异，**建议全部写全**）。

> [!danger] 报错速查：`Key columns should be a ordered prefix of the schema`
> 你肯定是把 key 列写在了普通列后面。修法只有两个：**调整列顺序**（把 key 列提到最前面）或**换一个 key**。注意这也意味着"事后想把某列变成 key 列"往往要重建表。

#### （4）`ENGINE = OLAP`

Doris 内部表统一写 `ENGINE=OLAP`。外表（`CREATE EXTERNAL TABLE`）不写这个、也不需要分区/分桶/副本声明。存算分离模式（3.0+）下 OLAP 表的 DDL 基本不变，差异在存储介质与副本语义（见 [[7-湖仓一体]]）。

#### （5）`ORDER BY (<cluster_cols>)`（4.1+，仅 UNIQUE 模型）

```sql
CREATE TABLE t (
    `k1` INT NOT NULL,
    `k2` INT NOT NULL,
    `v1` VARCHAR(32),
    `ts` DATETIME
)
ENGINE=OLAP
UNIQUE KEY(`k1`, `k2`)
ORDER BY(`k1`, `ts`)
DISTRIBUTED BY HASH(`k1`) BUCKETS 8
PROPERTIES ("replication_num" = "3");
```

用途：**让"唯一键"和"排序键"解耦**。默认两者相同（数据按 `key_cols` 有序）；指定 `ORDER BY` 后，数据改按 `<cluster_cols>` 排序，而唯一性约束仍由 `KEY` 决定。典型场景：主键是 `(k1, k2)`，但绝大多数查询按 `(k1, ts)` 过滤——把 `ts` 排进排序键就能吃到前缀索引。

| 注意 | 说明 |
| --- | --- |
| 版本 | **4.1.0 起支持**；3.x 上没有这个语法，只能通过调整 `KEY` 顺序间接实现，或另建 rollup/MV |
| 模型 | **仅 UNIQUE 模型**可用 |
| 影响 | `ORDER BY` 是**数据局部排序列**，改动它属于"改排序键"，基本等于重建表 |

#### （6）`COMMENT`

```sql
COMMENT '订单明细表(CDC 同步, 保留 90 天)'
```

强烈建议写。一张线上表半年后没人记得它的分区策略和用途，`COMMENT` 是最低成本的文档。列级 `COMMENT` 同理。

#### （7）分区 / 分桶 / 属性

### 1.3 三种模型的完整可执行建表示例

**Duplicate（明细）**

```sql
CREATE TABLE IF NOT EXISTS dwd_user_action_log (

    `page_id`     VARCHAR(64)           COMMENT '页面 id',

```

CREATE TABLE IF NOT EXISTS dim_order (

### 1.4 两个变种：CTAS 与 `CREATE TABLE LIKE`

```sql
-- CTAS：建表并灌入查询结果。注意 key/分区/分桶仍要自己声明，不能只写 AS SELECT
CREATE TABLE dws_tmp_order_stat
ENGINE=OLAP
DUPLICATE KEY(`dt`, `order_status`)
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`order_status`) BUCKETS 4
PROPERTIES ("replication_num" = "3")
AS
SELECT dt, order_status, count(*) AS cnt, sum(pay_amount) AS amt
FROM dim_order
WHERE dt >= '2026-10-01'
GROUP BY dt, order_status;

-- LIKE：复制表结构（列属性一起复制），不带数据
CREATE TABLE dim_order_bak LIKE dim_order;
-- 连同指定 rollup 一起复制
CREATE TABLE dim_order_bak LIKE dim_order WITH ROLLUP (r1, r2);
```

| 变种 | 用在哪 | 坑 |
| --- | --- | --- |
| CTAS | 快速产出临时/中间结果表 | 不写 `KEY`/`DISTRIBUTED BY` 时会走默认分布，容易建成不合适的形态；大数据量 CTAS 会长时间占用资源 |
| LIKE | 备份表结构、造影子表做迁移验证 | **不复制数据**，`LIKE` 出来的表是空的 |

## 二、分区语法详解

### 2.1 `RANGE` 分区与 `LESS THAN` 的边界（本节必记）

语法形态：

```sql
PARTITION BY RANGE (<partition_cols>) (
    PARTITION <name> VALUES LESS THAN (<value_list>),
    ...
)
```

**核心规则：`LESS THAN` 是上界且"不含"，分区整体是左闭右开区间 `[左界, 上界)`；左界由 Doris 自动接续前一个分区的上界决定。**

```sql
CREATE TABLE ods_order (
    `dt`       DATE   NOT NULL,
    `order_id` BIGINT NOT NULL,
    `amount`   DECIMAL(18, 2)
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `order_id`)
PARTITION BY RANGE(`dt`) (
    PARTITION p20261007 VALUES LESS THAN ("2026-10-08"),
    PARTITION p20261008 VALUES LESS THAN ("2026-10-09"),
    PARTITION p20261009 VALUES LESS THAN ("2026-10-10")
)
DISTRIBUTED BY HASH(`order_id`) BUCKETS 8
PROPERTIES ("replication_num" = "3");
```

| 数据 | 落进哪个分区 | 为什么 |
| --- | --- | --- |
| `dt = '2026-10-07'` | `p20261007` | `[..., 10-08)` 含 10-07 |
| `dt = '2026-10-08'` | `p20261008` | `p20261007` 的 `LESS THAN ('2026-10-08')` **不含** 10-08，所以落进下一个 |
| `dt = '2026-10-10'` | **没有分区 → 导入报错** | 三个分区只覆盖到 `[.., 10-10)`；10-10 及其后都是空洞 |

> [!danger] 三个最常见的 `LESS THAN` 错误
> **① 写成 `LESS THAN ("2026-10-09")` 却以为包含 10-09。** 不包含。要包含 10-09，上界必须写 `"2026-10-10"`。
> **② 用 `<=` 的思维推分区边界。** Doris 报错的典型信息是 `Tablet not found` / 导入时 `no partition for this tuple`，本质是数据落在了分区区间之外。
> **③ 用 `DATETIME` 列做分区但上界只写到天。** 例如列是 `DATETIME`，写成 `LESS THAN ("2026-10-10")`，那么 `'2026-10-10 00:00:01'` 就不在任何分区里。要么用 `DATE` 列做分区，要么上界写成 `'2026-10-11 00:00:00'`。
>
> **诊断口诀**：先 `SHOW PARTITIONS FROM tbl;` 看真实区间，再 `SELECT count(*) FROM tbl WHERE dt = '<可疑值>';` 对比——如果 count 为 0 但源数据明明有，就是分区空洞。

最后（或唯一）一个分区常用 `MAXVALUE` 兜底，避免"数据超出预期就导入失败"：

```sql
PARTITION BY RANGE(`dt`) (
    PARTITION p20261009 VALUES LESS THAN ("2026-10-10"),
    PARTITION pmax      VALUES LESS THAN (MAXVALUE)
)
```

> [!warning] `MAXVALUE` 兜底分区不是免费的
> 它让所有"未来数据"都堆进同一个分区——**分区裁剪对它无效**，查未来数据就变成扫一个大分区。所以用 `MAXVALUE` 只是"别让导入失败"的保险，同时必须配**动态分区或告警**来及时切出正常分区。

### 2.2 多列分区与元组比较

```sql
CREATE TABLE ods_order_region (
    `dt`       DATE       NOT NULL,
    `region`   VARCHAR(32) NOT NULL,
    `order_id` BIGINT     NOT NULL,
    `amount`   DECIMAL(18, 2)
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `region`, `order_id`)
PARTITION BY RANGE(`dt`, `region`) (
    PARTITION p20261009_bj VALUES LESS THAN ("2026-10-10", "beijing"),
    PARTITION p20261009_sh VALUES LESS THAN ("2026-10-10", "shanghai"),
    PARTITION p20261010_bj VALUES LESS THAN ("2026-10-10", "zzzzzz"),
    PARTITION pmax         VALUES LESS THAN (MAXVALUE, MAXVALUE)
)
DISTRIBUTED BY HASH(`order_id`) BUCKETS 8
PROPERTIES ("replication_num" = "3");
```

`LESS THAN` 后面的值列表是一个**元组**，比较规则是**字典序**（先比第一列，相等再比第二列），等价于：

```text
(dt, region) < ("2026-10-10", "beijing")
```

| 要点 | 说明 |
| --- | --- |
| 约束 | 分区列必须是 KEY 列，且**顺序要与 KEY 前缀一致** |
| 写法要求 | 每个分区的上界元组要保证**区间连续、不重叠、不留空洞**；留空洞 → 对应数据导入失败 |
| 排序方向 | `region` 是字符串，字典序里 `"beijing" < "shanghai" < "zzzzzz"`；想给"某天下所有 region"兜底，就用一个大于所有真实值的小写字母串（或 `MAXVALUE`） |
| 什么时候用 | 需要"同一时间维度内再按业务维度切一刀"（例如多机房/多区域独立归档）；**大多数场景不需要**，单列时间分区 + 分桶已经够 |

> [!danger] 多列分区是运维负担，非必要不用
> 它把"新增分区"从"加一个"变成"维护一张二维区间表"。一旦业务新增一个 region，老的兜底分区（`MAXVALUE, MAXVALUE`）就必须拆分，而拆分要 `DROP` + `ADD` + 重灌该部分数据。**除非有明确的多区域独立生命周期管理需求，否则优先用"单列时间分区 + 分桶"或"多列分桶"来达到类似效果。**

### 2.3 左闭右开区间写法与"批量创建分区"

**（1）只写上下界的写法**

```sql
PARTITION BY RANGE(`dt`) (
    PARTITION p20261007 VALUES [("2026-10-07"), ("2026-10-08")),
    PARTITION p20261008 VALUES [("2026-10-08"), ("2026-10-09"))
)
```

`VALUES [lower, upper)` 是**显式左闭右开**写法，只要一个分区，比 `LESS THAN` 更不容易搞错边界；**但注意**：如果只指定右界（`VALUES LESS THAN`），左界由系统自动接续。两种写法不要在一次建表里混着用得让人看不懂。

**（2）批量创建分区（强烈推荐）**

手写 365 个分区定义不现实，直接用 `FROM ... TO ... INTERVAL n <unit>`：

```sql
-- 建表时批量生成：从 2026-01-01 起每 1 天一个分区
CREATE TABLE ods_order_2026 (
    `dt`       DATE   NOT NULL,
    `order_id` BIGINT NOT NULL
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `order_id`)
PARTITION BY RANGE(`dt`) (
    FROM ("2026-01-01") TO ("2027-01-01") INTERVAL 1 DAY
)
DISTRIBUTED BY HASH(`order_id`) BUCKETS 8
PROPERTIES ("replication_num" = "3");

-- 给已有表批量加分区（ALTER 侧同样支持）
ALTER TABLE ods_order ADD PARTITIONS FROM ("2026-01-01") TO ("2027-01-01") INTERVAL 1 DAY;
ALTER TABLE ods_order ADD PARTITIONS FROM ("2026-01-01") TO ("2027-01-01") INTERVAL 1 MONTH;
ALTER TABLE ods_order ADD PARTITIONS FROM ("2026-01-01") TO ("2027-01-01") INTERVAL 1 WEEK;
ALTER TABLE ods_order ADD PARTITIONS FROM ("2026-01-01") TO ("2027-01-01") INTERVAL 1 YEAR;
-- 数值分区列也可以
ALTER TABLE ods_num ADD PARTITIONS FROM (1) TO (100) INTERVAL 10;
```

> [!tip] 建完必须核对
> `FROM/TO/INTERVAL` 生成的最后一个分区的确切上界在不同版本上可能有细微差异。**建完立刻 `SHOW PARTITIONS FROM tbl;` 核对区间**，并确认"你真正要写的边界值"确实落在某个分区里。宁可多花 10 秒核对，也不要第二天发现导入失败。

### 2.4 `LIST` 分区

`RANGE` 只能按有序值的**连续区间**切，`LIST` 是按**枚举值集合**切：

```sql
CREATE TABLE ods_order_list (
    `region`   VARCHAR(32) NOT NULL,
    `order_id` BIGINT      NOT NULL,
    `amount`   DECIMAL(18, 2)
)
ENGINE=OLAP
DUPLICATE KEY(`region`, `order_id`)
PARTITION BY LIST(`region`) (
    PARTITION p_north VALUES IN ("beijing", "tianjin"),
    PARTITION p_east  VALUES IN ("shanghai", "hangzhou", "nanjing")
)
DISTRIBUTED BY HASH(`order_id`) BUCKETS 8
PROPERTIES ("replication_num" = "3");
```

| 要点 | 说明 |
| --- | --- |
| 多列 LIST | 支持多列：`PARTITION BY LIST(a, b)`，取值写成元组集合 `VALUES IN (("x","y"), ("p","q"))` |
| default 分区 | LIST 分区可以额外有一个 **default 分区**，用来承接所有**不匹配任何已定义取值**的数据，通过 `ALTER TABLE tbl ADD PARTITION p_default;`（不带 `VALUES IN`）添加。**没有 default 分区时，未匹配的取值导入会失败** |
| 典型用途 | 维度取值固定且需要按维度做独立生命周期的表（区域、租户、业务线） |
| 不适用 | 取值会持续新增的维度（每次新增都要改分区定义），这种场景用 RANGE 或干脆只做分桶 |

### 2.5 自动分区（Auto Partition）—— 官方推荐的现代做法

动态分区（下一节）靠**当前时间**推进分区；如果分区列与当前时间无关（例如交易日期是历史/离散值），动态分区就不好用。**自动分区**改成由**写入的数据**驱动：导入时若目标分区不存在就自动创建并正常导入。

```sql
-- AUTO RANGE：按 date_trunc 指定的粒度自动建分区
CREATE TABLE auto_range_tbl (
    `dt`       DATE   NOT NULL,
    `order_id` BIGINT NOT NULL,
    `amount`   DECIMAL(18, 2)
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `order_id`)
AUTO PARTITION BY RANGE(date_trunc(`dt`, 'month'))
()
DISTRIBUTED BY HASH(`order_id`) BUCKETS 8
PROPERTIES ("replication_num" = "3");

-- AUTO LIST：按枚举列自动建分区
CREATE TABLE auto_list_tbl (
    `region`   VARCHAR(32) NOT NULL,
    `order_id` BIGINT      NOT NULL
)
ENGINE=OLAP
DUPLICATE KEY(`region`, `order_id`)
AUTO PARTITION BY LIST(`region`)
()
DISTRIBUTED BY HASH(`order_id`) BUCKETS 8
PROPERTIES ("replication_num" = "3");
```

| 维度 | 动态分区 | 自动分区 |
| --- | --- | --- |
| 触发依据 | **当前时间** + `time_unit`/`start`/`end` | **写入数据里的分区列值** |
| 分区列类型 | **仅** `DATE`/`DATETIME`/`TIMESTAMP_NS`，单列 | RANGE 走 `date_trunc` 指定粒度；LIST 支持枚举（含多列） |
| 适合 | 实时日志/时序，按天滚动保留 | 历史数据回灌、分区列与当下时间无关、离散值很多 |
| 生命周期清理 | **自带 TTL**（`start` 自动删旧分区） | 不自动删；过期清理要另配（`DROP PARTITION` 或冷热分层） |
| 官方定位 | 可用 | **"更推荐使用自动分区，它是动态分区的上位替代"** |

> [!important] 选哪个（面试也爱问）
> 一句话：**"分区列跟当前时间一起往前走" → 动态分区（自带 TTL 最省心）；"分区列是历史/离散值、写入时才确定" → 自动分区。** 官方文档明确把自动分区定位为动态分区的上位替代，但它**不自带过期删除**，所以"实时日志滚动保留 N 天"这种需求，动态分区反而更省事。

### 2.6 分区命名与可读性

- 命名建议带语义和粒度：`p20261009`（天）、`p202610`（月）、`p2026`（年）。
- **动态分区/自动分区会自动按 `dynamic_partition.prefix` 生成名字**（如 `prefix=p` → `p20261009`），不要手工造一批命名风格冲突的分区，否则将来排查和脚本处理都会很痛。
- `SHOW PARTITIONS FROM tbl;` 是唯一可信的"当前长什么样"来源，脚本和文档都可能过时。

## 三、动态分区

### 3.1 属性逐项含义

在 `PROPERTIES` 里以 `dynamic_partition.` 为前缀声明：

| 属性 | 必填 | 含义与取值 |
| --- | --- | --- |
| `dynamic_partition.enable` | 否 | 总开关，`TRUE`/`FALSE`。**只要填了其他必填参数，默认就是 TRUE** |
| `dynamic_partition.time_unit` | **是** | 调度粒度：`HOUR` / `DAY` / `WEEK` / `MONTH` / `YEAR` |
| `dynamic_partition.start` | 否 | **起始偏移，负数**。以当天（或本周/本月）为基准，在此偏移之前的分区会被删除。默认 `-2147483648`，即**不删历史分区** |
| `dynamic_partition.end` | **是** | **结束偏移，正数**。提前创建未来多少范围的分区 |
| `dynamic_partition.prefix` | **是** | 自动创建的分区名前缀，如 `p` → `p20261009` |
| `dynamic_partition.buckets` | 否 | 新建分区的分桶数。**设置后会覆盖 `DISTRIBUTED BY` 里的分桶数**（动态分区表里它有更高优先级） |
| `dynamic_partition.replication_num` | 否 | 新建分区的副本数，不填则用建表时的副本数 |
| `dynamic_partition.create_history_partition` | 否 | 默认 `false`。开启后会把 `start` 到现在的历史分区一次性补齐；受 FE 参数 `max_dynamic_partition_num` 限制，超限会被拒绝 |
| `dynamic_partition.history_partition_num` | 否 | 与 `create_history_partition` 配合时，指定要创建的历史分区**数量**。默认 `-1`（未设置）；与 `start` 作用相同，**建议只设一个** |
| `dynamic_partition.start_day_of_week` | 否 | `time_unit=WEEK` 时，指定每周起始日：`1`=周一 … `7`=周日，默认 `1` |
| `dynamic_partition.start_day_of_month` | 否 | `time_unit=MONTH` 时，指定每月起始日：取值 `1~28`，默认 `1`。**不支持 29/30/31**（避免闰年闰月歧义） |
| `dynamic_partition.reserved_history_periods` | 否 | 需要**额外保留**的历史时间段，格式 `[yyyy-MM-dd,yyyy-MM-dd],[...,...]`；`time_unit=HOUR` 时格式带时分秒。默认 `"NULL"` |
| `dynamic_partition.time_zone` | 否 | 动态分区时区，默认跟随服务器系统时区（如 `Asia/Shanghai`） |
| `dynamic_partition.replication_allocation` | 否 | 按标签指定新建分区副本分布 |

### 3.2 完整配置示例

```sql
-- 实时日志：保留过去 7 天 + 当天，预建未来 3 天
CREATE TABLE dwd_log_dynamic (
    `dt`       DATE         NOT NULL,
    `log_time` DATETIME     NOT NULL,
    `user_id`  BIGINT       NOT NULL,
    `event`    VARCHAR(32)  NOT NULL
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `log_time`, `user_id`)
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`user_id`) BUCKETS 32
PROPERTIES (
    "replication_num" = "3",
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-7",
    "dynamic_partition.end" = "3",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.buckets" = "32",
    "dynamic_partition.create_history_partition" = "true",
    "dynamic_partition.time_zone" = "Asia/Shanghai"
);
```

```sql
-- 把已有普通表改造成动态分区表：注意不会立即生效
ALTER TABLE dwd_log SET (
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-7",
    "dynamic_partition.end" = "3",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.create_history_partition" = "true"
);

-- 查看调度情况（Enable / TimeUnit / Start / End / Prefix / Buckets / LastSchedulerTime / State …）
SHOW DYNAMIC PARTITION TABLES;

-- 单独查某张表，可从 State 与 Last*Msg 看出失败原因
SHOW DYNAMIC PARTITION TABLES FROM dw;
```

```sql
-- 保留指定历史时间段（例如监管要求保留两个特定区间）
ALTER TABLE dwd_log SET (
    "dynamic_partition.reserved_history_periods" = "[2026-06-01,2026-06-20],[2026-10-01,2026-10-07]"
);
```

### 3.3 相关 FE 参数

动态分区是 **FE 侧的后台线程**在做，几个关键 FE 配置（`fe.conf`，也可用 `ADMIN SET FRONTEND CONFIG` 动态改）：

| 参数 | 作用 |
| --- | --- |
| `dynamic_partition_enable` | 动态分区功能的**总开关**（只影响动态分区表，不影响普通表）。**注意默认是关闭的**——很多人第一次配动态分区发现不生效，就是这里 |
| `dynamic_partition_check_interval_seconds` | 调度线程的执行间隔（秒）。**默认 600 秒（10 分钟）**，所以"改了配置没立刻建分区"是正常的 |
| `max_dynamic_partition_num` | 限制一次可创建的最大分区数，防止 `create_history_partition` 一次建太多把 FE 打爆 |

> [!warning] 三个必需的排查前置
> 动态分区"不生效"时，按顺序检查：**① FE 的 `dynamic_partition_enable` 是否为 true；② `SHOW DYNAMIC PARTITION TABLES` 里 `Enable` 是否为 true、`TimeUnit`/`Start`/`End` 是否符合预期；③ 是否还没到 `dynamic_partition_check_interval_seconds` 的调度周期。** 只有这三关都过了，才需要考虑时区、`max_dynamic_partition_num` 之类的深层原因。

### 3.4 常见坑

| 坑 | 现象 | 原因与解法 |
| --- | --- | --- |
| **时区不对** | 分区名差一天；"今天的数据"导不进去 | 服务器时区 ≠ 业务时区。显式设置 `dynamic_partition.time_zone`（如 `Asia/Shanghai`），并统一 FE/BE 与容器时区 |
| **`start` / `end` 写反** | 分区不建、或建到明年、或历史被大量删除 | `start` 必须是**负数**（往前保留），`end` 必须是**正数**（往后预建）。写反的破坏力很大：`start` 设成正数可能被理解成不保留历史 |
| **历史分区没补** | 回灌历史数据时导入失败 | 默认 `create_history_partition=false`，只创建"从现在往后"的分区。回灌前开启它，或先用 `ADD PARTITIONS FROM ... TO ... INTERVAL ...` 手工补 |
| **`buckets` 覆盖了建表分桶数** | 新建分区桶数跟老分区不一致 | `dynamic_partition.buckets` 优先级更高。要么别设它（继承建表值），要么保证设的值就是你想要的 |
| **改配置不生效** | `ALTER TABLE ... SET (...)` 后分区没变化 | 见上：受 `dynamic_partition_check_interval_seconds` 周期控制，不会立即执行 |
| **一次性创建被拒** | `create_history_partition` 报错 | 要创建的分区数超过 `max_dynamic_partition_num`。分批建，或调大该 FE 参数 |
| **默认 `start` 不删历史** | 以为配了 TTL，结果磁盘一直涨 | `start` 默认是 `-2147483648`（等于不删）。要 TTL 必须显式设 `start` |
| **`WEEK`/`MONTH` 起始日理解错** | 分区边界与业务周/月不一致 | 用 `start_day_of_week`（1~7，默认周一）和 `start_day_of_month`（1~28，默认 1）显式对齐业务口径 |

## 四、分桶

### 4.1 语法与约束

```sql
DISTRIBUTED BY { HASH (<distribute_cols>) | RANDOM } [ BUCKETS { <bucket_count> | AUTO } ]
```

| 片段 | 说明 |
| --- | --- |
| `HASH(cols)` | 按列哈希取模分桶。**推荐**，能支撑点查/裁剪与 bucket shuffle |
| `RANDOM` | 随机分布，规避倾斜，但**无法按分桶列裁剪 tablet** |
| `BUCKETS n` | 固定桶数，任意正整数 |
| `BUCKETS AUTO` | 由系统按数据量与集群配置自动推算 |
| 省略 `DISTRIBUTED BY` | 会走默认分布（往往不是你想要的），**生产建表一律显式写** |

**硬约束**：

| 约束 | 说明 |
| --- | --- |
| 分桶列模型限制 | **Duplicate 模型任意列**可做分桶列；**Aggregate / Unique 模型分桶列必须是 KEY 列** |
| 分桶数与分区数关系 | `Tablet 总数 = 分区数 × 分桶数` |
| 能否修改 | 官方手册明确：**分桶数一旦指定就不能修改**（另见 4.5 的 `MODIFY DISTRIBUTION`，它只改**新分区**的默认值） |
| 单 tablet 大小 | 建议落在 **1G ~ 10G**（过大不利于副本迁移与 schema change 重试，过小则聚合效果差、元数据压力大） |
| tablet 总数 | 不考虑扩容时，**略多于集群磁盘总数**为宜；与数据量原则冲突时**优先数据量原则** |
| 分桶列多寡的取舍 | 分桶列**多** → 分布更均匀，但点查会同时扫所有桶（适合**高吞吐低并发**）；分桶列**少** → 点查精准落一个桶（适合**高并发点查**） |

数量级参考（官方手册给出的例子）：

| 单表 / 单分区数据量 | 分桶数量级 |
| --- | --- |
| 几百 MB | 4 ~ 8 |
| 约 5 GB | 8 ~ 16 |
| 约 50 GB | 32 |
| 500 GB 及以上 | **先分区**，让单分区约 50GB，每分区 16 ~ 32 个桶 |

```sql
-- 常规写法
DISTRIBUTED BY HASH(`order_id`) BUCKETS 32

-- 组合分桶列（稀释单一列的不均匀）
DISTRIBUTED BY HASH(`user_id`, `city`) BUCKETS 32

-- 随机分布（配合单 tablet 导入）
DISTRIBUTED BY RANDOM BUCKETS 32
```

### 4.2 `BUCKETS AUTO` 与 `estimate_partition_size`

```sql
DISTRIBUTED BY HASH(`order_id`) BUCKETS AUTO
PROPERTIES (
    "estimate_partition_size" = "100G"
);
```

| 项 | 说明 |
| --- | --- |
| `BUCKETS AUTO` | 把分桶数交给系统推算，避免"人拍脑袋定桶数" |
| `estimate_partition_size` | **单个分区的数据量**估计值，可选；不给时系统用一个默认估计（量级为 10GB） |
| 推算目标 | 让**单 tablet 大小落在 1G~10G** 的推荐区间 |
| 约束 | 系统还有一个基于 **BE 节点数 × 磁盘容量** 的上限，并对极端值做截断（例如最多 128 个桶、最少若干桶），最终取"数据量推算值"与"集群能力推算值"的较小者，并保证不低于一个最小值 |
| 动态性 | **不同分区的桶数可以不同**——后续分区会参考已有分区的实际大小滚动修正估计 |
| 限制 | `estimate_partition_size` **不支持 `ALTER`**，想改只能重建表 |
| 适用 | 拿不准桶数时（新业务、增长不确定）；已经明确知道数据量与查询形态时，显式桶数更可控 |

> [!tip] 实用策略
> **新表 + 不确定数据量 → 用 `BUCKETS AUTO` 起步，跑几周后用 `SHOW TABLETS` / `SHOW DATA` 看真实单 tablet 大小，再决定是否需要调整。** 但要注意两点：① AUTO 的推算依赖写入时能拿到的信息，冷启动阶段不准；② 改桶数只能影响**新分区**（4.5），所以"发现桶数不对"往往意味着要重建历史分区。

### 4.3 分桶与 tablet 的关系

```text
表 = 分区集合
每个分区 = BUCKETS 个 tablet
Tablet 总数 = 分区数 × 分桶数
每个 tablet = 3 份副本（replication_num=3）

例：90 个天分区 × 32 桶 = 2880 个 tablet
    3 副本 → 8640 个 tablet 副本文件
```

**tablet 过多的问题**（"小文件问题"的 Doris 版本）：

| 症状 | 原因 |
| --- | --- |
| 导入变慢、导入报错超时 | 一次导入的元数据事务要覆盖命中的大量 tablet |
| compaction 任务数量爆炸、CPU/IO 打满 | 每个 tablet 都是独立的 compaction 单元 |
| FE 元数据占用高、`SHOW TABLETS` 很慢 | 分区 × 分桶 的映射规模过大 |
| 查询不一定更快 | tablet 调度开销可能超过并行扫描带来的收益 |
| 副本修复/扩容很慢 | 迁移与补齐的粒度是 tablet |

**排查命令**：

```sql
-- 表/分区整体大小与行数（注意：结果包含所有副本，需自行除以副本数）
SHOW DATA FROM dwd_user_action_log;

-- 逐 tablet 的行数/大小，直接看单桶是否过小、是否倾斜
SHOW TABLETS FROM dwd_user_action_log;

-- 各 BE 的磁盘使用情况，看是否某台明显偏高
SHOW BACKENDS;
```

### 4.4 `RANDOM` 分布与单 tablet 导入

```sql
DISTRIBUTED BY RANDOM BUCKETS 32
```

| 收益 | 代价 |
| --- | --- |
| 彻底规避哈希倾斜（每批导入随机选 tablet 写） | 没有分桶列 → **任何查询都会扫命中分区的全部桶**，不能按分桶列裁剪 |
| 适合"整表聚合分析、日志类大表" | **不适合高并发点查** |

**配套技巧：单 tablet 导入**。随机分布下，导入时可以开启"一次导入只写一个 tablet"的模式（`load_to_single_tablet`），显著减少写入与 compaction 的写放大，提升导入吞吐与集群稳定性。这组"`RANDOM` + 单 tablet 导入"是日志类大表很实用的配置。

> [!warning] 别把它当成万能药
> `RANDOM` 换来的是**均匀**，失去的是**裁剪**。如果你的查询大量是 `WHERE user_id = ?`，用 `RANDOM` 会让每次点查都扫全桶——这才是"为了省事付出了几十倍代价"。

### 4.5 修改分桶数：`MODIFY DISTRIBUTION` 的真实代价

```sql
-- 修改表的"默认分桶数"（只影响之后新建的分区）
ALTER TABLE dwd_log MODIFY DISTRIBUTION DISTRIBUTED BY HASH(`user_id`) BUCKETS 64;

-- 切到 AUTO
ALTER TABLE dwd_log MODIFY DISTRIBUTION DISTRIBUTED BY HASH(`user_id`) BUCKETS AUTO;

-- RANDOM 分布的表也能改桶数
ALTER TABLE dwd_log_random MODIFY DISTRIBUTION DISTRIBUTED BY RANDOM BUCKETS 12;
```

**这是"看起来能改、其实改不动存量"的典型**，把规则记清楚：

| 规则 | 说明 |
| --- | --- |
| 生效范围 | **只改变"新建分区"的默认分桶数；已有分区保持原桶数不变** |
| 能改什么 | **只能改桶数**（`num` 或 `AUTO`，可自由来回切、可多次改） |
| 不能改什么 | **不能改分布类型**（HASH ↔ RANDOM 会报 `Cannot change distribution type`）、**不能改分桶列**（报 `Cannot assign hash distribution with different distribution cols`） |
| 适用对象 | **只支持分区表**（RANGE/LIST）；未分区表报 `Only support change partitioned table's distribution` |
| Colocate | **Colocate 表不支持**（报 `Cannot change default bucket number of colocate table`） |
| 与动态分区 | 之后由调度器新建的分区用新桶数；**`dynamic_partition.buckets` 优先级更高**，如果它被显式设了，仍以它为准 |
| 与自动分区 | 之后由写入触发新建的自动分区用新桶数 |
| 已有分区怎么办 | 官方手册明确"分桶数一旦指定就不能修改"。要改变**存量分区**的桶数，实际只有重建路线：**建新表 → 重灌（或 `ALTER TABLE ... REPLACE` 做切换）** |
| 所以真正的代价 | 不是"执行这条 SQL 的成本"（它是同步的、很快），而是"**你为存量数据买单**"：要么永远忍受"老分区 32 桶、新分区 64 桶"的不一致，要么重建全量数据 |

> [!important] 一句话总结（面试可直接用）
> **"`ALTER TABLE ... MODIFY DISTRIBUTION` 只改新分区的默认桶数，是一次同步的元数据操作，几乎瞬间返回；但它对已有分区无效——而已有分区的桶数官方明确说不能改。所以它的真实代价是'存量数据要么不一致、要么重建'，而不是这条 SQL 本身有多慢。定分桶数时必须预留扩容空间，原因就在这里。"**

### 4.6 给单个新分区单独指定分桶数

建表时分桶数是**统一指定**的，但 `ADD PARTITION` 时可以单独指定：

```sql
ALTER TABLE ods_order
ADD PARTITION p20261231 VALUES LESS THAN ("2027-01-01")
DISTRIBUTED BY HASH(`order_id`) BUCKETS 64;
```

| 注意 | 说明 |
| --- | --- |
| 未指定分桶方式 | 自动使用建表时的分桶方式与分桶数 |
| 指定了分桶方式但**没写 `BUCKETS`** | **桶数会使用默认值 10**，而不会沿用建表时的桶数——这是很隐蔽的坑，务必显式写 `BUCKETS n` |
| 能改什么 | 指定分桶方式时**只能改桶数**，不能改分桶方式或分桶列 |
| 用途 | 数据量增长/缩减时期望"新分区桶数不同"（例如年底大促分区想多给点并行度） |

## 五、表结构变更（Schema Change）

### 5.1 轻量级 vs 重量级（本节必记）

Doris 的 schema change 分两类，差别是**要不要重写数据文件**：

| 特性 | 轻量级 Schema Change | 重量级 Schema Change |
| --- | --- | --- |
| 执行速度 | **秒级**（几乎实时） | 分钟级 / 小时级 / 天级，**取决于数据量** |
| 是否重写数据 | **不需要**，只改元数据 | **需要**，涉及数据文件重写 |
| 资源消耗 | 较低 | 较高，占用大量计算资源 |
| 存储影响 | 基本无 | 转换过程中**表数据占用空间会翻倍**（双写） |
| 典型操作 | 增加/删除 **Value 列**、**修改列名**、**修改 `VARCHAR` 长度**（UNIQUE 和 DUP 表的 **Key 列除外**） | **修改列的数据类型**、`NOT NULL` 改为 `NULL`、**更改主键**、**修改列的排序顺序** |

重量级的执行流程（理解它就知道为什么"重"）：

```text
1. BE 后台启动数据转换任务，以 tablet 为单位重写数据到新文件
2. 转换期间"双写"：新数据同时写进新 tablet 和旧 tablet
3. 转换完成 → 删除旧 tablet → 新 tablet 接管
```

> [!warning] 在业务高峰期做重量级 schema change 的后果
> - 存储空间短时间**翻倍**（如果磁盘水位本来就高，直接写满）；
> - BE 的 IO/CPU 被后台任务抢走，查询 P99 抬升、导入变慢；
> - 任务以 tablet 为单位推进，**中途失败要重试，粒度很粗**；
> - 表越大越慢，期间新旧数据共存，运维窗口难以预估。
>
> 规矩：**重量级变更排到低峰期、提前确认磁盘余量、提前想好失败回滚（多数情况只能等它跑完或取消）**。

### 5.2 常用 Schema Change DDL

```sql
-- 加列：加 value 列（轻量）
ALTER TABLE dim_order ADD COLUMN channel VARCHAR(32) DEFAULT "" COMMENT '渠道' AFTER order_status;

-- 加列：加 key 列（非聚合模型必须写 KEY 关键字；通常会改变排序/分区约束，需谨慎）
ALTER TABLE dwd_log ADD COLUMN app_version VARCHAR(16) KEY DEFAULT "" AFTER user_id;

-- 加到首列
ALTER TABLE dim_order ADD COLUMN tenant_id BIGINT KEY DEFAULT "0" FIRST;

-- 一次加多列（聚合模型加 value 列必须写 agg_type）
ALTER TABLE dws_ad_click_1d ADD COLUMN (cost2 DECIMAL(18,2) SUM DEFAULT "0.00", pv BIGINT SUM DEFAULT "0");
ALTER TABLE dim_order ADD COLUMN (channel VARCHAR(32) DEFAULT "", src VARCHAR(32) DEFAULT "");

-- 删列
ALTER TABLE dim_order DROP COLUMN src;

-- 改列类型 / 位置（多数属于重量级）
ALTER TABLE dim_order MODIFY COLUMN pay_amount DECIMAL(20, 4) COMMENT '支付金额';

-- 改列名（轻量）
ALTER TABLE dim_order RENAME COLUMN channel TO channel_code;

-- 只对某个 rollup 操作
ALTER TABLE dim_order ADD COLUMN extra VARCHAR(32) DEFAULT "" TO rollup_name;
```

要点：

| 操作 | 备注 |
| --- | --- |
| 聚合模型加 value 列 | **必须**指定聚合类型（`SUM`/`MIN`/…） |
| 非聚合模型加 key 列 | **必须**写 `KEY` 关键字 |
| 加列位置 | 用 `AFTER col` / `FIRST`；不写则追加到末尾。**位置变更可能属于重量级**（涉及排序顺序） |
| 改 `VARCHAR` 长度 | 一般轻量；但 **UNIQUE 和 DUP 表的 Key 列例外**（可能触发重写） |
| 不能加的列 | 不能在 rollup 里加 base index 已存在的列（需要就重建 rollup） |

### 5.3 进度查看、取消与状态

```sql
-- 查看 schema change 作业进度（State: PENDING / WAITING_TXN / RUNNING / FINISHED / CANCELLED）
SHOW ALTER TABLE COLUMN;

-- 只看某张表
SHOW ALTER TABLE COLUMN FROM dw WHERE TableName = "dim_order";

-- 也支持按时间倒序取最近提交的作业
SHOW ALTER TABLE COLUMN FROM dw ORDER BY CreateTime DESC LIMIT 5;

-- 查看 rollup / 物化索引变更
SHOW ALTER TABLE ROLLUP;

-- 取消某个 schema change 作业（过滤条件以你所处版本的手册为准）
CANCEL ALTER TABLE COLUMN FROM dw.dim_order WHERE ...;
```

`SHOW ALTER TABLE COLUMN` 的关键列：

| 列 | 怎么读 |
| --- | --- |
| `JobId` | 作业 id，用于定位/取消 |
| `State` | `PENDING`（排队）/ `WAITING_TXN`（等事务）/ `RUNNING`（进行中）/ `FINISHED` / `CANCELLED` |
| `Progress` | 进度百分比；**长时间不动**说明卡住 |
| `Msg` | 失败/取消原因，排查第一现场 |
| `CreateTime` / `FinishTime` | 判断耗时是否符合预期 |

> [!danger] "Schema Change 卡住"的三种典型原因
> 1. **`WAITING_TXN` 长期不动**：有长事务/未提交的导入在挡着（等它结束才能推进）。看导入任务是否卡死或 label 未结束。
> 2. **`RUNNING` 但进度几乎不走**：BE 资源被其他任务（compaction、导入、其他 schema change）抢占，或者 tablet 太多/太大。查 BE 的 IO、compaction 队列，必要时把其他重任务错峰。
> 3. **反复失败**：常见于磁盘水位高（重量级变更要双份空间）、或个别 tablet 副本异常。先 `ADMIN SHOW REPLICA STATUS` 看副本健康度，再腾磁盘。

### 5.4 变更期间的注意事项

1. **轻量 vs 重量先判断**：能选轻量的操作（加 value 列、改列名、改 VARCHAR 长度）尽量用；必须重量级的（改类型、改顺序、改主键）排低峰期。
2. **磁盘余量**：重量级变更期间空间近似翻倍，提前确认水位。
3. **不要在变更期间同时上其他重活**（大批量导入、大 compaction、另一个 schema change），否则互相抢资源、都变慢。
4. **变更期间查询可用**，但性能可能波动（双写、后台重写抢 IO）。
5. **改排序键/改分区/改分桶**这类"重量级中的重量级"，很多版本实际上不支持原地改，只能**重建表 + 重灌**（`ALTER TABLE ... REPLACE` 可用来做表切换，实现近似"在线重建"）。
6. **变更前先 `SHOW CREATE TABLE` 存一份**，出问题时至少有原始 DDL 可对照。

## 六、分区管理与运维 SQL 速查

### 6.1 命令用途一览

| 命令 | 用途（一句话） |
| --- | --- |
| `SHOW TABLES [FROM db] [LIKE '%pat%']` | 看库里有哪些表 |
| `DESC tbl [ALL]` | 看列结构；`ALL` 会带出隐藏列等内部信息 |
| `SHOW COLUMNS FROM tbl` | 等价于看列信息（更细的字段） |
| `SHOW CREATE TABLE tbl` | **拿到权威的完整 DDL**（含分区、分桶、全部属性），排查/比对第一命令 |
| `SHOW PARTITIONS FROM tbl` | 看当前所有分区的区间、大小、行数、副本数 |
| `SHOW DATA [FROM tbl]` | 看数据量/行数（**结果含全部副本，需除以副本数得真实数据量**） |
| `SHOW TABLETS FROM tbl` | 看 tablet 级分布，判断单桶大小与倾斜 |
| `SHOW INDEX FROM tbl` | 看表上的索引（含倒排/NGRAM_BF 的 `IndexType`） |
| `SHOW DYNAMIC PARTITION TABLES` | 看动态分区表的调度情况与状态 |
| `ADMIN SHOW REPLICA STATUS FROM tbl` | 看副本是否健康/缺失（高可用排查） |
| `SHOW BACKENDS` / `SHOW FRONTENDS` | 看 BE/FE 节点状态、容量、是否存活 |
| `SHOW ALTER TABLE COLUMN` | 看 schema change 进度 |
| `SHOW ALTER TABLE ROLLUP` | 看 rollup / 物化索引变更进度 |

### 6.2 分区运维 DDL

```sql
-- 增加分区（只写右界，左界自动接续上一个分区）
ALTER TABLE ods_order ADD PARTITION p20261010 VALUES LESS THAN ("2026-10-11");

-- 增加分区：显式左闭右开区间
ALTER TABLE ods_order ADD PARTITION p20261011 VALUES [("2026-10-11"), ("2026-10-12"));

-- 增加分区：同时指定新分桶数与分区属性
ALTER TABLE ods_order ADD PARTITION p20261012 VALUES LESS THAN ("2026-10-13")
DISTRIBUTED BY HASH(`order_id`) BUCKETS 64
("replication_num" = "3");

-- 批量增加分区
ALTER TABLE ods_order ADD PARTITIONS FROM ("2026-10-01") TO ("2026-11-01") INTERVAL 1 DAY;

-- 删除分区（至少保留一个分区；一段时间内可用 RECOVER 恢复）
ALTER TABLE ods_order DROP PARTITION p20260101;

-- 强制删除分区：不检查未完成事务、且不可恢复（一般不要用）
ALTER TABLE ods_order DROP PARTITION p20260101 FORCE;

-- 批量删除分区
ALTER TABLE ods_order DROP PARTITION p20260101, DROP PARTITION p20260102;

-- 清空分区数据（保留分区结构，比 DROP+ADD 更省事，常用于重灌）
ALTER TABLE ods_order TRUNCATE PARTITION p20261009;

-- 修改分区属性（单分区 / 多分区 / 全部分区）
ALTER TABLE ods_order MODIFY PARTITION p20260101 SET ("replication_num" = "1");
ALTER TABLE ods_order MODIFY PARTITION (p20260101, p20260102) SET ("storage_medium" = "HDD");
ALTER TABLE ods_order MODIFY PARTITION (*) SET ("storage_medium" = "HDD");

-- LIST 分区：增加 default 分区（承接所有未匹配取值）
ALTER TABLE ods_order_list ADD PARTITION p_default;
```

分区级可修改的属性（`MODIFY PARTITION ... SET`）只有这几项：

| 属性 | 说明 |
| --- | --- |
| `storage_medium` | 存储介质（SSD/HDD） |
| `storage_cooldown_time` | 介质降级（冷却）时间点 |
| `replication_num` | 分区副本数 |
| `in_memory` | 是否常驻内存 |

> [!note] 关于 `ALTER TABLE ... MODIFY PARTITION ... SET` 的两个事实
> - 单分区表的 "partition name" 就是**表名**。
> - `MODIFY PARTITION (*)` 可以一次改所有分区，是做**冷热分层批量下沉**最方便的写法。

> [!warning] `ADD PARTITION` 的三个坑
> 1. **建表时如果一个分区都没显式创建**（只有空的 `()` 且没开动态/自动分区），**不支持通过 `ALTER` 增加分区**。所以"完全空分区定义"的表要配动态分区/自动分区才行。
> 2. 指定 `DISTRIBUTED BY HASH(...)` 却**不写 `BUCKETS n`** → 桶数用**默认 10**，不是建表时的桶数。**永远显式写 `BUCKETS`**。
> 3. `DROP PARTITION` 之后表里必须**至少保留一个分区**；`FORCE` 不检查未完成事务、且**不可恢复**，正常运维不要用。

## 七、索引 DDL

### 7.1 各类索引的创建方式对照

| 索引 | 在哪里声明 | 语法 |
| --- | --- | --- |
| 前缀索引 | 无需声明 | 自动建在排序键上（把过滤列设计成前导 key 列即可） |
| ZoneMap | 无需声明 | 自动建在每一列上 |
| **倒排索引** | 建表 `INDEX` 子句，或 `CREATE INDEX` | `INDEX idx (col) USING INVERTED [PROPERTIES(...)]` |
| **BloomFilter 索引** | **只能用表属性**（历史原因，语法与通用 `INDEX` 不同） | `PROPERTIES("bloom_filter_columns" = "c1,c2")` |
| **NGram BloomFilter 索引** | 建表 `INDEX` 子句，或 `CREATE INDEX` | `INDEX idx (col) USING NGRAM_BF PROPERTIES("gram_size"="3","bf_size"="1024")` |
| BITMAP 索引（历史） | — | 老版本 `USING BITMAP`；**新版本官方已说明"BITMAP 索引被倒排索引取代"**，新项目直接用倒排 |

### 7.2 倒排索引

```sql
-- 建表时声明
CREATE TABLE docs (
    `id`      BIGINT       NOT NULL,
    `title`   VARCHAR(256) NOT NULL,
    `content` TEXT,
    `tags`    ARRAY<VARCHAR(32)>,
    INDEX idx_title (`title`) USING INVERTED PROPERTIES("parser" = "chinese"),
    INDEX idx_content (`content`) USING INVERTED
        PROPERTIES("parser" = "chinese", "support_phrase" = "true"),
    INDEX idx_tags (`tags`) USING INVERTED
)
ENGINE=OLAP
DUPLICATE KEY(`id`)
DISTRIBUTED BY HASH(`id`) BUCKETS 10
PROPERTIES ("replication_num" = "3");

-- 对已有表创建索引
CREATE INDEX idx_tagname ON docs (`title`) USING INVERTED PROPERTIES("parser" = "chinese");

-- 为存量数据构建索引（大表耗时较长）
BUILD INDEX idx_tagname ON docs;

-- 查看索引（IndexType 会显示 INVERTED / NGRAM_BF 等）
SHOW INDEX FROM docs;
SHOW CREATE TABLE docs;

-- 删除索引
DROP INDEX idx_tagname ON docs;
-- 老版本 ALAO 写法，同样可用
ALTER TABLE docs DROP INDEX idx_tagname;
```

常见 `PROPERTIES`（倒排索引）：

| 属性 | 作用 |
| --- | --- |
| `parser` | 分词器，如 `english` / `chinese` / `unicode` / `icu` / `basic` / `ik` |
| `parser_mode` | 中文分词模式，如 `fine_grained`（细粒度，召回更高、索引更大） |
| `support_phrase` | 是否支持短语查询（`MATCH_PHRASE`），开启会增加索引体积 |
| `lower_case` / `stopwords` | 大小写归一、停用词 |

支持的查询形态（定性）：等值、`IN`、范围、`IS NULL`、`MATCH_ANY` / `MATCH_ALL` / `MATCH_PHRASE` / `MATCH_PHRASE_PREFIX` / `MATCH_REGEXP`，以及数组类函数（`array_contains`、`array_overlaps`）等。`LIKE` 不在倒排的加速范围内——那要用 NGRAM_BF。

### 7.3 BloomFilter 索引

```sql
-- 建表时通过属性指定（不是 INDEX 语法）
CREATE TABLE dim_order (
    `dt`       DATE   NOT NULL,
    `order_id` BIGINT NOT NULL,
    `user_id`  BIGINT NOT NULL,
    `amount`   DECIMAL(18, 2)
)
ENGINE=OLAP
UNIQUE KEY(`dt`, `order_id`)
DISTRIBUTED BY HASH(`order_id`) BUCKETS 32
PROPERTIES (
    "replication_num" = "3",
    "enable_unique_key_merge_on_write" = "true",
    "bloom_filter_columns" = "order_id,user_id"
);

-- 已有表新增/删除 BloomFilter 列：整体重设这个属性
ALTER TABLE dim_order SET ("bloom_filter_columns" = "order_id,user_id,amount");
ALTER TABLE dim_order SET ("bloom_filter_columns" = "order_id");

-- 查看（体现在 SHOW CREATE TABLE 里）
SHOW CREATE TABLE dim_order;
```

要点：**各列的 BloomFilter 是独立索引，不是组合索引**；只加速**等值/`IN`**，对范围查询与 `LIKE` 无效；成本很低，是高基数列点查的"性价比之王"。

### 7.4 NGram BloomFilter 索引（加速 `LIKE '%x%'`）

```sql
-- 建表时
CREATE TABLE review (
    `id`     BIGINT NOT NULL,
    `body`   VARCHAR(4096),
    INDEX idx_body (`body`) USING NGRAM_BF
        PROPERTIES("gram_size" = "3", "bf_size" = "1024")
)
ENGINE=OLAP
DUPLICATE KEY(`id`)
DISTRIBUTED BY HASH(`id`) BUCKETS 8
PROPERTIES ("replication_num" = "3");

-- 已有表
CREATE INDEX idx_body2 ON review (`body`) USING NGRAM_BF
    PROPERTIES("gram_size" = "3", "bf_size" = "1024");
ALTER TABLE review DROP INDEX idx_body2;
```

原理：把文本切成 n-gram 存进 BloomFilter，`LIKE` 时对 pattern 做同样切分，**任一个 token 缺失就整块跳过**。所以它加速的是 `LIKE`，**不加速 `=`**。

| 属性 | 作用 |
| --- | --- |
| `gram_size` | n-gram 的 n。越大越省空间、误判概率越高（跳过更少） |
| `bf_size` | BloomFilter 位图大小（字节）。越大越精确、越占空间 |

### 7.5 索引的代价（建之前先想清楚）

| 索引 | 存储代价 | 写入代价 | 什么时候值得建 |
| --- | --- | --- | --- |
| 前缀索引 / ZoneMap | 极小 | 无（自动） | 永远先用满 |
| BloomFilter | 小 | 小 | 高基数列点查（**优先加**） |
| 倒排索引 | **较大，可能与原始数据相当** | **明显**（写入放大 + compaction 更重） | 等值/范围/全文检索等通用过滤，且 profile 证明收益 |
| NGram BloomFilter | 中等 | 中等 | 只有 `LIKE '%x%'` 子串查询 |
| 行存（`store_row_column`） | **通常是原表 2~10 倍** | 明显 | 高并发主键点查 / 宽表 TOPN（**且建表后不能 ALTER**） |

> [!tip] 有一个"推迟写索引"的开关
> 表属性 `skip_write_index_on_load = "true"` 可以**导入时不写索引（目前仅对倒排索引生效），改到 compaction 时延迟构建**，避免"首次写入和 compaction 重复写索引"的 CPU/IO 浪费。这是**高吞吐导入**场景很实用的优化，代价是索引在一段时间内不可用（查询暂时享受不到加速）。

## 八、`PROPERTIES` 详解表

### 8.1 属性速查

| 属性 | 取值 | 建议 / 说明 |
| --- | --- | --- |
| `replication_num` | 正整数 | **默认 3**；BE 数少于 3 时必须设成 ≤ BE 数。自 0.15 起会自动转成 `replication_allocation`（如 `3` → `tag.location.default:3`）。生产用 3，本地/测试用 1 |
| `replication_allocation` | `tag.location.<tag>:<n>` | 按标签描述副本分布，表达力强于 `replication_num`，可完全覆盖它 |
| `min_load_replica_num` | 整数，默认 `-1` | 导入成功所需的最小副本数；**小于等于 0 表示仍需多数派副本成功**。提高它会更"稳"但更容易导入失败 |
| `storage_medium` | `SSD` / `HDD` | 数据的初始存储介质，冷热分层起点 |
| `storage_cooldown_time` | 时间字符串 | 超过该时间后自动降级到更低一级介质。**配 TTL 归档而不是直接删数据** |
| `storage_policy` | 策略名 | 通过存储策略做冷热分层/远端存储迁移（比单机 `storage_medium` 更完整，适合湖仓/对象存储） |
| `colocate_with` | group 名 | 启用 Colocation Join；把需要 JOIN 且分桶一致的几张表放进同一 group |
| `bloom_filter_columns` | `"c1,c2"` | BloomFilter 索引列（等值过滤）。**性价比最高的手动索引** |
| `compression` | `LZ4F` / `ZSTD` / `ZLIB` / `SNAPPY` | **4.0.3 起默认 ZSTD**；4.0.3 之前默认 LZ4F。ZSTD 压缩率更高但更吃 CPU |
| `enable_unique_key_merge_on_write` | `true` / `false` | **2.1 之前默认关闭，2.1 起默认开启**。仍建议显式写 `true`。MoM 与 MoR **只能在建表时确定、之后不能用 schema change 改** |
| `enable_persistent_index` | `true` / `false` | 把 Unique(MoW) 的主键索引持久化到磁盘，**降低内存占用**，代价是索引查询多一次 IO。大表/回灌必看 |
| `light_schema_change` | `true` / `false` | **2.0.0 起默认开启**。开启后 value 列的加减可**同步、秒级**完成 |
| `function_column.sequence_col` | 列名 | **Sequence 列**：Unique 表里同一 Key 的新旧数据按该列比较，**较大值才替换较小值**。列可为整型或时间类型，建表后**不能改类型** |
| `function_column.sequence_type` | `DATE`/`DATETIME`/`TIMESTAMP_NS`/整型 | 只声明类型，Doris 会创建一个隐藏的 sequence 列。与 `sequence_col` 同时存在时后者优先 |
| `disable_auto_compaction` | `true` / `false` | 置 true 后后台自动 compaction **跳过该表的所有 tablet**。**不要为了"导入时别抢资源"随手开它** |
| `compaction_policy` | `time_series` / `size_based` | `time_series`（时序场景）按累积体积触发合并并直接晋级 base compaction，**降低持续导入下的写放大**；配套 `time_series_compaction_*` 参数 |
| `skip_write_index_on_load` | `true` / `false` | 导入时不写索引（目前仅倒排），延迟到 compaction 时构建。**高吞吐导入优化** |
| `group_commit_interval_ms` | 毫秒 | Group Commit 攒批间隔（默认 10s 量级），与下面一项**谁先到就下刷** |
| `group_commit_data_bytes` | 字节 | Group Commit 攒批数据大小（默认 128MB 量级） |
| `enable_mow_light_delete` | `true` / `false` | Unique MoW 上让 `DELETE` 走 delete predicate，提升删除性能；**代价是删除后再做部分列更新可能出现数据错误**。默认 false，了解风险再开 |
| `enable_unique_key_skip_bitmap_column` | `true` / `false` | Unique MoW 上开启"灵活部分列更新"能力 |
| `store_row_column` | `true` / `false` | **全列行存**（2.0+）。**建表后不可 ALTER**；额外存储通常是原表 2~10 倍 |
| `row_store_columns` | `"c1,c2"` | **部分列行存**（3.0+），会隐式启用 `store_row_column`；比全列行存省很多。**同样不可 ALTER** |
| `row_store_page_size` | 字节，默认 16384 | 行存 page 大小；调小（4KB）点查更快但更占空间，调大（64KB+）省空间但延迟更高 |
| `estimate_partition_size` | 如 `"100G"` | 仅供 `BUCKETS AUTO` 估算单分区数据量；**不支持 ALTER** |
| `dynamic_partition.*` | 见第三节 | 动态分区全套属性 |
| `enable_duplicate_without_keys_by_default` | `true` / `false` | 置 true 时，建表不指定模型会默认建一张**没有排序列和前缀索引**的 Duplicate 表（谨慎使用） |
| `binlog.enable` / `binlog.format` | `true` / `"ROW"` | 行级变更日志（版本较新才支持），用于增量消费；**只能在建表时开启、之后不可关闭** |

### 8.2 三个"值得单独强调"的属性

**（1）`function_column.sequence_col`：解决乱序更新**

CDC/多上游写入时，同一主键的数据可能**乱序到达**（旧值后到，把新值覆盖掉）。Sequence 列让 Doris 按该列判断：

```sql
CREATE TABLE dim_order_seq (
    `dt`          DATE   NOT NULL,
    `order_id`    BIGINT NOT NULL,
    `order_status` TINYINT,
    `update_time` DATETIME,
    `amount`      DECIMAL(18, 2)
)
ENGINE=OLAP
UNIQUE KEY(`dt`, `order_id`)
DISTRIBUTED BY HASH(`order_id`) BUCKETS 16
PROPERTIES (
    "replication_num" = "3",
    "enable_unique_key_merge_on_write" = "true",
    "function_column.sequence_col" = "update_time"
);
```

语义：同一 Key 的多行里，**只有 sequence 列更大的那一行才会替换已有行**（更小的直接丢弃）。这是 Flink CDC 乱序场景的关键配置（用法见 [[6-数据导入与FlinkCDC]]）。

**（2）`enable_persistent_index`：主键索引的内存/磁盘取舍**

Unique MoW 需要维护"主键 → 行位置"的索引。这个索引**默认在内存里**，主键列宽、行数多时会吃掉大量内存；`enable_persistent_index=true` 把它落到磁盘，省内存但点查/写入时多一次索引 IO。**大表或历史回灌前一定评估**。

**（3）`compression`：CPU 与 IO 的换算**

自 **4.0.3 起默认 ZSTD**（此前默认 LZ4F）。ZSTD 压缩率更好 → 磁盘占用更低、扫描 IO 更少；但**解压更吃 CPU**。IO 受限的集群受益，CPU 受限的集群可能变差。换压缩算法**只影响新写入的数据**，已有数据不会自动重压。

## 九、修改表属性

```sql
-- 通用形式
ALTER TABLE [db.]tbl SET ( "key" = "value" [, ...] );

-- 开/关动态分区
ALTER TABLE dwd_log SET ("dynamic_partition.enable" = "false");

-- 改副本分布
ALTER TABLE dwd_log SET ("replication_allocation" = "tag.location.default:3");

-- 改压缩算法（只影响之后写入的数据）
ALTER TABLE dwd_log SET ("compression" = "ZSTD");

-- 调整 BloomFilter 列
ALTER TABLE dim_order SET ("bloom_filter_columns" = "order_id,user_id");

-- 冷热分层
ALTER TABLE dwd_log SET (
    "storage_medium" = "SSD",
    "storage_cooldown_time" = "2026-11-09 00:00:00"
);

-- 只改某个分区的属性（见第六节）
ALTER TABLE dwd_log MODIFY PARTITION p20260101 SET ("storage_medium" = "HDD");
```

| 注意 | 说明 |
| --- | --- |
| 不是所有属性都能改 | `estimate_partition_size`、`store_row_column`、`row_store_columns`、Unique 的 MoW/MoR 选择、`function_column.sequence_col` 的列类型等**都不能改** |
| 有些"改了也不重建历史数据" | 例如 `compression`、分桶数相关的属性：只影响后续写入/新建分区 |
| 动态分区属性改完不立即生效 | 受 `dynamic_partition_check_interval_seconds` 周期控制 |
| 属性有依赖 | 例如 `store_row_column` 与 `row_store_columns`、MoW 与部分列更新/行存/持久化索引之间存在前置关系，改之前先查手册 |

## 十、常见报错与解决

| # | 报错 / 现象 | 根因 | 解决 |
| --- | --- | --- | --- |
| 1 | `Key columns should be a ordered prefix of the schema` | KEY 列没排在 schema 最前面 | 把 KEY 列提到最前，或换 KEY；改不了就重建表 |
| 2 | `Key column[...] should not be nullable` / key 列类型不被支持 | KEY 列用了可空类型或 `FLOAT`/`DOUBLE` 等不适合做 key/分桶的类型 | KEY/分桶列改用整型、`VARCHAR`、`DATE`/`DATETIME`、`DECIMAL` 等 |
| 3 | `Failed to find enough host with storage medium...` / `replication_num` 相关错误 | `replication_num`（或 `replication_allocation` 总数）**超过可用 BE 数/磁盘数** | 降低副本数（单机测试用 1），或先加 BE；也可用标签让副本落到有容量的位置 |
| 4 | `Partition[xxx] is duplicate` / 区间重叠 | 分区名重复，或两个分区区间**重叠** | 检查 `SHOW PARTITIONS`，改名/改边界；用 `FROM..TO..INTERVAL` 批量生成更不容易错 |
| 5 | 导入报 `no partition for this tuple` / `Tablet not found` | 数据落在**分区空洞**里（`LESS THAN` 边界写错、多列分区留洞、`DATETIME` 分区只写到天） | `SHOW PARTITIONS` 核对区间；补 `ADD PARTITION`；考虑开动态分区或自动分区 |
| 6 | 建表时 `BUCKETS` 过大导致超时/报错 | 桶数过多 → 一次性创建海量 tablet，元数据操作超时 | 按"单 tablet 1~10G"重算桶数；必要时减少分区数；分批建分区 |
| 7 | `Cannot change distribution type` / `Cannot assign hash distribution with different distribution cols` | `MODIFY DISTRIBUTION` 试图改分布类型或分桶列 | 只能改桶数；要换分桶列必须重建表 |
| 8 | `Only support change partitioned table's distribution` | 对未分区表做 `MODIFY DISTRIBUTION` | 改成带分区的表，或接受重建 |
| 9 | `Cannot change default bucket number of colocate table` | Colocate 表不支持改默认桶数 | 先解除 Colocate 关系，或重建 |
| 10 | `ADD PARTITION` 后新分区桶数不对（变成 10） | 指定了 `DISTRIBUTED BY HASH(...)` 但没写 `BUCKETS n`，走了默认值 | 显式写 `BUCKETS n` |
| 11 | 建表时未显式创建分区，之后 `ALTER ... ADD PARTITION` 报错 | 完全空分区定义的表不支持用 ALTER 加分区 | 建表时给至少一个分区，或直接配动态分区/自动分区 |
| 12 | 动态分区**不生效** | ① FE `dynamic_partition_enable` 未开；② 表级 `enable` 为 false；③ 未到 `dynamic_partition_check_interval_seconds` 周期；④ 时区/`start`/`end` 写反；⑤ `create_history_partition` 没开导致历史分区缺失 | 按 ①②③④⑤ 顺序排查；`SHOW DYNAMIC PARTITION TABLES` 看 `State`/`Last*Msg` |
| 13 | `create_history_partition` 报分区数超限 | 要创建的分区数 > FE `max_dynamic_partition_num` | 分批创建，或调大该 FE 参数 |
| 14 | Schema Change 长期 `WAITING_TXN` | 有长事务/未结束的导入在挡 | 查并结束卡住的导入事务/label |
| 15 | Schema Change `RUNNING` 但进度不动 | BE 资源被 compaction/导入/其他变更抢占，或 tablet 过多过大 | 错峰执行；查 BE IO 与 compaction 队列；先减少并行重任务 |
| 16 | 重量级 Schema Change 失败或磁盘写满 | 变更期间数据**双写**，存储近似翻倍 | 提前清磁盘/扩盘；低峰期执行；分批（按分区）做 |
| 17 | 加索引后**导入变慢** | 倒排索引带来写入放大，且与 compaction 重复写索引 | 只为确有收益的列建索引；考虑 `skip_write_index_on_load`；上线前压测导入吞吐 |
| 18 | `LIKE '%x%'` 依然很慢（已加倒排） | **倒排索引不加速 `LIKE`** | 用 `USING NGRAM_BF` 建索引 |
| 19 | 行存想后补却报错 | `store_row_column`/`row_store_columns` **不支持 ALTER** | 只能重建表（可用新表 + 数据迁移/`ALTER TABLE ... REPLACE` 切换） |
| 20 | 导入时 BE 内存飙升（Unique MoW 大 batch） | MoW 要维护主键索引与删除标记，大 batch 吃内存 | 开 `enable_persistent_index`；拆分导入批次；避免一次性回灌过大数据 |
| 21 | 删了数据磁盘没降 | 删除只写标记，要靠 compaction 真正回收 | 等 compaction 或手动触发 optimize；确认自动 compaction 没被 `disable_auto_compaction` 关掉 |
| 22 | 查询很慢，`EXPLAIN` 显示扫了所有分区 | 分区列上套了函数，或没带分区列条件 | 把函数套在常量上（`dt >= date_sub(now(),7)`），或强制查询带上分区列 |

## 十一、必答与自测

> [!important] 必答 1：`VALUES LESS THAN` 的边界到底含不含？
> **`LESS THAN` 是上界且"不含"**，分区整体是**左闭右开**区间 `[左界, 上界)`；**左界由 Doris 自动接续前一个分区的上界**（只写右界即可）。
> 所以 `PARTITION p20261009 VALUES LESS THAN ("2026-10-10")` 装的是 `dt < '2026-10-10'`，**包含 10-09**，不包含 10-10。要让 10-10 有地方去，必须再有一个 `LESS THAN ("2026-10-11")` 的分区，或者用 `MAXVALUE` 兜底。
> 两个高频翻车点：**① 把 `LESS THAN ('2026-10-09')` 当成"包含 10-09"** → 10-09 的数据找不到分区；**② 用 `DATETIME` 列做分区但上界只写到天** → 当天 00:00 之后的数据全部溢出。诊断口诀：`SHOW PARTITIONS` 看区间，`count(*)` 验证数据是否真的落进去了。

> [!important] 必答 2：分桶数怎么定？
> 分层次回答：
> - **先看乘积**：`tablet 总数 = 分区数 × 分桶数`。分桶数不能孤立定。
> - **按数据量**：官方建议**单个 tablet 落在 1G~10G**，所以 `分桶数 ≈ 单分区数据量 ÷ 目标单桶大小(2~5G)`。太小 → 导入元数据开销大、compaction 任务爆炸、FE 元数据压力大；太大 → 副本迁移/补齐慢，schema change 与 rollup 的重试粒度是 tablet，很痛。
> - **按集群规模校验**：不考虑扩容时 tablet 总数**略多于集群磁盘总数**为宜；两条原则冲突时**优先数据量原则**。
> - **量级参考**：几百 MB → 4~8 桶；约 5GB → 8~16；约 50GB → 32；500GB 以上**先分区**，让单分区约 50GB、每分区 16~32 桶。
> - **必须预留扩容**：官方手册明确**分桶数一旦指定就不能修改**（`MODIFY DISTRIBUTION` 只改**新分区**的默认值，存量分区不变）。这是"必须一次定对"的最强理由。
> - **分桶列的选择同样重要**：高基数、分布均匀、常用于等值过滤或 JOIN（Aggregate/Unique 下必须是 KEY 列）。分桶列多 → 分布均匀但点查扫所有桶（高吞吐低并发）；分桶列少 → 点查精准落一个桶（高并发点查）。
> - **落地校验**：`SHOW DATA`（记得**除以副本数**）、`SHOW TABLETS` 看真实单桶大小与倾斜。
> - **拿不准时**：用 `BUCKETS AUTO` + `estimate_partition_size` 让系统推算，但要记得 `estimate_partition_size` 不支持 ALTER，且冷启动阶段估算不准。

> [!important] 必答 3：什么是轻量级 Schema Change？
> **轻量级 Schema Change 只修改元数据、不重写数据文件**，所以通常**秒级、近乎同步完成**，对系统性能影响很小。典型操作：**增加/删除 Value 列、修改列名、修改 `VARCHAR` 列长度**（注意 **UNIQUE 和 DUP 表的 Key 列除外**）。它由 `light_schema_change` 属性控制，**自 2.0.0 起默认开启**。
> 相对的是**重量级 Schema Change**：需要 BE 后台**以 tablet 为单位重写数据**，流程是"转换期间双写新旧 tablet → 完成后删除旧 tablet"。耗时从分钟级到天级（取决于数据量），期间**存储空间近似翻倍**、占用大量计算资源。典型操作：**修改列的数据类型、把 `NOT NULL` 改成 `NULL`、更改主键、修改列排序顺序**。
> 所以工程结论是：**能用轻量操作解决的（加 value 列、改列名、扩 VARCHAR 长度）就绝不走重量级；必须走重量级时排低峰期、先确认磁盘余量、并把 schema change 与其他重任务（大批导入/大 compaction/另一个 schema change）错开。**
