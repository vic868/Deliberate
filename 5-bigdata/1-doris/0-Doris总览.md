## 三、30 秒速查表

| 问题 | 一句话答案 | 详见 |
|---|---|---|
| Doris 是什么 | **MPP 架构的列式 OLAP 数据库**，主打**实时写入 + 高并发查询 + 易运维** | [[1-架构与原理]] |
| 架构角色 | **FE**（前台：元数据、解析优化、调度）+ **BE**（后台：存储与计算） | [[1-架构与原理]] |
| 怎么选数据模型 | 要保留所有原始行 → Duplicate；要按主键更新 → **Unique + MoW**；只要指标 → Aggregate | [[2-数据模型]] |
| `DUPLICATE KEY` 是唯一约束吗 | **不是！** 它只是**排序键**，不保证唯一 | [[2-数据模型]] |
| MoW 是什么 | **Merge-on-Write**：Unique 模型在写入时合并，读时无需合并，**读性能大幅提升** | [[2-数据模型]] |
| 前缀索引吃什么 | 只吃**排序键的最左前缀**（约前 36 字节）→ 过滤字段要往前放 | [[2-数据模型]] |
| 分区和分桶啥区别 | 分区（PARTITION）做**数据裁剪**（按时间/范围），分桶（BUCKET）做**数据打散与并行** | [[4-建表与分区分桶]] |
| 分桶数怎么定 | 按数据量估算单桶大小，**别多别少**；建好后调整代价大 | [[3-表设计]] |
| 数据怎么导入 | Kafka 常驻 → **Routine Load**；Flink 写入 → **Doris Connector**；批量文件 → **Broker Load** | [[6-数据导入与FlinkCDC]] |
| Flink 写 Doris 怎么不重 | **`label` 幂等** + 攒批 + `DeliveryGuarantee.EXACTLY_ONCE`(2PC) | [[6-数据导入与FlinkCDC]] |
| 慢 SQL 怎么查 | `EXPLAIN` 看计划 → `PROFILE` 看真实耗时 → 查分区裁剪/索引/Join 方式 | [[5-查询优化]] |
| 四种 Join | Broadcast / Shuffle / **Bucket Shuffle** / **Colocate**（分桶键一致则零 shuffle） | [[5-查询优化]] |
| 什么是 `-235` | 导入太频繁导致**版本堆积、Compaction 跟不上**；治本靠攒批与 Compaction 调优 | [[8-运维与调优]] |
| 能直接查数据湖吗 | 能，通过 **External Catalog** 联邦查询 Hive/Iceberg/Hudi/Paimon | [[7-湖仓一体]] |
| 存算分离何时引入 | **3.0** 起支持；4.x 继续增强；适合弹性与负载隔离场景 | [[7-湖仓一体]]、[[1-架构与原理]] |
| Doris vs ClickHouse | 要**频繁更新/复杂 join/高并发**选 Doris；海量明细单表聚合可用 ClickHouse | [[9-对比StarRocks与ClickHouse]] |

## 四、核心概念最小记忆集

| 概念 | 精确定义 | 常见误解 |
|---|---|---|
| **FE (Frontend)** | 元数据管理、SQL 解析与优化、查询计划生成与调度；有 Follower/Observer 角色 | 以为 FE 只做转发 |
| **BE (Backend)** | 数据存储与计算执行；tablet 落在 BE 上 | 与 FE 职责混淆 |
| **Tablet** | 表的**最小数据分片单位** = 一个分桶在一个分区里的副本 | 以为是文件 |
| **Partition** | 逻辑上的数据分区（通常按时间），用于**裁剪** | 与分桶混淆 |
| **Bucket** | 按 Hash 分桶，决定**并行度与数据分布** | 以为分桶越多越快 |
| **排序键 / KEY** | 决定数据物理排序（Doris 按此建前缀索引） | **以为 DUPLICATE KEY 是唯一约束** |
| **前缀索引** | 基于排序键前若干字节的稀疏索引，**最左前缀匹配** | 以为所有列都能吃到索引 |
| **ZoneMap** | 每列的 min/max 索引，用于范围过滤 | —— |
| **MoW** | Merge-on-Write，Unique 模型写入时合并，读时不合并 | 与读时合并（ROM）混淆 |
| **Compaction** | 后台把多个数据版本合并成大版本，**减轻读放大** | 以为它只是"清理" |
| **Label** | 导入事务的**幂等标识**，同 label 重复提交视为同一事务 | 以为 label 只是日志 |
| **Catalog** | 数据源目录；Internal Catalog 是 Doris 自己的数据，External 是外部湖 | —— |
| **Colocate Group** | 分桶键与分桶数一致的一组表，可**本地 Join、零 Shuffle** | 忽视它对建表的影响 |
| **Workload Group** | 资源组，用于 CPU/内存/并发的**隔离与限流** | —— |

> [!warning] 五个最经典的面试陷阱
> 1. **"`DUPLICATE KEY` 是唯一键"** —— 错。它只是排序键；要唯一必须用 **Unique 模型**。
> 2. **"Unique 模型一定慢"** —— 老版本读时合并确实慢，**1.2+ 的 MoW 已大幅改善**，生产应开 `enable_unique_key_merge_on_write`。
> 3. **"分桶数越多查询越快"** —— 错。分桶过多会产生大量小 tablet，**加重元数据与 Compaction 压力**。
> 4. **"分区列上做函数运算还能裁剪"** —— 不能。`DATE_FORMAT(dt,'%Y%m%d')='20240101'` 会让分区裁剪失效，要改成对常量做运算。
> 5. **"开了 Stream Load 就不会重复"** —— 只有当 **label 相同**时才有幂等效果；label 每次变化（比如用 UUID）就等于放弃幂等。

## 五、版本演进与选型要点

| 版本 | 里程碑 | 对使用者的影响 |
|---|---|---|
| 1.2 | **Unique 模型 Merge-on-Write（MoW）** | 主键模型终于能兼顾写入与读取性能 |
| 2.0 | 倒排索引、更完善的优化器与物化视图 | 点查与半结构化查询能力提升 |
| **2.1** | **VARIANT 类型**、异步物化视图、子查询与湖分析性能大幅增强 | 半结构化与湖仓场景可用性提升 |
| **3.0** | **存算分离架构**（计算存储解耦） | 云原生部署、负载隔离、弹性扩缩容 |
| 3.1 | 半结构化分析里程碑：稀疏列/模板化 schema、湖仓增强、灵活列更新 | 宽表与湖仓一体更进一步 |
| 4.0 / 4.1 | 持续迭代（MoW 表 ANN 索引、多模态/向量能力、CDC Streaming Job 等） | 新特性叠加，**上线前以官方文档为准** |

> [!note] 本系列的口径
> 以 **3.x 为基线**表述，涉及 3.0 引入的**存算分离**、4.x 的新能力会明确标注版本。
> 版本细节以官方 [Doris Core 发布说明](https://doris.apache.org/zh-CN/releases/core) 为准。

## 六、Doris 在实时数仓中的位置

```
MySQL/业务库 ──CDC──┐
                     ├──▶ Kafka ──▶ Flink（清洗/去重/聚合/维表） ──┬──▶ Doris（DWS/ADS：高并发查询、报表、API）
日志/埋点 ───────────┘                                             │        ▲
                                                                   └──▶ 数据湖 Iceberg/Paimon（ODS/DWD 明细、低成本）
                                                                            │
                                                              Doris External Catalog 直接查湖
```
