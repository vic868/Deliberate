# 🧱 二、Doris 数据模型

> 本篇回答四个问题：为什么 OLAP 引擎不能照搬 MySQL 那一套（行存 + 事务隔离），而要在**存储布局**和**数据模型**上另起炉灶？**Duplicate / Unique / Aggregate** 三种模型各自在什么负载下成立、代价在哪里？同一个 `KEY` 关键字在三种模型里的语义**完全不同**，怎么避免踩坑？以及排序键、前缀索引、ZoneMap、Bloom Filter、倒排索引、行列混存这些机制是怎么把"查询快"落到实处的？

## 一、为什么 OLAP 要分"数据模型"

### 1.1 先看 MySQL 那套为什么不够用

MySQL/InnoDB 的默认假设和数仓查询的假设**几乎相反**：

| 维度 | MySQL（OLTP 行存） | Doris（OLAP 列存） |
| --- | --- | --- |
| 存储布局 | 按**行**连续存，一行所有列挨在一起 | 按**列**分文件存，同列的值连续 |
| 一次 IO 拿到的数据 | 整行（哪怕只查 1 列） | 只有查询涉及的列（**列裁剪**） |
| 典型查询 | `WHERE id = ?` 主键点查，读写几行 | `WHERE dt BETWEEN ... GROUP BY ...` 扫百万行、算几列 |
| 数据组织 | B+ 树按主键有序 | 按**排序键**有序 + 稀疏索引 + 分区裁剪 |
| 更新语义 | 原地更新（undo/redo 保证事务） | **追加写**（Append-only），更新靠模型语义与 compaction 实现 |
| 并发模型 | 高并发小事务 | 低并发大扫描（MPP 并行） |
| 压缩 | 有限（行存难压） | 极好（同列同类型、有序，压缩比通常远高于行存） |

关键差距有两点：

1. **列存 + 排序键**让"扫几列 + 按范围过滤"变得极便宜：数据在磁盘上就是按查询常用维度排好序的，过滤时能直接跳过大量数据块。
2. 数仓要面对**同一个业务事实的不同消费方式**：`INSERT` 进来的可能是"每一次点击"，但看板要的是"每个广告每分钟的点击总数"。MySQL 只能用明细表 + 实时 `GROUP BY`（贵）或预聚合表 + 定时任务（慢）。Doris 的思路是：**在存储层就用模型的语义把这个聚合/去重做掉**。

### 1.2 Doris 的两个核心存储思想

**（1）列式存储 + 排序键（Sort Key）**

Doris 表在物理上被切成一个个 **Tablet**（= 一个分区 × 一个分桶）。每个 Tablet 内部的多个 **Rowset** 各自按**排序键**有序排列。排序键就是建表时 `DUPLICATE KEY` / `UNIQUE KEY` / `AGGREGATE KEY` 后面那串列。

```text
Tablet（一分区 × 一分桶）
├── Rowset 1（有序）: [2026-10-01, A, ...] [2026-10-01, B, ...] [2026-10-02, A, ...] ...
├── Rowset 2（有序）: ...                  ← 新导入的一批，内部也有序
└── Rowset 3 ...
        ↑ 查询时多个 Rowset 归并（merge-on-read）或由 compaction 合成一个
```

排序带来三个直接收益：
- 同列数据聚在一起 → **压缩率高**（游程编码、字典编码效果极好）；这直接决定扫描的 IO 量。
- 有序 → 范围内连续读，顺序 IO 而非随机 IO。
- 有序 → 可以建**稀疏的前缀索引**（见第七节），用极小的索引代价定位数据块。

**（2）"同一个表按不同模型建，承担不同负载"**

这是 Doris 设计上非常值得理解的一点：三种数据模型在**物理存储层**是同一套东西（列存 + Rowset + Tablet），差别只在 **导入时如何合并、查询时如何解读**。所以：

> [!important] 模型不是"表的类型"，而是"这份数据在存储层被承诺的语义"
> - 承诺"每一行都在" → Duplicate
> - 承诺"同一个 key 只有一行" → Unique
> - 承诺"同一个 key 只有一行，且 value 是聚合结果" → Aggregate
>
> 承诺越强，**写入代价越高**（要判断/合并），但**查询越省**（不用现场去重/聚合）。选模型本质是在"写入放大"和"读取放大"之间选一个点。

### 1.3 一个具体例子：同一份点击流，三种建模

原始数据是每次曝光/点击一行：

```text
dt=2026-10-01, ad_id=1001, user_id=U1, city=beijing, is_click=1
dt=2026-10-01, ad_id=1001, user_id=U2, city=beijing, is_click=1
dt=2026-10-01, ad_id=1001, user_id=U1, city=beijing, is_click=0
```

| 建模方式 | 存储后的样子 | 适合回答 |
| --- | --- | --- |
| **Duplicate** | 原样 3 行都在 | "U1 今天点了几次""原始日志回溯" |
| **Unique (dt, ad_id, user_id)** | 2 行（U1 保留最后一条，即 `is_click=0`） | "U1 最新一次是否点击"——**注意这会丢掉点击次数** |
| **Aggregate (dt, ad_id, city) + SUM(is_click), BITMAP_UNION(user_id)** | 1 行：`click=1, uv={U1,U2}` | "这个广告今天的点击数和去重人数" |

同一个 `KEY(dt, ad_id, ...)`，三种模型给出三种不同的世界。**如果没有先想清楚要回答什么问题，KEY 选错就等于数据错了。**

## 二、三种模型总览与选型逻辑

### 2.1 一句话区分

| 模型 | 声明关键字 | 一句话语义 |
| --- | --- | --- |
| Duplicate 明细 | `DUPLICATE KEY(...)` | KEY 只是**排序键**，行不去重不聚合，全部保留 |
| Unique 唯一 | `UNIQUE KEY(...)` | KEY 是**唯一约束**，同 key 新行覆盖旧行 |
| Aggregate 聚合 | `AGGREGATE KEY(...)` | KEY 是**聚合维度**，同 key 的 value 按聚合函数合并 |

### 2.2 选型决策树

```text
需要保留每一次原始行为（可回溯、可重算）？
├── 是 ──► 需要按主键做更新/去重吗？
│           ├── 是 ──► Unique（订单、维表、CDC 同步）
│           └── 否 ──► Duplicate（日志、埋点、明细宽表）
└── 否 ──► 只关心聚合后的指标（点击/曝光/GMV/UV）？
            ├── 是，且指标固定、查询量极大 ──► Aggregate（预聚合，配 Rollup/MV 更进一步）
            └── 否，只是"暂时没有明细需求" ──► 优先 Duplicate，别急着 Aggregate
```

> [!warning] 最常见的选型错误
> **"暂时不需要明细"就上 Aggregate。** Aggregate 是**有损且不可逆**的：一旦某个维度被聚合掉，后续任何"我想按这个维度再看一眼"的需求都得回原始数据重刷。除非指标口径已经冻结、且写入压力/查询压力确实需要用预聚合换性能，否则从 Duplicate 或 Unique 起步更安全。

## 三、Duplicate 明细模型

### 3.1 语义

`DUPLICATE KEY` 声明的是**排序键**（sort key），**不是唯一约束，也不做任何去重**。写入 N 行就有 N 行，哪怕所有列完全一样。

```sql
CREATE TABLE IF NOT EXISTS dwd_user_action_log (
    `dt`          DATE         NOT NULL COMMENT '分区日期',
    `log_time`    DATETIME     NOT NULL COMMENT '事件时间',
    `user_id`     BIGINT       NOT NULL COMMENT '用户 id',
    `event`       VARCHAR(32)  NOT NULL COMMENT '事件类型',
    `page_id`     VARCHAR(64)           COMMENT '页面 id',
    `device`      VARCHAR(32)           COMMENT '设备',
    `duration_ms` INT                   COMMENT '停留时长(ms)',
    `props`       VARCHAR(512)          COMMENT '扩展属性'
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `log_time`, `user_id`, `event`)
COMMENT '用户行为明细日志'
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`user_id`) BUCKETS 32
PROPERTIES (
    "replication_num" = "3",
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-30",
    "dynamic_partition.end" = "3",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.buckets" = "32"
);
```

### 3.2 最容易误解的一点

> [!danger] `DUPLICATE KEY` ≠ 主键，重复数据不会被去掉
> 很多从 MySQL 过来的人看到 `KEY` 就默认"唯一"。在 Doris 里：
> - `DUPLICATE KEY(a, b)` 只表示**数据在 tablet 内按 (a, b, ...) 排序**；
> - 连续插入两条 `(1, 'x')`，`SELECT count(*)` 结果就是 **2**；
> - 想让 `(a, b)` 唯一，必须用 `UNIQUE KEY`。
>
> 由此引出的经典线上事故：**CDC 同步（会重复投递/重放）误建成 Duplicate 表**，跑了一周后发现报表翻倍。Flink 的 at-least-once + Doris Duplicate 表 = 数据必然膨胀。

### 3.3 适用与不适用

| 场景 | 是否合适 | 说明 |
| --- | --- | --- |
| 埋点/日志/流水明细 | ✅ 最佳 | 需要保留每一次发生，可回溯 |
| ODS 层落地 CDC 原始数据 | ✅ | 保留变更历史，便于重算 |
| 需要"同一主键只留最新" | ❌ | 用 Unique |
| 只需要指标、不需要明细 | ⚠️ | 可以用，但查询时的 `GROUP BY` 成本要靠 Rollup/MV 补 |
| 需要对某列做 `UPDATE` | ❌ | Duplicate 表不支持 `UPDATE`（只能整行追加） |

### 3.4 写入与查询代价

- **写入**：最便宜。无需比较 key，导入即落盘，compaction 只做**多路归并排序**，不涉及去重/聚合，所以 Duplicate 表几乎不会出现"compaction 追不上导入"的问题。
- **查询**：最贵的地方在**去重/聚合要现场算**。`SELECT count(distinct user_id)` 这种在 Duplicate 大表上就是灾难，应该改用 `BITMAP` 预聚合或 `approx_count_distinct`。

## 四、Unique 唯一模型

### 4.1 语义

`UNIQUE KEY` 是**真正的唯一约束**：同一个 key 只保留一行，新写入的行覆盖旧行。

```sql
CREATE TABLE IF NOT EXISTS dim_order (
    `dt`          DATE         NOT NULL COMMENT '分区日期(与订单创建日一致)',
    `order_id`    BIGINT       NOT NULL COMMENT '订单号',
    `user_id`     BIGINT       NOT NULL COMMENT '用户 id',
    `order_status` TINYINT              COMMENT '状态',
    `pay_amount`  DECIMAL(18, 2)        COMMENT '支付金额',
    `update_time` DATETIME              COMMENT '业务更新时间'
)
ENGINE=OLAP
UNIQUE KEY(`dt`, `order_id`)
COMMENT '订单维表(CDC 同步)'
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`order_id`) BUCKETS 16
PROPERTIES (
    "replication_num" = "3",
    "enable_unique_key_merge_on_write" = "true",
    "enable_persistent_index" = "true",
    "light_schema_change" = "true"
);
```

### 4.2 读时合并 vs 写时合并（核心考点）

Unique 模型实现"覆盖"有两条完全不同的路线：

**（1）读时合并（Merge-on-Read, MoR）——老实现**

- 写入时**不判断 key 是否重复**，新行直接以新 Rowset 落盘，并在 Rowset 的删除向量/标记位里记录"我覆盖了哪些 key"。
- 查询时把**所有 Rowset 归并**，同 key 取版本号最大的那一行。这叫"归并读"。
- 代价：**读放大**。一个 key 被更新 100 次，查询就要归并 100 份 Rowset 才能算出一行；Rowset 越多查询越慢。
- 缓解手段：靠 **Base Compaction / Cumulative Compaction** 定期把多个 Rowset 合并成一层，但 compaction 期间读性能仍受影响，且 compaction 本身吃 IO 与 CPU。

**（2）写时合并（Merge-on-Write, MoW）——1.2 起引入，2.1+ 基本是默认选择**

- 写入时**先定位同 key 的旧行，直接把新值写进去**（在内存中用主键索引 + 删除标记把旧行标删，新行写在新 Rowset 中，保证查询时**只需读最新 Rowset 就能得到正确结果**）。
- 代价：**写放大 + 内存开销**。每批导入要构建/查询主键索引（key → 行位置），大 batch 导入会消耗明显的内存；主键索引本身要占内存，于是有了 `enable_persistent_index`（把索引持久化到磁盘，降低内存占用，代价是点查时可能有额外 IO）。

| 维度 | Merge-on-Read | Merge-on-Write |
| --- | --- | --- |
| 写入开销 | 低（不查重，直接落盘） | 高（要查旧 key、维护删除标记与索引） |
| 读取开销 | 高（Rowset 多时归并成本大） | 低（读最新 Rowset 即可） |
| 对 compaction 的依赖 | **强依赖**，不 compaction 就越来越慢 | 弱一些，但仍需 compaction 清理被覆盖的数据 |
| 主键索引内存 | 不需要 | 需要；可用 `enable_persistent_index` 转移到磁盘 |
| 高频率小批量更新（CDC） | 容易积压大量 Rowset，查询退化 | 表现稳定 |
| 大批量一次性导入 | 更快 | 更慢（构建索引开销） |

> [!tip] 实践结论
> **新表一律开 MoW**：`"enable_unique_key_merge_on_write" = "true"`。较新版本（2.1 起）新建 Unique 表默认就是 MoW，但**显式写出来**可以避免"换版本/换集群后行为不一致"的困惑。MoW 时代价是写放大，但数仓的读远多于写、且读来自多个下游，把成本放在写侧通常更划算。另外 MoW 是部分列更新、行存等特性的**前置条件**。

> [!warning] MoW 的内存陷阱
> MoW 导入时要把主键索引和删除标记放在内存里。当你**一口气导入几千万行**（例如历史数据回灌）时，可能看到 BE 内存飙升甚至导入直接报内存不足。对策：`enable_persistent_index=true`、拆分导入批次、适当调小 `streaming_load_max_mb` / 分批 `INSERT`。这不是"MoW 有 bug"，而是它的设计取舍。

### 4.3 部分列更新（Partial Update）

很多业务只需要更新几个字段（例如只更新订单状态、只更新用户的最后登录时间），其余字段保持原值。MoW 支持**部分列更新**。

语法上通过会话变量 + `INSERT INTO` 指定列：

```sql
-- 只更新 order_status，其余列保持不变
SET enable_unique_key_partial_update = true;

INSERT INTO dim_order (dt, order_id, order_status)
VALUES ('2026-10-09', 202610090001, 3);
```

语义要点：

| 情况 | 未指定列的结果 |
| --- | --- |
| 该 key **已存在** | 保持**原值**不变 |
| 该 key **不存在**（新行） | 填**默认值**；无默认值且 nullable 则为 `NULL` |

Stream Load 侧用 HTTP header 打开：

```bash
curl --location-trusted -u root: \
  -H "label:dim_order_partial_20261009_01" \
  -H "column_separator:," \
  -H "partial_columns:true" \
  -H "columns:dt,order_id,order_status" \
  -T order_status.csv \
  http://fe_host:8030/api/dw/dim_order/_stream_load
```

Flink Doris Connector 侧用属性打开（[[6-数据导入与FlinkCDC]] 里会展开）：

```properties
sink.properties.partial_columns = true
```

> [!warning] 部分列更新的代价与限制
> - 它**依赖 MoW**：MoR 表不支持真正的部分列更新（老版本会用整行补齐的近似实现，语义不保证）。
> - 它内部需要读取旧行来做合并，**CPU/IO 会比普通导入高**。
> - 只有 Unique 模型有；Duplicate/Aggregate 都没有"更新某一列"的概念。
> - 如果发现"更新后某些列莫名变成 NULL"，基本就是：目标 key 不存在（走了新行分支）或者列不是 nullable 却有默认值约束。

### 4.4 适用场景

| 场景 | 说明 |
| --- | --- |
| **Flink CDC / Kafka 同步业务库表** | 这是 Unique 的**标准用法**。MySQL binlog 里 UPDATE 会产生一条新行，Unique 模型天然把"同一主键覆盖"的语义接住，应用层不需要写 upsert 逻辑 |
| 订单、用户、商品等实体表 | 主键天然唯一 |
| 需要按主键点查的维表 | 配合行存（第十节）可以做到很低延迟的点查 |
| 需要 `DELETE` 的数据合规场景 | Unique 表支持条件删除/按 key 删除，比 Duplicate 灵活（详见 [[8-运维与调优]] 的数据管理部分） |

> [!note] CDC 场景的一个重要细节：分区键不要用会被更新的字段
> 上面 `dim_order` 用 `dt` 做分区键。如果业务上订单的 `dt`（下单日期）不会变，那没问题；但如果用 `update_time` 的日期做分区键，一条订单今天更新就会"跑到今天的分区"，**同一个 order_id 会同时存在于两个分区**——Doris 的 Unique 唯一性**只在分区内保证**（不同分区的 key 各自唯一）。这是 CDC 同步里非常典型的数据重复来源。

## 五、Aggregate 聚合模型

### 5.1 语义

`AGGREGATE KEY` 是**聚合维度**。相同 key 的多行在导入时按各 value 列声明的聚合函数合并成一行。

```sql
CREATE TABLE IF NOT EXISTS dws_ad_click_1d (
    `dt`        DATE          NOT NULL COMMENT '统计日期',
    `ad_id`     BIGINT        NOT NULL COMMENT '广告 id',
    `city`      VARCHAR(32)   NOT NULL COMMENT '城市',
    `show_cnt`  BIGINT        SUM DEFAULT "0"          COMMENT '曝光次数',
    `click_cnt` BIGINT        SUM DEFAULT "0"          COMMENT '点击次数',
    `cost`      DECIMAL(18,2) SUM DEFAULT "0.00"       COMMENT '消耗金额',
    `uv`        BITMAP        BITMAP_UNION             COMMENT '去重用户',
    `dur_p99`   QUANTILE_STATE QUANTILE_UNION          COMMENT '停留时长分位'
)
ENGINE=OLAP
AGGREGATE KEY(`dt`, `ad_id`, `city`)
COMMENT '广告点击日汇总'
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`ad_id`) BUCKETS 16
PROPERTIES (
    "replication_num" = "3",
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-365",
    "dynamic_partition.end" = "3",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.buckets" = "16"
);
```

### 5.2 支持的聚合函数

| 聚合类型 | 适用列类型 | 语义 | 典型用途 |
| --- | --- | --- | --- |
| `SUM` | 数值 | 求和 | 次数、金额 |
| `MIN` | 可比较类型 | 取最小 | 首次时间、最低价 |
| `MAX` | 可比较类型 | 取最大 | 最后时间、最高价 |
| `REPLACE` | 任意 | **保留最后写入的那一行**的值 | 状态类字段（只关心最新） |
| `REPLACE_IF_NOT_NULL` | 任意 | 最后写入的**非 NULL** 值 | CDC 里字段可能缺省的更新 |
| `HLL_UNION` | `HLL` | 近似去重基数 | UV（省空间，有误差） |
| `BITMAP_UNION` | `BITMAP` | 精确去重集合求并 | UV、活跃用户（精确但更占空间） |
| `QUANTILE_UNION` | `QUANTILE_STATE` | 分位数草图求并 | P95/P99 延迟 |

查询时 value 列应显式套上对应的聚合/查询函数，语义最清晰，也便于让优化器做改写：

```sql
SELECT
    dt,
    ad_id,
    SUM(show_cnt)                AS show_cnt,
    SUM(click_cnt)               AS click_cnt,
    SUM(click_cnt) / SUM(show_cnt) AS ctr,
    bitmap_union_count(uv)       AS uv,
    quantile_percent(QUANTILE_UNION(dur_p99), 0.99) AS dur_p99
FROM dws_ad_click_1d
WHERE dt = '2026-10-09'
GROUP BY dt, ad_id;
```

> [!note] 没写聚合函数的 value 列
> 建表时 value 列如果不写聚合类型，Doris 按 `REPLACE` 语义处理（即"后写的覆盖先写的"）。不同版本对默认聚合方式的推断细节略有差异，**建议建表时把聚合类型全部显式写全**，别依赖默认。

### 5.3 预聚合的收益

- **查询省**：`SUM` 已经在存储层算完了，查询只需扫描聚合后的少量行。数据量大、指标固定的看板场景，收益是数量级的。
- **空间省**：1000 万条明细可能聚合后只剩几万行；配合 `BITMAP` 存 UV，比 `count(distinct)` 便宜得多。
- **可叠加**：多个分区、多个 Rollup 之间可以继续合并（`SUM` 的 `SUM` 还是 `SUM`），这是 Aggregate 能配合物化视图做"上卷"的基础。

### 5.4 "聚合不可逆"这条限制

> [!danger] Aggregate 表是有损存储，聚合掉的信息永远回不来
> 三个典型翻车现场：
>
> **① 事后想加维度。** 表按 `(dt, ad_id, city)` 聚合，某天老板要看"按 `device` 分"。`device` 已经在聚合时被丢掉了，只能回 ODS 重刷全量历史。
>
> **② 用非 key 列过滤，结果悄悄错了。** 表按 `(dt, ad_id)` 聚合，`user_id` 只是被 `BITMAP_UNION` 进去的。这时写 `WHERE user_id = 123`，Doris 没有任何办法在聚合后的行上判断"这行里包不包含 user 123"，结果要么报错、要么返回不符合预期的行。**过滤条件必须落在 key 列上**（或者你能接受"按 key 粒度近似"）。
>
> **③ 以为 `count(*)` 有意义。** Aggregate 表里 `count(*)` 数的是"聚合后的行数"（即 key 组合数），不是明细条数。想看明细条数，得单独留一个 `SUM(1)` 的计数列。
>
> 工程建议：**ODS/DWD 层永远保留 Duplicate 或 Unique 明细**，Aggregate/DWS 层只是"派生的加速层"，随时可以从明细重算。这样聚合模型就只是性能优化，而不是数据资产的一部分。

### 5.5 适用与不适用

| 场景 | 是否合适 |
| --- | --- |
| 广告/电商固定指标看板，查询 QPS 高、明细无人看 | ✅ |
| 需要精确去重人数（UV、活跃） | ✅ 用 `BITMAP_UNION` |
| 分位数监控（P95/P99） | ✅ 用 `QUANTILE_UNION` |
| 需要随时下钻到任意维度 | ❌ 用 Duplicate + 物化视图 |
| 需要按用户/订单维度查明细 | ❌ |
| 指标口径还在频繁变 | ⚠️ 先把模型做宽（多留几列 key），或退回明细 |

> [!tip] 更现代的做法
> 如果你的 Doris 版本支持，很多过去必须用 Aggregate 表硬扛的场景，现在可以用 **Duplicate/Unique 明细表 + 物化视图（异步 MV）** 来做：明细保留、聚合由 MV 增量维护。这样既有查询加速，又不损失可回溯性。取舍点在于 MV 的刷新延迟与运维成本。详见 [[5-查询优化]]。

## 六、三种模型横向对比

| 维度 | Duplicate | Unique | Aggregate |
| --- | --- | --- | --- |
| KEY 语义 | 排序键 | **唯一键** | **聚合维度** |
| 是否去重 | ❌ | ✅（分区内） | ✅（key 唯一） |
| 是否聚合 | ❌ | ❌（覆盖而非聚合） | ✅ |
| 保留历史版本 | 全部保留 | 只保留最新 | 只保留聚合结果 |
| 支持部分列更新 | ❌ | ✅（需 MoW） | ❌ |
| 支持 `UPDATE` / 条件 `DELETE` | ❌ | ✅ | ❌ |
| 查询代价 | 高（要去重/聚合现场算） | 低（MoW）/ 中（MoR） | 最低（已预聚合） |
| 写入代价 | 最低 | 高（MoW）/ 中（MoR） | 中高（要按 key 合并） |
| Compaction 压力 | 低（只归并排序） | 高（要清理被覆盖数据） | 高（要重新聚合） |
| 典型场景 | 日志、埋点、ODS 明细 | 订单、维表、CDC 同步 | 固定指标体系表 |
| 是否需要主键索引内存 | 否 | MoW 需要 | 否（用排序键定位） |
| 能否做 Rollup/MV 上卷 | 可以，但意义有限 | 可以 | **最自然**（聚合可叠加） |

> [!important] 一句话记忆
> **Duplicate 保全部、Unique 保最新、Aggregate 保汇总。** 三者的写代价递增、读代价递减。选哪个取决于"下游要问什么问题"和"哪一侧更贵"。

## 七、排序键、KEY 列与前缀索引

### 7.1 KEY 列的两条硬规则

> [!warning] KEY 列必须满足的两个条件
> 1. **KEY 列在 schema 里必须排在最前面**，普通列只能跟在后面。你把 `dt` 写在第三位又想让它做 KEY，建表会直接失败（或需要重排列顺序）。
> 2. **KEY 列的顺序决定了排序顺序**，而排序顺序决定了前缀索引能不能命中。`KEY(dt, order_id)` 和 `KEY(order_id, dt)` 是两种不同的数据布局。

### 7.2 前缀索引（Short Key Index）怎么工作

Doris 为每个 Tablet 维护一份**前缀索引**：

- 内容 = 排序键的**最左若干列**（从第一列开始连续取，累计长度上限约 **36 字节**）；
- 形式 = **稀疏索引**，数据块之间**每隔若干行取一条索引项**（粒度是数据块级别，不是每行都建）；
- 作用 = 查询条件命中前缀时，直接**二分定位到数据块**，跳过大量不需要读的数据。

举例，排序键是 `(dt, order_id, user_id)`：

| 查询条件 | 能否用前缀索引 | 原因 |
| --- | --- | --- |
| `dt = '2026-10-09'` | ✅ | 命中第 1 列 |
| `dt = '2026-10-09' AND order_id = 123` | ✅ | 连续命中前 2 列，定位更精确 |
| `order_id = 123`（不带 dt） | ❌ | **跳过最左列，前缀断裂** |
| `dt = '2026-10-09' AND user_id = 9` | ⚠️ 部分 | 只能用 `dt` 那一列定位，`user_id` 只能在块内过滤 |
| 第 1 列是 `VARCHAR(200)` | ⚠️ | 单列就超过 36 字节，前缀索引**只能包含这一列**，后面的列进不来 |

> [!danger] 这就是"最左前缀匹配"的代价
> 索引是全表共用的，数据物理顺序只有一个。**你不可能同时为 `dt` 最左和 `order_id` 最左各建一份前缀索引**（除非用物化视图/rollup 复制一份不同排序的数据）。所以：
> - 如果**点查（按 order_id）和高频范围聚合（按 dt）都重要** → 排序键放 `(dt, order_id)`，让 `dt` 先吃到前缀索引；点查 `order_id` 靠 **Bloom Filter + 行存**（见第八、十节）补，而不是靠前缀索引。
> - 反过来 `(order_id, dt)` 会让"最近 7 天报表"这类查询**完全命中不到前缀索引**，退化为全表扫描。数仓里这个选择通常是致命的。
>
> 详细的方法论与 `EXPLAIN` 验证方式见 [[3-表设计]] 第二节。

### 7.3 怎么验证命中情况

用 `EXPLAIN` 看扫描的 `tablet` / `rows` 估算，以及 `SHORT KEY` / `PREDICATES` 相关信息；更细的执行期指标用 `EXPLAIN ANALYZE`：

```sql
EXPLAIN
SELECT count(*)
FROM dwd_user_action_log
WHERE dt = '2026-10-09' AND user_id = 10086;

EXPLAIN ANALYZE
SELECT count(*)
FROM dwd_user_action_log
WHERE dt = '2026-10-09' AND user_id = 10086;
```

判断方法（定性）：把 `WHERE` 里的列逐个去掉再 `EXPLAIN`，比较 `rows`/扫描量的估算变化。如果去掉 `dt` 后扫描量几乎不变，说明前缀索引/分区裁剪本来就没起作用——大概率是查询没带上分区列，或者条件写法不支持裁剪（例如把列套进函数：`WHERE date_format(dt,'%Y-%m-%d')='2026-10-09'` **会让分区裁剪和前缀索引全部失效**，这是最常见的"查询莫名很慢"的原因之一）。

## 八、列类型选择

### 8.1 常用类型的定位

| 类型 | 说明 | 使用建议 |
| --- | --- | --- |
| `TINYINT` / `SMALLINT` / `INT` / `BIGINT` | 整型 | 按实际取值范围选，别一律 `BIGINT`；状态码用 `TINYINT` |
| `LARGEINT` | 128 位整型 | 特殊大数，一般不用 |
| `FLOAT` / `DOUBLE` | 浮点 | **不要用于金额**；只用于本就允许误差的比值类指标 |
| `DECIMAL(p, s)` | 定点小数 | **金额、单价、费率一律用它**。`p` 是总位数、`s` 是小数位 |
| `DATE` / `DATEV2` | 日期 | 分区列首选；`DATEV2` 是新的紧凑实现，新表优先 |
| `DATETIME` / `DATETIMEV2` | 日期时间 | 事件时间；注意精度（`DATETIMEV2(3)` 支持毫秒） |
| `VARCHAR(n)` | 变长字符串 | **必填长度**，按实际长度给，别无脑给大 |
| `STRING` | 大文本 | 等价于超长 `VARCHAR`，会走不同的存储/索引路径，慎用于索引列 |
| `CHAR(n)` | 定长 | 很少用 |
| `BOOLEAN` | 布尔 | 用 `TINYINT` 表示也行 |
| `JSON` / `JSONB` | 半结构化 | `JSONB` 写入时转二进制，读取更快更省空间，新表优先 `JSONB` |
| `VARIANT` | 动态半结构化 | **2.1+ 引入，3.x 增强**，自动展开子列，见 8.3 |
| `ARRAY` / `MAP` / `STRUCT` | 复杂类型 | 适合半结构化分析，**不能做分区/分桶键**，索引能力受限 |
| `BITMAP` | 位图 | 配合 `BITMAP_UNION` 做精确去重 |
| `HLL` | 基数草图 | 近似去重，省空间 |
| `QUANTILE_STATE` | 分位草图 | 分位数聚合 |
| `AGG_STATE` | 聚合中间态 | 配合 `agg_state` 函数做自定义聚合（进阶） |

### 8.2 `VARCHAR` 长度为什么真的影响性能

`VARCHAR(n)` 的 `n` 不是"随便写大点没坏处"：

1. **影响前缀索引能容纳多少列。** 前缀索引上限约 36 字节，`VARCHAR(200)` 一列就吃满——如果你把一个 `VARCHAR(200)` 放在排序键第一列，后面的列**全都进不了前缀索引**。
2. **影响写入校验与内存估算。** 导入时按声明长度做校验与内存预留，声明过大会让 BE 的内存预算偏保守。
3. **影响字符串处理开销。** 虽然 Doris 是变长存储（不会为短值补齐到 n），但类型元信息会参与表达式与比较的代码路径。
4. **影响语义正确性。** 声明 `VARCHAR(32)` 却写进 40 字符的值，会导入报错或被截断——这是"字段莫名其妙丢了尾巴"的常见原因。

经验做法：

| 字段 | 建议 |
| --- | --- |
| 手机号 / 身份证 | `VARCHAR(20)` 级别即可 |
| url / user_agent | 视长度，`VARCHAR(512)` / `VARCHAR(1024)`，且**不要放排序键首位** |
| 城市 / 枚举型字符串 | 能转成 `TINYINT` 编码就转（省空间、比较更快） |
| 不确定长度的扩展字段 | 放 `VARIANT`/`JSONB`，不要给一个巨大的 `VARCHAR(65533)` |

> [!danger] `VARCHAR(65533)` 这个数字
> 它经常出现在"反正我不知道多长，给个最大"的建表里。后果：**这一列做排序键会让前缀索引只剩它自己**，做过滤时几乎没有块级裁剪能力，存储与内存估算也全面失真。OCR/日志类超长文本应该放进 `STRING` 或独立附表，并且**不要进排序键**。

### 8.3 `VARIANT`：半结构化数据的现代选择

`VARIANT` 在 **2.1 引入、3.x 持续增强**（4.x 上进一步成熟）。它解决的是"JSON 字段又多又可变，用 `JSON` 类型每次都要解析"的问题：

- 写入时 Doris 自动**识别并展开子字段**，为高频子字段建立独立的列式存储（子列），从而支持列裁剪、ZoneMap、甚至倒排索引；
- 读取时用下标语法访问，像访问列一样：`v['device']`、`v['nested']['k']`；
- 类型不确定的字段有兜底路径（sparse 存储），不是"展不开就丢"。

```sql
CREATE TABLE IF NOT EXISTS dwd_event_variant (
    `dt`      DATE   NOT NULL,
    `log_time` DATETIME NOT NULL,
    `event`   VARCHAR(32) NOT NULL,
    `props`   VARIANT
)
ENGINE=OLAP
DUPLICATE KEY(`dt`, `log_time`, `event`)
PARTITION BY RANGE(`dt`) ()
DISTRIBUTED BY HASH(`event`) BUCKETS 8
PROPERTIES ("replication_num" = "3");

SELECT props['device'] AS device, count(*)
FROM dwd_event_variant
WHERE dt = '2026-10-09'
GROUP BY props['device'];
```

| 对比项 | `JSON` | `JSONB` | `VARIANT` |
| --- | --- | --- | --- |
| 存储 | 文本/半结构化 | 二进制 | **子列式展开** |
| 子字段过滤/裁剪 | 弱 | 弱 | **强（可裁剪、可索引）** |
| 适合 | 偶尔取整段 | 偶尔取整段 | 高频按子字段过滤/聚合 |
| 版本 | 早 | 2.1+ | 2.1+ / 3.x 增强 |

> [!tip] 选择建议
> - **固定 schema 的字段一律建成真列。** 不要因为"JSON 方便"就把已知结构的字段塞进 `VARIANT`——真列永远最快、最省、索引能力最强。
> - `VARIANT` 留给**真的会变、真的不知道有哪些 key** 的扩展属性（埋点 props、上报的原始报文）。
> - 如果某个子字段后来变成了高频查询字段，考虑把它**提取成独立列**（`ADD COLUMN` 后用 SQL 回填），而不是长期依赖 VARIANT 的展开。

### 8.4 金额为什么必须 `DECIMAL`

`DOUBLE` 是二进制浮点，`0.1 + 0.2 != 0.3`。金额、费率、结算价这类要求"分位精确、可对账"的字段，用 `DOUBLE` 会导致：

- 多行求和后出现 `1234.5600000000001` 这类结果，对账平不了；
- 分位/取整后的误差被放大，财务口径无法解释。

正确做法：`DECIMAL(18, 2)`（金额到分）或 `DECIMAL(18, 4)`（费率）。代价是 `DECIMAL` 运算比整型慢，所以**能不用小数就不用**——很多团队会把金额统一存成"分"的 `BIGINT`，这是更极致的做法，取舍看团队习惯与 BI 工具兼容性。

## 九、稀疏索引与 ZoneMap

Doris 的"跳过不必要的数据"靠几层机制叠加，各自的适用条件完全不同，混用会白花写入成本。

| 机制 | 原理 | 适用条件 | 代价 |
| --- | --- | --- | --- |
| **分区裁剪** | 按分区范围排除整分区 | 查询带上分区列且未套函数 | 无（建表时想清楚分区粒度） |
| **前缀索引（Short Key）** | 排序键最左列的稀疏索引，二分定位数据块 | 条件命中排序键**最左前缀** | 无（自动维护） |
| **ZoneMap 索引** | 每个数据块记录各列 min/max，过滤时跳过区间外数据块 | **列值有局部聚集性**（如自增 id、时间、有序枚举） | 存储极小，自动维护 |
| **Bloom Filter** | 每个数据块记录一个位图，判断"该块是否可能包含某值" | **高基数列的等值 / `IN` 过滤**（如 `order_id`、`user_id`） | 存储与写入开销小；**对范围查询和 `LIKE` 无效** |
| **倒排索引（Inverted Index）** | 值 → 行的倒排表，支持分词与多条件交并 | 等值、`IN`、全文检索（`MATCH_*`），字符串/数值 | **写入放大明显**，列多、值多、分词多时导入变慢、存储变大 |
| **Bitmap 索引** | 值 → 位图 | **低基数**枚举列（性别、状态、城市）的等值过滤 | 低基数才划算，高基数会爆炸 |
| **NGRAM_BF 索引** | n-gram 布隆过滤器 | `LIKE '%xxx%'` 这类**子串匹配** | 有写入开销；n 值越大越省空间但越容易误判 |

### 9.1 怎么选

- **点查多、列基数高**（`order_id` 点查）→ `bloom_filter_columns`，成本极低，优先加。
- **枚举列过滤多**（`status`、`city`）→ `USING BITMAP` 索引。
- **要全文检索 / 多条件组合过滤 / 需要分词**（商品名、日志正文）→ `USING INVERTED`。中文要配分词器。
- **只有 `LIKE '%...%'` 子串查询** → `USING NGRAM_BF`。
- **范围查询（时间、金额区间）** 不需要额外索引，靠分区裁剪 + 前缀索引 + ZoneMap 就够。

```sql
-- Bloom Filter：建表属性，成本低，点查首选
ALTER TABLE dim_order SET ("bloom_filter_columns" = "order_id,user_id");

-- 倒排索引：新建索引会触发一次异步 schema change 为存量数据补建
ALTER TABLE dwd_user_action_log ADD INDEX idx_event (`event`) USING INVERTED;

-- 中文分词倒排索引
ALTER TABLE dwd_user_action_log ADD INDEX idx_props (`props`)
    USING INVERTED PROPERTIES("parser" = "chinese", "parser_mode" = "fine_grained");

-- NGRAM_BF：子串模糊匹配
ALTER TABLE dwd_user_action_log ADD INDEX idx_page_ngram (`page_id`)
    USING NGRAM_BF PROPERTIES("gram_size" = "3", "bf_size" = "1024");

-- Bitmap：低基数枚举列
ALTER TABLE dim_order ADD INDEX idx_status (`order_status`) USING BITMAP;
```

> [!warning] 倒排索引不是免费的
> 线上常见事故：为了几个 `LIKE` 查询，给 10 个字符串列都加了倒排索引，结果**导入吞吐掉一半、compaction 压力翻倍、磁盘涨了 30%**。倒排索引的构建发生在**写入路径**上，是要写入放大的。原则：**先加 Bloom Filter（便宜），再用 `EXPLAIN`/profile 证明某列真的在过滤大量数据，最后才为这一列加倒排**。

### 9.2 ZoneMap 为什么有时没用

ZoneMap 的收益前提是"**同一列的值在物理上局部聚集**"。因为 Doris 按排序键有序存储、且分区一般按时间切，所以：

- `dt`、`log_time`、自增 id 这类跟着写入顺序走的列，ZoneMap 效果很好；
- 一个**完全随机**的列（例如 UUID、随机的 `session_id`），每个数据块的 min/max 范围几乎覆盖全域，ZoneMap 等于没有。

这也解释了为什么"把高基数随机列放在排序键最前面"是错误的：它既让前缀索引失去选择性，也毁掉了其他列的局部聚集性。

## 十、行存与列存混存（Hybrid Row-Columnar Storage）

### 10.1 问题：列存对点查不友好

列存擅长"读很少的列、扫很多的行"。但点查恰好相反：`SELECT * FROM dim_order WHERE order_id = ?` 要读**全部列**，列存就变成了"每列各读一次"，IO 次数多且都是随机读。

### 10.2 行存列的做法

Doris 3.0 引入**行列混存**：在列存的基础上，额外存一份**整行编码后的隐藏二进制列**（Row Store）。点查时先按 key 定位到行，再直接从行存里取出整行，不用一列一列拼。

开启方式（建表属性，仅对 Unique 模型有意义）：

```sql
ALTER TABLE dim_order SET (
    "store_row_column" = "true"
);
```

要点：

| 维度 | 说明 |
| --- | --- |
| 前置条件 | 一般是 **Unique 表 + MoW**；依赖轻量级 schema change 能力 |
| 收益 | `SELECT *` 形态的**主键点查**大幅加速（少了按列拼装的开销） |
| 代价 | **额外一份存储**（同一份数据存两遍）；写入路径更重；compaction 更贵 |
| 适用 | 高并发的**维表点查**（风控、推荐、订单详情接口直接查 Doris） |
| 不适用 | 以聚合/范围扫描为主的表（列裁剪本来就更划算，行存纯属浪费） |

> [!tip] 判断要不要开
> 问自己："这张表上跑得最多的 SQL，是不是 `WHERE <主键> = ?` 且要取很多列？" 是 → 可以考虑。否 → 不要开。
> 另一种更简单的替代方案是让上游用 Redis/HBase 扛点查、Doris 只做分析；选型对比可以放在 [[9-对比StarRocks与ClickHouse]] 的语境里一起看。

## 十一、数据模型与 Compaction、内存的关系

不同模型对 **compaction** 的依赖程度差别很大，这直接影响线上稳定性（详细调优留给 [[8-运维与调优]]，这里只建立因果）。

```text
导入产生 Rowset ──► 查询要读多个 Rowset（读放大）
                      │
          Compaction │ 把多个 Rowset 归并成更少、更大的
                      ▼
                 读放大下降，但消耗 CPU/IO/内存
```

| 模型 | Compaction 做的事 | 压力 | 不 compaction 的后果 |
| --- | --- | --- | --- |
| Duplicate | 多路归并排序 | **低** | 读放大缓慢上升，一般不会突然恶化 |
| Unique (MoW) | 归并 + 清理被覆盖版本 + 维护主键索引 | **中高** | 存储快速膨胀（旧版本还在），点查变慢 |
| Unique (MoR) | 归并 + 合并删除标记 | **高** | 查询要归并大量 Rowset，可能严重退化 |
| Aggregate | 重新按 key 聚合 | **高** | 读放大 + 同 key 多版本，指标可能被重复计算 |

几个关键关联：

1. **MoW 的持久化索引（`enable_persistent_index`）本质上是在"内存 vs 磁盘 IO"之间选**：关掉省磁盘 IO 但吃内存，大表可能压不住；打开省内存但点查/写入多一次索引查询。它在索引大到内存放不下时几乎是必需的。
2. **`DELETE`/覆盖产生的删除标记需要 compaction 真正清理**。如果只删不 compact，空间不会立刻释放——所以"删了数据但磁盘没降"是正常现象，要等 compaction 或手动触发。
3. **`disable_auto_compaction` 不要随便开**。有团队为了"导入期间别抢资源"关掉自动 compaction，结果几天后查询全线退化。正确做法是调 compaction 的并发与阈值，而不是关掉它。

## 十二、必答与自测

> [!important] 必答 1：三种数据模型怎么选？
> 先问"下游要问什么"：
> - **要保留每一次原始发生、可回溯可重算** → `Duplicate`（日志、埋点、ODS 明细）。记住它的 `KEY` 只是排序键，**不去重**。
> - **要按主键保留最新一行**（订单状态、维表、CDC 同步） → `Unique`，并**开 MoW**（`enable_unique_key_merge_on_write=true`，MoW 下才有部分列更新、行存等能力）。
> - **只要固定指标的汇总结果**（点击/曝光/GMV/UV，且口径稳定） → `Aggregate`，用 `SUM/MIN/MAX/REPLACE/BITMAP_UNION/QUANTILE_UNION`。同时接受"**聚合不可逆**"：过滤只能落在 key 列，聚合掉的维度回不来。
> 补充一句体现工程判断：**"我通常 ODS/DWD 层保留明细，Aggregate 只作为派生加速层，这样模型选错了还能从明细重刷。"**

> [!important] 必答 2：Duplicate 模型的 KEY 是唯一约束吗？
> **不是。** `DUPLICATE KEY(...)` 只声明**排序键（sort key）**，用于决定 Tablet 内的物理有序性，从而支撑前缀索引、ZoneMap 与高效的范围扫描。它不做任何去重：插入两条完全相同的行，`count(*)` 就是 2。要实现唯一性必须用 `UNIQUE KEY`。
> 反问一句加分：**"所以 CDC 同步这类可能重复投递的链路，绝对不能建 Duplicate 表，否则会静默地数据翻倍。"**

> [!important] 必答 3：MoW 是什么，为什么推荐？
> MoW = **Merge-on-Write 写时合并**。Unique 表实现"同 key 覆盖"有两条路线：
> - **MoR（读时合并）**：写入不查重，直接落新 Rowset，查询时归并所有 Rowset 取最新版本 → **读放大**，强依赖 compaction，更新频繁时查询会持续退化。
> - **MoW（写时合并）**：写入时就定位并标记旧行，保证**查询只需读最新数据**即可拿到正确结果 → **读放大基本消除**，代价是**写放大 + 主键索引的内存开销**（可用 `enable_persistent_index` 缓解）。
> 推荐 MoW 的理由：数仓读远多于写、下游多，"把成本放在写入侧、让读路径稳定"更划算；而且 MoW 是**部分列更新**与**行存点查**的前置条件。代价要能说出来：**大批量导入（尤其历史回灌）会吃内存，需要分批 + 持久化索引。**

> 1. 为什么列存 + 排序键能让 `WHERE dt BETWEEN ... GROUP BY` 变快？说清"列裁剪"和"数据块跳过"两件事。
> 2. 你的日志表建成了 `DUPLICATE KEY(dt, user_id)`，现在要"按 user_id 查最近一条"，前缀索引能命中吗？（不能——`dt` 断了前缀）
> 3. Aggregate 表按 `(dt, ad_id, city)` 聚合，写 `WHERE user_id = 123` 会发生什么？为什么？
