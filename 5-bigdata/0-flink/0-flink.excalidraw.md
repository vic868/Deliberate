Flink 定义了 3 种时间语义，
Event time 是事件实际发生的时间。
Processing time 是数据被处理的机器时间。
Ingestion time 是数据进入 Flink 的时间，你选的哪一种直接影响计算结果的重要性。

生产推荐用 event time，因为它是数据本身的属性，不受网络延迟和系统负载的影响。结果可重放、可复现

Processing time 虽然简单，但是同样的数据跑两次可能得到不同的结果，因为机器时间每次都不一样。

Event time 处理乱序数据不是很麻烦吗？
所以 Flink 引入了一个关键机制来解决这个问题：watermark 水位线。
Watermark 本质上是一个进度条，它告诉 Flink 某个时间点之前的数据。我认为已经到齐了，比如谁会先跑到替补，T5 之前的数据都到期了，可以计算了。
那如果 T5 之前的数据又迟到了呢？有两种处理方式：
一种是允许一定时间的迟到，设置 allowed lateness。窗口结果先出一次迟到数据，到了再更新一次。
另外一种是完全超时的迟到数据。通过 set output 收集起来另行处理，不能丢。

所以 watermark 是允许一定不完美的，它是一种权衡。用可能的少量数据延迟换取整个流的持续推进。
