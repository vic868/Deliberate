## 一、部署模式全景：Session / Per-Job / Application

### 1.1 三种模式的本质区别

Flink 的部署模式差异，本质是回答两个问题：

1. **集群的生命周期归谁**——是常驻的，还是跟着作业生灭？
2. **`main()` 在哪里执行**——客户端，还是集群里的 JobManager？

`main()` 的执行位置决定了一件极其重要的事：**作业的依赖（jar、配置文件、`StreamExecutionEnvironment` 的构建过程）在哪里解析**。在客户端执行，意味着客户端必须能访问所有依赖和提交环境的凭证；在集群执行，意味着客户端只是一个"提交请求"的角色。

| 维度 | Session 模式 | Per-Job 模式（已弃用） | Application 模式 |
| --- | --- | --- | --- |
| 集群生命周期 | 常驻，多个作业共享 | 一个作业一个集群 | 一个 Application 一个集群 |
| `main()` 执行位置 | **客户端** | **客户端** | **集群（JobManager）** |
| 资源隔离 | ❌ 无，作业抢 Slot | ✅ 完全隔离 | ✅ 完全隔离 |
| 单作业失败影响面 | 可能抢占/耗尽资源影响其他作业 | 仅自己 | 仅自己 |
| 依赖分发 | 每个作业单独上传 jar | 每个作业单独上传 jar | cluster 启动时一次性分发 |
| 客户端负载 | 高（要解析依赖、生成 JobGraph） | 高 | **极低（适合当成"提交 API"）** |
| 启动延迟 | 低（集群已存在） | 中 | 中（要起 cluster，但无逐作业上传） |
| 多作业支持 | ✅ | ❌（一对一） | ✅（同一个 `main()` 里 `executeAsync()` 多次） |
| 适用场景 | 开发调试、SQL Client 交互、短作业/临时作业 | 历史遗留 | **生产标准**，尤其 K8s |

### 1.2 为什么 Per-Job 被淘汰

- **Flink 1.15 起 Per-Job 模式被标记为 deprecated**，并在后续大版本中移除（以你所用的版本文档为准）。
- 淘汰的原因不是它不好，而是 **Application 模式在 K8s 场景下完全覆盖了它的能力，而且更干净**：
  - Per-Job 模式下 `main()` 依旧在客户端执行，客户端依然是"重"的、依然要持有依赖和集群凭证；
  - Application 模式把 `main()` 搬到 JobManager，客户端退化成纯粹的控制面，**正好契合 K8s 上"提交一次、集群自管"的模型**。
- 在 YARN 上曾经有 `yarn-per-job` 与 `yarn-application` 的区分，迁移到 Application 模式后行为基本对齐。

> [!important] 一句话记住选择结论
> **生产一律用 Application 模式；开发调试、临时 SQL 查询用 Session 模式；Per-Job 只在你维护老集群时才会遇到。**
>
> 判断标准：如果这个作业需要 7×24 稳定运行、需要明确的资源配额、需要独立的 HA 和升级节奏 → Application（或 K8s Operator）。

### 1.3 各模式的提交命令对照

```bash
# ---- Session 模式：先起集群，再往里提交作业 ----
# 1) 起一个常驻 session 集群
./bin/start-cluster.sh                       # Standalone
# 2) 提交作业（main 在客户端执行，jar 上传到集群）
./bin/flink run -m localhost:8081 -c com.demo.OrderJob order-job.jar

# ---- Application 模式（K8s，Native）----
./bin/flink run-application -t kubernetes-application \
  -Dkubernetes.cluster-id=order-job-prod \
  -Dkubernetes.container.image=registry.internal/flink:1.18-scala_2.12-java11 \
  -Dkubernetes.jobmanager.service-account=flink \
  -Dkubernetes.namespace=flink-prod \
  local:///opt/flink/usrlib/order-job.jar     # local:// 表示 jar 已在镜像里

# ---- Application 模式（YARN）----
./bin/flink run-application -t yarn-application \
  -Djobmanager.memory.process.size=2048m \
  -Dtaskmanager.memory.process.size=4096m \
  -Dyarn.application.name=order-job-prod \
  hdfs:///flink/usrlib/order-job.jar
```

> [!warning] `local://` 的含义不是"本地文件"
> 它表示 **jar 已经存在于集群容器的镜像/文件系统里**，不需要客户端上传。这是 Application 模式下依赖分发的推荐做法：**镜像里带依赖，提交时只引用路径**。
> 反之如果你用 `file://` 或裸路径，客户端会尝试上传 jar —— 在容器化提交（CI/CD）场景下常常因为路径不存在而失败。

## 二、资源提供者：Standalone / Kubernetes / YARN

### 2.1 三种提供者对比

| 维度 | Standalone | **Kubernetes** | YARN |
| --- | --- | --- | --- |
| 资源调度 | 无，静态分配 | K8s 调度器 | YARN RM/NM |
| 弹性 | ❌ 手工扩缩容 | ✅ 原生弹性、可配 Operator 自动扩缩容 | ✅ 动态申请容器 |
| 隔离性 | 弱（进程级） | 强（Pod 级，CPU/内存 limit） | 中（容器级） |
| 运维复杂度 | 低 | 高（要懂 K8s、镜像、RBAC） | 中（依赖 Hadoop 生态） |
| HA 支持 | 需 ZooKeeper | ✅ **Kubernetes HA（基于 ConfigMap 选主）** | ✅ ZooKeeper 为主 |
| 镜像/依赖管理 | 手工分发 jar | 镜像化，CI/CD 友好 | jar 放 HDFS，按作业分发 |
| 云原生程度 | 低 | ✅ 高 | 中 |
| 典型场景 | 开发、测试、小规模自建 | **生产主流（云原生/混合云）** | 已有 Hadoop 集群的公司 |

**选型建议**：新项目、有 K8s 基建 → **Kubernetes**；已有成熟 Hadoop 平台、数据都在 HDFS → **YARN**；本地/测试环境 → Standalone 或 Local。

### 2.2 Kubernetes：Native 集成 vs Flink Kubernetes Operator

这是两个不同的层次，别混：

| 维度 | Native K8s 集成（内置） | Flink Kubernetes Operator |
| --- | --- | --- |
| 是什么 | Flink 客户端直接调用 K8s API 创建 JM/TM Pod | 一个运行在 K8s 里的 Controller，管理 CRD |
| 声明方式 | `flink run-application -t kubernetes-application -D...` | `kubectl apply -f FlinkDeployment.yaml` |
| 集群形态 | Session / Application 模式都支持 | 以 Application 模式为主（另有 `FlinkSessionJob`） |
| 升级能力 | 手工：savepoint → 停 → 起 | ✅ 声明式：`upgradeMode` 自动处理 savepoint / last-state |
| 定时 Savepoint | 需自己写脚本/调 REST API | ✅ `savepointTriggerNonce`、Operator 内置周期 savepoint |
| 状态观测 | Flink Web UI + K8s | ✅ CRD `status` 里直接有 job state、savepoint 信息 |
| 推荐度 | 知道原理即可 | **生产推荐** |

### 2.3 Native K8s 部署关键步骤与参数

```bash
# 1) 创建配置（Flink 配置文件以 ConfigMap 形式挂载）
kubectl create -f flink-configuration-configmap.yaml
kubectl create -f jobmanager-service.yaml          # REST/UI 的 Service
kubectl create -f jobmanager-session-deployment.yaml
kubectl create -f taskmanager-session-deployment.yaml

# 2) 权限：Pod 的 ServiceAccount 必须能创建/删除 Pod（Flink 自己起 TM）
kubectl create serviceaccount flink
kubectl create clusterrolebinding flink-role-binding \
  --clusterrole=edit --serviceaccount=default:flink

# 3) Session 集群暴露 UI
kubectl port-forward service/flink-jobmanager 8081:8081
```

**Native K8s 常用配置键：**

| 配置键 | 作用 | 注意 |
| --- | --- | --- |
| `kubernetes.cluster-id` | 集群唯一标识 | 决定生成资源的名字前缀；**也是 HA 选主的依据之一** |
| `kubernetes.namespace` | 命名空间 | 多环境隔离必配 |
| `kubernetes.container.image` | 镜像 | 生产必须用**自建并打了业务 jar 与连接器**的镜像，不要用裸 `flink:` |
| `kubernetes.container.image.pull-policy` | 拉取策略 | 用固定 tag 一般 `IfNotPresent`；用 `latest` 会拉到不可控版本 |
| `kubernetes.jobmanager.service-account` | JM Pod 使用的 SA | **不配 = 无法创建 TM Pod**（Flink 需要 `pods` 的 create/delete 权限） |
| `kubernetes.rest-service.exposed.type` | `ClusterIP`/`NodePort`/`LoadBalancer` | 生产通常 `ClusterIP` + 内部网关/端口转发 |
| `kubernetes.jobmanager.cpu` / `kubernetes.taskmanager.cpu` | CPU 申请 | 和并行度、Slot 数一起算 |
| `taskmanager.numberOfTaskSlots` | 每个 TM 的 Slot 数 | Slot 数 × TM 数 ≥ 总并行度需求 |
| `kubernetes.container.image.pull-secrets` | 私有仓库凭证 | 内部镜像仓库必配 |
| `high-availability.type: kubernetes` | 用 K8s 做 HA 选主 | 需配 `high-availability.storageDir` |

> [!danger] `kubernetes.jobmanager.service-account` 是新手最容易漏的一项
> 漏配的典型症状：JM Pod 正常起来、UI 能打开，但作业一直卡在 **`Job is not yet running`** / `CREATED`，TM Pod 一个都起不来。日志里会看到 K8s API 的 403（`pods is forbidden`）。排查入口就是 `kubectl describe pod <jm-pod>` 和 JM 日志。

### 2.4 Flink Kubernetes Operator：`FlinkDeployment` CRD

```yaml
apiVersion: flink.apache.org/v1beta1
kind: FlinkDeployment
metadata:
  name: order-job-prod
  namespace: flink-prod
spec:
  image: registry.internal/flink:1.18-scala_2.12-java11
  flinkVersion: v1_18
  serviceAccount: flink
  flinkConfiguration:
    taskmanager.numberOfTaskSlots: "4"
    # 状态后端：大状态用 rocksdb，小状态用 hashmap
    state.backend.type: rocksdb
    state.backend.incremental: "true"
    state.checkpoints.dir: s3://flink-state/checkpoints/order-job
    state.savepoints.dir: s3://flink-state/savepoints/order-job
    execution.checkpointing.interval: 60s
    execution.checkpointing.timeout: 10min
    execution.checkpointing.min-pause: 30s
    execution.checkpointing.externalized-checkpoint-retention: RETAIN_ON_CANCELLATION
    # 并行度上限：一旦设定，决定未来可扩到多大，务必显式设置
    pipeline.max-parallelism: "128"
    # 重启策略
    restart-strategy: exponential-delay
    restart-strategy.exponential-delay.initial-backoff: 10s
    restart-strategy.exponential-delay.max-backoff: 5min
    # HA
    high-availability.type: kubernetes
    high-availability.storageDir: s3://flink-state/ha/order-job
  jobManager:
    resource:
      memory: "2048m"
      cpu: 1
  taskManager:
    resource:
      memory: "4096m"
      cpu: 2
  job:
    jarURI: local:///opt/flink/usrlib/order-job.jar
    entryClass: com.demo.OrderJob
    args: ["--env", "prod"]
    parallelism: 8
    upgradeMode: savepoint
    state: running
```

```bash
kubectl apply -f order-job-prod.yaml
kubectl get flinkdeployment -n flink-prod
kubectl describe flinkdeployment order-job-prod -n flink-prod   # 看 status / 事件
kubectl logs -n flink-prod -l app=order-job-prod --tail=200 -f  # 按 cluster-id 对应的 label 拉日志
```

**`upgradeMode` 三种取值（生产最关键的语义）：**

| 取值 | 行为 | 恢复来源 | 状态是否保留 | 适用 |
| --- | --- | --- | --- | --- |
| `stateless` | 直接停旧作业、起新作业 | 无 | ❌ 全部丢失 | 无状态作业、首次部署默认 |
| `savepoint` | 触发一次 Savepoint → 停 → 从 Savepoint 恢复 | Savepoint 目录 | ✅ | **改代码/改逻辑后要保状态**，最稳 |
| `last-state` | 不额外打 Savepoint，直接用 HA 元数据里最新 checkpoint | HA `storageDir` | ✅ | 快速重启/滚动重启，**要求 HA 元数据可访问** |

> [!tip] `savepoint` 与 `last-state` 怎么选
> **改了作业逻辑、需要保证状态语义正确 → `savepoint`**（显式、可回滚、可留存归档）。
> **只是重启/换镜像/调资源，不想多等一次 Savepoint → `last-state`**（快，但依赖 HA 元数据；如果 HA 目录丢了就恢复不了）。
> 另外：改 `parallelism`、改 `entryClass`、改 jar 之后 Operator 才会判定需要重新部署；有时需要显式 bump 一个"触发符"（如 `savepointTriggerNonce`）来强制走一次 Savepoint 流程。

## 三、高可用（HA）

### 3.1 JobManager 为什么需要 HA

JobManager 是**单点**：它持有 JobGraph、调度决策、Checkpoint 协调者（Checkpoint Coordinator）等关键角色。JM 挂了：

- 没有 HA：作业直接失败，只能人工重新提交（从最近一次 Checkpoint/Savepoint 恢复）
- 有 HA：standby JM 通过选主接管，从最近的 Checkpoint 恢复作业，**自动继续跑**

### 3.2 两种 HA 服务对比

| 维度 | ZooKeeper HA | **Kubernetes HA** |
| --- | --- | --- |
| 选主机制 | ZK 临时节点 + 分布式锁 | K8s **ConfigMap** 做 leader 选举 |
| 引入的额外组件 | 必须维护 ZK 集群 | ❌ 不需要（K8s 自身即可） |
| 元数据存储 | `high-availability.storageDir`（DFS/对象存储） | 同左，**必须是所有 JM 都能访问的持久化存储** |
| 配置键 | `high-availability.type: zookeeper`<br>`high-availability.zookeeper.quorum`<br>`high-availability.zookeeper.path.root`<br>`high-availability.cluster-id` | `high-availability.type: kubernetes`<br>`kubernetes.cluster-id`<br>`high-availability.storageDir` |
| 适用 | 已有 ZK 基建（Hadoop 平台）、Standalone/YARN | **K8s 上的首选** |
| 运维成本 | 高（ZK 自己也是个集群） | 低 |

**HA 元数据里存了什么**（这决定了恢复能力）：

- 作业的 **JobGraph**（重启后重新提交用）
- **Checkpoint 的元数据指针**（`last-state` 升级模式直接读它）
- 各算子的最新完成 Checkpoint 信息

> [!warning] `high-availability.storageDir` 千万别配成本地路径
> 每个 JM Pod 的本地文件系统是独立的。配成 `/tmp/flink-ha` 之类的本地路径，会出现"选主成功了，但新 JM 读不到元数据，作业起不来"的诡异现象。
> 正确做法：**S3/HDFS/NFS 等所有 JM 都能访问的持久化存储**，并且确认凭证（IAM Role / AccessKey）在新 Pod 上也可用。

### 3.3 故障恢复行为

| 场景 | 无 HA | 有 HA |
| --- | --- | --- |
| JM 进程崩溃 | 作业失败，需人工提交 | standby JM 接管，从最近 Checkpoint 自动恢复 |
| JM 所在节点/Pod 挂掉 | 同上 | K8s 重建 JM Pod，重新选主后接管 |
| TM 挂掉 | 由 JobManager 触发 failover，重启受影响的 Task | 同左（**与 JM HA 无关**，这是 Flink 自身的 failover 机制） |
| 整个集群挂掉（含所有 JM） | 需人工 | 仍可能需要人工（取决于 K8s 是否重建了足够多的 JM），**元数据在 storageDir 里保住了** |

> [!important] Application 模式下 JM 挂了会发生什么
> Application 模式下 **JM 就是集群本身**，没有独立客户端存活。所以：
> - **没有 HA**：JM Pod 被 K8s 重启，新进程发现没有 leader 信息 → **Application 集群等于丢失**，作业需要重新提交（这正是"Application 模式必须配 HA"的原因）。
> - **有 HA**：`high-availability.type: kubernetes` 让多个 JM（或重建后的 JM）通过 ConfigMap 选主，新 leader 从 `storageDir` 读回 JobGraph 与 Checkpoint 元数据，作业自动恢复。
> - Operator 管理时，Operator 会感知到作业异常并按 `upgradeMode`/restart 逻辑处理，CLI 侧通常无需干预。

## 四、内存模型（面试与线上事故的双重重点）

### 4.1 TaskManager 进程内存分区

Flink 1.10 之后统一了内存模型，把"进程总内存"切成若干块。理解它的唯一目的是：**知道容器为什么被 OOMKilled，以及该调哪个键**。

```
taskmanager.memory.process.size   （= K8s Pod memory limit 的依据）
├── JVM Metaspace                 taskmanager.memory.jvm-metaspace.size
├── JVM Overhead                  taskmanager.memory.jvm-overhead.{min,max,fraction}
└── Flink 总内存 taskmanager.memory.flink.size
    ├── Framework Heap            taskmanager.memory.framework.heap.size
    ├── Framework Off-Heap        taskmanager.memory.framework.off-heap.size
    ├── Task Heap                 taskmanager.memory.task.heap.size
    ├── Task Off-Heap             taskmanager.memory.task.off-heap.size
    ├── Managed Memory            taskmanager.memory.managed.{size,fraction}
    └── Network Memory            taskmanager.memory.network.{min,max,fraction}
```

| 区域 | 配置键 | 作用 | 放什么 |
| --- | --- | --- | --- |
| **进程总内存** | `taskmanager.memory.process.size` | 整个 TM 容器的上限 | 下面所有 + JVM 自身 |
| Flink 总内存 | `taskmanager.memory.flink.size` | 不含 JVM 额外开销 | 下面几项之和 |
| Framework Heap | `taskmanager.memory.framework.heap.size` | Flink 框架自身对象 | 一般不用改 |
| Framework Off-Heap | `taskmanager.memory.framework.off-heap.size` | 框架的堆外（如某些网络缓冲） | 一般不用改 |
| **Task Heap** | `taskmanager.memory.task.heap.size` | **用户代码（算子、UDF、HashMap 状态后端）用的堆** | HashMap 状态、UDF 里的集合、反序列化对象 |
| Task Off-Heap | `taskmanager.memory.task.off-heap.size` | 用户代码显式申请的堆外 | 少用 |
| **Managed Memory** | `taskmanager.memory.managed.size` / `.fraction` | **RocksDB 状态后端的主要内存来源**，也供批算子（sort/hash/join）使用 | RocksDB 的 block cache、write buffer、memtable |
| **Network Memory** | `taskmanager.memory.network.{min,max,fraction}` | 网络缓冲（shuffle/交换数据的缓冲池） | 上下游数据传输 |
| JVM Metaspace | `taskmanager.memory.jvm-metaspace.size` | 类元数据 | 动态生成类多时（大量 UDF、Groovy）会涨 |
| JVM Overhead | `taskmanager.memory.jvm-overhead.{min,max,fraction}` | 线程栈、GC 结构、code cache、JNI、JVM 自身 | **OOMKilled 的常见元凶** |

> [!important] 三句必须记住的话
> 1. **Managed Memory 是给 RocksDB 的**。用 HashMap 状态后端跑纯流作业时，managed memory 基本闲置（它不会被自动借给 Task Heap）。所以"状态后端换 RocksDB 后堆内存压力下降"是正常的，因为状态从堆搬到了 managed memory + 本地磁盘。
> 2. **`process.size` 才是容器大小的依据**。JVM Overhead 是"给 JVM 自己留的余量"，如果实际 JVM 开销超过它（大量线程、大 direct memory、频繁 GC 产生的结构），就会超出容器 limit → **被 cgroup OOMKilled**，而不是抛 Java `OutOfMemoryError`。
> 3. **Task Heap 和 Managed Memory 是此消彼长的关系**。给 RocksDB 更多 managed memory → 留给 Task Heap 的更少。反过来把 managed 调成 0 又想用 RocksDB，性能会非常差（频繁刷盘）。

### 4.2 JobManager 内存

| 区域 | 配置键 | 说明 |
| --- | --- | --- |
| 进程总内存 | `jobmanager.memory.process.size` | 容器大小依据 |
| Flink 总内存 | `jobmanager.memory.flink.size` | 不含 JVM 额外开销 |
| JVM Heap | `jobmanager.memory.heap.size` | 调度元数据、状态句柄、算子指标 |
| Off-Heap | `jobmanager.memory.off-heap.size` | JM 的堆外 |
| JVM Metaspace | `jobmanager.memory.jvm-metaspace.size` | 类元数据 |
| JVM Overhead | `jobmanager.memory.jvm-overhead.{min,max,fraction}` | JVM 自身 |
| 直接内存限制 | `jobmanager.memory.enable-jvm-direct-memory-limit` | 打开后按容器限制 JVM direct memory，**K8s 上建议开** |

> [!note] JM 内存什么时候会不够
> - 作业**算子数量极多**（几百个算子、复杂 DAG）：调度元数据、Checkpoint 协调状态都在 JM 堆里
> - 大量**短生命周期作业频繁提交**：JM 上累积的指标/历史状态
> - 用 `-XX:+UseG1GC` 之外的 GC 且堆太小 → 表现为频繁 Full GC、UI 卡顿、心跳超时
>
> 症状通常是 UI 打不开、`JobManager is not responding`、REST API 超时，而不是作业报错。JM 内存给 2G 起步是常见做法，算子特别多时再往上加。

### 4.3 一个合理的配置示例

```yaml
flinkConfiguration:
  # ---------- TaskManager：容器 4G ----------
  taskmanager.memory.process.size: 4096m
  # 让 Flink 自动按比例切分 Flink 内存与 JVM overhead（一般不用手写每一项）
  taskmanager.memory.managed.fraction: "0.4"      # 40% 给 RocksDB
  taskmanager.memory.network.fraction: "0.1"      # 10% 给网络缓冲
  taskmanager.memory.jvm-overhead.fraction: "0.1" # 10% 给 JVM 自身
  taskmanager.numberOfTaskSlots: "4"

  # ---------- JobManager：容器 2G ----------
  jobmanager.memory.process.size: 2048m
  jobmanager.memory.enable-jvm-direct-memory-limit: "true"
```

对应 K8s 侧要让**容器 memory limit ≥ `process.size`**（Operator 会从 `resource.memory` 反推 `process.size`；如果你两边都写了且不一致，会直接报配置冲突）：

```yaml
taskManager:
  resource:
    memory: "4096m"     # >= taskmanager.memory.process.size
    cpu: 2
jobManager:
  resource:
    memory: "2048m"
    cpu: 1
```

> [!danger] 容器被 OOMKilled 的四个常见原因
> 1. **只配了 `flink.size` 没配 `process.size`**，或者 K8s limit 小于 `process.size` → JVM 开销溢出被内核杀
> 2. **JVM Overhead 不够**：线程数多（并行度高、异步 IO 多）、direct memory 大
> 3. **容器里跑了别的东西**（agent、日志采集 sidecar 同容器）→ 挤占内存
> 4. **RocksDB 用堆外/本地内存超预期**（block cache 配置过大、原生内存泄漏）
>
> **排查顺序**：`kubectl describe pod` 看 `Last State: Terminated, Reason: OOMKilled` → 对比 `resources.limits.memory` 与 `process.size` → 看 TM 日志有没有 Java OOM 堆栈（**有 Java 堆栈说明是 Task Heap 不够，直接 OOMKilled 才是 JVM Overhead 不够**）→ 用监控看 `Heap.Used`、`Metaspace.Used`、GC 频率的趋势。

## 五、日志与监控

### 5.1 日志

| 项 | 做法 |
| --- | --- |
| 日志目录 | 由 `env.log.dir` 指定（镜像里通常是 `/opt/flink/log`） |
| 日志文件名 | `flink-<user>-jobmanager-<host>.log`（框架日志）、`...out`（stdout/stderr，**启动期异常常在这里**） |
| 日志配置 | 覆盖 `conf/log4j2.properties`；可以用 `-Dlog4j.configurationFile=` 指向自定义配置 |
| 日志轮转 | log4j2 里配 RollingFile + 大小/时间策略，避免撑爆磁盘 |
| 日志级别动态调整 | Flink Web UI 上可以直接改**某个 logger 的级别**，排障时非常有用，不用重启 |
| K8s 日志收集 | `kubectl logs <pod>` / `kubectl logs -l app=<cluster-id>`；生产建议接 Fluent Bit / Loki / ELK，按 `cluster-id` 打标签聚合 |
| YARN 日志聚合 | 开 `yarn.log-aggregation-enable`，用 `yarn logs -applicationId <appId>` 一次拿全 |
| 排查要点 | **异常堆栈的 root cause 认准 `.log` 和 `.out` 两处**；TM 的 OOM/exit code 也在里面 |

> [!tip] 生产日志至少要落一份到持久化存储
> Pod 被删除/replace 后，容器内日志随之消失。作业"凌晨 3 点挂了一次、早上才发现"的场景下，**日志已经没了**，只能靠监控指标反推。所以日志集中收集和指标上报是配套的两件事，缺一不可。

### 5.2 指标体系与 Metric Reporter

```yaml
# conf/flink-conf.yaml（或 flinkConfiguration）
metrics.reporters: prom,jmx
# Prometheus：Flink 1.19 前后类名有调整，按你的版本文档取
metrics.reporter.prom.factory.class: org.apache.flink.metrics.prometheus.PrometheusReporterFactory
metrics.reporter.prom.port: 9250-9260        # 端口区间，多实例自动错开
metrics.reporter.prom.filterLabelValueCharacters: true

metrics.reporter.jmx.factory.class: org.apache.flink.metrics.jmx.JMXReporterFactory
metrics.reporter.jmx.port: 8789

# 采集间隔（不要太密，指标上报本身也是开销）
metrics.reporter.prom.interval: 10 SECONDS

# 端到端延迟指标：开启后会在每条记录里注入延迟标记，有额外开销，按需开启
metrics.latency.interval: 30000
metrics.latency.granularity: operator
```

| Reporter | 适用 | 说明 |
| --- | --- | --- |
| **Prometheus** | K8s / 云原生 | 最常用，配套 Grafana + Alertmanager |
| **JMX** | JVM 生态、外部 APM | 便于 JConsole/自研采集 |
| **InfluxDB** | 时序库直连 | 需要 `metrics.reporter.influxdb.*` 一组配置 |
| **Graphite** | 传统监控 | 老平台常见 |
| **SLF4J / 日志** | 调试 | 直接打日志，不要在生产长期开 |

> [!warning] 不要一上来就开全量指标
> 每个算子的每个指标都是一条时间序列。**算子数 × 并行度 × 指标数** 会迅速变成几十万序列，把 Prometheus 打爆（典型症状：Prometheus OOM、Grafana 加载超时）。生产做法是**只上报关键指标 + 用 `metrics.reporter.prom.filter` 类配置或 Prometheus 侧 relabel 做裁剪**。

### 5.3 关键指标清单

**① 作业级（JobManager / Job）**

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| `uptime` / `downtime` | 作业运行/停机时长 | `uptime` 反复归零 = 正在反复重启 |
| `numRestarts` / `fullRestarts` | 重启次数 | **持续增长是最高优先级告警** |
| `restartingTime` | 处于重启中的累计时间 | 长时间不归零说明恢复困难 |
| `numberOfFailedCheckpoints` | 失败的 Checkpoint 数 | 持续增长说明快照链路有问题 |
| `numberOfCompletedCheckpoints` | 成功的 Checkpoint 数 | 与配置间隔对比，能看出是否"根本打不出来" |
| `lastCheckpointDuration` | 最近一次 Checkpoint 耗时 | 接近或超过 `timeout` 就是危险信号 |
| `lastCheckpointSize` | 最近一次 Checkpoint 大小 | **持续单调增长 = 状态膨胀** |
| `lastCheckpointRestoreTimestamp` | 最近一次恢复的时间点 | 判断恢复是否在推进 |
| `numberOfInProgressCheckpoints` | 进行中的 Checkpoint 数 | 长期 > 1 说明有 Checkpoint 卡住 |

**② 算子级（Operator / Task）**

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| `numRecordsIn` / `numRecordsOut` | 累计流入/流出记录数 | 上下游对不齐 = 有数据被过滤或堵塞 |
| `numRecordsInPerSecond` / `numRecordsOutPerSecond` | 实时速率 | **判断吞吐与瓶颈的第一指标** |
| `numBytesInLocal` / `numBytesInRemote` / `numBytesOut` | 网络流量 | `numBytesOut` 远大于 `Local` 说明大量跨节点 shuffle |
| `currentInputWatermark` | 当前输入水位 | **长期不推进 = 有分区空闲或数据延迟** |
| `currentOutputWatermark` | 当前输出水位 | 与 input 对比可看出算子在压水位 |
| `numLateRecordsDropped` | 被丢弃的迟到记录数 | 突增说明 watermark 策略/迟到容忍有问题 |
| `backPressuredTimeMsPerSecond` / `accumulatedBackpressuredTimeMsPerSecond` | 背压时间占比 | **持续高 = 真正背压**，偶发高不必惊慌 |
| `busyTimeMsPerSecond` / `idleTimeMsPerSecond` | 忙碌/空闲时间占比 | 全员 busy 而吞吐上不去 → 典型瓶颈 |
| `numRecordsInErrors` | 反序列化/处理错误数 | 数据质量问题入口 |

**③ TaskManager 级**

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| `taskmanager.Status.JVM.Memory.Heap.Used` / `.Max` | 堆使用/上限 | 长期贴近 Max + 频繁 Full GC → 堆不够 |
| `taskmanager.Status.JVM.Memory.Metaspace.Used` | 元空间 | 持续增长不回落 → 类加载泄漏 |
| `taskmanager.Status.JVM.GarbageCollector.<GC>.Time` / `.Count` | GC 时间与次数 | GC 时间占比高会直接拉低吞吐 |
| `taskmanager.Status.JVM.Threads.Count` | 线程数 | 异常增长 → 线程泄漏 |
| `taskmanager.Status.Flink.Memory.Managed.Used` / `.Total` | Managed Memory 用量 | RocksDB 场景下应稳定在较高水位，长期打满要注意调大 |
| `taskmanager.Status.JVM.CPU.Load` | CPU 负载 | 配合容器 CPU limit 判断是否被 throttle |

**④ JobManager / 集群级**

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| `numRegisteredTaskManagers` | 已注册的 TM 数 | **低于预期 = TM 掉了或起不来** |
| `numRunningJobs` | 运行中的作业数 | Session 集群上用于判断资源是否被占满 |
| `taskSlotsAvailable` / `taskSlotsTotal` | 可用/总 Slot | 可用为 0 = 新作业无法启动 |
| JM 的 `Heap.Used` / GC 指标 | JM 健康度 | JM 内存不足表现为 UI 卡、REST 超时 |

**⑤ Checkpoint 与延迟**

| 指标 | 含义 | 关注点 |
| --- | --- | --- |
| `lastCheckpointAlignmentBuffered` | 对齐阶段缓存的字节数 | 大且抖动 → 背压导致对齐慢，可考虑非对齐 Checkpoint |
| `lastCheckpointExternalPath` | 快照外部路径 | 排查恢复问题时用来定位文件 |
| `currentEmitEventTimeLag`（Kafka Source） | 事件进入 Source 到发出的延迟 | **消费滞后的直接代理指标** |
| `currentFetchEventTimeLag`（Kafka Source） | 数据产生到被拉取的延迟 | 判断是上游积压还是 Flink 处理慢 |
| 端到端 `latency`（需 `metrics.latency.interval`） | 记录从 Source 到 Sink 的耗时 | 有额外开销，按需开启 |
| Kafka 消费组 lag | 用 `kafka-consumer-groups.sh --describe` 或 kafka-exporter 采集 | **Flink 侧不直接暴露消费组 lag，别指望它** |

### 5.4 建议的告警项

| 告警 | 触发条件 | 为什么 |
| --- | --- | --- |
| **作业重启** | `numRestarts` 或 `fullRestarts` 在窗口内增长 | 最直接的故障信号 |
| **Checkpoint 持续失败** | `numberOfFailedCheckpoints` 连续增长 / 长时间无 `numberOfCompletedCheckpoints` 增长 | 说明容错能力已经失效，下一次故障就会丢数据 |
| **Checkpoint 变慢/变大** | `lastCheckpointDuration` 上升趋势、`lastCheckpointSize` 单调上升 | 状态膨胀的早期信号，越早发现越好治 |
| **持续背压** | `backPressuredTimeMsPerSecond` 长期高于阈值（偶发尖峰不告警） | 背压持续 = 处理能力不足，延迟会随之劣化 |
| **消费延迟/滞后** | `currentEmitEventTimeLag` 持续上升 | 直接对应业务可见的数据延迟 |
| **Kafka lag** | 消费组 lag 超阈值 | 上游积压，链路入口就堵了 |
| **TM 数不足** | `numRegisteredTaskManagers` 低于期望值 | 资源层故障，作业可能降级运行 |
| **资源水位** | 堆使用长期 > 80%、CPU throttle、磁盘（RocksDB 本地目录）使用率高 | 事故前兆 |
| **Watermark 停滞** | `currentInputWatermark` 长时间不推进 | 窗口永远不触发，结果出不来 |

> [!important] 告警设计的核心原则：告警"症状"而不是"噪声"
> 一个作业每天偶发几次背压尖峰是正常的。要告警的是 **"持续 5 分钟背压 > 阈值"**、**"15 分钟没有完成一次 Checkpoint"**、**"重启次数增加"** 这类**有业务含义的持续状态**，而不是每一个瞬时抖动。

## 六、作业生命周期运维命令

### 6.1 常用 CLI 命令

```bash
# ---- 查看 ----
bin/flink list                       # 列出运行中的作业
bin/flink list -a                    # 包含已结束/失败的作业
bin/flink list -m <jm-host:port>     # 指定集群（Session 模式下常用）

# ---- 停止 ----
bin/flink cancel <jobId>                                  # 直接取消，不保状态
bin/flink cancel -s s3://flink-state/savepoints <jobId>    # 先打 Savepoint 再取消
bin/flink stop --savepointPath s3://flink-state/savepoints <jobId>
bin/flink stop --drain --savepointPath s3://... <jobId>    # 排空（发 MAX_WATERMARK，触发所有窗口）

# ---- Savepoint ----
bin/flink savepoint <jobId> s3://flink-state/savepoints/order-job
bin/flink savepoint --dispose s3://flink-state/savepoints/order-job/savepoint-xxxx   # 删除
bin/flink savepoint -d <path>

# ---- 提交与恢复 ----
bin/flink run -d -p 8 -c com.demo.OrderJob order-job.jar          # -d 后台提交，-p 并行度
bin/flink run -s s3://flink-state/savepoints/savepoint-xxxx \
              -c com.demo.OrderJob order-job.jar                   # 从 Savepoint 恢复
bin/flink run -s <savepoint> --allowNonRestoredState order-job.jar # 跳过无法映射的状态（危险）
bin/flink info order-job.jar                                       # 打印执行计划（新版本已不推荐）

# ---- Application 模式 ----
bin/flink run-application -t kubernetes-application -Dkubernetes.cluster-id=xxx ...
bin/flink run-application -t yarn-application ...
```

### 6.2 `stop` vs `cancel`：必须分清

| 命令 | 语义 | 是否产生 Savepoint | 数据完整性 | 适用 |
| --- | --- | --- | --- | --- |
| `flink cancel` | **立即取消**，停止所有 Task | ❌ 默认不产生（加 `-s` 才产生） | 可能丢未处理数据 | 开发调试、作业放飞了要紧急止血 |
| `flink stop` | **优雅停止**：先停 Source → 打 Savepoint → 取消作业 | ✅ 一定产生 | 更好，能保住状态 | **生产下线、升级、迁移的标准做法** |
| `flink stop --drain` | 在 `stop` 基础上发送 `MAX_WATERMARK`，**让所有事件时间窗口先触发输出** | ✅ | 窗口结果最完整 | 需要"把最后的数据算完再停"的场景 |
| `flink savepoint` | **只打快照，不停作业** | ✅ | 作业继续运行 | 定期备份、升级前的保险 |

> [!tip] `--drain` 的代价与收益
> `--drain` 会发 `MAX_WATERMARK`，让所有基于事件时间的定时器/窗口立即触发。好处是**停之前把能算的都算完**；代价是会有一波集中的下游写入压力，并且**如果作业里有依赖 watermark 做清理的逻辑，可能一次性产生大量输出**。
>
> 判断标准：下游能承受瞬时冲高 → 用 `--drain`；否则用普通 `stop`，并接受窗口尾部会有一点延迟数据（重启后靠 `allowedLateness` 或后续补偿处理，见 [[2-时间与窗口]]）。

### 6.3 REST API 要点

| --- | --- | --- |
| 列出作业 | `GET /jobs` | 返回 jobId、状态、名称 |
| 作业详情 | `GET /jobs/:jobid` | 状态、时间戳、任务统计 |

## 七、升级与扩缩容

### 7.1 状态兼容与 Savepoint 恢复

从 Savepoint 恢复时，Flink 会**按算子 UID 精确匹配状态**：

```java
// 显式指定 UID：状态匹配的依据，改了就恢复不了
env.fromSource(kafkaSource, WatermarkStrategy.noWatermarks(), "kafka-source").uid("kafka-source-uid")
   .keyBy(r -> r.getUserId()).window(TumblingEventTimeWindows.of(Time.minutes(5)))
   .aggregate(new OrderAgg()).uid("order-agg-uid")
   .addSink(dorisSink).uid("doris-sink-uid");
```

| 变更 | 能否从 Savepoint 恢复 | 说明 |
| --- | --- | --- |
| 改业务逻辑但状态结构不变 | ✅ | 最常见的安全升级 |
| **改了/删了算子 UID** | ❌ | 状态找不到归属，报 `Cannot map checkpoint/savepoint state for operator ...` |
| 删除某个算子 | ❌（除非 `--allowNonRestoredState`） | 该算子的状态无法分配 |
| 改状态数据结构（如 POJO 加字段且没有默认值/序列化器不兼容） | ❌ | 序列化器无法反序列化旧数据 |
| 改 `maxParallelism` | ❌ | key group 划分变了，元数据对不上 |
| 只改并行度（在 key group 允许范围内） | ✅ | 会做 key group 重分配 |
| 换状态后端（HashMap ↔ RocksDB） | ⚠️ 视状态类型而定 | keyed state 一般可通过 Savepoint 迁移，但要验证 |

> [!danger] `--allowNonRestoredState` 是把双刃剑
> 它让 Flink **跳过所有无法映射到当前作业的状态**并强行启动。好处是"作业能起来"；代价是**你可能在不知不觉中丢掉了关键状态**（比如去重用的 keyed state、去重导致下游重复数据）。
>
> 正确用法：只在**明确知道哪些状态可以丢**（比如纯缓存、可重建的维表状态）时使用，并且要在变更记录里写清楚"丢了什么"。
> 错误用法：把它当成"恢复失败的万能解药"——这是很多"数据莫名多出来/少了几条"事故的起点。

### 7.2 并行度变更与 key group：为什么 `maxParallelism` 一锤定音

**原理链条**：

```
key  --hash-->  key group（编号 0 .. maxParallelism-1）
key group  --分配-->  subtask（0 .. parallelism-1）
```

- 状态永远是**按 key group 存储**的，不是按 key 或按 subtask 存的
- 扩缩容时，Flink 只需把 key group 在 subtask 之间重新分配（**key group 的重分布**），不需要重新计算每个 key 的归属
- 所以：**并行度可以改（只要有足够的 key group 可分），`maxParallelism` 不能改**

| 项 | 结论 |
| --- | --- |
| `maxParallelism` 是什么 | key group 的总数，**决定了并行度能达到的上限** |
| 不显式设置会怎样 | Flink 按首次提交时的并行度推一个默认值（与并行度相关的策略），**你无法预知**，未来扩容可能直接被卡住 |
| 生产该怎么做 | **显式设置 `pipeline.max-parallelism`**，一般取预期最大并行度的数倍，并留足余量 |
| 上限 | key group 数量有编码上限（不能无限大），所以也不能随手写个天文数字 |
| 改了 `maxParallelism` 会怎样 | 从 Savepoint 恢复直接失败（key group 元数据不匹配），必须**不保留状态**重跑，或走特殊迁移方案 |
| 只想改并行度 | 从 Savepoint 恢复时指定新的 `-p` 即可，key group 会自动重分配 |

> [!important] 面试常问的"为什么扩容有上限"
> 因为状态是按 **key group** 组织的，key group 的总数就是 `maxParallelism`。并行度提高时，一个 subtask 分到的 key group 变少；当并行度 > maxParallelism 时，**必然有 subtask 分不到 key group**，无法拆分。所以 `maxParallelism` 在第一次提交时就"锁死"了这个作业未来的扩容天花板。**上线前显式设置它，是生产就绪清单里最容易被忽略、后果最严重的一条。**
>
> 另外：非 keyed 的算子状态（如 Source 的位点）用的是 union/split 重分布策略，扩缩容行为不同，但同样需要算子 UID 不变。

### 7.3 滚动升级 Flink 版本

```bash
# ① 升级前：打 Savepoint 并确认成功
bin/flink stop --savepointPath s3://flink-state/savepoints/order-job <jobId>
# 或对运行中作业直接打
bin/flink savepoint <jobId> s3://flink-state/savepoints/order-job

# ② 记录当前状态：jobId、并行度、maxParallelism、状态后端、Checkpoint 配置

# ③ 升级组件：换镜像 / 换 Flink 发行版（保持 jar 与连接器版本对齐）

# ④ 用新版本从 Savepoint 恢复
bin/flink run -s s3://flink-state/savepoints/order-job/savepoint-xxxx \
  -d -p 8 -c com.demo.OrderJob order-job.jar

# ⑤ 验证：吞吐、Checkpoint 成功、下游数据量、延迟指标
```

| 检查点 | 说明 |
| --- | --- |
| 状态格式兼容性 | 跨越多个大版本时状态格式可能不兼容；**降级通常不可行**（升级前务必留 Savepoint 作为回滚点） |
| 连接器版本对齐 | Flink 大版本升级往往要求连接器同步升级（`flink-connector-kafka`、CDC 连接器等） |
| Java 版本 | 新版本 Flink 对 JDK 的最低要求会提高（如 JDK 8 → 11 → 17 的迁移） |
| 配置键改名 | 例如状态后端相关配置在新版本中键名有变化（`state.backend` → `state.backend.type` 一类），**旧键可能被忽略而不报错**，要逐条核对 |
| 废弃 API | `Per-Job` 模式、部分 Source/Sink API 会被移除 |
| 先灰度 | 生产上先在预发环境用同一份 Savepoint 验证一遍，再动线上 |

### 7.4 扩缩容与升级核对清单

> **准备**

## 八、生产就绪核对清单（Production Readiness Checklist）

参考 Flink 官方 Production Readiness Checklist 的结构，按"配置 / 容错 / 资源 / 可观测 / 状态 / 依赖"六组组织。

### 8.1 配置（Configuration）

- [ ] **显式设置 `pipeline.max-parallelism`**（最重要的一条）
- [ ] 所有有状态的算子显式设置 **UID**
- [ ] 并行度、Slot 数、TM 数三者匹配（`Slot 数 × TM 数 ≥ 最大并行度`）
- [ ] 状态后端明确选择（小状态 HashMap / 大状态 RocksDB），大状态开启**增量 Checkpoint**
- [ ] RocksDB 场景配置本地目录（`state.backend.rocksdb.localdir`）到**高性能磁盘**，并确保容量充足
- [ ] Watermark 策略、空闲分区处理（`withIdleness`）、`allowedLateness` 明确配置
- [ ] 时区统一（`env` 时区、CDC 的 `server-time-zone`、下游存储时区，见 [[7-FlinkCDC与实时数仓]]）

### 8.2 容错（Fault Tolerance）

- [ ] Checkpoint 已开启：`execution.checkpointing.interval`、`timeout`、`min-pause`
- [ ] Checkpoint 语义为 `EXACTLY_ONCE`（除非明确接受 `AT_LEAST_ONCE`）
- [ ] `execution.checkpointing.externalized-checkpoint-retention` 设为 `RETAIN_ON_CANCELLATION` 或 `RETAIN_ON_FAILURE`（**否则取消作业会把 Checkpoint 一起删掉**）
- [ ] Checkpoint/Savepoint 目录指向**持久化存储**（S3/HDFS），且凭证有效
- [ ] 配置了合理的**重启策略**（`fixed-delay` / `exponential-delay`），避免"崩了就永久退出"或"疯狂重启打爆源库"
- [ ] 配置了 HA（K8s HA 或 ZooKeeper HA）+ `high-availability.storageDir`
- [ ] 定期 Savepoint 的机制（Operator 周期 Savepoint / 定时脚本），并验证过恢复流程
- [ ] 端到端一致性方案确定（Sink 2PC 或主键幂等），详见 [[11-端到端一致性]]

### 8.3 资源（Resources）

- [ ] JM/TM 的 `*.memory.process.size` 设置合理，并与 K8s `resource.memory` 一致
- [ ] TaskManager 内存分布合理（RocksDB 场景给足 managed memory）
- [ ] JVM Overhead 留足（避免 OOMKilled）
- [ ] JM 内存充足（算子数量多时尤其）
- [ ] CPU 请求/限制与实际负载匹配（观察 CPU throttle）
- [ ] 网络缓冲（`network.memory`）与 shuffle 量匹配
- [ ] 本地磁盘（日志 + RocksDB）容量与 IOPS 满足
- [ ] Java 版本与 GC 策略选定（大堆考虑 G1/ZGC 并观察 GC 指标）

### 8.4 可观测（Observability）

- [ ] Metric Reporter 已配置（Prometheus/JMX/InfluxDB），且指标量可控
- [ ] 关键指标有 Grafana 看板（吞吐、延迟、Checkpoint、背压、水位、GC）
- [ ] 告警已配置（重启、Checkpoint 失败、持续背压、延迟上升、Kafka lag、TM 数不足）
- [ ] 日志级别与轮转合理，日志已集中收集
- [ ] 知道怎么用 REST API `/jobs/:jobid/exceptions` 快速定位异常
- [ ] 有 runbook（谁在什么情况下怎么处理），而不只是有监控

### 8.5 状态（State）

- [ ] Keyed 状态配置了 **TTL**（`table.exec.state.ttl` 或 `StateTtlConfig`），避免无限膨胀
- [ ] 状态大小有基线，并监控趋势（`lastCheckpointSize`）
- [ ] 明确知道哪些算子的状态是"必须保留"、哪些是"可重建"
- [ ] 大状态作业演练过"从 Savepoint 恢复"（**没演练过的恢复方案等于没有方案**）
- [ ] 数据倾斜已评估（热点 key 会让单个 subtask 状态/负载远超其他，见 [[6-背压与性能调优]]）

### 8.6 依赖（Dependencies）

- [ ] 连接器版本与 Flink 版本对齐，SQL 作业用 `flink-sql-connector-*` uber jar
- [ ] 用户 jar 做了 shade，避免与 Flink 内置依赖冲突
- [ ] 镜像里包含所需 jar 与配置（Application 模式用 `local://` 引用）
- [ ] 外部系统凭证通过 Secret/环境变量注入，**不硬编码在 jar 或代码里**
- [ ] 提交脚本/CI 流程可重复（同样输入产生同样配置）

> [!important] 必答：生产上你怎么部署和保障 Flink 作业稳定
> **部署**：生产统一用 **Application 模式 + K8s（Flink Kubernetes Operator）**，作业以 `FlinkDeployment` CRD 声明式管理，镜像里带业务 jar 和连接器；JM/TM 用 `flink` ServiceAccount 起 Pod；HA 用 **Kubernetes HA + S3 上的 `high-availability.storageDir`**。
>
> **稳定**：五个支柱——
> ① **容错**：Checkpoint 开启（EXACTLY_ONCE + externalized retention）+ 合理重启策略 + 定期 Savepoint + 演练过恢复；
> ② **资源**：显式内存模型配置（`process.size` ≥ 容器 limit）、RocksDB 增量 Checkpoint、`maxParallelism` 预留扩容空间；
> ③ **可观测**：Prometheus 指标 + 关键告警（重启 / Checkpoint 失败 / 持续背压 / 延迟 / lag）+ 日志集中收集 + runbook；
> ④ **状态治理**：状态 TTL、状态大小趋势监控、倾斜检查；
> ⑤ **变更管理**：升级走 "Savepoint → 停 → 新版本恢复 → 指标验证 → 保留回滚点"，改逻辑前先确认状态兼容性，绝不用 `--allowNonRestoredState` 掩盖恢复失败。

## 九、常见故障排查表

| 现象 | 可能原因 | 排查动作 | 处理 |
| --- | --- | --- | --- |
| **作业反复重启** | 代码异常、数据脏、下游连接失败、TM OOM、Checkpoint 太久被 kill | 看 `numRestarts`/`fullRestarts` 趋势 → 看 JM 的 **`/jobs/:jobid/exceptions`** → 看 TM `.log`/`.out` 的 root cause | 修根因；临时把重启策略从"无限快速重启"改为 `exponential-delay`，避免打爆下游 |
| **容器 OOMKilled** | `process.size` > 容器 limit；JVM Overhead 不足；堆外/direct memory 超限；sidecar 挤占 | `kubectl describe pod` 看 `Reason: OOMKilled`；对比 `limits.memory` 与 `taskmanager.memory.process.size`；看堆指标与 GC | 调大 `process.size`/容器 limit，或调大 `jvm-overhead`；给 RocksDB 单独的 managed memory 预算 |
| **Checkpoint 超时/失败** | 状态太大；反压导致 Barrier 对齐慢；存储慢/限流；`timeout` 太短；并发 Checkpoint 冲突 | 看 `lastCheckpointDuration` vs `timeout`、`lastCheckpointSize` 趋势、`numberOfFailedCheckpoints`；看存储侧延迟 | 调大 `timeout`/`min-pause`；开启增量 Checkpoint；用**非对齐 Checkpoint** 缓解反压下的对齐；排查状态膨胀 |
| **Checkpoint 越来越慢** | 状态膨胀（无 TTL）、反压、磁盘 IO 瓶颈、存储端慢 | 看 `lastCheckpointSize` 是否单调增长；看背压指标；看 RocksDB 本地目录 IO | 加状态 TTL、清理无用状态、拆分作业、升级磁盘；详见 [[3-状态管理]] |
| **Savepoint 恢复失败** | 算子 UID 改了/删了；状态结构不兼容；`maxParallelism` 变了；状态后端不兼容 | 看异常里的算子名与 "Cannot map ... state"；对比变更记录 | 回滚到旧版本或旧 Savepoint；确需丢弃状态时明确评估影响后再用 `--allowNonRestoredState` |
| **恢复后又变成空状态** | Savepoint 路径不对/不可读；用了错的 savepoint；日志里有 "restored from empty state" | 看启动日志有没有 "No state was restored" / "restored from empty state" | 立刻停，检查路径与权限。**空状态启动 + append 下游 = 数据重复** |
| **K8s Pod 起不来** | 镜像拉不到（凭证/仓库）、资源不足（Pending）、SA 权限不足、配置冲突（`process.size` 与 `resource.memory` 不一致） | `kubectl describe pod` 看 Events；`kubectl get events`；看 CRD 的 `status` | 修镜像/凭证、加资源、补 SA 权限、对齐内存配置 |
| **作业卡在 "Job is not yet running"** | TM 起不来（SA 缺 `pods` 权限最常见）；Slot 不足；镜像里 jar 路径不对（`local://` 路径不存在） | JM 日志里的 K8s API 报错；`kubectl get pods` 看 TM 有没有被创建 | 补 `kubernetes.jobmanager.service-account` 与 RBAC；检查镜像内路径 |
| **状态后端目录权限报错** | Checkpoint/Savepoint 目录不可写、凭证过期、路径不存在 | 日志里的 `AccessDenied` / `FileNotFoundException` / `No FileSystem for scheme` | 修凭证（IAM Role / Secret）、确认 scheme 与依赖（s3a/hdfs 插件）、先用 `flink fs` 类手段或工具验证可写性 |
| **时钟不同步导致 watermark 异常** | 节点间时间漂移；事件时间来自上游且时钟不一致 | 对比各节点 `date`；看 `currentInputWatermark` 是否异常（超前/倒退/停滞） | 部署 NTP/chrony；避免依赖"处理时间"做跨节点一致性判断；watermark 生成策略改为基于事件时间 |
| **Watermark 不推进、窗口不出结果** | 有分区/子任务空闲（无数据）；某条流卡住；`withIdleness` 未配 | 看每个 source 的 `currentInputWatermark`，找停滞的那个 | 配 `WatermarkStrategy.withIdleness(...)`；排查空闲原因 |
| **背压持续告警** | 下游慢（sink 慢/维表查询慢）、数据倾斜、GC 停顿、并行度不足 | 从 Sink 往上逐算子看 `backPressuredTimeMsPerSecond`，找**第一个背压的算子** | 优化该算子：加并行度、改异步/批量写、解决倾斜；见 [[6-背压与性能调优]] |
| **Session 集群上作业抢不到资源** | Slot 被其他作业占满 | 看 `taskSlotsAvailable`、`numRunningJobs` | Session 模式本就不适合生产；迁到 Application 模式 |
| **UI 打不开 / REST 超时** | JM 内存不足、GC 长停顿、网络策略 | 看 JM 堆与 GC 指标；`kubectl logs` 看 JM | 加 JM 内存；检查 Ingress/NetworkPolicy/端口转发 |
| **上线后数据和离线对不上** | 口径不同、迟到数据、状态 TTL 过期、CDC 位点/主键问题 | 按 [[7-FlinkCDC与实时数仓]] 第五节的口径核对顺序排查 | 统一口径定义层；对账机制（T+1 与离线比对） |

> [!tip] 排查的通用三步法
> 1. **先定位"哪个环节"**：Source（位点/lag）→ 计算（背压/watermark/异常）→ Sink（写入失败/慢）
> 2. **再看"时间线"**：什么时候开始的？期间有什么变更（发版、扩容、上游 DDL、集群故障）？——**80% 的线上问题都能靠"最近改了什么"定位**
> 3. **最后看"证据"**：`/jobs/:jobid/exceptions` + TM/JM 日志 + 关键指标趋势，三者交叉验证，不要凭猜测改配置
