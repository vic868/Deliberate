## 一、怎么用这一篇

### 1.1 什么是"得分骨架"

面试回答有三个层次：

| 层次 | 表现 | 面试官感受 |
| --- | --- | --- |
| **背书层** | 只复述定义（"Flink 是一个流处理框架…"） | 像是看过文章 |
| **骨架层** | 分点、有因果、能讲清"为什么这么设计" | **会** |
| **落地层** | 能说出生产参数、失败场景、怎么排查 | **用过** |

**"得分骨架"就是骨架层的答案**：3-6 条短句，每条一个要点，合起来逻辑自洽。答题时**先抛骨架，再展开**——让面试官在你展开口水之前就知道你答全了。

### 1.2 三条通用技巧

> [!tip] 面试通用技巧
> 1. **先骨架后细节**：先说"我从四个方面回答"，再逐条展开。面试官能立刻判断你的完整度。
> 2. **主动给 tradeoff**：每个技术选型都说"好处是 X，代价是 Y，所以我们在 Z 场景下选了它"。**这是区分"会"和"背过"的关键。**
> 3. **主动抛生产细节**：一句话里带一个真实参数或一次真实故障（"我们把 `min-pause` 从 0 调到 30s 之后，Checkpoint 超时问题就消失了"），可信度会立刻拉满。

### 1.3 时间分配建议（45 分钟技术面）

| --- | --- | --- |
| 自我介绍 + 项目 | 5-8 min | 埋钩子（主动提"实时数仓"、"Exactly-Once"） |

## 二、八大必答题

### 题 1：Flink 架构与运行时

**得分骨架**

1. 运行时是**一个 JobManager + 多个 TaskManager** 的 Master/Slave 结构；JM 负责调度、协调 Checkpoint、故障恢复，TM 负责执行任务。
2. **Slot 是 TM 上的资源切片**（CPU/内存的逻辑划分，不是物理隔离），一个 Slot 可以跑**一条完整的算子链（pipeline）**。
3. **Slot Sharing** 让同一 Job 的不同算子共享同一个 Slot，好处是：一个 Slot 就能跑完整条流水线、负载更均衡；代价是**一个 Slot 里的任务互相影响资源**。
4. **算子链（Operator Chaining）** 把满足条件的算子合并成一个 Task：同一并行度、forward 连接、无 shuffle。好处是减少线程切换和序列化开销。
5. 作业的物理执行图分三层：**StreamGraph → JobGraph（合并算子链）→ ExecutionGraph（按并行度展开）**。

**深入追问：`setParallelism` 和"资源配置"是什么关系？**

- 并行度是**逻辑上的任务数**，资源是**物理上的 Slot 数**。总并行度需求必须 ≤ 集群可用 Slot 总数（`TM 数 × 每 TM 的 Slot 数`），否则作业会卡在 `CREATED`/资源不足。
- 调并行度 ≠ 调资源：并行度从 4 调到 8，如果 Slot 只有 4 个，作业根本起不来；反过来 Slot 有 16 个但并行度是 4，剩下 12 个就空着（**Session 模式会被别的作业抢走**）。
- 所以生产上要三件套一起算：**并行度 × Slot 数 × TM 数**，并给 `maxParallelism` 留余量（见题 3 与 [[9-部署与运维]]）。

**答案要点**：JM 的**单点属性**是理解 HA 的起点；Slot Sharing 与算子链是**性能与资源效率**的起点；三层执行图是理解"为什么 UI 上的算子数和代码里的不一样"的起点。

→ 详见 [[1-架构与运行时]]

### 题 2：时间语义与 Watermark

**得分骨架**

1. Flink 有三种时间：**事件时间**（数据自带的时间戳，结果可重放）、**处理时间**（系统时间，最快但不一致）、**摄入时间**（进入 Flink 的时刻，介于两者之间）。
2. **Watermark 是"事件时间已经推进到某个点"的承诺**：它不是一个字段，而是**给每条记录分配的时间戳 + 一个单调递增的水位线**。
3. Watermark 的语义是"**时间戳 ≤ 该水位的所有数据（理论上）都已经到了**"，所以窗口可以在 watermark 越过窗口结束时间时触发。
4. 生成方式：`WatermarkStrategy` = **时间戳分配器 + 水位生成器**，常用 `forBoundedOutOfOrderness(Duration)` 容忍乱序。
5. **空闲分区**会让 watermark 卡住（多分区里有一个长期没数据，水位取 min 就永远不推进），要用 `withIdleness(...)` 标记空闲。

**深入追问：迟到数据怎么办？（迟到数据三件套）**

| 手段 | 机制 | 代价 |
| --- | --- | --- |
| **Watermark 延迟（乱序容忍）** | 水位落后最大事件时间一段时间 | 结果延迟增加 |
| **`allowedLateness`** | 窗口触发后**继续保留状态**，迟到的数据会**再次触发**窗口输出（结果是更新/追加） | 状态存活时间变长；下游必须能处理重复/更新 |
| **侧输出流（Side Output）** | 超过 `allowedLateness` 的记录被丢到侧流，单独处理 | 需要额外处理逻辑，但**数据不丢** |

> [!important] `allowedLateness` 和侧输出流的区别（高频追问）
> - `allowedLateness` 是**"再等一会儿，等到了就重新算"**：窗口状态继续保留，迟到数据参与计算，窗口会**再次输出**。
> - 侧输出流是**"不要再等了，但我也不丢，另开一条路给你"**：数据被分流出去，由你决定怎么补（通常是回灌到下游做修正或人工排查）。
>
> 生产上典型组合：**`withIdleness` + 适度 `allowedLateness` + 侧输出流兜底 + 下游 upsert 幂等**。

**答案要点**：Watermark 的核心矛盾是**延迟与完整性的权衡**——等得越久越完整，但结果越晚。面试官想听的是你知道这个 tradeoff 存在，并且知道三种手段各自的代价。

### 题 3：状态管理与状态后端

**得分骨架**

1. Flink 的状态分两类：**Keyed State**（按 key 分区，只有 `keyBy` 之后能用，如 `ValueState`/`ListState`/`MapState`）和 **Operator State**（算子实例级，如 Source 的位点，重分布策略有 even-split / union）。
2. 状态的**最小组织单位是 key group**：`key → key group → subtask`，这决定了**扩缩容能力**。
3. **HashMapStateBackend**（原 MemoryStateBackend/FSStateBackend 路线）：状态在**堆内存**里，读写快，受限于堆大小和 GC。
4. **EmbeddedRocksDBStateBackend**：状态在**堆外（native 内存）+ 本地磁盘**，**支持增量 Checkpoint**，能支撑 TB 级状态，代价是读写要序列化、比堆慢。
5. 状态治理三件事：**TTL（防膨胀）+ 状态大小监控（看趋势）+ 倾斜检查（看单 key 热点）**。

**深入追问：怎么选状态后端？**

| 场景 | 选择 | 理由 |
| --- | --- | --- |
| 状态小（几 GB 以内）、追求低延迟 | HashMap | 无序列化开销，延迟最低 |
| 状态大（几十 GB ~ TB）、或状态增长不可控 | **RocksDB** | 突破了堆内存限制，增量 Checkpoint 让快照成本可控 |
| 状态中等但希望 Checkpoint 快 | RocksDB + `state.backend.incremental: true` | 增量快照只传变更的 SST 文件 |
| 定时器极多（每个 key 多个 timer） | RocksDB | 定时器也存在状态里，堆内容易被 timer 撑爆 |

> [!warning] 三个常见误区
> 1. **"RocksDB 一定慢所以不要用"** —— 错。状态规模决定选择。堆内存扛不住时，HashMap 的表现是频繁 Full GC 甚至 OOM，比 RocksDB 慢得多（甚至直接挂掉）。
> 2. **"状态 TTL 是万能的"** —— TTL 只对 Keyed State 生效，且默认是**惰性清理**（访问时才判断过期），状态可能实际比预期更久不释放。要真正清理需配合 `cleanupInBackground` 等策略，并且彻底清掉还得靠 RocksDB 的 compaction。
> 3. **"状态膨胀就是加内存"** —— 加内存只是拖延。真正的解法是**找膨胀源**：无 TTL 的 join 状态、不断累积的 ListState、长窗口、热点 key。

**答案要点**：说完两类状态 + 两种后端，一定要主动接一句**"状态膨胀怎么治"**——这是面试官判断你有没有运维经验的分水岭。

→ 详见 [[3-状态管理]]

### 题 4：Checkpoint 原理与 Barrier 对齐

**得分骨架**

1. Checkpoint 基于 **Chandy-Lamport 分布式快照算法**：JobManager 定期向 Source 注入 **Barrier**，Barrier 随数据流向下游传播。
2. 每个算子收到**所有输入流的 Barrier** 后，把当前状态快照异步上传到持久化存储，然后把 Barrier 转发给下游。
3. **对齐（Aligned）**：算子必须等所有输入的 Barrier 到齐才能快照，期间**后到的分区的数据被阻塞**（放在缓冲里）——**反压下对齐会非常慢**。
4. **非对齐（Unaligned）**：Barrier 直接越过正在传输的数据（数据被一起快照进去），不需要等待——**反压下快得多**，代价是快照体积更大、恢复时重放更多。
5. **Checkpoint 是自动的、周期性的、故障后自动恢复**；**Savepoint 是手动的、语义化的、用于有计划的重启/升级**。

**深入追问一：增量 Checkpoint 是什么？**

RocksDB 的增量 Checkpoint **只上传自上次 Checkpoint 以来新增的 SST 文件**（并引用未变的旧文件），而不是把整个状态重新写一遍。所以状态越大，增量 Checkpoint 的相对收益越明显。**HashMapStateBackend 不支持增量 Checkpoint。**

**深入追问二：Checkpoint 和 Savepoint 的区别（必问）**

| 维度 | Checkpoint | Savepoint |
| --- | --- | --- |
| 触发者 | 框架自动（按间隔） | 用户手动（CLI / REST / Operator） |
| 生命周期 | 可被自动清理，默认取消作业即失效（除非配 externalized retention） | 长期保留，需显式 `--dispose` |
| 格式 | 与状态后端强相关的内部格式，可能随版本变化 | **与状态后端解耦的规范化格式**，用于跨版本/跨后端迁移 |
| 主要用途 | 故障恢复 | **升级、扩缩容、迁移、备份** |
| 并行度 | 恢复时未必要改 | 支持扩缩容恢复 |

**答案要点**：**"对齐 vs 非对齐"是最能体现深度的一问**——要点是"对齐在反压下会阻塞数据流，非对齐用空间换时间"。

→ 详见 [[5-Checkpoint与Savepoint]]

### 题 5：怎么保证 Exactly-Once

**得分骨架**

端到端 Exactly-Once 是**三段式**，缺一段都不成立：

1. **Source 端可重放**：数据源（Kafka offset / CDC binlog 位点）作为**算子状态进 Checkpoint**，故障后从记录的位点重新消费。
2. **中间状态可恢复**：Checkpoint + Barrier 保证算子状态回到一致的快照点，**计算在 Flink 内部不会重复也不会丢**。
3. **Sink 端去重或事务提交**：
   - **两阶段提交（2PC）**：Sink 先预写（事务打开），等 Checkpoint 完成后再提交。失败则回滚，实现精确一次。
   - **幂等写**：靠下游主键 upsert（Doris/StarRocks Unique Key、Kafka 的幂等生产者 + 去重键），重复写被覆盖吸收。
4. **`AT_LEAST_ONCE` 与 `EXACTLY_ONCE` 的差别只在第 3 段**：至少一次不保证不重复，但因为没有"等 Checkpoint 再提交"的同步开销，**吞吐更高、延迟更低**。
5. 生产上常说"我们用的是 Exactly-Once"，实际含义通常是 **Flink 内部精确一次 + 下游主键幂等**，而不是严格的 2PC。

**深入追问：Kafka Sink 怎么做 Exactly-Once？**

- Flink 的 `KafkaSink` 支持 **`DeliveryGuarantee.EXACTLY_ONCE`**：每个 Checkpoint 对应一个 Kafka 事务，Checkpoint 完成时提交事务，失败时中止。
- 关键代价：**必须开启事务超时相关配置，并且下游消费者必须隔离级别为 `read_committed`**（否则会读到未提交数据）；事务与 Checkpoint 间隔耦合，**Checkpoint 太慢会导致事务超时**（`transaction.timeout.ms` 不够）。
- 所以很多团队选的是 **`AT_LEAST_ONCE` + 下游幂等**，反而更稳。

**答案要点**：**"Exactly-Once 需要下游配合"** 是本题的灵魂。说"Flink 保证了 Exactly-Once"而不提下游，会被直接判定为背书。

### 题 6：背压原理与调优

**得分骨架**

1. 背压是**下游处理不过来，反压传导到上游**的自然现象，Flink 里靠**基于 Credit 的流控**实现：下游向上游声明"我还有多少缓冲可用（credit）"，上游按 credit 发送，credit 用完就暂停。
2. **背压本身不是问题，持续背压才是问题**。偶发尖峰是正常的削峰行为。
3. 定位方法：在 **Flink Web UI 或指标**里**从 Sink 往 Source 方向逐算子看** `backPressuredTimeMsPerSecond`，**找到第一个背压高而下游不背压的算子**，那就是瓶颈。
4. 常见瓶颈只有四类：**Sink 慢（外部系统）、数据倾斜（单 key 打爆）、GC 停顿（堆压力）、算子本身低效（同步阻塞调用）**。
5. 解法对应：批量/异步写 Sink、打散热点 key、调内存/换 RocksDB、异步 IO、加并行度。

**深入追问：为什么"加并行度"不总能解决背压？**

- 如果是**数据倾斜**，加并行度只是把热点 key 分到更多 subtask 上，**同一个 key 仍然只在一个 subtask**，热点依旧。
- 如果是**下游外部系统的写入配额限制**（比如 Doris 单表导入吞吐上限），加并行度反而把下游打死。
- 如果是 **GC**，加并行度会让每个 TM 跑更多任务，堆压力更大，可能更糟。

> [!tip] 背压排查的正确顺序
> **先看是不是 Sink 的问题**（外部系统慢是最常见的）→ **再看倾斜**（看各 subtask 的 `numRecordsIn` 是否严重不均）→ **再看 GC**（`Heap.Used` 是否长期贴顶）→ **最后才是"加资源"**。
> 反过来的顺序（先加并行度）会让你在错误的路上花掉一周。

**答案要点**：一定要能说出**"从 Sink 往 Source 找第一个背压算子"**这个方法，以及**"倾斜不能靠加并行度解决"**这个反直觉结论。

→ 详见 [[6-背压与性能调优]]

### 题 7：Flink SQL 双流 Join 与状态膨胀

**得分骨架**

1. Flink SQL 的双流 Join 有三种：**Regular Join**（普通 join，两侧都保留全部历史状态，**状态无界增长**）、**Interval Join**（限定时间区间，状态可自动清理）、**Temporal Join**（按时间版本 join 维表，保留维表版本历史）。
2. **Regular Join 是状态膨胀的头号元凶**：两个流都全量保留，跑几天状态就爆了。
3. 因此 **`table.exec.state.ttl` 是双流 join 的必配项**，它决定了状态多久没被访问就过期。
4. `table.exec.state.ttl` 的代价：**过期状态被清理后，对应的历史数据 join 不上**，结果可能不准——**这是用准确性换稳定性**，必须和业务确认。
5. 更优的做法是**用 Interval Join 或窗口聚合替代 Regular Join**，让状态天然有界。

**深入追问：三种 Join 怎么选？**

| 类型 | 状态边界 | 结果准确性 | 适用 |
| --- | --- | --- | --- |
| **Regular Join** | ❌ 无界（除非配 TTL） | 最准（有 TTL 时不准） | 两侧数据量都不大、或能配合理 TTL |
| **Interval Join** | ✅ 有界（时间区间内的数据才保留） | 区间内的最准，区间外的 join 不上 | 两条流时间相近（如订单流与支付流） |
| **Temporal Join** | ⚠️ 取决于维表版本保留策略 | 按事件时间取维表当时的版本，语义正确 | 事实流 join 维度表（拉链表/changelog 维表） |

> [!danger] `table.exec.state.ttl` 不是"配了就没事"
> 它带来的是**静默的不准确**：状态过期后，晚到的另一侧数据匹配不到，结果里就少了一条关联。这类问题不会报错，只会让报表数字慢慢偏掉。
>
> 正确姿势：**给业务定一个"join 最大时间跨度"**（比如"订单和支付必须在 24 小时内匹配"），TTL 就按这个跨度设，超过这个跨度的不匹配本身就是业务上可接受的。

**答案要点**：主动说出**"Regular Join 状态无界，必须配 TTL；能用 Interval Join 就别用 Regular Join"**，这一句就够拿分。

→ 详见 [[8-FlinkSQL与TableAPI]]

### 题 8：Flink CDC 与实时数仓架构

**得分骨架**

1. **CDC = 把数据库的变更日志变成流**。基于日志的 CDC（binlog/WAL）**实时、对源库压力小、能捕获删除、不需要业务配合**，所以生产只用它。
2. Flink CDC 底层是 **Debezium**：伪装成 MySQL 从库订阅 binlog，先做全量快照、再从对应位点追增量。
3. **增量快照（incremental snapshot）**：按主键分片并行读，每个分片记录读取前后的 binlog 位点，分片读完后继续消费该区间的变更 —— **一致性靠"日志补齐"而不是靠锁**，所以能做到**不停机、不锁表**。
4. **断点续传**：位点 + 已完成分片都是**算子状态**，写进 Checkpoint；恢复时已完成的分片不重跑。
5. 实时数仓分层：**ODS（贴源/CDC 流）→ DWD（清洗 + 维表打宽）→ DWS（轻聚合）→ ADS（应用指标）**，下游必须是 **upsert sink**（Unique Key 模型）才能吸收 changelog。

**深入追问：CDC 链路怎么保证不丢不重？**

- **不丢**：binlog 位点进 Checkpoint，故障后从位点续消费。
- **不重**：Flink 内部由 Checkpoint 保证；端到端由**下游主键 upsert**（或 Doris label 幂等 / 2PC）保证。
- **唯一的硬约束**：源库 binlog 的保留时长必须大于最长恢复窗口，否则位点失效、无法重放 —— 这是运维上必须和 DBA 确认的一条。

**答案要点**：把"**不停机不锁表的原理是分片 + 位点区间变更回放**"讲清楚，就超过了 80% 的候选人（很多人只会背"Flink CDC 支持全量和增量"）。

→ 详见 [[7-FlinkCDC与实时数仓]]

## 三、快问快答表

> 面试官快速连问时用，**答案控制在一两句话**。

| # | 问题 | 一句话答案 |
| --- | --- | --- |
| 1 | Flink vs Spark Streaming 的核心区别 | Flink 是**真流**（逐条处理、事件驱动），Spark Streaming 是**微批**（按 batch interval 切）；Flink 延迟到毫秒/亚秒，Spark 至少一个 batch interval |
| 2 | 微批和真流对故障恢复的影响 | 微批的"一批"天然是一个恢复单元；Flink 靠 **Checkpoint + Barrier** 做全局一致快照，恢复粒度更细 |
| 3 | Task Slot 和并行度的关系 | Slot 是 TM 的资源切片，并行度是算子的任务数；**总并行度需求 ≤ Slot 总数**，Slot Sharing 让一个 Slot 跑一条完整链 |
| 4 | `maxParallelism` 的作用 | 决定 **key group 的总数**，从而决定并行度的**扩容上限**；一旦设定不能改（改了就恢复不了 Savepoint） |
| 5 | 为什么生产要显式设 `maxParallelism` | 不设的话框架按首次并行度推一个默认值，**未来的扩容天花板不可预知** |
| 6 | Watermark 为什么不推进 | 常见原因：**有分区空闲**（取 min 被拖住，用 `withIdleness`）、上游某条流卡住、数据源没数据、时钟/时间戳异常 |
| 7 | `allowedLateness` 和侧输出流的区别 | `allowedLateness` 保留窗口状态、迟到数据**重新触发窗口**；侧输出是**把超期数据分流出去**，不丢但要自己处理 |
| 8 | 为什么用 RocksDB | 状态大到堆扛不住时必须用；支持**增量 Checkpoint**，快照成本与状态增量而非全量相关 |
| 9 | RocksDB 的代价 | 读写要序列化/反序列化，**延迟高于堆内状态**；依赖本地磁盘 IO |
| 10 | Checkpoint 存在哪 | 存在 `state.checkpoints.dir` 指向的**持久化存储**（S3/HDFS）；本地目录只是临时中转 |
| 11 | Aligned vs Unaligned Checkpoint 怎么选 | 反压严重、对齐耗时占比高 → 用**非对齐**（用更大快照换更快完成）；正常情况用对齐即可 |
| 12 | 为什么 `AT_LEAST_ONCE` 更快 | 不需要等 Barrier 对齐、不需要等 Checkpoint 完成才提交，**少了同步等待和事务开销**，代价是可能重复 |
| 13 | Savepoint 的用途 | **有计划的重启**：升级、扩缩容、迁移、改逻辑；与状态后端解耦、可跨版本 |
| 14 | Checkpoint 能当 Savepoint 用吗 | 一般不。Checkpoint 是内部格式、会被自动清理；`last-state` 升级模式是利用 HA 元数据里的 Checkpoint，是特例 |
| 15 | 算子链（Operator Chaining）是什么 | 把满足条件的算子合并成一个 Task，**减少线程切换和序列化**；用 `disableChaining()`/`startNewChain()` 可干预 |
| 16 | 什么时候要断开算子链 | 想让某算子独占资源、或某算子有明显性能差异需要单独观察/调优时 |
| 17 | `flink run -d` 是什么 | **detached 模式**，提交后客户端立即退出，作业在集群后台运行；不加 `-d` 则客户端会阻塞并打印进度 |
| 18 | 状态后端和状态是不是一回事 | 不是。**状态是逻辑概念（Keyed/Operator State），状态后端是"状态存在哪、怎么存"的实现**，两者解耦，可通过 Savepoint 迁移 |
| 19 | TaskManager 内存模型的关键分区 | Task Heap（用户代码/堆内状态）、**Managed Memory（给 RocksDB）**、Network Memory（网络缓冲）、Metaspace、**JVM Overhead** |
| 20 | 容器为什么会被 OOMKilled | 通常是 **JVM Overhead 不够**（`process.size` 之外的 JVM 开销超容器 limit），而不是堆不够；堆不够会抛 Java OOM 异常 |
| 21 | 数据倾斜怎么发现 | 看各 subtask 的 `numRecordsIn`/`numBytesIn` 是否严重不均；反压只集中在少数 subtask |
| 22 | 数据倾斜怎么解决 | 热点 key 加盐打散 + 二次聚合；两阶段聚合；或者业务上换 key |
| 23 | 异步 IO 的顺序语义 | `AsyncDataStream.orderedWait` **保序**（吞吐受限），`unorderedWait` **不保序但吞吐高**；还要设**超时和容量上限** |
| 24 | `table.exec.state.ttl` 的作用 | 给 SQL 作业的状态设过期时间，**防止双流 join 等场景状态无界膨胀**；代价是过期后 join 不上 |
| 25 | key group 和扩缩容的关系 | 状态按 key group 存储，扩缩容只是**重新分配 key group**；所以只要 key group 够多就能扩，上限就是 `maxParallelism` |
| 26 | 为什么`flink stop` 比 `cancel` 安全 | `stop` 会**先优雅停止 Source 并打 Savepoint**；`cancel` 默认直接杀，可能丢数据 |
| 27 | Application 模式好在哪 | `main()` 在集群（JM）执行，**客户端只负责提交**；一个 Application 一个集群，隔离好，是生产首选 |
| 28 | Per-Job 模式为什么被淘汰 | 1.15 起弃用；`main()` 仍在客户端执行，能力被 **Application 模式完全覆盖** |
| 29 | Kafka Source 提交 offset 就能恢复吗 | **不能**。恢复只依赖 Checkpoint 里的位点；Kafka 的 offset 提交只是为了外部监控，不参与恢复 |
| 30 | 怎么判断一条链路是不是端到端 Exactly-Once | 看三段：Source 位点进状态？Checkpoint 开了？**Sink 是 2PC 或幂等**？三段齐才是 |
| 31 | 周期性重启策略有哪些 | `fixed-delay`、`exponential-delay`、`failure-rate`、`fallback`；生产推荐 `exponential-delay` 防止打爆下游 |
| 32 | 一个 Slot 能跑几个 Task | 默认 Slot Sharing 下，**同一 Job 的一条完整算子链**可以放进一个 Slot；不同 Job 不能共享 Slot |
| 33 | 背压和反压是一回事吗 | 是，backpressure 的两种译法；Flink 通过 **credit-based 流控**实现 |
| 34 | `setParallelism` 调大是不是一定更快 | 不是。受**下游吞吐上限、数据倾斜、Slot 总数、GC**制约，盲目调大往往更慢 |

## 四、易错陷阱 TOP 10

> 格式：**❌ 错误说法 → ✅ 正确说法**。这些是最容易在面试里"说出口就被扣分"的点。

### 陷阱 1：Kafka source 提交了 offset 就能恢复

- ❌ "我们的作业把 offset 提交到 Kafka 了，所以挂了能接着消费。"
- ✅ **恢复只依赖 Checkpoint 里的位点。** Flink 的 Kafka Source 从 Checkpoint/Savepoint 中的状态恢复 offset；向 Kafka 提交 offset 只是为了外部监控（或别的消费者），**它不参与 Flink 的故障恢复**。
- 补充：这也是为什么"从空状态启动 + `latest-offset`"会丢掉停机期间的数据，而"从空状态启动 + `earliest-offset`"会全量重放导致重复。

### 陷阱 2：EXACTLY_ONCE 不需要下游配合

- ❌ "我们在 Flink 里配了 EXACTLY_ONCE，所以整条链路精确一次。"
- ✅ **端到端精确一次必须 Sink 也支持**：要么两阶段提交（2PC），要么幂等写（下游主键 upsert）。只配 `execution.checkpointing.mode = EXACTLY_ONCE` 保证的是 **Flink 内部**状态一致，Sink 仍可能重复写。
- 补充：能主动说出"我们实际是 Flink 内部 EO + 下游主键幂等"会显得很真实可信。

### 陷阱 3：有背压就一定有问题

- ❌ "监控看到背压了，说明作业有性能问题。"
- ✅ **偶发背压是正常的削峰行为，持续背压才是问题。** 要告警的是"持续 N 分钟背压高于阈值"，而不是每一次尖峰。
- 补充：反过来，**完全没有背压也不一定是好事**——可能是上游没数据，或者瓶颈在别的环节（比如 Source 的 lag）。

### 陷阱 4：RocksDB 一定比堆内存慢，所以不要用

- ❌ "RocksDB 性能差，我们状态小，用堆就行。"
- ✅ **选择取决于状态规模。** 状态小、追求低延迟 → 堆（HashMap）；状态大或增长不可控 → RocksDB（否则频繁 Full GC 甚至 OOM，比 RocksDB 慢得多，甚至直接崩）。
- 补充：RocksDB 的**增量 Checkpoint** 在大状态下是决定性的优势。

### 陷阱 5：watermark 是数据里带的一个字段

- ❌ "数据里有 watermark 字段，读到它就知道进度。"
- ✅ **Watermark 不是数据里的字段。** 它是"**给每条记录分配事件时间戳 + 一个单调递增的水位线**"的组合机制：时间戳分配器给记录打时间戳，水位生成器基于观察到的最大时间戳推进水位，水位作为一条**特殊的流内标记**向下游传播。
- 补充：水位只能**单调不减**地推进，乱序数据不会让水位回退。

### 陷阱 6：Savepoint 就是 Checkpoint

- ❌ "Savepoint 就是一个手动触发的 Checkpoint，一样的。"
- ✅ 触发方式不同只是表象，本质区别是 **格式与用途**：Checkpoint 是**与状态后端强绑定的内部格式**、会被自动清理、主要给故障恢复用；Savepoint 是**与状态后端解耦的规范化格式**、长期保留、用于**升级/扩缩容/迁移**（因此可跨版本、可改并行度）。
- 补充：`externalized-checkpoint-retention` 让 Checkpoint 也能保留，但格式仍是内部格式，不等于 Savepoint。

### 陷阱 7：并行度可以随便改

- ❌ "扩容就是把并行度从 8 调到 16，重启就行。"
- ✅ 受两件事限制：
  1. **`maxParallelism`** 决定 key group 总数，**并行度不能超过它**；而且 `maxParallelism` 本身**一旦设定就不能改**（改了 Savepoint 恢复直接失败）。
  2. **算子 UID 与状态结构**必须保持兼容，否则恢复失败。
- 补充：还有一个硬条件 —— **集群得真的有那么多 Slot**。

### 陷阱 8：Flink SQL 双流 join 不用管状态

- ❌ "SQL 里写个 join 就行，Flink 会自己管状态。"
- ✅ **Regular Join 的状态是无界的**（两侧都保留全部历史），跑几天状态就会爆。**必须配 `table.exec.state.ttl`**，或者改用 **Interval Join / Temporal Join / 窗口聚合**让状态天然有界。
- 补充：配了 TTL 就接受了"超出跨度的关联会丢"，这是用准确性换稳定性，要和业务确认。

### 陷阱 9：把 `--allowNonRestoredState` 当恢复失败的万能解药

- ❌ "恢复报错加个 `--allowNonRestoredState` 就好了。"
- ✅ 它会**静默跳过所有无法映射的状态**——作业是起来了，但可能丢了关键状态（比如去重用的 Keyed State），后果是下游**悄悄多出一批重复数据或结果错误**，而且不报错。
- 补充：只在**明确知道哪些状态可丢**（纯缓存、可重建）时才用，并记录清楚丢了什么。

### 陷阱 10：作业卡在 `CREATED` 就是 Flink 的 bug

- ❌ "提交了但一直不 RUNNING，得重启集群。"
- ✅ 绝大多数是**资源或权限**问题：
  - Slot 不够（并行度 > 可用 Slot）
  - K8s 上 **`kubernetes.jobmanager.service-account` 没配或 RBAC 不足**（JM 无法创建 TM Pod，日志里有 403）
  - `local://` 指的 jar 在镜像里不存在
  - 内存配置冲突（`process.size` 与容器 `resource.memory` 不一致）
- 补充：排查入口是 **JM 日志 + `kubectl describe pod` + `kubectl get events`**，不是重启。

> [!tip] 陷阱题的回答公式
> 遇到"是不是/对不对"型问题，标准结构是：
> **"不完全对（或：有一个前提）。正确的说法是 X。原因是 Y。我们在生产上遇到的情况是 Z。"**
> 直接说"错"会显得生硬，说"对"就直接掉坑。

## 五、场景设计题

> 这类题没有标准答案，考的是**框架完整性**。答题时先给框架，再按框架逐条填。

### 场景 1：设计一个「Kafka → Flink → Doris」的实时链路

**答题框架（六步）**

**① 需求澄清（一定要先问）**

| 要问清的问题 | 影响的设计决策 |
| --- | --- |
| 数据量多大（QPS / 日增行数）？ | 并行度、状态后端、Doris 分区分桶 |
| 延迟目标（秒级 / 分钟级）？ | Checkpoint 间隔、窗口大小、是否用微批 |
| 结果是明细还是聚合？ | 表模型（Unique Key / Aggregate Key） |
| 能不能容忍重复/少量不准？ | 是否需要 2PC，还是主键幂等即可 |
| 有没有对账要求？ | 是否需要离线和实时对账机制 |

**② 分层设计**

```
Kafka（ODS：原始事件，开启 compaction 保留回放能力）
   ↓
Flink DWD 作业：清洗、去重、维表打宽（Lookup Join）
   ↓
Flink DWS 作业：窗口聚合（TUMBLE/HOP）
   ↓
Doris：DWD 明细表（Unique Key）+ DWS 聚合表（Aggregate/Unique）
   ↓
ADS：BI / 指标服务
```

关键取舍：**DWD 和 DWS 串在一个作业还是拆成两个？** 串起来延迟低、少一次落地，但状态大、故障影响面大、扩缩容难；拆开解耦、可独立扩缩容，但延迟 +1 跳。**大促场景建议拆开**（可分别扩容）。

**③ 幂等与一致性**

- Checkpoint：`EXACTLY_ONCE` + `externalized-checkpoint-retention = RETAIN_ON_CANCELLATION`
- Doris Sink：**Unique Key + Merge-on-Write**，配 `sink.label-prefix` 做事务幂等，开启 2PC（如连接器支持）
- 维表：Lookup Join 配缓存（`lookup.cache.max-rows` / `ttl`），或维表 CDC 进状态做 Temporal Join
- 全链路对账：T+1 与离线结果按同一口径比对（这是"防静默错误"的最后一道网）

**④ 资源配置**

- 先算并行度：目标吞吐 / 单并行度实测吞吐，再乘 1.5 冗余
- **显式设置 `pipeline.max-parallelism`**（留 2~4 倍扩容空间）
- 内存：`process.size` 给足 + RocksDB 场景 managed memory 占比调大
- Slot 数 × TM 数 ≥ 最大并行度

**⑤ 监控与告警**

- 作业级：重启次数、Checkpoint 成功率/时长/大小
- 算子级：`numRecordsInPerSecond`、`currentEmitEventTimeLag`、`backPressuredTimeMsPerSecond`
- Kafka lag（用 kafka-exporter 或 `kafka-consumer-groups.sh` 采集）
- 业务级：**Doris 表行数与上游对账、关键指标波动告警**（技术指标正常但业务指标异常，往往说明逻辑问题）

**⑥ 运维预案**

- 升级方案：Savepoint → 停 → 新版恢复 → 指标验证 → 保留回滚点
- 止损方案：作业放飞了用 `flink cancel`；需要保状态用 `flink stop`
- 降级方案：DWS 聚合窗口放大（1 分钟 → 5 分钟）、维表改本地缓存、非核心指标停算

> [!example] 加分句
> "我们会在 Doris 那边保留一份**对账表**，每小时用 Flink 批模式把实时结果和明细重新算一遍做比对。**纯技术的监控只能发现'作业挂了'，发现不了'数据算错了'。**"

### 场景 2：一个作业跑几天后 Checkpoint 越来越慢、状态越来越大，怎么排查

**答题框架（五步，按成本从低到高）**

**第一步：确认现象与趋势**

- 看 `lastCheckpointSize` 是否**单调增长**（膨胀），还是稳定但在某一刻跳变（某类数据引入）
- 看 `lastCheckpointDuration` 是**均匀上升**（状态大）还是**抖动剧烈**（反压/存储抖动）
- 看 `numberOfFailedCheckpoints` 是否开始出现失败
- **先确认"什么时候开始变慢的"**，对比那个时间点有什么变更（上游 DDL、发版、流量变化）

**第二步：定位是哪部分状态在涨**

- 在 Flink UI 的 Checkpoint 详情里**按算子看 state size**，找出增长最快的那几个算子
- 常见元凶：
  - **Regular Join 状态**（两侧全量保留）
  - **聚合算子的 keyed state**（`GROUP BY` 高基数维度，key 数无限增长）
  - **去重用的 MapState**（没有 TTL）
  - **窗口算子 + 大 `allowedLateness`**（窗口状态保留过久）
  - **定时器过多**（timer 也在状态里）

**第三步：区分"状态大"和"快照慢"**

| 现象 | 根因 | 方向 |
| --- | --- | --- |
| 状态大 + 快照耗时同比上升 | 状态膨胀 | 加 TTL / 换更省的算子 / 拆分作业 |
| 状态稳定但快照慢 | **反压**导致 Barrier 对齐慢 | 看 `backPressuredTimeMsPerSecond`，优化瓶颈算子；考虑非对齐 Checkpoint |
| 状态稳定、无背压但快照慢 | **存储侧慢**、并发冲突 | 看对象存储延迟、`min-pause` 是否太小导致重叠 |
| 快照大小远大于预期 | RocksDB 未 compaction、增量快照失效 | 检查 RocksDB 本地磁盘与 `state.backend.incremental` |

**第四步：治理**

- **加状态 TTL**：SQL 用 `table.exec.state.ttl`，DataStream 用 `StateTtlConfig`；**前提是和业务确认可接受的时间跨度**
- **改算法**：Regular Join → Interval Join；全量去重 → 布隆过滤器 / 有界 LRU；大窗口 → 小窗口 + 增量聚合
- **拆分作业**：把状态最大的那部分独立出来，单独扩缩容
- **降级**：热点 key 打散；必要时清理历史（**从空状态重启 + 下游幂等重建**，但要评估重放量）

**第五步：验证与防复发**

- 治理后观察 `lastCheckpointSize` 是否**转为平稳**（不是变小，而是不再单调增长）
- 加上**状态大小的趋势告警**（增长率，而不是绝对值）
- 复盘记录：把这次的膨胀源写进 runbook

> [!important] 加分点
> "状态大小**绝对值大不是问题，单调增长才是问题**。一个稳定在 50G 的状态是可以接受的，一个从 5G 涨到 50G 的状态一定有问题。所以我们的告警看的是**增长率**。"

---

### 场景 3：大促流量突增 10 倍，怎么让作业撑住

**答题框架（按时间线：事前 / 事中 / 事后）**

**① 事前准备（最重要，占 80% 的价值）**

| 动作 | 具体做法 |
| --- | --- |
| **压测** | 用历史峰值 ×N 倍做全链路压测，找出真正的瓶颈算子（不是猜） |
| **预留扩容空间** | 确认 `maxParallelism` 允许扩到目标并行度；**这是唯一无法临时补救的项** |
| **验证 Savepoint 恢复** | 提前演练"停 → 起"的完整流程，确认能恢复、恢复要多久 |
| **资源预扩** | 提前申请 Slot/节点（K8s 可以提前扩容节点池），避免大促当天排不上 Pod |
| **降级预案** | 明确"先停哪个指标、窗口放多大、维表怎么降级"，并写进 runbook |
| **监控加固** | 提高关键告警灵敏度；准备大促看板 |
| **上游限流协商** | 和上游约定：超阈值时限流/采样/写死信队列，而不是打爆 Flink |

**② 事中应对（按优先级）**

1. **先看能不能加并行度**：确认 Slot 够 → 从 Savepoint 恢复并调大 `-p`（注意 key group 重分配会有一小段恢复时间）
2. **看瓶颈在哪**：如果瓶颈是 Sink（Doris/StarRocks 写入），加 Flink 并行度没用，要**优化 Sink 侧**：开批量、开 `partial_columns`/`partial_update`、加 Doris BE、调 Stream Load 并发
3. **处理背压**：定位第一个背压算子；如果是倾斜，立即对热点 key 打散
4. **降级非核心链路**：先停 ADS 层非核心指标、放大窗口（1 min → 5 min）、关掉非必要的维表关联
5. **上游限流/削峰**：Kafka 缓冲天然削峰，允许短暂 lag（**要提前算清楚"允许积压多久"**，因为 Kafka retention 有限）
6. **极端情况**：把非核心作业 `flink cancel` 腾出资源给核心作业（Session 模式下尤其需要）

**③ 事后**

- 复盘：真实峰值 vs 预估峰值、瓶颈在哪、扩容耗时多少
- 调整容量水位（大促期间的常驻冗余）
- 把这次的降级操作固化进 runbook

**④ 主动指出的反模式**

> [!warning] 大促期间不要做的事
> - **不要在高峰期改作业逻辑**（改逻辑 = 需要 Savepoint 重启 + 状态兼容风险）
> - **不要无脑加并行度**（受 `maxParallelism`、下游配额、倾斜制约，可能更糟）
> - **不要关 Checkpoint**（用"性能"换掉容错能力，一旦挂了就是全量重跑，得不偿失）
> - **不要把 `--allowNonRestoredState` 当救火工具**（会静默丢状态）

> [!example] 加分句
> "大促的真正准备发生在提前两周，不在当天。当天能做的只有扩容和降级——**如果 `maxParallelism` 没提前留够，当天连扩都扩不了**。"

## 六、面试前 10 分钟速记卡

> 只看这 10 条，进面试间前扫一遍。

1. **架构**：JobManager（调度/协调/HA 单点）+ TaskManager（Slot）+ Slot Sharing（一条链放一个 Slot）+ 算子链（省线程切换和序列化）。
2. **时间**：Watermark = 时间戳分配器 + 单调水位，不是字段；不推进先查**空闲分区**（`withIdleness`）；迟到数据三件套 = 水位延迟 / `allowedLateness` / 侧输出流。
3. **状态**：Keyed vs Operator State；**key group 是扩缩容的最小单位**；小状态用堆、大状态用 **RocksDB + 增量 Checkpoint**；状态一定要配 **TTL**。
4. **容错**：Chandy-Lamport + Barrier；**对齐**在反压下慢、**非对齐**用大快照换速度；Checkpoint 自动/内部格式，Savepoint 手动/规范化格式用于升级。
5. **Exactly-Once 三段式**：Source 位点进状态 → 中间 Checkpoint → **Sink 必须 2PC 或幂等**。缺一段就不是端到端 EO。
6. **背压**：credit-based 流控；**持续背压才是问题**；从 Sink 往 Source 找**第一个背压算子**；倾斜不能靠加并行度解决。
7. **SQL**：Regular Join **状态无界**，必须配 `table.exec.state.ttl`；能用 Interval/Temporal Join 就别用 Regular Join。
8. **CDC**：基于日志（binlog）优于轮询；**增量快照 = 分片 + 位点区间变更回放**，所以不停机不锁表；位点有效性取决于 **binlog 保留时长**。
9. **部署**：生产用 **Application 模式 + K8s Operator**；内存模型重点记 **Managed Memory 给 RocksDB**、**OOMKilled 多半是 JVM Overhead 不够**；**显式设 `maxParallelism`**。
10. **运维**：`stop`（优雅 + Savepoint）vs `cancel`（直接杀）；`flink run -d` 是后台提交；告警看**重启次数、Checkpoint 失败/变慢、持续背压、消费延迟**；**`--allowNonRestoredState` 不是万能解药**。

## 七、把这一篇串起来

> Flink 面试的胜负手不在"知不知道"，而在**"能不能把设计意图和代价讲清楚"**：
> - 每个机制都问自己"**它解决了什么问题、又付出了什么代价**"

>
> 这三问能答上来，面试官就会认为你**真的用过**，而不只是**看过**。
